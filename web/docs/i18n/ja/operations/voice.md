# 通話を運用する

通話では、ログインしているユーザーがルームを開き、ほかの人を招待して話せます。音声の伝え方を選ぶまで、通話は無効です。
このガイドでは、その選び方と、それぞれの方法に必要な STUN サーバーと TURN サーバー、またはメディアノード、そしてデプロイ、プライバシー、モデレーションについて知っておくことを説明します。
ここで名前を挙げる設定は、すべて[設定のリファレンス](../reference/configuration.md#voice)で説明しています。

<!-- source: choose-how-the-audio-travels 2ef72c636c49 -->
## 音声の伝え方を選ぶ

`voice` はインスタンス全体で 1 つの方法を選びます。すべてのルームがその方法を使います。

| `voice` | 音声を運ぶもの | 向いている場合 |
| --- | --- | --- |
| `off` | なし。通話の API は `404` を返し、Web クライアントには通話が表示されず、ほかの `voice_*` の設定は起動時に確認されません。 | 既定値です。 |
| `p2p` | 参加者のブラウザーが互いに直接音声を送ります。サーバーは、接続を確立するためのメッセージだけを中継します。 | 小さなルームと、いちばん安い構成。任意の STUN サーバーか TURN サーバーのほかに、追加のサーバーは要りません。 |
| `sfu` | サーバー自身のメディアノード。各ブラウザーは自分のルームを持つノードに音声を送り、ノードが話す人の音声を参加者に転送します。 | 大きなルームと、誰が話せるかの厳密な制御。 |

![2 つの方法を並べた図。p2p では、サーバーがシグナルを中継し、ブラウザーは互いに、または TURN サーバーを通して音声を送ります。sfu では、ブラウザーはサーバーから grant を受け取り、シグナルと音声を自分のルームのメディアノードに送ります。下の一覧が各方法を説明しています。](images/voice-methods.svg)

どの方法でも、サーバー（`my serve`）はルームと、その参加者とセッションを保持し、各参加者に grant（ブラウザーが接続するのに必要なもの）を
渡します。違うのは、シグナリング（接続を確立するためのメッセージ）と音声の行き先です。

- **`p2p`。** ブラウザーは自分のシグナル（オファー、アンサー、ICE 候補）をサーバーに送り、サーバーはそれをルームのイベントストリームで
  相手のブラウザーに渡します。シグナルはキーバリューストアで最大 30 秒待ちます。音声は
  ブラウザーからブラウザーへ直接届きます。grant には、`voice_stun_urls` の STUN サーバーと、`voice_turn`（`coturn` か `cloudflare`）の TURN サーバーが、
  有効期間の短い認証情報とともに入っています。ブラウザーは STUN で自分の公開アドレスを知り、
  2 つのブラウザーが直接の経路を見つけられないときは TURN サーバーが音声を中継します。
- **`sfu`。** サーバーは各ルームをメディアノード（選択的転送ユニット、SFU）に置きます。メディアノードは `role = all` か `sfu` のプロセスです。
  grant には、そのノードの `wss:` の URL（`voice_sfu_public_url`）と、1 回しか使えないチケットが入っています。
  ブラウザーはシグナルを WebSocket でノードに送り、音声をノードの UDP ポート `voice_sfu_udp_port`
  （UDP がふさがれているときは TCP の `voice_sfu_tcp_port`）に送ります。ノードは話す人の音声をほかの
  参加者に転送します。ノードに直接届かないブラウザーのためには、`voice_turn` の TURN サーバーが中継します。

選ぶときの注意点です。

- **`p2p`** では、サーバーに UDP ポートは要りません。音声がサーバーを通ることはなく（TURN サーバーを使うときは、TURN サーバーを通ります）、サーバーの負荷は、ルームのメッセージ、ハートビート、ストリームだけです。小さなインスタンス、小さなルーム、Cloud Run だけでのデプロイに向いています。
- **`sfu`** では、誰が話せるかをサーバーが強制します。ノードは話す人の音声だけを転送します。ブラウザーが接続するのはメディアノードだけなので、参加者の IP アドレスはノードには見えますが、ほかの参加者には見えません。ノードごとに、公開 IP を持つマシンと、開放した UDP と TCP のポートが必要です（[メディアノード](#media-nodes)）。ノードには公開アドレスがあるので `voice_stun_urls` は要らず、`voice_ice_transport_policy = relay` は拒否されます。
- インスタンスは HTTPS で配信してください。ブラウザーは、安全なページでしかマイクへのアクセスを許しません。

上限は、ルームの費用に歯止めをかけます。`0` にすると、最後のものを除いて上限がなくなります。

| 設定 | 既定値 | 意味 |
| --- | --- | --- |
| `voice_max_room_duration` | `4h` | ルームが開いていられる最長の時間です。これに達したルームは終了します。 |
| `voice_max_open_rooms` | `10` | このサーバーで同時に開いていられるルームの数です。予定の時刻に向けて開いたルームは、最初の参加者を待っている間も、開いた時点から数えます。 |
| `voice_max_participants` | `10` | 最大のルームの人数で、2 から 500 まで（`p2p` では 50 まで）指定できます。ホストは自分のルームにそれより小さい上限を設定できます。 |

ルームを開ける人は、インスタンスの設定 `voice_room_starters` で決まります（[インスタンスの設定](instance-settings.md)）。既定では、権限 `start_voice_rooms` を持つ人だけです（組み込みの `admin` ロールが持っています）。`everyone` にすると、ログインしているローカルユーザーのうち、凍結も制限もされていない人なら誰でもルームを開けます。

## ピアツーピアのルーム

<!-- source: try-it-with-docker-compose ac3681681768 -->
### Docker Compose で試す

Docker Compose の構成（[`deploy/docker/compose.yaml`](../../deploy/docker/compose.yaml)）で、自分のマシンで通話を試すには、
`.env` に `MY_VOICE=p2p` を設定してサーバーを作り直します。

```sh
cd deploy/docker
docker compose up -d
```

- インスタンスを `http://localhost:8080`（`example.env` の `MY_WEB_ORIGIN`）で開いてください。ブラウザーがページにマイクを使わせるのは
  `localhost` か HTTPS のときだけなので、`http://192.168.1.10:8080` のようなアドレスでは話せません。
- 同じマシンのブラウザー同士（2 つのブラウザーのプロファイル、または通常のウィンドウとプライベートウィンドウ）は、STUN サーバーも TURN
  サーバーもなしで接続します。ほかのマシンのブラウザーとつなぐには、インスタンスを HTTPS の後ろに置き、`.env` に `MY_VOICE_STUN_URLS` を設定してください。
- 既定では、ルームを開けるのは `admin` ロールだけです。作成した管理者としてログインするか、サーバー設定の「通話」のページで `voice_room_starters` を `everyone`
  にして、すべてのユーザーがルームを開けるようにしてください。

### 人数と帯域

2 つのブラウザーは、少なくとも一方が話しているときに互いに接続します。聞いているだけの 2 人は接続しません。
そのため、話す人はほかの参加者それぞれに、自分の音声の別々のコピーを送ります。Opus の音声はオーバーヘッドを含めておよそ 30 から 50 kbit/s なので、10 人のルームで話す人はおよそ 9 つのコピー、数百 kbit/s をアップロードし、
50 人のルームで話す人は 49 のコピー、2 Mbit/s 前後をアップロードします。これは、モバイルデータ通信のスマートフォンや家庭の回線では維持できないことがあります。N 人のルームの接続の数は最大 N(N-1)/2 で、10 人なら 45、50 人なら 1,225 です。
そのため既定値は 10 です。`voice_max_participants` は、ユーザーにアップロードの帯域があるときにだけ上げてください。大きなルームには `sfu` を使ってください。

<!-- source: stun-and-turn 51e427976a77 -->
### STUN と TURN

NAT の後ろのブラウザーには、自分の公開アドレスを知るための STUN サーバーと、直接の経路がないとき（厳しい NAT、企業のファイアウォール、一部のモバイルネットワーク）に音声を中継する TURN サーバーが必要です。

- `voice_stun_urls`: カンマ区切りの `stun:` か `stuns:` の URL。公開されている STUN サーバーならどれでも使え、下の coturn サーバーも STUN に応答します。
- `voice_turn`: `none`、`coturn`、`cloudflare` のいずれか。

どちらもない場合、サーバーは起動時に警告します。接続できるのは同じネットワークのブラウザーだけです。公開のインスタンスには STUN が、そして直接接続できないユーザーのために TURN が必要です。

サーバーは各参加者に有効期間の短い TURN の認証情報を渡し、共有のパスワードは決して渡しません。その有効期間は `voice_turn_credential_ttl`（既定値は `6h`）で決まります。Web クライアントは期限切れの 10 分前に新しい認証情報を求めて ICE を再開するので、期限が切れても通話は止まりません。

<!-- source: coturn d665e942c91b -->
#### coturn

`voice_turn = coturn`、`voice_turn_coturn_urls`、`voice_turn_coturn_secret` を設定します。サーバーは認証情報を自分で計算する（ユーザー名は有効期限とセッション ID、パスワードはそれをシークレットで計算した HMAC-SHA1）ので、TURN サーバーにリクエストを送りません。
coturn もそれに合わせて、`turnserver.conf` で設定します。

```conf
# Time-limited credentials signed with a shared secret.
use-auth-secret
static-auth-secret=<the same value as voice_turn_coturn_secret>
realm=turn.example.org

listening-port=3478
tls-listening-port=5349
# If the host is behind NAT (most cloud VMs), tell coturn its public address.
external-ip=203.0.113.10

# Do not let the relay reach your internal networks.
no-multicast-peers
denied-peer-ip=0.0.0.0-0.255.255.255
denied-peer-ip=10.0.0.0-10.255.255.255
denied-peer-ip=100.64.0.0-100.127.255.255
denied-peer-ip=127.0.0.0-127.255.255.255
denied-peer-ip=169.254.0.0-169.254.255.255
denied-peer-ip=172.16.0.0-172.31.255.255
denied-peer-ip=192.168.0.0-192.168.255.255
```

- `denied-peer-ip` は重要です。これがないと、認証情報を持つ誰もが、TURN サーバーを使ってその内部ネットワークのホスト（クラウドのメタデータサービス、データベース、ほかの VM）に届いてしまいます。プライベート、ループバック、リンクローカルの範囲をすべて拒否し、内部のアドレス（`allowed-peer-ip`）は、本当にそこへ中継する必要があるときにだけ許可してください。
- UDP と TCP の 3478、`turns:` 用の TCP 5349、coturn の中継用ポートの範囲（`min-port` / `max-port`、既定では 49152-65535）を開けてください。
- `voice_turn_coturn_urls` には、`turns:` の URL か `?transport=tcp` 付きの URL も加えてください。UDP をふさぐネットワークのユーザーも接続できるようになります。
- coturn が認証情報の有効期限を確認するのは、アロケーションを最初に作るときだけです。すでにあるアロケーションは期限を過ぎても動き続け、新しい認証情報は次のアロケーションから有効になります。次のアロケーションは、Web クライアントが ICE を再開して作ります。

<!-- source: cloudflare-turn be5846573be8 -->
#### Cloudflare TURN

Cloudflare のダッシュボードで作成した TURN キーから、`voice_turn = cloudflare`、`voice_turn_cloudflare_key_id`、`voice_turn_cloudflare_api_token` を設定します。サーバーは、参加者がルームを開くか参加するときにその参加者の認証情報を Cloudflare に求め（失敗した場合、リクエストは `503` を返し、何も開かず参加もしないので、やり直せます）、参加者が退出するか退出させられたときに取り消します。

- 認証情報の有効期間は最大 48 時間なので、`voice_turn_credential_ttl` は `48h` を超えられません（超えると、サーバーは起動しません）。
- **Cloudflare は、認証情報の期限が切れると間もなく中継を切断します。** Web クライアントはその前に更新するので、`voice_turn_credential_ttl` は 10 分より十分に長くしておいてください。
- 料金（2026-10-26 時点で確認）: 月の最初の 1,000 GB は無料で、それ以降はクライアントに送った 1 GB あたり $0.05 です。当てにする前に、Cloudflare の現在の料金を確認してください。

<!-- source: hiding-ip-addresses de67ffa9e7b7 -->
### IP アドレスを隠す

`voice_ice_transport_policy = all`（既定値）では、ブラウザーはできるときには直接接続するので、ルームの参加者は互いの IP アドレスを知ることがあります。

`relay` では、ブラウザーは TURN サーバーだけを使うので、参加者に見えるのは TURN サーバーのアドレスで、ほかの参加者のアドレスは見えません。音声はブラウザー間で暗号化されたままです。`relay` が隠さないもの: TURN サーバーを運用する人（あなたか Cloudflare）にはすべての参加者のアドレスが見え、このサーバーには、その API を呼び出すすべての人のアドレスが見えます。
`relay` には、`voice_turn` が `coturn` か `cloudflare` であることが必要です（そうでなければ、サーバーは起動しません）。また、すべての通話が TURN サーバーを通るので、coturn ではあなたの帯域を、Cloudflare では転送料金を使います。

<!-- source: what-p2p-cannot-enforce 4f97611bece5 -->
### P2P で強制できないこと

ルームで話せるのは一部の参加者、つまりホストと、ホストが許可したリスナーだけです。`p2p` では、これを 2 か所で強制します。話せない人から音声を送ることになる接続のオファーを、サーバーが中継しないことと、話す人ではない参加者からの音声を、ほかのブラウザーが再生しないことです。

これで一般のユーザーと公式の Web クライアントは止められますが、完全な防御ではありません。**改変したクライアントを使う 2 人の参加者が協力すれば、それでも音声をやり取りできます**。話せない人の改変したクライアントが音声を送り、受け手の改変したクライアントがそれを再生でき、サーバーは暗号化されたメディアの中身を見られません。
誰が話すかを保証しなければならない場合（たとえば、モデレーションされた公開のイベント）は、`sfu` を使ってください。そこでは、メディアノード自身が話す人の音声だけを転送します。

<!-- source: media-nodes 17f4fc8eb80b -->
## メディアノード

`voice = sfu` では、すべてのルームを 1 つのメディアノードが保持し、そのプロセスがルームの音声を転送します。ルームが複数のノードにまたがることはありません。

<!-- source: run-media-nodes fac01c5bdbf9 -->
### メディアノードを動かす

- **`role = all`** は、ほかのすべてと同じプロセスでノードを動かし、`wss://<host>/voice/sfu` で受け付けます。UDP と TCP のポートを開けたマシンが 1 台あれば足ります。
- **`role = sfu`** は、`web` と `worker` のプロセスとは別に、専用のノードを動かします。ノードは、それらのデータベース、`stream`（`hub` は不可）、`kv`（`memory` は不可）を共有します。ノードは自分自身とそのルームをキーバリューストアに登録し、ルームの変更をストリームで知ります。ジョブは実行せず、ヘルスチェックとノードの WebSocket だけを提供します。必要なだけ動かせます。`web` プロセスは、新しいルームを、予約済みの席がいちばん少なく、そのルームを置ける余裕があるノードに置きます。`web` プロセスはノードを動かしません。

各ノードに必要なものです。

| 必要なもの | 設定 | 備考 |
| --- | --- | --- |
| 公開 IP アドレス | NAT の後ろでは `voice_sfu_public_ip` | ノードはこのアドレスをブラウザーに伝えます。設定がなければノード自身のアドレスを伝えます。クラウドの VM やコンテナは、たいてい自分用のプライベートアドレスを持っているので、設定してください。 |
| インターネットに開放した UDP ポート | `voice_sfu_udp_port`（7882） | ノードのすべてのセッションが共有します。 |
| インターネットに開放した TCP ポート | `voice_sfu_tcp_port`（7881） | UDP をふさぐネットワークのブラウザー用です。 |
| TLS の `wss:` の URL | `voice_sfu_public_url`（`wss://<host>/voice/sfu`） | ノードごとに別々の URL を持ちます（`wss://sfu1.example.org/voice/sfu` など）。手前のリバースプロキシが TLS を終端して WebSocket を転送するか、ノード自身が HTTPS を配信します。`role = sfu` でも `tls` の設定が使え、`voice_sfu_public_url` のホスト用になります（[サーバーから HTTPS を配信する](running.md#serving-https-from-the-server)）。 |
| 保持する参加者の数 | `voice_sfu_node_capacity`（500） | [収容量](#capacity)を参照してください。 |

UDP と TCP のポートは、そのままノードに転送してください。ノードは、自分のポート番号をブラウザーに伝えます。`host` とは別のホストにあるノードには、`web` プロセスにも `voice_sfu_origins`（`wss://*.sfu.example.org` など）が必要です。Web クライアントのコンテンツセキュリティポリシーが、その接続を許可するためです。

<!-- source: docker-compose 35fa31462add -->
### Docker Compose

レイヤー [`compose.sfu.yaml`](../../deploy/docker/compose.sfu.yaml) は、Caddy の後ろの PostgreSQL 上で、サーバー（`role = web`）、`worker`、メディアノード `sfu` を 1 台のマシンで動かします（[Docker Compose のファイル](running.md#docker-compose-files)）。

```sh
# In .env:
# COMPOSE_FILE=compose.yaml:compose.postgres.yaml:compose.caddy.yaml:compose.sfu.yaml
# MY_VOICE_SFU_PUBLIC_IP=203.0.113.10   the public address of this machine
docker compose up -d
```

- Caddy は `/voice/sfu` をノードに、それ以外のリクエストをサーバーに送るので、ノードの URL は既定の `wss://<MY_HOST>/voice/sfu` で、`voice_sfu_origins` は要りません。
- マシンのファイアウォールで、80 と 443 のほかに、UDP 7882 と TCP 7881 を開けてください。
- このレイヤーは、`.env` の内容にかかわらず、3 つのプロセスに `voice = sfu` と `stream = postgres` を設定します。

<!-- source: capacity 2137d8a7bcce -->
### 収容量

ルームは、置かれるときに、何人が参加したかにかかわらず、その最大人数（ホストが設定したルームの上限、または `voice_max_participants`）をノードに予約します。ノードがルームを受け入れるのは、予約の合計が `voice_sfu_node_capacity` に収まるときだけなので、ノードが収容量を超える参加者を抱えることはありません。どのノードにもルームの最大人数分の余裕がないときは、ルームを開くとき、またはその最初の参加が `503` を返し、ユーザーは後でもう一度試せます。

`voice_sfu_node_capacity` は、マシンが転送できる量から決め（[実測の費用](#measured-cost)）、`voice_max_participants` はルームに必要な大きさを超えないようにしてください。500 人のルームは、3 人しかいなくても 500 席を予約します。

<!-- source: measured-cost fef7c9ecfe21 -->
### 実測の費用

50 パケット/秒で Opus の音声を送るシミュレートしたクライアントで、AMD Ryzen 9 7900（12 コア）、WSL2 上の Linux、Go 1.27、すべてループバックで測定しました。CPU はそのマシンのコア数で表し、メモリはプロセスの残りに加えて、ノードのヒープとゴルーチンのスタックです。

| 対象 | CPU | メモリ |
| --- | --- | --- |
| 待機中のノード | 測定できない程度 | 約 0.1 MiB |
| 開いているルーム 1 つあたり | 測定できない程度 | 約 24 KiB |
| 参加者 1 人あたり | 無音のときは約 0.0002 コア | 約 200 KiB |
| 転送するストリーム 1 つあたり（話す人 1 人の音声を参加者 1 人が聞く） | 1 パケットあたり 20 から 27 µs、約 0.001 コア | 約 24 KiB |
| 100 人のルームで 3 人が音を出して話している | 約 0.3 コア | 約 25 MiB |

マシンが速ければ、または遅ければ、これらの数値は比例して変わります。ノード自身のメトリクス（[見るべきメトリクス](#metrics-to-watch)）で、ノードが何を担っているかが分かります。

転送の費用は、ノードが送るパケットに比例します。話す人全員の音声が、ほかのすべての参加者に届くので、N 人の参加者と K 人の話す人がいるルームは、30 から 50 kbit/s のストリームをおよそ K × (N − 1) 本送ります。聞く人が多く話す人が少ないルームは安く、全員が同時に話すルームがいちばん高くつきます。ノードの送信の帯域も同じように見積もってください。

<!-- source: drain-a-node-for-a-deploy 249929addcae -->
### デプロイのためにノードをドレインする

SIGTERM を受けると、ノードは停止する前にドレインします。

1. 新しいルームの受け入れをやめます。
2. 自分のルームを 1 つずつ別のノードに置き、そのルームのクライアントに移動を伝えます。クライアントは新しい grant で新しいノードに再接続し、音声はおよそ 1 から 2 秒途切れます。
3. クライアントが退出するまで待ちます。待つのは、シャットダウンの 25 秒のうち最大 20 秒で、その後、残りのリクエストを待って終了します（[サーバーを止める](running.md#stop-the-server)）。

プロセスが強制終了されるまでの猶予は 30 秒以上にし（Kubernetes と ECS の既定は 30 秒、Docker は 10 秒で、`compose.sfu.yaml` はこれを引き上げます）、ほかのノードがルームを引き受けられるよう、ノードは 1 つずつ再起動してください。ほかのどのノードにも置く余裕がないルームは、ルームが終わるか 20 秒が過ぎるまで、ドレイン中のノードに残ります。**ノードが 1 つだけの場合**は、すべてのルームが残ります。ノードが終了すると参加者は音声を失い、新しいノードが起動すると再接続します。

<!-- source: when-a-node-is-lost c577f2240d7e -->
### ノードが失われたとき

ノードがドレインせずに止まる（クラッシュ、マシンの喪失）と、そのクライアントの WebSocket が閉じ、キーバリューストアにあるノードのリースは 15 秒以内に期限切れになります。クライアントは新しい grant を求め、`web` プロセスがルームを別のノードに置き直します。ルームはノードとともに何かを失うことはありません。参加者、話す人、ミュートはデータベースにあるからです。

<!-- source: turn-for-clients-without-udp 1c1230dc875c -->
### UDP を使えないクライアントのための TURN

ブラウザーはノードに UDP で、UDP がふさがれているときは TCP で接続します。443 番ポートしか通さないネットワーク（一部の企業や公共のネットワーク）では、443 番の TLS で TURN サーバーに接続する必要があります。`voice_turn` を `coturn` にして `voice_turn_coturn_urls` に 443 番ポートの `turns:` の URL を入れるか、`cloudflare` にしてください。`p2p` と同じです（[coturn](#coturn)、[Cloudflare TURN](#cloudflare-turn)）。`sfu` では `voice_ice_transport_policy = relay` は拒否されます。参加者にはすでにノードのアドレスしか見えないためです。

<!-- source: cloud-run 5cf3ffcbb7a6 -->
### Cloud Run

Cloud Run は HTTP のリクエストしか受け付けないので、`role = sfu` はそこでは動かせません。`web` と `worker` のプロセスを Cloud Run で、ノードを公開 IP を持つ VM で動かし、データベース、`stream`（`postgres` か `pubsub`）、`kv`（`db` か `valkey`）を共有してください。各ノードには専用のホスト名と `voice_sfu_public_url` を付け、ノードで TLS を配信するか（`tls = acme`）、その手前で配信し、Cloud Run のサービスの `voice_sfu_origins` にノードのオリジンを設定してください。[Google Cloud へのデプロイ](deploy-google-cloud.md)の OpenTofu のモジュールは、ノードを作りません。

### 見るべきメトリクス

すべてのノードが、自分の `my.voice.sfu.*` のメトリクスを出力します（[メトリクス](running.md#metrics)）。

| メトリクス | 分かること |
| --- | --- |
| `my.voice.sfu.capacity.reserved` と `voice_sfu_node_capacity` の比較 | 新しいルームに対してノードがどれだけ埋まっているか。すべてのノードが上限に近いと、新しいルームは `503` になります。ノードを足すか、ノードの CPU に余裕があるなら収容量を上げてください。 |
| `my.voice.sfu.capacity.connected`、`my.voice.sfu.sessions`、`my.voice.sfu.rooms` | 誰が接続しているか。予約よりずっと少ないなら、ルームの最大人数が必要以上に大きいということです。 |
| `my.outcome` ごとの `my.voice.sfu.packets` | `forwarded` はノードの仕事です。`silent` と `not_allowed`（話せない、またはミュートされている参加者）は、設計どおり捨てられます。`queue_full` は、参加者の接続が追いつけなかったことを示します。数人だけなら遅いクライアント、すべてのクライアントで同時に増えるなら、CPU か帯域が足りないノードです。 |
| `my.voice.sfu.bytes` | 転送した音声の量。ノードの送信の帯域です。 |
| `my.voice.sfu.client.rtt`、`my.voice.sfu.client.packet_loss` | 参加者までの経路の品質。ほとんどのクライアントで悪いならノードのネットワークか場所が、数人だけならその人たち自身のネットワークが原因です。 |
| `my.voice.sfu.migrations`、`my.voice.sfu.ice_restarts`、`my.voice.sfu.renegotiations` | ドレインで移動したルーム、ネットワークを変えたクライアント、話す人の変更。 |
| `my.voice.sfu.reason` ごとの `my.voice.sfu.ticket_refusals` | `other_node` が増え続けるなら、クライアントが grant のノードとは別のノードに届いています。各ノードの `voice_sfu_public_url` がそのノードに通じているか確認してください。 |

## デプロイの注意点

- **ユーザーごとに 2 つのストリーム**: 通話中の参加者は、アプリが常に開いているストリームに加えて、ルーム自身のイベントストリーム（Server-Sent Events）を保持します。接続数の上限は、通話中のユーザー 1 人あたり 2 つの長時間のリクエストを見込んで決めてください。
- **複数のプロセス**: アプリのほかの部分と同じく、共有のストリームアダプター（`stream` を `postgres`、`valkey`、`sns`、`pubsub` のいずれか）を使ってください。`stream = hub` で `role` が `all` 以外の場合、サーバーは起動時に、通話がプロセスをまたいで動かないことを警告します。
- **Cloud Run**: ストリームは 1 つのリクエストで、開いている間は CPU が割り当てられます。リクエストのタイムアウトで切れると、クライアントは再接続します。タイムアウトはできるだけ長くしてください。[Google Cloud へのデプロイ](deploy-google-cloud.md#limits)の `service.request_timeout_seconds` です。
- **メディアノードには VM が必要**: `sfu` のメディアノードは、長時間動き続けるプロセスで UDP の音声を受けるので、Cloud Run では動かせません（[Cloud Run](#cloud-run)）。

## ルームの終了と記録

- `manage_reports` を持つモデレーターは、通話が無効の間も、開いているルームを全員に対して終了できます（[モデレーション](moderation.md#voice-chat-rooms)）。
- ルームに誰が参加したか（参加、話す人とリスナー、挙手、招待と退出）は、ルームの終了後 `voice_participants_retention_days` 日（既定値は 90、最低 30）の間、またはルームを指す通報がある間、保持します。ルームの名前、説明、ホスト、どのように終了したかは保持します。音声、マイクの状態、リアクションは決して記録しません。
- `local` のルームに参加できない訪問者が、そのページとリンクプレビューでルームの名前と開いているかどうかを見られるかは、`voice_public_summary` で決まります（[インスタンスの設定](instance-settings.md)）。

## ユーザー向けの注意点

- iPhone や iPad では、アプリがバックグラウンドにある間、音声の送信が止まることがあります。iOS は前面にない Web ページを停止させることがあるためです。通話中はアプリを画面に開いたままにしてください。
- ブラウザーは、初めてのときにマイクを使う許可を求めます。拒否した場合は、ブラウザーのサイトの設定でもう一度許可してください。
- ピアツーピアのルームでは、インスタンスが通話を中継経由にしていない限り、ほかの参加者があなたの IP アドレスを知ることができる場合があります。気になる場合は運営者に尋ねてください。
