# ADR-0122: リスト: フォロー中の人を自分だけに見えるリストにまとめ、リストごとのタイムラインを読む

- Status: Accepted
- Date: 2026-10-30
- Deciders: @rosylilly
- Issue: #1866

## Context（背景・課題）

FR-209（リスト・キーワードフィルタ）は v0 の範囲外（W）で、ホームタイムライン（FR-201）はフォロー中の全員の投稿を 1 本に並べる。
フォローが増えると、特定の人たち（仕事の仲間・趣味の仲間など）の投稿だけを追うことができない。

決定者は、v0 にリストを入れることにした（原文。問い → 答え）:

> フィルタ（リスト）機能 → フォローしている人をリストにまとめる機能。リストは他人から見えない。リスト単位でタイムラインを表示できる
> リストに入れた人をフォロー解除したら、リストからはどうなりますか？また、リストの人の投稿をホームから隠す選択肢は要りますか？ → 自動で外す・隠す機能なし

キーワードフィルタは別に決める。この ADR はリストだけを扱い、FR-209 をリストとキーワードフィルタに分ける。
決める必要があるのは、リストを持つモジュールと表、メンバーにできる人、リストのタイムラインの中身と更新の届け方、上限、API である。

## Decision Drivers（判断基準）

1. リストは持ち主にしか見えない（ほかの利用者・リモートのサーバー・未ログインの人のどれにも漏れない）
2. リストのタイムラインは、ホームと同じ規則（公開範囲・ブロック・ミュート・言語・ブーストの表示）で投稿を見せる
3. 既存の構成（ADR-0013 の fan-out-on-read、`timeline` が自前の投影だけを読むこと）を崩さない
4. 作る量が少ない

## Considered Options（選択肢）

- 持ち主のモジュール: A1 `timeline` がリストの表を持つ / A2 `graph` がリストを持ち、`timeline` は投影を持つ
- メンバーにできる人: B1 承認済みでフォロー中の人だけ（解除で外れる） / B2 誰でも（フォローしていなければ届いた投稿だけ出る）
- 連合: C1 連合しない（ローカルだけの機能） / C2 ActivityPub の `Collection` として出す

## Decision（決定）

**A1・B1・C1 を採用する。**

### 1. 持ち主と表

`timeline` がリストの表を持ち、書くのも読むのも `timeline` だけにする。
メンバーの条件（フォロー中）は `timeline` が自前で持つ `feed_follow_edges`（`active` のフォローだけ）で確かめられ、`graph` の公開 API を呼ばなくてよい（A2 は `graph` と `timeline` の両方に表が要る）。

- `lists`（リソース）: 持ち主のアカウントと作った時刻
- リストの名前（現在値）: 書記素で 1〜50。変えられる。名前の変更の履歴には意味がない（ADR-0020 規約 5）
- `list_members`（現在値）: （リスト、メンバーのアカウント）。足した時刻を持つ

表の細部（カラム・索引・分類）は data-model の §4.6 に書く。リストの削除はメンバーの行を同じトランザクションで消す。持ち主のアカウントの消去（data-model §8）でリストも消える。

### 2. メンバー

- メンバーにできるのは、持ち主が承認済み（`active`）でフォローしているアカウントだけ（ローカルとリモートの両方）。承認待ちのフォローの相手は足せない。
- フォローが終わったら（`graph.follow_terminated`。理由を問わない）、その相手を持ち主のすべてのリストから外す。`feed_follow_edges` の行を消す projector と同じ更新で消す。フォローし直しても戻さない。
- 移転（ADR-0089）でフォローが移転先へ移るときも、移転元のフォローの終了として外れる。移転先をリストに入れ直すのは持ち主がする。
- ブロック・ミュートはメンバーのまま残し、読み取りで除く（ホームと同じ）。
- リストはホームに影響しない。リストに入れた人の投稿もホームに出る（決定者の回答: 隠す機能なし）。

### 3. 見える人

- リストとメンバーは持ち主だけが読める。クライアント API は持ち主のトークンでだけ返し、ほかの利用者には存在も含めて返さない（`404`）。
- ActivityPub・プロフィール・検索・webhook のどれにも出さない（C1）。リストに入れられたことは相手に通知しない。
- 管理画面とモデレーターの画面にも出さない。データのエクスポート（FR-008）には持ち主のリストを含める（Mastodon の CSV と同じ形。後続の Issue）。

### 4. リストのタイムライン

- 中身は、ホームタイムラインの規則（`ListHomeEntries` と同じ公開範囲・`direct` の宛先・ブロック・ミュート・ドメインのミュート・処分・タイムラインの言語・フォローごとの `show_boosts`）を、作者をそのリストのメンバーに限って当てたもの。持ち主自身の投稿は入れない。
- fan-out-on-read（ADR-0013）のまま、`feed_entries` を `list_members` で絞って読む。新しい投影は作らない。
- 新着の自動の差し込み（ADR-0077）はホームと同じ設定に従う。
- リアルタイム更新（FR-207）: 既存のストリームに `list_update` を足す。`data` は `{"list_id": ..., "status": Status}` で、その投稿が入る持ち主のリストごとに 1 つ送る。新しいストリームの接続は作らない（接続の数の上限を増やさない）。

### 5. 上限

- 1 人あたり 50 リスト、1 リストあたり 1,000 メンバー。超える作成・追加は `422`。値は定数で、設定にしない。
- 上限は、fan-out-on-read の `IN` の大きさ（ホームのフォローの数と同じ程度に収まる）と、画面で扱える数から決めた。

### 6. API と画面

- クライアント API: リストの一覧・作成・名前の変更・削除、メンバーの一覧・追加・削除、あるアカウントが入っている自分のリストの一覧、リストのタイムライン（ホームと同じページング）。`pkg/mykit` にも入れる（ADR-0093）。
- Web: リストの一覧と管理の画面、リストのタイムラインの画面、プロフィールのメニューの「リストに追加」。画面の要件（L1）は `docs/architecture/web-client/screens/` に書いてから作る。

### この決定を見直す条件

- フォローしていない人（とくにローカルの人）をリストに入れたい要望が強いとき（B2）。
- 1,000 メンバーのリストのタイムラインの読み取りが遅いと分かったとき（投影 `feed_list_entries` を足す）。

## Consequences（影響）

- 良い: リストは持ち主だけの表で、連合にも他人の API にも出ないので、漏れる経路がない。
- 良い: 新しい投影を作らず、ホームの読み取りの規則をそのまま使うので、公開範囲などの規則がずれない。
- 悪い: フォローを解除するとリストから外れ、フォローし直しても戻らない。うっかり解除すると入れ直しが要る。
- 悪い: リストに入れた人の投稿はホームとリストの両方に出る（決定者が隠す機能は不要とした）。
- 悪い: ストリームの `update` と `list_update` の両方で同じ投稿が届くので、クライアントは画面に合う方だけを使う。
- 後続の作業（Issue にする）:
  - FR-209 をリスト（新しい FR、優先度 S）とキーワードフィルタ（W のまま）に分ける。data-model §4.6 に表を足す
  - サーバー: スキーマ・`internal/app/timeline`・クライアント API・ストリーム・`pkg/mykit`
  - 画面の要件（L1）: リストの一覧・リストのタイムライン・プロフィールのメニュー
  - Web: 上の画面
  - データのエクスポート（FR-008）にリストを足す

## Pros and Cons of the Options（詳細比較・任意）

- A2（`graph` が持つ）: リストを「関係」として扱え、フォローの終了と同じモジュールで外せる。ただし読み取りのために `timeline` に投影を写す必要があり、表が倍になる。
- B2（誰でも入れられる）: フォローせずに追える（Misskey のアンテナに近い）。ただしリモートの未フォローの投稿はこのサーバーに届かないことが多く、「入れたのに出ない」が起きる。ローカルだけ許すと規則が 2 つになる。
- C2（連合する）: 公開のリストを共有できる。ただし決定者の「他人から見えない」に反する。
