# ADR-0017: 公開範囲 `local`（サーバーローカル）

- Status: Accepted
- Date: 2026-10-16
- Deciders: @rosylilly
- Issue: #232

## Decision（決定）

公開範囲は次の 5 段階とし、この順で並べる: `public` / **`local`** / `unlisted` / `private` / `direct`。

### 1. `local` の意味

| 観点 | 振る舞い |
| --- | --- |
| ローカルタイムライン | 載る |
| 連合タイムライン | 載らない |
| ホームタイムライン | 作者のフォロワー（ローカル・リモートとも）に届く |
| ハッシュタグタイムライン | 閲覧権限のある閲覧者（下記）にだけ表示 |
| 閲覧できる人 | 作者、**ログイン中のローカルアカウント**、作者のフォロワー（承認済み、リモート含む）。ブロック・凍結は常に優先 |
| 未ログインの閲覧者 | 閲覧不可 |
| リモートへの配送 | **作者のリモートフォロワーの inbox だけ**（shared inbox に集約可） |

「外部へはフォロワーにしか届かない」（FR-102）は、投稿の中身だけでなく、その IRI と作者のハンドルも含む（ADR-0018 §15）。

### 2. ActivityPub での表現

- `to` は作者の followers コレクションだけにする。`as:Public` は `to` / `cc` のどちらにも入れない。
  リモートサーバーからはフォロワー限定投稿（Mastodon の `private`）として見える。
- **フォロワーでないリモートのメンション先には配送しない**（「外部へはフォロワーにしか届かない」を優先）。
  投稿作成時、フォロワーでないリモートアカウントへのメンションを含む場合はクライアントで警告する。
- `local` 投稿の `Create` / `Update` の文書は、`tag` に、作者の承認済みのフォロワーでないリモートのアカウントへの `Mention` を入れない。
  ローカルのアカウントへの `Mention` と、フォロワーであるリモートのアカウントへの `Mention` は入れる。
  - 本文の HTML のメンションのリンク（`<a href="…" class="u-url mention">`）はそのまま残す。受信側ではただのリンクとして表示される。
  - フォロワーの判定は、`Create` の文書を組み立てるときの承認済みのフォローで行う。`Update` も同じ規則で組み立て直す（その時点でフォロワーになっていれば入る）。
  - 主要実装が「宛先に含まれない `tag` のメンション」を閲覧の許可に使わなくなったことを、#44 の往復確認で確かめられたら、`tag` を残す形を見直す。
- オブジェクト URI への GET: HTTP 署名付きで、署名者がアクセス権を持つ（作者のフォロワーがいるサーバー）場合だけ返す。それ以外は 404 を返し、存在を漏らさない。
- `Update` / `Delete` は元の投稿を配送した inbox に送る（配送先を記録しておく）。

### 3. 派生ルール

- ブースト: ローカルアカウントは `local` 投稿をブーストできる。そのブースト（`Announce`）はローカルにだけ表示し、**連合しない**。
  リモートからはフォロワー限定に見えるため、リモート側はブーストできない。
- 返信: `local` 投稿への返信の既定の公開範囲は `local`（閲覧者が変更可）。
- 投稿後の公開範囲の変更は不可（全段階共通）。
- 公開範囲の判定は、ドメイン層の単一の `canView` 関数（`content.CanView`）に実装する（NFR-SEC-4）。タイムライン・検索・API・AP のオブジェクト取得はすべてここを通す。

## 経緯

インスタンス内のコミュニティには広く見せたいが、連合で外部に拡散させたくない投稿がある。そのための公開範囲として、サーバーの公開ローカルタイムラインには載るが、サーバーの外部へは作者のフォロワーにしか届かない `local` を設けた。

当初はメンションの `tag` を残し、配送先からだけ除いていた。配送は shared inbox に集約する（ADR-0006、NFR-COST-5）ので、メンション先と同じサーバーに作者のフォロワーが 1 人でもいれば投稿はそのサーバーに届く。2026-10-17 に Mastodon の main（4.8.0-dev）のソースで確かめると（[#232 の調査報告](https://github.com/mycroblog/my/issues/232)）、`related_to_local_activity?` が受け入れ、`process_mention` が `Mention` の行を作り、`silenced` 付きで通知し、`status_policy.rb` の `mention_exists?` でメンション先に閲覧を許す。約束が shared inbox を経由して破られるので、文書の `tag` から除くことにした。

## 採らなかった案

- メンション先のサーバーには、shared inbox ではなくフォロワーの個人の inbox に送る: 文書を変えずに済むが、Mastodon は受信した inbox に関わらず `process_mention` が動くので約束を守れず、リクエスト数も増える。
- `tag` を残して受信側の実装に任せる: 変更がなく、メンションがリモートでもメンションとして扱われるが、Mastodon ではフォロワーでないメンション先が投稿を閲覧できる。

## Consequences（影響）

- `canView` に「閲覧者がローカルアカウントか」という軸が増える。コントラクトテストとドメインのテーブル駆動テストで全組み合わせを検証する。
- リモートのフォロワーに届いた時点で、そのサーバー上での扱い（保存・表示）は制御できない（ActivityPub の本質的な制約）。UI で説明する。
- Misskey の「ローカルのみ」（連合しない）とは意味が異なる。混同しないよう、UI の文言と翻訳で区別する。
- shared inbox を使ったまま、フォロワーでないメンション先が、受信側のどの実装でも投稿を閲覧・通知できなくなる。規則が「文書を組み立てるときの絞り込み」1 か所で済み、フィクスチャのテストで確かめられる。
- リモートのフォロワーから見ると、メンションがメンションとして扱われない（通知もスレッドの参加者の扱いもない、ただのリンク）。投稿作成時の警告（§2、[web-client](../architecture/web-client/README.md)）で利用者に伝える。
- `Update` の時点でフォロー関係が変わっていると、版によって `tag` が変わる。
