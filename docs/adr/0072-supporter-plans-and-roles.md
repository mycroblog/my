# ADR-0072: 課金のプランとロールの連動

- Status: Accepted
- Date: 2026-10-22
- Deciders: @rosylilly
- Issue: #912, #925, #932, #909

## Decision（決定）

管理者が有効にしたときだけ、利用者が自分でプランに加入し、支払いを続ける間プランに結び付いたロールを持つ。既定の課金の形は用意しない。モジュールと状態の規則はこのサーバーが持ち、事業者のダッシュボードの設定に左右されない。

### 1. モジュールと依存の向き

- 新しいモジュール `supporters`（`internal/domain/supporters`・`internal/app/supporters`）を置き、課金の有効化・プラン・事業者の価格・顧客・加入・加入の状態・猶予・掲載の選択（ADR-0070 の `supporter_listings`）を所有する。
- ポート `PaymentProvider`（§17）は `internal/app/supporters` に置き、adapter は `internal/adapter/payment/<事業者>`（ADR-0074 が決める）。
- 依存の向き（ADR-0002）:
  - `internal/app/supporters` は `internal/app/identity`（ロールの付け外し、管理されたロール、メールの確認）、`internal/app/account`（ローカルか、凍結・削除の状態）、`internal/app/instance`（特商法の表記の文章）を呼ぶ。
  - 監査ログは `AuditRecorded` のドメインイベントで `moderation` に渡す（ADR-0067 と同じ）。
  - `identity`・`account`・`content` は `supporters` を呼ばない。`content` の `CustomEmojiQuota` の実装（§11）と、`finance` の `SupporterDirectory` の実装（§12）は、`internal/platform` が `supporters` の公開 API から組み立てる。
  - アカウントの削除・凍結・BAN（§10）は、`account` と `moderation` のドメインイベントを outbox のジョブで受ける。
- overview §2 のモジュールの表、data-model §4.0 の所有の表、`.golangci.yml` の depguard に `supporters` を足す。

### 2. 権限と有効化

- 新しい権限 `manage_supporters` を足す。区分は `server`（ADR-0058 §4）で、組み込みのロールでは `admin` だけが持つ。課金の有効化と無効化、プランの作成・変更・廃止、加入者と加入の状態の一覧、加入の解約（§10）に要る。
  個人ごとの支払いの額と収入は ADR-0067 のとおり `manage_finance` で見る。`manage_supporters` の画面は加入者・プラン・状態・期間の終わりを出し、金額の履歴を出さない。
- 管理画面は ADR-0058 §1 の表に「サーバー管理 | サポーター（`/admin/supporters`。課金の有効化、プランの一覧・作成・プランごとのページ、加入の一覧と加入ごとのページ） | `manage_supporters`」を足す。
- 課金は既定で無効。有効にする条件:
  - デプロイの設定で事業者が設定されている（ADR-0074。webhook の秘密を含む）
  - メールを送る構成である（`mail` が `none` でない。`none` ではメールの確認が済んだ人がいないため、加入の条件を誰も満たさない）
- 有効化と無効化は `supporter_program_changes`（§15）に、有効にしたときの事業者の名前と一緒に記録する。デプロイの設定の事業者が記録と違えば、新しい加入と変更を断り、管理画面に警告を出す（事業者は同時に 1 つ。#925）。
- **無効化は、続いている加入（§7 の `pending`・`active`・`canceling`・`past_due`・`lapsed`）が 1 つでもあれば `409` で断る。** 管理者は先にプランを廃止し（§9。すべての加入が期間の終わりで解約される）、加入が終わってから無効にする。
  無効のときは、利用者の画面・`/about`・API のどこにもプランと加入の導線を出さない（epic #925 の受け入れ基準）。ここで解約の手段を消しても請求が続かないのは、無効の時点で続いている加入がないからである。
- 事業者を替えるときは、無効にしてから新しい事業者で有効にする。既存の加入者は再加入する（#925。運営者向けの docs に書く）。

### 3. プラン

| 属性 | 型 | 変更 | 規則 |
| --- | --- | --- | --- |
| 名前 | `string(50)` | 版で変える | 1 行。管理者が書く文字列で、どのロケールでも同じ値を出す（インスタンスのルールと同じ）。利用者の内容として `dir="auto"` で描く |
| 説明 | `string(1000)` | 版で変える | 改行を含むプレーンテキスト。空でもよい |
| 月額 | 最小単位の整数（`bigint`、1 以上） | 版で変える | 事業者の最低の請求額（`MinimumAmount`、§17）以上 |
| 通貨 | ISO 4217 | 変えない | プランの作成で決まる。通貨を替えるときは新しいプランを作る |
| 年払いの割引率 | `int`（0〜90 の %） | 版で変える | 年額 = ⌊月額 × 12 × (100 − 割引率) / 100⌋（最小単位で切り捨て）。0 は割引なし |
| 結び付くロール | `roles.id` | 変えない | §5 の条件。1 つのロールは 1 つのプランにだけ結び付く |
| 絵文字の作成数の上限（毎月） | `int`（0〜10000） | 版で変える | 1 か月に作れる数（ADR-0070 §4）。ロールが `create_custom_emojis` を持つときに効く（§11） |
| 順位 | `int` | 版で変える | 廃止していないプランの間で一意。上下（§4）と並び順（小さい順）を兼ねる |
| 公開・非公開 | `enum(public, hidden)` | 版で変える | §9 |

- どのプランも月払いと年払いの両方を出す（FR-911）。年払いを出さないプランは持たない。
- 金額は ADR-0067 と同じく最小単位の整数で持ち、API では主単位の 10 進の文字列（`{"amount": "500", "currency": "JPY"}`）で受け渡す。
- **事業者の価格**: プランの作成と、月額か割引率の変更は、同じトランザクションで outbox にジョブ `supporters.ensure_prices` を積む。ジョブは月と年の金額を計算し、いまの価格（`supporter_plan_price_heads`）と金額が違う間隔について `EnsurePrice` で事業者に価格を作り（冪等キーはプラン・間隔・金額・通貨）、価格の行といまの価格を書き換え、古い価格を `ArchivePrice` でアーカイブする。
  月と年の両方の価格ができるまで、そのプランは加入を受け付けない（管理画面に「準備中」と出す）。ジョブが失敗し続ければ管理画面にその旨を出す。
- 管理者は事業者のダッシュボードで価格を作らない。このモジュールが作った価格だけを使う。

### 4. 上位は下位を含む（ロールは 1 つ）

- 利用者が持つプランのロールはいつも 1 つで、上位のプランのロールが下位のプランの特典をすべて持つ（#925）。そのために、廃止していないプランを順位で並べ、隣り合うどの 2 つ（下位 *i*、上位 *j*）についても次を満たすことを、プランの作成・変更・プランのロールの権限の変更のトランザクションで検査し、満たさなければ `422` にする。
  - ロールの `position`: *j* が *i* より高い
  - ロールの権限: *j* が *i* の権限をすべて含む
  - 絵文字の作成数の上限: 両方が `create_custom_emojis` を持つとき、*j* が *i* 以上
- 上位と下位は順位で決まり、プランの変更（§8）の上げる・下げるもこの順位で決まる。

### 5. 課金のロールの安全柵

- **お金でスタッフの権限を買えない**: プランのロールは `member` の権限だけを持ち、スタッフのどのロールより下にあり、どの操作の順でもこの不変条件が崩れない（FR-912）。
- `identity` に現在値の表 `managed_roles`（§15）を足す。プランを作ると、同じトランザクションで結び付くロールを `managed_roles` に入れる（`identity` の公開 API の、トランザクションを受ける操作）。
- プランに結び付けられるロールの条件（プランの作成のときに検査し、満たさなければ `422`）:
  - 組み込みのロール（`admin`・`moderator`）でない、ほかのプランに結び付いていない
  - 持っている人がいない（手で付けた付与と混ざらないため）
  - 権限がすべて区分 `member`（ADR-0070 §1。いまは `create_custom_emojis`・`view_finance`・`start_voice_rooms`・`create_invites`・`keep_posts_longer`）
  - `position` が、**スタッフのロール**（区分 `moderation` か `server` の権限を 1 つでも持つロール。`moderator` と `admin` を含む）のいちばん低い `position` より低い
- `identity` は `managed_roles` に入ったロールについて、次を `409`（`role_managed_by_plan`）で断る:
  - FR-720 の手での付与と剥奪（API・CLI・管理画面）。付け外しは `supporters` が §7 の規則でだけ行う
  - ロールの権限と `position` の直接の変更と、ロールの削除。権限と位置は `/admin/supporters` のプランのフォームから変え、`supporters` が §4 と上の条件を検査してから `identity` の操作を呼ぶ（監査ログは `role_updated`、操作者はフォームを使った人）
- `identity` は、管理されていないロールの変更が不変条件を壊すときも `409` で断る: スタッフのロールの `position` を管理されたロールのいちばん高い `position` 以下にする変更と、管理されたロールのいちばん高い `position` 以下にあるロールに `member` 以外の権限を足す変更。`identity` は自分の表だけでこれを判定できる。
- バッジ（ADR-0070 §10）は管理されたロールにもふつうに付けられる。
- **手で付けたロールとの関係（FR-720）**: プランのロールは手で付けられないので、プランのロールの付与はいつも加入から来る。プランのロールでないロール（たとえば管理者が作った「絵文字の係」に `create_custom_emojis` を持たせて手で付けたもの）は加入と独立に共存し、加入の終わりで外れない。
  スタッフが加入すれば、スタッフのロールとプランのロールの両方を持つ。
- プランを廃止し（§9）、そのロールを持つ人がいなくなったら、`supporters` がロールを `managed_roles` から外す。ロールはふつうのロールに戻り、管理者は削除できる。

### 6. 加入の条件と開始

- 加入できるのは、課金が有効で、次をすべて満たす利用者（#925）:
  - ローカルの利用者で、アカウントが凍結・削除・削除の予約（BAN）の状態でない
  - 主アドレスのメールの確認が済んでいる（`user_primary_emails` に行がある）
  - 続いている加入（§7）がない（同時に 1 つ。`supporter_live_subscriptions` の一意制約で守る）
- 加入の開始: 利用者がプランと間隔（月・年）を選び、§13 の最終の確認の画面を経て、`POST` で開始する。サーバーは 1 つのトランザクションで加入の行（状態 `pending`）を作り、トランザクションの外で `StartCheckout` を呼んで、Web クライアントが次に進む先（事業者の決済画面）を返す。
  こちらの加入の ID を事業者のサブスクリプションに載せ（§17）、取り直したスナップショットで照合する。2 回目以降は、記録した事業者の顧客（`supporter_customers`）を使う。メールの主アドレスを事業者に渡して入力を省く。
- 決済画面から戻った Web クライアントは、加入の状態を読み直す（webhook を待たずに、戻りの要求がジョブ `supporters.sync` を積む）。
- `pending` のまま 24 時間たった加入は、Scheduler が取り直して、事業者の側にもなければ `abandoned` で閉じる。`pending` の間にもう一度始めると、同じ加入の ID のまま、次の「支払いは 1 回まで」に従って決済画面を続けるか作り直す。
- **支払いは 1 回まで**: `pending` の間に決済画面を作り直すだけでは、前の画面も有効期限まで支払えるので、両方に払うと事業者のサブスクリプションが 2 つでき、片方は誰も管理しないまま課金が続く。これを次の 2 段で防ぐ。
  - **もう一度始めるとき**: 同じ加入の、期限の切れていない画面を読み直す（`ResumeCheckout`）。支払い済みの画面があれば新しい画面を作らず、決済からの戻りの画面へ送る。開いている画面が今の依頼（価格・顧客・戻り先）と同じで 15 分以上残っていれば、その画面に戻す。それ以外の開いている画面は失効させ（`ExpireCheckout`）、それから新しい画面を作る。失効できなければ始める操作を失敗にし、画面を渡さない。失効の時に支払いが完了していれば、支払い済みとして扱う。
  - 同時の開始は、加入の行をロックして画面を記録し、後から記録した側が前の画面を失効させる。
  - **それでも 2 つできたとき**: 同時の送信や、失効の失敗の直後の完了は防ぎきれない。リンク済みの加入を名指す別のサブスクリプションを見つけたら（§7 の取り直し）、`supporter_duplicate_subscriptions` に記録し、ジョブが読み直して確かめた上で `CancelNow` で解約し、`RefundSubscription` でその課金を全額返金する。先にリンクしたほうを正とする。このサブスクリプションからは何も提供していないので、自動の返金で失うものはなく、返金は全額で、済んだ課金には事業者が応じないので、繰り返しても二重にならない。
    事業者の画面で手で解約した後のサブスクリプションには触らない（返金をどうしたかは解約した人の判断である）。
    - **手で解約したものと、こちらが解約したものの区別**: 事業者の状態だけでは区別できず、PAY.JP は解約すると削除するので、こちらの加入の ID も読めなくなる。そこで、読み直して続いていると確かめたら、解約を送る前に `supporter_duplicate_cancellations` を書き、以後の試みは読み直さずに進める。読み直しの時点で終わっていれば手で解約したものとして返金せず、記録を済みにする。そのため、閉じた `pending` の加入には `CancelNow` を別に積まず、解約はこのジョブだけが行う。
    - **返金を先に、解約を後に**: PAY.JP は解約すると削除し、削除した定期課金の課金を一覧できるかは文書にないので、解約の後に一覧して空なら返金したと誤る。そこで返金を先に行う。解約との間の更新は無視できる。再試行で直りうる失敗なら解約せずに待ち、権限の不足などそれ以外の失敗でも請求は止めるために解約する。PAY.JP の定期課金には必ず初回の課金があるので、空の一覧は失敗として記録を未完了のままにする。
    - **終わったサブスクリプションはリンクしない**: 2 つとも通知を取りこぼした後で運営者が片方を解約すると、一覧の順によっては解約したほうをリンクし、残した生きているほうを返金してしまう。リンクは続いているサブスクリプションにだけ張る。リンクがないまま期限が来れば、`pending` は `abandoned` で閉じる。
    - **更新の分も返金する**: 2 つめのサブスクリプションはどの期間にも何も提供していないので、支払い済みの請求書をすべて返金する。一部を返金済みの課金は残りを返す。dispute 中の課金と事業者の期限を過ぎた課金は返せないので、ログに残して飛ばす。この規則のために、修正より前からある 2 つめのサブスクリプションも最初の照合で解約して全額を返金する。運営者には更新の前に事業者の側を確かめるよう案内し、移行の処理は作らない（本番の運用はまだない）。
  - 返金が権限の不足などで失敗したら、記録を未完了のまま残し、管理者の支払いの状態に警告 `duplicate_charge` を出し、ログに対象を書き、照合のたびに試し直す。
  - **閉じた `pending` の加入**: プランの廃止やアカウントの削除で閉じるときは、その加入の画面も失効させる。失効させられない画面（PAY.JP の署名した URL）や失効と行き違いの支払いでリンクしたサブスクリプションと、閉じる時点でリンクしていてまだ `active` になっていないサブスクリプションは、利用者が何も得ていないので、同じ記録で解約して返金する。開始の途中で閉じたら、作った画面を失効させて返さない。
  - PAY.JP は画面を失効させられず、続ける画面もない（`ResumeCheckout` はページを返さない）。こちらの加入の ID での検索と処理中の印（ADR-0074 §11）が、どの画面からでも 1 つのサブスクリプションにする。

### 7. 加入の状態の遷移とロールの規則

状態はこちらの規則で導く。webhook・決済画面からの戻り・Scheduler の期限・定期の照合は、どれも「この加入を取り直す」ジョブ `supporters.sync`（冪等、ADR-0004）を積むだけで、ジョブは `GetSubscription` のスナップショットと、こちらが記録した返金・チャージバックとアカウントの事実から状態を導く。
導いた状態か、ロールに効く属性（プラン・間隔・期間の終わり・予約された変更）が直前の遷移と違うときだけ、遷移のイベントを記録する。届く順序・重複・取りこぼしは結果を変えない。

| 状態 | ロール | 入る条件 | 期限（Scheduler） |
| --- | --- | --- | --- |
| `pending` 申し込み中 | なし | 加入の開始。事業者のサブスクリプションがまだないか、初回の支払いが済んでいない | 開始から 24 時間 → 取り直して `abandoned` |
| `active` 有効 | 付く | 事業者が有効（試用を含む）で、解約の予約がない | 期間の終わり → 取り直す（更新の取りこぼしを拾う） |
| `canceling` 解約の予約 | 期間の終わりまで付く | 有効で、期間の終わりの解約が予約されている | 期間の終わり → 取り直して `expired` |
| `past_due` 支払いの遅れ（猶予の内） | 付く | 事業者が支払いの遅れを示し、最初の失敗から 7 日たっていない | 最初の失敗 + 7 日 → 取り直して `lapsed` |
| `lapsed` 猶予の切れ | なし | 支払いの遅れが最初の失敗から 7 日を超えた（Stripe はまだ再試行していることがある。PAY.JP は再試行しない）。一時停止もここに入る | なし（定期の照合が拾う） |
| `expired` 失効 | なし | 事業者の側でサブスクリプションが終わった | 終端 |
| `revoked` 返金・チャージバック | なし | 全額の返金かチャージバックを記録した | 終端 |
| `abandoned` 取りやめ | なし | 初回の支払いが済まないまま終わった | 終端 |

- **ロールの規則**: 状態が `active`・`canceling`・`past_due` の間はプランのロールが付き、ほかの状態では付かない。遷移を記録するトランザクションで `identity` の操作（付与・剥奪・入れ替え）を呼ぶ。付与と剥奪の操作者は `system` で、監査ログは `identity` が `role_granted`・`role_revoked` を書く。
  ロールの剥奪は ADR-0070 §11 のとおりバッジの掲出の選択を消し、ロールが外れる遷移は同じトランザクションで `supporter_listings` の行を消す（ADR-0070 §14）。
- **加入中の定義**（ADR-0070 §14）: 状態が `active`・`canceling`・`past_due` の加入。ロールが付いている期間と同じである。
- **解約**: 期間の終わりまでロールが残る（`canceling`）。期間の終わりの後は `expired` で外れる（FR-911）。
- **猶予**: 猶予の起点は、最後に成功した支払いより後の最初の失敗の時刻（スナップショットが持つ。持たなければ、こちらが最初に遅れを観測した時刻）。猶予は 7 日の定数で、事業者の再試行の設定と独立である。
  猶予の間に支払いが成功すれば `active` に戻る。`lapsed` の後に支払いが成功しても `active` に戻り、ロールをもう一度付ける（バッジと掲載の選択は既定の「出さない」から始まる）。
  Stripe の運営者向けの docs に「事業者の再試行の期間を 7 日以上にし、最後は解約にする」と書く。PAY.JP は支払いに失敗した定期課金を再試行しないので、この設定はない（ADR-0074 §10）。
- **返金・チャージバック**:
  - 加入の支払いの**全額の返金**か**チャージバック**（dispute の開始）を記録したら、すぐ `revoked` にしてロールを外し、トランザクションの外で `CancelNow` で事業者のサブスクリプションもすぐ解約する（次の期間の請求を止める）。返金の額はこちらから返さない（返金は運営者が事業者の画面で行う。自動で返金するのは §6 の、何も提供していないサブスクリプションだけである）。
  - **一部の返金**ではロールを外さず、状態を変えない。
  - **dispute に勝っても**ロールを自動では戻さない。`revoked` は終端で、利用者は再加入する。
  - 返金とチャージバックの事実は、事業者の通知から `supporter_subscription_reversals`（§15）に、事業者の ID で一意に記録する。お金の額の記録（収入から引く）は ADR-0067 が決める。
- 定期の照合: ADR-0074 の定期ジョブ `supporters.reconcile_payments` が、前回の時刻から変わったサブスクリプションを `ListSubscriptions` で列挙し、それぞれを `supporters.sync` に渡す。webhook を取りこぼしても追いつく。周期は ADR-0074 が事業者のイベントの保持期間より短く決める。

### 8. プランの変更と解約

- 変更・解約・解約の取り消しは、このサーバーの画面と API から行い（規則をこちらに保つため）、ポートの命令（§17）で事業者に伝える。事業者の顧客ポータルは支払い方法と請求書のためにだけ開き、ポータルでのプランの変更は使わない（ADR-0074 がポータルの設定で無効にする）。ポータルでの解約は期間の終わりの解約だけに限り、スナップショットで `canceling` として観測する。
- プランの変更ができるのは `active` のときだけ（`canceling` は先に解約を取り消す。`past_due` と `lapsed` は先に支払い方法を直す）。変更先は公開のプランだけで、いまの価格を使う。
- **日割り**:
  - **上げる変更**（順位が上のプランへ、または月払いから年払いへ）: 差額を日割りですぐ請求し、**その支払いを確かめてから**変える（`ChangePrice` の `now_prorated`）。新しいプランのロールへの入れ替えは、スナップショットが新しい価格を示したときに行う。
    - **支払いに失敗したとき**: 加入は今のプランのまま `active` で続き、利用者にはエラーを出す（§18、`supporter-payment-failed`）。`past_due` にも §7 の猶予にも入らず、`supporter_payment_failed` も送らない。回収できるものは事業者に残さず、カードを直してもう一度試せば、1 回だけ請求して変わる。
    - **認証が要るカード**: 変更の請求はオフセッションなので、その場で認証できない。失敗と同じに扱い、カードの更新か別のカードを案内する。事業者の請求書の画面へ送って認証させることはしない。請求書を開いたままにすると、後から払われて利用者が予期しないときにプランが変わるからである。
    - **決済がまだ確定しないとき**: プランを変えず、処理中であることを伝える（`supporter-payment-processing`）。成功すれば事業者のスナップショットに従ってプランが変わる。
    - **更新の支払いの失敗との違い**: 支払いの確認を変更の条件にする。更新の支払いの失敗は §7 の猶予のままで、上げる変更の支払いの失敗だけが猶予に入らない。更新は特典を続けるための支払いで、失敗してもすぐには外さないが、上げる変更は新しい特典を得るための支払いだからである。
  - **下げる変更**（順位が下のプランへ）と**年払いから月払いへ**: 期間の終わりに変える（`period_end`）。それまではいまのプランのロールのままで、予約された変更を画面に出し、利用者は予約を取り消せる。
  - 同じ順位で間隔だけ変えるときも上の規則に従う。上げる変更と下げる変更が同時に起きる組（上位の月払いから下位の年払いへ、など）は、順位で判断する（下げる変更として期間の終わり）。
- ロールの入れ替えは ADR-0070 §11 の `identity` の操作（古いロールの剥奪と新しいロールの付与を 1 つのトランザクションで行い、バッジの掲出の選択を移す）を使う。掲載の選択（`supporter_listings`）は利用者ごとなので残る。
- もとの価格（§9 の据え置き）で続けている利用者がプランか間隔を変えると、変更先のいまの価格になり、同じプランに戻ってももとの価格には戻らない。画面に書く。

### 9. 価格の変更・非公開・廃止

- **価格の変更**: 月額か割引率を変えると、新しい価格は新しい加入とプランの変更から使い、既存の加入はもとの価格のまま更新を続ける（同意のない値上げをしない）。古い価格は事業者でアーカイブされ、新しい加入に使えなくなるが、既存のサブスクリプションは続く（§17 の契約）。
  既存の加入者を新しい価格に移す操作は持たない。移したいときは、新しいプランを作って古いプランを廃止する。
- **非公開**（`hidden`）: 新しい加入とそのプランへの変更を受け付けず、加入の画面と `/about` に出さない。既存の加入は続き、参加者の一覧（ADR-0070）にも出る。公開に戻せる。
- **廃止**: 戻せない。廃止は、同じトランザクションで廃止のイベントを記録し、そのプランの続いている加入それぞれにジョブを積む: `active` と `past_due` は `CancelAtPeriodEnd`（期間の終わりまでロールが残る）、予約された下げる変更は取り消してから同じく解約、`lapsed` は `CancelNow`（ロールはすでにない）、`pending` は `abandoned` で閉じる。
  加入者には通知（§16）で知らせる。廃止したプランは、管理画面の一覧の「廃止」の欄にだけ出て、加入の画面・参加者の一覧（ADR-0070 §14）・ADR-0070 の `plans` の人数に出ない。最後の加入が終わったら、ロールを `managed_roles` から外す（§5）。
- プランは削除しない。廃止したプランの行は加入・遷移・収入の記録が参照する。

### 10. アカウントの削除・凍結・BAN

- **アカウントの削除**（本人による削除と、BAN の削除の予約。`account_lifecycle_events` の `deleted`・`deletion_scheduled`）: ジョブが続いている加入を `CancelNow` ですぐ解約し、`expired`（理由 `account_closed`）にしてロールを外し、`supporter_listings` を消す。
  返金は自動では行わない（`pending` のまま閉じた加入の支払いは §6 のとおり返金する）。運営者が必要と判断すれば事業者の画面で返金し、返金は §7 のとおり記録される。BAN を覆しても加入は戻らない（利用者は再加入する）。
- **凍結**（`moderation.account_suspension_changed` で凍結が始まったとき）: ジョブが `CancelAtPeriodEnd` で期間の終わりの解約を予約する。凍結されたアカウントは特典を使えないので、次の期間の請求を止める。ロールは §7 の規則のまま期間の終わりまで残る（凍結の間は使えない）。
  凍結が解かれても自動では戻さず、本人が期間の終わりまでに解約を取り消すか、再加入する。
- 管理者（`manage_supporters`）は、管理画面から 1 つの加入をすぐ解約できる（`CancelNow`、理由 `staff`）。返金は伴わない（`pending` のまま閉じた加入の支払いは §6 のとおり返金する）。監査ログに残す。
- アカウントの消去（ADR-0020 規約 6）は、`supporter_listings` と `supporter_customers`（事業者の顧客との結び付き）の行を消す。加入・遷移・返金の記録は、会計の記録（ADR-0067）と事業者との照合のために残し、data-model の消去の表の「残すもの」に足す。
  加入の行の `user_id` は消去の後も残る `users` の識別子を指すだけで、名前・ハンドル・メールアドレスは引けない。`SupporterDirectory` の利用者の引き当て（§12）は、消去されたアカウントを「削除されたアカウント」として返す（ADR-0070 §3 の作成者と同じ）。

### 11. 絵文字の作成数の上限（ADR-0070 §4）

`content.CustomEmojiQuota.Limit(userID)` の実装を `supporters` の公開 API で組み立てる。

1. 利用者が、管理されていないロール（手で付けたロール）から `create_custom_emojis` を持つ → 上限なし（ADR-0070 §4）
2. そうでなく、いま持っているプランのロールが `create_custom_emojis` を持つ → そのプランのいまの版の上限
3. それ以外（課金が無効を含む） → 上限なし（`content` は権限を別に検査するので、権限がなければ作れない）

上限を下げても（プランの変更・下げる変更・プランの版）、既存の絵文字は残る。月の途中で上限が下がったときの数え方は ADR-0070 §4 に従う。

### 12. ADR-0067 の `SupporterDirectory` と ADR-0070 との契約

**加入中の定義**は、状態が `active`・`canceling`・`past_due` の加入である（§7。ロールが付いている期間と同じ）。ADR-0070 の参加者の一覧、ADR-0070 の `plans` の人数、ADR-0067 の `SupporterDirectory` はどれもこの定義で数え、`pending`・`lapsed`・終端の状態を数えない。

`finance` のポート `SupporterDirectory`（ADR-0067）を、`internal/platform` が `supporters` の公開 API で実装する。

- `PlanCounts(ctx)`: 廃止していないプランと、加入中の加入が残る廃止したプランごとに、プランの ID・名前・加入中の数を返す。`supporter_subscription_heads` の `(plan_id, state)` のインデックスで数える。
- 加入から利用者への引き当て: 加入の ID の集合を受け、それぞれの利用者の ID・加入のプラン・アカウントが消去されたかを、`supporter_subscriptions` から 1 回の問い合わせで返す。知らない ID は返さない。`manage_finance` の管理画面だけが使う（ADR-0067 §16）。
- 課金が無効なら、どちらも空を返す。

ADR-0070 との契約:

- プランの一覧（`id`・名前・順位・結び付くロール）を公開 API で読ませる。廃止したプランは出さない（§9）。
- 上位のプランの人は、持っているロールが 1 つなので上位のプランの見出しにだけ出る。
- `supporter_listings` はこのモジュールが持ち、ロールが外れる遷移と同じトランザクションで消す。プランの変更では消さない。
- プランの変更は `identity` の選択を移す操作を使う（§8）。

### 13. 特商法の表記などのページ

- `instance` の文章のキー（`instance_text_revisions.key`）に `commerce_disclosure` を足す。`terms`・`privacy_policy` と同じ形式・同じ権限（`manage_settings`）で書き、どのロケールでも同じ値を出す。
- Web は `/about/commerce` に出し、`/about`・加入の画面・最終の確認の画面からリンクする。文章が空ならページは `404` で、リンクを出さない。運営者は事業者のダッシュボードにこの URL を登録できる（spike §1.9）。
- 課金の有効化は文章の有無を条件にしない（運営者の国の法令をサーバーは知らない）。空のまま有効にすると、管理画面に警告を出す。
- 加入を始める直前の確認の画面に、プランの名前・間隔ごとの金額（更新の後も同じであること）・支払いの時期（いますぐ、以降は期間ごと）・特典が始まる時期・解約の方法と効果（期間の終わりまで特典が続く）・特商法の表記へのリンクを出す。
- **法的な正しさを my は保証しない**ことを、運営者向けの docs（`docs/operations/supporters.md`）と管理画面の文章の欄の説明に書く（#925）。docs には spike §9 の事項（表示事項、最終確認画面、消費税とインボイス）を、運営者が確かめる事項として要検証のまま挙げる。

### 14. 加入の操作は Web だけ

- 加入・プランの変更・解約・解約の取り消し・顧客ポータルの画面（`/settings/supporter`）と、`/about` のプランの区画は、Web クライアントが Tauri のアプリとして動くときは出さない。購入への導線も、Web で加入できることの案内も出さない（#925、spike §10）。
- 特典（プロフィールのバッジ、`/settings/custom-emojis`、`/finance`）はアプリでも使える。Google Play は購入の導線のないアプリでほかで買った特典を使うことを認めている。Apple で同じ形が審査に通るかは要検証（Open Questions）。
- API はクライアントを区別しない（区別はクライアントの規則で、サーバーは強制できない）。

### 16. 監査ログと通知

- **監査ログ（ADR-0058）**: `target_kind` に `supporter_program`・`supporter_plan`・`supporter_subscription` を足し、`action` に次を足す。操作者はスタッフか CLI。
  - `supporter_program_enabled`・`supporter_program_disabled`（`target_label` は事業者の名前）
  - `supporter_plan_created`・`supporter_plan_revised`・`supporter_plan_retired`（`target_label` はプランの名前）
  - `supporter_subscription_ended`（§10 の管理者による解約。`target_label` はプランの名前と利用者のハンドル）
- 利用者自身の加入・変更・解約と、事業者の状態からの遷移はスタッフの操作でないので監査ログに書かない（遷移のイベントに残る）。ロールの付け外しは `identity` が `role_granted`・`role_revoked` を操作者 `system` で書く。プランのフォームからのロールの権限と位置の変更は `role_updated` で残る。特商法の表記の変更は既存の `text_changed` で残る。
- **通知**（`client*` 以外の名前空間でも ADR-0009 の制約のとおり、`locales/en`・`locales/ja`）:
  - `supporter_payment_failed`: `past_due` に入ったとき本人に。猶予の終わりの日時と、支払い方法を直す画面へのリンク
  - `supporter_subscription_ended`: `lapsed`・`expired`・`revoked` に入ったとき本人に（理由を含む）
  - `supporter_plan_retired`: 廃止したプランの加入者に。期間の終わりで解約されること
  - メールでも送る（メールを送る構成が有効化の条件なので、いつも送れる）。Tauri のアプリでは通知の文面とリンクの先が加入の画面にならないようにする（§14）

### 17. ポート `PaymentProvider` に求める契約（ADR-0074 が満たす）

この ADR はポートの形と adapter を決めない。spike §4 の形はこの契約を満たす。型は標準ライブラリだけで、事業者の SDK の型を出さない（ADR-0068 と同じ）。

| 必要なこと | 契約 |
| --- | --- |
| 価格 | `EnsurePrice` は冪等で、同じプラン・間隔・金額・通貨に同じ価格を返し、要らなくなった価格をアーカイブする。アーカイブした価格の既存のサブスクリプションは更新を続ける。`MinimumAmount(通貨)` が最低の請求額を返す |
| 決済の開始 | `StartCheckout(こちらの加入の ID・顧客か メール・価格・ロケール・戻り先)` が、Web クライアントが次に進む先（リダイレクトの URL）を返す。こちらの加入の ID を事業者のサブスクリプションに載せ、スナップショットで返す。カード情報はこのサーバーを通らない |
| ポータル | 支払い方法と請求書の画面の URL を返す。ポータルでのプランの変更は無効、解約は期間の終わりだけにする |
| 命令 | `ChangePrice(サブスクリプション・価格・時期 {now_prorated, period_end})`、`CancelAtPeriodEnd`、`ResumeCancellation`、`CancelScheduledChange`（期間の終わりに予約した変更の取り下げ）、`CancelNow`（返金しない）。どれもこちらの ID から作る冪等キーで、2 回呼んでも 1 回と同じ |
| 決済の画面の続き | `GetCheckout` で読み直す。`ResumeCheckout`（開いていて今の依頼と同じ画面なら続ける）・`ExpireCheckout`（開いている画面を払えなくし、今の状態を答える）。§6 の、1 つの加入に 2 度課金しないため |
| 返金 | `RefundSubscription`（サブスクリプションの確定した課金の残りを返金する）。§6 の重複の片付けに使う |
| 通知 | webhook の検証の後、`(事業者, event_id)` で重複を除き、「どの加入を取り直すか」（事業者のサブスクリプション）と、お金の動きの ID を返す。順序を仮定しない |
| お金の動き | 返金・チャージバックを取り直すと、種類（返金・チャージバック・チャージバックの取り消し）・対象のサブスクリプション・返金の額と元の支払いの額（`MoneyMovement` の `Gross` と `ParentGross`。全額か一部かをこちらが判断する）・事業者の ID・確定したか（`Final`）が分かる。確定した動きだけで状態を変え、同じ動きを ADR-0067 の `RecordIncome` にも渡す |
| 正 | `GetSubscription` のスナップショット: こちらの加入の ID、顧客、価格、正規化した状態（`incomplete`・`active`・`past_due`・`unpaid`・`paused`・`canceled`・`incomplete_expired`。試用は `active`）、期間の始まりと終わり、期間の終わりの解約の予約、期間の終わりに予約された価格、最後の成功の後の支払いの失敗の時刻（なければなし） |
| 照合 | `ListSubscriptions(時刻・カーソル)` が、その時刻から変わったサブスクリプションを列挙する |
| 失敗 | 一時的な失敗（再試行する）と恒久的な失敗（管理画面に出す）を区別する |

- 正規化した状態から §7 の状態への写しはこのモジュールが持つ: `incomplete` → `pending`、`incomplete_expired` → `abandoned`、`active` → `active` か `canceling`（解約の予約で分ける）、`past_due` と `unpaid` → 猶予の内なら `past_due`、外なら `lapsed`、`paused` → `lapsed`、`canceled` → `expired`。
- webhook のジョブと定期の照合のジョブは、取り直したスナップショットをこのモジュールのユースケース（スナップショットを当てる、冪等で順序に依らない）に渡す。それが §7 の `supporters.sync` である。
- 外向きの HTTP の分類、設定と秘密、webhook の受け口の経路、fake と契約テストは ADR-0074 が決める。

### 18. API の形（[client-api.md](../architecture/client-api.md) の手順で細部を決める）

- 利用者（タグ `supporters`、新しいスコープ `read:supporters` / `write:supporters`。`read` / `write` に含む）:
  `GET /supporter/subscription`（自分の加入: 状態・プラン・間隔・期間の終わり・予約・猶予の終わり）、`POST /supporter/checkout`（`{plan_id, interval}`。条件を満たさなければ `422`、続いている加入があれば `409`）、
  `POST /supporter/subscription/change`（`{plan_id, interval}`）、`POST /supporter/subscription/cancel`、`POST /supporter/subscription/resume`、`POST /supporter/portal`（ポータルの URL）
- 公開（タグ `instance`、`security: []`）: `GET /instance/supporter_plans`（公開のプラン: 名前・説明・月額・年額・順位）。無効なら `404`。`GET /instance` に `supporters_enabled` を足す。
- 管理（タグ `admin-server`、`admin:read` / `admin:write` と `manage_supporters`）: `GET/PUT /admin/supporter_program`、`GET/POST /admin/supporter_plans`、`PATCH /admin/supporter_plans/{id}`（ロールの権限と位置を含む）、`POST /admin/supporter_plans/{id}/retire`、
  `GET /admin/supporter_subscriptions`（状態とプランで絞り込む。キーセットページング）、`GET /admin/supporter_subscriptions/{id}`、`POST /admin/supporter_subscriptions/{id}/end`
- CLI: `my admin supporters`（有効化・無効化・プランの一覧・加入の一覧と解約）。

### この決定を覆す条件

- 加入者から猶予の長さを延ばしたい声が多いか、事業者の再試行で後から払われる例が多いと分かったら、猶予の長さをインスタンス設定にする。
- 既存の加入者を新しい価格に移す需要が強いと分かったら、通知と同意を伴う移行の操作を別の ADR で決める。
- 1 人が複数のプランを同時に支援したいという要望が強いと分かったら、「同時に 1 つ」と「上位は下位を含む」を見直す（ロールを複数付ける形）。
- `member` の区分に、他人に効く権限を入れたくなったら、§5 の安全柵を見直す（ADR-0070 の覆す条件と同じ）。

## 経緯

M4.2（Supporters、epic #925）は、管理者が有効にしたときだけ利用者がプランに加入できる機能を入れる（FR-910〜FR-912）。ロールが運ぶ特典（バッジ・絵文字の作成・会計の閲覧）は [ADR-0070](0070-permission-split-emoji-finance.md) と [ADR-0070](0070-permission-split-emoji-finance.md) が決め、この ADR はプランと加入と、加入の状態からロールを付け外しする規則を決める。決済の事業者との境界は [ADR-0074](0074-payment-provider-port.md)、収入の記録と公開は [ADR-0067](0067-finance-cost-records.md) が決める。関連: FR-008、FR-704、FR-720、FR-910〜FR-917、[ADR-0002](0002-modular-monolith-hexagonal.md)、[ADR-0004](0004-job-queue-abstraction.md)、[ADR-0020](0020-data-modeling-principles.md)、[ADR-0058](0058-moderation-admin-separation.md)、[ADR-0058](0058-moderation-admin-separation.md)、[ADR-0067](0067-finance-cost-records.md)、[ADR-0068](0068-billing-import.md)。

判断の基準は、特典が支払いの状態に正しく従うこと（イベントの順序・重複・取りこぼしで結果が変わらない）、お金でスタッフの権限を買えないこと、状態の規則が事業者に依存しないこと、管理者の操作で既存の加入者が不意に困らないこと（同意のない値上げや、解約の手段のない請求が起きない）である。

spike #909 の[レポート](https://github.com/mycroblog/my/issues/909#issuecomment-6326974258)（2026-10-22 確認）の事実が形を決めた。価格は金額を変えられないので、年払いの割引は年の価格を別に作り、金額が変わるときは新しい価格を作って古い価格をアーカイブする（§3）。事業者のイベントは順序が保証されず重複するので、webhook は合図として受け、サブスクリプションを取り直して状態を導く（§7）。事業者の再試行の期間は最初の失敗から 7 日と一致しないので、猶予はこちらの Scheduler が持つ（§7）。Paddle は規約で認められないので spike の段階で落とし、事業者を Stripe だけにして始めた。PAY.JP は ADR-0074 が足した。

上げる変更（§8）は、はじめはすぐ変えて、差額の請求が失敗すれば新しいプランで `past_due` にして猶予に入れる形だった。下げる変更と違って利用者を待たせないためである。Stripe のテストモードで払えないカード（`4000 0000 0000 0341`）を試すと、上位のプランに切り替わって 7 日の猶予に入り、画面は「プランを変更しました」と出した。払えないカードで上位の特典を 7 日使えるので、支払いの確認を変更の条件にした。

§6 の「支払いは 1 回まで」は、`pending` の間に決済画面を作り直すと前の画面も有効期限まで支払えて、誰も管理しないサブスクリプションの課金が続くことが分かって足した（#2171）。

## 採らなかった案

- `finance` に置く: 収入と同じ事業者のデータを扱うが、会計のモジュールがロールの付け外しとアカウントの状態に依存し、`manage_finance` の範囲と混ざる。
- `identity` に置く: ロールの付け外しがモジュールの中で済むが、認証とロールのモジュールに決済の事業者と Scheduler の規則が入る。
- 権限を `manage_settings` にする: 権限が増えないが、設定を任された人がロールの権限とお金の流れを同時に動かせる。
- 権限を `manage_finance` にする: お金の担当がプランも扱えるが、記録の権限（ADR-0067）にロールと加入者の管理が入り範囲が広がる。
- プランのロールを手での付与と共存させる: 管理者が無償で付けられるが、`user_roles` は 1 つのロールに 1 つの付与しか持たず、加入の終わりの剥奪で手での付与も消えるか、付与の出どころを `identity` に持ち込むことになる。上限も同じロールで食い違う。
- `identity` がロールを変えるたびにポートで `supporters` に問い合わせる: `identity` に表が増えないが、毎回別のモジュールへの問い合わせが要り、組み立ての漏れで検査が抜ける。
- webhook のイベントを届いた順に状態へ当てる: 取り直しがなく速いが、両社とも順序を保証せず、遅れて届いた古いイベントでロールが戻る。
- 猶予を事業者の再試行の終わりまでにする: 実装が小さいが、再試行の期間は設定で 1 週間〜2 か月と変わり、7 日と一致しない。
- 価格の変更を次の更新から既存の加入者に効かせる: 金額がそろい集計が単純だが、同意のない値上げになり、事前の通知と同意の仕組みと法令の確認が要る。
- 廃止しても既存の加入を続ける: 加入者は何もしなくてよいが、非公開と同じになり、ロールがいつまでも管理されたまま残る。
- 無効化で新しい加入だけを止める: 管理者はいつでも止められるが、「無効のときは何も出ない」と両立させると解約の画面も消え、請求だけが続く。
- 凍結で何もしない: 短い凍結が解かれれば元どおりだが、使えない特典に請求が続く。
- 凍結ですぐ解約する: 請求も特典もすぐ止まるが、凍結は覆ることがあり、払った期間の特典まで失う。
- 上げる変更の失敗を元に戻す: ロールと掲載の入れ替えを往復させ、その間に特典が付く。
- 上げる変更の失敗の猶予を短くする: 払っていない特典が付くことを変えない。
- 決済画面を毎回失効させて作り直す: 実装は短いが、3D セキュアの途中の画面を失効させるおそれがある。
- 開いている画面へ戻すだけにする: プランや間隔の違う依頼と、同時の 2 回の開始に足りない。
- 2 つめのサブスクリプションの返金を手で行う: 鍵の権限を増やさずに済むが、利用者が返金を待つ間ずっと損をし、運営者が見落とせば残る。
- 2 つめのサブスクリプションを解約だけで返金しない: 何も得ていない利用者に課金を残す。
- 2 つめのサブスクリプションの初回だけを返金する: どの期間にも何も提供していないので、更新の分も返す。

## Consequences（影響）

- 良い影響
  - 状態は事業者のスナップショットとこちらの事実からいつも同じ規則で導くので、webhook の順序・重複・取りこぼしと、事業者の再試行の設定がロールの結果を変えない。
  - プランのロールは `identity` の表 1 つで守られ、手での付け外し・権限と位置の変更・スタッフのロールの変更のどの順でも、お金でスタッフの権限に届かない。
  - 値上げは既存の加入者に効かず、廃止と無効化で解約の手段のない請求が残らない。
  - ADR-0070 の上限と ADR-0070 の一覧・バッジの契約を、プランの属性と加入中の定義 1 つで満たす。
- 悪い影響・トレードオフ
  - テーブル（§15）と、遷移を導く規則と Scheduler の期限、事業者へのジョブが増える。
  - プランのロールは手で付けられず、管理者が特定の人に特典を無償で渡すには、プランでない別のロールを作って付ける必要がある（上限なしになる）。
  - 価格を据え置くので、古い価格の加入が長く残り、同じプランに金額の違う加入者が並ぶ。収入の集計（ADR-0067）はプランごとの金額を加入の価格から読む必要がある。
  - Stripe では猶予の後もしばらく事業者が再試行し、`lapsed` の利用者はロールがないのに後から請求されうる。通知と docs で、支払い方法を直すか解約するよう案内する。PAY.JP は再試行せず、停止のまま課金しない。
  - 凍結で自動的に解約が予約されるので、短い凍結が解かれた後に本人が解約を取り消し忘れると加入が終わる。
  - `mail = none` のサーバーでは課金を有効にできない。
  - 上位は下位を含むという検査のため、管理者はプランのロールの権限と位置をプランのフォームから変える必要があり、`/admin/roles` からは変えられない。
  - 加入を Web だけにしても、Apple の審査がアプリで特典を使う形を認めるかは確かめていない。
