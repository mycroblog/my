# ADR-0138: ワーカーが実行するジョブの種類を選ぶ

- Status: Proposed
- Date: 2026-11-03
- Deciders: @rosylilly
- Issue: #1996

## Context（背景・課題）

ワーカーはすべての種類のジョブを実行する。`role = worker` はワーカーとして動くかを決めるだけで、種類を選べない（NFR-PERF-2、[ADR-0004](0004-job-queue-abstraction.md)）。
そのため、配送が大量にたまるとメールや通知も待たされ、ワーカーを増やしても増えた分はすべての種類で分け合う。特定のジョブのためだけのスケールアウトを設計できない。

コードの現状は次のとおり。

- `Source.Claim`（`PickJob`）は、`run_at` がいちばん早いジョブを種類を問わずに取る。`jobs` の索引は `run_at` と `(ordering_key, run_at)` で、`type` にはない。
- 1 つのプロセスは `PullRunner` を 1 つ持ち、`RunOnce` の繰り返しでジョブを **1 件ずつ** 実行する。同時実行数の設定はない。今のスケールアウトの単位はプロセスである。
- `queue = sqs` / `cloudtasks` は、ジョブ ID だけを持つ合図を 1 つのキューで運ぶ（[ADR-0120](0120-external-queue-wake-up-signals.md)）。受け取る側は合図を選べない。
- 順序キーの判定は種類を見ない。同じキーの前のジョブが残っていれば、種類が違っても待つ。

## Decision Drivers（判断基準）

1. 大量のジョブがたまっているときこそ、選んだ種類を速く取れる（この機能が要る場面）
2. 指定しない構成の claim を遅くせず、動作も変えない
3. 誰も実行しない種類を放置しない
4. 順序キーの順序を壊さない
5. 運営者が分かりやすい設定で、種類の増減に追従できる
6. スキーマの変更と実装の量が小さい

## Considered Options（選択肢）

1. **種類の指定 + 種類ごとに索引を引く claim**（`(type, run_at, id)` を足す）
2. **種類の指定 + 今の `PickJob` に条件を足すだけ**
3. **`jobs` にレーンの列を足し、種類をコードでレーンに割り当てて、ワーカーはレーンを選ぶ**
4. **何もしない**（全体のワーカーを増やすだけ）

## Decision（決定）

> Proposed の推奨案。Accepted にするのは人間の Decider のみ。

**推奨案は選択肢 1。** 選択肢 2 は測定で、この機能が要る場面で遅いと分かった。選択肢 3 は同じ索引の形を、列の追加と割り当ての維持をして得ることになる。

### 測定

手元の WSL2 上の PostgreSQL 18.6 と SQLite 3.45.1 で、期限の来た 100 万件（`federation.deliver` が 90 万件）を置いて測った。90 万件が他より古い最悪の分布の値である。
**本番相当の環境ではなく**、ページはすべてメモリに載っていた。小さなインスタンスでキャッシュがないときはもっと遅いはずだが、測っていない。詳細と手順は [#1996 の報告](https://github.com/mycroblog/my/issues/1996) と枝 `spike/1996-worker-job-claim` にある。

| claim（1 回、PostgreSQL） | ms | 読んだブロック |
| --- | ---: | ---: |
| 今（指定なし） | 0.16 | 12 |
| `type = ANY` で少ない 1 種類（`jobs_run_at` で 90 万件をたどる） | 80 | 16,388 |
| `type <> ALL` で多い種類を除く | 79 | 14,765 |
| ジョブのない種類を待つポーリング（順次走査） | 55 | 13,328 |
| 種類ごとに引く（LATERAL）: 1 種類 / 3 種類 / 83 種類 | 0.18 / 0.20 / 0.31 | 12 / 24 / 267 |

- `(type, run_at, id)` を足しても、`type = ANY` と `type <> ALL` のプランは `jobs_run_at` のまま変わらず、75〜85 ms のままだった。**索引だけでは足りず、クエリの形を変える必要がある。**
- 8 クライアントで取って消す負荷では、条件を足すだけの形が毎秒約 100 件、種類ごとに引く形が毎秒約 5,600 件だった。同じ条件の測定でも 2.5 倍ほど振れたので、桁だけを読む。実際の claim のリースの書き込みと advisory lock は含まない。
- SQLite も同じ傾向で、条件を足すだけなら 84〜104 ms、種類ごとに引くなら 0.07 ms 以下だった。SQLite の claim は書き込みロックの中で動くので、遅い claim は他の書き込みもすべて止める。
- 新しい索引は 64 MB（同じ 100 万件で `jobs_run_at` は 21 MB）。投入の速さは 3 回の中央値で差が見えなかったが、外れ値が大きく、索引の書き込みのコストを切り分けられてはいない。

### 1. 設定

- 設定のキーを 2 つ足す。同時に指定すると起動に失敗する。どちらも指定しなければ今と同じで、すべての種類を実行する。
  - `worker_job_types`: このプロセスが実行する種類だけを並べる
  - `worker_job_types_except`: このプロセスが実行しない種類を並べる
- 値はカンマ区切りで、種類の名前（`federation.deliver`）か接頭辞（`federation.*`）を書く。`role = web` で指定すると起動に失敗する。`role = all` では使える。
- プロセスごとの違いは環境変数で与えられるので、`my serve` のフラグは足さない。
- 起動時に、プロセスが持つハンドラの一覧に照らして実行する種類の集合を求める。**どのハンドラにも当たらない名前や接頭辞があれば起動に失敗する**。誤字に気づくためで、種類の名前を変えたリリースでも、起動の時点で分かる。求めた一覧はログに出す。
- `worker_job_types_except` は、ハンドラの一覧から除いた集合に直してから使う。除外も、種類ごとに引く速い形で取れる。

種類の名前は運営者の設定に現れるようになる。名前の変更はリリースノートに書く（v0 では設定のキーの変更と同じ扱い。ADR-0087）。

### 2. claim

- 指定のないプロセスは今の `PickJob` のままで、速さも動作も変わらない。
- 指定のあるプロセスは、種類ごとに `(type, run_at, id)` を引いて候補を 1 件ずつ得て、`run_at` がいちばん早いものを取る。PostgreSQL は `unnest` と `LATERAL`、SQLite は `UNION ALL` か種類ごとの問い合わせで書く。
- 期限・リース・順序キーの条件は今の `PickJob` と同じで、PostgreSQL の advisory lock と 2 回目の確かめもそのまま使う。
- PostgreSQL では、種類ごとの先頭の行を `FOR UPDATE SKIP LOCKED` でトランザクションの間だけロックする。使わなかった行のロックは他のワーカーに飛ばされるだけで、待たせない。83 種類を多数のワーカーで同時に引く場合の競合は測っていない。
- `jobs` に索引 `(type, run_at, id)` を足す（両方の方言）。指定を使わない構成にも索引の書き込みのコストがかかる。`jobs_run_at` は指定のないプロセスと `queue.wake` の掃除が使うので残す。

### 3. 誰も実行しない種類

種類を外すと、どのワーカーも実行しない種類が生まれうる。定期の後始末のジョブも対象になる。プロセスは他のプロセスの設定を知らないので、起動時には判定できない。**ジョブが待ち続けていることで検知する**。

- 指標 `my.queue.oldest_ready_age` に種類のラベルを足す。警告のルールの例を運用の文書に書く。
- ジョブの画面で、種類ごとの最も古い待ち時間を見せる。
- 指定のあるプロセスは起動時に、**自分が実行しない種類** をログに出し、他のプロセスが実行する必要があることを伝える。
- `/readyz` には反映しない。他のプロセスの設定の問題で、正常なワーカーを落とさないため。
- ワーカーの一覧を登録する仕組みは持たない。指標はワーカーがいない以外の滞りも検知するし、登録の表や KV の管理が増えるため。

### 4. 順序キー

判定は今のまま種類を見ない。順序を保つためで、前のジョブの種類を実行するワーカーが動いている限り、別のワーカーに分かれていても順序は守られる。

ただし、前のジョブの種類を誰も実行しないと、後ろのジョブも止まる。今のコードで種類をまたいでキーを共有するのは次のとおりで、同じワーカーの組に置くよう運用の文書に書く。

| キー | 種類 |
| --- | --- |
| `like:` | `federation.fanout`、`federation.deliver`（お気に入りの配送だけ） |
| `voice_room:` | `voice.media_event`、`voice.apply` |
| `supporter_subscription:` | `supporters.sync`、`supporters.command` |

分けた結果、片方の種類が滞ると、同じキーのもう一方も待つ。

### 5. 外部のキュー

`worker_job_types` と `worker_job_types_except` は **`queue = db` だけで使え**、`cloudtasks` / `sqs` / `inline` では起動に失敗する。

- 合図は ID だけを持つので、受け取ってからでないと種類が分からない。受け取って実行しない場合に合図を出し直すと、合図が回り続けて課金も増える。
- SQS の受信の API にメッセージを選ぶ引数はない（[ReceiveMessage](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/APIReference/API_ReceiveMessage.html)）。Lambda のイベントのフィルターは、条件に合わないレコードを捨てる（[Event filtering](https://docs.aws.amazon.com/lambda/latest/dg/invocation-eventfiltering.html)）ので、合図を失う。
- 将来は、種類の組ごとに外部のキューと受け口を分けられる。Cloud Tasks はキューごとに送る速さと同時数を設定できる（[Configure queues](https://docs.cloud.google.com/tasks/docs/configuring-queues)）。`Wake` と掃除に行き先の判定が要るので、別の ADR で決める。
- 3 つの文書はいずれも 2026-11-03 に確認した。

### 6. Scheduler

`role = all` / `worker` のプロセスは、指定の有無によらず今のままプロセス内の Scheduler を動かす。投入は実行するワーカーと関係なく、周期の投入は冪等キーで 1 回になる。

### 7. 同時実行数

この ADR に含めない。種類を分けてプロセスを増やせば、種類ごとのスケールアウトはできる。
1 プロセス内の同時実行は、ハンドラの並行の安全性・DB 接続の数・停止の処理・レート制限の確認が要るので、別の Issue と ADR で決める。待ちの多い配送では費用の面で効く可能性があるが、測っていない。

### 8. リース

リースは全種類で一律の 5 分（`queue.DefaultLease`）のままにする。遅いジョブと速いジョブを分けても設定を増やさない。

**覆る条件**: 本番に近い環境で、種類ごとに引く claim が速くならない場合や、索引の書き込みが投入を明らかに遅くする場合は選択肢 3 と比べ直す。

## Consequences（影響）

- 良い影響
  - 配送がたまっていても、メールや通知だけを別のワーカーで実行し、配送だけのワーカーを増やせる。
  - 指定しない構成の claim は変わらない。
- 悪い影響・トレードオフ
  - 指定しない構成にも、索引の容量と書き込みのコストがかかる。容量は 100 万件で 64 MB で、書き込みは切り分けられていない。
  - 誤った組み合わせで誰も実行しない種類ができると、検知まではジョブが止まる。定期の後始末やメールも止まりうる。
  - `worker_job_types` のプロセスは、新しいバージョンで増えた種類を実行しない。`worker_job_types_except` のプロセスは自動で実行する。リリースごとに確認が要る。
  - 種類の名前が設定の一部になり、変更が運営者に見える。
  - Cloud Run / Lambda の構成では使えない。そちらでは全種類が 1 つの受け口を通る。
  - libSQL は測っていない。SQLite と同じクエリを使うが、遠隔の場合の往復は `UNION ALL` なら 1 回、種類ごとの問い合わせなら種類の数だけかかる。
- 後続の作業
  - #1997: 実装と運用の文書
  - [#1994](https://github.com/mycroblog/my/issues/1994): 指定できる種類の名前は、ジョブのリファレンスから引けるようにする
  - 同時実行数と、外部のキューの分割を検討するときは、それぞれ Issue を作る

## Pros and Cons of the Options（詳細比較・任意）

### 選択肢 2: `PickJob` に条件を足すだけ

- 良い点: クエリの変更が最小で、索引もいらない。スキップするジョブが少なければ 1〜3 ms で済む（均一に混ざった分布の測定）。
- 悪い点: 大量のジョブが先にたまると 1 回の claim に 80 ms かかり、処理できる件数が 2 桁ほど下がる。ジョブのない種類を待つだけのポーリングでも、1 秒ごとに順次走査が走る。

### 選択肢 3: レーンの列

- 良い点: 名前が少なく安定し、種類の名前の変更が運営者に見えない。誰も実行しないレーンを判定しやすい。プローブの数も少なく、種類をまたぐ順序キーを同じレーンにまとめられる。
- 悪い点: 列の追加と、投入のすべての経路でのレーンの決定が要る。種類の割り当てをコードで決めるので、運営者の環境に合わせて分けられない（「特定の種類だけ」が割り当て次第でできない）。

### 選択肢 4: 何もしない

- 良い点: コストがない。全体を増やせば、たまったジョブはいずれ減る。
- 悪い点: 配送の洪水の間、メールや通知は順番を待つ。問題が解決しない。

## Open Questions / 要検証

- 本番に近い環境（小さなインスタンス、キャッシュなし）での claim の時間と、索引の書き込みのコスト。#1997 の実装の前後で確かめる。
- `worker_job_types` と `worker_job_types_except` の名前と形（2 つのキーか、1 つのキーの中の否定か）。
