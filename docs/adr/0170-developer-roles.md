# ADR-0170: 開発の役割（言語ごとの実装とテスト・育つ知識・検査）

- Status: Accepted
- Date: 2026-11-14
- Deciders: @rosylilly
- Issue: #3063

## Decision（決定）

### 1. 役割

実装を 1 つの役に任せず、言語ごとに作る役とテストを書く役の 4 つに分ける。役は人格ではなく、持つ知識と見るものの違いで分ける（ADR-0169 §2）。

- **Go の実装**: サーバーのコード。層・モジュール・スキーマの決まり（ADR-0002 §1、ADR-0023）に従う。
- **Go のテスト**: サーバーのテストとテストの補助。
- **TS の実装**: Web クライアントのコードと、部品の隣に置くストーリー（ADR-0025、ADR-0110 §9）。ADR-0169 §2 の実装の役はこれである。
- **TS のテスト**: 単体・部品・ストーリー・E2E のテスト。

どの役も、1 つの課題かその片側を 1 つのコミットで終える。

### 2. テストの役は実装を読まない

テストの役は、課題の完了条件、ADR、公開されたインターフェイス（公開された宣言、API の仕様、SDK の型）、既存のテストとその補助だけを読んでテストを書き、テストとその補助だけを書き換える。これは指示ではなくフックで守る。

実装を読んで書いたテストは、頼まれたことではなく書かれたことを確かめ、実装の誤りをそのまま固める。作った過程を知らない評価役を置くのと同じ理由である（ADR-0169 §2）。

### 3. 束ねる役は置かない

Go と TS をまたぐ調整は、課題を配る指揮役が持つ。クライアントとサーバーの取り違えが繰り返されたら、束ねる役を足す。

### 4. 進める順

- 言語ごとに、作る役の後にテストの役が続く。
- Go と TS をまたぐ課題は、API の取り決め（OpenAPI の仕様）を先に決めてコミットし、両側の作る役はそれに合わせる。片側を待たずに進められ、食い違いは仕様との差として検査で見つかる。

### 5. 知識

ADR-0169 §3 と同じ形を役ごとに持つ。必ず読む小さな索引と、作業が触れるときだけ読む領域ごとの決定と実例で、大きさの上限は検査で守る。最初の中身は、すでに決まっていて ADR か検査が持つことだけにする。

### 6. 繰り返す訂正は検査になる

決定者の訂正の 1 回目は決定の 1 行になり、同じ訂正の 2 回目は、その行を検査に変える提案になる。検査になった行は消す（ADR-0169 §4）。

### 7. 最初の検査

- Go のテストで決まった時間だけ待つことを、新しいコードには許さない。決まった時間の待ちは遅く、負荷の下で不安定になる。直し方は `testing/synctest`、チャネル、偽物の時計である。今ある箇所は減る方向にしか変えられない一覧に載せ、別の課題で空にする。
- E2E のテストは要素をロールとアクセシブルネームで探し、順番（`nth()`、`first()`）、CSS セレクタ、文言の一部では探さない。画面の補助は E2E の共有パッケージだけに置く。この検査はそのパッケージとともに入る（#2876）。

## 経緯

実装の役が 1 つだと、Go と TS の知識を 1 つのコンテキストに載せ、決定者の訂正がどの領域のものかも残らなかった。デザインのハーネス（ADR-0169）で、役ごとの小さな知識と、作った過程を知らない評価役が効いたので、同じ形を開発に広げた。

## 採らなかった案

- 実装の役を 1 つのまま、モデルの力に任せる: 受け渡しがなく最も安いが、訂正が領域ごとに貯まらず、自分の実装を確かめるテストしか書かない。
- 言語ごとに 1 役で、テストの役を分けない: 受け渡しが半分で済むが、テストが実装を見て書かれ、§2 の理由で誤りを固める。
- もっと細かい役（React、Storybook など）: 知識が絞れるが、1 つの課題の受け渡しが増え、役ごとの知識が薄すぎて育たない。役の中の領域のファイルで分けられる。
- 束ねる役を今置く: 境界の取り違えを早く拾えるが、繰り返された証拠はまだなく、指揮役が §4 の順で持てることに課題ごとのコンテキストを足す。

## 見直す条件

- 取り決めを先にしても、クライアントとサーバーの食い違いが繰り返される: 束ねる役を足す。
- テストの役が、読めるものだけではテストを書けないと繰り返し返す: 読める範囲か、公開されたインターフェイスの形を見直す。
- 役ごとの決定者の訂正の回数（ADR-0000 §7）が減らない。
