# ADR-0087: 実運用開始後のスキーマ変更とデータの引き継ぎ

- Status: Accepted
- Date: 2026-10-23
- Deciders: @rosylilly
- Issue: #1028

## Context（背景・課題）

[ADR-0012](0012-v0-breaking-change-policy.md) は、v0.x の間 DB スキーマを任意に変え、マイグレーション履歴を持たず、DB を作り直す（`db reset`）と決めている。
[ADR-0023](0023-declarative-schema-management.md) もこの前提に立ち、v0 ではデータを失う差分も `atlas schema apply` で流してよいとしている。
版付きのマイグレーションは v1 に向けた ADR で決めることになっている。

M5 の受け入れ基準は「メンテナのインスタンスが実運用されている」で、v0.x のまま実運用を始める。今の方針のままでは:

- データを失う差分（列・表の削除、型の変更）を含む版に上げると、`schema apply` がそのまま流し、利用者の投稿・フォロー・設定が消える。
  Atlas Community Edition 1.3.0 の `schema apply --auto-approve` は、列の削除を警告なしに適用する（SQLite で確認、2026-10-23）。
  `deploy/docker/compose.yaml` の `schema` サービスはこのフラグで動く。
- 差分を適用できずに作り直すと、鍵暗号化鍵で包んだアカウントの鍵が消え、同じ URI の Actor の鍵が変わる。連合先にはフォロー関係と古い鍵が残るので、
  データの消失より悪い（[docs/operations/database.md](../operations/database.md) の「作り直す」）。
- ADR-0012 は「データ移行ツールは提供しない」としているので、データを書き換える変更の手段がない。

関連: FR-801（DB の初期化。v0 では作り直し）、[ADR-0020](0020-data-modeling-principles.md)（投影は再構築できる。`my projection rebuild` / `verify`、#174）、
[ADR-0082](0082-conflict-free-file-layout.md)（並行の作業で衝突しないファイルの構成、`schema/<dialect>/<NN>-<module>.sql`）、
[ADR-0078](0078-postgres-uuid-columns.md)（PostgreSQL の ID の `uuid` 型化。#1022。Accepted で、#1049 で実装済み）、
[ADR-0084](0084-maintenance-mode.md)（更新の間のメンテナンスモード）。

実運用の開始より前に決めないと、最初の更新でデータを失うので、今決める。

## Decision Drivers（判断基準）

1. 実運用のインスタンスの利用者のデータと連合の関係（Actor の鍵・フォロー）を、更新で失わない
2. 宣言的なスキーマ管理（ADR-0023: 目標スキーマが正、マイグレーション SQL を手で書かない）と、並行の作業で衝突しない構成（ADR-0082）を保つ
3. 運営者の更新の手順が単純である（Compose なら新しいイメージで `up` するだけ。Kubernetes・Cloud Run なら一回限りのジョブ）
4. SQLite と PostgreSQL を同じ規則で扱える
5. v0 の開発の速さを大きく落とさない（破壊的な変更の手間を、必要なときだけ払う）

## Considered Options（選択肢）

1. **今のまま**（ADR-0012・ADR-0023 の v0 の扱い）。破壊的な差分もそのまま適用し、適用できなければ作り直す
2. **宣言的なまま、更新でデータを失わない変更だけを許す**。データを失う変更は 2 段階（expand / contract）に分け、データの書き換えは `my` の冪等な更新の手順（Go）で行う。
   CI で破壊的な差分を検出する
3. **今から版付きのマイグレーションに移る**（ADR-0023 が v1 に予定しているもの）。`atlas migrate diff` で方言ごとのマイグレーションのディレクトリを生成してコミットし、
   データの書き換えはその SQL に書き足し、`atlas migrate apply` で適用する
4. **開発は宣言的、リリースの時に版付き**。`main` では目標スキーマだけを編集し、リリースを作るときに前のリリースの目標スキーマからの差分を
   1 版 1 ファイルのマイグレーションとして生成し、データの書き換えを書き足す

## Decision（決定）

**選択肢 2 を採る。** 宣言的な管理と並行の作業の構成を変えずに、実運用のデータを守れる。破壊的な変更は 2 段階に分ける手間がかかるが、
その手間は破壊的な変更をするときだけで、多くの変更（表・列・索引の追加）には要らない。

見直す条件: データの書き換えを伴う変更が頻繁になる（目安としてマイナー版ごとに複数）か、版を飛ばした更新を保証する必要が出たら
（メンテナ以外の運営者が増えるなど）、選択肢 3 に移る ADR を書く。ADR-0023 が v1 に予定している移行を前倒しすることになる。

### 1. いつから効くか

- **最初のリリース `v0.1.0` から効く。** メンテナのインスタンスはリリースの版だけを動かし、`main` を直接は動かさない。
- `v0.1.0` より前は、今までどおり作り直してよい。運用開始の前に済ませたい破壊的なスキーマ変更は、`v0.1.0` の前に入れる。
  #1022 の `uuid` 型化（ADR-0078）は実装済みなので、この ADR との順序の問題はない。
- `v0.1.0` 以降に `main` に入る PR は、**1 つ 1 つが「直前の `main` から更新できる」スキーマ変更である**ことを求める。
  リリースの時にまとめて揃える形にすると、並行の作業で溜まった変更をリリースの直前に組み直すことになるため。CI の検査（§3）も PR ごとに効かせる。

### 2. 変更の分類と扱い

| 分類 | 例 | 扱い |
| --- | --- | --- |
| A. 追加 | 表・索引の追加、NULL 可の列や `DEFAULT` のある列の追加、制約を緩める | そのまま `schema apply` で適用してよい |
| B. 投影の作り直し | ADR-0020 の投影の表の列の変更・削除・作り直し | 許す。更新の手順（下）で `my projection rebuild` を実行し、元のイベントから作り直す |
| C. データを失う・書き換える | リソース・イベント・現在値の表の列や表の削除、型の変更、列の分割、既存の行が満たさないかもしれない `NOT NULL`・`UNIQUE`・`CHECK` の追加 | 1 つの PR では行わない。下の 2 段階に分ける |

C の 2 段階:

1. **expand（版 N）**: 新しい表・列を A の形で足す。サーバーは新しい側に書き、読むときは新しい側を使う。
   既存の行の書き換えは、`my` に組み込んだ**更新の手順**（Go。キー付き・冪等・小さなトランザクションの繰り返し）で行う。
   手順を実行したことは、イベントの表（`10-infrastructure.sql` に置く。例: `data_upgrade_runs`、手順のキーと完了時刻）に記録する（ADR-0020 規約 1）。
2. **contract（版 N より後のマイナー版）**: 古い列・表を目標スキーマから消す。contract を含む版は、前提とする更新の手順のキーを `my` に持つ。

- 新しい版のサーバーが動く前に、古い版のサーバーが新しいスキーマで短い間動くことがある（スキーマの適用 → サーバーの入れ替え）。
  そのため A の追加は、古い版の書き込みを壊さない形にする（`NOT NULL` の列には `DEFAULT` を付けるか、新しい表に置く）。
  無停止の入れ替えは保証しない。更新の間はメンテナンスモード（ADR-0084）を使える。
- 戻すときは、更新の前に取ったバックアップから戻す。逆向きのマイグレーションは作らない。
- ActivityPub の外部仕様と連合の識別子（Actor URI・投稿 URI）は、ADR-0012 のとおり v0 でも変えない。

### 3. CI での検出

- Atlas Community Edition の `migrate lint` で、破壊的な差分を検出する。CI の中で一時的なマイグレーションのディレクトリを作り
  （空 → 比べる元の目標スキーマ、比べる元 → PR の目標スキーマ、の 2 つを `atlas migrate diff` で生成）、最新の 1 つを `migrate lint --latest 1` にかける。
  コミットするマイグレーションのファイルは作らない（ADR-0023 を保つ）。
- Atlas Community Edition 1.3.0 の `migrate lint` は `atlas login` なしに動く。報告の範囲は次のとおり（2026-10-23 に SQLite と PostgreSQL 18 で確認）。

| 変更 | SQLite | PostgreSQL |
| --- | --- | --- |
| 表の削除・列の削除（列の名前の変更も、削除と追加の差分になる） | エラー（`DS102`・`DS103`、終了コード 1） | 同左 |
| `NOT NULL` にする、`NOT NULL` で `DEFAULT` のない列の追加、一意の索引の追加 | 警告だけ（終了コード 0） | 同左 |
| 型の変更 | 報告しない（表の作り直しで行をコピーする） | 暗黙に変換できる型（`integer` → `bigint`、`text` → `varchar(10)` の縮小も）は報告しない。変換できない型（`text` → `uuid`）は dev DB での実行の失敗として終了コード 1 |
| `CHECK` の追加 | 報告しない | 報告しない |

- そのため CI は、`migrate lint` の終了コードだけでなく、警告を含むすべての診断を失敗として扱う。さらに、比べる元と PR の `atlas schema inspect` を比べ、既存の列の型と `CHECK` の変化も失敗として扱う。
- 比べる元は、PR では `main`、Merge Queue では queue の先頭の基準のコミットの目標スキーマ。SQLite と PostgreSQL の両方で行う。
- 投影の表（B）への破壊的な差分と、contract の PR（C の 2 段階目）は、決定者の承認があるときだけ通す。承認の印は PR のラベルで、PR の実行の検査がラベルを確かめる。
  ラベルがなければ、破壊的な差分の検査は落ちる。
- Merge Queue では承認を確かめ直さない。`merge_group` の event は `head_sha`・`head_ref`・`base_sha`・`base_ref`・`head_commit` だけを持ち、PR の番号やラベルの欄を持たない
  （2026-10-23 に [octokit/webhooks の `merge_group` の schema](https://github.com/octokit/webhooks/blob/aa80c24a3f55354465b8b1438d33dd5602956d0d/payload-schemas/api.github.com/merge_group/checks_requested.schema.json) で確認）。
  Merge Queue は、PR の実行で承認された差分を通し、後から `main` に入った変更と合わせて目標スキーマが適用できることだけを確かめる。
- `docs/operations/database.md` の手順は、`--auto-approve` の前に `--dry-run` で流れる SQL を確かめることを勧める。

### 4. 版の間の更新

- **保証するのは、同じマイナー版の中の更新と、1 つ前のマイナー版（の最新のパッチ）からの更新。** マイナー版を飛ばすときは、各マイナー版の最新のパッチを順に通る。
  contract はマイナー版でだけ行い、パッチ版はスキーマを A・B の範囲でしか変えない。
- 更新の手順（運営者向け、`docs/operations/database.md` に書く）:
  1. バックアップを取る（SQLite はファイルの複製、PostgreSQL は `pg_dump`）
  2. 新しい版の `my db upgrade --check`: この DB に、新しい版の contract が前提とする更新の手順が記録されているかを確かめる。足りなければ、通るべき版を示して止まる
  3. `atlas schema apply`（スキーマのイメージ。今のまま）
  4. 新しい版の `my db upgrade`: 未実行の更新の手順と、作り直しの要る投影の `my projection rebuild` を実行する
  5. サーバーを起動する。readiness は今の「スキーマが適用済み」に加え、必要な更新の手順が済んでいることを確かめる
- `my db upgrade --check` と `my db upgrade` は、運営者が `schema apply` の前後に動かす一回限りのジョブとする（Cloud Run のジョブ、Kubernetes の Job、Compose の一回限りのサービス）。
  `my serve` の起動時には実行しない。複数のインスタンスが同時に起動しても、更新の手順が並んで走らないようにするため。
- Compose では 2〜4 を一回限りのサービスとして `schema` の前後に並べ、`docker compose up -d` だけで済むようにする。
- `db reset`（作り直し）は、公開して連合しているインスタンスでは使わない手順として残す（開発・検証用）。

### 5. ADR-0012 の他の項目

`v0.1.0` 以降も v0.x の間は次を許す。ただしリリースノートに書く。

- 設定キーの変更・削除: 起動時の設定の検査で、消えた・名前の変わったキーを新しい名前とともにエラーにする（黙って無視しない）
- 内部インタフェイス・ディレクトリ構成の変更: 制限しない

クライアント API（`/api/v1`）の安定性は [ADR-0090](0090-third-party-oauth-apps.md) §8 が決める（M5 以降は追加を既定とし、破壊的変更は
`Deprecation`・`Sunset` のヘッダを付けて少なくとも 1 つのマイナー版の間残す）。この ADR は API の扱いを決めない。

リリースノートには、自動で作る変更の一覧（`!` の付いたコミットを含む）に加えて、次の 2 節を必ず置く: **更新の手順**（その版で要る `my db upgrade` と、通るべき版）、
**破壊的変更**（設定キー・API・スキーマの contract）。リリースノートの形は M5 のリリースの作業（エピック #30）で揃える。

### 6. 既存の ADR との関係

- この ADR は ADR-0012 の全体を置き換える（ADR-0012 は `Superseded by ADR-0087`）。ADR-0012 のうち引き続き効く項目（連合の外部仕様と識別子は壊さない、`!` とリリースノート）は、§2・§5 に含めている。
  クライアント API の部分は ADR-0090 が引き継ぐ。
- ADR-0023 は目標スキーマを正とする決定のまま残す。ADR-0023 の「v0 の破壊的変更」の項（データを失う差分も適用してよい、`db-reset`）は、`v0.1.0` 以降はこの ADR が置き換える。
  ADR-0023 の本文は書き換えず、この ADR への参照を追記する（ADR-0000 の「追記は可」）。
- FR-801 の「v0 では作り直し」は、「`v0.1.0` 以降は `schema apply` と `my db upgrade` で更新する」に変わる。

## Consequences（影響）

- 良い影響
  - 実運用のインスタンスで、利用者のデータと Actor の鍵・フォロー関係を、更新で失わない
  - 目標スキーマが正のまま、PR ごとのマイグレーションのファイルも `atlas.sum` もないので、並行の作業で衝突しない（ADR-0082）
  - 多くの変更（追加）は今までどおり目標スキーマを編集するだけで済む
- 悪い影響・トレードオフ
  - 列の削除や型の変更は、2 つのマイナー版にまたがり、間の版では古い列を持ち続ける。開発の手間とスキーマの見通しが少し悪くなる
  - データの書き換えを Go の手順で書くので、SQL 1 文で済む変換でも、手順のコードと記録の表が要る
  - マイナー版を飛ばした更新は保証しない。長く更新しなかった運営者は、版を順に通る必要がある
  - `migrate lint` の検出は Atlas の解析器の範囲に限られ、型の変更と `CHECK` の追加は報告しない。そのため `schema inspect` の比較を自前で足す。意味の変わる変更（値の解釈を変えるなど）はどちらでも検出できず、レビューで見る
  - 古い版のサーバーが新しいスキーマで動く間の互換は「追加は書き込みを壊さない」という規則に頼り、検査は CI の外（レビュー）になる
  - 承認は PR の実行だけで確かめるので、ラベルを付けた後に PR の差分が変わっても、Merge Queue は承認を確かめ直さない。ラベルを付けた後の差分の変化はレビューで見る
- 後続で必要になる作業（issue にする）
  - CI: `scripts/task.sh db:lint`（両方言の `migrate lint` と `schema inspect` の比較、比べる元のスキーマの取り出し）、承認のラベルの作成と PR の実行での確認、PR・Merge Queue の `check` への組み込み
  - `my db upgrade` / `my db upgrade --check`（一回限りのジョブ）、更新の手順の登録の仕組み、記録の表（`10-infrastructure.sql`、データモデルの文書への追加）、readiness の検査の拡張
  - `deploy/docker/compose.yaml` の更新の順序（check → schema → upgrade → my）と `scripts/docker-smoke.sh` での前の版からの更新の検査
  - 設定の検査で、消えた・名前の変わったキーをエラーにする（今の挙動を確かめてから）
  - 文書: `docs/operations/database.md` に「更新する」節（バックアップ、上の手順、戻し方）を足し、「作り直す」を開発・検証用と明記する。
    FR-801 の文言、`schema/README.md` の変更の分類、`docs/agents/releasing.md` のリリースノートの 2 節、ADR-0023 への追記、ADR-0012 の Status
  - リリースの関門（`release.yml`）で、1 つ前のマイナー版のスキーマとデータからの更新を実際に試す検査（スローな検査に入れるか）

## Pros and Cons of the Options（詳細比較・任意）

### 1. 今のまま

- 良い: 手間が一切増えない。スキーマを自由に整理できる
- 悪い: 破壊的な差分を含む版への更新で、実運用のデータを失う。作り直すと連合先と鍵が食い違う。M5 の「実運用」と両立しない

### 2. 宣言的なまま、データを失わない変更だけを許す（採用）

- 良い: ADR-0023・ADR-0082 の構成を変えない。手間は破壊的な変更のときだけ。Atlas Community Edition の範囲（`login` 不要）で検出できる
- 悪い: 破壊的な変更が 2 版にまたがる。データの書き換えのために Go の仕組みが要る。版を飛ばした更新を保証しない

### 3. 今から版付きのマイグレーション

- 良い（最も強い論拠）: 業界で標準のやり方で、Mastodon（Rails のマイグレーション）、GoToSocial（bun のマイグレーション。起動時に適用）、Misskey（TypeORM）も版付きのマイグレーションを使う。
  未適用のものを順に流すので、版を飛ばした更新も自然に扱える。データの書き換えを同じ SQL に書ける。ADR-0023 が v1 に予定しているので、移行の作業を 1 回で済ませられる
- 悪い: PR ごとにマイグレーションのファイルと `atlas.sum` が両方言にでき、並行の作業で必ず衝突する（`atlas.sum` は 1 つのファイル。ADR-0082 と逆行）。
  データの書き換えを方言ごとの SQL で書くことになり、「手で書かない」（ADR-0023）を変える。v0 で生成物のレビューと適用の運用を始める重さがある
- 参考: Mastodon はパッチ版を飛ばしてよいが、マイナー版の系列ごとに少なくとも 1 つの版を経ることを求める（[Upgrading to a new release](https://docs.joinmastodon.org/admin/upgrading/)、2026-10-23 確認）。
  GoToSocial はリリースノートで、起動時にマイグレーションが走るので中断しないよう求め、古い版からは前の版の手順に従うよう案内している（v0.17.4・v0.21.3・v0.22.0 のリリースノート、2026-10-23 確認）。
  Misskey は TypeORM の `migration:run` を `pnpm migrate` で実行し、Docker イメージは起動のたびに `migrate` の後にサーバーを起動する（`migrateandstart`）
  （2026-10-23 に [package.json](https://github.com/misskey-dev/misskey/blob/8f438a8a00ba7f08dfe5fe8db3394c86d82572f3/package.json)・[packages/backend/package.json](https://github.com/misskey-dev/misskey/blob/8f438a8a00ba7f08dfe5fe8db3394c86d82572f3/packages/backend/package.json)・[Dockerfile](https://github.com/misskey-dev/misskey/blob/8f438a8a00ba7f08dfe5fe8db3394c86d82572f3/Dockerfile) で確認）

### 4. 開発は宣言的、リリースの時に版付き

- 良い: PR ごとの衝突がない。リリースの間のマイグレーションは 1 版 1 ファイルで、版を飛ばした更新も扱える。データの書き換えを SQL で書ける
- 悪い: データの書き換えの設計がリリースの直前に集中し、リリースを作る人の負担が大きい。`main` の途中の状態からの更新の経路は試されない。
  生成したマイグレーションと目標スキーマの 2 つの正ができる
