# ADR-0090: OAuth・トークン・セッション

- Status: Accepted
- Date: 2026-10-23
- Deciders: @rosylilly
- Issue: #1038, #90, #1987, #2079

## Decision（決定）

OAuth をサードパーティのアプリに開く。登録の経路は、利用者による登録・Client ID Metadata Document（CIMD）・動的クライアント登録（[RFC 7591](https://www.rfc-editor.org/rfc/rfc7591)、未認証・上限つき）の 3 つで、管理者が無効にできる。どれも同じ認可サーバー（PKCE・ローテーション・失効）に載せる。
クライアント API（`/api/v1`）の安定性の約束はこの ADR の §8 が持つ（[ADR-0023](0023-declarative-schema-management.md) は DB スキーマ・設定・内部インターフェイスを扱い、クライアント API をこの ADR に委ねている）。

### 1. クライアントの登録

- **利用者による登録（設定の画面と client API）**: ログインしている利用者が、名前・サイトの URL・redirect URI・要求できるスコープの上限・種類（public / confidential）を入れてアプリを登録する。
  `oauth_clients.owner_user_id` に登録者を持つ。登録者は編集・削除・シークレットの再発行ができる。サーバーの連携・ボット・自作のクライアント向け。
- **Client ID Metadata Document**（[draft-ietf-oauth-client-id-metadata-document-02](https://datatracker.ietf.org/doc/draft-ietf-oauth-client-id-metadata-document/)、
  2026-07-06 更新の WG 草案で RFC ではない、2026-10-23 確認）: `client_id` が `https` の URL なら、事前登録なしに、その URL の JSON（`client_name`・`client_uri`・`logo_uri`・`redirect_uris` など）を取得してクライアントとして扱う。
  公式のモバイルアプリ・配布される CLI・Web のサードパーティのクライアント向け。
  - 取得は `kernel.HTTPClient`（ADR-0019 §1）を通す。草案に従い、リダイレクトを追わない、`client_id` の完全一致、応答は小さい上限（草案は 5 KB 程度を推奨）、エラーはキャッシュしない、HTTP のキャッシュ指示を尊重する。
  - CIMD のクライアントは public client だけにする（草案は共有シークレットを禁じる。`private_key_jwt` は受けない。§2）。
  - 取得した内容はキャッシュとして持ち（ADR-0020 の投影に近い扱い。再取得で作り直せる）、管理者の無効化はキャッシュではなく `client_id` の URL（とそのホスト）に対して記録する。
- **動的クライアント登録**（[RFC 7591](https://www.rfc-editor.org/rfc/rfc7591)）: `POST /oauth/register` を **認証なし** で受ける（RFC 7591 §3 は初期アクセストークンなしの登録を SHOULD としている、2026-10-23 に確認）。
  CIMD を扱えない汎用のクライアント・ツール向け。
  - 受けるのは public client（`token_endpoint_auth_method: "none"`）だけ。RFC 7591 は省略時の既定を `client_secret_basic` としているが、サーバーは要求されたメタデータを拒否・置き換えてよい（RFC 7591 §2・§3.2.1、2026-10-23 に確認）ので、
    省略時は `none` に置き換えて応答で返し、`client_secret_basic` などを明示した要求は `invalid_client_metadata` で拒否する。シークレットを持つクライアントは利用者による登録で作る。
  - 受けるメタデータは `client_name`・`client_uri`・`logo_uri`・`redirect_uris`・`scope`・`grant_types`・`response_types`。`scope` は一次専用のもの（§4）を除いた範囲に置き換える。
    software statement は受けない。登録したクライアントの読み取り・更新・削除（RFC 7592）は提供しない。変えたいアプリは登録しなおす。
  - **使われないクライアントの自動の削除**: 動的登録のクライアントのうち、登録から 24 時間以内に認可コードが 1 度も交換されなかったもの、または有効なトークン系列がなく最後に使われてから 90 日たったものを、定期のジョブで削除する（既定。設定で変えられる）。
    削除はクライアントのイベントとして記録し、ジョブは冪等にする（ADR-0004）。
  - Mastodon の `POST /api/v1/apps` とは別物で、互換はしない（ADR-0016）。Mastodon 向けのクライアントはどのみち使えない。
- **管理者**: 新しい権限 `manage_oauth_apps` で、全クライアントの一覧（登録の経路で絞り込める）・無効化・無効化の取り消し、CIMD のホスト単位の拒否をする。無効化は監査ログ（ADR-0058）に残し、そのクライアントの全トークンを失効させる。
- **インスタンス設定**: 「利用者によるアプリの登録」「CIMD のクライアント」「動的クライアント登録」をそれぞれ有効・無効にできる。既定はすべて有効。すべて無効なら一次のクライアントだけが使える。

### 2. クライアントの種類とグラント

- **public client**（SPA・ネイティブ・CLI）: シークレットなし、PKCE S256 必須（現行どおり）。
- **confidential client**（サーバーで動く連携・ボット）: 利用者による登録のときだけ選べる。`client_secret` は登録・再発行のとき 1 度だけ表示し、SHA-256 のハッシュで保存する（ADR-0019 §4）。
  認証は `client_secret_basic` と `client_secret_post`。再発行は古いシークレットを即時に無効にする（猶予期間は持たない）。confidential client でも PKCE は必須にする（RFC 9700 §2.1.1）。
  CIMD と動的登録のクライアントは public client だけなので、confidential client は利用者による登録のものに限られる。
- **グラントは `authorization_code` と `refresh_token` だけ。** `client_credentials`（利用者のいないトークン）・`password`・implicit・デバイス認可（RFC 8628）は受けない。
  API の操作はすべて利用者として行う設計で、ボットもボット用のアカウントの利用者として認可する。
- **登録者自身へのトークン発行**: 利用者による登録のアプリは、設定の画面から登録者自身のアカウントへのトークンを、redirect なしに発行できる（ボット・スクリプト向け。Mastodon の「開発」の画面と同じ使い方）。
  発行されるのは通常のアクセストークンとリフレッシュトークンの組（ADR-0019 §4 の有効期限のまま。長命のトークンは発行しない）で、同意の画面の代わりに設定の画面でスコープを選ぶ。
  ボットは、ローテーションされたリフレッシュトークンを保存しながら更新する（[ADR-0093](0093-api-client-library-mykit.md) の `Store`）。

### 3. ネイティブのアプリ（[RFC 8252](https://www.rfc-editor.org/rfc/rfc8252)）

- 許す redirect URI（いずれも利用者・動的登録で登録したもの、CIMD に記載したものと完全一致）:
  - **claimed `https`**（Universal Links / App Links）: 推奨。公式のモバイルアプリはプロジェクトのドメインの URL を使う。OS がドメインとアプリの対応を検証するので、ほかのアプリが横取りできない。
  - **private-use URI scheme**: 逆ドメイン表記（例: `com.example.app:/oauth/callback`、RFC 8252 §7.1）だけを許す。`http`・`https`・`javascript` など既知の危険なスキームは拒否する。
    スキームは OS が検証しないので、どのアプリも同じスキームを名乗れる。
  - **ループバック**: `http://127.0.0.1/...` と `http://[::1]/...`。照合のときポートは無視する（RFC 8252 §7.3）。`localhost` は許さない（RFC 8252 §8.3）。
- `urn:ietf:wg:oauth:2.0:oob` は受けない。
- **private-use URI scheme とループバックは、CIMD ではなりすましを防げない**（動的登録では、どのアプリも任意の名前を名乗れる）。正規のアプリの `client_id` の URL を名乗り、同じスキームやループバックのポートで待つ別のアプリが、正規のアプリの名前の同意の画面からコードを受け取れる
  （[MCP の認可の仕様 2025-11-25](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization) の Localhost Redirect URI Risks、2026-10-23 に確認）。
  そのため、CIMD・動的登録のクライアントの redirect URI が claimed `https` でないときは、同意の画面に redirect URI のホスト（またはスキーム）と「名乗っているアプリと別のアプリかもしれない」という注意を出す（§4）。
  CIMD の草案は、redirect URI を `client_id` と同じオリジンなどに制限してよいとしている（[draft -02 §8.1](https://www.ietf.org/archive/id/draft-ietf-oauth-client-id-metadata-document-02.html)、2026-10-23 に確認）が、ネイティブのアプリとループバックを使えなくなるので制限はしない。
- **公式のモバイルアプリ（#31）**: CIMD のクライアントとして、プロジェクトのサイトに置いた `client_id` の URL を使う。インスタンスにとっては一次のクライアントではないので、同意の画面を必ず出す（信頼済みとして同意を省く設定は持たない）。
  redirect URI には claimed `https` を使う。Tauri 2 の deep link プラグインは iOS の Universal Links・Android の App Links とカスタムスキームを受けられ、
  モバイルではリンクを設定に静的に書く必要がある（[Tauri の文書](https://v2.tauri.app/plugin/deep-linking/)、2026-10-23 に確認）。プロジェクトのドメインに `apple-app-site-association` と `assetlinks.json` を置く。
  OAuth のコールバックを実機で受けられるかは #31 の spike で確かめる。
- **CLI**（`pkg/mykit` を使うもの）: 配布されるものは CIMD + ループバック。個人のスクリプトは利用者による登録 + 登録者自身へのトークン発行。

### 4. スコープと同意の画面

- 現行のスコープの粒度をサードパーティにも使う。ただし次を **一次のクライアントだけのもの** にし、サードパーティには発行しない:
  - `admin` / `admin:read` / `admin:write`（管理の操作は一次の Web クライアントからだけ行う）
  - `write:supporters`（支払いを伴う）
  - アカウントの保安の操作（パスワード・二要素認証・メールアドレス・アカウントの削除・Move（[ADR-0089](0089-account-migration-move.md)）・認可したアプリの管理）は、スコープにかかわらず一次のクライアントだけにする。
- 次の操作も、スコープにかかわらず一次のクライアントだけにする（OpenAPI の `x-first-party-only`）。
  - データのエクスポート: `listDataExports`・`requestDataExport`・`downloadDataExport`・`exportCsv`
  - インポート: `startDataImport`・`previewDataImport`・`listDataImports`
  - 投稿の自動削除の設定の変更とプレビュー: `updateAutoDeletePolicy`・`previewAutoDeletePolicy`（設定の読み取り `getAutoDeletePolicy` は `read:accounts` のまま）
  - 別名の追加と削除: `addAccountAlias`・`removeAccountAlias`（`alsoKnownAs` として公開される情報なので、読み取り `listAccountAliases` は `read:accounts` のまま）
  - 招待の一覧・作成・取り消し: `listOwnInvites`・`createOwnInvite`・`revokeOwnInvite`
  - 異議申し立てと、本人の処分の一覧: `appealModerationAction`・`listOwnModerationActions`
- モデレーターの通知は、操作を閉じるのではなく、サードパーティのトークンから種類で隠す。`notification.ModeratorPermission` に属する種類を、利用者の権限にかかわらず、`FirstParty` でないトークンの通知の一覧・ストリーミングで返さない。未読の位置（`notifications_marker`）の件数にも同じ規則を当てる。Web Push の購読（`putPushSubscription`）でも、そのトークンの `alerts` から黙って落とす。プッシュの本文が同じ情報を運ぶので。
- サードパーティが要求した一次専用のスコープは、黙って落とさず `invalid_scope` にする。
- ダイレクトメッセージ（公開範囲 `direct`）の読み取りは `read:statuses` から分けて `read:direct` にする。`read:statuses` では `direct` の投稿は読めない。広いスコープ `read` は引き続き `read:direct` を含む。
  `direct` の投稿の送信は `write:statuses` のまま分けない。
- **同意の画面**（§16 の Go のフォーム、文言は `server` 名前空間、ADR-0009）に出すもの: アプリの名前、出どころ（CIMD なら `client_id` のホスト名、利用者の登録なら「@登録者 が登録したアプリ」、動的登録なら「自己申告で登録されたアプリ」）、サイトの URL、
  要求するスコープの説明（現行の `scopeDescriptions`）、redirect URI のホスト。DM・投稿の書き込み・プロフィールの変更は注意の表示を付ける。
  redirect URI が claimed `https` でない CIMD・動的登録のクライアントには、§3 のなりすましの注意を付ける。
  **サードパーティのアプリはすべて「このサーバーが確認していないアプリ」と表示する**（確認の制度は持たない）。名前・ロゴはアプリの自己申告で、ホスト名・登録者だけが検証済みの情報だと分かる表示にする。
- 同意は毎回求め、記憶しない（同意の記録のテーブルを持たない）。

### 5. 利用者による管理

- 設定の画面と client API に「認可したアプリ」の一覧を置く: アプリ・出どころ・付与したスコープ・最初に認可した日時・最後に使った日時。取り消すとその利用者とクライアントの組の全トークン系列を失効させる（`oauth_token_revocations` の `user`）。
- データモデル（ADR-0020）:
  - 一覧は有効なトークン系列（`oauth_access_tokens` の `family_id`、失効のイベントがないもの）を利用者とクライアントで束ねて導く。一覧のためのテーブルは持たない。
  - **最後に使った日時** は現在値（規約 5）のテーブル `oauth_token_family_last_used`（系列ごと）に持ち、認証のたびではなく **1 時間に 1 回まで** 更新する（`KeyValueStore` で間引く）。毎リクエストの書き込みを避けるため精度を落とす。
  - 登録の経路（一次・利用者・CIMD・動的）は、クライアントの不変の属性として `oauth_clients` に持つ（`is_first_party` を置き換える）。
  - 管理者の無効化・登録者の削除・使われない動的登録のクライアントの自動の削除はクライアントのイベント（無効化・無効化の取り消し・削除と理由）として記録し、`oauth_clients` に状態のカラムを足さない。
    トークンの失効の理由に `client_disabled` と `client_deleted` を足す。
  - 動的登録の自動の削除の判定は、認可コードの交換（`oauth_authorization_code_redemptions`）・トークン系列・最後に使った日時から導き、判定のためのカラムを足さない。
  - CIMD の取得結果はキャッシュのテーブルに持つ。`oauth_clients` に CIMD の部分型を足すか別テーブルにするかは実装の issue で data-model 文書とあわせて決める。

### 6. メタデータと発見

- **Authorization Server Metadata**（[RFC 8414](https://www.rfc-editor.org/rfc/rfc8414)）を `/.well-known/oauth-authorization-server` で出す
  （`issuer`・各エンドポイント（`registration_endpoint` を含む）・`scopes_supported`（一次専用は除く）・`response_types_supported: ["code"]`・`grant_types_supported`・`code_challenge_methods_supported: ["S256"]`・
  `token_endpoint_auth_methods_supported`、CIMD を示す `client_id_metadata_document_supported`（[draft -02 §6](https://www.ietf.org/archive/id/draft-ietf-oauth-client-id-metadata-document-02.html)、2026-10-23 に確認））。
- **Protected Resource Metadata**（[RFC 9728](https://www.rfc-editor.org/rfc/rfc9728)）を `/.well-known/oauth-protected-resource` で出し、`401` の `WWW-Authenticate` に `resource_metadata` を付ける。どちらも静的な JSON で費用はほぼない。
- OpenID Connect（ID トークン・`/.well-known/openid-configuration`）は提供しない。

### 7. 濫用への対策（NFR-SEC-5、ADR-0019 §5 に足す）

| 対象 | キー | 既定（要検証: 運用で調整） |
| --- | --- | --- |
| API 全体（認証済み） | アカウント（現行。アプリをまたいで合算） | 1,500 / 5 分 |
| API 全体（クライアントごと） | クライアント（全利用者の合算） | 設定で指定。既定は無制限で、管理者が問題のクライアントに上限を付ける |
| アプリの登録（利用者） | 利用者 | 5 / 時、1 利用者あたり 25 件まで |
| 動的クライアント登録 | IP（IPv6 は `/64` に集約） | 5 / 時 |
| 動的クライアント登録（全体） | インスタンス | 100 / 時。超えたら `429` |
| CIMD の取得 | `client_id` の URL / ホスト | URL ごとに 1 / 5 分（キャッシュがあればそれを使う）、ホストごとに 30 / 時 |
| `/oauth/token` | クライアント + IP | 60 / 分 |

- スパムのアプリは、登録の上限・使われない動的登録のクライアントの自動の削除・管理者の無効化（ホスト単位を含む）・「確認していないアプリ」の表示で抑える。
  利用者による登録のアプリは、登録者が凍結・削除されたら無効にする。
- **bot フラグ（FR-006）とは独立**: どのアプリから投稿してもアカウントの bot フラグは変わらない。ボットを動かす利用者が自分で bot フラグを付ける（`pkg/mybot` の文書で案内する）。投稿にアプリの名前は出さない（連合にも出さない）。

### 8. クライアント API の安定性

v0 リリース（M5）以降、`/api/v1` に次を約束する。この節がクライアント API の安定性の方針で、DB スキーマ・設定・内部インターフェイスは [ADR-0023](0023-declarative-schema-management.md) に従う。

- 変更は追加を既定とする（フィールド・操作・スコープの追加、列挙値の追加は破壊的変更と見なさない。クライアントは未知の値を無視する）。
- Web クライアントもこの約束に従う。API の値で引くラベルは `t()` が中立の語にし、ラベル以外（通知の行、アイコン、バッジ）は `lib/known.ts` の `known()` で既定に落とす。`Record` は網羅のまま残し、既知の値の追加を型検査で止める。
- 破壊的変更（削除・名前や型の変更・必須の追加・スコープの意味の変更）は v0 の間も許すが、
  OpenAPI で `deprecated: true` にし、応答に `Deprecation` ヘッダ（[RFC 9745](https://www.rfc-editor.org/rfc/rfc9745)、値は Structured Fields の Date（例: `@1688169599`）、2026-10-23 に確認）と
  `Sunset` ヘッダ（RFC 8594。`Deprecation` の日時より前にしない）を付け、**少なくとも 1 つの v0.x のマイナーリリースの間** は残してから削除する。
  リリースノートに「API の変更」の節を設ける。セキュリティの修正は猶予なしに変えてよい。
- バンドルした OpenAPI をサーバーが `/api/v1/openapi.yaml`（仮）で配り、文書のサイトにも載せる。
- v1.0 では `/api/v1` の破壊的変更をしない（必要なら `/api/v2`）。

### 9. 開発者向けの文書

英語（#1031 の方針）で、登録の 3 つの方法（利用者による登録・CIMD・動的登録。CIMD を優先して案内する）・認可の流れ（PKCE・ネイティブのリダイレクト・CIMD の書き方）・スコープ（一次専用のものを含む）・レート制限と `429`・API の安定性の約束を書く。
**Mastodon 向けのクライアント・ライブラリはそのままでは使えない**（`/api/v1/apps` も Mastodon の API もない。動的登録は RFC 7591 の `/oauth/register`）ことを冒頭に書く。

### 10. ログイン中のブラウザの一覧の行

セッションを単位に、そのセッションの一次の系列を束ねて 1 行にする。系列を単位にすると、同じセッションの系列が別の行に見え、系列のないセッションが一覧から漏れて、なくした端末で新しい系列を得られる資格情報が残る。

利用者のセッションのうち、次のどちらかを満たすものが 1 行になる。

- セッションが有効（失効がなく期限内）
- セッションの状態によらず、そのセッションから始まった **一次のクライアント** の系列に、まだ使えるトークンがある

サードパーティのアプリの系列は数えない。それは「認可したアプリ」の役割で、ここでは終わらない。
一次のクライアントのコードは必ずセッションの中で発行するので（`internal/interface/authpages/authorize.go`）、一次の系列にはセッションがある。

### 11. 行に見せるもの

- ログイン時の User-Agent から求めたブラウザと OS。解釈できなければ元の文字列を見せ、依存は増やさない（Web クライアントの小さな関数）
- ログイン時の IP アドレス。今の場所ではないことが分かる文言にする。位置情報には変換しない
- ログインした日時
- 最後に使った日時: `session_activity.last_seen_at` と、束ねた系列の `oauth_token_family_last_used.last_used_at` の新しいほう（1 時間の精度）
- 今のブラウザの印: API を呼んだアクセストークンの系列が束ねられている行

`session_origins` が無い行（不明、または ADR-0058 の保持期間で消去）は、ブラウザと IP を「不明」と見せる。保存するデータは増やさない。

### 12. ブラウザの一覧の API

すべて `x-first-party-only`（§4）で、利用者本人の分だけを扱う。

| 操作 | スコープ | 動作 |
| --- | --- | --- |
| `GET /api/v1/sessions` | `read:accounts` | 一覧。今のブラウザの行が先頭、以降は最後に使った日時の新しい順 |
| `DELETE /api/v1/sessions/{id}` | `write:accounts` | その行をログアウトする。他人の ID・一覧に無い ID は 404、今のブラウザは 409（ログアウトを使う） |
| `POST /api/v1/sessions/revoke_others` | `write:accounts` | 今のブラウザ以外のすべての行をログアウトする |

### 13. ログアウトで終わるもの

同じトランザクションで、`LockTokenGrants` を取ってから、次を失効させる。

- そのセッション（`logout`。すでに失効していれば何もしない）
- そのセッションから始まった一次のクライアントの系列の全トークン（`user`）

アクセストークンの認証は失効を DB で確かめるので、次の要求から 401 になる。開いているストリーミングは次のハートビートで切れる。
パスワード・二要素認証・サードパーティのアプリは変わらない。画面には、心当たりがないログインにはパスワードの変更と「認可したアプリ」の確認を勧める文を置く。

操作には確認のダイアログだけを出し、パスワードの再入力は求めない。盗まれたブラウザから操作されても持ち主を締め出せるだけで、権限は広がらず、持ち主も同じ操作ができる。

### 14. ログインし直しでの系列の失効

セッションが `replaced` で失効するとき、そのセッションから始まった一次の系列も、同じトランザクションで失効させる。`oauth_token_revocations.reason` に `session_replaced` を足す。
これが無いと、同じブラウザの古い系列が更新トークンの期限まで使える状態で残り、一覧に重複して見える。

### 15. 要件

FR-012 は、利用者が自分のログイン中のブラウザを一覧し、1 つずつ、または今のブラウザ以外をすべてログアウトできることを求める。

### 16. Web クライアントのトークンとログイン画面

トークンの仲介（token-mediating backend）にする。

- **リフレッシュトークン**: Web クライアントでは、`__Host-my_rt` Cookie（`HttpOnly`、`Secure`、`SameSite=Strict`、`Path=/`）に入れる。
- **Cookie を受け付けるのは `POST /oauth/token/refresh` だけにする。** このエンドポイントは、短命のアクセストークンだけを返す。
  - `net/http.CrossOriginProtection` と、必須の独自ヘッダで保護する。
- **アクセストークン**: メモリにだけ置く。`/api/v1` は引き続き Bearer トークンだけで認証する（CSRF の対象外という前提を保つ）。
- **Tauri**: リフレッシュトークンを OS のセキュアストレージに置く。API クライアントのコードは Web と共通で、「リフレッシュトークンの取得」部分だけを差し替える。
- **ログイン・登録・認可同意の画面は、Go が `html/template` で返すフォームにする**（OAuth の認可サーバーの画面）。
  - SPA は Authorization Code + PKCE でこの画面に遷移し、コールバックでコードをトークンに交換する。
  - 画面のスタイルには、Web クライアントのビルドで生成した CSS を共用する。文言は i18n のカタログ（`server` 名前空間）から引く。
  - JavaScript がなくても動くようにする。

### 見直す条件

- 未認証の動的登録がスパムに多用され、上限と自動の削除で抑えられない場合は、動的登録の既定を無効にするか、初期アクセストークン（RFC 7591 §3）を要求する形に変える。
- 主要なクライアントが CIMD に移り、動的登録が使われなくなった場合は、動的登録をやめる。
- CIMD が WG で大きく変わる・放棄される場合は、CIMD の扱いを見直す。
- 利用者による登録のアプリがスパムに多用され、上限と無効化で抑えられない場合は、管理者の承認制を設定で選べるようにする。
- Tauri のアプリ（Cookie のセッションを持たない一次のクライアント）が v0 に入るなら、ブラウザの一覧は系列を単位にする必要がある。
- バックアップや移行のアプリの要望が実際に届き、同意の画面で結果を説明できる方法が見つかったら、エクスポートだけを専用のスコープと同意の画面の警告で開く。
- 通知の種類ごとのスコープを作ることになったら、モデレーターの通知をそちらへ移せないかを見直す。

## 経緯

FR-003 と [ADR-0016](0016-client-api-style.md) は OAuth 2.0（Authorization Code + PKCE）でサードパーティのクライアントを受け入れられる設計にすると決めていたが、クライアントは起動時に登録される一次の Web クライアント（`my-web`、`oauth_clients.is_first_party`）だけで、サードパーティが `client_id` を得る手段がなかった。Tauri 2 のモバイルアプリ（FR-603、#31）は 1 つのアプリが任意のインスタンスにつなぎ、CLI・ボット（[ADR-0093](0093-api-client-library-mykit.md)、[ADR-0093](0093-api-client-library-mykit.md)）と連携サービスも同じ仕組みを要する。M5 の実運用の前に、登録の方法・ネイティブのリダイレクト・利用者による管理・濫用への対策と API の安定性を決めた（FR-006、NFR-SEC-5）。判断基準は、乗っ取り・なりすまし・資源の浪費をするアプリを作りにくいこと（RFC 9700、RFC 8252）、公式のモバイルアプリと CLI がインスタンスごとの手作業なしで使えること、RFC 7591 や CIMD を前提にする汎用のクライアントがそのまま登録できること、未認証で増える行を上限と自動の削除で抑えること（NFR-COST）、利用者が認可したアプリを見て取り消せること、既存の認可サーバーの延長で済むこと、API の変更が告知されること。

Web クライアントのトークンは、当初ブラウザだけで完結する方式（リフレッシュトークンを IndexedDB）だった。2026 年の RFC 10017（OAuth 2.0 for Browser-Based Applications、BCP 212）はこの方式を最も弱いものと位置づけ、ブラウザのストレージはトークンの持ち出しを防げないとする。XSS が 1 度あれば 30 日有効のリフレッシュトークンを盗まれるので、§16 に移した。

ログイン中のブラウザの一覧（FR-002、FR-003、FR-004）: 利用者は「認可したアプリ」で Web クライアントを取り消す（今のブラウザも含めてすべてログアウト）か、パスワードを変えるしかなく、パスワードのない利用者には後者がなかった。ブラウザのログインは 2 つの資格情報でできている。**OAuth トークンの系列**（`__Host-my_rt`）は `/api/v1` の資格情報で、更新のたびに期限が延びる。**セッション**（`__Host-my_session`）はログインと同意の画面の資格情報で、期限は 30 日で固定、一次のクライアントには同意を挟まずコードを発行するので、これだけで新しい系列を得られる。両者は `oauth_authorization_code_redemptions` → `oauth_authorization_codes.session_id` で結ばれるが 1 対 1 ではない（更新はセッションを見ないので系列はセッションより長く生き、Cookie をなくして同じセッションからコードを取り直すと 1 つのセッションに複数の系列ができ、同じブラウザでログインし直すとセッションは `replaced` で失効する）。なくした端末を取り残しなく締め出せること、選んでいないものは終わらないこと、1 行が利用者の考える「1 つのブラウザ」に近いこと、保存データと依存を増やさないことを基準に選んだ。

一次のクライアントだけの操作は、当初 `admin*`・`write:supporters` とアカウントの保安の操作だけだった。`v0.1.0` の前のクライアント API の監査（#2027）で、データのエクスポートが `read:direct` を含む細かい読み取りのスコープを無意味にし、自動削除が `write:statuses` なしで連合先にも届く削除を行い、別名の書き込み・招待・1 回限りの異議申し立て・モデレーターの通知が同意の画面の説明を飛び越えていると分かり、閉じた（#2044）。閉じたものを後から開くのは追加で済むが、開いたものを閉じるには §8 の非推奨の手順が要るので、`v0.1.0` の前に閉じた。同じ issue の残り（`read:follows` がブロックとミュートの状態を返さないこと、`read:favourites` を除くこと、`read:accounts`・`write:accounts` の説明の書き直し）は §4 の変更が要らないので、この ADR の決定に含めない。

FR-003 の本文は [01-functional.md](../requirements/01-functional.md) にある。

## 採らなかった案

- 利用者の登録 + CIMD + 管理者の無効化（RFC 7591 なし）: 登録の行は認証済みの利用者だけが作り、`client_id` の URL のホストが検証済みの手がかりになる（Bluesky の AT Protocol OAuth と同じ方式で、[MCP の認可の仕様 2025-11-25](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization) も CIMD を SHOULD、RFC 7591 を MAY にする。[atproto の文書](https://atproto.com/specs/oauth)と MCP の仕様、2026-10-23 に確認）。RFC 7591 だけに対応する汎用のクライアントが使えず、CIMD は草案で対応するクライアントがまだ限られる。
- 未認証の動的登録だけ: 標準化済みで汎用のライブラリの多くが対応するが、`oauth_clients` が増えつづけ（Mastodon の `POST /api/v1/apps` も認証不要、[Mastodon の文書](https://docs.joinmastodon.org/methods/apps/)、2026-10-23 確認）、同意の画面で出どころを示せず、confidential client の手段が欠ける。
- 利用者の登録だけ: 最も小さいが、公式のモバイルアプリが利用者に `client_id` の入力を強いる。
- 管理者による登録だけ: 管理者がすべて把握でき、スパムの心配がないが、インスタンスごとの手作業が要り、モバイルアプリが多数のインスタンスにつながれない。
- リフレッシュトークンを IndexedDB に置いたまま DPoP を足す: ブラウザの構成は変わらないが、ブラウザのストレージの持ち出しを防げない方式のままである。
- 完全な BFF（ブラウザにはトークンを渡さない）: トークンがブラウザに届かないが、Tauri との共通化を崩す。
- ブラウザの一覧を一次の系列の単位にする: API を使う資格情報に直接対応しクエリが単純だが、系列のないセッションが見えないまま残り、同じブラウザが複数行に見える。
- 一覧を作らず「他のブラウザをすべてログアウト」だけを足す: 画面もクエリも最小だが、身に覚えのないログインに気づけず、なくした端末 1 つのために他の端末もログアウトすることになる。
- エクスポートなどに専用のスコープを足し、同意の画面で警告する（`account:export` など）: 監査の修正案の最も強い対案だが、「すべての投稿と一覧を持ち出す」許可を同意の画面の 1 行で説明できず、スコープの体系も増える。
- 既存の細かいスコープを追加で求める: CSV には当てはまるが、データのアーカイブ（`moderation.json` を含む）と申し立て・別名・招待には対応するスコープがなく、自動削除に `write:statuses` を求めても「投稿を書く」の説明と結果が釣り合わない。
- 変えず、`read:accounts` がこれらすべてを含むとスコープの説明に書く: 説明は正直になるが、取り返しのつかない操作の害が残る。

## Consequences（影響）

- 良い影響
  - 公式のモバイルアプリと配布される CLI が、インスタンスごとの登録なしに任意のインスタンスにつながる。RFC 7591 だけに対応する汎用のクライアント・ツールも、そのまま登録できる。
  - 管理・支払い・アカウントの保安はサードパーティから触れないので、悪意のアプリの被害が投稿・閲覧の範囲に限られる。`read:direct` と細かい読み取りのスコープが、エクスポートで飛び越えられない。アプリが、利用者の投稿をまとめて消す・申し立てを使い切る・登録リンクを作ることができない。
  - XSS でリフレッシュトークンを直接盗まれることはない。アクセストークンは盗まれ得るが、有効期限は短い。
  - なくした端末だけを、パスワードを変えずに締め出せる。パスワードのない利用者にも同じ手段がある。身に覚えのないログインに気づける。同じブラウザでのログインし直しで、使われない更新トークンが残らない。
- 悪い影響・トレードオフ
  - CIMD は RFC になっていない草案で、仕様の変更に追従する費用がある。クライアントの側はメタデータの JSON を置いて URL を `client_id` に使うだけなので、ライブラリの対応は要らない
    （`golang.org/x/oauth2` は PKCE の S256 を持つ。[`oauth4webapi`](https://github.com/panva/oauth4webapi) は RFC 8414 と RFC 9728 の発見を持つ。2026-10-23 に確認）。CIMD の取得はサーバー側の外向きの HTTP で、SSRF の対策（ADR-0019 §1）とレート制限が要る。
  - private-use URI scheme とループバックの CIMD のクライアントは、なりすましを表示の注意でしか防げない（§3）。確認の制度がないので、名前・ロゴのなりすましは表示の工夫（ホスト名・登録者の表示）でしか防げない。
  - 未認証の動的登録で `oauth_clients` の行が増える。上限と自動の削除で抑えるが、削除のジョブと上限の調整の運用が要る。動的登録の名前・ロゴは何の検証もない。
  - 登録の経路が 3 つあり、実装・試験・説明の量が増える。
  - 最後に使った日時は 1 時間の精度しかない。
  - `read:direct` を分けるので、`read:statuses` だけのアプリには DM が見えない（DM を扱うアプリは `read:direct` を求める必要がある）。
  - `/api/v1` の非推奨の期間を守る分だけ、v0 の API の作り直しが遅くなる。
  - `admin` を一次専用にするので、サードパーティの管理ツールは作れない。サードパーティのバックアップ・移行のアプリはデータのアーカイブを使えない。招待の管理や申し立てをサードパーティのクライアントからできない。通知だけは「操作を閉じる」でなく「種類で隠す」ので、規則が 2 種類になる。
  - SPA と API が同じサイトにあることが前提になる（Go が HTML の外枠を返す ADR-0028 の構成では満たされる）。
  - ブラウザの一覧の IP と User-Agent はログイン時のもので、今の場所や端末を表さない。更新トークンで使い続ける間に 180 日を超えると「不明」になる。
  - セッションの Cookie が切れたあとに同じブラウザでログインし直すと、古いセッションを特定できず `replaced` にならない。古い系列は別の行として残る（ログアウトできる。更新されなければ 30 日で消える）。
  - ログインの直後、コードを交換する前に別のタブが古い更新トークンを使うと、失効済みとして Cookie が消え、そのタブはログイン画面に戻ることがある。
  - 通知のメールはない。身に覚えのないログインに気づくには、一覧を見る必要がある。ログアウトでは、そのブラウザから認可したサードパーティのアプリは終わらない。
- 対象外（必要なら別の Issue）
  - 新しいログインの通知メール
  - 管理者が利用者のセッションだけを終わらせる操作（処分の `disable_login` などが、ログインの禁止と一緒に行う）

## Open Questions / 要検証

- 要検証: Tauri 2 のアプリが Universal Links・App Links で OAuth のコールバックを実機で受けられるか（実機が要るため #31 の spike で確かめる）。
- 要検証: §7 のレート制限の既定値と、動的登録の自動の削除の期間（運用の計測が要る）。
