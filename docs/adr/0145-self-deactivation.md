# ADR-0145: 利用者による自分のアカウントの無効化

- Status: Proposed
- Date: 2026-11-03
- Deciders: @rosylilly
- Issue: #2079

## Context（背景・課題）

FR-008 にあるのは、取り消せないアカウントの削除です。データモデルには、ライフサイクルの軸の値として `deactivated`（`account_lifecycle_states`）と、イベント `deactivated` / `reactivated`（[data-model §5.1](../architecture/data-model/05-states-and-policies.md)・[§4.2](../architecture/data-model/04-tables/02-account.md)）があります。`initiated_by` には `self` があります。

`v0.1.0` の前のスキーマの監査（#2027）で、これらを書くコードが無いことが分かりました。使わないなら値を除く、という流れでしたが、決定者は機能を v0 の範囲に入れ、値を残すと決めました。そのため、何をするものかをこの ADR で決めます。投稿を消さずに離れたい人に、削除しかない状態をなくすためです。

いまのコードは次のとおりです。

| 面 | いまの振る舞い |
| --- | --- |
| 無効化・再有効化の操作 | API も画面も無い。テストがイベントを直接記録するだけ |
| サインイン | 正しいパスワードでも、間違いと同じ答えで断る（`identity.checkActive`）。[data-model §5.3](../architecture/data-model/05-states-and-policies.md#53-判定restrictionpolicy) は「本人による無効化は再有効化でログインできる」と書いており、食い違う |
| アクセストークン | 拒否する（`ErrAccountUnavailable`）。失効はしない |
| アカウントの表示 | `active` でなければだれにも出さない（`GET /accounts/{id}` は `404`、検索から除く） |
| タイムライン | 影響しない。`feed_author_restrictions` を作るのは削除と処分だけ |
| 連合 | 何も送らない。Actor の GET・WebFinger・個人の inbox は `404` |
| 削除 | `DeleteBySelf` は、削除済みでなければどの状態からでも通る |
| 消去と自動削除 | 消去は `deleted` だけ。投稿の自動削除は `active` でないアカウントを飛ばす |

凍結には再利用できる部品があります。`Update(Actor)` と `suspended: true` の空の文書（[federation.md §11](../architecture/federation.md#11-モデレーションとの連携)）、処分でサインインした人向けの、サーバーが描く画面（`Access.LoginRestricted`）です。

Mastodon の振る舞いは次のとおりです（2026-11-03 に確認）。

- 利用者向けの無効化はありません。[公式の文書](https://docs.joinmastodon.org/user/moving/)にあるのは移転と、取り消せない削除で、削除の猶予もありません。一時的に隠す機能の要望（[#33869](https://github.com/mastodon/mastodon/issues/33869)、2025-02-08）は開いたままで、メンテナーの回答はありません。
- [モデレーションの文書](https://docs.joinmastodon.org/admin/moderation/)の凍結は、30 日のあいだ戻せます。ログインだけを止める「凍結（freeze）」は、プロフィールとデータを残します。
- [ActivityPub の文書](https://docs.joinmastodon.org/spec/activitypub/)によると、凍結中の Actor は空の文書を返し、`Update` などの対象になります。v4.7.4 の [`process_account_service.rb`](https://github.com/mastodon/mastodon/blob/v4.7.4/app/services/activitypub/process_account_service.rb) は `suspended: true` の文書を受けると `origin: :remote` で凍結し、`suspended` が無くなると戻します。[`suspend_account_service.rb`](https://github.com/mastodon/mastodon/blob/v4.7.4/app/services/suspend_account_service.rb) は、この場合にフォローを切らず、ホームとリストのタイムラインから投稿を外します。

つまり、利用者の無効化は Mastodon に対応する機能がなく、連合では凍結の文書を借りることになります。

## Decision Drivers（判断基準）

1. **戻せること**: 本人が再び始めたとき、投稿・フォロー・フォロワーが元のままであること。
2. **隠れること**: 無効化の間、本人の投稿とプロフィールが、ローカルでも連合先でも、できるだけ見えないこと。
3. **処分を逃れる手段にしないこと**（FR-703）: 処分と独立であり、解除の代わりにならないこと。
4. **閉じ込めないこと**: 本人がいつでも戻れ、削除できること。保安の確認は省かないこと。
5. **実装を増やさないこと**: 凍結の部品と、既存のイベント・投影を使うこと。スキーマを足さないこと（ADR-0020）。
6. **連合の仕様を守ること**: 新しい語彙を作らないこと。

## Considered Options（選択肢）

### 連合での表し方

1. **A: `Update(Actor)` と `suspended: true`** — 凍結と同じ文書で、再有効化で元の文書を送ります。
2. **B: ローカルだけ** — 何も送りません。連合先では、プロフィールと投稿が見えたままです。
3. **C: `Delete`（Actor）を送る** — 連合先から確実に消えます。
4. **D: 投稿ごとの `Delete` と作り直し** — 戻すときに投稿を送り直します。

### 期間

1. **X: 無期限** — 本人が戻すか削除するまで続きます。
2. **Y: 期限のあとに自動で削除する** — X（旧 Twitter）のように 30 日などです（要検証。#33869 の記述による）。
3. **Z: 運営者が期限を設定できる**

### 再有効化

1. **P: サインインしてから、明示的に戻す**
2. **Q: サインインで自動的に戻す**
3. **R: 運営者に頼む**

## Decision（決定）

> 推奨案です。Accepted にするのは人間の Decider だけです。

**連合は A、期間は X、再有効化は P を推奨します。**

### 1. 本人ができること

- 無効化は本人だけが行います。`initiated_by = self` だけで、モデレーターの操作にはしません。処分は処分で行います（FR-703）。
- 一次のクライアントだけの操作にします（ADR-0090 §4）。確認は削除と同じです（パスワード・パスキー・連携先のログインの確認）。
- 次の状態では断ります: 処分でログインできない（`disable_login`・`suspend`・`ban`）、削除の予約中、移転済み、登録の審査中。
- 有料の支援が続いているあいだは断り、先に解約へ案内します。見えない人に課金を続けないためです。
- 無効化の間にできるのは、サインイン・再有効化・削除だけです。パスワードの再設定は使えます。データのエクスポートは再有効化してから行います。
- 無効化の時点で、すべてのセッションとアクセストークンを終わらせます。戻ったとき、アプリは認可をやり直します。
- 無効化と再有効化のどちらでも、本人へメールで知らせます。乗っ取られた場合に気付けるようにするためです。

### 2. ほかの人に見えるもの

- プロフィールは、ローカルでも `404` です（いまのとおり）。検索・おすすめ・メンションの補完からも除きます。
- 投稿は、タイムライン・検索・スレッド・埋め込みから外します。`feed_author_restrictions` の `profile_view` を、`deactivated` でも作り、`reactivated` で除きます。削除と違って行を戻せます。
- ブーストも同じように消えます。引用先としては「表示できない投稿」です。
- フォロー・フォロワー・ブロック・ミュートは残します。一覧からは除きます。ほかの人から見た件数は変えず、再有効化で一覧が元に戻ります。
- この人へのメンションや DM は記録しますが、通知・メール・Web Push は作りません。戻った後に DM は読めますが、留守の間の通知は見られません。
- 新しいフォローは、ローカルからは今のとおり断り、リモートからは `Reject(Follow)` を返します。
- 通話: 開いているルームを終え、参加を終わらせます（凍結と同じ経路）。
- モデレーターの画面には、無効化中であることと、通報を出します。無効化しても通報と処分は続けられます。
- ユーザー名は解放しません。

### 3. 連合（A）

| 契機 | 送るもの | 宛先 |
| --- | --- | --- |
| `deactivated` | `Update(Actor)`（`suspended: true`、プロフィールを空にする） | `Delete`（Actor）と同じ |
| `reactivated` | `Update(Actor)`（元のプロフィール） | 同上 |

- 凍結と同じ `federation.ActorDocument.Suspend` を使います。Actor の GET は、id・コレクション・inbox・鍵を残した最小の文書を返します。WebFinger は答えます。
- 凍結中の無効化と、無効化中の処分では、状態が「見えない」から変わらないので何も送りません。見えるようになるのは、処分が無く、かつ `active` のときだけです。
- 投稿の GET は `404`（`410` にしない）です。`Delete` は送りません。
- 個人の inbox は受け付けます。`404` を返すと相手の配送が永続の失敗となり、`Undo(Follow)` や DM が届かなくなるためです。

C は確実ですが、Mastodon が Actor の `Delete` で投稿とアカウントを消すので、判断基準 1 に反します。D は戻すときに投稿を送り直すことになり、id の再利用と大量の配送が問題です。B が最も強い対案です。送るものが無く、誤解もありません。ただ判断基準 2 を満たしません。

A の代償は、`suspended` の語彙にほかに候補がなく、連合先の UI では「モデレーターに凍結された」ように見えうることです。判断基準 6 からこれを受け入れ、設定の画面で説明します。

### 4. 期間（X）

期限はありません。消去は本人が削除したときだけです。

Y の強みは、残したデータを減らせることと、放置されたアカウントが残らないことです。ただ、無効化は投稿を残すために選ぶものなので、気付かない削除は、取り消せず、判断基準 1 に反します。戻さず消したい人は、いつでも削除できます。Z は運営者の設定を増やし、利用者に見えない規則を作ります。必要になれば、後から足せます。

### 5. 再有効化（P）

- 無効化中の人のサインインは、二要素認証まで含めて通常どおり通り、`Access.LoginRestricted` と同じく、サーバーが描く画面だけに入れます。アクセストークンは出しません。
- 画面には、再有効化と削除を出します。再有効化を押すと、イベント `reactivated` を記録します。
- 再有効化の前に、処分や削除の予約で状態が変わっていれば、その状態の規則に従います。処分は解除されません。

Q は手軽ですが、盗まれたパスワードや、サインインを試すだけの人が、本人の意図と別に公開へ戻してしまいます（判断基準 4）。R は小さなサーバーで運営者の負担になり、判断基準 4 にも反します。

### 6. 繰り返しの上限

再有効化はいつでもできます。無効化は、直前の再有効化から 24 時間たつまで断ります。全フォロワーの宛先への `Update(Actor)` とタイムラインの処理が、繰り返しで重くならないようにするためです。戻る側を止めないのは、判断基準 4 のためです。

### この決定を見直す条件

- Mastodon など主な実装に、本人の無効化を表す語彙ができたら、A の文書を見直します。
- `suspended` を読まない主な実装が多いと分かったら（判断基準 2）、本人への説明を強めるか、期間の案 Y を見直します。
- 無期限の無効化が運営者の保存費用の問題になったら、Z を足します。

## Consequences（影響）

- 良い影響
  - 投稿を消さずに離れられます。スキーマの変更はありません。
  - 処分と独立で、凍結の連合の部品を再利用できます。
- 悪い影響・トレードオフ
  - 連合先で「凍結された」ように見えることがあります。`suspended` を読まない実装には投稿が残ります。
  - 正しいパスワードで「間違い」と答えないので、無効化中であることが、パスワードを知っている人には分かります。
  - フォロワーの件数は、無効化中の人を含みます。データのエクスポートは、再有効化を挟みます。
  - トークンを終わらせるので、戻った後にアプリの認可をやり直す必要があります。
  - 無期限なので、データは本人が消すまで残ります。
- 後続で必要になる作業（Issue 化する）
  - 要件: FR-008 か新しい FR に無効化を足します。data-model §5.3 とサインインの食い違いを、この ADR に揃えます。
  - サーバー: 操作の API、`checkActive` とサーバーが描く画面、セッションの終了、タイムライン・通知・通話・支援の扱い、`Update(Actor)` の projector、個人の inbox の受け付け、無効化の上限、メール。契約テスト（`timeline_contract`・`session_contract`）の更新を含みます。
  - Web: 設定の画面と確認、`locales/en`・`locales/ja`。
  - 文書: `api/spec`、federation.md §7・§11、data-model、利用者向けの案内。

## Open Questions / 要検証

- 要検証: Misskey・Akkoma・GoToSocial が、`suspended: true` の `Update(Actor)` を受けて隠すか、戻るか。ソースもライブの相互運用も確かめていません（`federation-live` で確かめる）。
- 要検証: 表示の経路のすべてが `profile_view` を通るか。監査ではなく設計の読み取りなので、実装の issue で表ごとに確かめます。
