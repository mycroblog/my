# ADR-0145: 利用者による自分のアカウントの無効化は 30 日の猶予で、その後は削除する

- Status: Accepted
- Date: 2026-11-03
- Deciders: @rosylilly
- Issue: #2079

## Context（背景・課題）

FR-008 にあるのは、取り消せないアカウントの削除です。データモデルには、ライフサイクルの軸の値として `deactivated`（`account_lifecycle_states`）と、イベント `deactivated` / `reactivated`（[data-model §5.1](../architecture/data-model/05-states-and-policies.md)・[§4.2](../architecture/data-model/04-tables/02-account.md)）があります。`initiated_by` には `self` があります。

`v0.1.0` の前のスキーマの監査（#2027）で、これらを書くコードが無いことが分かりました。監査の推奨は値を除くことでしたが、決定者は機能を v0 の範囲に入れ、値を残すと決めました。この ADR は、その中身を決めます。無期限に隠せる状態として検討を始め、いったん離れて考え直せる 30 日の猶予として結論を出しました。

いまのコードは次のとおりです。

| 面 | いまの振る舞い |
| --- | --- |
| 無効化・再有効化の操作 | API も画面も無い。テストがイベントを直接記録するだけ |
| サインイン | 正しいパスワードでも、間違いと同じ答えで断る（`identity.checkActive`）。[data-model §5.3](../architecture/data-model/05-states-and-policies.md#53-判定restrictionpolicy) は「本人による無効化は再有効化でログインできる」と書いており、食い違う |
| アクセストークン | 拒否する（`ErrAccountUnavailable`）。失効はしない |
| アカウントの表示 | `active` でなければだれにも出さない（`GET /accounts/{id}` は `404`、検索から除く） |
| タイムライン | 影響しない。`feed_author_restrictions` を作るのは削除と処分だけ |
| 連合 | 何も送らない。Actor の GET・WebFinger・個人の inbox は `404` |
| 削除 | `DeleteBySelf` は、削除済みでなければどの状態からでも通る。予約された削除は 1 時間ごとの `account.execute_deletions` が実行する |
| 消去と自動削除 | 消去は `deleted` から 7 日後。投稿の自動削除は `active` でないアカウントを飛ばす |

凍結には再利用できる部品があります。`Update(Actor)` と `suspended: true` の空の文書（[federation.md §11](../architecture/federation.md#11-モデレーションとの連携)）、処分でサインインした人向けの、サーバーが描く画面（`Access.LoginRestricted`）です。

Mastodon の振る舞いは次のとおりです（2026-11-03 に確認）。

- 利用者向けの無効化はありません。[公式の文書](https://docs.joinmastodon.org/user/moving/)にあるのは移転と、取り消せない削除で、削除の猶予もありません。一時的に隠す機能の要望（[#33869](https://github.com/mastodon/mastodon/issues/33869)、2025-02-08）は開いたままで、メンテナーの回答はありません。
- [モデレーションの文書](https://docs.joinmastodon.org/admin/moderation/)の凍結は、30 日のあいだ戻せます。ログインだけを止める「凍結（freeze）」は、プロフィールとデータを残します。
- [ActivityPub の文書](https://docs.joinmastodon.org/spec/activitypub/)によると、凍結中の Actor は空の文書を返し、`Update` などの対象になります。v4.7.4 の [`process_account_service.rb`](https://github.com/mastodon/mastodon/blob/v4.7.4/app/services/activitypub/process_account_service.rb) は `suspended: true` の文書を受けると `origin: :remote` で凍結し、`suspended` が無くなると戻します。[`suspend_account_service.rb`](https://github.com/mastodon/mastodon/blob/v4.7.4/app/services/suspend_account_service.rb) は、この場合にフォローを切らず、ホームとリストのタイムラインから投稿を外します。

つまり、利用者の無効化は Mastodon に対応する機能がなく、連合では凍結の文書を借りることになります。

## Decision Drivers（判断基準）

1. **考え直せること**: 期限の前に戻れば、投稿・フォロー・フォロワーが元のままであること。
2. **離れていられること**: 無効化の間、本人の投稿とプロフィールが見えず、何も本人へ届かないこと。
3. **離れたまま残さないこと**: 無効化が、データを持ち続ける終わりのない状態にならないこと。
4. **処分を逃れる手段にしないこと**（FR-703）: 処分と独立であり、解除の代わりにならないこと。
5. **閉じ込めないこと**: 本人が期限まではいつでも戻れ、削除できること。保安の確認は省かないこと。
6. **実装を増やさないこと**: 凍結の部品、削除の経路、既存のイベント・投影を使うこと。
7. **連合の仕様を守ること**: 新しい語彙を作らないこと。

## Considered Options（選択肢）

### 連合での表し方

1. **A: `Update(Actor)` と `suspended: true`** — 凍結と同じ文書で、再有効化で元の文書を送ります。
2. **B: ローカルだけ** — 何も送りません。連合先では、プロフィールと投稿が見えたままです。
3. **C: 無効化の時点で `Delete`（Actor）を送る** — 連合先から確実に消えます。
4. **D: 投稿ごとの `Delete` と作り直し** — 戻すときに投稿を送り直します。

### 期間

1. **X: 無期限** — 本人が戻すか削除するまで続きます。
2. **Y: 30 日で削除する** — 期限を過ぎたら、既存の削除の経路で削除します。
3. **Z: 運営者が期限を設定できる**

### 知らせ

1. **M1: 無効化の操作のときに画面で、削除の日付を伝えるだけ**
2. **M2: 無効化と再有効化をメールでも知らせる**
3. **M3: 削除の前に、期限が近いことをメールで知らせる**

### 再有効化

1. **P: サインインしてから、明示的に戻す**
2. **Q: サインインで自動的に戻す**
3. **R: 運営者に頼む**

### 無効化の間に届くもの

1. **I1: 届かない** — メンションと DM を捨て、戻っても読めません。リモートのフォローには `Reject` を返します。
2. **I2: 記録して通知だけ止める** — 戻った後に DM を読めます。
3. **I3: 個人の inbox も `404` にする** — いまのコードの動きです。

## Decision（決定）

**連合は A、期間は Y、知らせは M1、再有効化は P、届くものは I1 とします。**

### 1. 本人ができること

- 無効化は本人だけが行います。`initiated_by = self` だけで、モデレーターの操作にはしません。処分は処分で行います（FR-703）。
- 一次のクライアントだけの操作にします（ADR-0090 §4）。確認は削除と同じです（パスワード・パスキー・連携先のログインの確認）。
- 次の状態では断ります: 処分でログインできない（`disable_login`・`suspend`・`ban`）、削除の予約中、移転済み、登録の審査中、有料の支援が続いている。支援は解約へ案内します。見えない人に課金を続けず、期限の削除で課金の扱いが問題にならないようにするためです。
- 無効化の間にできるのは、サインイン・再有効化・削除だけです。パスワードの再設定は使えます。データのエクスポートは再有効化してから行います。
- 無効化の時点で、すべてのセッションとアクセストークンを終わらせます。戻ったとき、アプリは認可をやり直します。

### 2. 期間と削除（Y）

- 無効化から 30 日（`deactivated` の `since` から 30 × 24 時間）で削除します。`account.execute_deletions` が期限を過ぎた `deactivated` を読み直して、`initiated_by = system` の `deleted` を記録します。以後は本人の削除と同じ経路で、このときに `Delete`（Actor）を送り（[federation.md §7.1](../architecture/federation.md)）、7 日後に消去します。ユーザー名は解放しません。
- スキーマは変えません。期限は `since` から求めます。`deletion_due_at` は `deletion_scheduled` のものなので、`deactivated` では使いません。
- 期限の前なら必ず再有効化でき、期限を過ぎたら、ジョブが記録するまでの隙間でも断ります。戻った後の無効化は、`since` が変わるので 30 日を数え直します。
- 無効化の間に処分を受けても期限は変わりません。`ban` は `deletion_scheduled` に移るので、その時点から再有効化できず、`ban` の期日に従います。`ban` の取り消しの `deletion_cancelled` は、いまの畳み込みのとおり `active` に戻します。保全（`retention_holds`）は消去を止めるだけで、削除は止めません。

X の強みは、取り消せない削除が本人の操作でしか起きないことです。ただ、離れた人のデータを無期限に持ち続けることになり（判断基準 3）、連合先に残る凍結の表示にも終わりがありません。投稿を残して離れたい人には、削除の前のエクスポートと移転があります。Z は、利用者に見えるサーバーごとの規則を増やします。

### 3. 知らせ（M1）

無効化の確認と完了の画面で、削除の日付を伝えます。これが唯一の知らせで、削除の前のメールはありません。再有効化の画面も、日付を改めて知らせる場にはしません。

M2 と M3 は、メールを読まなくなった人や、気付かないまま削除される人を減らせます。乗っ取りにも気付けます。ただ、離れると決めた人へ後から連絡すること自体が、この機能の目的に反します（判断基準 2）。代償は Consequences に書きます。

### 4. 再有効化（P）

- 無効化中の人のサインインは、二要素認証まで含めて通常どおり通り、`Access.LoginRestricted` と同じく、サーバーが描く画面だけに入れます。アクセストークンは出しません。
- 画面には、再有効化と削除のボタンを出します。再有効化を押すと、イベント `reactivated` を記録します。
- 処分は解除されません。再有効化の後も、処分の規則に従います。無効化の間に処分でログインを止められた人も、同じ画面から再有効化できます。

Q は手軽ですが、盗まれたパスワードや、サインインを試すだけの人が、本人の意図と別に公開へ戻してしまいます。R は小さなサーバーで運営者の負担になり、期限のある仕組みでは間に合わないことがあります（判断基準 5）。

### 5. ほかの人に見えるもの

- プロフィールは、ローカルでも `404` です（いまのとおり）。検索・おすすめ・メンションの補完からも除きます。
- 投稿は、タイムライン・検索・スレッド・埋め込みから外します。`feed_author_restrictions` の `profile_view` を、`deactivated` でも作り、`reactivated` で除きます。削除と違って行を戻せます。
- ブーストも同じように消えます。引用先としては「表示できない投稿」です。
- 通話: 開いているルームを終え、参加を終わらせます（凍結と同じ経路）。
- モデレーターの画面には、無効化中であることと通報を出します。無効化しても通報と処分は続けられます。

### 6. 無効化の間に届くもの（I1）

- **メンションと DM は、ローカルからもリモートからも捨てます。** 戻っても読めません。
  - ローカルの投稿では、存在しないユーザーの名前と同じように扱います。名前は本文の文字のまま残り、宛先にもメンションにもなりません。投稿した人には何も伝えません。
  - リモートの投稿では、この人への `Mention` と宛先を無視します。宛先がこの人だけの投稿は保存しません。
  - 捨てるのはこの人への宛先で、投稿そのものではありません。ほかの人に見える投稿は残り、戻った後に公開の投稿として読めることはあります。
- **通知・メール・Web Push は作りません。** お気に入りとブーストは投稿の数として記録しますが、通知しません。
- **リモートの新しいフォローには `Reject(Follow)` を返します。** 戻っても復元しません。

**フォローとフォロー申請**は、戻るときに元のままであるよう、次のとおりにします（判断基準 1）。

| 対象 | 振る舞い |
| --- | --- |
| すでにあるフォロー（両方向、ローカル・リモート） | 残す。無効化しても切らない。ほかの人の一覧からは除き、件数は変えない |
| ローカルからの新しいフォロー | いまのとおり、存在しない相手と同じく断る。戻っても復元しない |
| 無効化の前に届いていた、この人への申請 | 待ちのまま残す。相手には待ちのまま見える。答えるのは戻った後で、期限の削除で終わる |
| この人が出していた申請 | 残す。相手の一覧からは除く（いまのとおり）。リモートの `Accept` / `Reject` は処理する |
| ほかの人によるフォローの解除 | リモートの `Undo(Follow)` は処理する。ローカルの人はプロフィールを開けないので、無効化の間は解除できない（いまのとおり） |

新しいものは拒み、すでにあるものは触りません。これなら、戻った人にとっても相手にとっても、関係は無効化の前と同じです。

**個人の inbox は受け付けます**（`202`）。`404` では `Reject(Follow)` を返せず、相手の配送が永続の失敗になって、`Undo(Follow)` や `Accept` も届かなくなります（I3 を採らない理由）。`Follow` は `Reject` し、関係と Actor についての活動は処理し、この人への `Create` は上の規則で捨てます。shared inbox も同じで、ほかの宛先には影響しません。

I2 の強みは、DM を失わないことです。ただ、戻った途端に留守の間のものが届くので離れていられず（判断基準 2）、削除される 30 日の間の記録を増やすだけです。送った人には届いたように見えることは、I1 の代償として受け入れます。

### 7. 連合（A）

| 契機 | 送るもの | 宛先 |
| --- | --- | --- |
| `deactivated` | `Update(Actor)`（`suspended: true`、プロフィールを空にする） | `Delete`（Actor）と同じ |
| `reactivated` | `Update(Actor)`（元のプロフィール） | 同上 |
| 30 日後の `deleted` | `Delete`（Actor）（§2） | 既存の経路 |

- 凍結と同じ `federation.ActorDocument.Suspend` を使います。Actor の GET は、id・コレクション・inbox・鍵を残した最小の文書を返します。WebFinger は答えます。
- 凍結中の無効化と、無効化中の処分では、状態が「見えない」から変わらないので何も送りません。見えるようになるのは、処分が無く、かつ `active` のときだけです。
- 投稿の GET は `404`（`410` にしない）です。投稿ごとの `Delete` は送りません。

C は確実ですが、Mastodon が Actor の `Delete` で投稿とアカウントを消すので、判断基準 1 に反します。D は戻すときに投稿を送り直すことになり、id の再利用と大量の配送が問題です。B が最も強い対案です。送るものが少なく、誤解もありません。ただ判断基準 2 を満たしません。

A の代償は、`suspended` の語彙にほかに候補がなく、連合先の UI では「モデレーターに凍結された」ように見えうることです。判断基準 7 からこれを受け入れ、無効化の画面で説明します。

### 8. 繰り返しの上限

再有効化はいつでもできます。無効化は、直前の再有効化から 24 時間たつまで断ります。全フォロワーの宛先への `Update(Actor)` とタイムラインの処理が、繰り返しで重くならないようにするためです。戻る側を止めないのは、判断基準 5 のためです。

### この決定を見直す条件

- Mastodon など主な実装に、本人の無効化を表す語彙ができたら、A の文書を見直します。
- `suspended` を読まない主な実装が多いと分かったら（判断基準 2）、本人への説明を強めます。
- 気付かないまま削除されたという報告や、乗っ取りによる削除が起きたら、M2 か M3 を見直します。

## Consequences（影響）

- 良い影響
  - 投稿を消さずに、30 日のあいだ離れて考え直せます。スキーマの変更はありません。
  - 無効化が終わりのない状態にならず、データは期限で消えます。
  - 処分と独立で、凍結の連合の部品と削除の経路を再利用できます。
- 悪い影響・トレードオフ
  - **取り消せない削除が、本人の操作なしに起きます。** 無効化したことを忘れた人は、知らせなしに投稿とアカウントを失います。
  - **パスワードを盗んだ人が無効化すると、本人へ知らせないまま 30 日で削除されます。** 確認と二要素認証だけが守りです。本人はセッションが切れたことで気付けるだけです。
  - 留守の間の DM とメンションは失われ、送った人には分かりません。
  - 連合先で「凍結された」ように見えることがあります。`suspended` を読まない実装には投稿が残ります。
  - 正しいパスワードで「間違い」と答えないので、無効化中であることが、パスワードを知っている人には分かります。
  - フォロワーの件数は、無効化中の人を含みます。データのエクスポートは、再有効化を挟みます。
  - トークンを終わらせるので、戻った後にアプリの認可をやり直す必要があります。
- 後続で必要になる作業（Issue 化する）
  - 要件: FR-008 か新しい FR に無効化を足します。data-model §5 の記述とサインインの食い違いを、実装の PR でこの ADR に揃えます。
  - サーバー: 操作の API、`checkActive` とサーバーが描く画面、セッションの終了、`account.execute_deletions` の期限、タイムライン・通知・通話の扱い、メンションと DM の破棄、`Update(Actor)` の projector、個人の inbox の受け付けと `Reject(Follow)`、無効化の上限。契約テスト（`timeline_contract`・`session_contract`）の更新を含みます。
  - Web: 設定の画面と確認、削除の日付の表示、`locales/en`・`locales/ja`。
  - 文書: `api/spec`、federation.md §7・§11、利用者向けの案内。

## Open Questions / 要検証

- 要検証: Misskey・Akkoma・GoToSocial が、`suspended: true` の `Update(Actor)` を受けて隠すか、戻るか。ソースもライブの相互運用も確かめていません（`federation-live` で確かめる）。
- 要検証: 表示の経路のすべてが `profile_view` を通るか。設計の読み取りなので、実装の issue で表ごとに確かめます。
