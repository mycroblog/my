# ADR-0167: UX の計測（実際の利用者と CI）

- Status: Accepted
- Date: 2026-11-12
- Deciders: @rosylilly
- Issue: #2863

## Decision（決定）

### 1. 測るもの

利用者が体感するものだけを測る。押してから応えるまで（INP）、画面が出るまで（LCP）、長いタスク、エントリごとのバンドルの大きさ、通話の品質（RTT・ジッタ・パケットロス）。「良好」の目安は INP 200 ms 以下、LCP 2.5 s 以下（web.dev の Core Web Vitals、2026-11-12 に確認）。文字数や部品の数のような、体感と結びつかない量は測らない。

### 2. 機能にコードを書かせない

計測は層の持ち物から自動で決まる（ADR-0025 §4）。

- 遷移とフィードバックの種類はデザインシステムが持つので、遷移ごと・押下ごとの時間はデザインシステムが 1 か所で測る。
- 操作の名前は、ショートカットと同じ操作の ID（`post.reply`）を使う。遅い操作が、機能の側で何もしなくても名前で分かる。
- ルートの名前は app が付け、LCP をどの画面のものか区別する。
- 計測の仕組み（Web Vitals、Long Animation Frames）は platform が持ち、Tauri でも同じ形で使う。送り先はデザインシステムと通話（ADR-0101）に差し込む。

### 3. 実際の利用者のデータ

標本を取り、人を特定できるものを含めず、インスタンス自身のサーバーへ送る。経路はエラーの報告（ADR-0103 §6）と同じにし、管理画面で見られ、OpenTelemetry（ADR-0055）でも外に出せる。インスタンスの設定で止められる。

### 4. CI のデータ

E2E のシナリオ（ADR-0015 §5）を CPU を絞って動かし、§1 を測る。

## 採らなかった案

- 外部の RUM のサービスに送る: 集計と画面がそろうが、利用者のデータがインスタンスの外へ出る。
- 機能ごとに計測のコードを書く: 細かく測れるが、書き忘れた画面が測られず、書く手間が機能ごとに増える。
- CI だけで測る: 利用者のデータを集めないが、実際の端末と回線の遅さが分からない。

## 見直す条件

- 標本でも送る量がサーバーの費用を目に見えて増やす（NFR-COST）。
- 測った値が体感と食い違う画面が続く: 測るものか目安を見直す。
