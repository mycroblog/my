# ADR-0156: 投稿の下書きと予約投稿をサーバーに持つ

- Status: Accepted
- Date: 2026-11-09
- Deciders: @rosylilly
- Issue: #2575

## Decision（決定）

どの節も決定者が決めた事項である。§4 のテーブルの形は、記事（#2590）が子の行を足せない形だと分かれば見直す。
§6 の時刻どおりの公開は今のキューの実装で成り立つことをコードで確かめた。外部のキューに合図ではなくジョブそのものを積むアダプタを加えるときは見直す。

### 1. 範囲

- 下書きと予約投稿は `v0.1.0` に入れる。下書きはサーバーに保存し、別の端末で続きを書いて、すぐ公開するか、決めた時刻に公開する。
- 下書きは本人だけのものである。連合しない、ActivityPub の表現を持たない、モデレーターも見ない、通報できない。
- 予約投稿は、公開の時刻を持つ下書きである。予約を取り消すと、ただの下書きに戻る。

### 2. 検査は公開のときにする

- 処分（投稿の制限 `post`、公開範囲の上限、凍結）と投稿の自動削除の設定（FR-118）は、予約したときではなく公開するときの状態で判断する。
  公開範囲の上限に当たったときは、すぐの投稿と同じく黙って切り詰め（data-model §5.4）、失敗にしない。
- 予約のときにも同じ検査をして、明らかに通らない予約は 422 で断る。通っても公開のときに検査し直す。
- 公開できなかった予約は失敗として記録し（§5）、作者に通知する（§8）。下書きはそのまま残り、直して予約し直せる。
- 投稿の時刻は実際に作った時刻である。`statuses.id`（公開日時の UUIDv7）と `published_at` は公開のときに作り、下書きの ID とは別である。
  自動削除の日数もそこから数える。

### 3. 記事と同じテーブルを使う

記事（#2590、#2594）の下書きは、このテーブルの下書きに記事の子の行（題・要約・カバー・入力の形式）を足したものである。予約は記事にも働く。
そのため下書きの種類は列ではなく部分型のテーブルの有無で表し（ADR-0020 規約 4）、記事は `drafts` を指す自分の子テーブルを足すだけで済む形にする（§4）。
記事の子テーブルの中身は記事の ADR が決める。

### 4. テーブル（data-model §4.4「下書きと予約投稿」）

所有するモジュールは `content` である。JSON は使わない。

| テーブル | 分類 | 中身 |
| --- | --- | --- |
| `drafts` | リソース | `id`, `account_id`, `created_at`。下書きそのもの |
| `draft_contents` | 現在値 | 本文の入力・CW・センシティブ・言語・公開範囲・返信先・引用先と引用の許可・`updated_at`。保存のたびに置き換える |
| `draft_attachments` | 現在値 | 位置・`media_id`・代替テキスト |
| `draft_polls` / `draft_poll_options` | 現在値 | 複数選択・票数を隠す・期間（秒）と選択肢 |
| `draft_schedules` | リソース | `id`, `draft_id`, `publish_at`, `created_at`。1 回の予約 |
| `draft_schedule_outcomes` | イベント | `schedule_id`（PK）, `outcome`（`enum(published, failed, cancelled)`）, `failure_reason`（`failed` だけ）, `occurred_at` |
| `scheduled_drafts` | 投影 | `draft_id`（PK）, `schedule_id`（一意）, `account_id`, `publish_at`。結果の行の無い予約 |

- 中身を現在値にするのは、下書きの保存が頻繁で（自動保存）、その履歴を監査・モデレーション・連合・利用者への説明のどれにも使わないからである（ADR-0020 規約 5）。版のイベントにすると、自動保存のたびに個人データの版が増える。
- 予約はリソース、その終わりはイベントにする（ADR-0020 規約 1・2）。時刻の変更は、今の予約の `cancelled` と新しい予約である。状態を表す NULL 許容の時刻の列は持たない。
- `scheduled_drafts` は 1 つの下書きに有効な予約を 1 つまでに保ち（PK）、上限の数え上げ（§7）と予約の一覧に使う。`content` の projector が予約と結果を記録するトランザクションで同期に更新し、結果の行の無い `draft_schedules` から作り直せる。
- 投票は締め切りの時刻ではなく期間を持ち、公開のときに `closes_at` を決める。返信先・引用先は投稿の ID で持ち、公開のときに見られるかを確かめ直す。
- 公開した下書きは、投稿を作るトランザクションで行をすべて消す（ADR-0020 規約 6）。中身は投稿の版に移り、下書きに個人データを二重に残さない。取り消しと失敗の結果の行は下書きを消すまで残り、失敗の理由を画面に出すのに使う。
- アカウントの消去は下書きの行もすべて消す。
- 下書きはアカウントのデータのエクスポートに入れない。公開した投稿ではないからである。

### 5. 公開のジョブ

- 予約は、予約を記録するトランザクションで outbox に `content.publish_scheduled_draft`（`RunAt` = `publish_at`、ペイロードと冪等キーは予約の ID）を積む（ADR-0004）。
- ジョブは、`scheduled_drafts` の行がその予約を指すときだけ公開する。取り消された・時刻を変えた予約のジョブは何もせずに終わる。キューから消しには行かない。
- 公開は、すぐの投稿と同じコマンド（`content.Service.Create`）を通す。文字数・添付の `ready`・外部の審査（`hook_local_status_mode`）・返信と引用の検査は、すぐの投稿と同じに働く。
- 外部の審査（`local.status`、ADR-0147）は公開のときにだけ呼び、予約のときには呼ばない。審査の回数と費用が倍になり、結果は公開のときに変わり得るからである。
- 2 回の実行で 2 つの投稿を作らないように、コマンドの冪等キー（`local_statuses (author_account_id, idempotency_key)`）を下書きの ID から作る。同じトランザクションで `scheduled_drafts` の行を消し、`published` を記録して下書きを消す。同時の 2 つの実行は一意制約で 1 つだけが通る。
- 公開できないとき（処分・返信先や引用先が見られない・添付が使えない・検査で断られた・外部の審査で断られた）は、`failed` と理由を記録して `scheduled_drafts` から外す。理由の値は `enum` で、作者の画面と通知に出す。
- 一時的な失敗（DB や外部の審査に届かない）は失敗として記録せず、ジョブの再試行に任せる。再試行が尽きて死んだジョブは管理画面に出る（ADR-0004）。

### 6. 外部のキューの遅延の上限を超える予約も時刻どおりに動く

`internal/app/queue` のコードで確かめた（2026-11-09）。

- ジョブは常に DB のキュー（`jobs`）にあり、外部のキュー（Cloud Tasks）はジョブの ID を運ぶ合図だけを持つ（ADR-0004 §9）。合図が遅れても失われても、ジョブと `RunAt` は消えない。
- Cloud Tasks の上限（`cloudtasks.MaxDelay`、30 日）より先の合図は、`queue.NextVisible` が上限の時刻に送る。早く届いた合図は `PushReceiver.Receive` が `ClaimNotDue` を受けて `RunAt` で送り直す（再投入のチェーン）。30 日ごとに 1 回の合図が増えるだけで、最後の合図は `RunAt` に届く。
- 失われた合図は、定期のジョブ `queue.wake` が、`RunAt` から猶予（`DefaultWakeGrace`、2 分）を過ぎてもリースのないジョブに送り直す。遅れの上限はこの猶予と掃除の間隔である。
- `queue = db` の pull のワーカーは `RunAt` を見て取るだけなので上限がない。`inline` も `MaxDelay` で同じ再投入のチェーンを再現して試せる。SQS のアダプタは無い（ADR-0004 は SQS の常駐ワーカーをやめた）。
- そのため予約のための掃除のジョブは別に作らない。実装のタスク（#2576）は、`inline` の `MaxDelay` で上限を超える予約が時刻に公開されるテストを持つ。

### 7. 上限

インスタンス設定（data-model §4.9、1 キー 1 スカラー）に置く。

| キー | 既定値 | 数えるもの |
| --- | --- | --- |
| `max_drafts` | 100 | 予約の無い下書き |
| `max_scheduled_posts` | 300 | 有効な予約（`scheduled_drafts`） |
| `max_scheduled_posts_per_day` | 25 | `publish_at` が同じ UTC の日にある有効な予約 |
| `scheduled_post_min_lead_minutes` | 5 | 予約できる最も近い時刻（今からの分） |
| `scheduled_post_max_lead_days` | 366 | 予約できる最も遠い時刻（今からの日） |

- 既定値は Mastodon の `ScheduledStatus` の `TOTAL_LIMIT = 300`・`DAILY_LIMIT = 25` に合わせる（2026-11-09 に mastodon/mastodon の `app/models/scheduled_status.rb` で確認）。最も近い時刻の 5 分は Mastodon の `MINIMUM_OFFSET` と同じである。下書きの 100 と最も遠い時刻の 366 日は本 ADR の値である。
- 上限を超える保存・予約は、上限の値を含むローカライズした問題（422）で断る。上限を下げても既にある下書きと予約は消さず、新しく作れないだけである。

### 8. 失敗の通知

- 予約の失敗は、作者に通知 `scheduled_status_failed`（差出人なし、下書きの ID と理由）を 1 回作る（冪等キーは予約ごと）。アプリ内でオフにでき、Web Push は選べる。メールでは送らない。
- 公開の成功は通知しない。投稿が自分のタイムラインに現れる。

### 9. API

`POST /statuses` に `scheduled_at` を足さず、`/api/v1/drafts` を持つ（Mastodon のクライアント API とは合わせない、ADR-0016）。

| 操作 | 中身 |
| --- | --- |
| `POST /drafts`・`GET /drafts`・`GET /drafts/{id}`・`PUT /drafts/{id}`・`DELETE /drafts/{id}` | 下書きの作成・一覧（`scheduled` で絞る、キーセット）・読み取り・中身全体の置き換え・削除 |
| `PUT /drafts/{id}/schedule`・`DELETE /drafts/{id}/schedule` | 予約（時刻の変更を含む）と取り消し（`cancel`） |
| `POST /drafts/{id}/publish` | すぐ公開する。作った `Status` を 201 で返し、下書きは消える |

- `PUT /drafts/{id}` は `If-Match` に前に読んだ下書きの `updated_at` から作る ETag を求め、別の端末が先に保存していれば 412 を返す。端末をまたいで書き継ぐときに、黙って上書きしないためである。
- 予約された下書きも編集できる。公開は公開の時点の中身を使う。
- `pkg/mykit` は同じ操作を持つ（ADR-0093）。

## 経緯

コンポーザーは下書きをブラウザ（`app/web/src/features/compose/hooks/draftStore.ts`）にだけ持ち、別の端末では続きを書けず、決めた時刻に公開することもできない。GoToSocial 0.20・Sharkey・Misskey・Pleroma は予約投稿を持つ。

決定者は、下書きと予約を `v0.1.0` に入れること、処分と自動削除を公開のときに判断し投稿の時刻を実際に作った時刻とすること、記事が同じテーブルを使うことを決めた。続いて、上限と予約の範囲をインスタンス設定に置くこと、公開範囲の上限は黙って切り詰めること、下書きをエクスポートに入れないこと、失敗の通知をメールで送らないこと、外部の審査を公開のときにだけ呼ぶことを決めた。そこから、下書きの中身を版ではなく現在値で持つこと、予約をリソースと結果のイベントに分けること、冪等キーを今の投稿の一意制約に乗せることを詰めた。

予約が外部のキューの遅延の上限を超えるときの扱いは未決だったので、`internal/app/queue/push.go`・`wake.go`・`retry.go` と `internal/adapter/queue/cloudtasks/waker.go` を読み、今の再投入のチェーンと `queue.wake` の掃除で足りると確かめた（§6）。

## 採らなかった案

- `POST /statuses` に `scheduled_at` を足す（Mastodon の形）: 既存のクライアントに馴染むが、予約の一覧・取り消し・編集のために結局 `/scheduled_statuses` の別の資源が要り、下書きと二重になる。Mastodon のクライアント API の互換も持たない（ADR-0016）。
- 下書きを投稿の行（`statuses`）に未公開の状態として持つ: 一覧と表示の経路を共有できるが、すべての読み取りと連合が未公開を除く責任を負い、`id` が公開時刻にならない。可視性のポリシー関数を 1 か所に保つ規則とも合わない。
- 下書きの中身を版のイベントにする（ADR-0020 規約 1）: 投稿と同じ形になるが、自動保存のたびに版が増え、使い道のない個人データの履歴が残る。
- Mastodon のように予約の入力を 1 つの JSON（`params`）に入れる: 表は少ないが、添付の参照（未添付の掃除）・返信先・上限の数え上げを問い合わせられず、ADR-0020 規約 4 に反する。
- 予約の公開を定期の掃除のジョブ（毎分、期限の来た予約を探す）で行う: キューの遅延の上限を気にしなくてよいが、`RunAt` と `queue.wake` が同じことを既にしており、掃除の分の読み取りと遅れが増える。
- 予約のときにだけ処分を判断する: 予約の後に投稿を禁じられた人の投稿が出てしまう。決定者の判断（§2）に反する。

## Consequences（影響）

- 良い: 端末をまたいで書き継げ、記事も同じ仕組みで予約できる。公開は今の投稿のコマンドを通るので、検査・外部の審査・連合・通知が二重にならない。
- 良い: キューに手を入れずに、外部のキューの上限を超える予約が動く。
- 悪い: 公開のときの失敗は利用者には遅れて分かる。予約のときの検査で多くは防ぐが、処分や返信先の削除は防げない。
- 悪い: 取り消した予約のジョブが `RunAt` までキューに残り、30 日ごとに合図が 1 回増える。上限（300）があるので量は小さい。
- 悪い: 下書きを持つ添付は未添付の掃除から外れるので、下書きの上限の分だけ Blob が残る。
- 後続の作業:
  - #2576: §4 のテーブル（`schema/<dialect>/` の content のファイル）、`media.purge_unattached` が `draft_attachments` の参照を添付として数えること（下書きを消すと、そのファイルは次の実行で消える）、公開のジョブと結果、通知、上限の設定、API と `pkg/mykit`、`docs/reference/jobs.md` と設定の文書。
  - #2577: コンポーザーの下書き一覧・自動保存・予約の UI（web-client の画面の L1 を先に書く）。
  - #2594: 記事の子テーブルを `drafts` に足す。
  - 下書きと予約の FR を `docs/requirements/01-functional.md` に加える。
