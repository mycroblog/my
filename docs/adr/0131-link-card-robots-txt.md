# ADR-0131: リンクカードの取得で robots.txt とページのロボットの指定に従う

- Status: Proposed
- Date: 2026-11-02
- Deciders: @rosylilly
- Issue: #1947, #1949

## Context（背景・課題）

リンクカード（FR-117、[ADR-0062](0062-link-preview-cards.md)）の取得は `robots.txt` を読まず、ページの `<meta name="robots">` と `X-Robots-Tag` も読まない。相手のサイトの運営者は、標準の手段でこの取得を断れず、カードに出す内容も選べない。
ADR-0062 はこれらに触れておらず、この ADR がその §2「取得と解釈」に足りない部分を決める。

取得の精査（#1947）で確かめた事情は次のとおり。

- [RFC 9309](https://www.rfc-editor.org/rfc/rfc9309.txt)（2026-11-02 に本文を確認）はクローラーの規則を定める。利用者の要求で動く取得を除外する規定はない。
- Google は、利用者が起点の取得は `robots.txt` を原則として見ないと説明し、メッセージのリンクのプレビューもそこに入れている（[List of Google user-triggered fetchers](https://developers.google.com/crawling/docs/crawlers-fetchers/google-agent)、2026-11-02 に検索結果で確認）。
- Mastodon も見ない。これをバグとする [mastodon/mastodon#21738](https://github.com/mastodon/mastodon/issues/21738) は開いたまま（2026-11-02 確認）で、リモートの投稿を受けた各サーバーが誰にも頼まれず取りに行くのは利用者の要求と言いにくい、という[主張](https://jefftk.com/p/mastodons-dubious-crawler-exemption)がある。
- Meta の共有リンク用のクローラー `FacebookExternalHit` は、`robots.txt` を迂回し得るのはセキュリティと整合性の確認のときだと説明し、`robots.txt` の内容を最大 24 時間保持する。利用者の要求で取る `Meta-ExternalFetcher` は別の名前で、迂回し得る（[Meta Web Crawlers](https://developers.facebook.com/documentation/sharing/webmasters/web-crawlers.md)、2026-11-02 に本文を確認）。
- X の `Twitterbot` は、`robots.txt` がカードの情報を妨げ得ること、Google の `robots.txt` の仕様を実装していることを文書で説明している（[Troubleshooting Guide](https://developer.x.com/web/wordpress)。本文は取得できず、2026-11-02 に検索結果の抜粋で確認。要検証）。
- Slack の `Slackbot-LinkExpanding` は従わない。従う実装を試したが、インターネットの多くがクローラーに閉じているので利用者の苦情が多く、やめたと説明している。断るには Slack への連絡が要る（[Slack Robots](https://api.slack.com/robots)、2026-11-02 に本文を確認）。

ADR-0062 の取得は、ローカルの投稿でもリモートの投稿でもジョブが自動で行う。リモートの投稿では、上の主張がそのまま当てはまる。

ページのロボットの指定は検索エンジン向けに書かれた事実上の標準で（[ADR-0057](0057-crawler-opt-out.md)、[Robots Meta Tags Specifications](https://developers.google.com/search/docs/crawling-indexing/robots-meta-tag)。2026-11-02 に検索結果で確認）、リンクのプレビューがどう扱うかを定める仕様はない。
`noindex` はプレビューを止めないものとして使われており、このサーバー自身も `unlisted` の投稿に `noindex` を付けてプレビューは出す（[ADR-0057](0057-crawler-opt-out.md)）。

決定者は `robots.txt` に従う方針を示し（「#1947 は robots.txt に従う方針で ADR を起草」）、ページの指定の扱いも同じ ADR で決めるとした（「ページの <meta name="robots"> の扱い（#1949）も同 ADR に含めて」）。この ADR は従い方を決める。

## Decision Drivers（判断基準）

1. **相手のサイトの意思**: 標準の手段で断れること。断られたら取らない
2. **安全**: ADR-0019 の宛先の制限をそのまま使い、新しい穴を開けない
3. **外部 HTTP の量**: 取得が増えても、オリジンごとに 1 日 1 回程度に収まる（NFR-COST）
4. **カードが出ること**: 断っていないサイトのカードは、今までどおり出る
5. **実装と運用の小ささ**: 追加のミドルウェアを必須にしない

## Considered Options（選択肢）

1. **すべての取得で RFC 9309 に従い、カード専用のトークンを持つ**
   - 利点: サイトがカードの取得だけを名指しで断れる、または許せる。
   - 欠点: `*` を全面禁止にしたサイトでカードが出なくなる。
2. **従わない**（Google の利用者起点の取得・Mastodon と同じ）
   - 利点: カードがいちばん多く出て、要求も増えない。ほかのサーバーと同じ見え方になる。
   - 欠点: 相手のサイトが標準の手段で断れない。決定者の方針に反する。
3. **リモートの投稿の取得だけ従う**
   - 利点: 利用者が自分で貼ったローカルの投稿は「利用者の要求」と言え、カードが減らない。
   - 欠点: カードは URL ごとに共有する（ADR-0062 §6）ので、同じ URL のカードが先に貼った投稿の種類で変わる。相手から見ると同じボットが同じ URL を取ったり取らなかったりする。

ページのロボットの指定については、次の選択肢を比べた。

- **A. カードの部品ごとに対応させ、`noindex` は何も変えない**
  - 利点: サイトが説明や画像だけを出さないようにできる。`unlisted` の投稿のような、検索には出さないがプレビューは出すページのカードが残る。
  - 欠点: 検索エンジン向けの指定を、仕様のない用途に読み替える。
- **B. `noindex` もカードの拒否として扱う**
  - 利点: 「載せないで」という意思に広く応える。
  - 欠点: `noindex` を付けて共有は歓迎しているページ（このサーバーや Fediverse の `unlisted` の投稿など）のカードが消える。拒否には `robots.txt` がある。
- **C. 読まない**
  - 利点: 実装がなく、カードが減らない。
  - 欠点: `nosnippet` のように本文を出さないでほしいという明示の指定を無視する。

## Decision（決定）

**推奨案: `robots.txt` は選択肢 1、ページのロボットの指定は A。** 判断基準 1 を満たし、選択肢 3 の不整合がない。カードが減ることは受け入れる。

### 1. トークンと User-Agent

- トークンは `my-linkcard` とする。RFC 9309 §2.2.1 の文字種に収まり、大文字と小文字を区別せずに照合する。一致するグループがなければ `*` のグループに従う。
- トークンを User-Agent に含める（§2.2.1）。ページ・画像・`robots.txt` の取得は `my-linkcard/<version> (+https://<host>/)` にする。ほかの用途の取得は `my/<version> (+https://<host>/)` のまま。
- `my` をトークンにしない。サーバー全体の名前で、語としても一般的なので、カード以外の取得まで断ったように読めるため。

### 2. 取得と保持

- `kernel.HTTPClient` の新しい用途 `HTTPPurposeRobots` で `GET {scheme}://{authority}/robots.txt` を送る。上限は本文 512 KiB（§2.5 の下限の 500 KiB を満たす）、全体 10 秒。ADR-0019 §1 の宛先の拒否をそのまま使う。超えた分は読まず、読めた分だけを解釈する。
- 結果はオリジン（スキーム・ホスト・ポート）ごとに KeyValueStore に保持する。保持するのは `my-linkcard` に当たる規則だけで、本文は持たない。期間は下の表のとおりで、24 時間を超えない（§2.4）。

| 応答 | 扱い | 保持 |
| --- | --- | --- |
| 200 | 解釈して従う | 24 時間 |
| 429 以外の 4xx | ファイルなし。取得してよい（§2.3.1.3） | 24 時間 |
| 429、5xx、ネットワークの失敗、ADR-0019 が拒否したリダイレクト | 全面禁止とみなす（§2.3.1.4） | 1 時間 |
| リダイレクトが 5 回を超える | ファイルなし。取得してよい（§2.3.1.2） | 24 時間 |

429 は RFC では 4xx だが、「今は取らないでほしい」という応答を「ファイルなし」として進まないよう、全面禁止に入れる。

### 3. 解釈

- `allow`・`disallow`・`user-agent` だけを読み、`*` と `$`、最長一致、同じ長さなら `allow` を優先、複数の一致するグループの統合を RFC 9309 のとおりに行う。`/robots.txt` 自体は常に取得してよい。
- `Crawl-delay` は RFC にないので読まない。取得の間隔は #1948 で決める。
- パーサーは依存を足さず、`internal/domain/content` の純粋な関数として書き、RFC の例をテストにする。依存を足す案は、規則が小さいことと、ライブラリのライセンスと保守の確認が要ることから採らない（既存のライブラリの状況は要検証）。

### 4. 適用

- ページを取得する前に、ページの URL を確かめる。公開範囲によらず同じ。
- HTTP クライアントがリダイレクトを内部で追うので、途中の URL は取得の前に確かめられない。`HTTPResponse.URL`（最後に答えた URL）がそのオリジンの規則で禁止なら、読まずに捨ててカードを作らない。
- 画像は `HTTPPurposeImage` の取得の前に、画像の URL のオリジンの規則で確かめる。禁止なら画像なしのカードにする（ADR-0062 §7 の `media_fetch` と同じ見え方）。
- 禁止された URL は、取得の失敗と同じく 24 時間覚える（`LinkCardFailureTTL`）。
- 再取得（ADR-0062 §6 の 14 日）で `robots.txt` の禁止が分かったら、そのカードを消す。全面禁止とみなしただけのとき（表の 3 行目）は、一時的な失敗かもしれないので消さない。
- すでにあるカードを確かめるための一斉の取得はしない。規則を変えたサイトのカードは、次の再取得で消える。
- インスタンス設定で `robots.txt` を無視する設定は置かない。

### 5. ページのロボットの指定

- 読むのは、`<head>` の `<meta name="robots">` と `<meta name="my-linkcard">`、応答ヘッダの `X-Robots-Tag` のうちボットの名前がないものと `my-linkcard:` が付いたもの。ほかのボットを名指しした指定は当てはまらない。
- 複数の指定があれば、より厳しいものが勝つ。

| 指定 | カード |
| --- | --- |
| `nosnippet`、`max-snippet:0` | 説明を出さない（`description` の値をどの出どころからも取らない） |
| `noimageindex`、`max-image-preview:none` | 画像を取得せず、画像なしのカードにする |
| `noindex`、`nofollow`、`noarchive`、`none` など | 何も変えない |

- `none` は `noindex, nofollow` と同じ意味（上の Google の文書）なので、何も変えない。
- 題名・サイト名・作者は、どの指定でも残す。これらを出さないでほしいサイトは `robots.txt` で断る。
- 再取得のときは新しい指定に従ってカードを作り直す。

### この決定を見直す条件

- カードの出ないサイトが多く、Slack の報告のように利用者の不満が実害になった場合（選択肢 3 に寄せる、または「ファイルなし」の扱いなどを緩める）
- 主要なサーバーの実装と大きく食い違い、相手のサイトの多くが `my-linkcard` を名指しして許可する手間を強いられる場合
- `robots.txt` の取得そのものの量が問題になる場合

## Consequences（影響）

- 相手のサイトは `User-agent: my-linkcard` か `*` で、標準の手段でカードの取得を断れる。説明や画像だけを出さないようにもできる。
- `none` や `noindex` だけを付けたページのカードは出続ける。意図とずれるサイトがあり得るが、`robots.txt` で断れる。
- ページの指定は取得した後で分かるので、ページ自体への要求は止まらない。
- `*` を全面禁止にして特定のボットだけを許すサイトでは、Mastodon や Slack では出るカードがここでは出ない。Slack は同じ理由で従うのをやめており、起き得る実害として見込む。どの程度起きるかは確かめていない（要検証）。
- オリジンごとに 1 日 1 回程度の要求が増える。カードのジョブは遅れるが、投稿の表示は待たない。
- `robots.txt` が 5xx を返す間、そのサイトの新しいカードは出ない。
- 許可されていないリダイレクト先には 1 回要求が届く（§4）。ヘッダだけで本文は読まない。
- User-Agent が用途で分かれるので、`my/` で一括して識別していたサイトには別の名前に見える。
