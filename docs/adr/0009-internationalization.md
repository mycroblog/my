# ADR-0009: 国際化（i18n）と地域化（l10n）

- Status: Accepted
- Date: 2026-10-16
- Deciders: @rosylilly
- Issue: #5

## Decision（決定）

### 1. メッセージカタログ

- 形式: **ICU MessageFormat**（MF1。MessageFormat 2 は成熟したら移行を検討）。複数形・select は CLDR 規則に従う。
- 配置: リポジトリ直下 `locales/<BCP47>/<namespace>/<area>.json`（`area` の分け方は ADR-0081）。**ソースロケールは `en`**（翻訳者人口のため）、`ja` はメンテナが `en` と同じ変更で更新する。ほかのロケールはエージェントが後から追いつく（§8）。
- ロケールのディレクトリのタグは言語だけのタグ（`ja`・`es`・`de`）を基本とし、同じ言語で書き分けが要るものだけ地域を付ける（`zh-CN`・`zh-TW`・`pt-BR`）。どのタグがどのディレクトリに解決するかは §2。
- キーは意味ベース（`timeline.empty.home`）。文字列の連結・断片の組み合わせは禁止し、1 文 = 1 メッセージ。
- サーバー（Go）・Web・モバイル（TS）で **同一カタログファイルを共有** する（namespace でサーバー専用 / クライアント専用を分ける）。カタログは FormatJS の JSON 形式（`{"key": {"defaultMessage", "description"}}`）。
- ライブラリ（根拠は [#20 の調査報告](https://github.com/mycroblog/my/issues/20#issuecomment-6209364734)）:
  - Go: `github.com/kaptinlin/messageformat-go/mf1`（MIT）を自前パッケージの裏に隠して使う。FormatJS と、共有カタログ 96/96 件・CLDR 12 ロケール 132/132 件で出力が一致する。カタログはバイナリに `embed` する。
  - TS: FormatJS の `intl-messageformat`（BSD-3-Clause）。メッセージはビルド時に AST へコンパイルし、ランタイムは 2.6 KiB（gzip）。`eval` を使わないので Tauri の CSP と両立する。
  - 出力の一致テストと CLDR の差分テストを CI に常設し、ライブラリをフォーク / 自前実装に切り替えられるようにする。
- 型安全: 1 つの生成器（Bun スクリプト）から、Go と TS の両方にキーとプレースホルダの型付きアクセサを生成し、存在しないキーや引数不足をコンパイル時に検出する。
- コミットするのは Go が読む生成物（Go の型付きアクセサと `server` の疑似ロケール）だけで、TS のアクセサと `client` の疑似ロケールはコミットしない（ADR-0081）。
- Go が整形する namespace（`client*` 以外）は、Go と TS で出力が一致する共有サブセットに限る。リッチテキストタグ・数値スケルトン（`::`）・`date` / `time` 引数を禁止し、日付は整形済み文字列で渡す（lint で強制）。
- CI 検査: (a) `en` に対する未翻訳キーの一覧（警告であり、失敗にはしない。未翻訳のキーは `main` でもリリースでも許し、UI は `en` の文言を出す）、(b) プレースホルダの不一致・ICU 構文エラー（失敗にする）、(c) 未使用キー。
- **疑似ロケール**（`en-XA`: 文字列を 30〜40% 伸ばしアクセント付与、`ar-XB`: RTL 疑似）を開発・E2E テストで使う。FormatJS の AST 変換で生成し、`en` の CLDR 規則で整形する。

### 2. ロケール解決

- 優先順: 利用者設定 → `Accept-Language` → インスタンス既定 → `en`。
- 優先順の各候補のタグは、カタログのあるロケールのどれか 1 つに解決する。解決するロケールがない候補は飛ばし、次の候補を見る。
  - 地域などの付いたタグは、言語だけのタグのロケールに解決する（`ja-JP` → `ja`、`de-AT` → `de`）。
  - 中国語: `zh`・`zh-SG`・`zh-Hans`・`zh-Hans-*` は `zh-CN` に、`zh-HK`・`zh-MO`・`zh-Hant`・`zh-Hant-*` は `zh-TW` に解決する。
  - ポルトガル語: `pt`・`pt-PT` は `pt-BR` に解決する。
- フォールバック: ロケールのカタログにないキーは、常に `en` の文言で表示する。あるロケールから別のロケールへはフォールバックしない（`zh-TW` から `zh-CN` へも）。
- メール・Push 等の非同期処理は「受信者の」ロケールで生成する（ジョブペイロードにロケールを持たせず、実行時に受信者設定を引く）。
- 管理者が入力する値（インスタンスの名前・説明・規約とポリシー・画像の代替テキスト・ルールの文と補足など）はロケールごとに持たず、1 つの値をどのロケールでも表示する。
  管理者は好きな言語で 1 回だけ書き、ほかの言語の読み手は機械翻訳などで読む。どの値が表示されるかが管理者に分かりやすく、英語・日本語以外の言語圏の運営者もそのまま使える。
  管理画面の欄の名前や説明は、ほかの UI 文字列と同じくカタログで翻訳する。

### 3. 整形

- 日付・時刻・数値・相対時刻・リスト・単位は `Intl.*` を使う。タイムゾーンは利用者設定（IANA）。サーバーは常に UTC で保持。
- ハードコードされた日付フォーマット文字列を禁止（lint）。

### 4. 投稿の言語

- 投稿は BCP 47 の言語タグを持つ（FR-110）。ActivityPub では `contentMap` で表現し、受信時は `contentMap` / `@language` から取得。
- 言語でタイムラインをフィルタ可能にする（FR-208）。クライアント側での言語自動推定は任意。

### 5. 書字方向・タイポグラフィ

- CSS は論理プロパティ（`margin-inline-start` 等）のみを使う（lint）。ルート要素の `dir` をロケールから設定。
- 利用者生成コンテンツ（表示名・投稿・プロフィール）と管理者が入力する値は `dir="auto"` で個別に方向判定。
  管理者が入力する値は書かれた言語を記録しないので、`lang=""`（言語不明）で表示し、画面の言語を引き継がせない。
- フォントは OS フォントを優先し、CJK・アラビア文字等のフォールバックスタックを定義する。絵文字の符号位置だけは `--font-sans` と `--font-mono` の先頭の `"my Noto Color Emoji"` で描き、本文の文字は OS のフォントのままにする（ADR-0091）。

### 6. 文字列と識別子

- ユーザー名（`@name`）は連合互換のため `[A-Za-z0-9_]` に限定し、比較は小文字正規化。表示名は任意の Unicode（NFC 正規化）。
- ドメインは IDN を Punycode で保存し、表示時に Unicode へ変換。
- ハッシュタグは NFKC + 小文字化で正規化して照合（表示は元の表記）。

### 7. 検索（CJK）

- v0 のアカウント・タグ検索は、正規化した文字列のバイト順の前方一致の範囲で行う。拡張機能（FTS5、`pg_trgm`）を使わず、
  分かち書きに依存しない。
- 投稿の全文検索は、日本語をどこまで探せるかをバックエンドごとに決めて、その文書に書く（[ADR-0149](0149-full-text-search.md) §13）。

### 8. 翻訳ワークフロー

- 翻訳基盤は当面使わない。人による翻訳に頼らない（#2028）。
- `ja` はメンテナが `en` と同じ変更で更新する（§1）。
- `en`・`ja` のほかのロケールの言語は、zh-CN・zh-TW・es・pt-BR・de・fr をこの順に足す。いずれも v0.1.0 の前提条件ではない。
- 誰がいつ訳すか: `ja` のほかのロケールは、エージェントが訳す。訳す作業は手で始め、`en` に追いつく。`en` を変える PR に、これらのロケールの訳を課さない。
  CI・ワークフロー・ビルドから翻訳の API を呼ばない（ADR-0150 §9 と同じ理由）。
- 未翻訳のキー: `main` でもリリースでも許す。UI は `en` の文言を出し、`i18n:check` は警告する（§1）。リリースの手順（`docs/agents/releasing.md`）に、タグの前に追いつく手順を置く。ただしリリースの関門にはしない。
- 品質: ロケールは機械翻訳のまま出す。その言語を読む人の確認を要件にせず、確認を記録しない。
  - 設定の言語の選択肢で、機械翻訳のロケールにその旨（「機械翻訳」）を添える。ほかの画面には何も出さない。`ja` には添えない。
  - その言語を読む人の手直しは PR で受ける。
- 文体と用語: ロケールを足す Issue に、その言語の句読点と言い回しの規則（web-client §16 の G19〜G21 に足す）と、`tools/i18n/glossary.json` の項目を含める。
  エージェントがその言語の主な文体の手引きの慣例から下書きし、決定者が PR で確かめる。
- ドキュメントサイトの文書の訳は、エージェントが節ごとに書き、リポジトリに置く（ADR-0150 §9）。どのロケールも `ja` と同じ範囲を訳す。UI の用語はこのカタログの訳に揃える。

## 経緯

多様な言語の利用者が使う（G5）。後付けの i18n は文字列の連結・日付整形・レイアウトの作り直しを招くため、最初期から仕組みに組み込む。
i18n の対象は UI 文字列だけでなく、サーバー生成文言（メール・API エラー・通知）、投稿の言語メタデータ、検索、書字方向まで及ぶ。

`en` と `ja` のほかに 6 言語を足すことになった（#2419）。プロジェクトにはそのほとんどを読む人がおらず、メンテナが `en` と同じ変更で更新する `ja` の規則は使えない。
そこでドキュメントサイト（ADR-0150 §9）と同じく、エージェントが手で始める実行で追いつき、未翻訳のキーは `en` で出し、機械翻訳のまま出す形にした。
ロケールの解決は、ロケールどうしのフォールバック（繁体字から簡体字へなど）をやめ、ブラウザーの送るタグを 1 つのロケールに解決してから `en` に落とす形にした。
誰がいつ訳すか、未翻訳のキー、品質と表示、タグとフォールバック、文体、ドキュメントサイトの範囲は、決定者が決めた。

当初は生成物をすべてコミットしていたが、並行の PR の衝突を減らすため Go が読むものだけにした（ADR-0081）。絵文字のフォントは、どのブラウザーでも同じ形にするため OS のフォントから Noto Color Emoji に変えた（ADR-0091）。

## 採らなかった案

- 管理者が入力する値をロケールごとに持つ: どの値が表示されるかが管理者に分かりにくく、英語・日本語以外の言語圏の運営者がそのまま使えない（§2）。
- OSS 向けホスティング（Weblate の Libre プラン / Crowdin の OSS プラン）を使い、翻訳者がコードを触らずに貢献できるようにし、翻訳の取り込みを自動 PR にする: spike の推奨は Weblate の Libre プラン（GPL-3.0 でセルフホスト可、Format.JS JSON と ICU 検査をネイティブサポート）だった。#2028 で当面見送った（§8）。
- `en` を変える PR で、すべてのロケールの訳も直すことを求める: どのロケールも常に揃う。しかし UI を変えるすべての PR に 8 言語の訳と、そのための道具が要る（§8）。
- ロケールを出す前に、その言語を読む人の確認を求める: 訳の質を上げられる。しかし足す言語のほとんどに確認できる人がいない（§8）。
- ディレクトリのタグを `zh-Hans`・`zh-Hant` にする: 文字体系を表し、地域を問わない。しかし言語を足す Issue が `zh-CN`・`zh-TW` の名前で進んでおり、どちらの名前でも §2 の表が両方の形のタグを解決するので、得るものがない（§2）。
- 繁体字のロケールのないキーを簡体字で出す（`zh-TW` → `zh-CN` → `en`）: 中国語の読み手には英語より読める。しかし繁体字の読み手に簡体字を出すのは好まれず、フォールバックの規則も複雑になる（§2）。

## Consequences（影響）

- 初期実装コストは増えるが、後付けより圧倒的に安い。
- エージェントには「UI 文字列を書いたら必ずカタログに追加し、`en` と `ja` を更新する」ルールを課す（AGENTS.md）。
- Go 側ライブラリは保守者が実質 1 名で v0.x であり、バイナリが +5.1 MB、RSS が +7 MB 増える。出力の一致テストと CLDR の差分テストを常設し、フォーク / 自前実装（3〜5 人日の見積もり）へ切り替えられるようにしておく。
- `ja` のほかのロケールは `en` より遅れうる。その間は画面に `en` の文言が混じる。機械翻訳の訳は誤りを含みうる。
- 後続の作業（各言語の Issue とともに進める）
  - ロケールの解決（`internal/i18n/locale.go` と `app/web/src/lib/i18n.tsx`）を §2 の表に合わせ、ロケールどうしのフォールバックをなくす
  - 設定の言語の選択肢に、機械翻訳のロケールの印を出す
  - カタログを訳すエージェントの手順書（`docs/agents/`）と、リリースの手順の追いつく手順

## Open Questions / 要検証

- 訳したあとで `en` の文言が変わったキーを、`ja` のほかのロケールでどう見つけて訳し直すか（キーの名前を変える規約か、訳したときの `en` のハッシュを持つか）
