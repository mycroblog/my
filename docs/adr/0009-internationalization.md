# ADR-0009: 国際化（i18n）と地域化（l10n）

- Status: Accepted
- Date: 2026-10-16
- Deciders: @rosylilly
- Issue: #5, #2904

## Decision（決定）

### 1. メッセージカタログ

- 形式: **ICU MessageFormat**（MF1。MessageFormat 2 は §9）。複数形・select は CLDR 規則に従う。
- 配置: 名前空間の持ち主（§9）のそばに `<BCP47>/<area>.json`（`area` の分け方は ADR-0081）。**ソースロケールは `en`**（翻訳者人口のため）、`ja` はメンテナが `en` と同じ変更で更新する。ほかのロケールはエージェントが後から追いつく（§8）。
- ロケールのディレクトリのタグは言語だけのタグ（`ja`・`es`・`de`）を基本とし、同じ言語で書き分けが要るものだけ地域を付ける（`zh-CN`・`zh-TW`・`pt-BR`）。どのタグがどのディレクトリに解決するかは §2。
- キーは意味ベース（`timeline.empty.home`）。文字列の連結・断片の組み合わせは禁止し、1 文 = 1 メッセージ。
- Go と TS はキーを共有せず、形式・検査・用語集・翻訳の流れ・疑似ロケールだけを共有する。形式は FormatJS の JSON（`{"key": {"defaultMessage", "description"}}`）。
- 整形:
  - Go: ライブラリを使わず、`go generate` が各メッセージを Go のコードにする。複数形の規則と数値は `golang.org/x/text` で引く。カタログはバイナリに `embed` する。
  - TS: `@my/i18n` の Lingui。共有の形式はカタログ形式の差し込みで直接読み、キーは明示の ID のまま。エントリとデザインシステムは自分のカタログだけを読む。
- 型安全: 各側の生成器がキーとプレースホルダの型付きアクセサを生成し、存在しないキーや引数不足をコンパイル時に検出する。
- コミットするのは Go が読む生成物（Go の型付きアクセサと `server` の疑似ロケール）だけで、TS のアクセサと `client` の疑似ロケールはコミットしない（ADR-0081）。
- Go が整形する namespace は、Go の整形器が扱う plural・select・`#`・`number` に限る。リッチテキストタグ・数値スケルトン（`::`）・`date` / `time` 引数を禁止し、日付は整形済み文字列で渡す（lint で強制）。
- CI 検査: (a) `en` に対する未翻訳キー（`ja` は失敗にする。`en` と同じ変更で書くからである。ほかのロケールは警告で、`main` でもリリースでも許し、UI は `en` の文言を出す）、(b) プレースホルダの不一致・ICU 構文エラー（失敗にする）、(c) 未使用キー。
- **疑似ロケール**（`en-XA`: 文字列を 30〜40% 伸ばしアクセント付与、`ar-XB`: RTL 疑似）を開発・E2E テストで使う。カタログからカタログへの変換で作り、データとして両側に渡す。

### 2. ロケール解決

- 優先順: 利用者設定 → `Accept-Language` → インスタンス既定 → `en`。
- 優先順の各候補のタグは、カタログのあるロケールのどれか 1 つに解決する。解決するロケールがない候補は飛ばし、次の候補を見る。
  - 地域などの付いたタグは、言語だけのタグのロケールに解決する（`ja-JP` → `ja`、`de-AT` → `de`）。
  - 中国語: `zh`・`zh-SG`・`zh-Hans`・`zh-Hans-*` は `zh-CN` に、`zh-HK`・`zh-MO`・`zh-Hant`・`zh-Hant-*` は `zh-TW` に解決する。
  - ポルトガル語: `pt`・`pt-PT` は `pt-BR` に解決する。
- フォールバック: ロケールのカタログにないキーは、常に `en` の文言で表示する。あるロケールから別のロケールへはフォールバックしない（`zh-TW` から `zh-CN` へも）。
- メール・Push 等の非同期処理は「受信者の」ロケールで生成する（ジョブペイロードにロケールを持たせず、実行時に受信者設定を引く）。
- 管理者が入力する値（インスタンスの名前・説明・規約とポリシー・画像の代替テキスト・ルールの文と補足など）はロケールごとに持たず、1 つの値をどのロケールでも表示する。
  管理者は好きな言語で 1 回だけ書き、ほかの言語の読み手は機械翻訳などで読む。どの値が表示されるかが管理者に分かりやすく、英語・日本語以外の言語圏の運営者もそのまま使える。
  管理画面の欄の名前や説明は、ほかの UI 文字列と同じくカタログで翻訳する。

### 3. 整形

- 日付・時刻・数値・相対時刻・リスト・単位は `Intl.*` を使う。タイムゾーンは利用者設定（IANA）。サーバーは常に UTC で保持。
- ハードコードされた日付フォーマット文字列を禁止（lint）。

### 4. 投稿の言語

- 投稿は BCP 47 の言語タグを持つ（FR-110）。ActivityPub では `contentMap` で表現し、受信時は `contentMap` / `@language` から取得。
- 言語でタイムラインをフィルタ可能にする（FR-208）。クライアント側での言語自動推定は任意。

### 5. 書字方向・タイポグラフィ

- CSS は論理プロパティ（`margin-inline-start` 等）のみを使う（lint）。ルート要素の `dir` をロケールから設定。
- 利用者生成コンテンツ（表示名・投稿・プロフィール）と管理者が入力する値は `dir="auto"` で個別に方向判定。
  管理者が入力する値は書かれた言語を記録しないので、`lang=""`（言語不明）で表示し、画面の言語を引き継がせない。
- Web クライアントの文字は、自前で配る Noto Sans（ラテン・ギリシャ・キリル文字）と Noto Sans CJK で描く。どの OS でも同じ形になり、CJK の字形は文字の言語に従う。
  - 地域は JP・SC・TC・KR の 4 つで、それぞれ別のファミリーにする。`lang`（UI のロケールと、投稿ごとの言語）から `:lang()` で選ぶ。`zh`・`zh-Hans` は SC、`zh-Hant`・`zh-TW`・`zh-HK`・`zh-MO` は TC にする（§2 と同じ対応）。CJK でない言語の文字は、外側の文字の地域を引き継ぎ、ページの既定は JP にする。
  - フォントの並びは固定する。`"my Noto Color Emoji"`（ADR-0091 §10）、サーバー単位のテーマのフォント（ADR-0059 §2）、Noto Sans、その地域の Noto Sans CJK、どちらにも無い文字（アラビア文字・ヘブライ文字・タイ文字など）の OS のフォント、OS の絵文字のフォントの順である。等幅の並びは、CJK を持たない OS の等幅のフォントを Noto Sans CJK の前に置き、Noto Sans を持たない。Noto Sans と Noto Sans CJK のラテン文字は等幅でなく、OS の等幅のフォントがラテン・ギリシャ・キリル文字を持つため。
  - Noto Sans を Noto Sans CJK の前に置くのは、Noto Sans CJK に無い字（ą ł ż č ř ş ğ і ї など）のある語が、語の途中でフォントを替えて描かれたため。Noto Sans は `google/fonts` の固定したコミットの可変フォント（幅を既定に固定し、`wght` を持つ）を SHA-256 で確かめて使い、Google Fonts と同じ分け方（latin・latin-ext・greek・greek-ext・cyrillic・cyrillic-ext・vietnamese）で分割する。CJK の言語の文では、Noto Sans CJK が全角で描く約物（`…`・`※`・`×` など）を Noto Sans CJK に残す。
  - `notofonts/noto-cjk` の固定したリリースの可変フォント（`wght`、トークンの使うすべての太さ）を、SHA-256 で確かめて使う。地域ごとの部分集合のフォント（Noto Sans JP など）でなく、ハングルと全地域の漢字を持つ全体のフォントを使う（約 78 MB）。地域の集合に無いという理由で OS のフォントに落ちる字を無くし、韓国語の混じった日本語の投稿も同じ書体で描くため。
  - `unicode-range` で分割した WOFF2 をコミットし、ビルドで何も取得しない。ページは表示する文字の分割だけを読む。よく使う漢字とハングル（地域の文字集合の第 1 水準）を、ほかと別の分割にまとめる。`locl` と縦書きの表は持たない（地域はファミリーで選び、縦書きは使わない）。
  - `font-display: swap` で、読み込み中は OS のフォントで描く。入れ替えで行が動かないように、Noto Sans と Noto Sans CJK の字の箱を絵文字（ADR-0091 §10）と同じ 1 em に揃える。
  - SIL Open Font License 1.1 の表示をビルドの成果物に含める。
  - 見直す条件: リポジトリの大きさ（4 地域で約 78 MB）が問題になったとき、ブラウザーが `lang` から `locl` を引く振る舞いがすべての対象で確かめられ、1 つのフォントで 4 地域を描けるとき、縦書きが要るとき、Noto Sans CJK か Noto Sans の新しいリリースが出たとき。

### 6. 文字列と識別子

- ユーザー名（`@name`）は連合互換のため `[A-Za-z0-9_]` に限定し、比較は小文字正規化。表示名は任意の Unicode（NFC 正規化）。
- ドメインは IDN を Punycode で保存し、表示時に Unicode へ変換。
- ハッシュタグは NFKC + 小文字化で正規化して照合（表示は元の表記）。

### 7. 検索（CJK）

- v0 のアカウント・タグ検索は、正規化した文字列のバイト順の前方一致の範囲で行う。拡張機能（FTS5、`pg_trgm`）を使わず、
  分かち書きに依存しない。
- 投稿の全文検索は、日本語をどこまで探せるかをバックエンドごとに決めて、その文書に書く（[ADR-0149](0149-full-text-search.md) §13）。

### 8. 翻訳ワークフロー

- 翻訳基盤は当面使わない。人による翻訳に頼らない（#2028）。
- `ja` はメンテナが `en` と同じ変更で更新する（§1）。
- `en`・`ja` のほかのロケールの言語は、zh-CN・zh-TW・es・pt-BR・de・fr をこの順に足す。いずれも v0.1.0 の前提条件ではない。
- 誰がいつ訳すか: `ja` のほかのロケールは、エージェントが訳す。訳す作業は手で始め、`en` に追いつく。`en` を変える PR に、これらのロケールの訳を課さない。
  CI・ワークフロー・ビルドから翻訳の API を呼ばない（ADR-0150 §9 と同じ理由）。
- 未翻訳のキー: 機械翻訳のロケールでは `main` でもリリースでも許す。UI は `en` の文言を出し、検査は警告する。`ja` の未翻訳は検査が失敗にする（§1）。リリースの手順（`.claude/skills/release/SKILL.md`）に、タグの前に追いつく手順を置く。ただしリリースの関門にはしない。
- 品質: ロケールは機械翻訳のまま出す。その言語を読む人の確認を要件にせず、確認を記録しない。
  - 設定の言語の選択肢で、機械翻訳のロケールにその旨（「機械翻訳」）を添える。ほかの画面には何も出さない。`ja` には添えない。
  - その言語を読む人の手直しは PR で受ける。
- 文体と用語: ロケールを足す Issue に、その言語の句読点と言い回しの規則（translate-catalogs のスキルに足す）と、`tools/i18n/glossary.json` の項目を含める。
  エージェントがその言語の主な文体の手引きの慣例から下書きし、決定者が PR で確かめる。
- ドキュメントサイトの文書の訳は、エージェントが節ごとに書き、リポジトリに置く（ADR-0150 §9）。どのロケールも `ja` と同じ範囲を訳す。UI の用語はこのカタログの訳に揃える。

### 9. 名前空間の持ち主

- 名前空間ごとに整形する側を 1 つ決め、カタログをその持ち主と置く: Go、アプリ（`@my/i18n`）、デザインシステム（自分の文言を持ち、`@my/i18n` に依存しない）。
- Go は自分が出す文だけを持つ: API のエラー、メール（外枠の文も。外枠はロケールによらず 1 つ）、Push、プレビュー、フィード、保守の画面、CLI。認証と支払いの画面の文はアプリが持つ。
- 生成器と整形は側ごとに持ち、サーバーのビルドに Bun を要しない。Go の文は plural・select・`number` だけで（2026-11）、小さな整形器で足りる。
- TS は Lingui とする。共有の形式（ICU MF1）をそのまま読み、ビルド時にコンパイルし、本体が小さい。
- 見直す条件: 同じ文を両側で整形するとき、Go の文に日付が要るとき、`Intl.MessageFormat` が Stage 3 に進んだとき、Lingui が形式を読めなくなったとき。

## 経緯

多様な言語の利用者が使う（G5）。後付けの i18n は文字列の連結・日付整形・レイアウトの作り直しを招くため、最初期から仕組みに組み込む。
i18n の対象は UI 文字列だけでなく、サーバー生成文言（メール・API エラー・通知）、投稿の言語メタデータ、検索、書字方向まで及ぶ。

`en` と `ja` のほかに 6 言語を足すことになった（#2419）。プロジェクトにはそのほとんどを読む人がおらず、メンテナが `en` と同じ変更で更新する `ja` の規則は使えない。
そこでドキュメントサイト（ADR-0150 §9）と同じく、エージェントが手で始める実行で追いつき、未翻訳のキーは `en` で出し、機械翻訳のまま出す形にした。
ロケールの解決は、ロケールどうしのフォールバック（繁体字から簡体字へなど）をやめ、ブラウザーの送るタグを 1 つのロケールに解決してから `en` に落とす形にした。
誰がいつ訳すか、未翻訳のキー、品質と表示、タグとフォールバック、文体、ドキュメントサイトの範囲は、決定者が決めた。

両側が参照するキーは 0 件だった（2026-11。Go 716 件、クライアント 6,071 件。#2899・#2900 で 248 件がクライアントへ移り、9 件が分かれる）。

当初は生成物をすべてコミットしていたが、並行の PR の衝突を減らすため Go が読むものだけにした（ADR-0081）。絵文字のフォントは、どのブラウザーでも同じ形にするため OS のフォントから Noto Color Emoji に変えた（ADR-0091）。
本文の文字も、同じ理由で OS のフォントから自前の Noto Sans CJK に変えた。OS のフォントでは、日本語の UI で中国語の投稿が日本の字形で描かれ、OS ごとに形も幅も違った。テーマがフォントの並びを丸ごと上書きすると絵文字と CJK のフォントが落ちるので、並びを固定し、テーマには足す場所だけを残した（ADR-0059 §2）。

## 採らなかった案

- 管理者が入力する値をロケールごとに持つ: どの値が表示されるかが管理者に分かりにくく、英語・日本語以外の言語圏の運営者がそのまま使えない（§2）。
- OSS 向けホスティング（Weblate の Libre プラン / Crowdin の OSS プラン）を使い、翻訳者がコードを触らずに貢献できるようにし、翻訳の取り込みを自動 PR にする: spike の推奨は Weblate の Libre プラン（GPL-3.0 でセルフホスト可、Format.JS JSON と ICU 検査をネイティブサポート）だった。#2028 で当面見送った（§8）。
- `en` を変える PR で、すべてのロケールの訳も直すことを求める: どのロケールも常に揃う。しかし UI を変えるすべての PR に 8 言語の訳と、そのための道具が要る（§8）。
- ロケールを出す前に、その言語を読む人の確認を求める: 訳の質を上げられる。しかし足す言語のほとんどに確認できる人がいない（§8）。
- ディレクトリのタグを `zh-Hans`・`zh-Hant` にする: 文字体系を表し、地域を問わない。しかし言語を足す Issue が `zh-CN`・`zh-TW` の名前で進んでおり、どちらの名前でも §2 の表が両方の形のタグを解決するので、得るものがない（§2）。
- 繁体字のロケールのないキーを簡体字で出す（`zh-TW` → `zh-CN` → `en`）: 中国語の読み手には英語より読める。しかし繁体字の読み手に簡体字を出すのは好まれず、フォールバックの規則も複雑になる（§2）。
- キーを両側で使える形を保つ: 共有するキーがない（§9）。
- Go に `messageformat-go` を使い続ける: TS との一致が要らず、v0.x・+5.1 MB の費用だけが残る。
- Go に `go-i18n` や gotext を使う: ICU でなく、形式を共有できない。
- 形式を MessageFormat 2 にする: `Intl.MessageFormat` は Stage 1、Go の実装は v0.x である（2026-11-12 確認）。
- TS に Paraglide JS を使う: カタログの形が変わり、言語を替えると読み直す。
- TS に FormatJS を使う: AST を実行時に解釈し、エントリの分割も自前になる。
- TS に i18next を使う: 形式が ICU でなく、i18next-icu の中身は FormatJS である。
- API のエラーをクライアントが `type` から訳す: ほかのクライアントが文を失い、メールと Push は Go に残る（§9）。
- メールの外枠をロケールごとに描画する: 1 通の文が Go と TS に分かれる（§9）。
- 本文を OS のフォントで描く: 配る量が無い。しかし字形が OS で変わり、中国語の投稿を日本の字形で描き得る（§5）。
- 1 つの全体のフォントを `locl` で地域に切り替える: リポジトリの大きさが 4 分の 1 になる。しかし地域の選び方がブラウザーの `lang` の扱いに任され、対象のブラウザーで確かめていない（§5）。
- 地域ごとの部分集合のフォント（Noto Sans JP・SC・TC・KR）: 約半分の大きさで済む。しかし日本語や中国語の文のハングルと、地域の集合に無い漢字が OS のフォントになる（§5）。

## Consequences（影響）

- 初期実装コストは増えるが、後付けより圧倒的に安い。
- エージェントには「UI 文字列を書いたら必ずカタログに追加し、`en` と `ja` を更新する」ルールを課す（AGENTS.md）。
- Go の整形器は自前で保守し、複数形の規則は `x/text` の CLDR の版に従う。
- `ja` のほかのロケールは `en` より遅れうる。その間は画面に `en` の文言が混じる。機械翻訳の訳は誤りを含みうる。

## Open Questions / 要検証

- 訳したあとで `en` の文言が変わったキーを、`ja` のほかのロケールでどう見つけて訳し直すか（キーの名前を変える規約か、訳したときの `en` のハッシュを持つか）
