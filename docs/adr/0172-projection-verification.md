# ADR-0172: 投影の検証と再構築を本物の表に触れずに行う

- Status: Accepted
- Date: 2026-11-26
- Deciders: @rosylilly
- Issue: #3535

## Decision（決定）

### 1. 作り直しの書き先

投影を検証するときは、その投影の表と同じ名前の一時テーブルを同じトランザクションの中に作り、そこへ作り直す。一時テーブルは PostgreSQL でも SQLite でも同じ名前の表より先に解決されるので、各モジュールの作り直しの手順とそのクエリは変えずに一時テーブルへ書く。本物の表は空にも書き換えもしないので、検証の間も行はロックされず、読み手も書き手も待たない。

### 2. 比べ方

比べるのは DB の中で行う。一時テーブルと本物の表の両方向の差だけを、上限を付けて返す。表の全行をアプリに読み込まないので、メモリは差の大きさで決まり、読み取りが行数の二乗で増えることもない。

### 3. SQLite のトランザクション

SQLite では、検証のトランザクションを本体の書き込みロックを取らない始め方にする。書き込むのは一時のデータベースだけなので、インスタンスの書き込みを止めない。

### 4. 書き込みをまとめる

イベントを再生する作り直しと、再構築がずれを直す書き込みは、複数の行をまとめて 1 回で入れる。行の数だけ DB と往復しない。

## 経緯

検証は投影の表を全行読み、本物の表を空にして作り直し、もう一度全行読んでアプリの中で比べ、ロールバックしていた。空にした行はロールバックまでロックされ（SQLite ではインスタンスの書き込みがすべて待つ）、読み取りは行数の二乗で増え、イベントの再生は 1 行ごとに往復した。rc では一番大きい投影の検証がジョブの持ち時間を使い切り、終わらなかった（#3433）。定期の検証を既定で止め、ずれを報告するだけにすることは ADR-0020 規約 1 が決めた。この ADR は、手で動かす検証と、運営者が有効にした定期の検証を軽くするやり方を決める。一時テーブルが、それより前に用意したプリペアドステートメントからも同じ名前の表より先に解決されることは、PostgreSQL（pgx のステートメントキャッシュの 3 つのモード）と SQLite（アダプタのステートメントキャッシュ）の両方で spike が確かめた（#3535、2026-11-26）。

## 採らなかった案

- 本物の表のまま、読み取りをキー順の範囲に変えて書き込みだけまとめる: 変更は小さいが、作り直しの間、投影の全行のロックが残る。
- 最近変わった行や一部だけを検証する: 安いが、モジュールごとにキーを指定した作り直しが要り、古い行のずれは見つからない。
- 作り直しを SQL の集合演算で書き直す: 往復は最も少ないが、projector と同じ規則を SQL にもう一度書くことになり、2 つが食い違う。
- 本番の複製（読み取り用のレプリカやブランチ）で検証する: 本番に負荷をかけないが、ホスティングに依存し、すべての運営者が使えるわけではない。

## 見直す条件

- 一時テーブルの作成が、接続プーラー（トランザクション単位のプール）や DB のホスティングの制約で使えないと分かったとき。
- 差がまとめて返せないほど大きく、比べ方がメモリや時間の上限に当たると分かったとき。
