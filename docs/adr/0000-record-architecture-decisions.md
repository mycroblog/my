# ADR-0000: ADR と文書と作業の進め方

- Status: Accepted
- Date: 2026-11-04
- Deciders: @rosylilly
- Issue: #2078

## Decision（決定）

### 1. 設計判断を ADR で記録する

- 設計判断は `docs/adr/NNNN-kebab-case-title.md` に [template.md](template.md) の形で記録する。新規作成は `scripts/task.sh docs:adr-new`。
- **ADR は主題ごとに 1 ファイルとする。** 主題を持つ ADR があれば、新しいファイルを足さず、その ADR を直す。ファイルを足すのは、どの ADR も持たない主題だけにする。
- ADR には結論、そこに至る判断の変遷、採らなかった案を書く。決定者とのやり取りの原文は載せない。やり取りの経過は git と Issue が持つ。
- ステータスは `Proposed` → `Accepted` / `Rejected`。Accepted の ADR の結論を変えるときは、本文をその場で書き換え、置き換えた内容のうち読み手に要るものを `経緯` か `採らなかった案` に移す。
- 節番号は変えない。コードと文書が `ADR-NNNN §k` で引用している。節は末尾に足し、内容はその節の中で書き換える。
- ADR を別の ADR に統合した番号は廃番にし、移転先を `docs/adr/aliases.yaml` に書く。古い Issue や PR の引用はそのファイルで解決する。廃番は再利用しない。
- **エージェントは ADR を `Proposed` で起票・改訂してよいが、`Accepted` への変更と、Accepted の ADR の結論の変更は人間の Decider が行う。** Decider が述べた決定は、エージェントが ADR に反映してよい。
- 議論は ADR ごとの GitHub Issue（ラベル `type:adr`）で行い、結論を ADR 本文に反映して PR でマージする。
- ドキュメントの言語: 設計ドキュメント（ADR・要件）は v0 の間は日本語。コード・識別子・コミットメッセージ・コードコメントは英語。

### 2. リポジトリ内の文書は現在の状態だけを記述する

- **ソースコード・設計文書・要件・手順書など、リポジトリ内のすべてのファイルは「今」を記述する。** 変更の経緯・旧版との比較・変更履歴の節は書かない。経緯はコミットメッセージと PR の説明に書く。
- **ADR の `経緯` と `採らなかった案` だけは例外とする。** 決定が今の形である理由を読み手が知るために、判断の変遷と却下した案を短く書く。版ごとの変更の記録にはしない。
  - ADR の本文は結論を今の形で書く。「前の案では〜」は本文に書かない（§1）。
- **Open Questions には未解決の事項だけを書く。** 解決したら、その結論を本文（Decision / Consequences）に現在形で書き込み、項目を消す。完了のチェック（`[x]`）は残さない。
- 外部の事実（価格・制限値）の **確認日と出典** は、記載している値の属性なので書いてよい。

### 3. 調査（spike）の報告と試作コードはリポジトリに置かない

- **調査報告は、その調査の Issue にコメントとして書く。** リポジトリ（`docs/`）には置かない。
- **試作コードは、調査用ブランチ `spike/<issue>-<slug>` に push するだけで、main にはマージしない。** 報告からはコミットのパーマリンクで参照する。
- 調査の結論は、ADR・設計文書・要件の本文に現在形で書き込む。根拠として、報告のコメントへのリンクを付ける。
  - この文書の更新は、調査用ブランチとは別のブランチから PR にする。
- 調査の Issue は、報告のコメントと文書更新の PR がそろった時点で close する。

### 4. ボーイスカウトルール

**ボーイスカウトルール（来たときよりもきれいにして去る）を、人間・作業エージェント・統括エージェントのすべてに適用する。**

- 作業中に見つけた壊れた箇所は、担当範囲の外でも放置しない。「自分の担当範囲ではないので無視する」は禁止する。
  - 例: 失敗するテスト、CI の不調、lint 違反、ADR と食い違う文書、切れたリンク。
- 小さく直せるもの（数行の修正、文書の食い違い）は、その場で直す。
  - 同じ PR に入れる場合は、本題と別のコミットにし、PR の説明に「ついでに直したもの」として書く。
- その場で直せない大きなもの（設計判断が要るもの、別の作業中の Issue と衝突するもの）は、Issue を起票し、作業中の Issue からリンクする。
  - 見て見ぬふりをせず、必ず記録を残す。
- 他のエージェントが作業中のファイルを直す必要がある場合は、統括エージェントに知らせ、衝突を避ける。

### 5. タスク管理と作業フロー

タスク管理は GitHub の Issue / Project / Milestone で行う。

#### Issue の種類（ラベル `type:*`）

| 種類 | 用途 | テンプレート |
| --- | --- | --- |
| `type:adr` | 設計判断の議論・決定依頼。結論は ADR ファイルに反映 | ADR |
| `type:spike` | 調査・検証（タイムボックス付き）。成果物は報告と試作コード（置き場所は §3） | Spike |
| `type:task` | 実装・ドキュメント・設定の作業 | Task |
| `type:epic` | 複数 Task をまとめる親 Issue（sub-issues を使う） | — |
| `type:bug` | 不具合 | Bug |

#### 状態ラベル

- `agent:ready` — 受け入れ基準が明確で、依存する ADR が Accepted。**エージェントはこのラベルの Issue だけを自律的に着手してよい。**
- `status:needs-decision` — 人間の判断待ち（Proposed ADR に依存など）。エージェントは着手しない。
- `agent:blocked` — エージェントが作業中に判断が必要になった。理由を Issue にコメントして人間を待つ。
- `area:*` — 影響範囲（`federation`, `api`, `db`, `queue`, `storage`, `web`, `mobile`, `i18n`, `infra`, `harness`, `docs`）
- `priority:p0`〜`p2`

#### 作業フロー（エージェント）

1. `agent:ready` かつ担当者なしの Issue を選ぶ（Milestone の若い順 → priority の高い順）。自分を assign し、着手コメントを残す。
2. ブランチ `<type>/<issue番号>-<slug>`（例: `task/42-sqlite-adapter`）。
3. 関連 ADR・要件 ID を読み、Accepted の決定に従う。決定にない設計判断が必要になったら、
   小さいものは PR 説明に明記、大きいものは Proposed ADR を起票して `agent:blocked`。
4. コミットは Conventional Commits、英語。コミット・push・PR の前に検査を走らせる義務はなく、Merge Queue の全検査が `main` に入る前の唯一の関門である（ADR-0079）。
5. PR を作成（テンプレートに従い `Closes #N`、受け入れ基準のチェック結果を記載）。**main への直接 push はしない。**
6. 作業するエージェントは PR をマージしない。統括役か決定者が Merge Queue に入れる（[workflow.md §7](../agents/workflow.md#7-merge-through-the-merge-queue)）。

#### Definition of Ready / Done

- Ready: 背景・受け入れ基準・関連 ADR / 要件 ID・影響範囲が書かれている。依存 Issue が解決済み。
- Done: 受け入れ基準を満たす、Merge Queue の `check` を通ってマージ済み、ドキュメント（ADR / docs / i18n カタログ）が更新済み。

#### Milestone と Project

- Milestone = 期間ではなく到達状態（M0〜M6、[ビジョン](../requirements/00-vision.md) 参照）。
- GitHub Project（v2）でボード管理: Status（Backlog / Ready / In progress / In review / Done）、Priority、Area、Milestone。

## 経緯

本プロジェクトは複数のコーディングエージェントが並行して自律的に作業する前提で、人間は意思決定に集中する。口頭やチャットで決めたことはエージェントから見えないため、設計判断をリポジトリ内に機械的に辿れる形で残す必要がある。

当初は 1 判断 1 ファイルとし、Accepted の本文を書き換えず新しい ADR で置き換えていた。ADR が 140 件を超えると、1 つの主題の結論が複数のファイルと Status の注記に分かれ、結論を探すエージェントにとってノイズになった。そこで主題ごとに統合し、本文を書き換えてよいことにした。

変更の履歴は git（コミット・PR・Issue）が持つ。文書に「初版からの変更」「当初は〜だった」「旧案」などを書くと、履歴が git と二重になり、読み手は現在の決定と過去の経緯を読み分ける必要があり、文書が変更のたびに長くなって「今どうなっているか」が埋もれる。ADR も同じ規則で「この決定をした」という事実だけを記録していたが、判断の変遷と却下した案は ADR の主な役割なので、節を分けて書くことにした。調査は、ある時点で何を試し何が分かったかの記録であり性質として履歴なので、報告と試作コードはリポジトリの外に置く。

Issue 単位で並行して作業するエージェントが、各自「担当範囲ではない」という理由で壊れた箇所を見過ごすと、壊れた状態が積み重なって後続の作業を止める。これがボーイスカウトルールの理由である。

作業フローの検査は、当初は手元の `make check` を通す形だった。タスクランナーを go-task に移し（ADR-0081）、コミット・push・PR の前に検査を走らせる義務をなくした（ADR-0079）。マージは当初、人間がレビューを承認して行っていた。今は決定者の運用として、統括役か決定者が Merge Queue に入れ、レビューの承認を Done の条件にしない（[workflow.md §7](../agents/workflow.md#7-merge-through-the-merge-queue)）。

## 採らなかった案

- 不変の ADR を積み重ねる: 決定の時点の記録として正確だが、経過は git で足り、今の結論を複数のファイルから組み立てる負担のほうが大きい。
- 番号を 0001 から振り直す: 一覧はきれいになるが、書き換えられない古い Issue や PR の番号が別の ADR を黙って指す。
- 決定者とのやり取りの原文を残す: 決定の根拠を示せるが、読み手に要るのは結論と理由で、原文はノイズになる。
- ADR にも経緯を一切書かない: 規則は単純になるが、同じ案が繰り返し提案され、理由が git を掘らないと分からない。

## Consequences（影響）

- `scripts/agentkit.sh adr list` を見れば、何が決まっていて何が未決かを判断できる。
- 未決（Proposed）の ADR に依存する実装 Issue は `status:needs-decision` で止めておける。
- ADR の過去の版を知るには `git log` を見る。文書を読めば現在の状態が分かり、経過は `git log` / `git blame` / PR で辿れる。
- 経緯を知りたい読み手のために、コミットメッセージと PR の説明に「なぜ変えたか」を必ず書く。
- エージェントは、文書を更新するときに変更履歴の節を足さない（AGENTS.md と ADR の手順書に明記する）。
- リポジトリには、製品のコードと現在の設計だけが残る。lint やビルドの設定から試作コード用の除外を外せる。
- 調査用ブランチはマージ後の自動削除の対象にならないので、パーマリンクは残り続ける。不要になったブランチは、Issue のリンク切れを承知の上で削除してよい（コミットはパーマリンクから辿れなくなる）。
- 壊れた状態が main に残り続けにくくなる。本題の差分に関係のない修正が混ざりやすくなるので、コミットを分け、PR の説明に明記する規律が必要になる。
- エージェントは「どれを拾ってよいか」をラベルだけで判断できる。人間のボトルネックは `status:needs-decision` に集約される。
