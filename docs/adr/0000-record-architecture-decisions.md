# ADR-0000: ADR と文書と作業の進め方

- Status: Accepted
- Date: 2026-11-11
- Deciders: @rosylilly
- Issue: #2078

## Decision（決定）

### 1. 設計判断を ADR で記録する

- **ADR に書くのは、判断、その理由（採らなかった案を含む）、見直す条件の 3 つだけにする。** ファイル・関数・タスク・設定キーの名前、構成の一覧、手順は書かない。それらはコードが正であり、ADR に写すと、コードが変わるたびに ADR も変えることになる。
- ADR は主題ごとに 1 ファイルとする。主題を持つ ADR があればそれを書き換え、どの ADR も持たない主題にだけファイルを足す。
- Accepted の結論を変えるときは、本文をその場で書き換え、置き換えた内容のうち読み手に要るものだけを経緯か採らなかった案に移す。
- 節番号は変えない。コードと文書が節番号で引用している。統合して廃番にした番号は再利用せず、移転先を引けるようにする。
- **Accepted への変更と、Accepted の結論の変更は決定者だけが行う。** 決定者が述べた決定は、エージェントが ADR に反映してよい。決定者とのやり取りの原文は載せない。
- 設計文書（ADR・要件・アーキテクチャ）は v0 の間は日本語、コード・識別子・コミットは英語で書く。

### 2. リポジトリ内の文書は現在の状態だけを記述する

- リポジトリのすべてのファイルは「今」を記述する。変更の経緯はコミットメッセージと PR の説明に書く。
- 例外は ADR の経緯と採らなかった案だけである。決定が今の形である理由を短く書き、版ごとの変更の記録にはしない。
- 未解決の事項の一覧には未解決のものだけを置く。解決したら結論を本文に書き、項目を消す。
- 外部の事実（価格・制限値）の確認日と出典は、値の属性なので書いてよい。

### 3. 調査（spike）の報告と試作コードはリポジトリに置かない

調査の報告は Issue のコメントに書き、試作コードはマージしないブランチに置く。調査の結論だけを、ADR と設計文書に現在形で書く。調査は「ある時点で何が分かったか」の記録であり、性質として履歴だからである。

### 4. ボーイスカウトルール

作業中に見つけた壊れた箇所は、担当範囲の外でも放置しない。小さく直せるものは本題と別のコミットで直して PR に書き、直せない大きなものは Issue にする。

### 5. タスク管理と作業の単位

- タスクは GitHub の Issue と Milestone で管理する。Milestone は期間ではなく到達状態である。
- エージェントが自律的に着手してよいのは、受け入れ基準が明確で、依存する ADR が Accepted の Issue だけである。決定待ちの Issue には着手しない。
- **納品の単位は Issue ではなくゴール（Epic・フェーズ・Milestone）である。** 1 つのゴールは、共有するファイルが許すかぎり少ない PR にまとめ、その中で Issue ごとに 1 コミットにする。
- **ブランチの中の履歴は直線に保つ。** 最新化は rebase で行い、修正は直す対象のコミットに畳む。マージコミットは Merge Queue が作るものだけにする。
- **作業したエージェントが完了まで持つ。** 自分で Merge Queue に入れ、マージまで追い、作業場所を片付け、完了した Issue・Epic・Milestone を閉じる。
- 取り消せる判断は自分で決めて PR に書く。止まって決定を求めるのは、Accepted の ADR が扱わず、取り消しが高くつく判断だけである。
- 検査の配置は ADR-0079 が決める。

### 6. エージェントの挙動を守るもの

エージェントの挙動は、次の 4 つで守る。強い順に使い、上で済むものは下に書かない。

1. **枠**: 置き場所が形で決まり、追加は新しいファイルを置くだけで済む。
2. **道具**: 正しい手順がいちばん楽である。古い手段は残さない。
3. **関門**: 必ず通る所で検査し、失敗のメッセージが直し方を言う。
4. **文章**: 上の 3 つで扱えない判断だけを書く。

- 規則は、破った瞬間に出る場所（失敗のメッセージ）に置く。事前に読ませる文書には置かない。
- 文章を足せば通る検査は作らない。
- 設計文書とエージェント向けの文書の純増は、決定者の承認を要する。
- エージェント向けの指示に足せるのは、自明でない・繰り返し起きた・行動できるほど具体的、の 3 つをすべて満たすものだけである。エージェントは PR で提案し、決定者が採否を決める。
- 会話で決まった運用（使うモデル、作業場所、報告の形）は、会話ではなくエージェントの定義に固定する。
- サブエージェントは短く走らせ、待たせない。CI を待つのは統括役の監視 1 本にする。
- UI は、仕様の文章より枠と実例で統制する。画面ごとに量の予算を置き、PR の前に描画した画面を見ることを関門にし、模範とする画面を決める。

### 7. 見直す条件

§6 は計測で評価する。指標は、サブエージェントのコンテキストに占める生の検索出力の割合、決定者が同じ指示を言い直す回数、設計文書の総量、UI の変更 1 件あたりの指摘の回数である。これらが動かなければ §6 を見直す。

## 経緯

- 当初は 1 判断 1 ファイルで、Accepted の本文は書き換えなかった。ADR が 140 件を超えると、1 つの主題の結論が複数のファイルに分かれたので、主題ごとに統合し、書き換えてよいことにした。
- 統合で一度縮んだ ADR は、4 日で元の量に戻った。4 週間で ADR は約 9 倍、設計文書は約 5 倍になり、機能の変更の 57% が文書も変えていた。ADR が実装を写していたことと、文章を足せば通る検査があったことが原因だった。そこで ADR に書くものを 3 つに絞り（§1）、純増を承認制にした（§6）。
- 作業の単位は当初 Issue ごとに 1 PR で、マージは決定者が行っていた。並行する PR が同じファイルで衝突し、決定者は「まとめて 1 PR に」「rebase で」「マージまで自分で」を繰り返し指示していたので、それを決定にした（§5）。
- 4 週間の作業記録を計測すると、コードとスキーマへの決定者の訂正は 1〜2 件で、作業の進め方・UI・文書への訂正が約 100 件だった。前者には同じ形の置き場所と、直し方を言う検査があり、後者にはなかった。
- 指示の効き方も計測した。古い手段を無くしたとき（タスクランナーの移行）は翌日に 100% 切り替わった。拒否する仕組みは対象の形だけを止め、同じ目的の別の形に移った。文章は、必ず通る手順に具体的なコマンドとして埋めたものだけが効き、きっかけのない一般則は効かなかった。会話での指示は、コンテキストの圧縮の後に守られなくなった。§6 はこの結果による。

## 採らなかった案

- 不変の ADR を積み重ねる: 決定の時点の記録として正確だが、今の結論を複数のファイルから組み立てる負担のほうが大きい。
- ADR に実装の詳細まで書く: 1 か所で全体が分かるが、コードの写しになり、コードと一緒に変え続けることになる。
- ADR に経緯を一切書かない: 規則は単純になるが、同じ案が繰り返し提案される。
- 手順書を詳しく書いて守らせる: 追加が安いが、計測では効かず、書き足す作業だけが増えた。
- 拒否する仕組みだけで止める: 対象の形は止まるが、楽な代わりがなければ別の形に移る。
- Issue ごとに 1 PR: 変更は小さく読めるが、共有するファイルで衝突し、検査と待ちが Issue の数だけ繰り返される。
- マージを決定者が行う: 決定者が確かめられるが、決定者が律速になり、PR が放置される。

## Consequences（影響）

- 何が決まっていて何が未決かは、ADR の一覧で分かる。未決の ADR に依存する Issue は止めておける。
- ADR は短くなり、コードが変わっても判断が変わらないかぎり変えずに済む。実装の詳細を知るにはコードを読む。
- 文書を増やす変更は決定者の承認を待つので、決定者の手間が増える。
- 規則を足すには、文章を書く代わりに枠・道具・関門のどれかを作る必要があり、1 つの規則を足す費用は上がる。
- 1 つの PR が大きくなる。レビューは PR ではなくコミットの単位で読む。
