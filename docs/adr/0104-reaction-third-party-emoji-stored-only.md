# ADR-0104: リアクションの第三のサーバーのカスタム絵文字は記録済みのものだけを使う

- Status: Proposed
- Date: 2026-10-27
- Deciders: @rosylilly
- Issue: #1469

## Context（背景・課題）

[ADR-0052](0052-emoji-reactions.md) §1 は、受信したリアクション（FR-116）のカスタム絵文字を「ADR-0051 の規則で `custom_emojis` に取り込む（第三のサーバーの絵文字は、その `Emoji` の `id` で識別する）」と決めています。
Pleroma / Akkoma は、リアクションに第三のサーバーの絵文字を使えます（`pkg/testkit/fixtures/federation/akkoma/3.20/emoji-react*.json`）。

一方 [ADR-0051](0051-custom-emoji.md) §1 は、リモートの絵文字の `domain` を文書の送り手のホストにし、`uri` は `Emoji` の `id` が送り手と同じオリジンのときだけ記録します。他のサーバーの絵文字の `id` を名乗って行を奪わせないためです。
ADR-0052 §1 の文のとおりに第三のサーバーの絵文字を取り込むと、リアクションの送り手が、自分のものではないサーバーの `(shortcode, domain)` の行を作り、画像の URL を変える（`custom_emoji_images` に行を足す）ことができます。
その行は、そのサーバーの人の投稿・プロフィールの絵文字と同じ行なので、ある人のリアクション 1 つで、別のサーバーの絵文字の見た目をこのサーバー全体で差し替えられます。

main のコードはすでに次のように振る舞います。

- リアクションの絵文字のドメインは `Emoji` の `id` のホスト（`id` が無ければ主体のドメイン）です。
- 主体のドメインの絵文字は、ADR-0051 の規則で画像と一緒に取り込みます。
- ほかのサーバーの絵文字は、そのサーバーの文書から記録済みのときだけ使い（このサーバーの絵文字はローカルの絵文字）、行も画像も変えません。記録が無ければリアクションを捨てます（`content.RecordRemoteReaction`、[federation.md §3.4](../architecture/federation.md#34-アクティビティごとのハンドラ)）。

これは ADR-0052 §1 の文と食い違うので、どちらを正とするかを決めます。

## Decision Drivers（判断基準）

1. **他のサーバーの絵文字を偽れないこと**（ADR-0051 §1、ADR-0019）: あるサーバーの絵文字の行と画像は、そのサーバーの文書だけが決める。
2. **受信の忠実さ**（ADR-0052 の判断基準 3）: Akkoma の人が第三のサーバーの絵文字で付けたリアクションを、なるべく失わない。
3. **実装と運用の小ささ**: 取得のジョブや、ドメインごとに別の行を持つ仕組みを増やさない。

## Considered Options（選択肢）

1. **A: 記録済みのものだけを使う**: 第三のサーバーの絵文字は、そのサーバーの文書から記録済みのときだけ使い、行も画像も変えない。無ければリアクションを捨てる。
2. **B: ADR-0052 §1 のとおり取り込む**: リアクションの `Emoji` で、第三のサーバーの `(shortcode, domain)` の行を作り、画像を更新する。
3. **C: 送り手の名前空間に取り込む**: 第三のサーバーの絵文字を、リアクションの送り手のドメインの行（`(shortcode, 送り手のドメイン)`）として記録する。ほかのサーバーの行は変えない。
4. **D: `Emoji` の `id` を取得して確かめる**: 記録が無ければ `id` をそのサーバーから取得し、返った `Emoji` で取り込む。

## Decision（決定）

> Proposed の間は推奨案。Accepted にするのは人間の Decider のみ。

**推奨案は A** です。ADR-0052 §1 の「絵文字の行は ADR-0051 の規則で `custom_emojis` に取り込みます（第三のサーバーの絵文字は、その `Emoji` の `id` で識別する）」の文だけを、次の規則で置き換えます。ADR-0052 のその他の決定は変えません。

- リアクションのカスタム絵文字のドメインは、`Emoji` の `id` のホストです。`id` が無ければ、リアクションの主体のドメインです。
- ドメインが主体のドメインなら、ADR-0051 の規則で `custom_emojis` に画像と一緒に取り込みます。
- ドメインがこのサーバーなら、ローカルの絵文字を `(shortcode, '')` で引きます。
- それ以外（第三のサーバー）なら、`(shortcode, そのドメイン)` で記録済みの行があるときだけ使います。リアクションからは行も画像も作らず、変えません。行が無ければリアクションを捨てます（`EmojiReact` も、絵文字付きの `Like` も同じ）。

理由は判断基準 1 です。B は、送り手が他のサーバーの絵文字の行と画像を決められるので、ADR-0051 の識別の規則と両立しません。
C は偽装を防げますが、同じ絵文字が送り手ごとに別の行になり、集計（ADR-0052 §1 の絵文字の鍵）が割れ、送り手が名乗った shortcode で自分のドメインの行を上書きできてしまいます。
D は忠実さが一番高い方法ですが、リアクション 1 つごとに外への取得が増え、取得のジョブ・失敗の扱い・SSRF の経路の検査が要ります。Akkoma の利用者は、自分のサーバーにある絵文字（多くは同じサーバーの人が使うもの）を使うことが多く、その絵文字の作者の投稿やプロフィールを一度受け取っていれば A でも記録できます。

この決定を見直す条件:

- 第三のサーバーの絵文字のリアクションが、記録が無くて捨てられる割合が運用で大きいと分かったとき（D を検討する）。
- FEP-c0e0 などで、リアクションの `Emoji` の真正性を確かめる仕組みが定まったとき。

## Consequences（影響）

- 良い: リアクションの送り手は、他のサーバーの絵文字の行と画像を作れず、変えられません。絵文字の行と画像を決めるのは、そのサーバーの文書だけです（ADR-0051 §1 と一致する）。
- 良い: 取得や新しいジョブが要りません。
- 悪い: このサーバーがまだ見たことのない第三のサーバーの絵文字のリアクションは、記録されずに捨てられます。Akkoma の人のリアクションの一部が件数に出ません。
- 悪い: 記録済みの第三のサーバーの絵文字の画像が古くても、リアクションでは更新しません（そのサーバーの文書が届いたときに更新される）。
- この ADR が Accepted になったら、ADR-0052 の Status の行に、§1 のこの文をこの ADR が置き換えると注記します（ADR-0070 が ADR-0051 にしたのと同じ）。
- 実装（`content.RecordRemoteReaction` と `testkit.RemoteInteractionContract`）と [federation.md §3.4](../architecture/federation.md#34-アクティビティごとのハンドラ) は、すでにこの規則のとおりです。

## Pros and Cons of the Options（詳細比較・任意）

| | A: 記録済みだけ（推奨） | B: 取り込む | C: 送り手の名前空間 | D: 取得して確かめる |
| --- | --- | --- | --- | --- |
| 他のサーバーの絵文字の偽装 | 防ぐ | 防げない | 防ぐ | 防ぐ |
| 第三のサーバーの絵文字のリアクションの受信 | 記録済みのときだけ | すべて | すべて | 取得できたとき |
| 集計の一貫性 | 保つ | 保つ | 送り手ごとに割れる | 保つ |
| 追加の実装 | なし | なし | 行の分け方 | 取得のジョブ・失敗の扱い |

## Open Questions / 要検証

- 要検証: Akkoma の利用者のリアクションのうち、第三のサーバーの絵文字の割合（運用の指標が無いので、捨てた件数をログから見積もる）。
