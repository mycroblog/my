# ADR-0151: 投稿の自動削除のサーバーの既定と上限

- Status: Accepted
- Date: 2026-11-07
- Deciders: @rosylilly
- Issue: #2434

## Decision（決定）

[この決定を見直す条件](#この決定を見直す条件) に当たれば覆る。要件は FR-118・FR-121・FR-912 である。

投稿の自動削除（FR-118）は利用者ごとの設定である。運営者はその上に、新しいアカウントが始める既定（§2）と、どの設定も超えられない保持の上限（§3）を置ける。

### 1. 対象

- 対象はローカルの投稿だけである。リモートの投稿は FR-803 の保持期間に従い、ここの既定と上限の影響を受けない。
- ブーストは投稿ではないので、今までどおり対象外である。
- 消し方は FR-118 と同じで、本人の削除と同じく連合先へ `Delete` を送る。

### 2. サーバーの既定（登録のときに写す）

運営者はインスタンス設定で既定の設定を決める。項目は利用者の設定と同じである。設定は 1 キー 1 スカラーなので（data-model §4.9）、項目ごとにキーを分ける。

| キー | 型 | 既定値 |
| --- | --- | --- |
| `auto_delete_default_enabled` | bool | `false` |
| `auto_delete_default_min_age_days` | int（1〜3650） | `30` |
| `auto_delete_default_keep_pinned` / `_keep_bookmarked` / `_keep_favourited` | bool | `true` |
| `auto_delete_default_keep_media` / `_keep_polls` | bool | `false` |
| `auto_delete_default_keep_public` / `_keep_local` / `_keep_unlisted` / `_keep_private` | bool | `false` |
| `auto_delete_default_keep_direct` | bool | `true` |
| `auto_delete_default_keep_min_boosts` / `_keep_min_favourites` | int（0〜1,000,000。0 は閾値なし） | `0` |

- キーの既定値は今の組み込みの既定（無効、30 日、ピン留め・ブックマーク・お気に入り・`direct` を残す）と同じなので、運営者が何も決めなければ今と変わらない。
- 新しいローカルのアカウントは、作られたときにこの既定を自分の設定として受け取る。`content` が `account.local_account_created` を同期で購読し、同じトランザクションで `status_auto_delete_policies` の行を書く。
  - このイベントはローカルのアカウントを作るすべての経路（登録のフォーム、外部のログインの提供元、招待、CLI の `my admin` による作成）が発行するので、経路ごとの書き分けはない。インスタンスの Actor は発行しないので対象外である。
  - 書く値は、既定に §4 の実効の設定を当てたものである。登録のときの上限を既定が超えていても、新しいアカウントは最初から上限の内にいて、§5 の猶予の対象にならない。
- 既存のアカウントは変わらない。登録の後の設定はそのアカウントのものであり、既定を後で変えても、既定を写したアカウントも含めて変わらない。
- 設定の画面は、既定から来た値もふつうの値として出す（既定から来たことは示さない）。保存の有無を記録する列は持たない。

### 3. サーバーの上限

上限は任意で、既定では無い。

| キー | 型 | 既定値 | 意味 |
| --- | --- | --- | --- |
| `auto_delete_max_age_days` | int（0〜3650） | `0` | 0 は上限なし。1 以上で、どの設定もこの日数より長く残せない |
| `auto_delete_max_allow_pinned` | bool | `true` | 上限の下でピン留めを残せる |
| `auto_delete_max_kept_pins` | int（1〜5） | `5` | 上限の下で残せるピン留めの数。ピン留めした時刻の新しい順に数える |
| `auto_delete_max_allow_bookmarked` / `_allow_favourited` / `_allow_media` / `_allow_polls` | bool | `false` | 上限の下でその例外を使える |
| `auto_delete_max_allow_visibilities` | bool | `false` | 上限の下で残す公開範囲を使える |
| `auto_delete_max_allow_thresholds` | bool | `false` | 上限の下でブースト数・お気に入り数の閾値を使える |
| `auto_delete_grace_days` | int（0〜365） | `30` | 新しく上限に縛られたアカウントが縛られるまでの猶予（§5） |

- 例外は投稿をいつまでも残せるので、既定で使えるのはピン留めだけである。ローカルのピン留めは 1 アカウント 5 件までなので、既定の 5 件は「ピン留めは全部残る」を意味する。
- 上限が有効な間、`keep_posts_longer`（§6）を持たないアカウントについて:
  - 自動削除を無効にできない。
  - `min_age_days` は上限以下でなければならない。短いのは構わない。
  - 運営者が許していない例外は使えない。
- 上限の有効化・引き下げ・例外の変更はどれも、すでに保存された設定を書き換えない。保存された設定と上限の食い違いは §4 の実効の設定で解き、§5 の猶予の後に効く。

### 4. 実効の設定

ジョブ・プレビュー・設定の API は、同じ 1 つのドメインの関数 `content.EffectiveAutoDeletePolicy(保存した設定, 上限, 免除)` で実際に使う設定を決める。

- 上限が無いか、アカウントが `keep_posts_longer` を持てば、保存した設定そのものである。
- そうでなければ:
  - 有効である。
  - 日数は、保存した設定が有効ならその日数と上限の短いほう、無効なら上限である。
  - 例外は、保存した設定の例外のうち運営者が許したものだけである。ピン留めは新しい順に `auto_delete_max_kept_pins` 件までを残す。
- 設定の行が無いアカウントの保存した設定は、組み込みの既定（FR-118）である。サーバーの既定（§2）は登録のときに写すだけで、行の無い既存のアカウントに後から効くことはない。
- 自動削除を無効にしている人と行の無い人も、上限が有効なら対象になる。どの設定も上限を超えて投稿を残せないからである。

### 5. 猶予と事前の通知

上限の有効化・引き下げと、アカウントが `keep_posts_longer` を失ったときには、多くの投稿が一度に期限を迎えうる。そこで、保存した設定と実効の設定が違うアカウント（**縛られるアカウント**）には、猶予の後にだけ実効の設定を当てる。

データ（ADR-0020）は次の 2 つの表で持つ。

| テーブル | 分類 | カラム | 制約 |
| --- | --- | --- | --- |
| `status_auto_delete_limit_notices` | イベント | `id`, `account_id`, `max_age_days`（通知した上限）, `noticed_at`, `enforce_from`（`noticed_at` + 猶予） | インデックス `(account_id, id DESC)` |
| `status_auto_delete_limits` | 投影 | `account_id`（PK）, `notice_id`, `max_age_days`, `enforce_from` | 今縛られているアカウントだけが行を持つ |

- 猶予の始まりを NULL 可の時刻の列で持たず、通知のイベントと、今効いている通知の投影で表す。
- 検出: 1 時間ごとのジョブ `content.auto_delete_statuses` は、上限が有効な間、有効な設定のアカウントだけでなく `active` なローカルのアカウントをすべて同じカーソルで読む。アカウントごとに:
  - 縛られる（実効の設定が保存した設定と違う）のに投影の行が無い、または行の `max_age_days` が今の上限より長い（上限の引き下げ）なら、新しい通知を記録する。`enforce_from` はその時刻に `auto_delete_grace_days` を足したものである。投影はこの通知を指す。
  - 縛られないなら（設定を上限の内に直した、`keep_posts_longer` を得た、上限を外した・引き上げた）、投影の行を消す。通知のイベントは残る。
  - 猶予の始まりは、上限の変更や権限の喪失をジョブが見つけた時刻で、変更から 1 時間以内である。権限の喪失のイベントを個別に購読しないので、プランの終わり（ADR-0072 §7）も手での剥奪もロールの削除も同じ道を通る。
- 削除: 投影の行が無いか `enforce_from` の前は、保存した設定で消す（無効なら消さない）。`enforce_from` を過ぎたら実効の設定で消す。
- 速さ: 1 回の実行で 1 アカウント 100 件、1 トランザクション 20 件のままである。上限で古い投稿の多いアカウントが一度に縛られても、`Delete` の配送は数時間から数日に分かれる。
- 猶予の日数を変えても、すでに記録した通知の `enforce_from` は変わらない。
- 投影は、最新の通知と今の設定・権限・上限から作り直せる。

### 6. 権限 `keep_posts_longer`

- 新しい権限 `keep_posts_longer` を持つアカウントは上限に縛られず、自動削除を無効にもできる（§4 の免除）。
- 区分は `member` で（ADR-0070 §1）、どのロールにも付けられる。FR-912 の課金のロールの許可された権限にも加わるので、サポーターのプランに含められる（ADR-0072 §5）。
- 権限を失えば §5 の猶予を経て上限に縛られる。

### 7. 通知

- 新しい通知の種類 `auto_delete_limit` を足す。§5 で通知を記録したトランザクションでイベント `content.auto_delete_limit_noticed` を発行し、`notification` がそれを購読して、通知の ID を重複の鍵に 1 回だけ送る。
- アプリ内・Web Push・メールで送り、メールも既定で有効である。投稿が消えるのは取り返しがつかないので、ふだんログインしない人にも届ける。種類は通知の設定（FR-210）でほかの種類と同じく切れる。
- 内容は、上限の日数、実効の設定が効き始める日、設定の画面（プレビューのあるところ）へのリンクである。
- i18n（ADR-0009）: アプリ内は `client` の名前空間で日付を出す。Web Push とメールは Go が整形する名前空間なので、日付の引数を使わず、残りの日数を数の引数で出す。メッセージは `locales/en` と `locales/ja` に足す。
- 運営者が上限を有効にすると、次の実行で縛られるローカルのアカウントすべてに通知が出る。管理画面は保存の前にこのことを示す。

### 8. API

- `GET /preferences/auto_delete` と `PUT` の応答は、保存した設定に `server_limit` を加える。上限がこのアカウントに効かなければ `null` で、効けば上限の日数、許された例外、残せるピン留めの数、実効の設定、縛られていれば実効の設定が効き始める時刻を持つ。
- `PUT /preferences/auto_delete` は、上限が効くアカウントの、無効化・上限を超える日数・許されていない例外を `422` で断る。`detail` はほかの検証と同じく違反した項目を示す。
- `POST /preferences/auto_delete/preview` は、送られた設定に §4 を当てて数える。縛られているアカウントの画面は、保存した設定のプレビューで、猶予の後に何が消えるかを示す。
- 上限は公開する。上限が有効なら `GET /api/v1/instance` の `auto_delete_limit` に上限の日数・許された例外・残せるピン留めの数を返し（無効なら `null`）、紹介のページ（about）が表示する。登録する前に知れるようにするためである。サーバーの既定は公開しない。
- 既定・上限・猶予の変更は `manage_settings` を要し、ほかの設定と同じく `setting_changed` として監査ログに残る（ADR-0058）。

### この決定を見直す条件

- 1 時間ごとの全アカウントの走査が大きなサーバーで重くなったら、権限と設定の変更のイベントから縛られるアカウントを求める形に変える。
- 運営者が既存のアカウントにも既定を当て直したいと求めたら、§2 の「既存のアカウントは変わらない」を見直す。

## 経緯

FR-118 の自動削除は利用者ごとの設定だけで、運営者がサーバー全体の既定や、保持の上限を決める手段がなかった。投稿を長く持たないことをサーバーの方針にしたい運営者（保持の費用、法令、コミュニティの性格）がいる一方で、サポーターのプランの特典として長く残せるようにしたいという求めもある。

決定者は次の形を決めた: 既定は登録のときに写し、既存のアカウントを変えない。上限は任意で、例外は運営者が選び、既定ではピン留めだけを数を限って残せる。上限で多くの投稿が一度に期限を迎えるときは事前に通知し、猶予を置き、ジョブの速さは変えない。上限は公開する。権限 `keep_posts_longer` は上限を外し、プランのロールにも付けられる。無効にしている人も上限の対象であること、ピン留めの数の既定が 5 件であること、通知がメールにも届くこと、既定から来た値を画面で区別しないことも決定者が決めた。

## 採らなかった案

- 既定を、設定の行の無いアカウントに読むたびに当てる: 既定の変更が既存のアカウントの投稿を消しうる。決定者は既存のアカウントを変えないことを選んだ。
- 上限を有効にしたときに保存した設定を書き換える: 実装は単純だが、権限を取り戻したときや上限を外したときに本人の設定が戻らない。実効の設定を毎回求めれば、保存した設定は本人のもののまま残る。
- 猶予の始まりを、ロールの剥奪・プランの終わり・設定の変更のイベントごとに記録する: 始まりの時刻が正確になるが、権限を失う経路（手での剥奪、プランの終わり、ロールの権限の変更、ロールの削除）ごとに購読が要り、取りこぼしが猶予なしの削除になる。ジョブが毎回縛られるかを判定すれば、どの経路でも同じ規則になり、遅れは 1 時間以内である。
- 上限の下で自動削除を無効にしている人を対象外にする: 上限が新しい設定にしか効かず、保持の方針として意味をなさない。
- 上限を連合先へ伝える: リモートのサーバーが持つ写しを消す手段は `Delete` だけで、それは FR-118 の削除がすでに送る。

## Consequences（影響）

- 運営者は保持の方針をサーバーとして決め、登録の前に公開できる。サポーターのプランが長く残す権利を特典にできる。
- 上限を有効にすると、すべてのローカルのアカウントに通知とメールが一度に出る。ジョブの走査も、有効な設定のアカウントからすべての `active` なローカルのアカウントに広がる。
- 猶予の後、縛られたアカウントの古い投稿は 1 時間に 100 件ずつ消え、量によっては数日かかる。その間に設定を直せば止まる。
- 後続の作業: #2435（サーバーの既定）、#2436（上限と権限）。FR-118・FR-912 の更新と FR-121 の追加は ADR と同じ変更で行う。
