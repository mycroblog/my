# ADR-0105: 利用料金の取り込みの要求の予約

- Status: Proposed
- Date: 2026-10-27
- Deciders: @rosylilly
- Issue: #1469

## Context（背景・課題）

[ADR-0068](0068-billing-import.md) §4 は、AWS の課金される要求（Cost Explorer のページ 1 つ = $0.01）を、`billing_import_runs` の `requests` の UTC の日・暦月の合計で数えて止めると決めています（FR-904、NFR-COST）。
ハンドラは呼ぶ前に日と月の残りを読み、その数までしか事業者を呼びません。

この数え方では、記録の前の試行は数に入りません。同じ事業者の試行が同時に走る（定期のジョブと手動の取り込み、ジョブの再試行とリースの切れた二重の実行、複数のレプリカ）と、
どの試行も同じ残りを読んで呼ぶので、合わせて日の上限を超えて課金されます。§4 が許すずれ（「プロセスが要求の後・記録の前に止まると数えられない」、1 回につき 4 要求まで）は 1 つの試行が止まった場合だけのもので、同時の試行のずれは試行の数だけ大きくなります。

決定者は 2026-10-27 に、#1552 が実装した予約の規則を「採用し Proposed ADR で supersede」すると答えました。この ADR は、その規則で ADR-0068 §4 の数え方を置き換える案です。ADR-0068 の上限の値と、上限に達したときの扱いは変えません。

## Decision Drivers（判断基準）

1. **上限を超えて課金しない**: 同時の試行が何個あっても、日と月の上限の合計を超えて事業者を呼ばない（NFR-COST、ADR-0068 の判断基準 2）
2. **止まった試行で取り込みが長く止まらない**: 記録の前にプロセスが止まっても、次の取り込みが一定の時間のうちに走る（ADR-0068 の判断基準 3）
3. **同じジョブを二度呼ばない**: 成功したジョブの再実行（at-least-once、ADR-0004）は事業者を呼ばない
4. **トランザクションに外への I/O を入れない**（ADR-0003）、状態を NULL 可の時刻の列で表さない（ADR-0020）

## Considered Options（選択肢）

1. **A: 呼ぶ前に予約を記録する**: 事業者ごとに 1 つずつ走る短いトランザクションで、残りの要求を予約の行として書き、記録されるまで予約を上限の合計に数える
2. **B: 記録の後に数える（ADR-0068 §4 のまま）**: 同時の試行のずれを許す
3. **C: 事業者ごとのロックを呼び出しの間ずっと持つ**: 呼び出しをロックの中で行う

## Decision（決定）

> Proposed の間は推奨案。Accepted にするのは人間の Decider のみ。

**推奨案は A** です。ADR-0068 §4 の「数えるのは、§5 の `billing_import_runs` の `requests` の、その UTC の日・その UTC の暦月の `occurred_at` の行の合計」と、それに続くハンドラの手順を、次の規則で置き換えます。ADR-0068 §4 の上限の値（`billing_aws_max_requests_per_day`・`_per_month`）、`request_cap` の扱い、Google Cloud の上限は変えません。

- 試行は事業者を呼ぶ前に、事業者ごとに 1 つずつ走るトランザクション（PostgreSQL は事業者ごとのトランザクションのアドバイザリロック、SQLite は書き込みのトランザクションが 1 つずつ走ること）で次を順に決めます。
  1. 同じ `run_key` の試行がすでに成功していれば、何も呼ばず、何も記録せずにジョブを成功で終えます。
  2. 同じ事業者に、まだ記録されていない予約で `ReservationHold`（15 分）より新しいものがあれば、呼ばずに 1 分後に再試行します。
  3. 日と月の残り（記録された試行の `requests` と、記録されていない予約の `requests` の合計を上限から引いたもの）の小さいほうを求め、0 なら `request_cap` として記録します（ADR-0068 §4 のとおり）。
  4. 残りがあれば、その数を `billing_import_reservations`（イベント。`id` は試行の `billing_import_runs.id`、`source`、`run_key`、`requests`、`reserved_at`）に書き、その数を `MaxRequests` として渡します。上限のない事業者は `requests` を 0 で予約します。
- 事業者の呼び出しはトランザクションの外で行い、試行の記録（`billing_import_runs` の行）は ADR-0068 §2 のとおり別のトランザクションで書きます。
- 予約は、同じ `id` の試行が記録されるまで、その試行の要求の代わりに日と月の合計に入ります。記録された後は試行の `requests` だけを数えます。
- 記録されないまま `ReservationHold` を過ぎた予約（記録の前にプロセスが止まった試行）は、ほかの試行を待たせませんが、上限の合計には入り続けます。`ReservationHold` はジョブが走りうる時間（キューのリース）より長くします。

理由は判断基準 1 です。B は同時の試行のずれに上限がなく、C は事業者の呼び出しの間トランザクション（またはロックを持つ接続）を開いたままにするので ADR-0003 と両立しません。
A は予約の行を 1 つ書くだけで、呼び出しはロックの外です。

この決定を見直す条件:

- 事業者の課金が要求の数ではなくなったとき、または事業者の API が冪等キーや予算の上限を持つようになったとき。
- 止まった試行の予約が上限を使い、取り込みが止まることが運用で多いと分かったとき（予約を古くなったら数えない規則を検討する）。

## Consequences（影響）

- 良い: 同時の試行が何個あっても、課金される要求は日と月の上限を超えません。
- 良い: 成功したジョブの再実行は事業者を呼びません。
- 悪い: 記録の前にプロセスが止まった試行の予約は、実際に呼んだ数より多くても上限に数えられ、その日・その月の残りが減ります（ADR-0068 §4 では数えられずに上限が緩くなる側でした）。
- 悪い: 同じ事業者の試行は 1 つずつしか呼べず、重なった試行は 1 分ずつ遅れます。止まった試行があると、次の取り込みは最大 15 分待ちます。
- 悪い: `billing_import_reservations` の行は試行ごとに増えます。
- 実装（`internal/app/finance` の `Service.reserve`、両方言の `billing_import_reservations`）、[データモデル](../architecture/data-model/04-tables/12-finance.md)、運用の文書（`docs/operations/billing-import.md`）は、すでにこの規則のとおりです。
- この ADR が Accepted になったら、ADR-0068 の Status の行に、§4 の数え方をこの ADR が置き換えると注記します。

## Pros and Cons of the Options（詳細比較・任意）

| | A: 呼ぶ前に予約（推奨） | B: 記録の後に数える | C: 呼び出しの間ロック |
| --- | --- | --- | --- |
| 同時の試行で上限を超えない | ○ | ×（試行の数だけずれる） | ○ |
| トランザクションに外への I/O がない | ○ | ○ | × |
| 止まった試行の影響 | 予約が上限に残り、15 分待たせる | 数えられず上限が緩む | ロックが接続の切れるまで残る |
| 表とクエリ | 予約の表が 1 つ増える | 増えない | 増えない |
