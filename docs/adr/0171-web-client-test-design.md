# ADR-0171: Web クライアントのテスト: 保証は決められる最下層で 1 回だけ立てる

- Status: Proposed
- Date: 2026-11-17
- Deciders: @rosylilly
- Issue: #3161

## Decision（決定）

検査の配置の原則（ADR-0079 §18）を Web クライアントのパッケージ（ADR-0025 §3）に当てる。目的はテストを減らすことではなく、保証の持ち主を 1 つにし、壊れたときに足す場所を決めることである。

### 1. 原則

- **保証は、決められる最下層で 1 回だけ立てる。** 上の層は確かめ直さない。確かめ直したくなるのは下の保証が立っていない印で、直すのは下である。
- **種類は、固定する対象で決まる。** 安い種類で決まるものを高い種類で確かめない。

  | 種類 | 決められるもの |
  | --- | --- |
  | 静的な検査（型、lint、トークン、文言） | 書いてはいけない形、値の組の性質、層の越境 |
  | 単体テスト（DOM なし） | 値を受けて値を返すロジック |
  | 部品のテスト（DOM のシミュレーション） | ロール、名前、`aria-*` の状態、キー操作の結果、フォーカスの行き先 |
  | レイアウトの検査（実ブラウザ） | 溢れ、折り返し、鏡像、重なり、フォントの当たり方 |
  | 旅（本物のサーバー） | クライアントとサーバーの食い違い、画面とプロセスをまたぐ流れ |

- **テストは契約を固定する。** 期待に書くのは利用者・支援技術・上の層が頼るもので、クラス名・マークアップの文字列・内部の状態は書かない。
- 見た目の良し悪しはテストせず、人と評価役が見本を見る（ADR-0169 §2）。

### 2. パッケージごとの保証

| パッケージ | 保証するもの | 種類 |
| --- | --- | --- |
| design-tokens | 色の組のコントラスト（両テーマ）、トークンの完全性 | 静的な検査 |
| design-system | 物理方向を書かない、色はトークンだけ、レイアウトを書くのはレイアウトの部品だけ（§3） | 静的な検査 |
| design-system | 操作の部品のロール・名前・状態・キー操作・フォーカス | 部品のテスト |
| design-system | レイアウトの部品が、最小幅と各ブレークポイントの両側、長い文言、RTL、重なる面で崩れない | レイアウトの検査 |
| app-components・app-features・app | 渡された値からの意味のある出力、機能の中の操作、経路ごとの画面とその状態、遷移のあとのフォーカス | 部品のテスト（偽の API、§5） |
| app-data・platform | キャッシュ・再送・合流・失敗の扱い、ブラウザの API の包みの契約 | 単体テスト |
| i18n・ビルドの成果物 | キーの対応、同梱する文書、入口ごとに入るもの | 静的な検査 |
| e2e | クライアントとサーバーの食い違い（§5） | 旅 |

画面を RTL・ダークテーマ・幅ごとに描いて確かめない。向きは lint とレイアウトの部品、色はトークン、幅はレイアウトの部品が決め、画面はその合成である。計算されたスタイルが要る axe の規則は、デザインシステムの見本に対するレイアウトの検査だけが回す。

### 3. デザインシステムの作り

これがないと「描かないと分からない」場所が部品の数だけ増える。

- **レイアウトを書く部品を閉じた集合にする。** 配置・寸法・余白・溢れ・ブレークポイント・コンテナクエリを書けるのは、子を置くだけの部品に限り、lint で縛る。ほかの部品はそれを組む。ビューポートのブレークポイントはページの枠だけが使う（ADR-0025 §4）。
- **mycroblog を知る合成は置かない。** レイアウトを書かなくなった合成は `app-` のパッケージへ移す（ADR-0025 §3）。
- **向きで分かれるコードは 1 か所に集め**、単体テストで決める。
- **意味は動きなしで成り立つ。** フォーカスの移動・開閉の状態・読み上げをアニメーションの完了に乗せない。
- **操作しないと届かない状態は、値で描ける**ように部品を作る。

### 4. ストーリーは見本であり、テストではない

- 1 つのストーリーは、1 つの部品か画面の 1 つの状態で、渡す値だけで決まる。ロケール・テーマ・ビューポートを固定せず、操作も確かめも持たない。決めるのはカタログのツールバーだけである。
- 置くのは人か評価役が見て判断する状態だけで、組み合わせを並べない。テストは見本を入力として読んでよい。
- ストーリーを回すランナーは持たない。ブラウザを使わないテストのランナーは 1 つ（ADR-0025 §10）、ブラウザを動かすランナーも旅のもの 1 つで、レイアウトの検査はビルドしたカタログをそれで開く。
- DOM のシミュレーションは軽いもの（happy-dom）を使う。それで契約が決まらないテストだけを、決まるもの（jsdom）で回す。今それに当たるのは、React Aria の部品のキー操作によるフォーカスの移動である。

### 5. 旅と偽の API

- 旅に置くのは、本物のサーバーがないと決まらず、画面かプロセスの境界をまたぐものだけである: 認証と同意、書き込みが読み込み直しのあとも残ること、複数の人にまたがる流れ、ストリーム、サーバーでのメディアの処理、オフライン、Web Push。1 つの画面のふるまい、応答の扱い、レイアウト、サーバーのふるまい、成果物は、§2 の持ち主が確かめる。
- 偽の API は 1 つにし、API の仕様から型を取り、シナリオ（ADR-0015 §5）のデータで答える。本物との食い違いは仕様との適合の検査と旅が拾う。
- PR では 1 回ずつ回し、失敗したものだけ回し直す。同じサーバーで 2 回ずつ、回し直しなしで回すのは遅い検査（ADR-0079 §8）である。

### 6. 壊れたときに保証を足す場所

上の層（旅、掃引、手での確認、利用者の報告）で見つかった不具合は、**見つけた層にテストを足さない。** 欠けていた保証の層に、再現する最小の検査かテストを足してから直す。

| 見つかった不具合 | 足す場所 |
| --- | --- |
| 物理方向、トークンの外の色、レイアウトの部品の外のレイアウト、層の越境 | lint |
| コントラストの不足 | トークンの組の検査 |
| ロール、名前、状態、キー操作、フォーカス | その部品の部品のテスト |
| 溢れ、折り返し、鏡像、重なり | 原因のレイアウトの部品の検査。原因が合成なら §3 の違反 |
| キャッシュ、再送、並び | app-data の単体テスト |
| 画面の状態、経路、遷移のあとのフォーカス | app の部品のテスト |
| クライアントとサーバーの食い違い | 偽の API と仕様との適合の検査。流れがなければ旅 |

- 同じ層で繰り返す不具合は検査にする（ADR-0170 §6）。
- 遅い検査に**掃引**を置く。すべての見本を両方の向き・両テーマ・最小幅で開き、溢れと axe を見る。関門ではなく下の保証の抜けの検出器で、見つけたものは上の表へ返す。

### 7. 予算

PR ごとの上限を検査にする: ブラウザを使わないテストは全パッケージで 60 秒、レイアウトの検査は 60 秒、旅は分けた 1 つあたり本体 60 秒。超えたら分割せず、下へ移すか、何も守っていないものを消す。

## 経緯

- 2026-11-17 に数えた。ストーリー 717 個を 3 通りで実ブラウザに描いて 1,731 テスト、393 秒。約 170 個がロケールか幅を固定してプレビューとして働かず、約 220 個が操作と確かめを持ち、寸法や位置を読むのは 26 か所だった。
- デザインシステムの単体テストは DOM を持たず、11 ファイルがクラス名を比べていた。レイアウトは部品ごとに散らばり、mycroblog を知る合成も持っていた。
- 旅 160 のうち本物のサーバーが要るのは 56 で、74 は画面のふるまいと応答の扱い、30 はレイアウトとブラウザの API だった。
- 物理方向の検査は PR の関門に入っていなかった。下の保証が立たないので、すべてを描き直すテストが不具合を見つけ続けていた。
- 2026-11-17 に試した。happy-dom ではダイアログのフォーカス、Escape、スイッチが確かめられ、React Aria のメニューの矢印キーでのフォーカスの移動だけが動かなかった。jsdom ではそれも動いた。メニューを閉じたあとフォーカスが戻ることはどちらでも確かめられず、戻す処理が退場のアニメーションのあとに走る作りが原因かは要検証である。

## 採らなかった案

- **全ストーリーを分割して速くする**: 何も移さずに済む。保証は立たないままで、部品が増えるだけ増える。
- **DOM のシミュレーションをすべて jsdom にする**: 環境が 1 つで済む。軽い方で決まるテストまで重い方で回すことになる。
- **確かめをストーリーに残して DOM のシミュレーションで回す**: 状態と確かめが 1 か所になる。固定する理由が残り、見本がまたテストの入れ物になる。
- **ストーリー用のランナーのブラウザモードを残す**: 既に動く。ブラウザを動かすランナーが 2 つになる。
- **合成ごとにレイアウトの検査を書く**: デザインシステムを組み替えずに済む。検査が合成の数に比例する。
- **旅をすべて偽の API で回す**: 速く安定する。旅が見つけるべき食い違いを見なくなる。

## 見直す条件

- §6 の表のどの層にも返せない不具合が繰り返す。
- レイアウトの部品の集合が増え続ける。
- 掃引が見つけ続ける。半年見つけなければ外す。
- DOM のシミュレーションが操作の部品の土台の更新で契約を確かめられなくなる。
