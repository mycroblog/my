# ADR-0171: Web クライアントのテスト設計: 各性質は検証できる最下層で 1 回だけ検証する

- Status: Proposed
- Date: 2026-11-17
- Deciders: @rosylilly
- Issue: #3161

## Decision（決定）

検査の配置の原則（ADR-0079 §18）を Web クライアントの各パッケージ（ADR-0025 §3）に適用する。目的はテストの削減ではない。性質ごとに検証を担当する層を 1 つに決め、不具合が出たときにテストを追加する層を決めることである。

### 1. 原則

- **1 つの性質は、検証できる最下層で 1 回だけ検証する。** 上位の層は同じ性質を再検証しない。再検証が必要になるのは下位の層の検証が不足しているときで、修正するのは下位の層である。
- **テストの種類は、検証する対象で決まる。** コストの低い種類で検証できるものを、高い種類で検証しない。

  | 種類 | 検証できること |
  | --- | --- |
  | 静的解析（型、lint、トークンと文言のチェック） | 禁止する書き方、値の組み合わせの性質、層をまたぐ import |
  | ユニットテスト（DOM なし） | 入力から出力が決まるロジック |
  | コンポーネントテスト（DOM のシミュレーション） | ロール、アクセシブルネーム、`aria-*` の状態、キーボード操作の結果、フォーカスの移動先 |
  | レイアウトテスト（実ブラウザ） | はみ出し、折り返し、RTL での左右反転、オーバーレイの位置、フォントの適用 |
  | E2E テスト（実サーバー） | クライアントとサーバーの不整合、複数の画面やプロセスにまたがるフロー |

- **テストは契約を検証する。** アサーションの対象は、利用者・支援技術・上位の層が依存する振る舞いに限る。クラス名、マークアップの文字列、内部状態は対象にしない。
- 見た目の良し悪しはテストの対象にせず、人と評価役がストーリーを見て判断する（ADR-0169 §2）。

### 2. パッケージごとの責務

| パッケージ | 検証する性質 | 種類 |
| --- | --- | --- |
| design-tokens | 色の組み合わせのコントラスト（両テーマ）、トークンの定義漏れ | 静的解析 |
| design-system | 物理方向のプロパティを使わない、色はトークンだけを使う、レイアウトを記述するのはレイアウト用の部品だけ（§3） | 静的解析 |
| design-system | 操作できる部品のロール、アクセシブルネーム、状態、キーボード操作、フォーカス | コンポーネントテスト |
| design-system | レイアウト用の部品が、最小幅、各ブレークポイントの前後、長い文言、RTL、オーバーレイで崩れない | レイアウトテスト |
| app-components・app-features・app | props に対する出力、機能内の操作、ルートごとの画面と状態、画面遷移後のフォーカス | コンポーネントテスト（API のフェイク、§5） |
| app-data・platform | キャッシュ、再送、ストリームのマージ、エラー処理、ブラウザ API のラッパーの契約 | ユニットテスト |
| i18n・ビルド成果物 | キーの対応、同梱するライセンス文書、エントリごとのバンドルの内容 | 静的解析 |
| e2e | クライアントとサーバーの不整合（§5） | E2E テスト |

画面を RTL、ダークテーマ、画面幅ごとに描画して検証することはしない。書字方向は lint とレイアウト用の部品、色はトークン、画面幅はレイアウト用の部品が保証し、画面はそれらの組み合わせである。計算済みスタイルが必要な axe のルールは、デザインシステムのストーリーを対象にしたレイアウトテストだけが実行する。

### 3. デザインシステムの構造

次の構造にしないと、描画しなければ検証できない箇所が部品の数だけ増える。

- **レイアウトを記述できる部品を限定する。** 配置、寸法、余白、overflow、ブレークポイント、コンテナクエリを記述できるのは、子要素を配置するだけの部品とし、lint で強制する。他の部品はそれらを組み合わせる。ビューポートのブレークポイントを使うのはページのフレームだけである（ADR-0025 §4）。
- **mycroblog 固有の複合コンポーネントを置かない。** レイアウトを記述しなくなった複合コンポーネントは `app-` のパッケージへ移す（ADR-0025 §3）。
- **書字方向で分岐する処理は 1 か所にまとめ**、ユニットテストで検証する。
- **アクセシビリティ上の状態をアニメーションに依存させない。** フォーカスの移動、開閉状態、読み上げを、アニメーションの完了を待って行わない。
- **操作しないと到達できない状態は、props で描画できる**ように部品を作る。

### 4. ストーリーはカタログであり、テストではない

- 1 つのストーリーは、1 つの部品または画面の 1 つの状態を表し、props だけで決まる。ロケール、テーマ、ビューポートを固定せず、`play` 関数とアサーションを持たない。これらを切り替えるのはカタログのツールバーだけである。
- 作るのは、人か評価役が見て判断する状態だけである。ロケール・画面幅・テーマの組み合わせごとに作らない。テストはストーリーを入力として利用してよい。
- ストーリーを実行するテストランナーは持たない。ブラウザを使わないテストのランナーは 1 つ（ADR-0025 §10）、ブラウザを使うテストのランナーも E2E テストのもの 1 つとし、レイアウトテストはビルドしたカタログをそれで開く。
- DOM のシミュレーションには軽量な実装（happy-dom）を使う。それで検証できないテストだけ、検証できる実装（jsdom）で実行する。現時点で該当するのは、React Aria の部品のキーボード操作によるフォーカス移動である。

### 5. E2E テストと API のフェイク

- E2E テストにするのは、実サーバーがないと検証できず、かつ画面またはプロセスの境界をまたぐフローだけである: 認証と同意、書き込みがリロード後も残ること、複数ユーザーにまたがるフロー、ストリーミング、サーバー側のメディア処理、オフライン、Web Push。1 画面の振る舞い、レスポンスの処理、レイアウト、サーバーの振る舞い、ビルド成果物は、§2 の担当が検証する。
- API のフェイクは 1 つにし、API 仕様から型を生成し、シナリオ（ADR-0015 §5）のデータを返す。実サーバーとの差異は、API 仕様との適合テストと E2E テストが検出する。
- PR では各テストを 1 回実行し、失敗したテストだけ再実行する。同じサーバーに対して 2 回ずつ、再実行なしで実行するのは遅い検査（ADR-0079 §8）である。

### 6. 不具合が見つかったときにテストを追加する層

上位の層（E2E テスト、全ストーリーの一括チェック、手動確認、利用者の報告）で不具合が見つかった場合、**検出した層にテストを追加しない。** 検証が不足していた層に、その不具合を再現する最小のチェックまたはテストを追加してから修正する。

| 不具合 | 追加する層 |
| --- | --- |
| 物理方向のプロパティ、トークン外の色、レイアウト用の部品以外でのレイアウト、層をまたぐ import | lint |
| コントラスト不足 | トークンの組み合わせのチェック |
| ロール、アクセシブルネーム、状態、キーボード操作、フォーカス | その部品のコンポーネントテスト |
| はみ出し、折り返し、左右反転、オーバーレイ | 原因となったレイアウト用の部品のレイアウトテスト。原因が複合コンポーネントなら §3 の違反として修正する |
| キャッシュ、再送、並び順 | app-data のユニットテスト |
| 画面の状態、ルーティング、画面遷移後のフォーカス | app のコンポーネントテスト |
| クライアントとサーバーの不整合 | API のフェイクと API 仕様との適合テスト。該当するフローがなければ E2E テスト |

- 同じ層で繰り返す不具合は、テストではなく lint などの自動チェックにする（ADR-0170 §6）。
- 遅い検査で**全ストーリーの一括チェック**を実行する。すべてのストーリーを、両方の書字方向、両テーマ、最小幅で開き、はみ出しと axe を確認する。マージの条件にはせず、下位の層の検証漏れを検出するために使う。検出した不具合は上の表に従って扱う。

### 7. 実行時間の上限

PR ごとの実行時間に上限を設け、超過を CI で検出する: ブラウザを使わないテストは全パッケージ合計で 60 秒、レイアウトテストは 60 秒、E2E テストは分割した 1 ジョブあたりテスト本体 60 秒。超過したら並列化で対処せず、下位の層へ移すか、何も検証していないテストを削除する。

## 経緯

- 2026-11-17 に計測した。717 個のストーリーを 3 通りの設定で実ブラウザに描画し、1,731 テスト、393 秒かかっていた。約 170 個がロケールか画面幅を固定していてプレビューとして機能せず、約 220 個が `play` 関数を持ち、寸法や位置を参照するアサーションは 26 か所だった。
- デザインシステムのユニットテストは DOM を使わず、11 ファイルがクラス名を比較していた。レイアウトの記述は部品ごとに分散し、mycroblog 固有の複合コンポーネントも含んでいた。
- E2E テスト 160 件のうち実サーバーが必要なのは 56 件で、74 件は 1 画面の振る舞いとレスポンスの処理、30 件はレイアウトとブラウザ API を検証していた。
- 物理方向のチェックは PR の CI で実行されていなかった。下位の層の検証が機能していないため、すべてを描画し直すテストが不具合を検出し続けていた。
- 2026-11-17 に検証した。happy-dom ではダイアログのフォーカス、Escape、スイッチを検証でき、React Aria のメニューの矢印キーによるフォーカス移動だけが動作しなかった。jsdom ではこれも動作した。メニューを閉じたあとのフォーカスの復帰はどちらでも検証できず、復帰の処理が退場アニメーションの完了後に実行される実装が原因かどうかは要検証である。

## 採らなかった案

- **全ストーリーのテストを分割して高速化する**: 移行が不要である。下位の層の検証は不足したままで、部品が増えるほど実行時間が増える。
- **DOM のシミュレーションをすべて jsdom にする**: 実行環境が 1 つで済む。軽量な実装で検証できるテストまで重い実装で実行することになる。
- **アサーションをストーリーに残し、DOM のシミュレーションで実行する**: 状態とアサーションを 1 か所で管理できる。設定を固定する理由が残り、ストーリーが再びテストの置き場になる。
- **Storybook 用テストランナーのブラウザモードを残す**: すでに動作している。ブラウザを使うランナーが 2 つになる。
- **複合コンポーネントごとにレイアウトテストを書く**: デザインシステムの再構成が不要である。テストの数が複合コンポーネントの数に比例する。
- **E2E テストをすべて API のフェイクで実行する**: 高速で安定する。E2E テストが検出すべき不整合を検出できなくなる。

## 見直す条件

- §6 の表のどの層でも対処できない不具合が繰り返し発生する。
- レイアウト用の部品が増え続ける。
- 全ストーリーの一括チェックが不具合を検出し続ける。半年間検出しなければ廃止する。
- DOM のシミュレーションが、部品の基盤ライブラリの更新によって契約を検証できなくなる。
