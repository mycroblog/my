# ADR-0153: テストの責務の境界とパッケージの分割

- Status: Accepted
- Date: 2026-11-07
- Deciders: @rosylilly
- Issue: #2454, #2463, #2477

## Decision（決定）

Go のテストを「何を確かめるか」で 3 つの層に分け、層ごとに置き場所と依存を決める。そのうえで、DB の集約点をモジュール（`internal/app/<module>`）ごとに分け、Go のテスト結果のキャッシュ（ADR-0079 §7）が変更の影響範囲のテストだけを走らせるようにする。

### 1. テストの 3 つの層

| 層 | 確かめること | 置き場所 | 依存するもの |
| --- | --- | --- | --- |
| ポートの契約 | 1 つのポートの、1 つのアダプタの実装（SQL・ドライバ・外部サービスの扱い） | アダプタのテストパッケージ。スイートはそのモジュールの契約（§3） | そのポートと、そのモジュールのドメイン |
| 業務の流れ | 複数のモジュールにまたがる振る舞い（受信の処理、アカウントの移行、消去、リモートのフォロー） | 最も多くのモジュールに依存するモジュールの `internal/app/<module>` のテスト | 各モジュールのアプリ層と、ポートのメモリの偽物（`pkg/testkit`） |
| 組み立て | 各モジュールが組み立てられ、API から届くこと | `internal/platform`・`cmd/my` | 全体 |

- 業務の流れは、アダプタごと・方言ごとに回さない。メモリの偽物の上で 1 回だけ回す。SQL が流れの前提を満たすことは、ポートの契約が確かめる。
- ポートの契約は、1 つのリポジトリのメソッドを確かめる。ほかのモジュールのサービスを組み立てない。前提のデータは、そのモジュールのリポジトリか、テスト用の最小の挿入で作る。
- 組み立ての層のテストは、配線の確認に限る（各モジュールの代表の操作が API から通る、設定の読み込み、起動と停止）。機能ごとの振る舞いは、業務の流れの層か `internal/interface/*` のテスト（偽物のポート）に置く。

### 2. 速さの目安

- ポートの契約と業務の流れは、パッケージごとに Merge Queue の最長のジョブより十分に短くする。
- 組み立ての層は全体に依存するので、どの変更でも走る。そのため、`cmd/my` と `internal/platform` のテストは合わせて 1 分以内に保つ。

### 3. DB の集約点をモジュールで分ける

- **sqlc の生成物**: `sqlc.yaml` の `sql` の項目をモジュールごとに分け、出力をモジュールごとのパッケージ（`internal/adapter/db/<dialect>/<module>gen`）にする。各パッケージは、自分のテーブルの `models.go` だけを持つ。
- **スキーマの埋め込み**: `schema` は、モジュールごとの desired-state のファイル（ADR-0023）を、モジュールごとに引ける形で埋め込む。テストは、そのモジュールと、そのモジュールが依存するモジュールのスキーマだけを当てる。本番の適用（Atlas）は、今までどおり全部を当てる。
- **DB アダプタ**: `internal/adapter/db/<dialect>` を、共通の部分（接続、トランザクション、再試行）と、モジュールごとのサブパッケージ（`internal/adapter/db/<dialect>/<module>`）に分ける。サブパッケージは、モジュールの DAG に沿って、依存するモジュールのサブパッケージだけを import する。下位のモジュールが上位のモジュールの補助関数を使うときは、その関数を共通の部分に移す。
- **契約スイート**: `pkg/testkit` の契約を、モジュールごとのパッケージ（`pkg/testkit/<module>test`）に分ける。時計・ID・偽物のポートのような共有の部品は `pkg/testkit` に残す。
- モジュールをまたぐ関心事（アカウントの消去、投稿の公開範囲の変更、決済）は、関わるモジュールのうち最も多くに依存するモジュールの置き場に入れる。決まらないものは、ADR-0002 の依存の向きに従って置き場を決める。

### 4. 順序

1. 業務の流れのテストを、アダプタの契約から `internal/app/<module>` に移す（§1）。効果が最も大きく、パッケージの構成を変えずにできる。
2. 組み立ての層のテストを、配線の確認に絞る（§1）。
3. DB の集約点を分ける（§3）。
4. main でテスト結果のキャッシュを作る（ADR-0079 §7、#2462）。

### 5. 覆す条件

- 業務の流れを偽物の上に移したことで、本物の DB でしか起きない不具合（トランザクションの境界、制約の違反の順序）が main に入るなら、流れのうち代表のものを、ポートの契約の層に「方言ごとの統合」として残す。
- §3 の分割で、モジュールの数の 2 倍（方言の数）のパッケージを保つ手間が、テストの時間の節約より大きいなら、§3 を sqlc の生成物と契約スイートの分割だけにする。

## 経緯

発端は #2119（`cmd/my` のテストが 600 秒の上限に迫る）で、CI 全体を見直した（#2463）。Merge Queue の `go test ./...` が、どの変更でも重いテストをほぼ全部走らせていることが分かった。テスト結果のキャッシュは効いておらず、効かせても、Go に触れた PR の 98% で重いパッケージが走る。

スパイク #2454 で、型情報からファイル単位の依存グラフを作り、直近にマージされた 150 PR を、仮のパッケージ構成で再生した。

- 今の構成では、1 つの PR が全テスト時間の中央値 99% を走らせる。DB の集約点をモジュールで分けても、中央値は 75〜84% までしか下がらなかった。
- 理由は、テストの中身にある。全テスト時間 1,198 秒のうち、`internal/app` と `internal/domain` のテストは 2 秒だった。`pkg/testkit` の 164 の契約のうち 97 は、3 つ以上のモジュールのサービスを組み立てて業務の流れを回し、sqlite のアダプタのテスト時間の 73%、postgres の 56% を使っていた。流れのテストは、通るモジュールのどれが変わっても走るので、置き場所を変えても走る回数は減らない。
- `internal/platform` のテスト（182 ファイル）は `platform.New` でアプリ全体を組み立てるので、モジュールで分けても効果がなかった。

モジュールの依存（`internal/app/*`）には循環がなく、`kernel`・`uow`・`queue` を土台にした DAG になっている。問題はモジュールの構造ではなく、テストの層の取り違えと集約点にある。

決定者は、3 つの層に分けたうえで DB の集約点を分け、テスト結果のキャッシュを最後に作る形を採った（#2477）。テストの書き直しだけ、またはパッケージの分割だけを先に行う形は採らなかった。

## 採らなかった案

- パッケージの分割だけを行う（§3 だけ）: テストを書き直さずに済むが、試算では中央値が 99% から 75% になるだけで、流れのテストが毎回走り続ける。
- テスト結果のキャッシュだけを入れる: 一番安いが、98% の PR で重いテストが走り、時間が縮まない。
- 業務の流れを、本物の DB の上で 1 方言だけ回す: 偽物を作らずに済むが、アダプタに依存するので、DB の集約点の変更のたびに走る。偽物はすでにほとんどある。
- 流れのテストを nightly に移す: Merge Queue は速くなるが、業務の退行を main に入れてから見つけることになる。

## Consequences（影響）

- 良い影響:
  - 業務の流れのテストが、DB を開かないぶん速くなり、方言の数だけ繰り返さなくなる。
  - 1 つのモジュールを変えた PR では、そのモジュールと、それに依存するモジュールのテストと、組み立ての層の薄いテストだけが走る。
  - 何を確かめるテストかが、置き場所から分かる。
- 悪い影響・トレードオフ:
  - 97 の流れのテストの移動と、ポートの契約の書き直しが要る。大きな作業で、マイルストーンを分ける。
  - 偽物のポートの振る舞いを、ポートの契約で本物と揃え続ける必要がある（偽物も契約を通す）。
  - DB アダプタのパッケージが、モジュールの数だけ増える。
- 後続の作業（Refactoring CI のマイルストーンに issue を起こす）: §4 の各段階。

## Open Questions / 要検証

- sqlc がモジュールごとの出力で、他のモジュールのテーブルを参照するクエリ（JOIN）をどう扱うか。依存するモジュールのスキーマを `schema` に並べれば型を生成できるが、生成される構造体の重複を確かめる。
- 偽物のポートがすでに契約を通しているか（`pkg/testkit` の偽物の契約テストの範囲）。
