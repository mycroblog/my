# ADR-0141: Web クライアントの更新は既定で割り込まず、動かなくなるときだけ促す

- Status: Proposed
- Date: 2026-11-03
- Deciders: @rosylilly
- Issue: #2021

## Context（背景・課題）

[ADR-0028](0028-html-shell-link-previews-and-pwa.md) は、更新を「新しい版があります」と通知し、利用者の操作で反映すると決めている（下書き中の自動リロードを避けるため）。
デプロイの多いインスタンスでは、アセットのどんな小さな変更でもこのトーストが出て、使うか閉じるまで残る。版の文字列だけが理由の更新は #2020 が取り除くので、この ADR は Web の実際の変更を扱う。

`v0.1.0` はメンテナが運用を始める版で、運営者がどのホスティングを選んでも動く必要がある（#2027）。CDN の有無、ローリングの入れ替え、古いアセットの保持を前提にできない。

### Service Worker の動き（2026-11-03 に確認）

- 新しい worker は裏でインストールし、古い worker を使うページがなくなるまで待つ。読み直しでは入れ替わらない
  （[web.dev: The service worker lifecycle](https://web.dev/articles/service-worker-lifecycle)、[MDN: Using Service Workers](https://developer.mozilla.org/en-US/docs/Web/API/Service_Worker_API/Using_Service_Workers)）。
- `skipWaiting()` は待っている worker を有効にする。web.dev は、古い版で読み込んだページを新しい worker が制御することになるので、壊れるなら使わないよう警告している。
  `clients.claim()` はスコープ内のすべてのクライアントを制御し、それぞれで `controllerchange` が発火する（[MDN](https://developer.mozilla.org/en-US/docs/Web/API/Clients/claim)）。
- Workbox の precache は、インストールで新しいか revision の変わったものだけを取得し、activate でマニフェストにないものを消す（[workbox-precaching](https://developer.chrome.com/docs/workbox/modules/workbox-precaching)）。
- `beforeunload` は特にモバイルで確実には発火せず、ダイアログには利用者の操作の履歴（sticky activation）が要る（[MDN](https://developer.mozilla.org/en-US/docs/Web/API/Window/beforeunload_event)）。
- 隠れたタブはブラウザの判断で凍結・破棄され、凍結の間はタイマーも fetch のコールバックも動かない（[Page Lifecycle API](https://developer.chrome.com/docs/web-platform/page-lifecycle-api)）。

### 今のコードから分かること（`113e19b9a`）

1. **読み直しは worker に関係なく新しい JS を動かす。** ページ遷移はネットワーク優先（`sw/sw.ts`）で、サーバーの外枠は新しいハッシュのチャンクを指す。
   古い worker の precache にないチャンクはネットワークへ抜ける。つまりオンラインの読み直しや起動は、トーストと無関係にすでに新しい版を動かしている。古い版を動かすのは、開いたままのタブと、3 秒以内に外枠を得られないときだけである。
2. **読み直した後もトーストが出る。** `registerServiceWorker` は `registration.waiting` があれば通知するので、すでに新しい JS で動くページに「新しい版があります」と出す。押すともう一度読み直す。
3. **別のタブの更新ボタンが効かなくなる。** タブ A の Update で `SKIP_WAITING` を送ると、タブ B は古い JS のまま新しい worker に制御される。B に残ったトーストの `apply` は、すでに有効な worker にメッセージを送って `controllerchange` を待つので、押しても何も起きない。
4. **`skipWaiting` は他のタブのチャンクを消す。** activate で古いチャンクが precache から消え、サーバーの `my serve` も今のビルドしか持たない。B の遅延読み込みは失敗し、`reloadOnPreloadError` が B を読み直す。通話中でも読み直そうとする。
5. **更新の量。** precache は 247 ファイル、8.22 MB（gzip で 1.94 MB）。設定画面の 1 コンポーネントの変更で 105 ファイルの名前が変わり、新しく取得するのは 1.42 MB（gzip で 0.46 MB）だった（`web:build` の前後の比較。ハッシュは import 元へ連鎖する）。
   `my serve` はアセットを圧縮しないので、転送量が gzip の値になるかは手前のプロキシ次第である。

### 読み直しで失うもの

| 状態 | 読み直しの結果 | 今の守り | 検知の手段 |
| --- | --- | --- | --- |
| 投稿の下書き（本文・投票・公開範囲・アップロード済みの添付）、送信中の投稿 | **残る**（`draftStore` の sessionStorage。送信中は Idempotency-Key 付きで再送できる） | 不要 | 不要 |
| 下書きのアップロード前の添付 | **失う**（ファイルはメモリの中だけ） | なし | `mediaId === null` の添付、実行中のミューテーション |
| 音声通話 | **切れる**。音声の再開には操作が要る（ADR-0101 §7）。`pagehide` で退室し、ほかの人がいる部屋の主は猶予が切れるまで主のまま | `beforeunload`（モバイルでは不確実） | `useVoiceCall` の `inCall` |
| 実行中の書き込み（アップロード、インポート） | **途切れる** | なし | `QueryClient.isMutating()` |
| ガードのあるフォーム（プロフィール、自動削除、文書の設定） | **失う** | `useUnsavedChangesGuard` | `hasChanges` |
| ガードのないフォーム（通報、部屋の作成、多くの管理画面）と開いたダイアログ | **失う** | なし | `@my/ui` の `Dialog`・`Sheet` の開いた数。管理画面は検知できない |
| 入力中の文字（IME を含む） | **失う** | なし | `document.activeElement` |
| 再生中の動画・音声、タイムラインの読んでいた位置 | **失う**（ホームの先頭だけ localStorage に残る） | なし | 再生中はメディア要素。位置は取り戻せない |

## Decision Drivers（判断基準）

1. 利用者が入力したものと通話を、頼んでいない読み直しで失わない
2. 古い版が動かなくなったままにしない
3. デプロイの頻度が利用者の邪魔にならない。頻度はインスタンスごとに違う
4. ホスティングに依存しない（CDN、ローリング、古いアセットの保持を前提にしない）
5. 検知の漏れが小さな失敗で済む。新しい画面を足すたびに壊れる仕組みにしない
6. 実装と検査が小さい

## Considered Options（選択肢）

| | 内容 | 最も強い論拠 | 最悪の場合 |
| --- | --- | --- | --- |
| A | 今のまま、すべての変更でトースト | 利用者の知らない読み直しがなく、もう実装されている | デプロイのたびに残るトースト。閉じられて更新されず、押すと別のタブが壊れる |
| B | 次の起動だけで適用し、何も出さない | ブラウザの既定の動きで、失うものがない。実は Context の 1 のとおりほぼ今もそう動く | 開いたままのタブが古いまま何週間も動く。API の変更で壊れても理由が分からない |
| C | 隠れたタブや画面遷移で、安全なら黙って読み直す | 開いたままのタブも更新され、誰も何も操作しない | 検知の漏れで、書きかけが知らせなしに消える。戻ると読んでいた位置が消え、スクリーンリーダーのフォーカスも失う。読み直しは worker を入れ替えない |
| D | リリースのときと必要なときだけトースト | 大きな変更だけ知らせられる | `main` を動かす運営者には「リリース」の区別がなく、版の情報をビルドに戻す（#2020 と逆行）。リリースが多ければ A と同じ |
| E | すぐ `skipWaiting`（`autoUpdate`） | 最も単純で常に最新 | 入力中に読み直され、下書き以外を失う。他のタブのチャンクが消える |
| F（推奨） | B を既定とし、古いまま長く動くタブには遅らせたトースト、動かないときは必要な更新 | 割り込みが頻度によらず上限を持ち、黙って読み直すのは安全な画面だけ | 古いタブが最長で閾値の間（と、利用者が無視する間）古いまま動く。必要な更新の番号を上げ忘れると、今と同じ「動かないまま」になる |

## Decision（決定）

> 推奨案（Proposed）。Accepted にするのは人間の Decider のみ。

**F を推奨する。** 通知を「新しい版がある」から「古いままで困るとき」へ変える。ADR-0028 の「更新の通知と、利用者の操作での反映」の部分をこの ADR で置き換える。
ADR-0028 のそれ以外（外枠、キャッシュの規則、`vite:preloadError` の読み直しの存在）は残す。

### 1. 既定は割り込まない（問 1）

- 新しい版の発見とインストールは今のまま裏で行う。トーストは出さない。
- オンラインで開き直せば新しい JS が動き、すべてのタブを閉じれば新しい worker が有効になる。どちらもブラウザの動きで、この ADR は何も足さない。
- リリースかどうかでは分けない（D を採らない）。

### 2. worker を入れ替えてよいとき（問 4）

`skipWaiting` は読み直しを伴わず、**どのタブのチャンクも消さないと分かったとき**だけ送る。

- 各タブは起動時に、自分のビルド（入口のチャンクの URL）を名前に入れた Web Locks の共有ロック `my:build:<url>` を持ち続ける。
- ページは、待っている worker に自分の入口のチャンクを持っているかを尋ねる（同じビルドか）。持っていて、かつ `navigator.locks.query()` の `held` に他のビルドのロックがなければ、`SKIP_WAITING` を送る。読み直しはしない。
- ロックはオリジンのタブと worker にまたがる（[MDN: Web Locks API](https://developer.mozilla.org/en-US/docs/Web/API/Web_Locks_API)、[`query()`](https://developer.mozilla.org/en-US/docs/Web/API/LockManager/query) は 2022 年 3 月から主要ブラウザで利用可、2026-11-03 確認）。凍結したタブにも返事を待たずに済む。
- Web Locks がないブラウザでは送らず、すべてのタブを閉じたときの入れ替えに任せる。
- `controllerchange` で読み直すのをやめる。Update は `location.reload()` だけにする。別のタブのボタンが死ぬこと（Context の 3）も、チャンクの消失（Context の 4）も、これでなくなる。
- 同じビルドのページには、トーストを出さない（Context の 2）。

### 3. 古いまま長く動くタブ

- 待っている worker を最初に見つけた時刻を localStorage に残す（`lib/storage` に宣言する。利用者のデータではない）。worker が入れ替わったら消す。
- **7 日**待っても自分のビルドが古いタブにだけ、今のトースト（Update のアクション付き、自動では閉じない）を出す。閉じたら、そのタブでは次の読み直しまで出さない。通話中は出さず、終わってから出す。
- 7 日は、タブごとの割り込みをデプロイの頻度によらず週 1 回に抑える値である。バグ修正の届く遅れの上限でもある。

### 4. 動かなくなる版は必要な更新として扱う（問 3）

- **消えたチャンク**: `reloadOnPreloadError` はこれからも読み直す。ただし、§5 の条件を満たさなければ読み直さず、必要な更新のトーストを出す。ガードの 10 秒はそのまま残す。
- **API の変更**: ADR-0090 §8 の非推奨の期間（少なくとも 1 つのマイナー版）で通常は壊れない。壊れるのは、期間なしのセキュリティ修正と、期間より長く開いているタブである。
  - サーバーとクライアントが整数の定数 `webClientEpoch` を持つ。古いクライアントを動かせない変更を入れる PR が手で上げる。版の文字列ではないのでビルドごとには変わらない（#2020 の検査を壊さない）。
  - サーバーは API の応答のヘッダで値を返す（Web のオリジンが別のときに読めるよう、CORS で公開する）。クライアントは、**サーバーの値が自分より大きいとき**だけ必要な更新として扱う。逆（ロールバックやローリングの最中に古いサーバーへ当たった）では何もしない。
- **必要な更新の適用**: §5 を満たせば読み直す。満たさなければ、すぐに Update 付きのトーストを出し、満たしたら読み直す。通話や書き込みは切らない。読み直しはオリジンの 1 タブにつきエポックごとに 1 回で、それでも解消しなければトーストのままにする（ローリングの最中に古い外枠を受け取っても繰り返さない）。
- 読み直しは新しい JS を得るためのもので、`skipWaiting` は要らない。オフラインでは precache の古い版のまま動く。

### 5. 安全な瞬間（問 2）

黙って読み直すのは必要な更新のときだけなので、次をすべて満たす必要がある。1 か所（`lib/pwa` の周辺）の関数にまとめ、機能がそれぞれの状態を登録する。

1. 今の画面のルートが `staticData` で読み直してよいと宣言している（ホーム、タイムライン、通知、プロフィール、投稿など読むための画面）。**宣言のない画面は安全でない**ので、管理画面やこれから足す画面は検知の漏れがあっても失わない
2. 通話していない
3. `QueryClient.isMutating()` が 0 で、下書きにアップロード前の添付がない
4. `Dialog`・`Sheet` が開いていない
5. 編集できる要素にフォーカスがない
6. 再生中のメディアがない

下書きの本文は条件に入れない。sessionStorage で残るので、ここで止めると下書きを持つ人が更新できないままになる。

### 6. 別の版どうしの組み合わせ

新しいページと古い worker の組み合わせは、すでに読み直しのたびに起きている（Context の 1）。`sw-protocol` のメッセージとプッシュの内容は、前後の版で理解できるものだけを変える。知らないメッセージは無視する（`isMessage` の今の動き）。

### 7. 費用（問 5）

このどの選択肢でも、インストールの費用は変わらない。発見すれば取得するからである。#2020 で版の文字列だけの更新が消えれば、利用者が払うのは Web の変更があったときだけで、1 回あたり 0.5〜2 MB（gzip、Context の 5）である。precache の範囲は変えない。

### 覆す条件

- 7 日のトーストでも古いタブのバグ報告が多いなら、閾値を縮めるか、読むための画面に限って C を足す。
- 必要な更新が 1 年に何度も起きるなら、ADR-0090 §8 の側を見直す。
- 利用者の転送量が問題になれば、precache を FR-604 のオフラインに要る範囲へ絞る別の ADR を書く。

## Consequences（影響）

- 良い影響
  - デプロイの頻度と割り込みが切り離され、タブごとに週 1 回が上限になる
  - 読み直しの判断の誤りが効くのは必要な更新のときだけで、まれである。新しい画面は既定で安全でない側に倒れる
  - タブが別の版でも互いのチャンクを消さない
  - どのホスティングでも同じに動く。サーバーに要るのは定数のヘッダだけである
- 悪い影響・トレードオフ
  - 開いたままのタブは最長 7 日、利用者が閉じ続ければそれ以上古い。バグ修正は読み直すまで届かない
  - タブを常に 2 つ以上開く人で、古いタブが残る間は worker が古いまま。オフラインの外枠とプッシュの処理が遅れて更新される（§6 が前提）
  - `webClientEpoch` は人が上げる。上げ忘れると今と同じで、API の失敗が読み直すまで続く
  - 必要な更新の読み直しでは、読むための画面の読んでいた位置を失う
  - ルートごとの宣言が増える
  - 「新しい版があります」をほとんど見なくなるので、変更を知らせる手段にはならない。リリースノートやお知らせが受け持つ
- 後続で必要になる作業（Accepted のあとに Issue にする）
  - `lib/pwa.ts`・`UpdatePrompt.tsx`・`sw/sw.ts`・`sw-protocol`: ロック、ビルドの確認、遅らせたトースト、必要な更新
  - `webClientEpoch`: サーバーのヘッダと CORS、クライアントの定数と確認、上げる場面の `docs/agents/` への追記
  - ルートの宣言と安全の判定、`reloadOnPreloadError` の条件付け
  - E2E: 2 タブの更新、同じビルドで何も出ないこと、通話中に読み直さないこと
  - `locales/` の必要な更新の文言、`docs/architecture/web-client/11-pwa.md` の「更新」の記述
  - この ADR を Accepted にする PR で、ADR-0028 の Status に「更新の通知の部分を ADR-0141 が置き換える」と書く

## Pros and Cons of the Options（詳細比較・任意）

- **A を残す理由はある**: 版がいつ変わったかが利用者に見え、読み直しは頼んだときだけである。ただし Context の 1 のとおり、起動はトーストなしで更新されているので、「利用者の操作で反映する」という約束は開いたままのタブにしか効いていない。
- **C は問 1 の素直な答えだが、「全ページ遷移」は worker を入れ替えない**（読み直しと同じ）。SPA には全ページ遷移もほとんどない。隠れたタブでの読み直しは、タイムラインの読む位置を失うのが最大の費用で、これは検知の精度では解決しない。そのため C は必要な更新にだけ使う。
- **D は「大きな変更だけ知らせたい」に応えるが**、知らせたいのは機能で、更新の仕組みの役割ではない。

## Open Questions / 要検証

- Web Locks のロックは、タブが閉じたり破棄されたりすると解放される想定である（MDN の該当ページには明記がない。実機のブラウザで確かめる）。解放されない場合の影響は、worker の入れ替えが遅れるだけである。
- 7 日の閾値は実運用の感覚で決める数字で、rc で確かめられない。`v0.1.0` の運用で見直す。
