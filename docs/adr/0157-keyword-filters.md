# ADR-0157: キーワードフィルタ: 語の照合と、フィルタを当てる読み取りの経路

- Status: Accepted
- Date: 2026-11-09
- Deciders: @rosylilly
- Issue: #2561

## Decision（決定）

どの節も決定者が決めたことである。

### 1. 対象のリリース

キーワードフィルタ（FR-209）は優先度 S で、`v0.1.0` に入れる。

### 2. 判定するのはサーバー

- 照合はサーバーが行い、Web・`pkg/mykit`・`pkg/mybot` は同じ結果を受け取る。クライアントは照合しない。
- 動作が「隠す」（`hide`）のフィルタに一致した投稿は、`canView` で見えない投稿と同じく、サーバーがページから除く。
- 動作が「警告」（`warn`）のフィルタに一致した投稿は、`Status` に印 `filtered` を付けて返し、クライアントが畳む（一致したフィルタの名前と「表示する」のボタンを出す）。

### 3. 照合する文字列

本文・内容の警告（CW）・投票の選択肢・添付の代替テキストを照らす。CW の後ろに畳まれた本文も照らす。

- 本文は HTML の文字のノードだけを使う（リンクの `href` などの属性は使わない。メンション・ハッシュタグ・`:shortcode:` は見えている文字として入る）。`contentMap` の本文はすべての言語の本文を照らす。
- 欄ごとに別々に照らし、語が 2 つの欄をまたいで一致することはない。
- ブーストは元の投稿の文字列を照らし、印と除外はブーストの行に効く。
- 引用（ADR-0069）は、引用した投稿と引用された投稿を別々に照らす。引用された投稿だけが一致したときは、引用の部分だけに印を付けて畳み、`hide` でも引用した投稿は除かない（他人の引用のせいで投稿ごと消えると、何が起きたか分からない）。

### 4. 正規化

- 語と照らす文字列の両方を、NFKC → 小文字（Unicode の単純な小文字化、Go の `strings.ToLower`）→ カタカナをひらがな（U+30A1〜U+30F6 を U+3041〜U+3096 に、U+30FD・U+30FE を U+309D・U+309E に）→ 連続する空白（改行を含む）を 1 つの空白、の順にそろえる。
  Web の絵文字の検索（web-client §12、ADR-0091）と同じそろえ方で、NFKC が半角のカタカナを全角にするので、半角・全角・大文字小文字・カタカナとひらがなの揺れが 1 つになる。
- 関数は `internal/domain/timeline` に 1 つ置き、語を保存するとき（正規化した形も保存する）と照らすときに同じものを使う。

### 5. 部分一致と「単語全体」

- 既定は部分一致。語ごとに「単語全体だけ」（`whole_word`）を選べる。
- 「単語全体だけ」は、一致の前後の文字が単語の文字でないときだけ一致とする。単語の文字は Unicode の文字・数字・結合文字と `_` で、ただし語を空白で区切らない用字（漢字・ひらがな・カタカナ・タイ文字・ラーオ文字・クメール文字・ミャンマー文字など）の文字は単語の文字に数えない。
  つまり日本語・中国語・タイ語では「単語全体だけ」を選んでも部分一致と同じに働く。
  設定の画面の説明は短い一文にとどめ、くどくしない。用字ごとの働きや例はドキュメンテーションサイトの利用者向けのマニュアル（`docs/guide/`）に書き、画面からはそこへ案内する。
- 正規表現は使えない。1 つのフィルタの語どうしは「どれか」（OR）で、「すべて」（AND）は持たない。空白を含む語は、その並びの句として照らす。

### 6. 文脈・動作・期限

- 文脈（複数選ぶ）:
  - `home`: ホームとリスト（FR-201・FR-211）
  - `notifications`: 通知の一覧、ストリームの通知、Web Push とメールの通知（FR-205・FR-206・FR-210）
  - `public`: ローカル・連合・ハッシュタグのタイムライン（FR-202・FR-203）とその公開のストリーム
  - `thread`: スレッド（投稿の前後、FR-106）
  - `account`: プロフィールのタイムラインとピン留め（FR-204）
- 動作は `warn`（畳む）と `hide`（除く）の 2 つ。1 つの投稿が複数のフィルタに一致したら、1 つでも `hide` があれば除き、なければ一致した `warn` のフィルタをすべて `filtered` に並べる。
- 期限（`expires_at`）は省略できる。期限を過ぎたフィルタは照合に使わないが消さず、一覧で期限切れと示し、期限を延ばせば再び効く。
- 当てないところ: 投稿の全文検索（FR-309。利用者が自分で探している）、ブックマーク・お気に入りの一覧、モデレーションと管理の画面（通報の中身を見る必要がある）、webhook、ActivityPub（フィルタは閲覧者ひとりの表示の設定で、連合しない）、ログインしていない閲覧者（フィルタを持たない）。
- 利用者が直接開いた投稿（`GET /api/v1/statuses/{id}` とスレッドの中心の投稿）は、`thread` の `hide` に一致しても除かず `warn` と同じに畳む。リンクを開いて何も出ないと、壊れたリンクと区別できない。前後の投稿は §2 のとおり除く。

### 7. 当てる場所: `canView` の後、ページを描くために読んだ文字列に

- 照合は Go で、`canView`（とミュート）を再適用して残った行について、ページの `Status` を作るために `content` から読んだ文字列（`StatusView` の版の本文・CW・投票・添付）に対して行う。照合のために別の読み取りはしない。
- 照合の結果は保存しない（投影を作らない）。フィルタを足す・変える・消すと、過去の投稿にもすぐ効き、投稿の編集にもそのまま追いつく。
- ページングは `canView` で除いた行と同じに扱う。次のページのカーソルは除いた行も含めて読んだ最後の行で、ページが `limit` 件より少なく、0 件になることもある（data-model §6）。
- ストリーム（FR-207、ADR-0013 §17〜§20）は、購読ごとの判定の後、送る前に照合する。`hide` は送らず、`warn` は印を付けて送る。
- 通知は、投稿を持つ通知の投稿を照らし、`hide` の通知は一覧・ストリーム・Web Push・メールから除く。`warn` の通知は一覧とストリームで印を付け、Web Push とメールでは本文を出さずにフィルタの名前だけを出す。
- 通知の未読の数（`notifications_marker`）は `hide` で除いた通知を数えない。`notification` は数えるときにも `timeline` の照合のユースケース（§8）を呼んで照らす。一覧に出ない通知が未読として残ると、消せない未読になるからである。
- 閲覧者自身の投稿は照らさない。閲覧者がブーストした行（ブーストした人が閲覧者）も照らさない。自分で書いた・選んだものを自分から隠す理由がない（Misskey も自分のノートは照らさない）。
- 1 回の照合は、閲覧者のすべての有効な語を 1 度に照らす（例えば Aho-Corasick のように、文字列を 1 度なめれば全部の語が分かる形）。照合器はリクエストごとに作るか、フィルタの更新で捨てるプロセス内のキャッシュに置く（作り方は実装の Issue で決める）。

### 8. 持ち主のモジュール: `timeline`

- `timeline` がフィルタの表を持ち、書くのも読むのも `timeline` だけにする。照合の関数（§4・§5）は `internal/domain/timeline`、照合を当てるユースケースは `internal/app/timeline` に置き、ホーム・リスト・公開・プロフィール・スレッド・通知（未読の数を含む）・ストリームの経路が同じ関数を呼ぶ。
- 理由: 当てる場所の大半はすでに `timeline` が組み立てるタイムラインで、`canView` の再適用（`Facts`）と同じ段階に置ける。言語のフィルタ（FR-208）のように持ち主を `identity` にすると、読み取りのたびに呼び出し側が語の一覧を運ぶことになり、語は言語の一覧より多い。
- 表（細部は data-model §4.6 に書く。ADR-0020 の分類）:
  - `keyword_filters`（リソース）: 持ち主のアカウントと作った時刻
  - フィルタの名前・動作・期限（現在値）: 名前は書記素で 1〜50。期限は「この時刻まで効く」という値で、状態を表す日時ではない（`feed_exclusions` の `expires_at` と同じ）
  - `keyword_filter_contexts`（現在値）: （フィルタ、文脈）。JSON にしない
  - `keyword_filter_words`（現在値）: （フィルタ、語）。入力した語・正規化した語・`whole_word`。一意は（フィルタ、正規化した語）
- 持ち主のアカウントの消去（data-model §8）でフィルタも消える。フィルタはデータのエクスポート（FR-008）に入れる。

### 9. 上限

- 1 人あたり 100 フィルタ、1 フィルタあたり 100 語、1 人のすべてのフィルタで合わせて 1,000 語、1 語は正規化した後の書記素で 1〜100。超える作成・追加は `422`。値は定数で、設定にしない。
- 合わせての上限は照合の費用から決めた。1 ページは 40 件ほどで、本文が長い投稿でも数 KB なので、1,000 語なら §7 の 1 度なめる照合で 1 ページあたり数ミリ秒に収まる。100 × 100 の 10,000 語をそのまま許すと、照合器の大きさと作る時間が 10 倍になり、安いインスタンス（NFR-COST-2）で読み取りの遅れになる。

### 10. API と画面

- クライアント API: フィルタの一覧・作成・変更・削除（語と文脈を含む）。持ち主のトークンでだけ返し、ほかの利用者には存在も含めて返さない（`404`）。`pkg/mykit` にも入れる（ADR-0093）。
- `Status` に `filtered` を足す。一致した `warn` のフィルタごとに `{filter: {id, title}, keyword_matches: [入力した語]}` を並べ、一致しなければ空の配列。引用（§3）は引用された投稿の `Status` に付く。
- Web: 設定にフィルタの一覧と編集の画面を置き、畳んだ投稿は「フィルタ「名前」に一致」と「表示する」のボタンで出す。フィルタを保存したら、開いているタイムラインを読み直す（クライアントは照合しないので、読み直すまで今の表示のまま）。画面の要件は `docs/architecture/web-client/screens/` に書いてから作る。

### 11. 見直す条件

- 正規表現や AND を求める声が強いとき（RE2 の Go の `regexp` なら線形時間で照らせるが、照合器を 1 つにまとめられなくなる）。
- 1,000 語の照合がページの読み取りの遅れとして計測に出たとき（照合器をプロセスの外にキャッシュする、または語の上限を下げる）。
- 言語ごとに語を区切って「単語全体だけ」を CJK でも効かせたいとき（形態素の辞書が要り、バイナリと費用が大きくなる）。

## 経緯

FR-209（キーワードフィルタ）は「W」で、ADR-0013 はリストの決定のときにキーワードフィルタを FR-209 に残した。Mastodon・Misskey・GoToSocial・Akkoma はどれもキーワードフィルタを持つので、決定者が FR-209 を上げて `v0.1.0` に入れると決めた（#2561）。
あわせて、`hide` はサーバーがページから除き `warn` は印を付けて返すこと、照らす文字列（CW の後ろの本文を含む）を決定者が決めた。Web だけでなく `pkg/mykit`・`pkg/mybot` の利用者も同じ結果を受け取るためである。
その後、推奨案のうち、持ち主を `timeline` にすること、上限（1 人 1,000 語の合計を含む）、`hide` の通知を未読の数に入れないこと、直接開いた投稿と引用された投稿の 2 つの例外を、決定者が推奨のとおりに決めた。

残る問いは、語を用字をまたいでどう照らすかと、読み取りのどこで当てるか、持ち主と上限だった。

- 照らし方: Mastodon は語を大文字小文字を区別せず照らし、`whole_word` は前後が単語の文字でないことで判定するが、単語の文字の定義はクライアントに任され、公式の実装は JavaScript で `[A-Za-z0-9_]` を使う（[Implementation guidelines for filters](https://docs.joinmastodon.org/api/guidelines/#filters)、確認日 2026-11-09）。これでは `café` のような非 ASCII の文字が単語の境界になり、日本語では意味をなさない。
  Misskey のワードミュートは CW と本文をつなげた文字列を部分一致で照らし、配列の中は AND、配列どうしは OR で、`/…/` の形は RE2 の正規表現として照らす。投票とブーストの中身は照らさず、自分のノートは照らさない（[check-word-mute.ts](https://github.com/misskey-dev/misskey/blob/develop/packages/backend/src/misc/check-word-mute.ts)、確認日 2026-11-09）。
  そこで、このサーバーにすでにある Web の絵文字の検索のそろえ方（NFKC・小文字・カタカナをひらがな）を照合にも使い、単語の境界は Unicode の文字の分類と用字で決めることにした。
- 当てる場所: Mastodon v2（4.0 以降）は `filtered` をサーバーが付け、`hide` の投稿を出さないことはクライアントに任せる（同ページ）。クライアントごとに結果が違い得るので、決定者の決めたとおりサーバーが除く。
  ADR-0013 §1 の fan-out-on-read は返す直前に `canView` を再適用しているので、同じ段階で、描くために読んだ文字列に照らせば追加の読み取りが要らない。
- 文脈・動作・期限は Mastodon の Filter（`home`・`notifications`・`public`・`thread`・`account`、`warn`・`hide`、`expires_at`。[Filter](https://docs.joinmastodon.org/entities/Filter/)、確認日 2026-11-09）に合わせた。利用者が乗り換えたときに同じ考え方で設定でき、エクスポート・インポートの形を写しやすい。

## 採らなかった案

- クライアントで照合する（Mastodon v1、Misskey のソフトミュート）: サーバーの負荷がなく、フィルタの変更が読み直しなしで効くが、Web・`pkg/mykit`・`pkg/mybot` で結果が揃わず、`hide` の投稿もクライアントへ送ることになる。決定者の決定に合わない。
- 投稿を受け取ったとき（書くとき）に照らして結果を投影に保存する（Mastodon v1 の `irreversible`）: 読み取りが軽いが、fan-out-on-read（ADR-0013）では閲覧者ごとの投影が要り、フィルタを変えても過去の投稿に効かず、投稿の編集に追いつかない。
- 正規表現を許す: 表現力は最も高い（Misskey）が、利用者の多くは書けず、照合器を 1 つにまとめられないので 1,000 語の照合が遅くなる。RE2 でも、利用者ごとの式を毎回コンパイルする費用が残る。
- AND の語の組（Misskey）: 「A と B の両方を含む」を書けるが、画面とデータの形が 1 段深くなる。空白を含む句と複数のフィルタで多くは足りる。
- Mastodon の `whole_word` の定義（`[A-Za-z0-9_]`）をそのまま使う: Mastodon のクライアントと挙動が揃うが、ラテン文字の発音記号やキリル文字の語の途中が境界になり、意図しない一致が出る。
- 形態素解析で CJK の語を区切る: 日本語でも「単語全体だけ」が効くが、辞書でバイナリと記憶が大きくなり、言語ごとの辞書が要る（NFR-COST-2）。
- `blur`（Mastodon 4.4 の、添付だけを隠す動作）: 一致した投稿の画像だけを隠せるが、閲覧の注意（`sensitive`）の表示と役割が重なる。要望が出てから足せる。
- 投稿ごとのフィルタ（Mastodon の FilterStatus）: 特定の投稿を隠せるが、それはキーワードの照合ではない。投稿を隠したいときはミュート・ブロックがある。
- 持ち主を `identity` にする（言語のフィルタと同じ）: 利用者の設定が 1 か所に集まるが、照合する読み取りのたびに呼び出し側が語を運ぶことになる（§8）。
- 新しいモジュール `filter` を作る: 境界がはっきりするが、表が 3 つの小さなモジュールになり、タイムラインの組み立てと同じ段階で当てるために `timeline` から呼び合うことになる。
- 上限を 100 × 100（1 人 10,000 語）だけにする: 単純だが、照合器の大きさと照合の時間が 10 倍になる（§9）。

## Consequences（影響）

- 良い影響: どのクライアントでも同じ投稿が畳まれ、除かれる。`hide` の投稿はクライアントへ送られない。フィルタの変更は過去の投稿と編集にすぐ効く。新しい表は `timeline` の 3 つだけで、投影は増えない。
- 良い影響: 半角・全角・大文字小文字・カタカナとひらがなの揺れを利用者が語ごとに書き分けなくてよい。
- 悪い影響: 照合は読み取りのたびに走り、ページの読み取りとストリームの送信に CPU が足される（§9 の上限で抑える）。
- 悪い影響: 通知の未読の数を求めるときにも未読の通知の投稿を照らすので、`notification` の数え方が SQL の数え上げだけでは済まなくなる。
- 悪い影響: `hide` の投稿が多いと、ページが少なく、ときに 0 件で返る（`canView` で除くのと同じ）。クライアントは次のページのカーソルがあれば読み続ける。
- 悪い影響: 日本語・中国語・タイ語では「単語全体だけ」が効かず、短い語は意図しない部分にも一致する（「猫」は「子猫」にも一致する）。画面の短い一文と、ドキュメンテーションサイトのマニュアルへの案内で補う。
- 悪い影響: カタカナとひらがなをそろえるので、両者を区別したい語は書き分けられない。
- 悪い影響: クライアントは照合しないので、フィルタを保存したあと開いているタイムラインを読み直すまで表示が変わらない。
- 後続の作業: サーバーの表・照合・すべての読み取りの経路（#2562）、設定の画面と畳んだ投稿（#2563）。data-model §4.6 と §6、`api/spec/` の `Status` と新しいパス、`pkg/mykit`、利用者のガイドを同じ作業で更新する。

## Open Questions / 要検証

- 照合の時間の見積もり（1,000 語・40 件で数ミリ秒、§9）は計算で、実装で測って確かめる（要検証）。
