# ADR-0064: キューとジョブのダッシュボード（ジョブの一覧と試行の記録）

- Status: Accepted（ADR-0120（外部のジョブキューは DB のジョブを起こす合図だけを運ぶ）で Cloud Tasks・SQS のジョブも DB の `jobs` に置くので、待ちのジョブの一覧はすべてのキューで出る）
- Date: 2026-10-21
- Deciders: @rosylilly
- Issue: #815

## Context（背景・課題）

決定者の回答（原文、要件の監査の結果について）: 「NFR-OPS-3: キュー及びワーカージョブの状態や失敗、ログなどが一覧できるキューダッシュボードを管理画面に追加」。

NFR-OPS-3 は「管理画面でキューの滞留・失敗ジョブ・連合先の状態を確認できる」ことを求める。今の管理画面と管理 API が見せるのは失敗して止まったジョブ（`dead_jobs`、`/admin/dead-jobs`）だけで、
待っているジョブ・実行中のジョブ・リトライを待つジョブと、ジョブごとの試行の経過は見えない。キューの滞留は `my.queue.*` のメトリクス（[ADR-0055](0055-service-observability.md)）にしかない。

今あるものと、決めていないこと:

- [ADR-0004](0004-job-queue-abstraction.md) はジョブのモデルとポート（`JobQueue`・`JobHandlerRegistry`・`JobRunner`・`Scheduler`）、失敗したジョブを DLQ のあるサービスでも DB の `dead_jobs` に寄せることを決める。
  未完了のジョブを読む口と、試行の記録は決めていない
- `internal/app/queue` には、ADR-0004 の外側の読み取りの口として `DeadJobs`（一覧・再実行・削除・消去）と `BacklogReader`（ADR-0055 のスナップショット用の件数）がある。
  実装は `queue/db` と `queue/inline` だけで、`queue/sqs`・`queue/cloudtasks` はまだパッケージの宣言しかない
- DB キューの `jobs` は未完了のジョブだけを持ち、完了で消える。試行ごとの情報は、最後の試行の `last_error` と試行回数 `attempt` だけで、前の試行の失敗の理由は上書きされて残らない
- ジョブの 1 回の実行の終わりに、runner は 1 行の構造化ログ（`job`、[running.md](../operations/running.md)）を標準出力に出す。ログの基盤がない Self-hosted では、管理画面から辿れない
- ADR-0055 §4 は「出来事の数は KV にも DB にも書かない（DB の書き込みが利用量に比例して増え、scale to zero を妨げる）」と決めた。試行をすべて DB に書くと、この理由に触れる
- 同じ形の前例として、連合の配送は試行をイベント `delivery_attempts` に記録し、30 日で消す（[federation.md](../architecture/federation.md)、[data-model.md](../architecture/data-model/README.md)）

この ADR は、ダッシュボードのために増やすポート、試行の記録の持ち方（ADR-0020 の分類・保持期間・量の上限・個人情報）、キューのアダプタごとに取れる情報が違うときの扱いを決める。
ポートを広げ、新しい表を足すので、Accepted の ADR が扱っていない決定として、実装の前に決める。

## Decision Drivers（判断基準）

1. **ほぼ $0 の構成を壊さない**（NFR-COST、ADR-0055 §4）: 正常に動くジョブのために DB の書き込みを増やさない
2. **障害の調べやすさ**（NFR-OPS-3）: 止まっている・繰り返し失敗しているジョブについて、いつ・どこで・なぜ失敗したかを管理画面だけで追える
3. **アダプタの差を吸収する**（ADR-0004）: どのキューでも同じハンドラ・同じ runner で、記録の経路も 1 つにする
4. **個人情報を増やさない**（NFR-SEC、ADR-0038 の考え方）: 記録が利用者の個人データの写しにならない。保持期間と量に上限がある
5. **データモデルの規則**（ADR-0020）: 表の分類が明確で、状態をタイムスタンプの NULL で表さない
6. **実装の小ささ**

## Considered Options（選択肢）

試行の記録の持ち方:

1. **A. すべての試行（成功を含む）をイベントの表に記録する**: ジョブの実行の履歴が完全に残り、完了したジョブも辿れる
2. **B. 成功しなかった試行（`retry` と `dead`）だけをイベントの表に記録する**: 成功は今の構造化ログに任せる
3. **C. 記録を持たない**: ダッシュボードは `jobs` と `dead_jobs` の今の値（最後のエラー・試行回数）だけを見せ、試行の経過はログの基盤（Cloud Logging・CloudWatch Logs・Loki）で `job_id` を検索してもらう
4. **D. ハンドラが出すログの行（slog）もジョブの実行に結び付けて保存する**: 試行の記録に加え、試行の間にハンドラが出した行を捕まえて DB に置く

未完了のジョブの読み方:

1. **a. キューのポートに読み取りの口を足し、取れるアダプタだけが実装する**（`DeadJobs`・`BacklogReader` と同じく、型アサーションで有無を判定する）
2. **b. すべてのアダプタに必須の口にする**: Cloud Tasks・SQS では API（`ListTasks`・`GetQueueAttributes`）で埋める

## Decision（決定）

**決定: B（成功しなかった試行だけを記録する）と a（未完了のジョブは読めるアダプタだけが見せる）。**

A を選ばない最も強い理由は ADR-0055 §4 と同じで、成功したジョブのたびに DB に書くと、書き込みが利用量に比例して増え、Neon・Aurora の scale to zero を妨げる。
B なら、記録の書き込みは失敗の数にしか比例しない。また、ダッシュボードに並ぶジョブ（未完了・失敗）の試行は、成功しなかった試行がすべてなので、B でも一覧に出るジョブの経過は欠けない。
A の利点（完了したジョブを後から辿れる）は、構造化ログの `job` の行（`job_id` を持つ）が担う。

C を選ばない理由: 前の試行の失敗の理由が残らず、ログの基盤を持たない Self-hosted では管理画面から辿る手段がない。
D を選ばない理由: ハンドラのログはリモートのアカウント・投稿の URL や本文の断片を含みうるうえ、個人情報の写しの置き場が増える。行の量も上限を決めにくい。runner が書く 1 試行 1 行の記録で、何が・どこで失敗したかは分かる。

### 1. 試行の記録 `job_attempts`（イベント）

| 列 | 内容 |
| --- | --- |
| `job_id` | ジョブの ID（`jobs.id` / `dead_jobs.id`。再実行しても同じ） |
| `attempt` | 試行の番号（1 から） |
| `job_type` | ジョブの型（絞り込みと、ジョブが消えた後の表示のため） |
| `outcome` | `retry`（もう一度試す）/ `dead`（失敗が確定した） |
| `error` | 失敗の理由。先頭の 2,000 バイトまで（UTF-8 の境界で切る） |
| `worker` | 試行したワーカーの名前 |
| `started_at`・`finished_at` | 試行の開始と終了 |

- 主キーは `(job_id, attempt, finished_at)` とし、同じ試行の記録を繰り返しても 1 行になる（冪等）。再実行（`RequeueDeadJob`）は試行回数を数え直すので、同じ `attempt` が 2 回現れうる。終了時刻で区別する
- 記録するのは runner（pull runner と、将来の push receiver が共有する結果の処理）で、新しいポート `queue.AttemptLog` を通す。キューのアダプタには依存しない（DB キューでも Cloud Tasks・SQS でも同じ DB の表に書く。ADR-0004 が失敗したジョブを DB に寄せるのと同じ考え方）
- 記録の失敗はジョブの結果を変えない（ログに出して続ける）。DB キューでは、`Release`・`Bury` と同じトランザクションで書く実装にしてよい
- 成功した試行（`success`）は記録しない。ジョブが最後に成功すれば、ジョブは一覧から消え、その前の失敗の記録は保持期間まで残る

### 2. 保持期間・量の上限・個人情報

- **保持期間**: `finished_at` から設定 `job_attempt_retention`（既定 30 日）。失敗したジョブの `dead_job_retention` とは別の設定で、既定値を揃える。毎時の消去ジョブ（今の `queue.purge_dead_jobs` を広げる）が、古い順に 1 文 1,000 行・20 文まで消す（`delivery_attempts` と同じ）
- **量の上限**: 1 行は `error` の 2,000 バイトで上限が決まる。1 つのジョブの行数は再試行の方針の `MaxAttempts` で上限が決まる（再実行のたびに増えるが、各行は保持期間で消える）。行の総数は「保持期間 × 失敗の数」で、正常なジョブは増やさない
- **個人情報**: ペイロード（`payload`）とハンドラのログは記録しない。`error` はハンドラが返したエラーの文で、ハンドラはエラーにメールアドレス・IP アドレス・トークン・本文を入れない（今の `last_error` と同じ規則を明文化する）。
  ペイロードは今の失敗したジョブの画面と同じく、管理者（`manage_jobs`）にだけ見せる

### 3. 未完了のジョブの一覧（アダプタごとの差）

- `internal/app/queue` に読み取りの口 `JobInspector` を足す: 状態と型で絞り込んだジョブのページ（カーソル）と、状態 × 型の件数を返す。実装は `queue/db` と `queue/inline`
- 状態は `jobs` の今の値から導く（列は足さない）:

  | 状態 | 条件（DB キュー） |
  | --- | --- |
  | 実行中（`running`） | リースが有効（`locked_until > now`） |
  | 待ち（`queued`） | 実行中でなく、`attempt = 0`（`run_at` が先なら予定の時刻を見せる） |
  | リトライ待ち（`retrying`） | 実行中でなく、`attempt > 0` |
  | 失敗（`dead`） | `dead_jobs` の行 |

- Cloud Tasks・SQS のアダプタは `JobInspector` を実装しない（b を選ばない）。SQS は個々のメッセージを覗くと可視性タイムアウトを変えてしまい、Cloud Tasks の `ListTasks` は API の呼び出しの費用がかかる。
  滞留はプラットフォームの標準の指標（ADR-0055 §2）で見る。ダッシュボードは「このキューでは未完了のジョブを一覧できない」と表示し、失敗と試行の記録（どちらも DB）は見せる
- 実装していないアダプタでも管理 API の形は変えない: 応答に、そのキューで読めるもの（`pending_listing` の可否）を持たせる

### 4. 管理 API と管理画面

- 権限は今と同じ `manage_jobs`（読み取りは `admin:read`、再実行・削除は `admin:write`）
- `GET /admin/queue`: 状態 × 型の件数、最も古い実行可能なジョブの待ち、アダプタが読めるもの
- `GET /admin/jobs?state=&type=`: ジョブのページ（`state=dead` は今の `dead_jobs` の一覧を兼ねる）
- `GET /admin/jobs/{id}/attempts`: ジョブの試行の記録（新しい順）
- 失敗したジョブの再実行・削除は今の操作をこの名前空間に移す（v0 は破壊的変更を許す。ADR-0012）
- 管理画面は `/admin/jobs` に 1 つのダッシュボードを置き、今の `/admin/dead-jobs` はその「失敗」の絞り込みにまとめる

### 覆る条件

- 成功した試行も DB で辿りたいという運用の要望が強い（ログの基盤なしで完了したジョブを調べたい）なら、A を設定で選べるようにすることを再検討する
- Cloud Tasks・SQS のアダプタを実装するとき、未完了のジョブを費用なく読める API があれば `JobInspector` の実装を足す

## Consequences（影響）

- 良い影響
  - 管理画面だけで、キューの滞留・実行中のジョブ・リトライの経過・失敗の理由を追える（NFR-OPS-3）
  - 正常に動くジョブは DB の書き込みを増やさない。記録の量は失敗の数と保持期間で決まる
  - 記録の経路が runner の 1 か所で、キューのアダプタを替えても試行の記録は同じ
- 悪い影響・トレードオフ
  - 完了したジョブの経過（成功した試行の時刻・所要時間）は DB に残らない。構造化ログで `job_id` を検索する
  - 失敗が大量に続く障害（連合先の停止で配送が全部リトライする）のとき、記録の行も同じだけ増える。保持期間と毎時の消去で上限を持つが、障害の間は DB の書き込みが増える
  - Cloud Tasks・SQS では未完了のジョブの一覧が出ず、ダッシュボードの見え方がアダプタで変わる
  - `error` に個人情報を入れない規則は、型では守れない。ハンドラのレビューとテストで守る
- 後続で必要になる作業（Issue 化する）
  - `job_attempts` の表（`schema/<dialect>.sql`）、`queue.AttemptLog` と `queue.JobInspector` のポートと `queue/db`・`queue/inline` の実装、contract test
  - 設定 `job_attempt_retention` と毎時の消去、[configuration.md](../reference/configuration.md) の再生成
  - 管理 API（`api/openapi.yaml`）と管理画面のダッシュボード（今の失敗したジョブの画面をまとめる）、[data-model.md](../architecture/data-model/README.md)・[web-client.md](../architecture/web-client/README.md)・[running.md](../operations/running.md) の更新

## Pros and Cons of the Options（詳細比較・任意）

| 観点 | A. すべての試行 | B. 成功しなかった試行 | C. 記録なし | D. ハンドラのログも |
| --- | --- | --- | --- | --- |
| DB の書き込み（正常時） | ジョブ数に比例 | 増えない | 増えない | ジョブ数・ログ行数に比例 |
| 一覧に出るジョブの経過 | ◎ | ◎ | △（最後の失敗だけ） | ◎ |
| 完了したジョブの経過 | ◎ | ×（ログで見る） | ×（ログで見る） | ◎ |
| 個人情報の写し | `error` だけ | `error` だけ | なし | ログの全文 |
| 実装量 | 中 | 中 | 小 | 大 |
