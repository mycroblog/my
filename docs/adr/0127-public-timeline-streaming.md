# ADR-0127: ローカル・連合のタイムラインにも新着を届け、自動の差し込みを既定にする

- Status: Accepted
- Date: 2026-10-30
- Deciders: @rosylilly
- Issue: #1906

## Context（背景・課題）

リアルタイム更新（FR-207、[ADR-0016](0016-client-api-style.md) の SSE、[ADR-0050](0050-stream-pubsub-across-processes.md) のプロセス間の配信）は、
ログインした利用者のホーム・リスト（[ADR-0122](0122-lists.md)）の新着、通知、お知らせだけを届ける。
[ADR-0077](0077-timeline-auto-insert.md) は、届いた新着の差し込みをアカウントの設定 `timeline_auto_insert` で選べるようにし、
既定を偽（押すまで溜める）、対象を「ストリーミングで新着が届くタイムライン」とした。ローカル・連合（FR-202）は新着が届かないので対象外で、開き直すまで新しい投稿が見えない。

決定者の決定（原文）:

> ローカル・連合・リストすべての「タイムライン」で自動更新が届くべきですし、自動更新のオプションは既定でオンにしてほしいです。

この ADR は、ローカル・連合のタイムラインに新着を届ける形（エンドポイント・誰が受け取れるか・何を届けるか・配信の経路）と、`timeline_auto_insert` の既定を真にすることを決める。
リストはすでに `list_update` で届き、ADR-0077 の規則が当たっているので、この ADR は変えない。

## Decision Drivers（判断基準）

1. 決定者の決定: ローカル・連合・リストのタイムラインで新着が届き、既定で自動で差し込まれること
2. 見えてはいけない投稿を届けないこと: 公開範囲・ブロック・ミュート・ドメインの処分は、REST のタイムラインと同じ 1 つの方針の関数で判定する（AGENTS.md の設計ルール、[ADR-0017](0017-visibility-local.md)）
3. ほぼゼロコストの運用（NFR、[ADR-0050](0050-stream-pubsub-across-processes.md) の Driver 2）: 見ていないタイムラインの新着を送らない。開いたままのつながりを増やしすぎない
4. 読んでいる位置とフォーカスを奪わず、利用者が止められること（WCAG 2.2.2、[ADR-0077](0077-timeline-auto-insert.md) の 3〜6）
5. 今のストリーム（ホーム・リスト・通知・お知らせ）を切らずに済むこと

## Considered Options（選択肢）

1. ローカル・連合ごとのストリームのエンドポイントを足し、そのタイムラインを表示している間だけ開く
2. 今の `GET /api/v1/streaming` に、受け取るタイムラインを選ぶクエリ（`timeline=local` など）を足し、表示するタイムラインが変わるたびにつなぎ直す
3. 今のストリームで、ログインした全員にローカル・連合の新着を常に届ける
4. ストリームを足さず、クライアントがローカル・連合の最初のページを一定の間隔で取り直す（ポーリング）

## Decision（決定）

**選択肢 1 を採用する。** 加えて `timeline_auto_insert` の既定を真にする。

### 1. エンドポイント

- `GET /api/v1/streaming/timelines/{timeline}`（`timeline` は `local` か `federated`）を足す。SSE で、`GET /api/v1/streaming` と同じく `fetch` と `Authorization` で読む。
- イベントは `update` の 1 種類で、`data` はそのタイムラインに入る投稿の `Status`。入る投稿は REST のローカル・連合のタイムラインと同じで、連合にはブーストを入れない。
- 何も再送しない。つなぎ直したら、クライアントはそのタイムラインの最初のページを読み直す（`GET /api/v1/streaming` と同じ約束、ADR-0077 の 7）。
- このストリームは、利用者が同時に開けるストリームの上限（429 `too-many-streams`）に数える。1 つのタブで開くのは、表示しているタイムラインの 1 本だけである。

### 2. 誰が受け取れるか

- ログインした利用者だけ。インスタンス設定 `local_timeline_access` / `federated_timeline_access` が `off` なら 404 にする（REST のタイムラインと同じ）。
- ログインしていない人には、`everyone` の設定でも届けない（401）。ログインしていない人のつながりは数を抑えられず、長く開いたつながりは Cloud Run などで費用になるからである（Driver 3）。ログインしていない人は、開き直して読む（今のまま）。

### 3. 何を届けるか

- REST の `GET /api/v1/timelines/local` / `GET /api/v1/timelines/public`（連合）が、その時点で同じ利用者に返す投稿と同じものだけを届ける。公開範囲・ブロック・ミュート・ドメインの処分・タイムラインの言語（FR-208）は、REST と同じ方針の関数で、受け取る利用者ごとに判定する。
- ローカルはこのサーバーのアカウントの公開の投稿とログインした人への `local` の投稿、連合は保存したリモートの公開の投稿も含み `local` を含まない（REST と同じ、ADR-0017）。リモートの投稿は、受信箱のジョブが保存したときに届く。

### 4. 配信の経路

- 投稿の作成（ローカルの投稿と、保存したリモートの投稿）は、今のホームの新着と同じく `uow.CommitHook` から `stream.Publisher` に「公開のタイムラインの新着」の知らせを 1 つ出す（ADR-0050 の `Relay` と `Bus` をそのまま使う）。
- 各プロセスの `Hub` は、そのタイムラインのストリームを開いている購読にだけ振り分け、購読ごとに 3 の判定をしてから送る。開いている購読がないプロセスは何もしない（遅延 listen、ADR-0050）。

### 5. クライアント

- ローカル・連合のタイムラインの画面は、表示している間だけそのストリームを開き、離れたら閉じる。届いた投稿は、ホーム・リストと同じ `NewPostsFeed` と ADR-0077 の 3〜7 の規則（先頭にいるか・アンカー・ピル・一時停止・つながらないとき）で扱う。
- 押すまで溜めるとき（設定が偽、または一時停止の間）も、ホームと同じ「N 件の新しい投稿」のボタンを出す。

### 6. 自動の差し込みの既定

- `timeline_auto_insert` の既定を真にする。設定を一度も変えていない利用者は、ホーム・リスト・ローカル・連合のすべてで自動で差し込まれる。偽を選んだ利用者は今のまま溜める。
- WCAG 2.2.2 は、設定で止められることと、フォーカスか選択がフィードの中にある間の一時停止（ADR-0077 の 4）で満たす。支援技術でフィードを読む人は、フォーカスがフィードの中にあるので、既定が真でも中身が動かない。

### 7. ほかの ADR との関係

この ADR は ADR-0077 の次の部分だけを置き換える。ADR-0077 は Accepted のままで、その他の決定と本文は変えない。Status の行に、この ADR が置き換えることを注記する。

- 1 の「既定は偽（オプトイン）」。既定は真にする。
- 2 の「ローカル・連合・ハッシュタグ・プロフィールの一覧は新着が届かないので対象外」のうち、ローカル・連合。ハッシュタグ（FR-203）とプロフィール（FR-204）は対象外のままにする。

**覆す条件**: ログインしていない人にも届けることを決定者が求めるとき（2 を改める）、または 1 つのタブで複数のつながりを持つことがブラウザ・ホスティングの制約になると分かったとき（選択肢 2 に寄せる）。

## Consequences（影響）

- 良い影響
  - ローカル・連合を開いたまま、新しい投稿が流れてくる。ホーム・リストと同じ見た目と規則で、既定で差し込まれる。
  - 見ていないタイムラインの新着は送らないので、モバイルの通信と、ほかの利用者のつながりの費用が増えない。
  - 今のストリーム（通知・お知らせ）はつなぎ直さずに済む。
- 悪い影響・トレードオフ
  - ローカル・連合を開いている間、つながりが 1 本増える。上限に数えるので、多くのタブを開く人は先に上限に当たる。
  - 投稿 1 件ごとに、開いている購読の数だけ公開範囲・ブロック・ミュートを判定する。大きなサーバーの連合のタイムラインでは、プロセスの負荷が購読の数に比例して増える。
  - 既定が真になり、設定を変えていない利用者の体験が変わる。スクロールの補正のずれ（ADR-0077 の悪い影響）に当たる人が増える。
  - ログインしていない人のローカル・連合は、今のまま自動では流れない。
- 後続で必要になる作業（Issue 化する）
  - サーバー: `GET /api/v1/streaming/timelines/{timeline}`（OpenAPI・ハンドラ・`Hub` の振り分け・方針の判定・上限・テスト）
  - サーバー: `timeline_auto_insert` の既定を真にする（スキーマの既定・data-model・client API の説明）
  - Web クライアント: ローカル・連合の画面で表示中だけストリームを開き、`NewPostsFeed` と ADR-0077 の規則で扱う（テスト・ストーリー・E2E）
  - 文書: 画面の仕様（`screens/local.md`・`screens/public.md`・`screens/home.md`）と web-client の §10・Y7、運営者向けの文書

## Pros and Cons of the Options（詳細比較・任意）

### 選択肢 1: タイムラインごとのエンドポイント

- 良い点: 表示している間だけ開くので、見ていないタイムラインの新着を送らない。今のストリームに触れない。サーバーの振り分けが単純（そのタイムラインの購読にだけ配る）。
- 悪い点: タブごとのつながりが表示中に 1 本増える。HTTP/1.1 でつなぐ環境では、同じオリジンへの同時接続の上限（多くのブラウザで 6、要検証）に近づく。

### 選択肢 2: 今のストリームにクエリで選ばせる

- 良い点: タブのつながりは 1 本のまま。上限の数え方が変わらない。
- 悪い点: タイムラインを移るたびにつなぎ直し、その間の通知・お知らせを取り逃す（再送はない）。読み直しの手順がホーム・通知にも及ぶ。

### 選択肢 3: 全員に常に届ける

- 良い点: クライアントは何もしなくてよい。
- 悪い点: 見ていない人にも連合の全投稿を送り、モバイルの通信とサーバーの判定の負荷が利用者の数に比例して増える（Driver 3 に反する）。

### 選択肢 4: ポーリング

- 良い点: サーバーの変更が要らない。ログインしていない人にも使える。
- 悪い点: 新着が遅れ、誰もいない時間も読み直しが続く。キャッシュ（ADR-0045）と読み込みの手順が増える。リアルタイム更新（FR-207）の形と揃わない。

## Open Questions / 要検証

- ブラウザの同じオリジンへの同時接続の上限（HTTP/1.1 で 6 本）と、HTTP/2 で多重化されるときの扱い（要検証。Cloud Run と、自前の VM でのリバースプロキシの既定の設定）。
- 大きなサーバーの連合のタイムラインで、購読ごとの判定がどこまで持つか。必要なら、同じ判定の結果になる購読（ブロック・ミュートのない利用者）をまとめる最適化を後で検討する。
