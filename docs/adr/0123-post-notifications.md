# ADR-0123: 投稿の通知: 特定のアカウントの新しい投稿を通知と Web Push で知らせる

- Status: Proposed
- Date: 2026-10-30
- Deciders: @rosylilly
- Issue: #1867

## Context（背景・課題）

通知（FR-205）は、ほかの人が自分に向けてした行動（フォロー・メンション・ブーストなど）だけを知らせ、特定の人の新しい投稿を知らせる手段がない。
フォローの設定 `follow_preferences.notify`（data-model §4.5）とクライアント API の `notify`（`FollowAccountRequest`・`Relationship`）、CSV の `Notify on new posts` の列はあるが、値を保存するだけで通知は作らない。

決定者の要望と回答（原文。問い → 答え）:

> 投稿通知 → フォローしている・していないに関わらず有効化できる。特定のアカウントの投稿を通知する。メール送信はしない。WebPush のみ
> 投稿通知で、フォローしていないリモート（他サーバー）のアカウントをどう扱いますか？ → リモートはフォロー必須

フォローしていないリモートのアカウントの投稿は、このサーバーに届かない（`Create` はフォロワーのいるサーバーへ配送される）ので、通知を約束できない。
決める必要があるのは、購読の持ち方（既存の `notify` との関係）、通知する投稿の範囲、通知の種類と経路、上限である。

## Decision Drivers（判断基準）

1. フォローしていないローカルのアカウントも購読できる（決定者の要望）
2. 見えない投稿（公開範囲・ブロック・ミュート・処分）を通知で漏らさない。公開範囲の判断は単一のポリシー関数に任せる
3. 届くと約束できない投稿は購読させない（リモートはフォロー中だけ）
4. メールでは送らない。アプリ内と Web Push で届く
5. 購読の置き場所を 1 つにする

## Considered Options（選択肢）

- 購読の持ち方: A1 `notification` が購読の表を持ち、フォローの `notify` をなくす / A2 フォローの `notify` を使い、未フォローのローカルの購読だけ別の表に持つ
- 通知する投稿: B1 新しい投稿（他人への返信とブーストを除く） / B2 返信とブーストも含むすべて

## Decision（決定）

推奨案は **A1・B1**。

### 1. 購読

- `notification` が購読の表（現在値。行は（購読する利用者、対象のアカウント）と作った時刻）を持つ。表の細部は data-model §4.7 に書く。
- 購読できる相手:
  - ローカルのアカウント: フォローの有無を問わない。自分自身は購読できない。
  - リモートのアカウント: 承認済み（`active`）でフォローしている間だけ。承認待ちのフォローの相手も購読できない。購読は `graph` の公開 API（`Follows`）で確かめる。
  - どちらかがブロックしている相手は購読できない（`422`）。
- リモートの相手へのフォローが終わったら（`graph.follow_terminated`。理由を問わない）、その購読を消す。ローカルの相手は、フォローを解除しても購読を残す。
- ブロックが始まったら（`graph.blocked`。どちら向きも）、その組の購読を消す。
- 購読は相手に知らせず、相手からは見えない（API・ActivityPub のどれにも出さない）。
- 上限は 1 人あたり 1,000 件。超える購読は `422`。
- フォローの設定 `follow_preferences.notify` はなくし、購読の表に置き換える（v0.1.0 の前なので、ADR-0087 によりデータは移さない）。
  クライアント API の `notify`（`FollowAccountRequest` と `Relationship`）は残し、購読の有無を読み書きする。フォローと同時の `notify: true` は、リモートの相手ではフォローが承認されたときに購読を作る（承認待ちの間は `Relationship.notify` が `false`）。
  CSV の `Notify on new posts` の列も購読を読み書きする。

### 2. 通知する投稿

- 対象のアカウントの新しい投稿で、次をすべて満たすもの:
  - このサーバーで作られた投稿か、リモートから `Create` が配送されて届いた投稿。取りに行った投稿（会話・検索・引用のための取得）は、古い投稿を新しい通知にしないよう通知しない
  - 返信でない投稿か、自分自身への返信（スレッドの続き）。他人への返信は通知しない
  - ブーストではない
  - 受け取る人がその投稿を見られる（単一の公開範囲のポリシー関数。`private` は受け取る人がフォロワーのとき、`direct` は宛先のとき）
- 編集（新しい版）は通知しない。
- 受け取る人が宛先のメンションの通知（`mention`）を同じ投稿で受け取るときは、`status` を作らない。
- ブロック・ミュート（`hide_notifications`）・ドメインのミュート・差出人の `unsolicited_reach`（受け取る人がフォローしていないとき）の除外は、ほかの通知と同じに効く（data-model §4.7）。
- 作り方: 投稿を記録したトランザクション（ローカルの作成と、配送された `Create` の取り込み）で積むジョブ（`notification.notify_post_subscribers`、冪等キーは投稿）が、購読者を 100 件ずつ通知する。`dedupe_key` は `status:<status_id>` で、投稿と受け取る人ごとに 1 つ。
- 投稿が消えたら、その通知は読み取り時に隠す（既存の `notification_deleted_statuses`）。

### 3. 通知の種類と経路

- 通知の種類 `status` を足す。ADR-0109 §2 の表では「普段の通知」の区分に 1 行として入れる。
- アプリ内は選べる・既定オン、Web Push は選べる（購読の `alerts` に `status` を足す。既定はほかの普段の通知と同じ）。
- メールでは送らない（決定者の回答）。通知の設定の表で、この行のメールのセルは出さない。ADR-0109 §4 の未読のメールの対象からも外す。
- 音は ADR-0109 §5 のとおり端末ごとに選べる。
- Web Push は投稿の画面を開く。

### 4. 画面

- プロフィールの見出しの操作に、購読を切り替えるボタン（ベルの形）を置く。リモートでフォローしていない相手には押せない状態で出し、「フォローすると新しい投稿を通知できます」と説明する。
- 通知の一覧の種類の絞り込み（ADR-0109 の D2）に `status` を足す。

### この決定を見直す条件

- フォローしていないリモートの購読の要望が強いとき（outbox を定期的に取りに行く方式を別の ADR で検討する）。
- 購読者の多い人の投稿で、通知のジョブが詰まるとき。

## Consequences（影響）

- 良い: ローカルの人は、フォローせず（タイムラインを増やさず）に新しい投稿だけを追える。
- 良い: 既存の `notify` の API と CSV の列が意味を持つようになり、Mastodon からのフォローの CSV の取り込みで購読も移る。
- 悪い: リモートのアカウントはフォローしないと購読できず、フォローを解除すると購読も消える。
- 悪い: 購読者の多い投稿は、投稿ごとに購読者の数だけ通知の行ができる（ジョブは 100 件ずつに分けるので、投稿のトランザクションは重くならない）。
- 後続の作業（Issue にする）:
  - FR-205 に `status` を足すか、投稿の通知の FR を足す。data-model §4.5（`notify` をなくす）と §4.7（購読の表・`status` の作り方）を書く
  - サーバー: スキーマ・`internal/app/notification`・`graph` の `notify` の置き換え・クライアント API・Web Push の `alerts`・CSV・`pkg/mykit`
  - Web: プロフィールのボタン・通知の行・通知の設定の行と絞り込み（画面の要件 profile.md・notifications.md・settings-notifications.md の更新を含む）

## Pros and Cons of the Options（詳細比較・任意）

- A2（フォローの `notify` を生かす）: 既存の表を使え、フォローの解除で自然に消える。ただし未フォローのローカルの購読に別の表が要り、購読の置き場所が 2 つになって、一覧・上限・CSV の扱いが分かれる。
- B2（返信・ブーストも含む）: 取りこぼしがない。ただし会話の多い人の通知が増えすぎ、Mastodon の利用者の期待（他人への返信は通知しない）とも違う。
