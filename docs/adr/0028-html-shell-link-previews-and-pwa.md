# ADR-0028: Web クライアントの配信・PWA・更新・キャッシュ

- Status: Accepted
- Date: 2026-10-16
- Deciders: @rosylilly
- Issue: #10, #88, #485, #2021

## Decision（決定）

Go がルートごとに HTML の外枠を `html/template` で返し、meta タグを埋め込んでから SPA を起動する。プレビューと PWA を、JS の実行環境なしで両立する。

### 1. HTML の外枠

- `my serve` がすべての HTML を返す。
  - `GET /@{acct}` と `GET /@{acct}/status/{id}`（投稿の表示用 URL は ADR-0018 §8）は meta タグ付きの外枠を返す。
  - それ以外の SPA のルートは、汎用の外枠を返す。
- ActivityPub のコンテントネゴシエーション（ADR-0018）を先に判定する。
  - `application/activity+json` / `application/ld+json` なら AP の JSON を返し、それ以外なら HTML を返す。
  - 常に `Vary: Accept` を付け、HTML には `<link rel="alternate" type="application/activity+json">` を入れる。
- **HTML のリクエストは常に未ログインとして扱う。** API は Bearer トークンだけで認証し、HTML の外枠は個人ごとに変えない。
  - 未ログインでも見られる投稿（`public` と `unlisted`）にだけ、プレビュー用の meta タグを付ける。
    - `unlisted` には `noindex` を付ける。
  - `local` / `private` / `direct` / 削除済み / 存在しない投稿は、**どれも同じ汎用の外枠を 404 と `X-Robots-Tag: noindex` で返す**（存在を漏らさない。ADR-0017, ADR-0018）。
    - ログイン中の閲覧者には、SPA が起動後にトークン付きで投稿を取得して表示する。
- テンプレートは `html/template` の文脈に応じたエスケープに任せる。利用者のデータを `template.HTML` に変換しない。
  - `og:description` は、投稿の HTML からタグを除いた平文を約 200 文字に切り詰めて使う。
- 外枠の HTML は `Cache-Control: public, max-age=60, stale-while-revalidate=300` と ETag で返す。
  - ETag はテンプレートの版・アセットの版・投稿の版・公開範囲・ロケールから作る（ブランドのリビジョンは ADR-0059 が足す）。
- CSP の nonce は使わない（キャッシュできなくなるため）。
  - インスタンスごとの設定（API のオリジン、インスタンス名など）は、`<script type="application/json">` のデータブロックで渡す。
  - ビルド成果物はどのインスタンスでも同じにし、`import.meta.env` にインスタンスごとの値を入れない。
- サーバーのテーマのスタイルシートは、この節と ADR-0019 §9 の CSP の範囲で、同じオリジンから 1 つ足す（ADR-0059）。

### 2. リンクプレビューの meta タグ

- **OGP**
  - `og:title`, `og:type`（プロフィールは `profile`、投稿は `article`）, `og:url`（正規 URL）, `og:image`（と `og:image:alt` / `width` / `height`）, `og:description`, `og:site_name`, `og:locale` を出す。
  - 投稿には `article:published_time` と `article:author` も出す。
- **X Card**: `twitter:card` を出す。画像の比率が合えば `summary_large_image`、なければ `summary` にする。そのほかの項目は X が OGP から読む。
- **Fediverse**: `fediverse:creator`、`<link rel="canonical">` を出す。
- `og:image` は次の順で選ぶ。カード画像の生成は後で検討する。
  1. 投稿の最初の添付画像（代替テキスト付き）
  2. プロフィールのヘッダー画像、またはアバター
  3. インスタンスの既定画像（`preview_image`）
  4. インスタンスのロゴから作る `preview-1200x630`（ADR-0059）
  5. 組み込みの 1200 × 630 の PNG（ADR-0059）
- `<html lang>` と `og:locale` は投稿の言語（またはアカウントの既定）から決める。`Accept-Language` では変えない（キャッシュを分けないため）。

### 3. PWA

- マニフェストはインスタンスの設定から Go が実行時に生成する（名前・テーマ色・言語。アイコンは ADR-0059）。
- Service Worker は `vite-plugin-pwa` の `injectManifest` で、自前の `sw.ts` を使う（Web Push に備える）。
  - **ハッシュ付きのアセット**: 事前にキャッシュする。
  - **ページ遷移**: ネットワーク優先にする（3 秒でタイムアウトし、オフライン用の外枠に切り替える）。サーバーが返す 404 や `noindex` を正とするため。
  - **`/api/*`**: キャッシュしない（NetworkOnly）。ログアウトしたら、すべてのキャッシュを消す。
  - **公開メディアとアバター**: キャッシュ優先にし、件数と期限に上限を設ける。
  - `/theme/`・`/brand/`・絵文字の分割は、それぞれの ADR（ADR-0059・ADR-0091）の決まりでキャッシュする。
  - Service Worker で扱わないパス: `/api/`, `/oauth/`, `/.well-known/`, `/nodeinfo`, `/ap/`, `/manifest.webmanifest`
- 更新の通知と反映は §9〜§15 が決める。
  - デプロイで古いチャンクが消えたとき（`vite:preloadError`）は、§12 の条件でページを読み直す。

### 4. 配信

- Vite は `build.manifest: true` と相対の `base` でビルドする。Go はマニフェストから `<script>` / `<link>` を組み立てる。
  - 埋め込みは `//go:embed all:dist`（`.vite/` を含めるため）。CDN から配信するときは `/assets/*` だけを置く。
- ハッシュ付きのアセットは `immutable` で 1 年キャッシュする。外枠の HTML・`sw.js`・マニフェストは長期キャッシュしない。
- CDN を前に置く場合は、`Accept` の種類をキャッシュキーに含める（AP の JSON と HTML を取り違えないため）。デプロイ文書に書く。
- プレビューの表示は X・Mastodon・Discord・Slack・LINE の実機で確認する（手動、リリースごと）。

### 5. クライアントの提供の形

- **Web クライアント**: TypeScript の SPA を PWA として提供する（ツールチェーンは Bun。サーバーは Go なので、API の型は OpenAPI 等から生成する）（インストール可能、Web Push、iOS はホーム画面追加で Push 可）。
  静的アセットとしてビルドし、各ターゲットの CDN / 静的配信（Cloud Storage + CDN、S3 + CloudFront、Go バイナリへの `embed` 同梱）から配る。UI フレームワークは ADR-0025 が決める。
- **モバイル**: **Tauri 2** で Web クライアントの UI を共有する方針を第一候補とする。モバイルアプリは v0 の範囲に含めない。
  既存の Mastodon アプリは使えない（ADR-0016）ため、v0 の間のモバイル体験は **PWA が担う**。PWA の完成度を v0 の必須要件とする。
  Push 通知・バックグラウンド処理・WebView の性能が要件を満たさない場合は、ネイティブ（または RN）に切り替える決定を別に行う。
- Web UI は最初から「モバイルファースト・タッチ操作・セーフエリア・オフライン耐性」を前提に作る（Tauri 移植のため）。

### 6. クライアントのキャッシュ（TanStack Query と TanStack Router）

- **TanStack Query がサーバーのデータの唯一のキャッシュ**（S1）。ルーターは自分のデータを持たない（`defaultStaleTime`・`defaultPreloadStaleTime` を `Number.NEGATIVE_INFINITY` にする。`0` では、壁時計が巻き戻ると新しく見えて loader を飛ばす）。
- **loader は「キャッシュにあって無効化されていなければそのまま、なければ・無効化されていれば取って待つ」で読む**: `queryClient.query({ ...options, staleTime: Infinity })`（無限スクロールは `infiniteQuery`）。
  `staleTime: "static"` は無効化の印を見ないので loader では使わない。
- **ルーターは再読み込みを待つ**: `routerOptions` に `defaultStaleReloadMode: "blocking"` を置く。
  無効化されていないクエリは loader が即座に返すので、書き込みのない移動はキャッシュから即座に描画する。
  無効化されたクエリがある画面だけ、取り直しが終わるまでいまの画面を残す（遷移は `startTransition` の中、E4）。
- **書き込みは、確かに分かる変化をキャッシュに書き、一覧は印を付ける**:
  - 応答で分かる単体のデータ（投稿・閲覧者・関係・設定）は `setQueryData` / `updateCachedStatuses` で書く
  - 並びや件数が変わり得る一覧は `invalidateQueries`（既定の `refetchType: "active"`）で印を付ける。表示中のものはその場で取り直し、表示していないものは次に開いたときに loader が取り直して待つ
  - 書き込みの成功表示は、表示中のクエリの取り直しを待ってから出す（`await invalidateQueries(...)`）。表示していないクエリの取り直しは待たない。`refreshQueries`（`refetchType: "all"`）は使わない
- **書き込みが変えるクエリは、その書き込みの関数の隣に書く**: `features/<x>/api` に書き込みごとのキャッシュ更新関数（`cachePostedStatus` のような）を置き、部品の `onSuccess` はそれを呼ぶだけにする。
  テストは「書き込み → 別の画面を開く → 最初の描画から反映している」を、遅延のある MSW で確かめる。

### 7. データの種類ごとの方針

| データ | 書き込みのあと | 時間で古くなったとき（既定 `staleTime` 30 秒） |
| --- | --- | --- |
| 閲覧者（`verify_credentials`）・設定（`preferences`） | 応答で書き換える。プロフィールの保存は、閲覧者のアカウント（`lookup`・`/accounts/{id}`）を書き換え、閲覧者の投稿を含む一覧の埋め込みアカウントを差し替えるか印を付ける | 画面を開いたときに裏で取り直す |
| アカウントと関係（`lookup`・`/accounts/{id}`・`relationships`） | 関係を応答で書き換え、件数を持つアカウント、フォロー一覧、ホーム、ブロック・ミュートの一覧に印を付ける | 同上 |
| 投稿単体（`/statuses/{id}`）と、各一覧の中の同じ投稿 | お気に入り・ブーストなどはすべてのキャッシュの写しを書き換える（楽観的更新、S8）。削除は写しを除く | 同上 |
| 一覧（タイムライン・プロフィール・タグ・スレッド） | 新しい投稿で、入り得る一覧に印を付ける | 画面を開いたときに裏で取り直す。読んでいる間は取り直さない（フォーカス・再接続では取り直さない、Y7）。ストリーミングで届く新着は、`timeline_auto_insert` が真なら ADR-0013 の 3・4 のとおりに差し込み、偽のときと一時停止の間は「N 件の新しい投稿」に溜める（S10） |
| 通知と未読数 | 既読は応答で書き換える | ストリーミングが未読数を書き換え、一覧に印を付ける（S10） |
| インスタンス情報 | 管理画面の書き込みが印を付ける | 画面を開いたときに裏で取り直す |
| 管理画面の一覧と件数 | 書き込みが、その書き込みで変わる一覧・件数・監査ログに印を付ける | 同上 |

すべてのデータに共通:

- 利用者が変わったら全部を捨てる（`removeQueries`）。表示言語が変わったら全部に印を付ける。
- 別のタブ・別の端末での書き込みは知らせない（v0。`BroadcastChannel` などでタブの間に知らせる仕組みは持たない）。次に画面を開いたときに、`staleTime` を過ぎていれば裏で取り直す。

### 8. サーバーのキャッシュ

| 応答 | `Cache-Control` | ほか |
| --- | --- | --- |
| client API の閲覧者つきの応答（`Authorization` あり）とエラー | `no-store` | 公開のインスタンス情報など、閲覧者の言語だけで変わるものは `private, max-age=60` |
| client API の匿名で取れる公開 GET の匿名の応答 | `public, max-age=60` | `Vary: Authorization, Accept-Language`。匿名の訪問者には最大 60 秒古い一覧が出る |
| ストリーミング | `no-store` | |
| ActivityPub の匿名で取れる文書 | `public, max-age=60` | `Vary: Accept`。inbox は `no-store` |
| 外枠の HTML | `public, max-age=60, stale-while-revalidate=300` | ETag（§1） |
| ハッシュ付きのビルド成果物・ローカルのメディア（`/media/<メディア ID>/...`） | `public, max-age=31536000, immutable` | URL は内容（メディア ID）が変わると変わる |
| リモートのメディアの中継（`/media/proxy/`） | `public, max-age=<中継の保持期間>` | |
| `sw.js` など固定の URL のファイル | `no-cache` | |

- client API は ETag と条件付き GET を使わない（v0）。閲覧者つきの応答は保存させず、クライアントのキャッシュは TanStack Query だけにする。
- Service Worker は API に答えない。画面の移動はネットワークを先に使い、公開の画像だけを cache-first で持つ（§3、#203）。

### 9. 更新: 既定は割り込まない

通知を「新しい版がある」から「古いままで困るとき」へ変える。

- 新しい版の発見とインストールは裏で行う。トーストは出さない。
- オンラインで開き直せば新しい JS が動き、すべてのタブを閉じれば新しい worker が有効になる。どちらもブラウザの動きで、この ADR は何も足さない。
- リリースかどうかでは分けない。

### 10. worker を入れ替えてよいとき

`skipWaiting` は読み直しを伴わず、**どのタブのチャンクも消さないと分かったとき**だけ送る。

- 各タブは起動時に、自分のビルド（入口のチャンクの URL）を名前に入れた Web Locks の共有ロック `my:build:<url>` を持ち続ける。
- ページは、待っている worker に自分の入口のチャンクを持っているかを尋ねる（同じビルドか）。持っていて、かつ `navigator.locks.query()` の `held` に他のビルドのロックがなければ、`SKIP_WAITING` を送る。読み直しはしない。
- ロックはオリジンのタブと worker にまたがる（[MDN: Web Locks API](https://developer.mozilla.org/en-US/docs/Web/API/Web_Locks_API)、[`query()`](https://developer.mozilla.org/en-US/docs/Web/API/LockManager/query) は 2022 年 3 月から主要ブラウザで利用可、2026-11-03 確認）。凍結したタブにも返事を待たずに済む。
- Web Locks がないブラウザでは送らず、すべてのタブを閉じたときの入れ替えに任せる。
- `controllerchange` で読み直さない。Update は `location.reload()` だけにする。これで別のタブの更新ボタンが効かなくなることも、別のタブのチャンクが消えることもない。
- 同じビルドのページには、トーストを出さない。

### 11. 古いまま長く動くタブ

- 待っている worker を最初に見つけた時刻を localStorage に残す（`lib/storage` に宣言する。利用者のデータではない）。worker が入れ替わったら消す。
- **7 日**待っても自分のビルドが古いタブにだけ、トースト（Update のアクション付き、自動では閉じない）を出す。閉じたら、そのタブでは次の読み直しまで出さない。通話中は出さず、終わってから出す。
- 7 日は、タブごとの割り込みをデプロイの頻度によらず週 1 回に抑える値である。バグ修正の届く遅れの上限でもある。

### 12. 動かなくなる版は必要な更新として扱う

- **消えたチャンク**: `reloadOnPreloadError` は読み直す。ただし、§13 の条件を満たさなければ読み直さず、必要な更新のトーストを出す。ガードの 10 秒は残す。
- **API の変更**: ADR-0090 §8 の非推奨の期間（少なくとも 1 つのマイナー版）で通常は壊れない。壊れるのは、期間なしのセキュリティ修正と、期間より長く開いているタブである。
  - サーバーとクライアントが整数の定数 `webClientEpoch` を持つ。古いクライアントを動かせない変更を入れる PR が手で上げる。版の文字列ではないのでビルドごとには変わらない（#2020 の検査を壊さない）。
  - サーバーは API の応答のヘッダで値を返す（Web のオリジンが別のときに読めるよう、CORS で公開する）。クライアントは、**サーバーの値が自分より大きいとき**だけ必要な更新として扱う。逆（ロールバックやローリングの最中に古いサーバーへ当たった）では何もしない。
- **必要な更新の適用**: §13 を満たせば読み直す。満たさなければ、すぐに Update 付きのトーストを出し、満たしたら読み直す。通話や書き込みは切らない。読み直しはオリジンの 1 タブにつきエポックごとに 1 回で、それでも解消しなければトーストのままにする（ローリングの最中に古い外枠を受け取っても繰り返さない）。
- 読み直しは新しい JS を得るためのもので、`skipWaiting` は要らない。オフラインでは precache の古い版のまま動く。

### 13. 安全な瞬間

黙って読み直すのは必要な更新のときだけで、次をすべて満たす必要がある。1 か所（`lib/pwa` の周辺）の関数にまとめ、機能がそれぞれの状態を登録する。

1. 今の画面のルートが `staticData` で読み直してよいと宣言している（ホーム、タイムライン、通知、プロフィール、投稿など読むための画面）。**宣言のない画面は安全でない**ので、管理画面やこれから足す画面は検知の漏れがあっても失わない
2. 通話していない
3. `QueryClient.isMutating()` が 0 で、下書きにアップロード前の添付がない
4. `Dialog`・`Sheet` が開いていない
5. 編集できる要素にフォーカスがない
6. 再生中のメディアがない

下書きの本文は条件に入れない。sessionStorage で残るので、ここで止めると下書きを持つ人が更新できないままになる。

### 14. 別の版どうしの組み合わせ

新しいページと古い worker の組み合わせは、読み直しのたびに起きる（ページ遷移はネットワーク優先で、サーバーの外枠は新しいチャンクを指すため）。`sw-protocol` のメッセージとプッシュの内容は、前後の版で理解できるものだけを変える。知らないメッセージは無視する（`isMessage` の動き）。

### 15. 更新の費用

インストールの費用は、発見すれば取得するので、通知の出し方によらない。版の文字列だけの更新は #2020 が除くので、利用者が払うのは Web の変更があったときだけで、1 回あたり 0.5〜2 MB（gzip）である。precache の範囲は変えない。

### 16. 更新の決定を覆す条件

- 7 日のトーストでも古いタブのバグ報告が多いなら、閾値を縮めるか、読むための画面に限って、隠れたタブや画面遷移で黙って読み直す形を足す。
- 必要な更新が 1 年に何度も起きるなら、ADR-0090 §8 の側を見直す。
- 利用者の転送量が問題になれば、precache を FR-604 のオフラインに要る範囲へ絞る決定を別に行う。

## 経緯

Web クライアントは React の SPA で、インストールできる PWA にする。同時に、公開プロフィールと公開投稿のリンクを X・Mastodon・Discord・Slack・LINE などに貼ったときにプレビューが出る必要がある（オーナーの要件）。プレビューを取得するボットは JavaScript を実行しないので、SPA だけでは meta タグを返せない。サーバーは Go の単一バイナリで、低コスト（NFR-COST-3）を前提とする。モバイルは、コード共有と多言語対応（G5、G6）から Tauri 2 を第一候補にし、v0 からは外した。

キャッシュの方針は、プロフィールを開く → 投稿する → もう一度開くと古い一覧が出るという不具合から決めた（#485。本物の `my serve` と Playwright で再現した）。原因はクライアントだけにあり、投稿は一覧に印を付けるだけなのに、loader は `staleTime: "static"` で印を見ず、ルーターの `defaultStaleReloadMode` の既定 `"background"` は loader を待たずに古い match を描画していた。書き込みごとに「どの画面のどのクエリが loader で読まれるか」を書き手が知る決まりは守られなかったので、データの種類ごとに一つの方針にまとめ（§6、§7）、サーバーの `Cache-Control` も書き留めた（§8）。spike では二つの変更がそろうと古い一覧が一度も出ず、片方だけでは出た。

更新は当初、すべての変更で「新しい版があります」と通知し、利用者の操作で反映していた。デプロイの多いインスタンスではこのトーストが残り続け、調べると約束も効いていなかった（`113e19b9a` と 2026-11-03 のブラウザの文書で確認）。ページ遷移はネットワーク優先で古い precache にないチャンクはネットワークへ抜けるので、オンラインの読み直しや起動はすでに新しい版を動かしていて、古い版を動かすのは開いたままのタブと 3 秒以内に外枠を得られないときだけである。読み直した後もトーストが出て、別のタブの更新ボタンは効かなくなり、`skipWaiting` は他のタブのチャンクを消していた（`my serve` は今のビルドしか持たない）。`v0.1.0` は運営者がどのホスティングを選んでも動く必要があるので（#2027）、CDN・ローリング・古いアセットの保持を前提にせず、割り込みに上限を持つ形にした（§9〜§16）。

読み直しで失うのは、下書きのアップロード前の添付、通話（`pagehide` で退室し、音声の再開には操作が要る。ADR-0101 §7）、実行中の書き込み、フォーム、開いたダイアログ、入力中の文字、再生中のメディア、読んでいた位置である。下書きの本文と送信中の投稿は sessionStorage と Idempotency-Key で残る。`beforeunload` はモバイルで確実には発火せず、隠れたタブはブラウザの判断で凍結・破棄されるので、§13 は検知の漏れが失敗にならない形にした。precache は 247 ファイル、8.22 MB（gzip で 1.94 MB）で、設定画面の 1 コンポーネントの変更で 105 ファイルの名前が変わり、新しく取得するのは 1.42 MB（gzip で 0.46 MB）だった。`my serve` はアセットを圧縮しないので、転送量が gzip の値になるかは手前のプロキシ次第である。

## 採らなかった案

- JS の実行環境でのサーバーサイドレンダリング（Bun / Node を併走）: JS の実行環境が要り、Go の単一バイナリと低コストの前提に合わない。
- 事前レンダリング: 投稿は実行時に増えるので合わない。
- ボットだけに別の HTML を返す動的レンダリング: Google が非推奨である。
- ネイティブ（Swift / Kotlin）: 最高の UX と OS 統合だが、Web と合わせて 3 重の実装になり、i18n カタログの共有に変換が要る。
- React Native / Expo: 単一コードベースで Push が成熟しているが、Web UI とは別実装になりやすい。
- 書き込みごとに表示していないクエリも `refetchType: "all"` で取り直して待つ: 画面を開くと即座に新しいデータが出るが、全一覧を取り直し、忘れると古い表示が残り続ける。
- `staleTime: 0` でキャッシュをやめる: 古い表示は出ないが、戻る・タブの切り替えのたびに待つ（E4 に反する）。サーバーの負荷も増える。
- 自分の書き込みの結果を SSE で受けて無効化する: 他のタブ・端末の書き込みも届くが、届く前に画面を開けるので自分の書き込みの解決にならない。
- 閲覧者つきの応答に ETag と条件付き GET: 転送量が減るが、閲覧者ごとの ETag の計算が要り、TanStack Query のキャッシュと二重になる。
- 更新をすべての変更でトーストする: 利用者の知らない読み直しがなく、版が変わったことが見えるが、デプロイのたびにトーストが残り、「操作で反映」は開いたままのタブにしか効いていなかった。
- 次の起動だけで適用し何も出さない: 失うものがないが、開いたままのタブが古いまま何週間も動き、API の変更で壊れても理由が分からない（既定としては採り、§11・§12 を足した）。
- 隠れたタブや画面遷移で安全なら黙って読み直す: 開いたままのタブも更新されるが、読んでいた位置を失い（検知の精度では解決しない）、読み直しは worker を入れ替えない。必要な更新にだけ使う。
- リリースのときと必要なときだけトースト: 大きな変更だけ知らせられるが、`main` を動かす運営者には区別がなく、版の情報をビルドに戻すことになる（#2020 と逆行）。知らせたいのは機能で、更新の仕組みの役割ではない。
- すぐ `skipWaiting`（`autoUpdate`）: 最も単純で常に最新だが、入力中に読み直され、他のタブのチャンクが消える。

## Consequences（影響）

- 書き込みを書く人は「何が変わり得るか」に印を付けるだけでよく、自分の書き込みのあとに開いた画面は最初の描画から書き込みを反映する。
- 印の付いた画面を開くと、取り直しが終わるまでいまの画面が残る（`defaultPendingMs` を過ぎると保留の表示）。印の付いた無限スクロールの一覧は、読み込んだページを全部取り直してから描画するので、奥まで読んだ一覧ほど待つ。
- 他のタブ・端末の書き込みは、`staleTime` を過ぎて画面を開き直すまで出ない。匿名の訪問者は、公開の一覧を最大 60 秒古く見ることがある（CDN とブラウザのキャッシュ）。
- 削除・処分されたローカルのメディアは、ブラウザ・CDN・Service Worker のキャッシュに残り得る（`immutable`、Service Worker は最大 30 日）。消すのは CDN の削除依頼など運用の範囲で、この ADR では決めない。
- デプロイの頻度と割り込みが切り離され、タブごとに週 1 回が上限になる。読み直しの判断の誤りが効くのは必要な更新のときだけで、新しい画面は既定で安全でない側に倒れる。タブが別の版でも互いのチャンクを消さず、どのホスティングでも同じに動く（サーバーに要るのは定数のヘッダだけ）。
- 開いたままのタブは最長 7 日、利用者が閉じ続ければそれ以上古い。バグ修正は読み直すまで届かない。
- タブを常に 2 つ以上開く人で、古いタブが残る間は worker が古いまま。オフラインの外枠とプッシュの処理が遅れて更新される（§14 が前提）。
- `webClientEpoch` は人が上げる。上げ忘れると API の失敗が読み直すまで続く。
- 必要な更新の読み直しでは、読むための画面の読んでいた位置を失う。ルートごとの宣言が増える。
- 「新しい版があります」をほとんど見なくなるので、変更を知らせる手段にはならない。リリースノートやお知らせが受け持つ。
- Tauri モバイルの成熟度リスクを v0 では負わず、UI・i18n・API クライアントの実装は 1 つで済む。

## Open Questions / 要検証

- 投稿のカード画像を生成するか（CJK フォントでバイナリが 10〜20 MB 増える。CPU コスト）
- oEmbed を提供するか
- #31 Spike: Tauri 2 で Web クライアントをラップし、iOS / Android で APNs / FCM のリモート Push を受信できるか（公式プラグインがなくコミュニティ製に依存する点は要検証。v0 の後に回す）
- 印の付いた無限スクロールの一覧を、読み込んだ全ページでなく最初のページから取り直すか（ホームの「N 件の新しい投稿」と同じく先頭のページだけにする。戻ったときのスクロール位置との兼ね合い）
- Web Locks のロックは、タブが閉じたり破棄されたりすると解放される想定である（MDN の該当ページには明記がない。実機のブラウザで確かめる）。解放されない場合の影響は、worker の入れ替えが遅れるだけである。
- 7 日の閾値は実運用の感覚で決める数字で、rc で確かめられない。`v0.1.0` の運用で見直す。
