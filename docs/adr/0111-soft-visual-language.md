# ADR-0111: 見た目の言語: 柔らかい面を、操作の手がかりを保って採る

- Status: Accepted
- Date: 2026-10-28
- Deciders: @rosylilly
- Issue: #1638

## Context（背景・課題）

ADR-0110 の体験の原則のうち、決定者は「楽しい」UI の見た目として、ニューモフィズム（Neumorphism、Soft UI）による柔らかな印象と洗練された部品を挙げた。
今の見た目の言語（[app/ui/README.md](../../app/ui/README.md) の「Shape, elevation and states」）は、クリームとココアの色、ボタンとバッジの丸い形（pill）、
角丸の大きいカードを持つが、「境界を先に」（カードは 1px の `border` と、ほとんど見えない `shadow-card` で区別する）を方針にしている。

ニューモフィズムは、背景と同じ色の面を、明るい影と暗い影の組で浮かせたりへこませたりする表現である。そのまま採ると次の問題がある。

- **操作の手がかり（シグニファイア）が弱まる**: 押せる面と押せない面の違いが影だけになり、ADR-0110 の P1（迷わない）とぶつかる。
- **品質ゲートに通らない**: WCAG 2.2 の 1.4.11（操作の部品の境界と背景のコントラスト 3:1）は、ADR-0027 の axe とコントラストの検査で毎 PR 測っている。
  背景と同じ色の面と弱い影では、この比に届かない。
- **テーマに追従しない**: ADR-0059 で管理者は色・角丸・影のトークンを上書きできる。明暗の影の色は面の色に合わせて調整したもので、背景色を変えると崩れる。ダークモードでも同じことが起きる。
- **強制カラーモードで消える**: 影は強制カラーモードで描かれないので、影だけで作った境界は消える。

## Decision Drivers（判断基準）

1. 操作の手がかりとコントラスト（WCAG 2.2 AA、NFR-A11Y-1、ADR-0110 の P1）を下げないこと。
2. 決定者が求める柔らかな印象と、部品の洗練を出すこと。
3. サーバーのテーマ（ADR-0059）とダークモードで崩れないこと。
4. トークンと部品の変更だけで画面全体に効き、`app/web` の変更が要らないこと（A4）。

## Considered Options（選択肢）

1. **ニューモフィズムを全面的に採る**: 面・ボタン・入力欄を背景と同じ色にし、明暗の影の組で形を作る。
2. **柔らかい面を、場所を限って採る**: 柔らかい影と面の段差、大きな角丸、入力欄の内側の影を使う。操作の部品の境界とコントラストは今のまま保つ。
3. **今の見た目の言語を保つ**: 「境界を先に」を変えない。

## Decision（決定）

**選択肢 2 を採る。** 柔らかさは「面」と「影」で出し、「操作できること」は色と境界で示す。

### 1. 柔らかさを出すところ

- **面の段差**: 画面の背景（`surface`）、区画（`surface-raised`）、へこんだ面（`surface-sunken`）を、柔らかい影の組で分ける。
  カードと設定のまとまりは、明暗の 2 つの影でわずかに浮かせる。
- **入力欄**: テキストの欄・選択・トグルの溝は、内側の影でへこみとして描く。ただし境界は 1.4.11 の 3:1 を満たす線か色の差で残す。
- **押した状態**: ボタンを押している間（`data-pressed`）は、浮いた面からへこんだ面に変える。P2（操作に必ず応える）のマイクロインタラクションとして、`duration-fast` と `ease-standard` で移す。
- **角丸**: 今の段階（`radius-*`）を保つ。柔らかさのために大きくするのは区画とカードだけにする。

### 2. 保つところ

- **主な操作のボタンは色で塗る**（`accent`）。影だけのボタンにしない。
- **操作の部品の境界は 3:1 を保つ**。影はそれに足す飾りで、境界の代わりにしない。強制カラーモードでは今の `border` と `outline` が残る。
- **フォーカスの輪**（`focus-ring`）は今のまま。

### 3. トークンとテーマ

- 明暗の影の組は、新しい影のトークン（例 `--elevation-soft-raised`・`--elevation-soft-inset`）にする。値は面の色のトークンから CSS の相対色（`oklch(from var(--color-surface) …)`）で
  明るさだけを変えて作り、面の色を上書きしたテーマでも追従させる。
  相対色は Chrome 119・Firefox 128・Safari 16.4 から使え、そろったのは 2024 年 7 月で、`theme.css` がすでに使う `light-dark()`（Baseline 2024、5 月）とほぼ同じ時期である
  （2026-10-28 に [MDN の light-dark()](https://developer.mozilla.org/en-US/docs/Web/CSS/color_value/light-dark) と [MDN の相対色](https://developer.mozilla.org/en-US/docs/Web/CSS/CSS_colors/Relative_colors) で確認）。
  対応しないブラウザでは `@supports (color: oklch(from white l c h))` で分け、今の影（`--elevation-*`）に戻す。
- **ダークモード**では、暗い面の上の明るい影は目立たず濁るので、明るい側の影を使わない。浮いた面は、面の上端の内側の 1px の明るい線（`inset 0 1px 0`）と暗い影で、
  へこんだ面は内側の暗い影だけで描く。ライトとダークの値は `light-dark()` で 1 つのトークンにまとめる。
- 影のトークンは ADR-0059 の上書きできるトークンに入る。新しいトークンは生成器の一覧に足す。
- 品質ゲート（ADR-0027）のスクリーンショットとコントラストの検査は、既定のテーマで、ライトとダーク、強制カラーモードで行う。

### 見直す条件

- 試作の部品（ボタン・入力欄・カード・設定のまとまり）で、柔らかい面が今の見た目と比べて決定者の意図に届かないと分かった場合（選択肢 1 の要素を足す前に、コントラストの扱いを別に決める）。
- 相対色で作った影が、サーバーのテーマで実用的な見た目にならない場合（影の組を、テーマの上書きの値として管理者が直接指定する形にする）。
- 試作で、ダークモードの浮いた面が段差として読めない場合（ダークモードでは柔らかい面をやめ、今の境界と影に戻す）。

## Consequences（影響）

- 良い影響: トークンと `@my/ui` の部品の変更だけで、すべての画面が柔らかい見た目になる。
- 良い影響: 押したときに面がへこむことが、P2 のマイクロインタラクションの共通の型になる。
- 悪い影響: README の「境界を先に」の方針を書き換え、すべての部品のスクリーンショットの基準画像が変わる。
- 悪い影響: 影が増えるので、低性能の端末で長い一覧（タイムライン）のスクロールが重くなるおそれがある。一覧の項目には影を付けない。
- 後続の作業（issue にする）:
  - 試作: ボタン・入力欄・カード・設定のまとまりのストーリーを、ライトとダークで今の見た目と並べ、PR のプレビュー（ADR-0112）で決定者が選ぶ。
  - 影のトークンの追加、生成器・ADR-0059 の上書きの一覧への追加、app/ui/README.md の「Shape, elevation and states」の書き換え。

## Pros and Cons of the Options（詳細比較・任意）

- **選択肢 1（全面）**: 印象の変化がいちばん大きく、決定者の挙げた見た目にいちばん近い。ただし 1.4.11 と強制カラーモード、サーバーのテーマで崩れ、ADR-0110 の P1 とぶつかる。
- **選択肢 3（今のまま）**: 費用がなく、アクセシビリティの検査も通っている。ただし決定者の求める柔らかさと洗練が出ず、のっぺりした印象が残る。
