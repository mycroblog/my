# ADR-0125: お知らせ: タイトル・通知・一覧と個別のページ・PC の右帯

- Status: Accepted
- Date: 2026-10-30
- Deciders: @rosylilly
- Issue: #1869, #1933

## Decision（決定）

### 1. タイトル

- お知らせの版に `title`（書記素で 1〜100。必須。プレーンテキスト）を持つ。本文と同じく変えるたびに版を記録する。
- v0.1.0 の前なので、既存のお知らせのタイトルは移さない（ADR-0023）。
- 一覧・右帯・通知・Web Push はタイトルを見出しに使い、本文は詳しい表示で出す。

### 2. 通知

- 通知の種類 `announcement`。受け取る人はローカルの利用者全員（凍結・削除済みを除く）。差出人を持たず、`announcement_id` を持つ。
- お知らせが利用者に見え始めた時（公開の操作の時と、期間の始まり `starts_at` の遅いほう。`ShowsFrom`）に作る。
  - 公開のトランザクションで、ジョブ（`instance.notify_announcement`、冪等キーはお知らせ）を `ShowsFrom` の時刻に動くよう積む。期間の始まりを変える版は、新しい時刻のジョブを積み直す。
  - ジョブは、動いた時点でお知らせが公開中で、期間の中にあり、`ShowsFrom` を過ぎているときだけ、ローカルの利用者を 100 件ずつ通知する（そうでなければ何もしない）。`dedupe_key` は `announcement:<announcement_id>` で、お知らせと受け取る人ごとに 1 つ。
  - 公開後の変更（本文・タイトル）では通知し直さない。
- 取り下げたお知らせと期間の終わったお知らせの通知は、読み取り時に隠す。
- ADR-0086 §9 の表では「インスタンスから利用者への知らせ」の区分に 1 行として入れるが、この区分のほかの行と違い、アプリ内は **選べる・既定オン** にする。Web Push は選べる。メールでは送らない（メールのセルを出さない）。
- 通知と Web Push はタイトルを出し、押すとそのお知らせの個別のページ（§5）を開いて既読にする。

### 3. 過去のお知らせの一覧

- 一覧のページ（`/announcements`）は、見え始めたことのあるお知らせ（公開中で `ShowsFrom` を過ぎたもの。期間の終わったものを含む）を `ShowsFrom` の新しい順に出す。取り下げたお知らせは出さない（取り下げは誤りを消すための操作なので）。
- 今見えているお知らせには未読の目印と既読にする操作を付け、期間の終わったお知らせには終わったことを示す。
- クライアント API は、期間の終わったものを含む一覧（`GET /announcements/history`、ページングあり）を持つ。`GET /announcements`（今見えているものだけ・ページングなし）も残す。

### 4. 画面の幅ごとの置き場所

- `xl` 以上（右帯のある幅）: 右帯の最上段（通話のルームの上）にお知らせの区画を置き、今見えているお知らせのタイトルを未読を先に並べ、一覧のページへのリンクを置く。この幅ではホームの上に出さない。右帯はどの画面にもあるので、ホーム以外を開いていても見える。
- `xl` 未満（右帯のない幅）: ホームのタイムラインの上に未読のお知らせを出し、一覧のページへのリンクを置く。
- メニューのシートに「お知らせ」（`/announcements`）を置く。画面の要件（L1）は `docs/architecture/web-client/screens/` に書いてから作る。

### 5. お知らせの個別のページ

- `/announcements/{id}` はログインした利用者のページで、一覧（`GET /announcements/history`）に出るお知らせ（公開中で `ShowsFrom` を過ぎたもの。期間の終わったものを含む）を読める。下書き・取り下げ・始まる前・不明なものは 404 で、ページは見つからないことを言って一覧へのリンクを出す。
- 通知・Web Push・右帯と一覧のタイトルはここへ向ける。開くと既読にする（§2）。行き先で開いた経路を区別しないので、タイトルから開いたときも既読にする。
- 一覧のページに `?id=` は持たない（v0.1.0 の前なので互換を残さない。ADR-0023）。

### この決定を見直す条件

- ローカルの利用者が多く、お知らせ 1 件の通知のジョブが長く掛かるとき（通知の行を作らずに読み取り時に合成する方式を検討する）。

## 経緯

サーバー全体へのお知らせ（FR-726）は、Markdown の本文と表示の期間だけを持ち、公開中で期間の中にあるものを Web のホームのタイムラインの上に未読の目印付きで出していた。開いていない利用者には届かず、期間が終わると読み返せず、PC の幅でもホームを開かない限り目に入らなかった。そこで、タイトル・利用者が止められる通知・過去の一覧・幅ごとの置き場所を決めた（スマホ幅はホームの上部のまま）。

判断の基準は、アプリを開いていない利用者にも Web Push で届くこと、取り下げたものや期間の始まっていないものを通知や一覧で見せないこと、既存の版と状態の表（data-model §4.9）を生かすことである。

当初、通知と Web Push の行き先は一覧のページのそのお知らせ（`/announcements?id=`）だった。1 つのお知らせに変わらないアドレスを持たせ、古いお知らせでも一覧を読み進めずに開け、取り下げられたものを開いたときにそのことがはっきり分かるように、個別のページを足して行き先をそちらへ移した。

## 採らなかった案

- 公開の操作の時に通知する: 予約したジョブが要らないが、期間の始まりが先のお知らせは、まだ見えないのに通知が届き、押しても何も出ない。
- 過去の一覧に取り下げたものも含める: 履歴として完全だが、誤って出したお知らせを消す手段がなくなる。
- PC で右帯とホームの両方に出す: 置き場所が幅で変わらないが、同じお知らせが 2 か所に出て、ホームの一覧が下に押される。
- 個別のページを足すが、通知と Web Push は一覧のページのそのお知らせのままにする: 通知から開いて目的のお知らせだけをすぐ読めない。

## Consequences（影響）

- 良い: アプリを開いていない利用者にも Web Push で届き、止めたい人は通知の設定で止められる。
- 良い: 期間の終わったお知らせも読み返せる。
- 良い: 一覧のページに、目的のお知らせを探して読み進める処理と取り下げの注記が要らない。
- 悪い: お知らせ 1 件ごとにローカルの利用者の数だけ通知の行ができる。
- 悪い: 「インスタンスから利用者への知らせ」の区分に、アプリ内を止められる行が 1 つだけ混ざる。
- 悪い: 幅によってお知らせの場所が変わる（`xl` の境で右帯とホームの上が入れ替わる）。
- 通知と Web Push で開いたお知らせが取り下げられていても、その 1 件について見つからないと言える。ただし取り下げと不明なアドレスは区別しない（どちらも 404）。
- 一覧のタイトルを押すだけで既読になる。
