# ADR-0125: お知らせのタイトル・通知・一覧の画面と PC の右帯

- Status: Proposed
- Date: 2026-10-30
- Deciders: @rosylilly
- Issue: #1869

## Context（背景・課題）

サーバー全体へのお知らせ（FR-726）は、Markdown の本文と表示の期間だけを持ち、公開中で期間の中にあるものを Web のホームのタイムラインの上に未読の目印付きで出す。
新しいお知らせはストリームで届くが、開いていない利用者には届かない。期間が終わったお知らせは API にも画面にも出ず、後から読み返せない。
PC の幅でも、ホームを開かない限りお知らせは目に入らない。

決定者の要望と回答（原文。問い → 答え）:

> お知らせ一覧とお知らせ表示位置の調整 → 新規お知らせは通知がくるように。過去のお知らせ一覧を見るページを追加。PC ビューではタイムライン右にお知らせ一覧を表示。お知らせにタイトルを設定できるようにする
> 新しいお知らせの通知は、利用者が止められるようにしますか？スマホ幅ではお知らせをどこに出しますか？ → 止められる・スマホはホーム上部

決める必要があるのは、タイトルの形、通知を作る時点と相手、通知の設定の区分（ADR-0109 §2）、過去のお知らせに含めるもの、画面の幅ごとの置き場所である。

## Decision Drivers（判断基準）

1. 新しいお知らせが、アプリを開いていない利用者にも届く（Web Push）
2. 利用者が通知を止められる（決定者の回答）
3. 取り下げたお知らせや、まだ期間の始まっていないお知らせを通知や一覧で見せない
4. 一覧でお知らせを見分けられる（タイトル）
5. 既存の版と状態の表（data-model §4.9）を生かす

## Considered Options（選択肢）

- 通知を作る時点: A1 利用者に見え始めた時（公開と期間の始まりの遅いほう） / A2 公開の操作の時
- 過去のお知らせ: B1 見え始めたことのあるお知らせ（期間の終わったものを含み、取り下げたものを除く） / B2 取り下げたものも含むすべて
- PC の置き場所: C1 `xl` の右帯の最上段にお知らせの区画を置き、その幅ではホームの上から外す / C2 右帯にもホームの上にも出す

## Decision（決定）

推奨案は **A1・B1・C1**。

### 1. タイトル

- お知らせの版に `title`（書記素で 1〜100。必須。プレーンテキスト）を足す。本文と同じく変えるたびに版を記録する。
- v0.1.0 の前なので、既存のお知らせのタイトルは移さない（ADR-0087）。
- 一覧・右帯・通知・Web Push はタイトルを見出しに使い、本文は詳しい表示で出す。

### 2. 通知

- 通知の種類 `announcement` を足す。受け取る人はローカルの利用者全員（凍結・削除済みを除く）。差出人を持たず、`announcement_id` を持つ。
- お知らせが利用者に見え始めた時（公開の操作の時と、期間の始まり `starts_at` の遅いほう。`ShowsFrom`）に作る（A1）。
  - 公開のトランザクションで、ジョブ（`instance.notify_announcement`、冪等キーはお知らせ）を `ShowsFrom` の時刻に動くよう積む。期間の始まりを変える版は、新しい時刻のジョブを積み直す。
  - ジョブは、動いた時点でお知らせが公開中で、期間の中にあり、`ShowsFrom` を過ぎているときだけ、ローカルの利用者を 100 件ずつ通知する（そうでなければ何もしない）。`dedupe_key` は `announcement:<announcement_id>` で、お知らせと受け取る人ごとに 1 つ。
  - 公開後の変更（本文・タイトル）では通知し直さない。
- 取り下げたお知らせと期間の終わったお知らせの通知は、読み取り時に隠す。
- ADR-0109 §2 の表では「インスタンスから利用者への知らせ」の区分に 1 行として入れるが、この区分のほかの行と違い、アプリ内は **選べる・既定オン** にする（決定者の回答）。Web Push は選べる。メールでは送らない（メールのセルを出さない）。
- 通知と Web Push はタイトルを出し、押すとそのお知らせ（一覧のページのそのお知らせ）を開いて既読にする。

### 3. 過去のお知らせの一覧

- 一覧のページ（`/announcements`）は、見え始めたことのあるお知らせ（公開中で `ShowsFrom` を過ぎたもの。期間の終わったものを含む）を `ShowsFrom` の新しい順に出す（B1）。取り下げたお知らせは出さない（取り下げは誤りを消すための操作なので）。
- 今見えているお知らせには未読の目印と既読にする操作を付け、期間の終わったお知らせには終わったことを示す。
- クライアント API に、期間の終わったものを含む一覧（ページングあり）を足す。今の `GET /announcements`（今見えているものだけ・ページングなし）は残す。

### 4. 画面の幅ごとの置き場所

- `xl` 以上（右帯のある幅）: 右帯の最上段（通話のルームの上）にお知らせの区画を置き、今見えているお知らせのタイトルを未読を先に並べ、一覧のページへのリンクを置く。この幅ではホームの上に出さない（C1）。右帯はどの画面にもあるので、ホーム以外を開いていても見える。
- `xl` 未満（右帯のない幅）: 今と同じくホームのタイムラインの上に未読のお知らせを出し、一覧のページへのリンクを足す（決定者の回答）。
- メニューのシートに「お知らせ」（`/announcements`）を足す。画面の要件（L1）は `docs/architecture/web-client/screens/` に書いてから作る。

### この決定を見直す条件

- ローカルの利用者が多く、お知らせ 1 件の通知のジョブが長く掛かるとき（通知の行を作らずに読み取り時に合成する方式を検討する）。

## Consequences（影響）

- 良い: アプリを開いていない利用者にも Web Push で届き、止めたい人は通知の設定で止められる。
- 良い: 期間の終わったお知らせも読み返せる。
- 悪い: お知らせ 1 件ごとにローカルの利用者の数だけ通知の行ができる。
- 悪い: 「インスタンスから利用者への知らせ」の区分に、アプリ内を止められる行が 1 つだけ混ざる。
- 悪い: 幅によってお知らせの場所が変わる（`xl` の境で右帯とホームの上が入れ替わる）。
- 後続の作業（Issue にする）:
  - FR-726 の文言、data-model §4.9（`title`）と §4.7（`announcement` の作り方）
  - サーバー: スキーマ・`internal/app/instance`・通知・管理 API とクライアント API・Web Push の `alerts`・`pkg/mykit`・CLI（お知らせを作るコマンドがあれば）
  - 画面の要件（L1）: お知らせの一覧のページ、右帯（09-app-shell）、ホーム、管理のお知らせの編集
  - Web: 上の画面と通知の行・通知の設定の行

## Pros and Cons of the Options（詳細比較・任意）

- A2（公開の操作の時に通知）: 予約したジョブが要らない。ただし期間の始まりが先のお知らせは、まだ見えないのに通知が届き、押しても何も出ない（判断基準 3 に反する）。
- B2（取り下げも含む）: 履歴として完全。ただし誤って出したお知らせを消す手段がなくなる。
- C2（右帯とホームの両方）: 置き場所が幅で変わらない。ただし PC で同じお知らせが 2 か所に出て、ホームの一覧が下に押される。
