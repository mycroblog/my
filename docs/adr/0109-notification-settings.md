# ADR-0109: 通知の経路と設定

- Status: Accepted
- Date: 2026-10-28
- Deciders: @rosylilly
- Issue: #1624

## Context（背景・課題）

通知（FR-205）は、アプリ内・Web Push（FR-206）・メールの 3 つの経路で届く。それぞれの設定は次のとおりで、まとまった設定の画面はない。

- アプリ内: すべての種類（`NotificationType`）が届き、利用者は絞れない。
- Web Push: 端末（ログインしたアプリ）ごとに、オン・オフと種類のグループを `/settings/preferences` の中で選ぶ（購読の `alerts`）。
- メール（[ADR-0086](0086-email-delivery.md)）: アカウントのメール（確認・パスワードの再設定・パスワードの変更の知らせ）、サポーターの通知（[ADR-0072](0072-supporter-plans-and-roles.md) §16）、サービスの終了（[ADR-0088](0088-service-shutdown-modes.md)）は必ず送る。
  モデレーター向けの通知（FR-712）は利用者設定 `email_moderator_notifications` で一括に選び、既定はオフ。フォロー・メンションなどの普段の通知はメールで送らない。
- 音: 鳴らす仕組みはない。

決定者は、通報が届いたら管理者にメールで知らせること、通知で音を鳴らすこと、Web Push だけ・メールだけを止めることを利用者が選べるべきだとし、今の設定の画面ではそれができないとした（#1624）。

## Decision Drivers（判断基準）

1. 利用者が、通知の種類ごとに、どの経路で受け取るかを 1 つの画面で選べる
2. モデレーターが、通報などを見落とさない（メールの既定）
3. メールが届きすぎない（アプリで読んだ通知はメールにしない）
4. お金とアカウントに関わる知らせは止められない
5. 既存の形（Web Push の端末ごとの購読、ADR-0086 の配信停止）を生かす

## Considered Options（選択肢）

- 画面: A1 専用の画面 `/settings/notifications` / A2 `/settings/preferences` の中で整理する
- 設定の形: B1 種類 × 経路の表 / B2 経路ごとの節に種類のチェックボックス
- 普段の通知のメール: C1 種類ごとに選べ、既定オフ / C2 まとめて送る（ダイジェスト） / C3 送らない
- アプリ内の絞り込み: D1 絞らない / D2 種類で絞る / D3 種類と相手で絞る
- 音: E1 アプリを開いている間に鳴らす / E2 Web Push の音も選べる / E3 入れない

## Decision（決定）

**A1・B1・C1・D2・E1 を採用する。**

決定者の回答（#1624、原文。問い → 答え）:

> 通知の設定はどこに置きますか？ → 専用画面を作る
> 普段の通知（フォロー・メンションなど）をメールでも送りますか？ → 送る・既定オフ
> 通知音はどうしますか？ → アプリを開いている間に鳴らす
> モデレーター向けのメール（通報など）の既定はどうしますか？ → 種類ごとに選べ、既定オン
> 設定の形はどうしますか？（アプリ内・Web Push・メール × 通知の種類） → 種類×経路の表
> アプリ内の通知を、種類や相手で絞れるようにしますか？ → 種類で絞れる
> 普段の通知のメールはいつ送りますか？ → すぐ送る・未読のものだけ
> サポーターのメール（支払いの失敗など）とサービス終了のメールは？ → 止められないまま
> ある種類を「アプリ内」でオフにしたとき、その通知はどうなりますか？ → 作らない（全経路で届かない）
> モデレーター向け、サポーター、サービス終了、凍結などのモデレーションの知らせも、アプリ内でオフにできますか？ → モデレーター向けもオフ可
> メールを送る前に未読を待つ時間は？ → 15 分・固定
> 通知音の設定の粒度は？ → 表に「音」の列を足す・端末ごと

### 1. 設定の画面

- 設定の中に「通知」（`/settings/notifications`）を置く。`/settings/preferences` の Web Push の節と `email_moderator_notifications` の項目はこの画面に移す。
- 画面の中心は表で、行が通知の種類のグループ（§2）、列が経路（アプリ内・Web Push・メール・音）。各セルはチェックボックス。
  - Web Push の列は、サーバーが Web Push を送り、この端末で使えるときだけ出す。この端末で受け取るかのスイッチは、今の Web Push の節と同じく表の上に置く。
  - メールの列は、サーバーがメールを送る（`Instance.sends_email`）ときだけ出す。主のアドレスにメールが届かない（`email_suppression`）ときは、列の上にその理由を出す。
  - 止められない経路のセルは、オンのまま操作できないものとして出す（§2 の「固定」）。
- アプリ内がオフの行では、Web Push・メール・音のセルを操作できないものとして出す（§3）。

### 2. 種類のグループと既定

行は今の Web Push のグループを引き継ぎ、次の 3 つに分ける。モデレーター向けは、その種類を受け取る権限を持つ人にだけ出す。サポーターの行は、サポーターの機能を出すクライアントにだけ出す（ADR-0072 §14）。

| 区分 | 行 | アプリ内 | Web Push | メール |
| --- | --- | --- | --- | --- |
| 普段の通知（ほかの利用者の行動） | `mention`、`follow`、`follow_request`、`follow_accepted`、`boost`、`favourite`、`reaction`、`quote`、`poll_closed`、`account_moved`、通話（`voice_room_started`・`voice_room_invited`） | 選べる・既定オン | 選べる | 選べる・既定オフ |
| モデレーター向け | `admin_report`、`admin_sign_up`、`admin_appeal`、`admin_webhook_disabled`、`admin_custom_emoji_request`、`admin_account_moved`、`admin_service_closure_due`、`admin_error_group`（種類ごとに 1 行） | 選べる・既定オン | 選べる | 選べる・既定オン |
| インスタンスから利用者への知らせ | モデレーション（`moderation_notice`・`report_resolved`・`appeal_decided`・`relationships_severed`・`custom_emoji_request_decided`）、`service_closure`、サポーター（`supporter_*`） | 固定（オン） | 選べる | `service_closure`・サポーターは固定（オン）、モデレーションは選べる・既定オフ |

- Web Push の既定は今と同じ（購読を作るときにクライアントが選ぶ）。
- 音は端末ごとの設定（§5）で、既定はすべてオフ。
- 新しい通知の種類を足すときは、この表のどの区分の、どの行に入れるかを決める。

### 3. アプリ内をオフにした種類

- アプリ内をオフにした種類の通知は作らない。作らないので、Web Push・メール・音のどれでも届かない。オフにする前の通知は消さない。
- モデレーター向けの種類をオフにしても、管理画面の未対応の件数（FR-712）は変わらない。件数は通知ではなく、通報や申請の状態から数える。
- インスタンスから利用者への知らせは、アプリ内で止められない。

### 4. 通知のメール

- 普段の通知とモデレーションの知らせのメールは、通知を作ってから **15 分後** に、次をすべて満たすときだけ 1 通ずつ送る。15 分は固定で、設定にしない。
  - 通知が未読のまま（既読の位置 `notifications_marker` より新しく、消していない）
  - 通知がまだ利用者に見える（Web Push の `stillShown` と同じ確認）
  - 利用者の設定で、その行のメールがまだオン
- モデレーター向けのメールは、今と同じく通知の作成と同じトランザクションでジョブを積み、すぐ送る。見落としを防ぐため、未読を待たない。
- 送り先は主のアドレス。確認していないアドレスと、届かなくなったアドレス（ADR-0086 §5）には送らない。
- 配信の停止（ADR-0086 §4）の区分は、メールの列の行と 1 対 1 にする。ワンクリックの配信停止は、そのメールの行のメールの設定をオフにする。
  これは ADR-0086 §4 の「区分は利用者設定の列と 1 対 1」「新しい表は作らない」を置き換える。設定は §6 の表に持つ。
- `service_closure`・サポーターのメールは、今と同じく取引のメールとして必ず送り、配信停止のリンクを付けない。アカウントのメール（確認・パスワード）も変えない。

### 5. 通知音

- Web クライアント（と Tauri のアプリ）は、開いている間に新しい通知をリアルタイム更新（FR-207）で受けたとき、その種類の行の音がオンなら音を 1 回鳴らす。音は組み込みの 1 種類で、選べない。
- 設定は端末ごとに、ブラウザの保存領域に持つ（サーバーには送らない）。表の音の列に加えて、全体を止めるスイッチを置く。既定はオフ。
- ブラウザが自動の再生を止めているときは鳴らさない。設定の画面に試しに鳴らすボタンを置き、そこで再生を許してもらう。
- 短い間に続けて届いたときは、まとめて 1 回だけ鳴らす。Web Push の通知の音は OS に任せる。

### 6. 設定の持ち方と API

- アプリ内とメールの設定は利用者ごとにサーバーに持つ。区分 `current-value` の表で、行は（利用者、種類、経路）。既定と違う値だけを持つかどうかは data-model に書くときに決める。
- `email_moderator_notifications` はこの表に置き換えて、なくす（v0.1.0 の前なので、ADR-0087 によりデータは移さない）。
- Web Push の設定は今の購読の `alerts` のまま（端末ごと）。
- クライアント API で、自分の設定を読んで変える。種類の一覧は、その利用者に出す行（権限とサポーターの機能による）を返し、クライアントはそれで表を作る。

### この決定を見直す条件

- 普段の通知のメールが多すぎるという声が目立つ場合は、まとめて送る（C2）を検討する。
- 特定の相手からの通知が問題になる場合は、相手による絞り込み（D3）を別の ADR で検討する。

## Consequences（影響）

- 良い影響: 通知の受け取り方が 1 つの画面で分かる。モデレーターは最初から通報などをメールで受け取る。アプリを開いている間に音で気づける。
- 悪い影響:
  - 通知を作るたびに、利用者の設定を読む。普段の通知のメールは、15 分後のジョブで未読を確かめる。
  - モデレーター向けのメールの既定がオンになるので、権限を付けた人に最初からメールが届く。運営者向けの文書にこれを書く。
  - ADR-0086 §4 の配信停止の区分を、利用者設定の列から通知の設定の表に変える。
- 後続の作業（Issue にする）:
  - サーバー: 設定の表と既定、アプリ内オフで作らない規則、普段の通知とモデレーションの知らせのメール（15 分後・未読のみ）と配信停止、モデレーター向けのメールの種類ごとの設定、`email_moderator_notifications` の置き換え、クライアント API、メールのテンプレート（`locales/en`・`locales/ja`）、data-model §4.7 と identity の表の更新、テスト
  - Web: `/settings/notifications`（表、Web Push の移設、メールの列、音の列と全体のスイッチ、試しに鳴らすボタン）、音の再生、`/settings/preferences` から移した項目の削除、`locales/en`・`locales/ja`、E2E
  - 文書: `docs/operations/email.md`（送るメールと既定）、`docs/operations/moderation.md`（モデレーター向けのメールの既定）、利用者向けの通知の案内

## Pros and Cons of the Options（詳細比較・任意）

- A2 は画面が増えないが、環境設定がさらに長くなり、通知の設定を探しにくい。
- B2 は経路ごとに分かりやすいが、同じ種類の設定が離れ、「メールだけ止めたい」の見通しが悪い。
- C2 はメールの数が減るが、まとめる間隔とテンプレートが要る。C3 はメールで気づきたい利用者に応えられない。
- D1 は簡単だが、アプリ内で要らない種類を止められない。D3 は相手の判定（フォロー・新しいアカウント）の設計が要る。
- E2 は Web Push の通知を無音にできるが、ブラウザと OS で振る舞いが揃わない。E3 は決定者の要望に応えない。
