# ADR-0158: 通知のポリシー（相手の条件による受け入れ・保留・破棄）とスレッドのミュート

- Status: Proposed
- Date: 2026-11-09
- Deciders: @rosylilly
- Issue: #2565

## Decision（決定）

推奨案。知らない相手からの通知は、利用者が条件ごとに選ぶ動作（受け入れる・保留する・破棄する）で振り分け、既定はすべて受け入れる。1 つのスレッドの通知は、ADR-0154 の会話を単位にミュートで止める。どちらも通知を作るときに 1 回だけ判定する。§1〜§6 がポリシー、§7 が保留した通知の受け入れ待ち、§8 がスレッドのミュート、§9 がデータの持ち方、§10 が API と画面である。

### 1. 条件

ポリシーの条件は Mastodon 4.3 以降の通知のポリシーと同じ 5 つとする。どれも通知の差出人（`source_account_id`）と受け取る人の関係、または差出人の事実で決まる。

| 条件 | 名前 | 当てはまるとき |
| --- | --- | --- |
| フォローしていない相手 | `not_following` | 受け取る人が差出人を承認済みでフォローしていない（承認待ちはフォローに数えない） |
| フォロワーでない相手 | `not_follower` | 差出人が受け取る人を承認済みでフォローしていない |
| 新しいアカウント | `new_account` | 差出人のアカウントができてから 30 日たっていない（§6） |
| 求めていない非公開の返信・メンション | `unsolicited_private_mention` | 種類が `mention` で、投稿の公開範囲が `direct`、かつ受け取る人が始めたやり取りへの返信でない（§6） |
| モデレーターが制限したアカウント | `limited_account` | 差出人本人かそのドメインに、制限 `unsolicited_reach`（`limit` の処分、data-model §5.2）がある |

- 30 日は固定で、設定にしない（Mastodon と同じ）。
- 受け取る人が承認済みでフォローしている差出人は、`not_following` 以外の条件のうち `not_follower`・`new_account`・`unsolicited_private_mention` に当てはまらないものとする。フォローは受け取る人自身が選んだ相手だからである（Mastodon も同じ）。`limited_account` はこの除外を受けない（§5）。
- 受け入れた差出人（§7）は、どの条件にも当てはまらない。

### 2. 動作と既定

- 動作は 3 つ。
  - **受け入れる**（`accept`）: 今と同じく通知の一覧に入れ、設定どおりに Web Push・メール・音で届ける。
  - **保留する**（`filter`）: 通知は作るが、一覧と未読数に入れず、差出人ごとの受け入れ待ち（§7）に置く。Web Push・メール・音・リアルタイム更新の通知の送り出しはしない。
  - **破棄する**（`drop`）: 通知を作らない。もとの行動（フォロー・メンション・お気に入りなど）はそのまま起きる。
- **すべての条件の既定は受け入れる** とする。既定のままなら、どの通知も今と同じに振る舞う。小さなサーバーは知らない人との交流を歓迎し、迷惑を受けた人が自分で絞る、という順にするためである。
- 1 つの通知に複数の条件が当てはまるときは、**当てはまった条件の動作のうち最も厳しいもの** を採る。厳しさの順は 破棄 > 保留 > 受け入れる。どの条件にも当てはまらなければ受け入れる。

### 3. ポリシーの対象の種類

- ポリシーは、ほかの利用者の行動から生まれる次の種類にだけ効く: `follow`、`follow_request`、`mention`、`boost`、`favourite`、`reaction`、`quote`、`voice_room_invited`。
- 次の種類は、利用者が自分で求めたもの（`follow_accepted`、`status`、`poll_closed`、`account_moved`、`voice_room_started`）か、インスタンスからの知らせなので、ポリシーの対象にしない。
- **モデレーター向けの通知（`admin_*`、FR-712）、処分と通報の知らせ（`moderation_notice`・`report_resolved`・`relationships_severed`・`custom_emoji_request_decided`）、異議申し立ての結果（`appeal_decided`・`hook_appeal_decided`）、そのほかのインスタンスからの知らせ（`service_closure`・`supporter_*`・`announcement`・`auto_delete_limit`）は、保留も破棄もしない。** 見落とすと利用者やサーバーが損をする知らせだからである。スレッドのミュート（§8）もこれらには効かない。
- `follow_request` を保留・破棄しても、フォローリクエストそのものはフォローリクエストの一覧に残る。止まるのは通知だけである。
- 新しい種類を足すときは、ADR-0086 §9 の表の区分と合わせて、ポリシーの対象かを決める。

### 4. 判定の時点と場所

- 通知は **作るときに 1 回だけ** 振り分ける。振り分けの結果（一覧か保留か）は通知の作成時の属性として記録し、後から変えない。ポリシーを変えても、作成済みの通知は振り分け直さない（受け入れ待ちを受け入れたときの扱いは §7）。
- 振り分けの判定は `internal/domain/notification` の 1 つの純粋な関数（条件の事実とポリシーから動作を返す）に置き、通知を作る唯一の経路（`internal/app/notification` の作成の処理）だけがそれを呼ぶ。API や連合のコードで判定を書き直さない。
- 作成時の判定は次の順に行う。前の段で作らないと決まれば後の段は見ない。
  1. 今ある作らない規則: 受け取る人がローカルでない、自分の行動、ブロック、`hide_notifications` 付きのミュート、ドメインのミュート、`unsolicited_reach` の除外（data-model §4.7）
  2. スレッドのミュート（§8）
  3. ポリシー（§1〜§3）
- 作成後のブロック・ミュート・投稿の削除で読み取り時に隠す規則（`notification_exclusions` ほか）は、保留した通知にも同じに効く。

### 5. 制限されたアカウントとモデレーションの規則

- 制限 `unsolicited_reach` は今と同じく、受け取る人が差出人をフォローしていなければ通知を作らない（§4 の 1 段め）。これはモデレーターの決定で、利用者のポリシーでは緩めない。
- そのため `limited_account` の条件が実際に当てはまるのは、受け取る人がフォローしている制限中の差出人である。この条件はフォローによる除外（§1）を受けず、制限された相手を、フォロー中でも保留・破棄したい利用者のためにある。既定の受け入れるは、今の振る舞いと同じになる。
- Mastodon 4.3 は、制限されたアカウントからフォローしていない人への通知を破棄から、このポリシーの保留（既定）に移した。`my` で同じにするかは Open Questions に置く。

### 6. 条件の事実の出どころ

- 条件の事実は、今の作成の処理と同じく、**イベントのトランザクションの中で各モジュールのアプリケーション層の公開 API を呼んで調べる**（ADR-0002 §1。data-model §4.7 が `graph` の `Follows`・`HidesNotifications`、`account` の `IsLocal`、ポート `ReachPolicy` で既にそうしている）。`notification` に他モジュールの事実の投影は作らない。
  - `not_following`・`not_follower`: `graph` の `Follows` を両方向に呼ぶ。
  - `new_account`: `account` の公開 API で差出人のアカウントの作られた時刻を得る。ローカルのアカウントは登録の時刻、リモートのアカウントは Actor の `published` があればそれ（未来の時刻なら無視する）、なければこのサーバーが初めて知った時刻（`accounts.created_at`）とする。今の `accounts` は `published` を持たないので、`account` に足す（後続の作業）。
  - `unsolicited_private_mention`: `content` の公開 API で、メンションの投稿の会話（ADR-0154）に、受け取る人の書いた `direct` の投稿で差出人をメンションしたものがあるかを調べる。あれば受け取る人が始めたやり取りへの返信として扱う。
  - `limited_account`: 今のポート `ReachPolicy`（`moderation.AccountPolicy` の `UnsolicitedReachRestricted`）。
- 投影にしない理由: outbox 経由の投影は通知のイベントより遅れることがあり、フォローの直後のメンションを誤って保留する。同じトランザクションで呼べば、通知のイベントの時点の事実で判定でき、再構築も要らない。同期の呼び出しが通知の作成を遅くすると測れたときだけ、投影を検討する（見直す条件）。

### 7. 受け入れ待ち（保留した通知）

- 保留した通知は **差出人ごとの受け入れ待ち**（リクエスト）にまとめる。1 つの受け入れ待ちは（受け取る人、差出人）で、件数・最新の通知・差出人を出す。
- 一覧と未読数には入れない。受け入れ待ちの数（差出人の数と通知の数）を別に返し、通知の画面の先頭に「N 人からのリクエスト」の行として出す。
- 保留した通知では、Web Push・メール（ADR-0086 §11）・音（ADR-0086 §12）を送らない。リアルタイム更新では通知を流さず、受け入れ待ちの数が変わったことだけを流す。後で受け入れても、過去の通知は送らない。
- **受け入れる**: その差出人の保留した通知を一覧に戻し、以後その差出人を受け入れた相手（§1）として扱う。一覧に戻した通知は既読の位置より新しければ未読に数える。
- **閉じる**（dismiss）: その時点までの保留した通知を受け入れ待ちから外し、一覧にも出さない。差出人は受け入れない。後から新しく保留した通知が来れば、受け入れ待ちはまた出る。
- 受け入れを取り消す操作は v0 では置かない。止めたくなった相手は、ミュートかブロックで止める。

### 8. スレッドのミュート

- スレッドのミュートは **ADR-0154 の会話**（安定した ID を持つリソース）を単位にする。利用者は自分が見られる投稿からその会話をミュートし、ミュートを解除できる。期限は付けない。
- ミュートは **自分の投稿のスレッドにも効く**。
- ミュートした会話について、次の通知を作らない（破棄）。
  - `mention`（返信を含む）: メンションした投稿がその会話にあるとき
  - `boost`・`favourite`・`reaction`: 対象の投稿がその会話にあるとき
  - `quote`: 引用された投稿がその会話にあるとき
  - `status`（購読した相手の新しい投稿）: 新しい投稿がその会話にあるとき
- ミュートしても、会話の投稿はタイムラインにそのまま出る。止まるのは通知だけである。
- ミュートは作成時の判定だけに効き、ミュートする前の通知は隠さない。解除しても、ミュート中に起きたことは通知にならない（`hide_notifications` 付きのミュートと同じ）。
- 会話が併合されたとき（ADR-0154 §3 の `content.conversation_merged`。outbox で届く）は、`notification` のハンドラが、併合された会話のミュートを併合先へ移す。両方をミュートしていれば 1 つにする。同じイベントを何度処理しても結果は同じにする。
- 移すまでの間も漏れないよう、作成時の判定は、投稿の会話（併合先をたどった先）と、そこへ併合された会話のどれかのミュートを見る（`content` の公開 API で引く）。
- 投稿の API は、見ている人がその投稿の会話をミュートしているかを返す（`notification` の公開 API で調べる）。

### 9. データの持ち方

ADR-0020 の分類に従い、`notification` モジュールが所有する。テーブルとカラムの名前は data-model §4.7 に書くとき（#2566・#2567）に決める。

| 内容 | 分類 | 持つもの |
| --- | --- | --- |
| ポリシー | 現在値 | （利用者、条件）ごとの動作。行が無ければ既定の受け入れる |
| 通知の振り分け | イベント（`notifications`）の作成時の属性 | 一覧か保留か。作成後に変えない |
| 受け入れた差出人 | リソース | （受け取る人、差出人）と作った時刻 |
| 受け入れ待ちを閉じたこと | イベント | （受け取る人、差出人）と、閉じた時点の最新の保留した通知 |
| 受け入れ待ちの一覧 | 投影 | （受け取る人、差出人）ごとの件数と最新の通知。上の 3 つから再構築できる |
| スレッドのミュート | 現在値 | （利用者、会話）と作った時刻。会話の併合で行を移す |

- 状態を NULL 可の時刻で表さない。保留した通知が一覧に出るかは、受け入れた差出人の行があるかを読み取り時に見て決める。
- アカウントの消去（data-model §8）は、そのアカウントが受け取る人か差出人のポリシー・受け入れ・閉じたこと・ミュートの行を消す。

### 10. API と画面

- クライアント API（ADR-0016 の独自の API）で、自分のポリシーの読み書き、受け入れ待ちの一覧・1 件・その通知の一覧・受け入れる・閉じる、受け入れ待ちの数、会話のミュートと解除を出す。`pkg/mykit` にも足す。
- 通知の設定の画面（ADR-0086 §8）に、条件ごとに 3 つの動作を選ぶ節を置き、それぞれの動作が何をするかを画面に書く。投稿のメニューに「このスレッドをミュート」を置く。
- 文言は `locales/en` と `locales/ja` に足す（ADR-0009）。

### 見直す条件

- 同期の呼び出しで通知の作成（とくにフォロワーの多い人の投稿の `status` の展開）が遅くなると測れたら、条件の事実を `notification` の投影にすることを検討する
- 既定の受け入れるのままでスパムや嫌がらせの報告が目立つようになったら、`unsolicited_private_mention` などの既定を保留にすることを検討する
- 受け入れの取り消しや、受け入れた相手の一覧を求める声が強ければ、その操作を足す
- 期限付きのスレッドのミュートを求める声が強ければ、期限を足す

## 経緯

FR-205 の通知と FR-210（ADR-0086 §8〜§13）の設定は、通知の種類ごとに経路を選ぶだけで、相手によって絞れず、スレッド単位でも止められなかった。ADR-0086 の見直す条件は、相手による絞り込みを別の ADR で検討するとしていた。今あるのは、ブロック・ミュート・ドメインのミュートと、モデレーションの制限 `unsolicited_reach` による作らない規則だけである（data-model §4.7）。

決定者は、条件を Mastodon と同じ 5 つにし、動作を受け入れる・保留する・破棄するの 3 つ、既定をすべて受け入れるとし、スレッドのミュートを会話（milestone Conversations、ADR-0154）を単位にして自分のスレッドにも効かせると決めた。残りの、最も厳しい動作を採ること、保留した通知の扱い、インスタンスからの知らせを絞らないこと、作成時の判定、ミュートの範囲は推奨案である。

Mastodon との比較（2026-11-09 に [API の文書](https://docs.joinmastodon.org/methods/notifications/)と `main` の [`notify_service.rb`](https://github.com/mastodon/mastodon/blob/main/app/services/notify_service.rb)・[`notification_policy.rb`](https://github.com/mastodon/mastodon/blob/main/app/models/notification_policy.rb)・[`notification.rb`](https://github.com/mastodon/mastodon/blob/main/app/models/notification.rb) で確認）:

- 4.3.0 で `GET/PUT /api/v2/notifications/policy` を足した。条件は `for_not_following`・`for_not_followers`・`for_new_accounts`（30 日）・`for_private_mentions`・`for_limited_accounts` で、値は `accept`・`filter`・`drop`。`main` には `for_bots` もある。
- 既定は `for_private_mentions` と `for_limited_accounts` が `filter`、ほかが `accept`。`my` は決定によりすべて `accept` とする。
- 判定は破棄の条件を先に、保留の条件を後に見るので、結果として最も厳しい動作が勝つ。フォローしている相手は条件から外れ、非公開のメンションは、受け取る人が差出人をメンションした `direct` の投稿への返信（先祖を 100 件までたどる）なら外れる。受け入れた相手（`NotificationPermission`）はすべての条件から外れる。運営からのメンションも外れる。
- ポリシーの対象は `mention`・`reblog`・`follow`・`follow_request`・`favourite`・`quote`（と `added_to_collection`）で、`poll`・`moderation_warning`・`severed_relationships`・`admin.*` などは対象外。保留した通知は Web Push もメールも送らない。
- 受け入れ待ち（`/api/v1/notifications/requests`）は差出人ごとで、受け入れるとその人の保留した通知を一覧に戻し（後ろのジョブで行い、`notifications_merged` を流す）、以後を受け入れる。閉じると受け入れ待ちの数から外れる。
- 会話のミュートは通知の作成時に、対象の投稿の会話で破棄する規則の 1 つである。

## 採らなかった案

- **条件の事実を `notification` の投影にする**（Issue の推奨案）: 他モジュールを呼ばずに済み、作成の処理が自分のテーブルだけで閉じる。だが outbox の遅れで判定が事実とずれ、フォロー（両方向）とアカウントの時刻を写す投影は大きく、再構築も要る。今の作成の処理が既に同期の公開 API で判定しているので、合わせた。
- **ポリシーを変えたら作成済みの通知を振り分け直す**: 設定の変化がすぐ目に見える。だが通知はイベントで、振り分けを読み取り時に毎回計算すると一覧と未読数のクエリが条件の事実に依存し、事実が後から変わる（相手がフォローを外す、30 日を過ぎる）たびに過去の通知が出入りする。
- **当てはまった条件のうち最も緩い動作を採る**: 受け入れる条件が 1 つでもあれば届くので、見落としが無い。だが破棄を選んだ条件が別の条件の受け入れで無効になり、利用者が選んだことが効かない。
- **保留した通知を Mastodon のように `mention` と `quote` だけ受け入れ待ちにする**: 受け入れ待ちが会話の始まりに絞られる。だが保留したフォローやお気に入りがどこにも見えなくなり、受け入れても戻る先が分からない。すべての種類を差出人ごとにまとめる。
- **`for_bots` の条件を足す**: ボットのアカウントの通知を絞れる。決定は Mastodon 4.3 の 5 つで、`actor_type` で判定はできるので、要望が出たら足す。
- **運営からのメンションを条件から外す**（Mastodon）: モデレーターが利用者に確実に連絡できる。`my` では処分の知らせ（`moderation_notice`）が保留されないので、運営の私信を特別に扱う必要は小さい。
- **スレッドのミュートで投稿もタイムラインから隠す**: 見たくないスレッドを消せる。だがスレッドから離れずに通知だけを止めたい、という目的を越え、アカウントのミュートと役割が重なる。
- **スレッドのミュートを `notifications` の読み取り時の除外にする**（アカウントのミュートの後からの隠し方と同じ）: ミュートの前の通知も消える。だが会話の ID を通知ごとに引くクエリが要り、解除で過去の通知が戻るのは止めた意図に合わない。

## Consequences（影響）

- 既定のままなら今と同じに振る舞い、迷惑を受けた人だけが絞る。Mastodon の利用者に分かる条件と動作の名前になる。
- 判定が作成時の 1 か所の純粋な関数にまとまり、テストしやすい。インスタンスからの知らせは保留も破棄もされない。
- 通知の作成に同期の呼び出しが増える（`graph` の逆向きの `Follows`、`account` の時刻、`content` の会話）。フォロワーの多い人の投稿の展開で効くので、測る。
- `limited_account` は、今の `unsolicited_reach` を残す限り、フォローしている制限中の相手にしか当てはまらず、効く場面が狭い。
- `new_account` は、`published` を送らないリモートのアカウントを、このサーバーが初めて知った日から数えるので、古いアカウントを新しいと誤ることがある。
- スレッドのミュートは ADR-0154 の会話に依存し、会話の併合に追従するハンドラが要る。`unsolicited_private_mention` の判定も ADR-0154 の会話を使う。
