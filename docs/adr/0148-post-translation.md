# ADR-0148: 投稿の翻訳

- Status: Accepted
- Date: 2026-11-05
- Deciders: @rosylilly
- Issue: #2229

## Decision（決定）

[この決定を見直す条件](#この決定を見直す条件) に当たれば覆る。要件は FR-120 と FR-727 である。

翻訳するのは利用者の投稿で、UI の翻訳（ADR-0009）とは別のものである。

### 1. LLM は提供元にしない

LLM を翻訳の提供元にしない。どの版でも同梱しない。

投稿はだれでも書けるので、翻訳の入力がプロンプトインジェクションの経路になる。サニタイズが守るのは HTML だけで、原文にない文を翻訳として見せることは止められない。読者は翻訳を原文が言っていることとして信頼する。

`my` が運営者のプラグインの中身を確かめることはできないので、プラグインで LLM を使うのは運営者の責任である（§14）。

### 2. 構成

- ポートは `internal/app/translation` に置き、アダプタは `internal/adapter/translator/<提供元>/` に置く。すべて `pkg/testkit` の 1 つのコントラクトテストを通す。
- ポートは小さく保つ。受け取るのは断片の列・原文の言語（`und` があり得る）・翻訳先の言語で、返すのは訳の列と検出した言語である。エラーは一時的な失敗・提供元が報告した上限・対応しない言語の 3 つを区別する。提供元に固有の選択肢は持たない。
- 提供元の名前・リンク・ロゴはポートの外の登録情報に置く（§15）。
- `v0.1.0` の前に作るのは、ポートと fake、サービス・キャッシュ・API、設定と上限、Web クライアント、ブラウザの内蔵翻訳（§12）、通報の画面（§13）、ポートのプラグインへの委譲（§14、ADR-0146）である。サーバー側の提供元のアダプタ（LibreTranslate・DeepL・Google Cloud Translation・Amazon Translate）は作らず、タグの後に足す（§15）。ポートのプラグインへの委譲（#2217）はこれらを待たない。

### 3. 既定はすべて無効

提供元はブラウザの内蔵翻訳を含めてすべて無効で始まる。無効の間は何も送らず、ボタンも出さない。

### 4. 求められたときだけ翻訳し、連合しない

- 読者が投稿ごとに求めたときだけ翻訳する。タイムラインの自動翻訳はしない。費用が読めなくなるからである。
- 翻訳を `contentMap` に書かない。書けば作者の言葉として広まる。コードでも、Note の `contentMap` は版の `status_revision_bodies` からだけ作られ（`internal/app/federation/document.go` の `statusNote`）、翻訳は別モジュールの別のテーブルにあるので、この経路に入らない。

### 5. サーバー側の提供元に送る公開範囲

| 公開範囲 | サーバー側の提供元（プラグインを含む） | ブラウザの内蔵翻訳 |
| --- | --- | --- |
| `public` / `local` / `unlisted` | 既定で送る。運営者が提供元ごとに外せる | 使える |
| `private` / `direct` | **既定で送らない**。運営者が提供元ごとに許せる | 使える |

- 許可は提供元ごとの設定 `translation_provider_visibilities`（`提供元=公開範囲|公開範囲` のカンマ区切り。`oauth_client_rate_limits` と同じ形）にする。書いていない提供元は表の既定に従う。サーバー全体の 1 つのスイッチにしないのは、自前の LibreTranslate に許したつもりで、優先順の次にある商用の提供元にも流れないようにするためである。
- 判定する公開範囲は `content.EffectiveVisibility` で求める実効の公開範囲である。上限を受けた作者の `public` は `private` として扱う。サーバーが投稿を判定する値と揃え、狭いほうに倒す。
- クライアントは実効の公開範囲を知らない。`Status.visibility` は作者が選んだ公開範囲で、§6 で公開する提供元の公開範囲と比べてボタンを出すので、上限を受けた作者の投稿にもボタンが出て、サーバーが `422`（`translation-unavailable`）で断ることがある。そのときはブラウザの内蔵翻訳が引き継ぐ（§12）。実効の公開範囲は API に足さない。
- 自前の提供元でも扱いは同じで、許可は運営者が明示する。`my` は相手が自前かどうかを判定できない（設定の URL から確かに言えることがない）。
- 送るのは本文・内容の警告・投票の選択肢・代替テキストの文字だけである。投稿の IRI、作者、閲覧者、メンション先、URL は送らない（§8）。

### 6. 利用者からの見え方と、ADR-0017・プライバシーポリシーのひな形との関係

**ADR-0017 は変えない。** ADR-0017 が決めているのは、だれが閲覧でき（`content.CanView`）、どの連合先に配送するかである。提供元は閲覧者でも連合先でもなく、運営者がホスティングやメールと同じように選ぶ委託先として扱い、`CanView` を提供元のために呼ばない。FR-102 と ADR-0017 §1 の「外部へはフォロワーにしか届かない」の外部は連合先とそこの利用者と読み、§5 のとおり投稿の IRI と作者のハンドルは提供元にも渡らない。

ただし、この読み方は `local` について言葉どおりではない。委託先も平たく言えばサーバーの外なので、利用者への説明は次のとおりにする。

| 運営者の設定 | 読者が見るもの | 作者が見るもの |
| --- | --- | --- |
| すべて無効 | 翻訳のボタンがない | 何も変わらない |
| サーバー側の提供元を有効（既定の公開範囲） | `private`・`direct` にはブラウザの内蔵翻訳が有効なときだけボタンが出る。訳には提供元の名前が付く | ひな形の §6 に提供元が載る |
| `private`・`direct` も許す | そのボタンがサーバー側の提供元を使い、訳に提供元の名前が付く | ひな形の §5 にそのことが載り、投稿の公開範囲の選択にも 1 行の説明が出る |

- 投稿の公開範囲の選択の 1 行は、許可された提供元があるサーバーでだけ出す。読者が求めると本文が提供元に送られることを、書く前に作者に伝えるためである。リモートの作者にはこの表示が届かないので、ひな形の §2 と §5 で説明する。
- サーバーは翻訳の設定をインスタンスの情報（`GET /instance` の `translation`）として公開する。有効な提供元を優先順に（ID・名前・リンク・ロゴと受け取る公開範囲）、ブラウザの内蔵翻訳を運営者が許したか（`browser`、§12）、通報の文字を提供元に送ってよいか（`reports_to_server`、§13）である。運営者の設定を外から確かめられ、サードパーティのクライアントもボタンの出し分けと、どの手段を使うかの判断に使える。
- **`local` の投稿は、サーバー側の提供元を有効にしたサーバーでは既定で提供元に送る。** 提供元はホスティングと同じ委託先で、IRI もハンドルも送らない。ひな形はこれを隠さず、`{{IF translation}}` で `local` の行と「選ぶサービス」の表に書く。
- ひな形（`docs/operations/privacy-policy-template.md`）の `private`・`direct` の行は読者という人の範囲を述べていて、`direct` の行は運営者が技術的に読めることも述べている。サーバー側の提供元を有効にしただけならこの行は正しいままで、「選ぶサービス」の表と §6 に `{{IF translation}}` の行を足す。§5 の表は受け取る相手の一覧として読めるので、`private`・`direct` を許した運営者だけが `{{IF}}` で §5 の行に提供元を足す。処理の記録のひな形にも提供先を足す。
- 翻訳は保持する記録なので、保持期間（§9）をひな形の §3 に足す。
- 提供元に一度送った文字を `my` から消すことはできない。ひな形にそう書く。設定の画面は、サーバー側の提供元を有効にする前にポリシーの更新が要ることを説明する（#2232）。

### 7. API とスコープ

- `POST /statuses/{id}/translation`（本文は翻訳先の言語）のスコープは **`read:statuses`** にする。
  - 投稿を読む操作なので `read:statuses`（「Read posts and timelines」）が合う。`POST` にするのは提供元の呼び出しと保存を伴うためで、読み取りのスコープの `POST` は `previewAutoDeletePolicy`（`read:accounts`）が先にある。
  - `direct` は既存の規則で守られる。`read:direct` のないトークンは `DirectDenied` によって `CanView` で落ち、`404` になる（ADR-0090 §4）。翻訳のために別の判定を書かない。
- トークンを必須とする。未ログインの訪問者は使えない（投稿の取得と違い `{}` を許さない）。費用が利用者に結び付かないからである。
- サードパーティのアプリも呼べる。`x-first-party-only` にしない。上限はアプリではなく利用者に数えるので（§11）、どのアプリから呼んでも合算され、ADR-0090 §7 のレート制限と `oauth_client_rate_limits` もそのまま効く。
- 翻訳の応答は利用者ごとの応答なので `Cache-Control: no-store` にする。

### 8. 流れと、送るものの形

サーバー側の流れは次の順で、ポートはトランザクションの外で呼ぶ。

1. `CanView`（`ContextStatus`）。見えなければ `404`。
2. 現在の版の本文に、翻訳先の言語の `status_revision_bodies` があれば、提供元を呼ばず作者の言葉として返す。言語はタグの完全一致で比べ、スクリプトの副タグがないときだけ主言語の一致も認める（`zh-Hant` と `zh-Hans` を混ぜない）。
3. 優先順と実効の公開範囲から提供元の候補を作る。候補がなければ、安定したエラーで断る。
4. 候補のキャッシュを優先順に引く。無効にした提供元や許可を外した提供元のキャッシュは返さないので、設定はすぐ効く。
5. `kernel.KeyValueStore` の短いロックで同じ翻訳の呼び出しを 1 回にする。ロックを待つ間に別の要求が翻訳を保存すれば、それを返す。ロックが失われたときは一意制約が守る。
6. 上限を確かめて予約する（§11）。ロックの後に置くのは、待った末に別の要求の翻訳を受け取った要求が文字数を予約せず、その予約で 3 つ目の要求を断らないようにするためである。
7. 提供元を呼ぶ。対応しない言語・提供元の上限・一時的な失敗なら優先順の次へ進む。
8. 本文の出力をサニタイザに通す。内容の警告・投票の選択肢・代替テキストはプレーンテキストとして扱う。
9. 投稿が削除されていないことを確かめて、同じトランザクションで保存する。

期限は次のとおりで、どれもサービスの定数である。

- 1 つの要求は、ロックを待つ時間と提供元を呼ぶ時間を合わせて 50 秒で終える。HTTP サーバーの書き込みの期限（60 秒）より短くし、要求が切られる前に問題の応答を返すためである。
- 提供元を呼ぶのは、候補がいくつあっても要求の始まりから 45 秒まで（残りの 5 秒は保存に使う）で、1 回の呼び出しは 20 秒までである。プラグインの `plugin_translator_timeout` がそれより長くても 20 秒で止める（§14）。時間の残らない候補は呼ばず、`503`（`translation-failed`）で答える。
- ロックを待つのは、持ち主が呼び出しと保存を終え得る 50 秒までである。待った後でロックを取った要求が提供元を呼べるのは、自分の始まりから 45 秒までの残りだけなので、待つ時間と呼ぶ時間を足しても 50 秒を超えない。

断片の作り方は次のとおりで、サーバーとブラウザで同じ考え方にする。

- ブロック要素（`p`・`li` など）の境目で断片に分ける。
- メンション・ハッシュタグ・リンク・`:shortcode:`・`pre`・`code` は番号付きの印に置き換えて、中身を送らない。翻訳から守るためと、§5 のハンドルと URL を渡さないためである。`b`・`em` などの飾りは印の対で残す。
- 印がすべてちょうど 1 回ずつ戻らない訳は失敗として扱い、保存しない。
- 印の形はポートの契約で 1 つに決める。提供元に合わせて書き換えるのはアダプタの仕事である。

### 9. `status_translations` の分類

**`現在値（キャッシュ）`** にする。`link_cards`・`remote_media_cache`・`oauth_client_metadata_documents` と同じ分類である。

- **イベントではない。** 起きた事実ではなく、版から作った派生物で、消してよく、INSERT のみの規約 1 にも保持期間で消す運用にも合わない。
- **投影でもない。** ADR-0020 規約 1 は投影に同じイベント列からの再構築を求めるが、提供元の出力は決定的でなく、作り直すと費用がかかる。data-model §9 の再構築の表にも載せない。
- **規約 5 の基準に照らしても** 監査・モデレーション・連合の整合・利用者への説明に履歴を使わない。設定の変更だけを監査ログに残す（§11）。

テーブルは `translation` モジュールが持つ（`schema/<方言>/17-translation.sql`）。

| テーブル | 分類 | 内容 |
| --- | --- | --- |
| `status_translations` | 現在値（キャッシュ） | `id`, `status_id`, `revision_id`, `target_language`, `provider`（文字列。提供元を足してもスキーマが変わらないよう CHECK を付けない）, `source_language`, `content_html`, `spoiler_text`, `created_at`。一意 `(revision_id, target_language, provider)`、インデックス `(status_id)`, `(created_at)` |
| `status_translation_attachments` | 同上（子） | `translation_id`, `position`, `description` |
| `status_translation_poll_options` | 同上（子） | `translation_id`, `position`, `title` |
| `translation_account_usage` | 現在値 | `account_id`, `month`, `characters` |
| `translation_server_usage` | 現在値 | `month`, `characters`, `cache_hits`, `cache_misses` |

- キーが版なので、編集すれば新しい版になり、古いキャッシュには当たらない。代替テキスト（`status_revision_attachments.description`）も投票（`polls.revision_id`）も版に属するので、子の行も版の単位で正しい。
- 同じ投稿を読める人の間で行を共有する。行を返す前に必ず §8 の 1 を通すので、キャッシュが閲覧の判定を飛び越えない。
- 定期ジョブ `translation.purge_cache` が、作成から `translation_retention_days`（既定 30 日）を過ぎた行を消す。読んでも延ばさない。利用量の行は翌々月に消す。
- `cache_hits`（キャッシュから答えた要求）と `cache_misses`（提供元を呼んだ要求）は管理画面のキャッシュヒット率のための数である。要求ごとには書かず、プロセスがメモリで数えて、多くても 1 分に 1 度と管理画面の読み取りの前に 1 つのトランザクションで足す。キャッシュに当たった要求が 1 つの行の書き込みを取り合わないようにするためである。止まったプロセスの最後の 1 分ほどは数えないことがあるので、率は目安である。要求の数は指標 `my.translation.requests` にも結果ごとに出る。

### 10. 削除と消去

- `translation` は `content.EventStatusDeleted` を同じトランザクションで受けて、その投稿の翻訳を消す。`timeline` の `DeleteStatusEntries` と同じ形で、依存の向きも `translation` から `content` の 1 方向で済む（ADR-0002）。
- この 1 か所で、作者の削除・モデレーションの削除・リモートの `Delete`・自動削除・保持期間（リモートの投稿、リレーの投稿）・アカウントの消去（`StatusEraser`）をすべて受けられる。どれも `StatusDeleted` を発行することをコードで確かめた。
- 通報や処分の証拠として行が残る投稿（`RetainedStatuses`）でも、翻訳は消す。証拠は原文で、翻訳に証拠の価値はない。
- 利用者の削除では `account.DataEraser` を足して `translation_account_usage` の行を消す。
- 作者の凍結では行を消さない。凍結はデータを保持して解除で戻る処分で、見えない投稿は §8 の 1 で止まり、残りは保持期間で消える。

### 11. 上限

- 利用者に既定の提供元を持たせない。提供元は運営者の優先順だけで決まる。
- 翻訳の設定はどれもインスタンスの設定で、変更は監査ログに残す。`translation_providers`（有効な提供元の ID を優先順にカンマで区切る。空なら何も送らない）、`translation_provider_visibilities`（§5）、`translation_browser`（ブラウザの内蔵翻訳、既定は無効、§12）、`translation_reports_to_server`（§13）、`translation_retention_days`（§9）と、下の 2 つの上限である。プラグインの訳に付ける名前だけは設定ファイルの鍵 `plugin_translator_name` で決める（§14）。
- 上限は月ごとの文字数で、利用者ごととサーバー全体の 2 つを持ち、どちらもインスタンスの設定で変える（変更は監査ログに残す）。

| 設定 | 既定 | 目安 |
| --- | --- | --- |
| `translation_user_monthly_characters` | 50,000 | 200 文字の投稿で 250 件、1 日に 8 件ほど |
| `translation_server_monthly_characters` | 500,000 | 上限まで使って Amazon Translate の単価（100 万文字で 15 ドル）で 7.5 ドル |

- 既定の値は、小さなサーバーの運営者が気付かないうちに月 10 ドルを超えないことを基準にした。`0` はサーバー側の提供元に何も送らない。「無制限」の値は設けない。自前の LibreTranslate なら大きな値を入れればよい。
- 数えるのは提供元に送った文字（コードポイント）で、印は数えない。キャッシュに当たれば数えず、§8 の 2 とブラウザの内蔵翻訳も数えない。提供元の請求の数え方とは一致しないことがあるので、請求の代わりにはならない。
- 超えたら提供元を呼ばず、安定したエラー（`429`）で断る。月の区切りは UTC とする。
- 費用を `finance` に書かない（ADR-0067）。文字数は指標として出す。

### 12. ブラウザの内蔵翻訳

- Translator API は運営者が有効にして、ブラウザが対応しているときだけ使う。`private`・`direct` を含むどの公開範囲にも使え、`my` のサーバーにも提供元にも何も送らない。
- **サーバー側の提供元が先で、サーバーが断ればブラウザが引き継ぐ。** 読者がサインインしていて、投稿の公開範囲を受け取れる提供元があるとき（§5、§6）、Web クライアントはまずサーバーに求める。サーバーが断ったとき（`422` の `translation-unavailable` と `translation-unsupported-language`、`429` の上限、`503` の `translation-failed`、そのほかの `5xx`）、ブラウザがその投稿を訳せるなら（このあとの条件）ブラウザが訳す。読者が読めない投稿（`404`）や、認可で断られた要求は引き継がない。ブラウザで訳せなければ、サーバーの断りをそのまま伝える。提供元のない投稿、サインインしていない読者には、はじめからブラウザだけを使う。選ぶのは `hooks/useTranslator.ts` の 1 か所で、通報の画面（§13）も同じ順にする。
- §5 の上限を受けた作者の投稿もこの形で扱う。ボタンが出てサーバーが断り、ブラウザが引き継ぐ。Translator API のないブラウザでは断りが出る。
- 一度サーバーに断られた投稿（版と翻訳先の言語ごと）は、カードがある間、次に押すとサーバーを通さずブラウザに渡す。モデルのダウンロードを伴う `create()` は読者の操作の直後でないと断られ、サーバーを待つ間にその操作が切れることがあるので、押し直した操作でダウンロードを始められるようにするためである。
- 対応しないブラウザ、対応しない言語の組（`Translator.availability()` が `unavailable`）ではこの経路を出さない。プラグイン（§14）を設定していないサーバーでは、そのブラウザに翻訳のボタンは出ない。原文の言語が `und` なら Language Detector API で検出し、使えなければ出さない。初回はモデルのダウンロードがあるので進み具合を見せる。
- 検出の結果は、最も確からしい言語の `confidence` が 0.5 未満なら使わず、言語が分からないとして断る。Chrome の文書は確からしさで切ることを求めるが値を示さないので、0.5 は仮の値である（要検証）。
- モデルは §8 の印を保たないことがある（Chrome の `en` から `ar` は印をただの数字に変えた）。印が戻らなかった断片は、印の間の部分ごとに訳し直して印を自分で戻し、印の確認をもう一度通す。文の文脈は一部失うが、投稿の形は保つ。それでも確認を通らない訳は §8 と同じく失敗として扱う。
- **出力を HTML として解析しない。** 仕様は入力を文字列とし、平文の入力でも出力がマークアップを含み得るとして、サニタイズせず HTML として挿入しないよう求めている。一方で `PostContent` が受け取るのはサーバーがサニタイズした `SanitizedHtml` だけで（web-client A8）、クライアントにサニタイザはなく、Trusted Types のポリシーも足さない。そこで、サーバーがサニタイズした本文の構造を保ったまま、訳を React のテキストノードとして入れる。出力に HTML が混ざっても文字として見える。#2238 の「同じサニタイズを通す」はこの形で満たす。
- 訳はメモリにだけ持つ。サーバー側の訳も含めて、オフライン用の保存やブラウザのストレージに入れない。`private`・`direct` をブラウザに保存しないという、ひな形にある既存の約束を保つためである。
- `Permissions-Policy` は機能 `translator`（既定の許可は `self`）を閉じていないので（`internal/platform/http.go`）、変更は要らない。訳には使ったブラウザの名前を付ける。

### 13. 通報の画面

- モデレーターは通報の対象の投稿と通報のコメントを翻訳できる。閲覧の権限はモデレーションの既存の権限に従う（ADR-0058）。API は一次のクライアントだけが使う管理の操作に置く。
- ブラウザの内蔵翻訳は設定によらず使える（有効なら）。
- 設定 `translation_reports_to_server`（既定は無効）で、通報の文字をサーバー側の提供元に送ってよいかを決める。無効なら何も送らない。
- 有効でも §5 の提供元ごとの公開範囲はそのまま効く。モデレーターの権限で公開範囲の規則を広げない。通報された `direct` は、その提供元に `direct` が許されていなければ送らない。通報のコメントは閲覧者が限られた文章なので `private` と同じに扱う。
- 通報のコメントは保存しない。投稿の翻訳は §9 のキャッシュを共有するが、削除済みの投稿では保存しない。利用量はサーバー全体の上限にだけ数える。

### 14. プラグインへの委譲

- プラグインは `internal/adapter/translator/plugin` のアダプタとして動き、同じコントラクトテストを通す（#2217、ADR-0146）。
- `my` から見るとサーバー側の提供元の 1 つで、§5 の既定、§8 の印の確認とサニタイズ、§11 の上限がそのまま効く。
- 宛先は `unix://` か `https://` だけで、`http://`（平文の TCP）はループバックでも断る（ADR-0146 §6 の kind ごとの規則）。投稿の本文が暗号化されずにネットワークを流れないようにするためである。
- 1 回の呼び出しの期限は設定 `plugin_translator_timeout`（既定 10 秒）だが、サービスは §8 のとおり 20 秒で止めるので、それより長い値は効かない。設定の文書（`docs/reference/configuration.md`）と運営者の文書にそう書く。
- 訳に付ける名前は運営者が設定する。プラグインの中で LLM を使えば §1 の危険は残り、それを `my` は検出できないので、運営者の文書にその責任を明記する。

### 15. 提供元のアダプタが後で必要とするもの

足すのは次だけで、**ポート・サービス・テーブル・API・Web クライアントは変わらない**。

- `internal/adapter/translator/<提供元>/` と、コントラクトテストの通過
- 提供元のエラーとポートのエラーの対応: レート制限とクォータは `ErrProviderLimit`、扱わない言語は `ErrUnsupportedLanguage`、それ以外（届かない・時間切れ・提供元のその他のエラー）は `ErrTemporary`。エラーには API キーも投稿の文字も含めない
- 設定の鍵（API キーは config に置き、API では返さない）と、`tools/agentkit/context-map.yaml` の項目
- 登録情報: ID・表示名・リンク・ロゴ。応答とインスタンスの情報で配るので、クライアントは提供元の種類を知らずに表示できる
- `docs/operations/` の運営者向けの文書（ひな形の「選ぶサービス」に受け取るものを足す）
- HTTP クライアントの選択: 運営者が設定した宛先なので、SSRF を防ぐ `kernel.HTTPClient` ではなくアダプタの HTTP クライアントを使う（`internal/adapter/voice/livekit` が例）
- §8 の印が実際の出力で戻るかの確認と、§要検証の表にある規約・データの扱いの確認

### この決定を見直す条件

- 実際の出力で §8 の印が戻らない提供元が主要なものの半分を超える。ポートの断片の形を見直す。
- 既定の上限で読者の多くが月の途中で止まる、または運営者の費用が想定を超える。
- Translator API が標準化の過程で大きく変わる、またはオンデバイスの保証がなくなる。§5 と §12 の「どの公開範囲にも使える」を見直す。

## 経緯

連合は読者の読めない言語の投稿を運んでくる。費用も、だれに投稿の文字を渡してよいかもサーバーごとに違うので、1 つの提供元には決められない。モデレーターも他の言語の通報を読む。

最初の案は、ブラウザの内蔵翻訳・LibreTranslate・商用の提供元を 1 つ揃えて、`private`・`direct` はブラウザだけにする形だった。決定者が判断するなかで、自前の LibreTranslate に送るのを禁じる理由はないので運営者の設定で許せることになり、LLM は入力の性質から候補から外れた。利用者の既定の提供元は、運営者の優先順で足りるとして持たないことになった。

`local` は ADR-0017 の言葉に照らして迷ったが、提供元を委託先と読めば ADR-0017 を変えずに済み、IRI もハンドルも渡らないので、既定で送ってひな形で説明する形になった。作る順序も、提供元のアダプタを `v0.1.0` の後に回し、コアだけを先に作る形になった。`v0.1.0` からはスキーマの変更に移行の手順が要る（ADR-0023）ので、テーブルと API を先に固めれば、アダプタは足すだけで済む。

実装を監査すると、サーバー側の提供元とブラウザの内蔵翻訳の順が決まっておらず、サーバーに断られた投稿がブラウザに渡らないことが分かった。決定者は、サーバー側の提供元を先にし、断られたときはブラウザが訳せるならブラウザに渡すと決め、上限を受けた作者の投稿もこの形で扱うことにした（§12）。

コードを読むと、翻訳の置き場所の問いは既存の形で答えられた。`現在値（キャッシュ）` の分類はすでにあり、`StatusDeleted` がすべての削除の経路を通り、`DirectDenied` が `read:direct` の規則を 1 か所で守っている。逆に、ブラウザの出力は A8 の `SanitizedHtml` に入らないと分かったので、§12 のテキストノードの形にした。

## 採らなかった案

- LLM を提供元の 1 つにする: 品質と文脈の扱いでは最も強いが、§1 のとおり読者への信頼を入力から崩せる。
- `private`・`direct` を設定でも送らない（ブラウザだけ）: 約束が最も単純だが、自前の LibreTranslate しか使わない運営者にも禁じることになり、スマートフォンの読者は翻訳を使えない。Mastodon はこちらに近く、`distributable?`（`public` か `unlisted`）の投稿だけを翻訳する（2026-11-05 にソースで確認）。
- `private`・`direct` の許可をサーバー全体の 1 つのスイッチにする: 設定は単純だが、§5 のとおり意図しない提供元に流れる。
- `local` も既定で送らない: ADR-0017 の言葉には最も忠実だが、ローカルの読者が読む投稿の多くを占め得るのに翻訳できなくなり、ハンドルも IRI も渡らないので守れるものと釣り合わない。
- 翻訳専用のスコープ（`read:translations`）: 費用を伴う操作を同意の画面で区別できるが、利用者に見えるのは投稿を読むことだけで、スコープが増える割に上限が費用を抑えるので要らない。Mastodon も `read:statuses` を使う。
- `write:statuses` を求める: 保存を伴うことには合うが、読むだけのアプリに書く権限を求めさせ、ADR-0090 の細かいスコープの趣旨に反する。
- 利用者ごとの既定の提供元: 読者の好みに合わせられるが、優先順で足り、設定と画面が増える。需要が出てから足せる（追加なので ADR-0090 §8 の約束を破らない）。
- `status_translations` を投影にする: `data-model` の枠に収まるが、再構築の保証を満たせない。
- 翻訳を `status_revision_bodies` に足す: テーブルが増えないが、連合の `contentMap` に出てしまい、消去も分けられない。
- 文字列の連結だけで HTML をそのまま提供元に送る: アダプタは最も単純になるが、ハンドルと URL が渡り、タグの保持を提供元に任せることになる。
- ブラウザの出力をサーバーに送ってサニタイズする: `SanitizedHtml` にできるが、この経路の約束（サーバーに何も送らない）を破る。
- クライアントにサニタイザを入れる: 訳の中の HTML を活かせるが、A8 の監査の範囲と Trusted Types のポリシーが増え、訳に飾りは要らない。
- 通報では `translation_reports_to_server` が公開範囲の規則に優先する: 設定が 1 つで分かりやすく #2239 の書き方に近いが、コメントを送りたいだけの運営者が DM まで送ることになる。

## Consequences（影響）

- 良い: 無効の間は費用も外部への送信もない。提供元を足すときにスキーマと API を変えなくてよい。投稿の IRI・作者・ハンドル・URL が提供元に渡らないので、提供元が受け取る個人データが本文の文字に限られる。
- 悪い: `v0.1.0` の時点で動くのはブラウザの内蔵翻訳とプラグインだけである。Translator API はデスクトップの Chrome・Edge・Opera だけなので、**スマートフォン・Firefox・Safari の読者には、プラグインのないサーバーでは翻訳のボタンが出ない**。
- 悪い: 実在の提供元で試す前にポートを固めるので、印の形が合わない危険がある。ポートは v0.x の内部インターフェイスとして変えられるが、「何も変わらない」は確かめた事実ではなく設計の目標である。
- 悪い: キャッシュは提供元ごとなので、提供元を入れ替えると文字数を再び消費する。
- 悪い: 提供元に渡した文字は取り戻せない。とくに規約が保存を認める提供元（§要検証）を選ぶと、この ADR の範囲では守れない。
- 悪い: クライアントが実効の公開範囲を知らないので、上限を受けた作者の投稿にもボタンが出る。Translator API のないブラウザでは、押すとサーバーの断りが出る（§5、§12）。
- 悪い: 翻訳の精度は保証されない。機械翻訳であることを帰属の表示で示すだけで、原文にないことが訳に現れる可能性はどの提供元にも残る。

## Open Questions / 要検証

2026-11-05 に公式の文書で確かめたことと、確かめられなかったこと（§15 のアダプタを作るときに読み直す）:

### ブラウザの Translator API

- 対応: Chrome 138 以降、Edge 148 以降、Opera 122 以降。Firefox・Safari・モバイルのブラウザは未対応（[caniuse](https://caniuse.com/mdn-api_translator)、[Chrome の文書](https://developer.chrome.com/docs/ai/translator-api)）。Worker では使えない。HTTPS だけ（[MDN](https://developer.mozilla.org/en-US/docs/Web/API/Translator)、実験的な機能と表示）。
- 仕様は W3C の Community Group のドラフト（2026-10-14 版）で標準化の過程にない。[仕様](https://webmachinelearning.github.io/translation-api/) はモデルがローカルでもクラウドでもあり得る書き方である。オンデバイスと述べているのは実装の文書で、Edge は入力がデバイスを出ないと明記し（[Edge の文書](https://learn.microsoft.com/en-us/microsoft-edge/web-platform/translator-api)）、Chrome は組み込みモデルの一般論として第三者に送らないと書く（[Chrome](https://developer.chrome.com/docs/ai/translate-on-device)）。だから `my` が約束するのは「`my` のサーバーと提供元に送らない」までで、ブラウザの提供者の扱いまでは約束しない。
- 要検証: モデルのダウンロードで言語の組がブラウザの提供者に分かるか。§8 の印がどの言語の組で戻らないか（戻らない断片は §12 のとおり印の間ごとに訳し直す）。言語の検出の確からしさの下限 0.5 が適切か（§12）。CSP の下で動くかの実機の確認（#2238）。
