# ADR-0108: 利用者による招待の作成と、招待の使える登録モード

- Status: Accepted
- Date: 2026-10-28
- Deciders: @rosylilly
- Issue: #1617

## Context（背景・課題）

招待（FR-001 の `invite` モード）は、`manage_invites` を持つスタッフだけが `/moderation/invites`・管理 API・`my invite` で作れる。
招待は `invite` モードでしか使えず、`open` と `approval` では登録の画面が招待コードを受け取らない。

決定者は、利用者も招待を作れるようにしたいとしている（#1617、原文）:

> 新権限「招待作成」を追加し、サーバー設定で招待を作れるユーザーを全員・権限持ちで区切れるようにして、サポーターの権限として招待作成を付与できるようにする

同じ形の決まりがすでに通話のルームにある（[ADR-0100](0100-voice-chat-rooms.md)）。インスタンス設定 `voice_room_starters`（`everyone` / `permitted`）と、区分 `member` の権限 `start_voice_rooms` である。
課金のプランのロールが持てるのは区分 `member` の権限だけなので（[ADR-0070](0070-permission-split-emoji-finance.md) §1、[ADR-0072](0072-supporter-plans-and-roles.md)）、
サポーターに付けられるようにするには、新しい権限を `member` にする。`invites.created_by_user_id` は招待を作った人をすでに記録している。

## Decision Drivers（判断基準）

1. 決定者の要望どおり、全員か権限を持つ人かをサーバー設定で選べ、権限をプランのロールに付けられる
2. 既存の形（ADR-0100 の設定と権限、ADR-0070 の `member` の区分）に揃え、新しい概念を増やさない
3. 利用者の招待で、スタッフが知らないうちに大量の登録が起きない（上限、作成者の資格の確認、監査ログ）
4. 招待された人が誰の招待で来たかを、モデレーターが確かめられる

## Considered Options（選択肢）

- 作れる人: A1 新しい権限 `create_invites`（`member`）とインスタンス設定 `invite_creators` / A2 `manage_invites` をプランのロールにも付けられるようにする
- 上限: B1 インスタンス設定で変えられる上限 / B2 コードに固定した上限 / B3 スタッフと同じ（上限なし）
- 作成者が資格を失ったとき: C1 未使用の招待を使えなくする（登録のときに確かめる） / C2 期限まで使える

## Decision（決定）

**A1・B1・C1 を採用する。** 招待は `invite` に加えて `open` と `approval` でも使える。

決定者の回答（#1617、原文）:

> 1\. サーバー設定で変えられるようにする
> 2\. これは現行の招待についても approval モード・誰でも登録モードでも使えるようにする
> 3\. 未使用の招待は無効化
> 4\. a でモデレーターが確認できる
> 5\. a で監査ログを記録

### 1. 権限とインスタンス設定（A1）

- 新しい権限 `create_invites` を足す。区分は `member`（ADR-0070 §1）。自分の招待を作り、自分の招待を一覧して取り消すことだけを許し、他人の招待やサーバー全体の設定は変えられないので、区分の条件を満たす。
  組み込みのロールでは `admin` だけが持つ。プランのロールに付けられる（ADR-0072 の許可リストは区分 `member` の権限）。
- インスタンス設定 `invite_creators`（`instance_settings`、`manage_settings`）: `everyone`（ログイン済みで有効なローカルの誰でも）か `permitted`（`create_invites` を持つ人だけ）。既定は `permitted`。
- 利用者が招待を作れるのは、`invite_creators` が `everyone` か、`create_invites` を持つとき。凍結・制限中・登録の承認待ちのアカウントは作れない。
- `manage_invites` を持つスタッフは、これまでどおりすべての招待を作り、一覧し、取り消せる。スタッフの招待に §2 の上限は効かない。

### 2. 利用者の招待の上限（B1）

上限はインスタンス設定（`manage_settings`）で変えられる。利用者が作る招待にだけ効く。

| 設定 | 意味 | 既定 | 範囲 |
| --- | --- | --- | --- |
| `member_invite_max_active` | 1 人が同時に持てる使える招待（取り消し・期限切れ・使い切りでないもの）の数 | 5 | 0〜100（0 は作れない） |
| `member_invite_max_uses` | 1 つの招待で登録できる人数の上限 | 10 | 1〜1,000 |
| `member_invite_max_expires_in` | 招待の有効期間の上限 | 30 日 | 1 時間〜365 日 |

- 利用者は回数と期間を上限の中で選ぶ。既定は 1 回・7 日（上限がそれより小さいときは上限）。無制限（`max_uses` や期限なし）は選べない。
- 上限を下げても、すでにある招待は変えない。新しく作るときだけ検査する。

### 3. 作成者の資格の確認（C1）

- 利用者が作った招待は、登録のたびに作成者がまだ §1 の条件を満たすかを確かめる。満たさなければ、その招待は使えない招待（既存の `ErrInvalidInvite`。取り消し・期限切れ・使い切りと同じ答え）として断る。
  条件を外れる場合: `create_invites` やプランのロールを失った、`invite_creators` が `permitted` に戻った、凍結・制限・削除された。
- 招待の行は変えない。資格が戻れば（再加入など）、期限の中ならまた使える。ADR-0070 §3 の絵文字の作成者と同じく、操作のたびに決める。
- スタッフの招待（作成者が `manage_invites` で作った招待と CLI の招待）は、これまでどおり作成者を確かめない。どちらの経路で作ったかは招待の行に記録する（data-model に書くときに列を決める）。

### 4. 招待の使える登録モード

- 招待は `open`・`approval`・`invite` のどれでも作れて使える。`closed` では作れず、使えない（`closed` は運営者のみ）。
- `invite`: これまでどおり、使える招待が要り、すぐ承認する。
- `approval`: 招待は任意。使える招待で登録した人は、承認待ちにせずすぐ承認する（招待した人が承認を肩代わりする）。招待なしの登録は、これまでどおり承認待ちになる。
- `open`: 招待は任意。招待で登録しても扱いは招待なしと同じで、誰の招待で来たかだけが記録される。
- どのモードでも、入力された招待が使えない（取り消し・期限切れ・使い切り・§3 の作成者の資格なし・コードがない）ときは、招待なしとして通さずに `ErrInvalidInvite` で断る。打ち間違いに気づけるようにするため。
- 登録の制限（`/moderation/signup-blocks` のメールアドレスのドメインと IP の制限）が承認待ちにする登録は、招待があっても承認待ちにする。
- 登録の画面は、どのモードでも招待コードの欄と `?invite=<code>` を受ける（`invite` では必須、ほかは任意）。

### 5. 画面と API

- 利用者は設定の中の「招待」（`/settings/invites`）で、自分の招待を作り、一覧し（状態: 使える・取り消し・期限切れ・使い切り・作成者の資格なし）、リンクをコピーし、取り消す。ナビゲーションの項目は増やさない（ADR-0070 §1 の `/settings/custom-emojis` と同じ）。
  §1 の条件を満たさない利用者には、この画面への入口を出さない。
- クライアント API: 自分の招待の `GET` / `POST /api/v1/invites` と `POST /api/v1/invites/{id}/revoke`。管理の `/api/v1/admin/invites` は変えず、応答に作成者を足す。
- モデレーション: `/moderation/invites` に作成者を出す。`/moderation/accounts/{id}` に、そのアカウントが使った招待と招待した人（作成者）を出す（`manage_accounts`。招待の行と登録の申請の `InviteID` からたどる）。

### 6. 監査ログ

- 利用者の招待の作成と取り消しも、スタッフと同じ `invite_created` / `invite_revoked` で記録する。実行者はその利用者。対象名は今と同じくコードの先頭 4 文字。
- 招待での登録は、登録の申請と承認の記録（既存）に招待の ID が残るので、新しい監査の action は足さない。

### この決定を見直す条件

- 利用者の招待からのスパムの登録が目立つ場合は、招待で登録した人の初期の制限（投稿数など）や、招待した人への責任のひも付け（招待した人の凍結で招待された人を確認待ちにする）を検討する。

## Consequences（影響）

- 良い影響: サポーターの特典に招待を足せる。`approval` のサーバーで、信頼できる利用者の招待なら承認の手間が減る。誰の招待で来たかをモデレーターが確かめられる。
- 悪い影響:
  - `approval` の承認を招待で省けるので、`everyone` にすると承認制の意味が弱まる。運営者向けの文書にこの関係を書く。
  - 登録のたびに作成者の資格を確かめるので、招待での登録の読み取りが 1 回増える。
  - 既存の振る舞いが変わる: `open` と `approval` で招待コードを受けるようになり、使えないコードは断る。
- 後続の作業（Issue にする）:
  - サーバー: 権限と区分、インスタンス設定、§2〜§4 の規則、利用者の招待の API、モデレーションの表示、監査、テスト。data-model §4.1 の招待の行に作成の経路を足す
  - Web: `/settings/invites`、管理の設定の画面に §1・§2 の設定、`/moderation/invites` の作成者、アカウントの画面の招待した人、登録の画面の招待コードの欄（`open` と `approval`）、`locales/en`・`locales/ja`
  - 文書: `docs/operations/registration.md`（招待を作れる人、モードごとの招待の扱い、上限）、サポーターのプランの案内（プランのロールに付けられる権限）

## Pros and Cons of the Options（詳細比較・任意）

- A2 は新しい権限が要らないが、`manage_invites` は全員の招待を一覧して取り消せるスタッフの権限で、区分 `member` の条件を満たさず、お金でスタッフの権限を買えない決まり（ADR-0072 判断基準 2）に反する。
- B2 は設定が増えないが、決定者はサーバー設定で変えられることを選んだ。B3 は `everyone` のときに 1 人が無制限の招待を作れてしまう。
- C2 は登録のときの読み取りが増えないが、凍結した利用者やプランをやめた利用者の招待で登録が続く。
