# ADR-0140: 1 つのワーカーのプロセスで複数のジョブを同時に実行する

- Status: Accepted
- Date: 2026-11-03
- Deciders: @rosylilly
- Issue: #2004

## Context（背景・課題）

`PullRunner` は `RunOnce` の繰り返しでジョブを 1 件ずつ実行し、数を変える設定がない。スケールアウトの単位はプロセスで、配送のように相手の応答を待つ時間が長いジョブでも、待っている間はプロセスが丸ごと空く（NFR-PERF-2、[ADR-0004](0004-job-queue-abstraction.md)）。
[ADR-0138](0138-worker-job-selection.md) §7 は同時実行数を別の決定に分けた。外部のキューの分割は [ADR-0139](0139-external-queue-routing.md) が決めた。

コードの現状は次のとおり。

- `PullRunner` は「1 つまたは複数のプロセスの複数の `PullRunner` が 1 つの `Source` を共有してよい」と定めている（`internal/app/queue/runner.go`）。claim は今でも複数のワーカーの間で並行する。
- Cloud Tasks の合図は 1 件が 1 つの HTTP 要求なので、`queue = cloudtasks` では 1 つのプロセスの中でハンドラが今でも並行して動く。Cloud Run の既定の同時要求数は 80（2026-11-03 に [About concurrency](https://docs.cloud.google.com/run/docs/about-concurrency) で確認）。SQS の Lambda の受け口はレコードを順に処理する（`internal/interface/queuepush/lambda.go`）。
- PostgreSQL の接続は `pool_max_conns` を指定しなければ「4 と CPU 数の大きいほう」（pgx の既定）。プールの設定をコードで変えていない。
- **トランザクションを持ったまま別の接続で読む箇所が、通知の主経路を含めて今もある**（§4）。ハンドラの数がプールに届くと、全員が 2 本目の接続を待って止まる。

## Decision Drivers（判断基準）

1. 指定しない構成の動作を変えない
2. 待ちの多いジョブで、プロセスを増やすより安く処理量を増やせる
3. ジョブがないときの DB への負荷を増やさない（ゼロに近い費用での運用）
4. 停止の処理とリースの意味を変えない
5. 実装と設定が小さい

## Considered Options（選択肢）

1. **スロットごとに並行して claim し、キューが空の間は 1 つのスロットだけがポーリングする**
2. **スロットの数だけ `PullRunner` を並べるだけ**
3. **1 つの claim のループが空いたスロットにジョブを渡す**
4. **種類ごとに同時実行数を持つ**
5. **何もしない**（プロセスを増やすだけ）

### 1. 設定

- 設定のキー `worker_job_concurrency` を足す。1 つのプロセスが同時に実行するジョブの数で、**既定は 1**。1 のときは今と同じ動作にする。範囲は 1〜128（測った範囲）。
- 種類ごとの数は持たない。種類ごとに変えたいときは、[ADR-0138](0138-worker-job-selection.md) の `worker_job_types` でプロセスを分け、プロセスごとに数を与える。
- `role = web` で 2 以上を指定すると起動に失敗する。`queue` が `db` 以外のときも同じ。
- **`worker_job_concurrency` が PostgreSQL のプールの最大以上なら、起動に失敗する**（§4）。

既定を 1 にするのは、実際のハンドラで本番の検証をしていないため。実際のインスタンスで確かめてから既定を上げることは、この ADR を覆さずに別に決められる。

### 2. 動作

- スロットごとに `RunOnce` と同じ claim と実行を行う。ジョブごとに **空いたスロットが claim する** ので、claim 済みのジョブがスロットを待つことはなく、リースの意味は今のまま変わらない（先読みをしない）。
- ジョブが見つからなければ、1 つのスロットだけが `PollInterval` ごとにポーリングを続け、残りは待つ。ジョブが見つかれば、待っているスロットを起こす。
- スロットごとにワーカーの名前を持つ（claim と試行の記録に出る）。
- claim の並行と順序キーの扱いは、今の複数のワーカーの間と同じ。`queue/db` の変更は要らない。

### 3. ハンドラの安全性

82 種類のハンドラとその依存を読んだ範囲では、接続の待ち（§4）を除いて、同時実行で壊れるものは見つからなかった。ただし全行は読んでおらず、実行して確かめたのは試作の範囲（ハンドラは試作のもの。`-race` で 1 × 32 を 10 秒実行し、競合の報告なし。`Meter` と `Tracer` は付けていない）。

| 場所 | 状態 | 同時実行での扱い |
| --- | --- | --- |
| `internal/app/federation/breaker.go` | ホストごとの状態を持つ | mutex あり。プロセスごとの状態で、スロットで共有されるぶん早く開く |
| `internal/app/content/link_card_hosts.go` | ホストごとの fetch の制限 | KV の lock で守る。`linkCardHostHold` は 1 つの fetch だけのもの |
| `internal/adapter/media/native/native.go` | 画像の処理 | 既定で CPU の半分までの semaphore がある（後述） |
| `internal/adapter/httpclient/httpclient.go` | 1 ホスト 8 接続 | 1 つのクライアントを共有する。超えると待つ（後述） |
| `internal/adapter/jsonld/jsonld.go` | `@context` の読み込み | 読むたびに新しく解く。並行を前提に書かれている |
| `internal/adapter/mail/smtp/smtp.go` | メールの送信 | 接続を共有しない |
| `internal/app/kernel/keymanager_cache.go`、`internal/app/instance/overview.go`、`internal/app/content/remote_media.go`、`internal/app/uow/projector.go` | キャッシュと登録 | mutex または atomic あり |

実装では、複数のスロットを動かした統合テストを `-race` で回し、見つかったものを直す。

待ちの注意点が 2 つある。

- **画像の処理**: semaphore を待つ時間もリースに数える。スロットが CPU より多く、`media.process` ばかりがたまると、待っている間にリースが切れてやり直す可能性がある。測っていない。CPU を使う種類は、ADR-0138 で少ないスロットのプロセスに分けるよう運用の文書に書く。
- **同じホストへの集中**: 1 ホストの上限を超えたスロットは接続を待つ。止まっているホストへの配送でスロットが埋まると、他の種類も待つ。これはプロセスが 1 スロットのときも同じで、割合はスロットが増えても変わらないが、1 ホストの上限 8 はプロセス単位なので、プロセスを増やす場合より早く上限に当たる。

### 4. DB の接続

スロットの数に合わせて接続を自動で増やさない。`database_url` の `pool_max_conns` は運営者の設定で、外部の接続の上限（Cloud SQL、RDS、接続プール）を知っているのは運営者だから。

**`worker_job_concurrency` がプールの最大以上なら、起動に失敗する。** 警告では足りない。トランザクションを持ったまま別の接続を取るハンドラがあり、スロットがプールに届くと、全員が互いを待ってハンドラの期限まで止まることを上の表で再現した。プールの既定は「4 と CPU 数の大きいほう」なので、1 vCPU の既定なら 3 までで、それより多くするには `pool_max_conns` を上げる。
指定のないとき（既定の 1）は判定しない。`pool_max_conns=1` の今の構成を起動できなくしないためで（Driver 1）、この構成は 2 本目を取った時点で今も止まる。この制限は `worker_job_concurrency` だけのもので、プッシュの受け口には適用しない（§6）。

SQLite と libSQL ではプールの最大がないので判定せず、32 を超えると起動時に警告のログを出す。SQLite の書き込みは 1 つずつで（`BEGIN IMMEDIATE`、`busy_timeout` 5 秒）、128 で処理量が下がったため。libSQL は測っていない。

### 5. 停止とリース

- `stop` を閉じたら、どのスロットも新しいジョブを claim しない。実行中のジョブは今と同じく `ShutdownTimeout`（既定 25 秒）まで続ける。その後に取り消し、`JobStopTimeout`（既定 3 秒）だけ待つ。
- リースは今のまま一律の 5 分で、ハンドラの期限は claim の前から数える（`RunOnce`）。
- 同時に止まるジョブの数はスロットの数だけ増える。取り消されたジョブは試行を 1 回使う。試作の強制終了でも、処理中の数だけリトライが記録された。また、結果の記録の上限 `RecordTimeout`（10 秒）は `JobStopTimeout` より長いので、取り消しの後の記録が間に合わないジョブはリースの期限まで待つ。これは今もある動作で、数が増える。
- `ShutdownTimeout` は変えない。応答に時間がかかる種類を大きなスロットで動かすと、デプロイのたびに試行を使う数が増えることを運用の文書に書く。

### 6. プッシュの受け口

`queue = cloudtasks` と `sqs` では同時実行数はプラットフォームが決める（Cloud Run の同時要求数、Cloud Tasks のキューの同時数、Lambda の同時実行数）。`worker_job_concurrency` は使えず、2 以上で起動に失敗する。外部のキューで種類ごとに処理能力を分ける方法は [ADR-0139](0139-external-queue-routing.md) が決めた。プールの判定は、プッシュの受け口には適用しない。

**覆る条件**: 実際のハンドラの統合テストで安全に並行できない種類が多く見つかる場合や、本番に近い環境で処理量が伸びない場合は、選択肢 5 と比べ直す。

## Consequences（影響）

- 良い影響
  - 待ちの多いジョブの処理量を、メモリと DB 接続をあまり増やさずに増やせる。接続はプロセスを増やす場合より少ない（測定では 32 に対して 24 以下）。
  - 既定のままなら今と同じで、ジョブがないときの負荷も増えない。
- 悪い影響・トレードオフ
  - 1 つのプロセスの障害で、実行中のジョブがスロットの数だけ止まり、リースの期限まで待つ。パニックは今もジョブごとに回復するが、メモリ不足で落ちると全部が巻き込まれる。
  - 1 つのプロセスの CPU とメモリを、スロットで奪い合う。実際のハンドラのメモリは測っていない。
  - スロットの実行の順序は保証しない。順序キーのないジョブは、今の複数のワーカーと同じく順に終わらない。
  - 1 ホスト 8 接続の上限はプロセス単位のままで、1 プロセスに集めるとその分だけ早く当たる。
  - 設定が増え、プールの最大より小さくする必要があるので、`pool_max_conns` を一緒に考えることになる。既定のプールのままでは 3 スロットまで（1 vCPU の場合）。
  - 接続の数がプールに届く構成は、処理量が増えても起動できない。外部の接続の上限が低い環境では、スロットの上限もそこで決まる。
- 測っていないこと
  - 実際のハンドラ（配送の署名、投稿の取り込みなど）の並行時の処理量とメモリ
  - 実際のリモートのサーバーとの接続（TLS）、DNS、多数のホスト
  - キャッシュの乗らない小さなインスタンス、libSQL、ネットワーク越しの DB
  - 長時間の動作、停止のときに実行中のジョブの数ごとの影響
  - 2 本目の接続で止まる現象を、本物のハンドラや実際のプッシュの受け口で再現すること（試作のハンドラで再現した）
  - 選択肢 1 のポーリングの毎秒 8 が 1 より多い理由（窓の中のスロットの再開と思われるが未確認）
- 後続の作業
  - #2009: トランザクションの中で 2 本目の接続を使う箇所の修正（この ADR の実装より先に行う）
  - #2010: 実装と運用の文書

## Pros and Cons of the Options（詳細比較・任意）

### 選択肢 2: `PullRunner` を並べるだけ

- 良い点: 試作は数行で、`PullRunner` の定めた使い方のまま。
- 悪い点: ジョブがないときのトランザクションがスロットの数に比例する（128 で毎秒 131）。常時動く小さな DB では無視できない。

### 選択肢 3: 1 つの claim のループ

- 良い点: ポーリングが最も少ない（毎秒 2）。空きを確認してから claim する形が単純。
- 悪い点: 128 スロットで 88〜101 件/秒に留まり、32 スロットより遅い。

### 選択肢 4: 種類ごとの同時実行数

- 良い点: 1 つのプロセスで、遅い種類と速い種類に別の数を与えられる。
- 悪い点: claim に種類ごとの空きの判定が要り、ADR-0138 と重なる。プロセスを分ければ同じことができる。

### 選択肢 5: 何もしない

- 良い点: 変更がない。プロセスの障害の範囲が小さく、CPU の取り合いがない。CPU を使うジョブでは、これが正しい選択のままである。
- 悪い点: 待ちの多いジョブで、同じ処理量に多くのメモリが要る（推定 2.7 GiB と約 100 MiB）。
