# ADR-0070: 権限・ロール・バッジ（絵文字の作成、会計の閲覧、参加者の一覧）

- Status: Accepted
- Date: 2026-10-22
- Deciders: @rosylilly
- Issue: #910, #911, #925, #928, #929, #1868

## Decision（決定）

### 1. 権限の区分と組み込みのロール

- 権限 `create_custom_emojis` と `view_finance` を置く。組み込みのロールでは `admin` だけが 2 つの権限を持つ。
- ADR-0058 §4 の区分の 3 つめに **`member`（利用者の機能）** を置く。`member` の権限は、自分のものを作る・変える、または読み取りだけの閲覧を許し、他人の行やサーバー全体に効く変更を許さない。
  `create_custom_emojis` と `view_finance` は `member` に入る。`Category` は `member` の権限を明示して返し、区分の分からない権限を `server` にする扱いは変えない。
- FR-912 の許可リストは「区分が `member` の権限」とする。ADR-0072 はこの区分でプランのロールの権限を検査し、プランのロールの `position` をモデレーターより下に固定する。`member` の権限を後から足すときは、その ADR が区分の条件（自分のものか読み取りだけか）を満たすことを示す。
- ナビゲーション: `member` の権限だけを持つ閲覧者には「モデレーション」も「管理」も出さない（ADR-0058 §2 の規則は `moderation` と `server` の権限だけで決まる）。
  `view_finance` を持つ閲覧者には、レール・サイドバー・メニューのシートの設定の後に「会計」（`/finance`）を足す。`create_custom_emojis` の画面は設定の画面の中（`/settings/custom-emojis`）に置き、ナビゲーションの項目を増やさない。
- 組み込みのロール: `admin` はすべての権限（2 つを含む）を持つ。`moderator` は持たない（いまと同じ `manage_reports`・`manage_accounts`・`view_audit`）。プランのロールは管理者が作る（ADR-0072）。
- 包含: `manage_custom_emojis` を持つ人は申請なしで `/admin/custom-emojis` から作れるので、`create_custom_emojis` の画面と上限は使わない。`manage_finance` を持つ人は `/finance` も読め、そこでは §5 の設定にかかわらずすべての項目を見る。

| 区分 | 画面（Web の経路） | 権限 |
| --- | --- | --- |
| 利用者の機能 | 自分の絵文字（`/settings/custom-emojis`。申請・申請の状態・自分の絵文字の変更と削除・上限と使った数） | `create_custom_emojis` |
| 利用者の機能 | 会計（`/finance`。費用と収入の集計の読み取り） | `view_finance` |
| サーバー管理 | カスタム絵文字（`/admin/custom-emojis`。ADR-0051 の画面に「申請」のタブを足す） | `manage_custom_emojis` |

### 2. 絵文字の作成の申請

- 利用者は、shortcode と画像（自分の upload。ADR-0051 §2 の制約）で**作成の申請**をする。カテゴリと別名は申請に含めず、承認の後に作成者が付ける。
- `manage_custom_emojis` を持つ人が、申請を**承認**するか、理由（任意、500 文字まで。申請者に見える）を付けて**却下**する。申請者は審査の前なら**取り下げ**られる。
- 承認すると、同じトランザクションで ADR-0051 の絵文字（`custom_emojis`・`custom_emoji_images`・既定の設定）を作り、作成者に申請者を記録する。カテゴリなし・ピッカーに出す・有効で作る。
  承認のときに次を検査し、満たさなければ承認は `409` で失敗する（承認する人は却下する）: 申請者がまだ `create_custom_emojis` を持つ、shortcode がローカルの絵文字にない。
- 画像: 承認のときに、申請者の upload の処理結果を、インスタンスの Actor の upload として複製し、絵文字はその複製を指す（ADR-0051 §4 の複製と同じ）。申請者の upload は未添付に戻り、既存の掃除が消す。
  絵文字の画像が申請者のアカウントの削除・消去（FR-803）と一緒に消えないようにするため。申請中の画像は申請者の未添付の upload のままで、どの公開の文書からも参照されない。
- shortcode の予約: 審査中の作成の申請は shortcode を予約し、同じ shortcode の申請とローカルの絵文字の作成を `422`（ADR-0051 の `EmojiShortcodeTaken`）にする。却下・取り下げで予約は外れる。
- 承認されていない申請は、ADR-0051 の読み取りの経路（ピッカー、本文からの抽出、`GET /ap/emojis/{uuid}`、リアクション、`/admin/custom_emojis` の一覧）に一切現れない。申請は別のテーブルにあり、絵文字の行は承認まで存在しないから。

### 3. 作成者による変更と削除

- 作成者が `create_custom_emojis` を持つ間、自分が作った（`created_by_user_id` が自分の）ローカルの絵文字に対して、別名・カテゴリ・ピッカーに出すかの変更と、削除を直接できる。ADR-0051 の管理の操作と同じアプリ層の操作を、作成者の検査を足して呼ぶ。
- **画像の差し替えは申請にする**（種類 `image` の申請。承認すると ADR-0051 の画像の差し替えになる）。承認された画像を後から別の画像に変えて審査を通り抜けられないようにするため。1 つの絵文字に審査中の画像の申請は 1 つまで。
- 無効化と有効化は `manage_custom_emojis` だけが行う（作成者は削除できる）。shortcode は ADR-0051 のとおり変えられない。
- **権限を失った後**: 絵文字は残り、作成者も変更・削除できなくなる。作成者かどうかは操作のたびに「作成者であり、いま `create_custom_emojis` を持ち、アカウントが有効（凍結・削除されていない）」で決めるので、再加入すればまた変更できる。
  `manage_custom_emojis` を持つ人は、作成者にかかわらずすべての絵文字を ADR-0051 のとおり変更・削除できる。
- 作成者のアカウントが消去されても絵文字は残り、管理画面は作成者を「削除されたアカウント」と出す。

### 4. 上限

- `internal/app/content` にポート `CustomEmojiQuota` を置く: `Limit(ctx, userID) (limit int, limited bool, err error)`。`limited` が false なら上限なし。`internal/platform` が実装を組み立てる。
  プランごとの値と、利用者のプランからの導き方は ADR-0072 §11 が決め、その実装を差し込む。課金が無効か、ロールがプランから来ていない（管理者が手で付けた）ときは上限なしを返す。
- 数えるもの: 利用者がその月（UTC の暦月。1 日 00:00 UTC から翌月 1 日 00:00 UTC まで）に出した作成（`kind = create`）の申請のうち、承認された（`approved`）ものと審査中のものの数。月は申請を出した時刻（`custom_emoji_requests.created_at`）で決める。
  - 却下（`rejected`）・取り下げ（`withdrawn`）・失効（`lapsed`）した申請は数えない。
  - 承認した絵文字を後で削除しても、その月の数は減らない（枠は戻らない）。
  - 画像の差し替えの申請（`image`）は数えない。
  - 管理画面や CLI で作った絵文字は申請ではないので数えない（作る人は上限のない管理者のため）。
  - 申請のときに、その月の数が上限以上なら `422` にする。前の月に出して翌月に承認された申請は、出した月に数える。
- 上限の値は「1 か月に作れる数」で、プランの項目の名前は「絵文字の作成数の上限（毎月）」、値の範囲は 0〜10,000 である。
  月の途中で上限が下がったら（プランの変更）、その月のすでに数えた申請と既存の絵文字は残し、数が上限より少なくなるまで新しい申請だけを断る。上限が上がったら、すぐその分だけ申請できる。
- 上限なしのときは数えず、作成した絵文字の数も審査中の申請の数も制限しない。申請の量は承認する人が却下で抑える。
- 使った数の API（`Used`・`Pending`・`Limit`）は、その月の数と、次にリセットされる時刻（翌月 1 日 00:00 UTC）を返す。上限の値も API で返す。
- 画面は「今月の作成 使った数 / 上限」と、次のリセットの日時を閲覧者のタイムゾーンで出す。管理画面のプランの編集の項目の文言もこれに合わせる。

### 5. 会計の閲覧

`view_finance` は、ADR-0067 の費用の集計と ADR-0067 の収入の集計を**読むだけ**で、記録・改定・終了・取り消し・取り込みの開始はできない。
見せる範囲はインスタンス設定の 3 つのキーで決める。ADR-0067 §8 の `finance_visibility` と同じく `manage_settings` で守り、サーバーの設定の画面（`/admin/settings`）の費用の区画に置く。
公開範囲（`finance_visibility` と ADR-0067 §17 の `income_visibility`）とは独立で、`/finance` は少なくとも公開のページに出ている範囲を出す。

| キー | 型（未設定の値） | 内容 |
| --- | --- | --- |
| `finance_viewer_item_names` | `bool`（`false`） | 費用の項目の名前と、取り込んだ費用のサービス名を見せる |
| `finance_viewer_item_memos` | `bool`（`false`） | 費用の項目のメモを見せる |
| `finance_viewer_income` | `enum(totals, plans)`（`totals`） | 収入を合計だけ（`totals`）か、加えてプランごとの加入者の数まで（`plans`）見せる |

- **常に見せる**: 期間ごとの通貨ごとの費用の合計（按分と現金主義、ADR-0067 §4）、事業者・区分ごとの内訳（項目の名前とメモではないので、設定によらず見せる）、見込みの印、区切りの規則（ADR-0067 §5）。
  収入は ADR-0067 が決める手数料を引いた合計を、期間ごと・通貨ごとに見せる。
- **設定で足すもの**: 名前かメモのどちらかが有効なら、期間ごとに項目の行（事業者・区分・その期間の額に、有効なら名前・メモ）を出す。メモだけが有効なら、名前のない行にメモが付く。
  `plans` なら、ADR-0067 §17 が決める時点でのプランごとの加入者の数を出す。プランごとの金額は出さない。
- **どの設定でも見せないもの**: 誰がいくら払ったか、加入者の名前やアカウント、決済の事業者の顧客や取引の ID、費用の改定の履歴、記録した人。これらは `manage_finance` を持つ人だけが管理画面で見る。
- API: 利用者の名前空間に `GET /finance/cost_totals`（ADR-0067 §9 の `GET /admin/cost_totals` と同じ問い合わせで、設定で省くフィールドを返さず、項目の行 `items` を足す）と、ADR-0067 の収入の集計を置く。
  どちらもタグ `finance`、新しいスコープ `read:finance`（`read` に含む）と `view_finance` か `manage_finance` を要する。応答は閲覧者ごとに変わらないが、権限で守るので `Cache-Control: private, no-store` にする。
  `GET /instance` には何も足さない（設定の値は `/finance` の応答に含めて返す）。
- `/admin/finance` は、いまの 3 つの設定を示し、`manage_settings` を持つ閲覧者にはその設定へリンクする（ADR-0067 §7 の公開範囲と同じ扱い）。

### 6. API の置き場所

- 利用者の名前空間（タグ `custom-emojis`、新しいスコープ `read:custom_emojis` / `write:custom_emojis`。`read` / `write` に含む）:
  `GET /custom_emoji_requests`（自分の申請。キーセットページング）、`POST /custom_emoji_requests`（作成か画像の申請）、`POST /custom_emoji_requests/{id}/withdraw`、
  `GET /custom_emojis/mine`（自分が作った絵文字と、上限・使った数）、`PATCH /custom_emojis/mine/{id}`（別名・カテゴリ・ピッカー）、`DELETE /custom_emojis/mine/{id}`。どれも `create_custom_emojis` を要する。
- 管理（タグ `admin-server`、`admin:read` / `admin:write` と `manage_custom_emojis`）: `GET /admin/custom_emoji_requests`（審査中を既定にし、状態で絞り込む）、
  `POST /admin/custom_emoji_requests/{id}/approve`、`POST /admin/custom_emoji_requests/{id}/reject`（理由）。`/admin/custom_emojis` の表現に `created_by`（作成者のアカウント、NULL 可）を持つ。
- 管理の名前空間の `admin:*` のスコープを、スタッフでない利用者のトークンに求めない。`member` の操作を `/admin/*` に置かないのはこのため。
- CLI: `my admin emoji requests`（一覧・承認・却下）を足す。経路とフィールドの細部は [client-api.md](../architecture/client-api.md) の手順で決める。

### 7. データモデル（`content` が持つ。ADR-0020）

| テーブル | 分類 | カラム | 制約・規則 |
| --- | --- | --- | --- |
| `custom_emojis` | リソース（ADR-0051） | `created_by_user_id`（NULL 可） | 作った利用者。CLI とリモートの絵文字は NULL。承認で作った絵文字は申請者、管理画面で作った絵文字と複製はその管理者。変えない |
| `custom_emoji_requests` | リソース | `id`, `kind`（`enum(create, image)`）, `requester_user_id`, `emoji_id`（NULL 可。`image` の対象）, `shortcode`, `media_id`, `created_at` | `kind = 'create'` は `emoji_id` が NULL、`image` は NULL でない（`CHECK`）。`image` の `shortcode` は対象の写し |
| `custom_emoji_request_outcomes` | イベント | `id`, `request_id`（一意）, `outcome`（`enum(approved, rejected, withdrawn, lapsed)`）, `decided_by_user_id`（NULL 可 = CLI と `lapsed`）, `reason`（NULL 可、500 文字まで。`rejected` だけ）, `emoji_id`（NULL 可。`approved` の結果の絵文字）, `decided_at` | 行がない申請が審査中。`lapsed` は対象の絵文字が削除された画像の申請 |
| `custom_emoji_pending_requests` | 投影 | `request_id`（PK）, `requester_user_id`, `reserved_shortcode`（NULL 可。`create` だけ）, `emoji_id`（NULL 可。`image` だけ） | 一意 `(reserved_shortcode)`, `(emoji_id)`。インデックス `(requester_user_id)`。申請で行を作り、結果の行と同じトランザクションで消す。`custom_emoji_requests` と結果から再構築できる |

- 審査中・却下などの状態を nullable な時刻で表さず、結果のイベントと審査中の投影で表す（ADR-0020 規約 4）。
- 終わった申請の行は残し、申請者の画面の履歴と監査ログの対象の表示名に使う。画像の upload は結果の後に未添付に戻るので、却下された画像の Blob は既存の掃除が消す。
- 絵文字の削除（ADR-0051 §1）は、その絵文字を対象とする審査中の画像の申請を `lapsed` で閉じる。

### 8. 監査ログと webhook

- **ADR-0058 の監査ログ**: `target_kind` に `custom_emoji_request`（`target_label` は `:shortcode:`）を持ち、`action` に `custom_emoji_request_submitted`・`custom_emoji_request_withdrawn`・`custom_emoji_request_approved`・`custom_emoji_request_rejected` を持つ。
  承認は、申請への `custom_emoji_request_approved` と、作った絵文字への `custom_emoji_created`（画像の申請は `custom_emoji_image_replaced`）の 2 行を、承認した人を操作者として残す。
  作成者による変更と削除は、ADR-0051 の `custom_emoji_updated`・`custom_emoji_deleted` を、作成者を操作者として残す。ADR-0058 の他の規則は変えない。
- 会計の閲覧は記録しない（読み取りは監査ログの対象でない）。§5 の 3 つの設定の変更は、既存の設定の変更（`setting_changed`）として残る。
- webhook（ADR-0060）は、承認で `custom_emoji.created`（画像の申請は `custom_emoji.updated`）、作成者の変更で `custom_emoji.updated`、削除で `custom_emoji.deleted` を出す。申請そのものには webhook のイベントを持たない。

### 9. 通知

- `admin_custom_emoji_request`: 作成と画像の申請を、`manage_custom_emojis` を持つ人に送る（`admin_sign_up` と同じ配り方・重複の排除のキーは申請ごと）。リンクは `/admin/custom-emojis` の申請のタブ。
  ADR-0058 §2 のとおり「管理」には件数のバッジを付けず、審査中の件数は絵文字の画面のタブに出す。
- `custom_emoji_request_decided`: 承認と却下を申請者に送る（却下の理由を含む）。取り下げと `lapsed` は送らない。
- 通知の種類の enum・Web Push・メールの文言は既存の通知と同じ仕組みで持つ（ADR-0009 のカタログ、`locales/en` と `locales/ja`）。

### 10. バッジの属性

- バッジはロールの属性で、1 つのロールに 0 か 1 つ。持つのは**名前**（`label`、1〜32 文字の 1 行）と**色**（`neutral`・`red`・`orange`・`yellow`・`green`・`teal`・`blue`・`purple`・`pink` の 9 色の名前）だけである。
- 名前は管理者が書く文字列で、どのロケールでも同じ値を出す（インスタンスのルールと同じ扱い、data-model §4.9）。翻訳の機構は持たず、UI の文言ではなく利用者の内容として `dir="auto"` で描く。
  ロールの `key`（`small-support` など）は管理のための識別子で、利用者には出さない。
- 色は `@my/ui` のトークン `badge-<色>`（背景）と `badge-<色>-fg`（文字）の組で、ライトとダークの両方で 4.5:1 を `scripts/task.sh web:tokens` が検査する。
  サーバーのテーマ（ADR-0059）はバッジのトークンを上書きしない。色は飾りで、意味は名前が運ぶ（WCAG 1.4.1）。
- アイコンは持たない。
- 組み込みのロールを含め、どのロールにもバッジを付けられ、既定ではどのロールもバッジを持たない。バッジの設定・変更・削除は `manage_roles` を持つ人が行い、FR-720 の位置の規則（自分のいちばん高いロール以下だけ）に従い、監査ログの `role_updated` に残す。
- 本人が出すかどうかは、運用者のロールでも課金のロールでも同じく本人が選ぶ（ロールの設定で常に出す形は持たない）。

### 11. 本人の掲出

- 利用者は、自分が持っていてバッジのあるロールごとに、プロフィールに出すかを選ぶ。既定は出さない。
- 出るのは「いま持っているロール（`user_roles`）で、バッジがあり、本人が出すと選んだもの」で、ロールの `position` の高い順に並べる。数の上限は置かない。
- ロールが剥奪されたとき（解約後の期間の終わり・支払いの失敗の猶予の後・返金を含む）と、ロールのバッジが削除されたときは、その選択を同じトランザクションで消す。もう一度付与されれば、また既定の「出さない」から始まる。
- プランの変更でロールが入れ替わるとき（small → medium）は、選択を引き継ぐ。`identity` は、古いロールの剥奪と新しいロールの付与を 1 つのトランザクションで行い、古いロールの選択を新しいロールに移す操作を出し、プランのモジュール（ADR-0072）はプランの変更でこの操作を使う。新しいロールにバッジが無ければ、選択は消える。

### 12. 出す場所と API

- バッジはプロフィールにだけ出す。Web では、プロフィールの見出し（表示名とハンドルの近く）に、見出しの付いたリスト（アクセシブルな名前は `client` の文言「バッジ」）で出す。投稿の作者の表示・通知・アカウントの一覧には出さない。
- API:
  - アカウント自身の取得（`Server.newProfile` が作る応答。`GET /accounts/{id}`・`GET /accounts/lookup`・`verify_credentials`）の `Account` に `badges`（`[{role_id, label, color}]`）を足す。一覧の `Account`（`newAccounts`・`presentStatuses`）では空の配列を返し、読みに行かない。リモートのアカウントはいつも空。
  - 本人の選択: `GET /preferences/badges`（`read:accounts`）が、持っていてバッジのあるロールごとに `{role_id, label, color, displayed}` を返し、`PUT /preferences/badges/{role_id}`（`write:accounts`、本文 `{displayed: bool}`）が変える。持っていないかバッジの無いロールは `404`。Web は `/settings/profile` にこの区画を置く。
  - 管理: `PATCH /admin/roles/{role}` の本文に `badge`（`{label, color}` か `null` で削除）を足し、`AdminRole` に `badge` を返す。`/admin/roles` の画面にバッジの名前と色を選ぶ欄と、見本を置く。
- ActivityPub: Actor の JSON-LD（`attachment`・`tag`・拡張の項目を含む）、NodeInfo、WebFinger のどれにもバッジを載せない。リモートのバッジも取り込まない。

### 13. 参加者の一覧

- インスタンス設定のキー `supporter_list_visibility`（`enum(off, public, signed_in)`、未設定は `off`）を `instance` に置く。`manage_settings` で守り、サーバーの設定の画面から変える（ADR-0067 の `finance_visibility` と同じ扱い）。
  - `off`: API は `404`、Web は一覧への導線を出さない。
  - `public`: 誰でも見られる。
  - `signed_in`: このサーバーにサインインした人だけが見られる。サインインしていなければ API は `401`、Web はサインインへ案内する。
- 本人の掲載: 加入している利用者が、自分を一覧に載せるかを選ぶ。既定は載せない。選択は利用者ごとに 1 つで、プランごとには持たない（同時に加入できるプランは 1 つ）。プランを変えても選択は残り、加入が終わったとき（ロールが外れる時と同じ）に同じトランザクションで消える。
- 出す項目: プランごとの見出し（プランの名前、プランの並び順）と、各人のアバター・表示名・ハンドル・プロフィールへのリンクだけを出す。
  金額・月払いか年払いか・加入した日・続けた期間・人数の合計は出さない。人数は収入の公開（ADR-0067）の範囲の設定に従う情報で、一覧の行の数を数えても載せた人の数しか分からない。
- 一覧に出す人は、閲覧者に見せられるアカウント（[visibility.md §6](../architecture/visibility.md#6-アカウントの表示)、`Server.visibleAccount` と同じ規則。凍結・制限されたアカウントと、閲覧者とブロックの関係にあるアカウントを除く）に限る。並びは載せた順（新しい順）で、カーソルでページを送る。
- ページは Web の `/about/supporters` で、`/about` から `supporter_list_visibility` が `off` でないときにリンクする。
- API（タグ `instance`）: `GET /instance/supporters?plan_id=&cursor=`。`public` のときは `security: []`、`signed_in` のときはトークンを要する（`read:accounts`）。`Cache-Control` は `public` のとき `public, max-age=60`、`signed_in` のとき `private, no-store`。
  `GET /instance` は `supporter_list_visibility` を返し、Web はそれで導線を出し分ける。本人の掲載の選択は `GET/PUT /preferences/supporter_listing`（`{listed: bool}`）で、加入していなければ `PUT` は `404`。
- クローラー: `/about/supporters` の外枠と API の応答は、サーバーの設定に関わらずいつも `noindex, noarchive`（meta と `X-Robots-Tag`）にする。AI の表明は ADR-0057 のとおりサーバーの設定に従う。一覧は ActivityPub・NodeInfo に出さない。

### 14. プランとの契約（ADR-0072 が満たす）

プランの資源と加入の状態はここでは決めない。一覧と掲載の選択のために、ADR-0072 のプランのモジュールに次を求める。

- プランの一覧（`id`・名前・並び順・結び付くロール）を読める。廃止したプランは一覧に出さない。
- 「いまプラン X に加入している利用者」を、ロールが付いている期間と同じ定義で列挙できる（解約後の期間の終わりまでは加入中、猶予の間も加入中）。
- 掲載の選択の表（§15）を持ち、加入が終わる処理と同じトランザクションでその行を消す。
- 上位のプランの人は、上位のプランの見出しにだけ出る（ロールは 1 つだけ付く）。
- プランの変更では、ロールの入れ替えに `identity` の選択を移す操作（§11）を使い、バッジの掲出の選択を引き継ぐ。

### 15. バッジと参加者の一覧のデータモデル

| テーブル | 分類 | 持つモジュール | カラム | 制約 |
| --- | --- | --- | --- | --- |
| `role_badges` | 現在値 | `identity` | `role_id`（PK）, `label`（`string(32)`）, `color`（`enum(neutral, red, orange, yellow, green, teal, blue, purple, pink)`）, `updated_at` | 行がある = バッジがある |
| `user_role_badge_displays` | 現在値 | `identity` | `user_id`, `role_id`, `created_at` | PK `(user_id, role_id)`。行がある = 出す |
| `supporter_listings` | 現在値 | ADR-0072 のプランのモジュール | `user_id`（PK）, `created_at` | 行がある = 載せる |

- インスタンス設定は `instance_setting_revisions` のキー `supporter_list_visibility` で、`instance_settings` の投影に入る。
- 「選んだか」を NULL 許容の列や真偽の列で持たず、行の有無で表す（ADR-0020 規約 4）。本人の選択は履歴を問わない設定で、`user_preferences` と同じく現在値にする。
- ロールの剥奪（`user_role_revocations` を足す処理）とバッジの削除が `user_role_badge_displays` を、加入が終わる処理が `supporter_listings` を、同じトランザクションで消す。ロールの削除は持っている人がいないときだけできる（data-model §4.1）ので、`role_badges` の行もそのとき消す。
- プロフィールのバッジは `user_roles`・`role_badges`・`user_role_badge_displays` の結合 1 回で読み、アカウント自身の取得でだけ行う。

### この決定を覆す条件

- 承認の待ちが長く、承認する人の負担が問題になったら、信頼できるロールに審査なしの作成を許す権限（たとえば `create_custom_emojis_unreviewed`）を別の ADR で検討する。
- 画像の差し替えの申請がほとんど使われず、作成者が削除と作り直しで済ませていると分かったら、画像の申請をやめる。
- `member` に入れたい権限が、自分のものでも読み取りだけでもない（他人に効く）と分かったら、区分の条件を見直す。
- 月の初めに申請が集中して、承認する人の負担が問題になったら、上限を直近 30 日の移動窓で数える形にする。
- 投稿の作者の表示にもバッジを求める声が強いとき（タイムラインの読み出しに 1 回の結合を足す設計が要る）。
- 名前を言語ごとに変えたい運用者が多いとき（ロケールごとの名前の表）。
- アイコンを求められたとき（ローカルのカスタム絵文字の ID を `role_badges` に足す）。

## 経緯

M4.2（Supporters、Epic #925）は、課金のプランに結び付いたロールに、絵文字の作成（FR-915）と会計の閲覧（FR-916）を渡す。medium プランは絵文字を増やせるが他人の絵文字は更新・削除できず、large プランは管理者にしか開示していない会計レポートを読める。
当時の権限は全部か無しかだった。`manage_custom_emojis`（ADR-0051）はすべての絵文字の操作を許し、`custom_emojis` は作成者を記録せず、`manage_finance`（ADR-0067 §7）は費用の記録と集計の閲覧の両方を許した。プランのロールに渡せないので、2 つの権限と第 3 の区分 `member` を足した。判断の軸は、承認されていない絵文字がどの経路にも載らないこと、払った分より強い権限を渡さないこと、払った人の個人情報を出さないことだった。ローカルの絵文字の作成を `create_custom_emojis` の申請でも行うこと、作成者の操作、`created_by_user_id`、区分の 3 つめは、ADR-0051 と ADR-0058 の側に反映している。

バッジと参加者の一覧（FR-913・FR-914、#928）では、バッジも一覧も本人が選ぶまで何も出さないこと、どのテーマでも読めること（文字の対比 4.5:1、色だけで意味を伝えない）、ロールの仕組みを 1 つに保つこと、タイムラインに N+1 を足さないことを軸にした。バッジと一覧は ActivityPub に載せない。一覧を見られる範囲はサーバー管理者が設定する。

作成数の上限は当初、存在する絵文字と審査中の申請の合計を数え、削除すれば枠が空いた。上限まで作った人はサポーターを続けても作れる数が増えないので、#1868 で UTC の暦月ごとの申請数を数える形に変えた（§4）。ポート、上限なしの扱い、ADR-0072 §11 の導き方は変えていない。

参考にした他の実装（一次資料を確かめていない。決定には効かない。要検証）: Mastodon はロールに名前・色（自由な 16 進）・`highlighted` を持たせ、出すかどうかはロールで決まり、投稿の作者の表示には出さず、ActivityPub に載せない。Misskey はロールに名前・色・アイコンの画像を持たせ、ノートの作者名の横にアイコンを出し、連合先に送らない。

## 採らなかった案

- 申請のときに絵文字の行を「審査中」で作る: 承認は状態を変えるだけで画像の複製もいらない。すべての読み取りの経路に「審査中を除く」が要り、1 か所の漏れで承認されていない画像が連合先に送られ、取り消せない。
- 作成者がすべて直接変更できる: 審査の待ちがなく実装も小さい。承認の後に画像を差し替えれば審査を素通りできる。
- 作成者の変更をすべて申請にする: 承認する人がすべて見る。ピッカーの検索と並びにしか効かない別名やカテゴリまで待たせる。
- `server` の区分に入れ `/admin/*` に置く: 区分も名前空間も増えない。支払った利用者に「管理」が出て、スタッフでない人のトークンに `admin:*` を求め、FR-912 の許可リストを別の表で持つことになる。
- 上限をインスタンス設定の 1 つの値にする: 実装が最も小さい。プランごとに変えられない。
- 上限をロールの属性にする: `identity` だけで決まり、手で付けたロールにも効く。上限は課金のプランの属性（FR-910）で、値が 2 か所にできる。
- 会計の見せ方を `finance` の設定（`manage_finance`）にする: 書いた本人が見せる先を決められる。見せる範囲の設定が 2 つの権限に分かれ、ADR-0067 §8 と食い違う。
- 月内に承認された数だけを数える: 単純だが、審査中を数えないので月末に大量に申請でき、承認する人が上限を数えて却下することになる。
- 直近 30 日の移動窓で数える: 月初の集中が起きない。いつ何件空くかが申請ごとに違い、説明しにくい。
- 自由な色（16 進）を入れ対比を検査する: ブランドの色を使える。ライトとダークの両方で読めるとは限らず、サーバーのテーマ（ADR-0059）で背景が変わると検査をやり直す。
- 自由な色を受け文字の色を黒か白で選ぶ: 入力が 1 つで済む。周りの背景との対比（非文字の 3:1）を保証できず、中間の明るさで 4.5:1 に届かないことがある。
- バッジのアイコンにローカルのカスタム絵文字を選ぶ: 画像の保存を足さない。絵文字の削除・無効化との関係を決める必要があり、狭い幅の配置と読み上げの順を設計し直す。画像を上げる案は保存・代替テキスト・モデレーションが要る。
- 課金のロールだけにバッジを付ける: FR-913 の最小の範囲。ロールに課金かどうかの区別を持ち込み、運用者のバッジを後で足すときに作り直す。
- 運用者のロールは常に出す: 誰がモデレーターかを利用者が知れる。ロールによって規則が変わり、モデレーターであることを出したくない人の選択が無くなる。
- 投稿の作者の表示にもバッジを出す: どこでもサポーターと分かる。タイムラインの全件の作者についてロールとバッジを読み、狭い幅で表示名を圧迫する。
- 本人の選択をイベントと投影で持つ: 履歴を残せる。読む機能が無く維持が増え、個人的な選択の履歴を長く持つこと自体が望ましくない。
- 一覧のページのクローラーへの表明を設定に従わせる: ADR-0057 のほかのページと同じ規則になる。載っている人の `indexable` がまちまちで、掲載を選んでも検索への掲載まで選んだとは限らない。

## Consequences（影響）

- 良い: 承認されていない絵文字は行そのものがないので、既存の読み取りの経路を変えずにどこにも出ない。
- 良い: プランのロールの権限は `member` の区分で検査でき、FR-912 の許可リストが権限の定義と一緒に保たれる。スタッフでない利用者に「管理」も `admin:*` も要らない。
- 良い: 作成者を記録するので誰が作った絵文字かが分かり、権限を失った後の扱いも操作のときの検査 1 つで決まる。
- 良い: 会計の見せ方は 3 つのキーだけで、既定は最も狭い。個人ごとの支払いはどの設定でも出ない。
- 良い: サポーターを続ける人は毎月上限まで新しい絵文字を作れ、審査中の申請も数えるので申請を溜めて上限を超えられない。
- 良い: 本人が選ぶまでバッジも一覧も何も出さず、権限の元がなくなれば表示も消え、再加入しても既定に戻る。
- 良い: 色はトークンの組なのでどのテーマでも対比が保証される。ロールの仕組みは 1 つのままで、運用者のロールにも同じバッジが使える。タイムラインの読み出しも ActivityPub の形式も変わらない。
- 悪い: 申請・結果・審査中の投影の 3 つのテーブルと、2 つの通知の種類、2 つの画面、新しいスコープ 3 つが増える。
- 悪い: 承認のときに画像の Blob を複製するので、申請者の upload が掃除されるまで一時的に Blob が増える。
- 悪い: 審査中の申請が shortcode を予約するので、審査されないまま残るとその shortcode を管理者も使えない。管理者は却下してから作る。
- 悪い: 作成者は画像を直接差し替えられず、差し替えのたびに審査を待つ。
- 悪い: `plans` を選ぶと、加入者の少ないプランでは人数から誰が加入しているかが推測できることがある（参加者の一覧やバッジと合わせると特に）。設定の画面にこのことを書く。
- 悪い: `/admin/finance` と `/finance` の 2 つの画面が同じ集計を出す。
- 悪い: `member` の区分が増え、`Category` と ADR-0058 のナビゲーションの規則、`my admin role` の表示が 3 つの区分を扱う。
- 悪い: 管理者が手で付けたロールには上限がないので、その利用者が申請を大量に出すと、承認する人が 1 件ずつ却下することになる。
- 悪い: 1 人が作れる絵文字の総数に上限がなく、ローカルの絵文字は増え続ける。数を抑えるのは承認する人の却下と作成者自身の削除だけである。削除しても枠が戻らないので、作り直しの申請はその月の枠を使う。
- 悪い: 月の区切りは UTC で、日本では毎月 1 日の 9:00 にリセットされる。画面でリセットの日時を出して補う。
- 悪い: 色は 9 色だけで、サーバーのブランドの色を使えない。アイコンが無く、絵のバッジは作れない。
- 悪い: バッジの名前は 1 つの値で、多言語のサーバーでは管理者がどの言語で書くかを選ぶ。
- 悪い: 運用者のロールのバッジも本人が出さなければ出ず、「この人はモデレーター」と示すことをサーバーが強制できない。
- 悪い: 投稿の作者の表示にバッジが無いので、サポーターであることはプロフィールを開かないと分からない。
- 悪い: 一覧はいつも `noindex` で、サーバーが検索を許していても検索エンジンに載らない。
