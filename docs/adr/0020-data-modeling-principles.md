# ADR-0020: データモデリングの規約（リソース・イベント・投影の分離と状態の直交分解）

- Status: Accepted
- Date: 2026-10-16
- Deciders: @rosylilly
- Issue: #45

## Decision（決定）

**テーブルをリソース / イベント / 投影の 3 種類に分類し、正規化する（イミュータブルデータモデルと CQRS の読み取りモデルを組み合わせる）。** 以下を規約として、論理データモデル（[data-model](../architecture/data-model/README.md)）とすべての後続設計に適用する。

### 規約 1: テーブルを 3 種類に分類する

| 分類 | 意味 | 書き込み | 例 |
| --- | --- | --- | --- |
| **リソース** | 識別子を持ち、ライフサイクルを通じて存在する「もの」。不変の事実（作成時に決まる属性）だけを持つ | INSERT のみ（例外は規約 6 の消去） | `actors`, `statuses`, `follows`, `users` |
| **イベント** | 起きた事実。**日時属性を 1 つだけ** 持ち、どのリソースに起きたかを参照する | INSERT のみ。訂正は新しいイベントで行う | `moderation_actions`, `follow_acceptances`, `status_revisions` |
| **投影** | イベントから導出した、読み取り用の現在値。同じイベント列から **再構築できる** ことを保証する | 投影を所有するモジュールの projector だけが UPSERT / DELETE する | `actor_restrictions`, `follow_edges`, `feed_entries` |

- 変わり得る属性は、リソースの UPDATE ではなく **版（リビジョン）のイベント** として持つ。プロフィールや投稿本文が該当する。現在版は投影で指す。
- 投影には「どのイベントから作るか」と「再構築コマンド」を必ず定義する。再構築は CLI から実行できるようにする（FR-801）。

### 規約 2: 状態は直交する軸に分解する

1 つの `status` enum に詰め込まず、責任を持つ主体ごとに独立した軸として持つ。軸ごとにイベントと投影がある。

| 軸 | 主体 | 例 |
| --- | --- | --- |
| 登録審査 | 運営 | 申請中 / 承認 / 却下 |
| メール確認 | 本人 | 未確認 / 確認済み |
| ライフサイクル | 本人（とシステム） | 有効 / 本人による無効化 / 削除予約 / 削除済み |
| モデレーション上の制限 | モデレーター / ドメイン単位の処分 / 連合先 | サイレンス / 投稿禁止 / ログイン停止 / 凍結 / BAN / メディアの強制センシティブ … |
| 権限 | 管理者 | ロールの付与 / 剥奪 |

「ログインできるか」「投稿できるか」「この公開範囲で投稿できるか」は、軸の組み合わせからドメイン層のポリシー関数で判定する。

### 規約 3: モデレーションは「処分（イベント）」と「制限（能力の剥奪）」に分ける

- **処分**（`moderation_actions`）は、モデレーターが下した決定の記録。種類・理由・根拠の通報・処分者・開始・期限を持ち、不変。解除は別のイベントで表す（`moderation_action_lifts`）。
- **制限**（`actor_restrictions`）は、有効な処分から導出した「剥奪されている能力」の投影。処分の種類と制限の対応はドメインのコードで定義する。対応を変えたら投影を再構築する。
  - 能力の例: ログイン、投稿、公開範囲の上限、公開タイムラインや検索への露出、メディアの非センシティブ表示、連合。
- 新しい処分の種類を追加するときは、enum に値を足し、制限への対応を書くだけでよい。テーブル変更は要らない。
- ドメイン単位の処分（ドメインブロック）も同じ型で持ち、アカウントの制限と合成する。

### 規約 4: 正規化

- 少なくとも第 3 正規形（BCNF を目標）。繰り返し属性・多値属性は子テーブルにする。
- **JSON は「解釈しない文書」だけに使う**: 受信した ActivityPub 文書の原本、外部 API の応答など。検索条件・一意制約・部分更新・翻訳の対象になる値は JSON に入れない。
- 「状態を表す NULL 許容カラム」を作らない。任意の事実は、その事実を表すイベントの行の有無で表す。
- 部分型（ローカル / リモートの Actor、ローカル投稿の入力ソース）は、NULL カラムではなく部分型テーブルで表す。
- **不変な事実の非正規化は許容する**（例: 投稿の公開範囲を投影にコピーする）。変わり得る値の非正規化は、投影として projector の管理下に置く場合に限る。

複数の値を持つ `login_provider_revisions.scopes`・OAuth の `scope`・設定の `featured_accounts` は、項目ごとに絞り込まず制約もしないので、1 つの文字列のカラムのままでよい。

### 規約 5: 履歴に意味がない高頻度の関係と設定値は「現在値」として持つ

お気に入り・ブックマーク・ミュート・ピン留めなどの関係と、利用者設定・フォローごとの設定などの設定値は、履歴に業務上の意味がなく、変更・取り消しが頻繁にある。
これらは規約 1 の例外として、行の存在 = 現在値とし、取り消しは物理削除する。連合上の履歴は `received_activities` と配送記録に残る。

次も規約 1 の例外とする。

- 消去と保持期間によらない `relays`（`relay_events` を含む）・`custom_emojis`（`custom_emoji_images` を含む）・`roles`・`lists` の削除。管理者の操作の履歴は監査ログに残る。
- `roles.position` の UPDATE。並びの履歴に意味はない。
- `my kek rewrap` の再暗号化（`ReplaceSealed*`）の UPDATE。値の意味は変わらない。
判定基準は「その履歴を、監査・モデレーション・連合の整合・利用者への説明に使うか」。使うなら規約 1、使わないなら規約 5。

### 規約 6: 消去（プライバシー）はイベントの不変性より優先する

- 個人データ（本文・プロフィール・メールアドレスなど）はリソースや版のテーブルに置く。イベントには参照と分類だけを持たせる。
- 削除・消去は「消去イベント」を記録したうえで、消去ジョブが個人データの行を物理削除する。
  - 投影は再構築すれば消える。
  - 連合の重複排除に必要な URI だけは残す（tombstone）。
- 処分の記録は、法令対応・再発防止のため、本文の消去後も（理由・種類・日時のみ）保持期間内は残す。

### 規約 7: 投影の更新は同期を既定とする

- **同期投影（既定）**: コマンドと同じトランザクションで、イベントを購読するモジュールの projector が、自分の投影テーブルを更新する。
  書き込み主体は常に所有モジュールなので、テーブルの所有権（ADR-0002）は守られる。read-your-writes が保証される。
- **非同期投影**: 件数が利用者数・フォロワー数に比例する投影や重い投影は、outbox → ジョブで更新する。
- **連携メッセージ**（outbox → キュー）とは区別する。永続化された事実はイベントテーブル、プロセス内の通知はドメインイベント、外部・非同期への連携は outbox、と 3 つを混同しない。

## 経緯

アカウントの状態だけをとっても、有効・無効のほかに、サイレンス（全投稿がフォロワー限定になる）、投稿禁止、ログイン停止、凍結、BAN などがある。これらは種類が増え、重なり、期限を持ち、誰がなぜ下したかの説明責任を伴う。投稿・プロフィール・フォロー関係も、編集・承認・取り消しといった時間に沿った変化を持つ。

1 エンティティ 1 テーブルで現在値だけを持つ設計（状態を NULL 許容の時刻カラムで表す、性質の違う概念を 1 テーブルに同居させる、状態遷移を行の移動で表す、繰り返し属性を JSON に入れる）では、状態の種類が増えるたびにカラムが増え、期限・理由・処分者・解除の履歴と重なったときの合成規則を表せない。遷移の事実（いつ・誰が承認したか）が残らず、JSON に入れた値には制約・検索・部分更新を適用できず、読み取りを速くするためにモジュール境界（ADR-0002）の例外が要る。

監査と利用者への説明に使える形で事実を残し、読み取りの性能とコスト（NFR-COST）を落とさず、削除・消去の要求（プライバシー、FR-008）と両立し、複雑さが v0 の規模に見合うことを基準に選んだ。

## 採らなかった案

- 現在値モデル（1 エンティティ 1 テーブルで、状態はカラムで持つ）: 最も単純だが、上の問題が起きる。
- 完全なイベントソーシング（すべての状態を単一のイベントストアから再生する）: 履歴と再構築の一貫性は最も強いが、実装・運用の複雑さが v0 の規模に見合わない。

## Consequences（影響）

- 処分・状態の種類が増えても、テーブル変更なしで対応できる。
  - 「なぜこの利用者は投稿できないのか」を、処分の記録から説明できる（利用者への通知・異議申し立ての基盤）。
- タイムラインは自前の投影（`feed_entries` など）を読むため、ADR-0002 の例外（他モジュールのテーブルの直接 JOIN）が不要になる。
- 書き込み行数は、イベント + 投影でおおむね 1.5〜2 倍になる。従量課金 DB の書き込みコストが増えるが、読み取りは投影 1 本で済むので総量は抑えられる見込み（M2 で計測）。
- テーブル数が増える。各テーブルの分類・所有者・再構築手順を [data-model](../architecture/data-model/README.md) に必ず書き、方言別スキーマとの乖離は CI で検査する（ADR-0003）。
- 投影の再構築・整合性検査（イベントから作り直した結果と現在の投影の比較）を、テスト（コントラクトテスト）と CLI の両方で用意する必要がある。
