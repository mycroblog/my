# ADR-0133: ログインと登録を外部 IdP だけに制限するインスタンス設定

- Status: Accepted
- Date: 2026-11-02
- Deciders: @rosylilly
- Issue: #1955

## Context（背景・課題）

[ADR-0106](0106-external-login-providers.md) は、外部 IdP でのログインと登録を、メールアドレスとパスワード（FR-002）とパスキー（FR-004）に**足す**決定である。
組織の IdP だけを入口にして退職者の扱いや多要素認証の方針を IdP に任せたいサーバーでは、ほかの入口が残ること自体が困る。これを決める Accepted ADR はない。

Decider の依頼と回答（Issue #1955）:

> 「Login Provider がひとつ以上設定されている時、メールアドレスとパスワードによる登録・ログインを禁止して LoginProvider のみでの認証に制限する機能が欲しい」

- パスキーについて: 「パスキーも止める」
- IdP をひも付けていない既存の利用者について: 「警告して管理者に任せる」
- 有効な IdP がなくなったときについて: 「自動でパスワードに戻す」
- この ADR について: 「Accepted に」
- ブラウザの Cookie のセッションだけ切れた利用者のひも付けについて: 「このまま受け入れる」
- 有効な IdP を足すと制限が始まるときの管理画面の警告について: 「追加」

既存の規約で効くものは次のとおり。

- アカウントはメールアドレスでひも付かない（ADR-0106 §3）。パスワードだけの利用者が IdP に移る道は、ログイン中に設定の画面でひも付けることだけである。
- ひも付けには、パスワードかパスキーか別の IdP での確認がいる（`confirm`、ADR-0106 §3.5）。
- インスタンス設定は再起動なしに変わり、変更は監査ログに残る（ADR-0010、FR-704、FR-705）。
- 利用者は最後のログイン手段を失えない（`ErrLastSignInMethod`）。

## Decision Drivers（判断基準）

1. 断りの正しさ: 画面を隠すだけでなく、サービスとハンドラがどの経路でも断る。開いたままの画面からの POST も断る。
2. Decider が選んだ移行の道を壊さない: ログイン中のパスワードとパスキーの**確認**は動き続ける。
3. アカウントの有無を漏らさない: どのメールアドレスとパスワードでも同じ答えにする。
4. 運営者が締め出されない: CLI から戻せる。IdP がなくなれば自動で戻る。
5. 最小の変更: 新しい概念を増やさず、既存のインスタンス設定とログインの流れに載せる。

## Considered Options（選択肢）

1. **パスワードとパスキーのログインを止め、確認は残す。IdP のない既存の利用者は警告して管理者に任せる**（採用）
2. パスキーのログインは残し、パスワードだけ止める
3. 猶予のモードを置く: 制限の間も、IdP をひも付けるためだけにパスワードとパスキーでのログインを許す
4. パスキーと、ひも付けていない既存の利用者には制限をかけない

## Decision（決定）

選択肢 1 を採用する。

### 1. 規則

インスタンス設定 `login_providers_only`（真偽値、既定 `false`）を足す。

**制限中 = 設定が `true` かつ、ログインに使える IdP がひとつ以上ある**

規則は `identity.Service.LoginProvidersOnly` の 1 か所にある。ログインに使える IdP は、ログインの画面にボタンが出るもの（`ExternalLoginProviders`）と同じで、無効・削除の IdP とドメインの措置の下にある Mastodon サーバーは数えない。
設定と IdP はリクエストごとに読むので、再起動なしに変わる。設定の変更は他の設定と同じく監査ログに残る。スキーマは、設定のキーの CHECK 制約だけが変わる。

### 2. 断るもの

制限中は、次のものをサービスで断り（`ErrLoginProvidersOnly`）、画面はそれを出さない。答えは入力によらず同じで、アカウントを引く前に断る。レート制限にも数えない。

- パスワードでのログイン（`SignIn`）。パスキーでのログイン（`SignInWithPasskey`）。
- パスワードかパスキーで始めたログインの 2 段目（`CompleteSignIn`）。チャレンジに 1 段目が何だったかを持たせ、IdP で始めたものは通す。
- パスワードでの登録（`SignUp`）。IdP での登録は、IdP の `allow_signup` と登録のモードに従って続く。
- パスワードのリセットの依頼（`RequestPasswordReset`）と、リセットのリンクでの設定（`ResetPassword`）。キューに残ったリセットのメールは送らない。リンクは使い切らず、制限が終われば有効期限まで使える。
- パスワードの設定と変更（`ChangePassword`）。パスキーの追加（`BeginPasskeyRegistration`・`FinishPasskeyRegistration`）。どちらもログインに使えない資格を作るだけであり、パスワードの変更はほかの端末のセッションを切って、その端末を締め出す。

### 3. 残すもの

- 既存のセッション、アクセストークン、リフレッシュトークン。
- ログイン中のパスワードとパスキーの**確認**（`confirm`）。パスワードだけの利用者はこれで IdP をひも付ける。
- IdP でのログイン・登録・ひも付けと、その後の TOTP。
- パスワードとパスキーの削除（`RemovePassword`・`RemovePasskey`）。
- 管理者のリセットのリンクの発行（`IssuePasswordResetLink`）。制限を解く直前に要ることがあるので発行は続け、今は使えないことを CLI の出力と API の応答（`login_providers_only`）と管理画面で言う。`my admin create` も続け、そのパスワードでログインできないことを警告する。

### 4. 最後のログイン手段

`ErrLastSignInMethod` の判定は次のとおり。

- パスワードとパスキーの削除では、制限中もパスワードとパスキーを今までどおり手段に数える。制限が終われば戻る手段であり、ひも付けの確認に使う手段でもあるからである。
- ひも付けの解除では、制限中はパスワードとパスキーを手段に数えない。ログインに使える IdP への最後のひも付けは解除できない。無効な IdP へのひも付けは、誰もログインさせないので解除でき、今までの判定に従う。

### 5. 警告と回復

- 有効にするときは断らず、警告する（Decider の「警告して管理者に任せる」）。管理画面の確認のダイアログと `my instance set` の出力が、ログインに使える IdP へのひも付けのない有効なローカルの利用者の数を言う。管理画面は、そこに管理者自身が含まれることをはっきり言う。数は `GET /api/v1/admin/settings/login_providers_only/impact`（`manage_settings`）が返す。
- 設定がオンで使える IdP がないときは、IdP の設定（作ると同時に有効になる）と有効化が制限をその場で始める。管理画面は、その操作のときだけ実行の前に確認のダイアログを出し、その IdP へのひも付けのない有効な利用者の数と、管理者自身が含まれることを言う。数と始まるかどうかは同じ API が返す（`provider_id` で有効にする IdP を指定する。権限は `manage_settings` か `manage_login_providers`）。断らない。
- `my login-provider create`・`enable`・`disable`・`delete` は、設定がオンのときに制限の今の状態を出す。
- 締め出された管理者は、サーバーのホストで `my instance set login_providers_only false` を実行して戻す。
- 有効な IdP がなくなると制限は自動で働かなくなる。パスワードもパスキーもない利用者は、今までどおりリセットのリンクがいる。

### 6. 登録のモードと公開する情報

制限中で、新規登録を許す IdP がひとつもないときは、登録のモードを `closed` と読む（`GET /instance` の `registrations.mode`、NodeInfo の `openRegistrations`、ログインの画面の登録へのリンク、招待の作成）。設定の値は変えない。
`GET /instance` の `login_providers_only` が、クライアントに制限中かどうかを伝える。招待のリンクの招待コードは、IdP を経由して登録のフォームまで運ぶ。

### この決定を見直す条件

- パスワードだけの利用者の締め出しが許容できなくなったとき（選択肢 3 へ）。
- 組織が、パスキーのログインを IdP と別に許す必要を示したとき（選択肢 2 へ）。

## Consequences（影響）

- 組織の IdP だけを入口にできる。入口の管理が IdP に一本化する。
- **セッションのない利用者は、管理者が動くまで締め出される。** これがこの決定の害である。IdP をひも付けていないパスワードだけの利用者は、セッションが切れるともう入れない。Decider はこれを承知で「警告して管理者に任せる」を選んだ。
- 同じ理由で、IdP のないパスワードだけの利用者が `disable_login`・`suspend`・`ban` を受けてセッションを失うと、ログインの画面からの異議申し立てに届かない。
- **アプリのトークンは生きていてブラウザの Cookie のセッションだけ切れた利用者は、制限中はひも付けに進めない。** ひも付けの開始はブラウザのセッションを確かめる（ログイン CSRF の対策、ADR-0106 §3.5）。Cookie のセッションとリフレッシュトークンはどちらも 30 日で、リフレッシュで延びるのはトークンだけなので、これは実際に起きる。Decider はこのまま受け入れた。運営者は、制限を有効にする前に利用者へ知らせる。
- 管理者が CLI のないホスティングだけを持つと、自分を締め出したときに戻す道がない。IdP を無効にする API にも届かない。
- IdP の障害の間は、制限中のサーバーには誰も新しくログインできない。設定をオフにするか IdP を無効にすれば戻る。
- 有効な IdP を足すと、設定がオンなら制限がその場で始まる。管理画面は実行の前に警告し、CLI は実行の後に状態を出す。

## Pros and Cons of the Options（詳細比較・任意）

### 1. 確認を残して警告する（採用）

Decider の 3 つの回答をそのまま満たす。パスワードの置き場所が残るので、制限を解けば元に戻る。害は上の Consequences のとおり。

### 2. パスワードだけ止める

パスキーは推測に強く、端末を失わない限り締め出しを減らす。組織がログインの入口を IdP に集めたいという目的に合わず、Decider が「パスキーも止める」と答えた。

### 3. ひも付けのための猶予のモード

パスワードだけの利用者がセッションを失っても自分で移行でき、締め出しがいちばん少ない。その代わり、パスワードが制限の間も有効な入口として残り、IdP に入口を集めるという目的を満たさない。ログインできても何もできないセッションの状態を新しく作ることにもなる。Decider は「警告して管理者に任せる」と答えた。

### 4. パスキーと未連携の利用者には制限をかけない

締め出しは起きない。既存の利用者のパスワードの入口がいつまでも残り、依頼の「制限」にならない。
