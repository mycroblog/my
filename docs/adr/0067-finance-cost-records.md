# ADR-0067: 費用の記録・支払いの周期・期間の集計・公開範囲

- Status: Accepted（§7 の「費用の一覧・登録・変更・終了・取り消し・集計の閲覧に要る」のうち集計の閲覧を ADR-0070（権限の分割: 絵文字の作成と会計の閲覧） が、§1 の「ほかのモジュールは `finance` を呼ばない」と §8 の `/about` の「運営の費用」の区画を出す条件を ADR-0073（収入の記録と公開） が、§2 の内訳の行に出す事業者の表記を ADR-0098（費用の内訳の事業者を入力どおりの表記で出す）が置き換える）
- Date: 2026-10-22
- Deciders: @rosylilly
- Issue: #873

## Context（背景・課題）

決定者の指示（#883、原文）: 「「費用」には月ごとだけでなく年ごとのドメイン更新費用なども記述できるようにしてください。最小値は週単位や単発の支払いです。」

M4.1 は、サーバーの維持費用を記録し（FR-901）、週・月・年で集計し（FR-902）、公開範囲を選んで公開する（FR-903）。
AWS と Google Cloud の利用料金の自動の取り込み（FR-904）の方法は ADR #875 が決める。この ADR は、取り込んだ費用を載せる側の形と、期間の区切りの契約を決める。
取り込みの元になる事業者の請求期間は、spike #874 の[調査報告](https://github.com/mycroblog/my/issues/874#issuecomment-6321153767)（2026-10-22 に公式の文書で確認）による。

- AWS Cost Explorer: 期間は UTC の暦の日付と暦月（"All times are in Universal Coordinated Time (UTC)"、[GetCostAndUsage](https://docs.aws.amazon.com/aws-cost-management/latest/APIReference/API_GetCostAndUsage.html)）。金額は USD。期間ごとに `Estimated` が付き、締めの後もクレジット・返金・サポート料で翌月の半ばまで値が変わる。
- Google Cloud（BigQuery への請求データの export）: 請求月 `invoice.month` は米国太平洋時間（夏時間あり）で切られる（"Pacific Time to calculate the billing period for all customers"、[Understand your bills and charges](https://docs.cloud.google.com/identity/docs/how-to/understand-your-bills-and-charges)）。金額は請求先アカウントの通貨。確定の印はなく、訂正は打ち消しの行として追加される。

いまのコードには費用を扱うモジュールも、日付（時刻なし）や金額の論理型もない（[data-model §1.2](../architecture/data-model/01-conventions.md#12-論理型)）。
近いものは次のとおり。

- インスタンス設定は `instance` の `instance_setting_revisions`【イベント（版）】と `instance_settings`【投影】のキーと値で、変更には `manage_settings` が要る（`internal/domain/instance/setting.go`）。
  処分したドメインの公開（FR-718）は、設定 `domain_actions_visibility` と匿名で読める `GET /instance/domain_actions`・`/about` のページで出している。
- 権限は `internal/domain/identity/role.go` の `Permission` で、ADR-0058 §4 の区分（モデレーション / サーバー管理）を持つ。
- 管理操作は、元のイベントと同じトランザクションの `AuditRecorded` で監査ログに残す（ADR-0037）。
- 日時は UTC で保持し、表示は利用者のタイムゾーン（`user_time_zones`）で `Intl.*` が整形する（ADR-0009 §3）。`client*` 以外の名前空間は Go も整形するので number skeleton を使えない。

決めること: モジュールの置き場所、データモデル、支払いの周期、計上のしかたと按分の端数、期間の区切り、通貨、権限と画面、公開範囲、API の形と i18n。
実装の #876（core と永続化）・#877（管理 API と画面）・#878（公開範囲と公開のページ）がこの ADR を待っている。

## Decision Drivers（判断基準）

1. 集計が正しく、説明できること: どの費用がどの期間にいくら載ったかを、誰が見ても同じ結果で再現でき、端数の合計が支払った額とずれない
2. 運営者が実際の支払いをそのまま書けること: 単発・週・月・年（ドメイン）、月末と 2/29、値上げ、解約
3. 公開しても安全なこと: 公開を選ばない限り何も出さず、出すときも運営者が選んだ粒度だけを出す
4. 既存の規約（ADR-0002 のモジュール境界、ADR-0020 のデータモデル、ADR-0037 の監査ログ、ADR-0058 の管理画面）にそのまま乗ること
5. 取り込み（#875）と期間の区切りが食い違わないこと
6. 1 人で運用するサーバーで、設定と実装が小さく済むこと（費用の項目は数十件の規模）

## Considered Options（選択肢）

論点ごとに比べる。各論点の 1 つめを採用する。

- **モジュール**: M1 新しいモジュール `finance` / M2 既存の `instance` に置く
- **集計の持ち方**: A1 読み取りのときに計算する / A2 期間ごとの合計を投影に持つ
- **計上のしかた**: B1 現金主義と按分の両方を出し、按分を既定にする / B2 現金主義だけ / B3 按分だけ
- **按分の単位**: R1 日割り（累積の丸め）/ R2 月割り（1/12 ずつ）
- **期間の区切り**: T1 日付（時刻なし）で持ち、タイムゾーンを持たない / T2 インスタンスのタイムゾーン設定で時刻を区切る / T3 閲覧者のタイムゾーン / T4 UTC
- **週の始まり**: W1 ISO 8601（月曜）に固定 / W2 閲覧者のロケールに合わせる
- **金額の表現**: C1 通貨の最小単位の整数 / C2 10 進の文字列
- **複数の通貨**: X1 通貨ごとに合計する / X2 運営者が入れた為替で 1 つの通貨に換算する
- **権限**: P1 `manage_finance` を 1 つ足す / P2 閲覧と変更を分ける（`view_finance`・`manage_finance`）/ P3 既存の `manage_settings` を使う
- **公開範囲**: V1 非公開・合計だけ・内訳（事業者と区分）までの 3 段階 / V2 公開か非公開かの 2 段階で、公開すると項目まで出す

## Decision（決定）

**M1・A1・B1・R1・T1・W1・C1・X1・P1・V1 を採用する。** 既定の見方は按分（§4）、公開範囲の設定は `manage_settings` で守る（§8）。

### 1. モジュール（M1）

新しいモジュール `finance`（`internal/domain/finance`・`internal/app/finance`）を置き、費用の項目・改定・終了・取り消しと、取り込んだ費用（#875）の行を所有する。
`instance` は設定・規約・テーマなどサーバーが出す中身を持つモジュールで、取り込みのポート（`BillingSource`）と定期ジョブを足すと責務が混ざる。

- 依存の向き（ADR-0002）: `internal/app/finance` は公開範囲の設定を `internal/app/instance` から読み、監査ログは `AuditRecorded` のドメインイベントで `moderation` に渡す。ほかのモジュールは `finance` を呼ばない。
- 期間の展開・按分・集計は `internal/domain/finance` の純粋な関数にし、表駆動のテストで確かめる。
- overview §2 のモジュールの表、data-model §4.0 の所有の表、`.golangci.yml` の depguard に `finance` を足す。

### 2. データモデル（ADR-0020）

| テーブル | 分類 | 内容 |
| --- | --- | --- |
| `cost_items` | リソース | `id`, `schedule`（`enum(once, weeks, months, years)`）, `interval`（`int`。`once` は 1、ほかは 1〜99。`CHECK`）, `starts_on`（`date`。単発は支払日）, `created_by_user_id`（NULL 可 = CLI）, `created_at` |
| `cost_item_label_revisions` | イベント（版） | `id`, `cost_item_id`, `name`（`string(100)`）, `provider`（`string(100)`）, `provider_normalized`, `category`（enum。下記）, `memo`（`text`。公開しない）, `revised_by_user_id`（NULL 可）, `revised_at` |
| `cost_item_price_revisions` | イベント（版） | `id`, `cost_item_id`, `effective_on`（`date`。この日以降の支払いに効く）, `amount_minor`（`bigint`、0 以上）, `currency`（`string(3)`。ISO 4217）, `revised_by_user_id`（NULL 可）, `revised_at`。最初の行の `effective_on` は `starts_on` |
| `cost_item_end_changes` | イベント | `id`, `cost_item_id`, `ends_on`（`date`。NULL 可 = 無期限に戻す）, `changed_by_user_id`（NULL 可）, `changed_at` |
| `cost_item_cancellations` | イベント | `id`, `cost_item_id`（一意）, `canceled_by_user_id`（NULL 可）, `canceled_at` |
| `cost_item_heads` | 投影 | `cost_item_id`（PK）, `label_revision_id`, `ends_on`（NULL 可 = 無期限）。行がある = 取り消されていない |

- 区分 `category` は `enum(compute, database, storage, network, domain, email, software, other)` の固定の一覧にし、表示名はカタログで翻訳する（ADR-0009）。事業者は自由な文字列で、内訳は `provider_normalized`（NFKC・小文字）でまとめる。
- 「終了した」「取り消した」を NULL 可の時刻の列で表さない（ADR-0020 規約 4）。終了は `cost_item_end_changes` の最新の行、取り消しは `cost_item_cancellations` の行の有無で表す。
  `ends_on` の NULL は data-model §1.2 の「無期限」に当たる。
- **取り消し**は、記録の誤りや不要になった項目を集計から外す操作で、過去の期間からも消える。**終了**は解約で、終了日より後の支払いだけが消える。取り消しを戻す操作は持たない（作り直す）。
- 改定（`cost_item_price_revisions`）は値上げ・値下げにも誤記の訂正にも使う。誤記は `effective_on = starts_on` で改定すれば全期間が直る。同じ `effective_on` の改定が複数あれば、最後に記録した行が効く。
  `effective_on` と `revised_at` は、効く日（業務の日付）と記録した時刻で、`moderation_actions` の開始・期限と同じく、イベントの日時属性は `revised_at` の 1 つである。
- 支払いの周期と開始日は項目の不変の事実にする。周期を変えるときは、項目を終了して新しい項目を作る。1 回だけの支払いを抜く例外（スキップ）は持たない。
- 取り込んだ費用の行（事業者・請求期間・サービス・見込みと確定・取り込みの世代）のテーブルは #875 が `finance` の中に決める。この ADR は §5 の境界の契約だけを決める。
- 新しい論理型 `date`（暦の日付 `YYYY-MM-DD`）を data-model §1.2 に足す。SQLite は `TEXT` と形の `CHECK`、PostgreSQL は `date`（data-model §1.2）。

### 3. 支払いの周期

- `once`: `starts_on` に 1 回払う。
- `weeks` / `months` / `years` と間隔 N: k 回目（k = 0, 1, …）の支払日は、**開始日から数えて**決める。前の支払日から足していかない（月末で日がずれていかない）。
  - `weeks`: `starts_on + 7·N·k` 日。日単位の周期は持たない（決定者の指示）。
  - `months`: `starts_on` の月から N·k か月後の、`starts_on` の日。その月にその日がなければ月の最終日（1/31 開始の毎月は 2/28 か 2/29、3/31、4/30 …）。
  - `years`: N·k 年後の同じ月日。2/29 開始は、うるう年でない年は 2/28。
- 終了日 `ends_on` があれば、支払日が `ends_on` 以下の回だけを数える（終了日を含む）。
- 各回の金額と通貨は、その支払日以前で最も新しい `effective_on` の改定の値にする。

### 4. 計上のしかたと按分（B1・R1）

- **現金主義**（`cash`）: 各回の金額を支払日の期間に載せる。
- **按分**（`amortized`、既定）: 周期が 1 か月より長い費用（`months` の N ≥ 2、`years`、`weeks` の N ≥ 5）の各回の金額を、その回が覆う期間（支払日から次の支払日の前日まで。終了日の後も、払った最後の回は覆う期間の終わりまで）に日割りで載せる。
  それ以外（単発と 1 か月以下の周期）は、按分でも支払日に載せる。
- 日割りの端数は**累積の丸め**で決める。金額 A（最小単位）を D 日に按分するとき、最初の d 日の合計を `floor(A·d / D)` とし、ある期間に載る額は、その期間の終わりと始まりの累積の差にする。
  どの期間の分け方でも各日の額の合計が A に一致し、週・月・年の合計がそれぞれ A を超えも欠けもしない。
- 例: 2026-04-10 に 1,650 円で払う年 1 回のドメインは、2026-04-10〜2027-04-09 の 365 日に載り、2026 年 4 月には 21 日分の `floor(1650·21/365) = 94` 円が載る。月ごとの額はちょうど 1/12 にはならず、月の日数で変わる（R2 を採らない理由は Pros and Cons）。
- 管理画面と公開のページは、どちらの見方かを選べ、既定は按分にする。「月にいくらかかるか」を示すのは按分で、現金主義は通帳と照らし合わせるときに使う。

### 5. 期間の区切り（T1・W1）と取り込みとの契約

- 手入力の費用は日付（時刻なし）だけを持つ。支払日はカードの明細や請求書に書かれた暦の日付で、時刻とタイムゾーンを持たない。ADR-0009 §3 の「サーバーは UTC で保持」は時刻の値の規則で、暦の日付には当たらない。
- 期間は暦の日付の範囲で、タイムゾーンで区切らない。週は ISO 8601 の週（月曜〜日曜、ラベルは `2026-W17` と期間の日付）、月と年は暦のとおりにする。週・月・年はそれぞれ独立に日付で区切るので、年をまたぐ週は年の集計では 2 つの年に分かれる。
- 「今週」「今月」を決める今日の日付だけは、閲覧者の端末のタイムゾーンで Web クライアントが決め、API には期間を日付で渡す。
- **取り込みとの契約**（#875 が守る）:
  - 取り込んだ費用の 1 件は、事業者の請求期間（ふつうは事業者のタイムゾーンでの暦月）を暦の日付の範囲 `[starts_on, ends_on]` で持ち、その期間の金額を持つ。日付は事業者のタイムゾーンのまま持ち、変換しない（AWS は UTC、Google Cloud は米国太平洋時間。Context の出典）。
    事業者の暦月を閲覧者やインスタンスのタイムゾーンで切り直すと、請求書の金額と合わなくなる。月の境目の数時間の利用が日本時間の暦月とずれることは、画面に請求期間の基準を示して受け入れる。
  - 現金主義でも按分でも、金額をその範囲の日数に日割り（累積の丸め、§4）で載せる。請求期間が暦月なら、月と年の集計ではその月にそのまま入り、週の集計では日数に比例して分かれる。
    事業者が日ごとの値を返すなら 1 日の範囲で持てばよい。どの粒度で取るかは #875 が決める。
  - 同じ事業者・請求期間・サービス・費用の種類の金額は、取り込んで値か見込み・確定の別が変わったときに新しいイベント（見込み・確定・確定後の修正）として記録し、集計には最新の値を使う。過去の行は直さない。
    Google Cloud の打ち消しの行やクレジット・返金は、取り込みの側で合計してから記録する。取り込んだ金額は負の値（クレジット・返金）も持てる。
- 画面と公開のページは、この区切りの規則（日付の扱い・週の始まり・事業者ごとの請求の日付の基準・按分の規則）を集計の近くに示す（FR-902）。

### 6. 通貨（C1・X1）

- DB は通貨の最小単位の整数（`amount_minor`、`bigint`）と ISO 4217 の通貨コードで持つ。小数の桁は ISO 4217 の表（JPY は 0、USD は 2）を `internal/domain/finance` に持つ。float は使わない。
- 取り込みの 10 進の金額（AWS の文字列、Google Cloud の `NUMERIC` に変えた合計）は、記録する 1 件（請求期間 × サービス × 費用の種類）ごとに、最近接偶数への丸めで最小単位にする。
- 合計は通貨ごとに出し、換算しない。円とドルで払うサーバーの合計は「12,300 円 + $45.67」になる。為替の換算は、為替の日付と出典を記録する仕組みが要り、公開した合計が為替で動くので持たない。

### 7. 権限と画面（P1）

- 新しい権限 `manage_finance` を足す。ADR-0058 §4 の区分はサーバー管理で、組み込みのロールでは `admin` だけが持つ。費用の一覧・登録・変更・終了・取り消し・集計の閲覧に要る。
- 管理画面は ADR-0058 §1 の表に次の行を足す: サーバー管理 | 費用（`/admin/finance`。項目の一覧とフォーム、週・月・年の集計） | `manage_finance`。
  公開範囲（§8）はサーバーの設定（`/admin/settings`、`manage_settings`）に置き、費用の画面はいまの公開範囲を示して、`manage_settings` を持つ閲覧者にはその設定へリンクする。
- 監査ログ（ADR-0037）: `target_kind` に `cost_item` を足し、作成・ラベルの変更・改定・終了の変更・取り消しを記録する。`target_label` は項目の名前。公開範囲の変更は、既存の設定の変更として記録する。

### 8. 公開範囲（V1）

- インスタンス設定のキー `finance_visibility`（`enum(private, totals, breakdown)`、未設定は `private`）を `instance` に足す。ほかの設定と同じく `manage_settings` で守り、サーバーの設定の画面から変える。何を公開するかはサーバー全体の決定なので、費用を記録する人（`manage_finance`）ではなく設定を任された人が決める。
  - `private`: 公開の API は `404` を返し、`/about` に費用を出さない。
  - `totals`: 期間ごとの通貨ごとの合計だけを出す。
  - `breakdown`: 合計に加え、事業者ごと・区分ごとの内訳を出す。
- どの段階でも、項目の名前・メモ・個々の支払い・改定の履歴は公開しない。名前とメモにはバケット名・リージョン・プランのような構成の細部が入りやすい。
  内訳でも事業者と区分は出るので、どのクラウドで動いているかは知られる。設定の画面で `breakdown` を選ぶところにこのことを書く。
- 公開する場所: 匿名で読める API（§9）と、`/about` の「運営の費用」の区画と、そこからリンクする `/about/costs` のページ。公開するのは今日を含む期間までで、それより後の予定の支払いは出さない。

### 9. API の形（[client-api.md](../architecture/client-api.md)）

- 管理（タグ `admin-server`、スコープ `admin:read` / `admin:write` と `manage_finance`）:
  - `GET /admin/cost_items`（キーセットページング）・`POST /admin/cost_items`・`GET /admin/cost_items/{id}`
  - `PATCH /admin/cost_items/{id}`（名前・事業者・区分・メモ）・`POST /admin/cost_items/{id}/price_revisions`（改定日・金額）・`PUT /admin/cost_items/{id}/end`（終了日。`null` で無期限）・`POST /admin/cost_items/{id}/cancel`
  - `GET /admin/cost_totals?granularity=week|month|year&from=YYYY-MM-DD&to=YYYY-MM-DD&basis=amortized|cash`: 期間ごとの通貨ごとの合計と、事業者・区分・通貨ごとの内訳、`rules`（週の始まり、事業者ごとの請求の日付の基準）を返す
- 公開（タグ `instance`、`security: []`、`Cache-Control: public, max-age=60`）: `GET /instance/cost_totals` は管理と同じ問い合わせを受け、`finance_visibility` で内訳を省く。`private` では `404`。
  `GET /instance` に `finance_visibility` を足し、Web クライアントはそれで `/about` の区画を出し分ける。
- 金額は JSON で `{"amount": "12.34", "currency": "USD"}`（主単位の 10 進の文字列）にする。数値にすると JavaScript の倍精度で丸まる。入力の小数の桁が通貨の桁より多ければ `422` にする。日付は `YYYY-MM-DD` の文字列にする。
- 1 回の集計で返す期間の数に上限を持つ（週 104・月 60・年 20。超えたら `422`）。

### 10. i18n（ADR-0009）

- 金額は Web クライアントが `Intl.NumberFormat`（`style: "currency"`、`currency` は API の値）で書式化し、文字列としてメッセージに渡す。通貨はデータで決まるので ICU の number skeleton には書けない。Go は金額を書式化しない。
- 期間のラベルは `Intl.DateTimeFormat`（月・年）と `formatRange`（週の日付の範囲）で書く。周期（「3 か月ごと」）・区分・計上のしかた・区切りの規則の説明は `client*` 名前空間の ICU メッセージ（`plural`）にする。
- 事業者と項目の名前は運営者の入力で、ロケールごとに持たず `dir="auto"` で出す。

### この決定を覆す条件

- 取り込みの行が増え、読み取りのときの集計が公開のページの応答時間や DB の費用（NFR-COST）を押し上げると計測で分かったら、A2（期間ごとの合計の投影）に変える。
- 複数の通貨で払う運営者の多くが 1 つの合計を求めたら、為替を記録する X2 の ADR を書く。
- 日割りの月の額が「1/12 ずつ」と違うことが運営者に分かりにくいと分かったら、月と年の集計だけ R2 にすることを検討する（週の集計との食い違いを受け入れる）。

## Consequences（影響）

- 良い影響
  - 単発・週・月・年の支払い、月末と 2/29、値上げ、解約、誤記の訂正を、1 つの規則（開始日から数える支払日と、日付で効く改定）で表せる。
  - 按分の端数が累積の丸めで決まるので、どの期間の分け方でも合計が支払った額に一致し、週・月・年の表が互いに矛盾しない。
  - 日付だけで区切るので、閲覧者のタイムゾーンで集計が変わらず、公開した額を誰が見ても同じになる。
  - 集計を読み取りのときに計算するので、投影の再構築・検証（ADR-0020 規約 1）が要らない。項目が数十件の規模では、全項目を読んで展開しても軽い。
- 悪い影響・トレードオフ
  - 按分の月の額は月の日数で変わり、年払い 1,200 円が毎月ちょうど 100 円にはならない。
  - 通貨ごとの合計しか出ないので、複数の通貨で払うサーバーは全体でいくらかを 1 つの数で示せない。
  - 1 回だけの支払いを抜く例外がないので、1 か月だけ無料だった月は、その日に効く改定を 2 つ（0 円と元の額）入れて表す。
  - 取り込みの事業者ごとに請求の日付の基準が違い（UTC と太平洋時間）、同じ日付でも同じ瞬間を指さない。基準を画面に示すことで受け入れる。
  - 費用を記録する人（`manage_finance`）と公開範囲を決める人（`manage_settings`）が分かれ、`manage_finance` だけを持つ人は公開範囲を変えられない。
  - モジュールと論理型 `date` が増え、overview・data-model・depguard の更新が要る。
- 後続で必要になる作業（Epic #883 の実装の issue）
  - #876（T1）: `finance` モジュール、論理型 `date` と `schema/<dialect>.sql`・sqlc、ISO 4217 の表、支払日の展開・按分・集計のドメインの関数と表駆動のテスト（月末・うるう年・境界・改定日・終了日・取り消し）。集計の投影は持たない（読み取りのときに計算する）
  - #877（T2）: `manage_finance`、監査ログの `action` と `target_kind`、管理 API（§9）と `/admin/finance` の画面、`client*` のメッセージ
  - #878（T3）: 設定 `finance_visibility`（`manage_settings`、`/admin/settings` の画面）、`GET /instance/cost_totals` と `GET /instance` の項目、`/about` の区画と `/about/costs`
  - #875: §5 の契約（事業者の請求期間を暦の日付の範囲で持つ・日割り・取り込みごとのイベントと最新の値・丸め）に合わせて取り込みの行を決める

## Pros and Cons of the Options（詳細比較・任意）

### モジュール: M1 `finance`（採用）/ M2 `instance`

- M1 の良い点: 取り込みのポートと定期ジョブ（#875）を含めても責務が 1 つにまとまる。悪い点: モジュールが増える。
- M2 の最も強い論点: 公開範囲は `instance` の設定で、`/about` も `instance` が出すので、モジュール間の呼び出しが要らない。悪い点: 設定とお知らせのモジュールに、周期の計算と外部の請求の取り込みが入る。

### 集計: A1 読み取りのときに計算（採用）/ A2 投影

- A2 の最も強い論点: 公開のページへの匿名のアクセスが多くても、合計を 1 回読むだけで済む。悪い点: 終わりのない繰り返しの費用は、どこまで先の期間を作るかの上限と、日付が進むたびの補充が要る。
  改定・終了・取り消しのたびに過去の期間を作り直す必要があり、再構築と検証（`projection.verify`）を持つことになる。公開の API は 60 秒のキャッシュを持つので、A1 でも匿名のアクセスの負荷は抑えられる。

### 計上: B1 両方・按分が既定（採用）/ B2 現金主義だけ / B3 按分だけ

- B2 の最も強い論点: 実際に払った額と日がそのまま出て、説明が要らない。悪い点: ドメインの更新月だけ費用が跳ね、「月にいくら」が分からない（FR-902 も両方を求める）。
- B3 の良い点: 表が 1 つで済む。悪い点: 通帳と照らし合わせられない。

### 按分の単位: R1 日割り（採用）/ R2 月割り

- R2 の最も強い論点: 年払いが毎月ちょうど 1/12 になり、運営者の直感に合う。悪い点: 週の集計に載せる規則が別に要り、週の合計を足しても月の合計にならない。
  月の途中に払った年払いの最初と最後の月の扱い（半端な月）も別の規則になる。

### 期間の区切り: T1 日付（採用）/ T2 インスタンスのタイムゾーン / T3 閲覧者 / T4 UTC

- T2 の最も強い論点: 時刻を持つ取り込み（AWS の UTC の時刻など）を 1 つの基準にそろえられる。悪い点: 運営者が入力する支払日は時刻を持たないので、日付を時刻にしてから戻す変換が増えるだけで、事業者の請求書の日付とも合わなくなる。
- T3 は閲覧者ごとに公開の額が変わる。T4 は日本の運営者の支払日が前日に動く。

### 週の始まり: W1 月曜（採用）/ W2 ロケール

- W2 の良い点: 日曜始まりの地域の利用者に見慣れた週になる。悪い点: 公開した週の合計がロケールで変わる。

### 金額: C1 最小単位の整数（採用）/ C2 10 進の文字列

- C2 の最も強い論点: 取り込みの細かい金額（0.0000123 ドル）を丸めずに持てる。悪い点: SQLite には 10 進の型がなく、SQL で合計できない。請求書も最小単位で締まるので、保存の粒度ごとに丸める誤差（1 行あたり最小単位の半分まで）は受け入れる。

### 複数の通貨: X1 通貨ごと（採用）/ X2 換算

- X2 の最も強い論点: 「月にいくら」を 1 つの数で示せ、寄付の目標に使いやすい。悪い点: 為替の日付と出典の記録、為替の改定の扱いが要り、過去の公開した額が変わる。

### 権限: P1 `manage_finance`（採用）/ P2 閲覧と変更を分ける / P3 `manage_settings`

- P2 の良い点: 会計を確かめるだけの人に変更を許さない。悪い点: 1 人か少人数のサーバーで使われる見込みが低い。必要になれば後から足せる。
- P3 の良い点: 権限が増えない。悪い点: サーバーの設定を任せた人に費用（支払いの額）も見せることになる。
- 公開範囲の設定だけは `manage_finance` で守る案もある。費用を記録する人がそのまま公開を決められるが、設定の定義にキーごとの権限が要り、サーバーが外に何を出すかを決める権限が 2 つに分かれる。公開範囲は `manage_settings` で守る。

### 公開範囲: V1 3 段階（採用）/ V2 2 段階

- V2 の良い点: 設定が単純で、項目まで出すので最も透明。悪い点: 項目の名前とメモから構成の細部が漏れる。合計だけ出したい運営者の選択肢がない（FR-903 も 3 段階を求める）。
