# ADR-0110: Web クライアントの体験の原則と、情報設計の要件・批評のサイクル

- Status: Accepted（§7 の、L4 を PR の前に行うことと nightly への組み込みを ADR-0114（L4 の課題テストを nightly で回す） が置き換える）
- Date: 2026-10-28
- Deciders: @rosylilly
- Issue: #1638

## Context（背景・課題）

Web クライアントの規約（[web-client/](../architecture/web-client/README.md)、ADR-0026・ADR-0027・ADR-0059）は、React の書き方、状態、間隔・文字・アイコン、
4 つの状態（空・読み込み中・エラー・オフライン）、文言のトーンを細かく決め、lint・型・テストで強制している。
これらはどれも「どう描くか」の正しさと一貫性の規約で、「この画面で利用者は何をしたいか」「何を先に見せ、何をまとめ、何を隠すか」を決める規約がない。

その結果、規約をすべて守ったまま、操作の部品を縦に並べただけの画面ができる。設定の画面（`/settings` 以下）を後述の 4 つの観点で点検すると、16 の問題が見つかった。
観点ごとの内訳は、情報設計 9、シグニファイア 3、フィードバック 2、UX ライティング 2 である。既存の規約を守っていないのは 3 つだけで、残りは規約の穴である。主なもの:

- **設定のメニュー**（`SettingsMenu`）は、最大 23 の項目を、まとまりの見出しもアイコンもなく 1 本のリストに並べる。
- **「表示と投稿」**（`PreferencesForm`）は、表示・ナビゲーション・投稿の既定値・タイムラインの 11 の操作を見出しなしで並べる。
  サーバーに保存するものと、このブラウザにだけ残すものも区別しない。
- **すぐ保存する設定**は、保存の成功を視覚的に隠した読み上げ（`Announcer`）だけで伝え、見える人には何も出ない。
  設定の画面全体では、成功の伝え方が 3 通り（見えるメッセージ・トースト・読み上げだけ）あり、見えるメッセージの位置も画面の先頭と送信ボタンの直後に分かれる。
- **区画の見出し**（`h2` と `section`）は、8 つのファイルに同じ部品が複製され、大きさもずれている。
- **通知の設定**は、最大 22 行 × 4 列のチェックボックスの格子で、列をまとめて切り替える操作がない。

A4（`app/web` は Tailwind のクラスを書かず `@my/ui` の部品で組む）のもとでは、画面を組む最短の道は `Stack` などの下位の部品を積むことである。
下位の部品と画面のあいだのパターンの部品（設定のまとまり、要約から詳しく見せる形、主な操作、保存の状態、図）が少ないので、その道がそのまま画面になる。

画面の追加の多くはエージェントが行う（[docs/agents/](../agents/)）。エージェントはスクリーンショットから見た目の良し悪しを判断するのは苦手だが、
テキストで書いた意図と構造（ARIA のツリー、文言のカタログ）を照らし合わせて点検するのは得意である。
v0 のリリース（M5）までに既存の画面を整え、以後の画面がこの状態に戻らない仕組みが要る。
関連する要件は vision の利用者の関心「使いやすさ」（[00-vision.md](../requirements/00-vision.md)）と NFR-A11Y-1。

UI の評価の観点は、CodeZine「AIが作ったUIはなぜ『使いづらい』のか？」（2026-10、[記事](https://codezine.jp/article/detail/29762)）の 4 つの観点を使う。

- **シグニファイア**: 操作できることが伝わり、押すと何が起きるかを予測できるか。
- **フィードバック**: 操作のあと、処理中・成功・失敗が伝わり、反応がないと誤解されないか。
- **UX ライティング**: 文が、システムの説明で終わらず、利用者の次の行動につながるか。
- **情報設計**: 必要な情報が適切な順序で出て、主要な情報と補助の情報が分かれ、目的までの導線が見えるか。

## Decision Drivers（判断基準）

1. 利用者が道に迷わず、混乱しないこと（決定者の最優先の関心）。
2. エージェントが実装の前と後に、機械的に、またはテキストで点検できること。人の目だけに頼る規約は守られ続けない。
3. 一度直した問題が、部品か検査として残り、後戻りしないこと（ADR-0024 の boy scout rule と同じ向き）。
4. 既存の規約・品質ゲート（ADR-0027）・テーマ（ADR-0059）と矛盾しないこと。
5. 画面を 1 つ足すときの手間が、得られる品質に見合うこと。

## Considered Options（選択肢）

1. **原則だけを文書にする**: 体験の原則を書き、守るかどうかはレビューに任せる。
2. **パターンの部品だけを増やす**: 原則や画面の要件を書かず、`@my/ui` に設定のまとまり・主な操作・図などの部品を足し、それで組むよう求める。
3. **画面を AI に見せて評価させる**: スクリーンショットを LLM に渡し、4 つの観点で点数と指摘を出させて PR に付ける。
4. **原則・画面の要件・パターンの部品・機械検査・人の批評を同じ 4 観点でつなぐ**（下の 5 層）。

## Decision（決定）

**選択肢 4 を採る。** 原則に優先順位を付け、実装の前（画面の要件）・実装（パターンの部品）・実装の後（機械検査・課題テスト・人の批評）を、同じ 4 観点で通す。

### 1. 体験の原則と優先順位

原則がぶつかったときは番号の小さい方を取る。

| # | 原則 | やること | やらないこと |
| --- | --- | --- | --- |
| P1 | **迷わない** | 画面ごとに主な操作を 1 つにする。要約を先に見せ、詳しい内容はその後に見せる。主要な情報と補助の情報を分け、関係するものをまとめる。1 つの画面の保存の仕方は 1 つにする（すぐ保存か、まとめて保存か） | 楽しさのために導線・境界・文言を弱める |
| P2 | **操作に必ず応える** | 押した直後に見た目が反応する。処理中・成功・失敗の移り変わりを、動きの小さな演出（マイクロインタラクション）で、操作した場所に出す。動きの長さと緩急はトークンから選ぶ。`prefers-reduced-motion` のときは、動きの代わりに色と形の変化で応える | 反応を読み上げだけで伝える。結果を操作した場所から離れた所にだけ出す。待たせるための演出 |
| P3 | **形で先に伝える** | 状態はバッジとアイコンの形で、数と推移は図で示す。アイコンには文言を添える（G12）。1 つの区画に出す文字と操作の量に上限を設ける | 説明文を並べて終える。アイコンだけで意味を当てさせる |
| P4 | **同じ意味は同じ見た目と動き** | 新しい見た目は、まず `@my/ui` のパターンの部品として作り、画面はそれを使う | 画面ごとに少しずつ違う、似た部品を作る。機能の中で部品を複製する |

見た目の言語（面・影・角丸）は原則ではなく手段なので、ADR-0111 で決める。

### 2. 5 つの層

| 層 | 中身 | 効かせ方 |
| --- | --- | --- |
| L1 画面の要件 | 画面ごとのテキスト（下の 4） | UI の issue を `agent:ready` にする条件にする |
| L2 パターンの部品 | 判断を型で強制する `@my/ui` の部品（下の 5） | 画面の側（`app/web`）は L2 の部品で組む。足りなければ `@my/ui` に足す（A4 と同じ） |
| L3 機械検査 | ARIA スナップショット・部品のテスト・lint・文言のカタログで測る規則（下の 6） | E2E・部品のテスト・Oxlint・`i18n:check` に足す |
| L4 課題テスト | L1 の作業を、エージェントが ARIA のツリーだけで行い、手数と lostness を測る（下の 7） | UI を変える issue の作業の中で行い、結果を PR に書く |
| L5 人の批評 | PR ごとと main の画面・部品の一覧を決定者が見てコメントし、各コメントを 4 観点と直す層（L1〜L3 か個別の issue）に分類する | 一覧の置き場は ADR-0112。一度直したものは L1〜L3 に残る |

### 3. 4 観点と層の対応

| 観点 | L1 | L2 | L3 |
| --- | --- | --- | --- |
| シグニファイア | 主な操作、保存の仕方 | 主な操作の部品、送信の帯 | 主なボタンの数、送信ボタンのある `form` の中のスイッチ |
| フィードバック | 操作ごとの結果の出し方 | 保存の状態の部品、送信の帯 | 書き込みの結果の出し方を宣言する型、操作の直後の見た目の変化 |
| UX ライティング | 画面の次の行動 | — | カタログの lint。カタログの差分への LLM の点検（テキストなので効きやすい） |
| 情報設計 | 優先順位・まとまり・導線 | 設定の画面・区画・メニュー、要約の部品、図 | 見出しの順、区画に入っていない操作、区画ごとの操作の数 |

### 4. 画面の要件（L1）

- 置き場は `docs/architecture/web-client/screens/` で、画面（ルート）ごとに 1 ファイルにする（ADR-0082 の衝突しない構成）。設計の文書なので v0 の間は日本語で書く。
  `tools/agentkit/context-map.yaml` の各画面の機能の entry の `docs` に足し、`agentkit ctx` がその画面の issue に要件を入れる。
- 書式は Shape Up の Breadboarding（場所・操作・つながり）と、OOUX の ORCA（Objects・Relationships・CTAs・Attributes）を下敷きにした、次の節を持つ短いテキストにする。
  1. 誰が・何のために・どのくらいの頻度で使うか
  2. 作業の一覧（L4 の課題になる。作業ごとに、最短の手順の数）
  3. 情報の優先順位とまとまり（区画の見出しの順。L3 が実装の見出しの順と比べる）
  4. 主な操作と保存の仕方
  5. 操作ごとの結果の出し方（その場・トースト・画面の遷移）
  6. 入口と出口（どこから来て、終えたらどこへ行くか）
- 雛形と最初の要件は、設定の画面で書く。

### 5. 最初のパターンの部品（L2）

設定の画面の点検から、次の部品を `@my/ui` に足す。名前は実装で決める。

| 部品 | 決めること |
| --- | --- |
| 設定のメニュー | まとまりの見出し・アイコン・件数のバッジを必須にする |
| 設定の画面と区画 | 画面は区画の並びだけを受け取り、区画は見出しを必須にする。機能の中で区画の部品を作らない |
| 保存の状態 | すぐ保存する操作の保存中・保存済み・失敗を、操作の隣に小さな動きで出す |
| 送信の帯 | まとめて保存するフォームの送信ボタンと結果を同じ場所に出し、長いフォームでは画面に固定する |
| 一覧と追加 | 件数付きの一覧を主にし、追加を主な操作として 1 か所に置き、空の状態から追加へ導く |
| 状態の要約 | 状態のバッジと次の操作を持つカード（セキュリティの要約など） |
| 通知の経路の表 | 列ごとのまとめての切り替え、セルごとの保存の状態と、無効の理由 |

### 6. 最初の機械検査（L3）

- 送信ボタンのある `form` の中に `role="switch"` を置かない（`Switch` は「すぐ効く」操作の部品である）。
- 見出しを持つ区画と、区画に入っていない操作を、同じ親の下に混ぜない。
- 機能の中で `Heading level={2}` に `size` を渡さない（G5）。
- すぐ保存する操作の部品は、保存の状態を必須の props で受け取る。書き込みのフックは、結果の出し方（その場・トースト・画面の遷移）を型で宣言する。
- 1 つの区画の操作は 7 個まで、メニューの 1 つのまとまりの項目は 7 個までにし、超えるときは区画を分ける。7 は設定の画面に当てて誤検知が多ければ見直す。
- 画面の `h2` の順は、L1 の区画の順と一致する（ARIA スナップショット）。

### 7. 課題テスト（L4）

- UI を変える issue のエージェントは、PR の前に、変えた画面の L1 の作業を Playwright の ARIA スナップショットだけを手がかりに行う。そのときの操作の数・戻った回数・
  lostness（Smith, 1996。訪れた場所の総数 S・異なる場所の数 N・最短の手順の数 R から、√((N/S − 1)² + (R/N − 1)²)）を PR に書く。
- lostness が 0.4 を超える作業は、PR で理由を書くか、L1 か画面を直す（Smith の研究で、0.4 未満の利用者は迷った様子を見せず、0.5 を超えると迷っていた）。
- エージェントの作業の中で行うので、CI に費用も秘密情報も増えない。nightly の CI への組み込みは、課題の数が増えてから別に決める。

### 見直す条件

- 設定の画面の試験で、L1 を書く手間に対して画面の改善が小さいと分かった場合（L1 を必須にせず、L2・L3 だけにする）。
- L3 の規則が誤検知ばかりで、無効化のコメントが増え続ける場合。

## Consequences（影響）

- 良い影響: 実装の前に「何を・なぜ」が決まり、エージェントがそれに照らして実装と点検ができる。批評が部品と検査に変わって残る。
- 良い影響: パターンの部品が増え、画面ごとの実装の量は減る（設定の画面では、複製された区画の部品 8 つがなくなる）。
- 悪い影響: UI の issue を `agent:ready` にする前に L1 を書く手間が増える。決定者のレビューの負担も L5 の分だけ増える。
- 悪い影響: L3 の規則は、情報設計の良し悪しの代わりの量しか測れない。上限を守っても良い画面になるとは限らない。
- 悪い影響: lostness は、エージェントが ARIA のツリーで迷うかを測るもので、人が見た目で迷うかとは一致しない。L5 の人の批評で補う。
- 後続の作業（issue にする）:
  - web-client/ に「体験の原則と画面の要件」の節と `screens/` を足し、`docs/agents/workflow.md` に L1 と L4 の手順を足す。
  - 設定の画面の L1 と、上の 5 の部品、上の 6 の検査（設定の画面の 16 の指摘を、どの部品と検査が直すかで分ける）。
  - 設定の画面の個別の問題: 配信停止の知らせが求める「確認のメールをもう一度求める」操作がない、自動削除で消える投稿の件数が分からない（API の見積もりが要る）。
  - 既存の画面を、利用者が多く使う順（タイムライン・投稿・通知・プロフィール）に点検する。

## Pros and Cons of the Options（詳細比較・任意）

- **選択肢 1（原則だけ）**: いちばん安く、決定者の意図をそのまま書ける。ただし「どう描くか」の規約が厚いのに画面がのっぺりしている今の状態は、レビューだけでは守られないことを示している。
- **選択肢 2（部品だけ）**: 効果が見えやすく、A4 の仕組みにそのまま乗る。ただし何を強制する部品にすべきかは画面の目的から決まるので、L1 がないと「立派な部品を置いただけ」の画面に変わるだけになる。
- **選択肢 3（画面を AI に見せる）**: 実装の負担がなく、見た目そのものを評価できる唯一の自動の方法である。
  ただし評価が画面の目的を知らずに行われ、同じ画面でも結果がぶれる。指摘が部品や検査として残らない。L5 の補助（2 つの案を目的に照らして比べさせる）には使える。
