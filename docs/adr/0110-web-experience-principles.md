# ADR-0110: Web クライアントの体験の原則・品質ゲート・見た目

- Status: Accepted
- Date: 2026-10-28
- Deciders: @rosylilly
- Issue: #87, #328, #660, #1638, #1646

## Decision（決定）

原則に優先順位を付け、実装の前（画面の要件）・実装（パターンの部品）・実装の後（機械検査・課題テスト・人の批評）を、同じ 4 観点で通す。4 観点は CodeZine「AIが作ったUIはなぜ『使いづらい』のか？」（2026-10、[記事](https://codezine.jp/article/detail/29762)）のものを使う。

- **シグニファイア**: 操作できることが伝わり、押すと何が起きるかを予測できるか。
- **フィードバック**: 操作のあと、処理中・成功・失敗が伝わり、反応がないと誤解されないか。
- **UX ライティング**: 文が、システムの説明で終わらず、利用者の次の行動につながるか。
- **情報設計**: 必要な情報が適切な順序で出て、主要な情報と補助の情報が分かれ、目的までの導線が見えるか。

### 1. 体験の原則と優先順位

原則がぶつかったときは番号の小さい方を取る。

| # | 原則 | やること | やらないこと |
| --- | --- | --- | --- |
| P1 | **迷わない** | 画面ごとに主な操作を 1 つにする。要約を先に見せ、詳しい内容はその後に見せる。主要な情報と補助の情報を分け、関係するものをまとめる。1 つの画面の保存の仕方は 1 つにする（すぐ保存か、まとめて保存か） | 楽しさのために導線・境界・文言を弱める |
| P2 | **操作に必ず応える** | 押した直後に見た目が反応する。処理中・成功・失敗の移り変わりを、動きの小さな演出（マイクロインタラクション）で、操作した場所に出す。動きの長さと緩急はトークンから選ぶ。`prefers-reduced-motion` のときは、動きの代わりに色と形の変化で応える | 反応を読み上げだけで伝える。結果を操作した場所から離れた所にだけ出す。待たせるための演出 |
| P3 | **形で先に伝える** | 状態はバッジとアイコンの形で、数と推移は図で示す。アイコンには文言を添える（G12）。1 つの区画に出す文字と操作の量に上限を設ける | 説明文を並べて終える。アイコンだけで意味を当てさせる |
| P4 | **同じ意味は同じ見た目と動き** | 新しい見た目は、まず `@my/ui` のパターンの部品として作り、画面はそれを使う | 画面ごとに少しずつ違う、似た部品を作る。機能の中で部品を複製する |

見た目の言語（面・影・角丸）は原則ではなく手段なので、§12〜§15 で決める。

### 2. 5 つの層

| 層 | 中身 | 効かせ方 |
| --- | --- | --- |
| L1 画面の要件 | 画面ごとのテキスト（§4） | UI の issue を `agent:ready` にする条件にする |
| L2 パターンの部品 | 判断を型で強制する `@my/ui` の部品（§5） | 画面の側（`app/web`）は L2 の部品で組む。足りなければ `@my/ui` に足す（A4 と同じ） |
| L3 機械検査 | ARIA スナップショット・部品のテスト・lint・文言のカタログで測る規則（§6） | E2E・部品のテスト・Oxlint・`i18n:check` に足す |
| L4 課題テスト | L1 の作業を、エージェントが ARIA のツリーだけで行い、手数と lostness を測る（§7） | nightly で回す（ADR-0015 §4）。UI を変える PR は最短の手順を書く |
| L5 人の批評 | PR ごとと main の画面・部品の一覧を決定者が見てコメントし、各コメントを 4 観点と直す層（L1〜L3 か個別の issue）に分類する | 一覧の置き場は ADR-0079。一度直したものは L1〜L3 に残る |

### 3. 4 観点と層の対応

| 観点 | L1 | L2 | L3 |
| --- | --- | --- | --- |
| シグニファイア | 主な操作、保存の仕方 | 主な操作の部品、送信の帯 | 主なボタンの数、送信ボタンのある `form` の中のスイッチ |
| フィードバック | 操作ごとの結果の出し方 | 保存の状態の部品、送信の帯 | 書き込みの結果の出し方を宣言する型、操作の直後の見た目の変化 |
| UX ライティング | 画面の次の行動 | — | カタログの lint。カタログの差分への LLM の点検（テキストなので効きやすい） |
| 情報設計 | 優先順位・まとまり・導線 | 設定の画面・区画・メニュー、要約の部品、図 | 見出しの順、区画に入っていない操作、区画ごとの操作の数 |

### 4. 画面の要件（L1）

- 置き場は `docs/architecture/web-client/screens/` で、画面（ルート）ごとに 1 ファイルにする（ADR-0081 の衝突しない構成）。設計の文書なので v0 の間は日本語で書く。
  `tools/agentkit/context-map.yaml` の各画面の機能の entry の `docs` に足し、`agentkit ctx` がその画面の issue に要件を入れる。
- 書式は Shape Up の Breadboarding（場所・操作・つながり）と、OOUX の ORCA（Objects・Relationships・CTAs・Attributes）を下敷きにした、次の節を持つ短いテキストにする。
  1. 誰が・何のために・どのくらいの頻度で使うか
  2. 作業の一覧（L4 の課題になる。作業ごとに、最短の手順の数）
  3. 情報の優先順位とまとまり（区画の見出しの順。L3 が実装の見出しの順と比べる）
  4. 主な操作と保存の仕方
  5. 操作ごとの結果の出し方（その場・トースト・画面の遷移）
  6. 入口と出口（どこから来て、終えたらどこへ行くか）
- 雛形と最初の要件は、設定の画面で書く。

### 5. 最初のパターンの部品（L2）

設定の画面の点検から、次の部品を `@my/ui` に足す。名前は実装で決める。

| 部品 | 決めること |
| --- | --- |
| 設定のメニュー | まとまりの見出し・アイコン・件数のバッジを必須にする |
| 設定の画面と区画 | 画面は区画の並びだけを受け取り、区画は見出しを必須にする。機能の中で区画の部品を作らない |
| 保存の状態 | すぐ保存する操作の保存中・保存済み・失敗を、操作の隣に小さな動きで出す |
| 送信の帯 | まとめて保存するフォームの送信ボタンと結果を同じ場所に出し、長いフォームでは画面に固定する |
| 一覧と追加 | 件数付きの一覧を主にし、追加を主な操作として 1 か所に置き、空の状態から追加へ導く |
| 状態の要約 | 状態のバッジと次の操作を持つカード（セキュリティの要約など） |
| 通知の経路の表 | 列ごとのまとめての切り替え、セルごとの保存の状態と、無効の理由 |

### 6. 最初の機械検査（L3）

- 送信ボタンのある `form` の中に `role="switch"` を置かない（`Switch` は「すぐ効く」操作の部品である）。
- 見出しを持つ区画と、区画に入っていない操作を、同じ親の下に混ぜない。
- 機能の中で `Heading level={2}` に `size` を渡さない（G5）。
- すぐ保存する操作の部品は、保存の状態を必須の props で受け取る。書き込みのフックは、結果の出し方（その場・トースト・画面の遷移）を型で宣言する。
- 1 つの区画の操作は 7 個まで、メニューの 1 つのまとまりの項目は 7 個までにし、超えるときは区画を分ける。7 は設定の画面に当てて誤検知が多ければ見直す。
- 画面の `h2` の順は、L1 の区画の順と一致する（ARIA スナップショット）。

### 7. 課題テスト（L4）

- エージェントが L1 の作業を Playwright の ARIA スナップショットだけを手がかりに行い、操作の数・戻った回数・
  lostness（Smith, 1996。訪れた場所の総数 S・異なる場所の数 N・最短の手順の数 R から、√((N/S − 1)² + (R/N − 1)²)）を測る。
- しきい値は lostness 0.4 である（Smith の研究で、0.4 未満の利用者は迷った様子を見せず、0.5 を超えると迷っていた）。0.4 を超える作業は、L1 か画面を直す。
- いつどこで測るか、0.4 を超えた作業をどう issue にするか、UI を変える PR に何を書くかは ADR-0015 §4 が決める。

### 8. 原則と層を見直す条件

- 設定の画面の試験で、L1 を書く手間に対して画面の改善が小さいと分かった場合（L1 を必須にせず、L2・L3 だけにする）。
- L3 の規則が誤検知ばかりで、無効化のコメントが増え続ける場合。

### 9. 品質ゲート: 検査の層

規約の全文は [Web クライアントの設計規約](../architecture/web-client/README.md) にある。検査の場所は ADR-0079 が決める。「本検査」は Merge Queue の `check`、「遅い検査」はリリースの関門・nightly・手動で回す `slow-suite.yml` である。

| 層 | 道具 | 何を保証するか | CI |
| --- | --- | --- | --- |
| lint | Oxlint（Testing Library・境界・Tailwind のルール）、物理方向のユーティリティの禁止 | クリックできる `div` の禁止、論理プロパティだけを使う、ロールで要素を探すテスト | 本検査 |
| 部品（ロジック） | Vitest + Testing Library + `user-event`（DOM のシミュレーション） | ロールとアクセシブルネーム、キーボード操作、`aria-*` の状態 | 本検査 |
| 部品（実ブラウザ） | Storybook 10 + a11y アドオン + Vitest ブラウザモード（Playwright） | すべてのストーリーで axe の違反がない（`a11y.test: 'error'`）、コントラスト、`ar-XB` での表示 | PR（ui の文脈が変わったとき、`ui-test`） |
| 見た目 | Vitest ブラウザモードのスクリーンショット | 部品をコンテナ幅 3 種 × ライト / ダーク × LTR / RTL で比較 | PR（ui の文脈が変わったとき、`ui-test`） |
| E2E | Playwright + `@axe-core/playwright`、ARIA スナップショット | 主要な流れ。画面幅 320 / 390 / 768 / 1024 / 1440 px × 4 ロケール | 遅い検査（全体）。部分集合は手動。PR と main への push では回さない |
| 手動 | VoiceOver（iOS / macOS）、TalkBack、NVDA、200% / 400% 拡大、強制カラーモード | 自動化できない部分 | リリースごと |

- axe のタグは `wcag2a`, `wcag2aa`, `wcag21a`, `wcag21aa`, `wcag22aa` を使う。
- スクリーンショットの基準画像は、CI の固定したコンテナで生成してコミットする。手元で生成した画像はコミットしない。
- 部品を作るときはストーリーを必ず書く。部品のストーリーが、そのままアクセシビリティ・見た目・RTL のテストの入力になる。
- 品質ゲートは既定のテーマに対して働き、管理者のテーマについては色のトークンのコントラストだけをサーバーが保証する（ADR-0059）。

### 10. 品質ゲート: 部品と画面のルール

- **タイムラインは WAI-ARIA の feed パターンで作る。**
  - `role="feed"`、各投稿は `<article>`、`aria-posinset` / `aria-setsize`、読み込み中は `aria-busy` を付ける。
  - Page Down / Page Up で投稿間を移動する。
- **新しい投稿の差し込みは ADR-0013 と ADR-0013 が決める。** `timeline_auto_insert` が偽のときと一時停止の間は、タイムラインに自動で差し込まず、「N 件の新しい投稿」ボタン（`role="status"`）にする（WCAG 2.2.2）。
- **ルートが変わったら、新しい画面の `h1` にフォーカスを移し、`document.title` を更新する。**
- **CW は disclosure パターンで作る。** `aria-expanded` を付けたボタンで開閉し、閉じた内容は `hidden` にする。
- **文字数カウンタは入力が止まったとき、またはしきい値（残り 50 / 20 / 0）で読み上げる。**
- **レスポンシブ**
  - モバイルファーストにする。画面幅のブレークポイントはアプリの外枠だけで使い、部品にはコンテナクエリを使う。
  - 320 px で横スクロールが出ない。
  - タップ領域は 24 px 以上、主要な操作は粗いポインタ（`pointer-coarse:`）で 44 px 以上にする。
  - 端に固定する要素には `env(safe-area-inset-*)` を足す。高さには `100vh` ではなく `svh` / `dvh` を使う。
  - アニメーションは `motion-safe:` の下に置く。

### 11. モバイルのナビゲーションと投稿の入口

下端のタブバーは 6 項目（ホーム・ローカル・連合・通知・検索・メニュー）にする。プロフィール・ブックマーク・設定は「メニュー」のシートにまとめる。投稿のボタンはアイコンだけの浮かぶボタンにする。

- ローカル（`/local`）と連合（`/public`）は、どの幅でもナビゲーションの別の項目・別の画面にする。どちらの画面もそのタイムラインだけを置き、もう一方へのタブを持たない。
- タブバーのタイムラインの項目は、インスタンスが提供するタイムライン（`GET /instance` の `timelines`）だけを出すので、項目の数は 4〜6 つになる。無効にしたサーバー（FR-202）では項目が減るだけで、形は変わらない。
- 項目名は省略しない。各項目は文言の幅を基本にして残りの幅を分け合い、6 つが 320 px に収まらない翻訳では単語の途中でも折り返して、全体を読めるようにする。
- 浮かぶボタンは `md` 未満でアイコンだけ（アクセシブルネームとツールチップは「投稿を書く」）にし、タイムラインとプロフィールの画面にだけ出す。
- `md` 以上のレールとサイドバーは、ホーム・ローカル・連合・通知・検索・プロフィール・ブックマーク・設定を並べる。タブバーと同じ 1 つのリストの同じ順番で、その幅で出ない項目を隠す。
- ブックマークの一覧の入口は、`md` 以上のレールとサイドバー（プロフィールと設定の間）と「メニュー」のシートに置き、タブバーには置かない。
  「メニュー」のシートには、タブバーにないレールの項目をレールと同じ順（プロフィール・ブックマーク・設定、権限のある閲覧者にはモデレーションと管理、ADR-0058）で並べる。
- レイアウトの詳細は [web-client §9](../architecture/web-client/09-app-shell.md#9-アプリの外枠) が受け持つ。
- 覆る条件: 6 つの項目では折り返しても読みにくい（3 行以上になる）ロケールを加える場合や、利用の計測でタブバーの項目の使われ方が大きく偏ると分かった場合は、タブバーの項目の選び方を見直す。

### 12. 見た目の言語: 柔らかさを出すところ

柔らかい面を、場所を限って採る。柔らかさは「面」と「影」で出し、「操作できること」は色と境界で示す。

- **面の段差**: 画面の背景（`surface`）、区画（`surface-raised`）、へこんだ面（`surface-sunken`）を、柔らかい影の組で分ける。
  カードと設定のまとまりは、明暗の 2 つの影でわずかに浮かせる。
- **入力欄**: テキストの欄・選択・トグルの溝は、内側の影でへこみとして描く。ただし境界は 1.4.11 の 3:1 を満たす線か色の差で残す。
- **押した状態**: ボタンを押している間（`data-pressed`）は、浮いた面からへこんだ面に変える。P2 のマイクロインタラクションとして、`duration-fast` と `ease-standard` で移す。
- **角丸**: 段階（`radius-*`）を保つ。柔らかさのために大きくするのは区画とカードだけにする。
- 一覧の項目には影を付けない（低性能の端末でのタイムラインのスクロールのため）。

### 13. 見た目の言語: 保つところ

- **主な操作のボタンは色で塗る**（`accent`）。影だけのボタンにしない。
- **操作の部品の境界は 3:1 を保つ**。影はそれに足す飾りで、境界の代わりにしない。強制カラーモードでは `border` と `outline` が残る。
- **フォーカスの輪**（`focus-ring`）は変えない。

### 14. 見た目の言語: トークンとテーマ

- 明暗の影の組は、新しい影のトークン（例 `--elevation-soft-raised`・`--elevation-soft-inset`）にする。値は面の色のトークンから CSS の相対色（`oklch(from var(--color-surface) …)`）で
  明るさだけを変えて作り、面の色を上書きしたテーマでも追従させる。
  相対色は Chrome 119・Firefox 128・Safari 16.4 から使え、そろったのは 2024 年 7 月で、`theme.css` がすでに使う `light-dark()`（Baseline 2024、5 月）とほぼ同じ時期である
  （2026-10-28 に [MDN の light-dark()](https://developer.mozilla.org/en-US/docs/Web/CSS/color_value/light-dark) と [MDN の相対色](https://developer.mozilla.org/en-US/docs/Web/CSS/CSS_colors/Relative_colors) で確認）。
  対応しないブラウザでは `@supports (color: oklch(from white l c h))` で分け、前の影（`--elevation-*`）に戻す。
- **ダークモード**では、暗い面の上の明るい影は目立たず濁るので、明るい側の影を使わない。浮いた面は、面の上端の内側の 1px の明るい線（`inset 0 1px 0`）と暗い影で、
  へこんだ面は内側の暗い影だけで描く。ライトとダークの値は `light-dark()` で 1 つのトークンにまとめる。
- 影のトークンは ADR-0059 の上書きできるトークンに入る。新しいトークンは生成器の一覧に足す。
- 品質ゲート（§9）のスクリーンショットとコントラストの検査は、既定のテーマで、ライトとダーク、強制カラーモードで行う。

### 15. 見た目の言語を見直す条件

- 試作の部品（ボタン・入力欄・カード・設定のまとまり）で、柔らかい面が前の見た目と比べて決定者の意図に届かないと分かった場合（ニューモフィズムの要素を足す前に、コントラストの扱いを別に決める）。
- 相対色で作った影が、サーバーのテーマで実用的な見た目にならない場合（影の組を、テーマの上書きの値として管理者が直接指定する形にする）。
- 試作で、ダークモードの浮いた面が段差として読めない場合（ダークモードでは柔らかい面をやめ、前の境界と影に戻す）。

### 16. データの図: 最初の部品

データの図の部品は `@my/ui` に手書きの SVG と HTML で作る（新しい依存なし）。要る図は、軸 1 本の棒・折れ線と、割合の帯と、数だけである。これらは線形の目盛りと数十行の座標の計算で描け、ライブラリの機能の大半を使わない。
手書きなら、色・向き・動き・読み上げを、ほかの `@my/ui` の部品と同じ規則（トークン・論理プロパティ・`forced-colors:`・`motion-safe:`）で書ける。

名前は実装で決める。数と日時の書式は、`@my/ui` がカタログを持たないので（ADR-0025）、書式済みの文字列か書式の関数を props で受け取る。

| 部品 | 描き方 | 役割と読み上げ |
| --- | --- | --- |
| 数の要約（`StatTile`） | HTML | 名前・値・前の期間との差。差は上下の矢印のアイコン（`Icons.tsx`）と「+12%」の文字で示し、色だけにしない。状態（注意・危険）は `Badge` と同じトークン |
| 推移の図（`TrendChart`） | SVG | 期間ごとの棒か折れ線（系列は 3 本まで）。図は `role="img"` で、見出しと要約の文（最大・最新・増減）を `aria-labelledby` と `aria-describedby` にする。「図 / 表」の切り替え（React Aria の `ToggleButtonGroup` を `@my/ui` で包む）で同じデータを `@my/ui` の `Table` で出す。切り替えの選択は URL か `lib/storage` に置く画面の側の状態にする |
| 小さな推移（`Sparkline`） | SVG | 一覧の行の中の折れ線。飾りとして `aria-hidden` にし、同じ行に数を文字で必ず出す |
| 内訳の帯（`BreakdownBar`） | HTML | 項目ごとの割合を 1 本の帯に並べ、凡例に名前・値・割合を文字で出す。帯は `flex` の論理の向きで並ぶので RTL で自然に反転する |
| 進み具合（`ProgressMeter`） | HTML | React Aria の `ProgressBar`（決まった量の進み）と `Meter`（量の度合い）で包み、`aria-valuetext` に「1,234 / 5,000 件」の文を渡す |

SVG を描くのは `TrendChart` と `Sparkline` だけである。帯・進み具合・数の要約は HTML と CSS で描く。

### 17. データの図: 規約

- **G10（`restrict/svg`）**: 例外に「データの図（`TrendChart`・`Sparkline`）」を足し、`app/.oxlintrc.json` に 2 つのファイルを理由とともに挙げる。アイコンは `Icons.tsx` だけから使う。レビューで図以外の絵を入れないよう見る。
- **ADR-0025**: 依存を増やさないので許可リストは変えない。
- **web-client §14**: 費用・収入（`/admin/finance`・`/finance`・`/about/costs`）・ジョブ・エラー・サービスの終了の規約は、図と表の切り替えで出す形にする。

### 18. データの図: 色・テーマ・向き・動き

- **色**: SVG の `fill` と `stroke` は Tailwind のユーティリティ（`fill-*`・`stroke-*`）でトークンから取り、`light-dark()` とサーバーのテーマにそのまま追従させる。
  系列の色は新しい 3 つのトークン `--color-data-1`〜`--color-data-3` にし、ADR-0059 の上書きできるトークンと生成器の一覧に足す。
  各色は面（`surface`・`surface-raised`）に対して 3:1 を満たし、`check-tokens` の対象にする。
- **色だけに頼らない**: 系列は線の形（実線・破線）と凡例の文字でも分ける。差・状態はアイコンと文字を添える。
- **強制カラーモード**: 系列の色は失われるので、`forced-colors:` で線と棒を `CanvasText`、強調を `Highlight` にし、系列は線の形で分ける。帯の区切りは境界線で残す。
- **ダークモードと面**: 図は区画（`surface-raised`）の上に置き、格子の線は `border` のトークンにする。§12〜§14 の影を図の要素には使わない。
- **RTL**: 時間の軸は行の向きに合わせ、RTL では新しい期間を左に置く。SVG は `dir` に従わないので、React Aria の `useLocale().direction` で x の目盛りを反転する。数と日時は `dir="ltr"` の `bdi` で出す。
- **動き**: 描き始めの動きは付けない。値が変わったときの移り変わりだけを `motion-safe:` とトークンの長さ・緩急（`duration-fast`・`ease-standard`）で付ける。

### 19. データの図: 検査

部品ごとにストーリー（ライト・ダーク・強制カラー・`ar-XB`・空のデータ・1 点のデータ）と、座標の計算・目盛り・表の切り替えの単体テストを置き、§9 の axe とスクリーンショットの検査に入れる。

### 20. データの図を見直す条件

- 散布図・拡大・範囲の選択・ツールチップでの点の読み取りのように、対話の多い図が要る画面の要件（L1）が出た場合（visx の低水準の部品を許可リストに足して、その図だけに使う）。
- 手書きの図の計算（目盛り・欠けたデータ・負の値・通貨の違う系列）の不具合が、部品の追加のたびに続く場合。

## 経緯

Web クライアントは WCAG 2.2 AA を目標とし（NFR-A11Y-1）、RTL を含む多言語（ADR-0009）、スマートフォンから PC までが対象である。自動検査（axe）で見つかる問題は件数で約 57% にとどまる（Deque の調査）ので、自動化の層を重ね、残りを手動の確認で補う品質ゲートを最初に決めた（§9、§10）。E2E の頻度はその後 ADR-0079 に、lint は ADR-0025 §8 に、新着の差し込みは ADR-0013 に移った。

M3.5 の UI 監査（#328）で 320 / 390 px × `en` / `ja` / `ar-XB` で表示すると、7 項目を等分に並べたタブバーは 1 項目が 45〜55 px で項目名が切れ、文言付きの浮かぶボタンは 320 px で画面幅の約半分を占めていた。主要な類似クライアントは下端を 5 つ以下にしている。決定者の指示（#660）で、ローカルと連合は 1 つの画面のタブにせず別の場所に置いた（§11）。

その後の点検で、「どう描くか」の規約を守ったまま、操作の部品を縦に並べただけの画面ができることが分かった。設定の画面を 4 観点で点検すると 16 の問題（情報設計 9、シグニファイア 3、フィードバック 2、UX ライティング 2）が見つかり、既存の規約を守っていないのは 3 つだけで、残りは規約の穴だった。A4 のもとで画面を組む最短の道は `Stack` などの下位の部品を積むことで、パターンの部品が少なかった。画面の追加の多くはエージェントが行い、エージェントはスクリーンショットの評価は苦手だが、テキストの意図と構造（ARIA のツリー、文言のカタログ）の照合は得意である。そこで v0 のリリース（M5）までに既存の画面を整え、以後戻らない仕組みを 5 層で作った（§1〜§8）。判断基準は、利用者が迷わないことを最優先に、エージェントが点検できること、直した問題が部品か検査として残ること（ADR-0000）、既存の規約・テーマと矛盾しないこと、手間が品質に見合うことである。

L4 は当初 PR の前に行うと決めたが、並列の作業では PR ごとにアプリを動かす価値がなく、最初の並列の作業（#1643）で測れなかったので、nightly に移した（ADR-0015 §4）。

決定者は「楽しい」UI の見た目としてニューモフィズムの柔らかな印象を挙げた。そのまま採ると、押せる面と押せない面の違いが影だけになって P1 とぶつかり、WCAG 2.2 の 1.4.11（3:1）に届かず、ADR-0059 のテーマとダークモードで崩れ、強制カラーモードで境界が消える。そこで場所を限って採った（§12〜§15）。

Issue #1638 の管理の画面の点検は、要約がない（A1）、費用と収入の推移・内訳・収支が見えない（A3）、ジョブの失敗が目立たない（A9）、エラーの推移が 24 行の表である（A10）、配送の進み具合の割合が見えない（A11）と指摘した。P3 は数と推移を図で示すことを求めるが、`@my/ui` に図の部品がなかったので、依存（ADR-0025）と G10 に触れる作り方を先に決めた（§16〜§20。比較は 2026-10-28 に npm の registry と Bundlephobia で確かめた）。

## 採らなかった案

- 原則だけを文書にする: いちばん安く意図をそのまま書けるが、「どう描くか」の規約が厚いのに画面がのっぺりしている状態は、レビューだけでは守られないことを示している。
- パターンの部品だけを増やす: 効果が見えやすく A4 にそのまま乗るが、何を強制する部品にすべきかは画面の目的から決まるので、L1 がないと部品を置いただけの画面に変わるだけになる。
- 画面を AI に見せて評価させる: 見た目そのものを評価できる唯一の自動の方法だが、画面の目的を知らずに評価し、結果がぶれ、指摘が部品や検査として残らない。L5 の補助（2 つの案を目的に照らして比べさせる）には使える。
- タブバーに 7 項目を並べ 2 行まで折り返す: すべての場所に 1 回で届くが、`ar-XB` と `en` で 2 行にしても 320 px で切れる項目が残り、頻度の低いプロフィールと設定が幅を使う。
- 下端を 5 項目にしローカルと連合を「タイムライン」のタブにする: 項目が 5 つで済むが、決定者の指示に反し、1 タップ多くかかる。
- 投稿をタブバーの中央に置く（Mastodon Web と同じ）: 他のクライアントから来た人に馴染むが、「場所でない項目」が混ざり、`aria-current` の付く項目と付かない項目が並ぶ。投稿の入口が `md` 以上と違う形になり、ローカルか連合がタブバーに入らない。
- ニューモフィズムを全面的に採る: 印象の変化がいちばん大きいが、1.4.11 と強制カラーモード、サーバーのテーマで崩れ、P1 とぶつかる。
- 「境界を先に」の見た目を保つ: 費用がなく検査も通っているが、決定者の求める柔らかさと洗練が出ない。
- Recharts を許可リストに足す: 棒・折れ線・面・円とツールチップ・凡例・軸がすぐ使え、端の場合が解かれているが、約 150 kB（gzip）で依存の木が大きい（Redux Toolkit・immer・`victory-vendor` など 11 個）。
- visx の低水準の部品（`@visx/shape`・`@visx/scale`）を許可リストに足す: 描画を自分で持ちながら目盛りと形の計算を借りられるが、今の図には要らない。§20 に当たったときの移り先である。
- Chart.js・ECharts のような canvas で描くライブラリ: 機能が豊富だが、図がアクセシビリティのツリーにも CSS の変数にも乗らない。

## Consequences（影響）

- 実装の前に「何を・なぜ」が決まり、エージェントがそれに照らして実装と点検ができる。批評が部品と検査に変わって残る。パターンの部品が増え、画面ごとの実装の量は減る。
- UI の issue を `agent:ready` にする前に L1 を書く手間が増える。決定者のレビューの負担も L5 の分だけ増える。
- L3 の規則は、情報設計の良し悪しの代わりの量しか測れない。上限を守っても良い画面になるとは限らない。
- lostness は、エージェントが ARIA のツリーで迷うかを測るもので、人が見た目で迷うかとは一致しない。L5 の人の批評で補う。
- CI に実ブラウザのジョブが増え、時間が延びる。
- 320 px でもすべての項目名が省略されずに読め、ローカルと連合にどの幅でも 1 タップで届く。6 つの項目では 1 項目の幅が狭く、長い翻訳では項目名が単語の途中で折り返し、タブバーの高さが増える。プロフィールと設定は 1 タップ遠くなり、「メニュー」のシートという画面の型が 1 つ増える。
- トークンと `@my/ui` の部品の変更だけで、すべての画面が柔らかい見た目になり（`app/web` の変更は要らない）、押したときに面がへこむことが P2 の共通の型になる。影が増えるので、低性能の端末でのスクロールが重くなるおそれがある。
- 図の部品は依存が増えず、公開の `/about/costs` に足す JavaScript は部品の分だけで済む。表への切り替えを必須の形にするので、図を足しても表の情報を失わない。
- 目盛りの丸め（1・2・5 の刻み）、欠けた期間、負の収支、通貨ごとの系列の扱いを自分で書いてテストする。ツールチップ・拡大・凡例の切り替えのような対話は持たず、値は表への切り替えで読む。`restrict/svg` の例外が 2 つ増える。
- 後続の作業: 既存の画面を、利用者が多く使う順（タイムライン・投稿・通知・プロフィール）に点検する。
