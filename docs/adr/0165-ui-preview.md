# ADR-0165: PR ごとの UI のプレビュー

- Status: Accepted
- Date: 2026-11-11
- Deciders: @rosylilly
- Issue: #1638, #2863

## Decision（決定）

### 1. 置くもの

PR ごとに、部品と画面のカタログを 1 つの URL で公開する。画面のストーリーはアプリ全体を描き、画面の要件（ADR-0110）の作業ごとの状態（通常・空・読み込み中・エラー・長い文言・RTL・最小幅）を列挙する。画面のストーリーは品質ゲートのアクセシビリティの検査に入れる。

ストーリーは各パッケージが自分の部品の隣に置く。Storybook のホストは 1 つで、層（デザインシステム・アプリの部品・画面）ごとに束ねてこのカタログにする。

### 2. 置き場

静的なファイルを返すだけのホスティングに置く。サーバーの実行環境にはしない。PR ごとの URL は検索に載せず、閉じた PR のものは消す。main のものが、決定者が全画面を見る一覧になる。

### 3. CI の構成

ビルドと公開を分ける。ビルドは秘密情報を持たず、フォークの PR でも動く。公開は main の側の定義で動き、成果物を静的なファイルとしてだけ扱って実行しない。プレビューはマージの条件にしない。変わったストーリーの一覧を PR に示し、決定者が見る順にする。

## 経緯

決定者が PR の画面と動きを見て批評するために足した。品質ゲートのスクリーンショットは動きを止めて撮るのでマイクロインタラクションが写らず、画面にはストーリーがなかった。そのスクリーンショットの比較は、のちに廃止した（ADR-0110 §9）。フォークの PR は秘密情報を読めないので、ビルドと公開を分けた。

## 採らなかった案

- 部品のカタログだけにする: 安いが、問題の中心である画面の情報設計を見られない。
- アプリ全体のデモにする: 導線を確かめられるが、特定の状態を作る仕組みが要り、状態を列挙するカタログより批評の入口として弱い。
- 見た目の比較と承認を持つ外部のサービスに置く: 機能はそろうが、無料の枠をすぐ超える。
- リポジトリに 1 つだけのサイトに置く: 外部の依存が増えないが、PR ごとの URL を持てない。

## 見直す条件

- 画面のストーリーの手入れが、画面の追加のたびに大きな手間になる: アプリ全体を差し替えた API で動くデモに切り替える。
- PR ごとの URL を持てなくなる: main の一覧だけを置く。
