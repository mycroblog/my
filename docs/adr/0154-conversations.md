# ADR-0154: 会話を ID と IRI を持つリソースにし、リモートの `context` を優先し、後から分かった同じスレッドを併合する

- Status: Proposed <!-- Proposed | Accepted | Rejected | Deprecated。Accepted にするのは人間の Decider のみ -->
- Date: 2026-11-09
- Deciders: @rosylilly
- Issue: #2550

## Decision（決定）

投稿を会話（スレッド）にまとめる単位を、`statuses.conversation_uri` の文字列から、ID と IRI を持つリソース「会話」に変える。
会話は投稿が届いた順によらず同じ結果になるように決め、後から同じスレッドと分かった会話は併合して、その事実をイベントとして残す。
ダイレクトメッセージの一覧とスレッドのミュートは、会話の ID を鍵にする。

§1〜§7 の結論は決定者が決めたもので、細部（表の列、上限の値、ページの大きさなど）は推奨案である。

### 1. 会話はリソースで、`statuses.conversation_uri` を置き換える

`content` モジュールに次の 3 つの表を置き、`statuses.conversation_uri` とその索引を消す（data-model §4.4）。

| 表 | 分類 | 持つもの |
| --- | --- | --- |
| `conversations` | リソース | `id`（UUIDv7）、`uri`（会話の IRI。一意）、`is_local`（IRI をこのサーバーが作ったか） |
| `status_conversations` | 現在値 | 投稿ごとに 1 行（`status_id` が PK）。投稿が今属する会話の `conversation_id` |
| `conversation_merges` | イベント | 併合された会話（PK）、併合先の会話、併合のきっかけの投稿、時刻 |

- 保存したどの投稿も、ちょうど 1 つの会話に属する。会話の行は、投稿が消えても残す（IRI が別の会話に使い回されないようにするため）。
- 会話の `uri` は、リモートが宣言した IRI（§2）か、このサーバーが作った IRI（§4）のどちらか。どちらも一意で、併合された会話の `uri` も併合先を指し続ける（§3）。
- スレッドの表示（`GET /api/v1/statuses/{id}/context`）は、`status_conversations` で同じ会話の投稿を候補として引き、祖先と子孫は返信のつながり（`status_reply_links`）でたどる。
  会話は候補を絞るだけで、返信のつながりの無い投稿をスレッドに出さない（§2 の宣言だけで他人のスレッドに投稿を差し込めないようにするため）。

### 2. 投稿の会話の決め方

投稿を保存するトランザクションで、次の順に最初に当てはまるものを使う。

1. **リモートの投稿の宣言**: `context`（FEP-7888）、無ければ `conversation`（OStatus 由来、Mastodon が送る）の IRI。
   その `uri` の会話があればそれ（併合されていれば併合先）、無ければその `uri` で新しい会話を作る。
   - `context` は `https` の IRI だけを読む（文字列・`Link` の `href`・埋め込みの `id`、federation.md §4 の規則）。`conversation` は `https` に加えて Mastodon の `tag:` の URI も読む。どちらも識別子として比べるだけで、取得しない。
   - このサーバーの会話の IRI（§4 の形）を宣言したリモートの投稿は、宣言を使わず 2 以降で決める。宣言だけで、ローカルの会話（ダイレクトメッセージを含む）にリモートの投稿を入れさせないため。
     返信のつながりがあれば 2 と §3 で同じ会話に入るので、正しい投稿が外れることはない。
2. **親の会話**: 返信で、親（`in_reply_to_uri`）が保存済みなら、親の会話。ローカルの投稿の返信はいつもここで決まる。
3. **新しい会話**: どれでもなければ、このサーバーの IRI（§4）で新しい会話を作る。返信でないローカルの投稿と、宣言も既知の親も無いリモートの投稿がここに来る。

1 で決めた会話と、保存済みの親の会話が違うときは、§3 の併合を同じトランザクションで行う。
宣言はスレッドを親より先に知る手がかりで、返信のつながりは同じスレッドである証拠として扱う。こうすると、親が先に届いても後に届いても、最後の状態は同じになる。

ADR-0006 の取り込み範囲の判定（federation.md §6.3 の 3: 返信先の会話にローカルの投稿がある）は、親の会話で行い、投稿が宣言した会話では行わない。宣言だけで取り込み範囲を広げさせないため。

### 3. 併合

返信のつながりが 2 つの会話を同じスレッドだと示したら、子の側の会話を親の側の会話へ併合する。残るのは親の会話。

- きっかけは 2 つで、どちらも投稿の保存と同じトランザクションで行う。
  - 保存する投稿の親が保存済みで、親の会話と投稿の会話が違う（§2 の 1 で決まったとき）
  - 保存する投稿を親とする返信（`statuses (in_reply_to_uri)`）が保存済みで、その返信の会話が投稿の会話と違う（返信が先に届き、親が後から届いたとき）
- 併合は、`conversation_merges` に 1 行を記録し、`status_conversations` の併合される会話の行をすべて併合先に移し、ドメインイベント `content.conversation_merged`（併合された会話、併合先）を outbox に発行する。
  会話の投影（ダイレクトメッセージの一覧）とスレッドのミュートは、このイベントで行を併合先へ移す（§6）。
- 併合するのは、どちらも併合されていない会話（併合先をたどった先）どうしだけ。併合された会話の ID・`uri` は、`conversation_merges` を併合先へたどって引く。
  たどる回数は併合の回数だけ増えるので、引く側は回数に上限（32）を置き、超えたら不整合としてエラーにする。
- 返信先（`in_reply_to_uri`）は不変の事実なので、併合を戻すことはない。親が後で消えても、併合はそのまま残る。
- 同じ会話の組を 2 回併合しようとしても、2 回目は「同じ会話」になって何もしない。投稿の取り込みと親の取得のジョブを何度繰り返しても、どの順で行っても、同じ結果になる。
- 同時に届いた親と返信が互いを見落とさないよう、投稿の取り込みの projector が取るキー（`Repository.LockStatusKeys`、data-model §4.4）に、関わる会話の ID を加え、決まった順に取る。

親の会話を残すのは、スレッドの根に近い側の ID と IRI を変えないため。ローカルの投稿が根なら、送った `context` の IRI はそのまま残る。

### 4. 会話の IRI

このサーバーが作る会話の IRI は `https://{host}/ap/contexts/{uuid}`（`{uuid}` は会話の `id`）とし、ADR-0018 §1 の一覧に加える。一度送った IRI の形は変えない（ADR-0023 §9 の連合の識別子）。

- 最初の版から、この IRI で会話のスレッドを FEP-7888 のコレクションとして配信する（§9）。ほかのサーバーがスレッドを補えるようにするため。
- `is_local` が偽の会話（リモートが宣言した IRI）の IRI は、受けたままの値で、このサーバーは何も配信しない。

### 5. ローカルの投稿は `context` と `conversation` を送る

ローカルの投稿の Note には、投稿の会話（併合されていれば併合先）の `uri` を `context` に載せ、同じ値を `conversation`（`ostatus:conversation`）にも載せる。

- `uri` が `https` でない会話（Mastodon の `tag:` の URI）では、`conversation` だけを載せ、`context` は省く（Mastodon と同じ扱い）。
- `conversation` も載せるのは、Mastodon（v4.5.21・v4.7.5・v5.0.0-beta.1 で確認）が受信で `conversation` だけを読み、`context` を読まないため。`context` だけでは、Mastodon の利用者がこのサーバーの投稿に返信したとき、その返信がこのサーバーと同じ会話に入らない。
- 併合の後の Note の GET と次の `Update` は、併合先の `uri` を載せる。併合のためだけの `Update` は送らない（併合はスレッドの根に近い側に寄せるので、送った IRI は根の側の会話を指し続ける。§3）。
- `@context` に `ostatus:conversation` の語を加える（federation.md §7.4）。`context` は AS2 の語なので加えるものは無い。
- `context` の IRI は、作者のハンドルも本文も含まない不透明な識別子なので、返信の `inReplyTo`（ADR-0018 §15）と同じく、親の公開範囲によらず載せる。

### 6. ダイレクトメッセージの一覧とスレッドのミュートの鍵

- ダイレクトメッセージの一覧（`direct` の投稿を会話ごとにまとめたもの）は `v0.1.0` に入れる。UI の名前は `en` で「Direct messages」、`ja` で「DM」。Misskey のチャットのような、投稿と別の仕組みは作らない。
- 一覧の投影（`timeline` モジュール）は会話の ID を鍵にする。`content.conversation_merged` を受けたら、併合された会話の行を併合先へ移し、既読の境界と非表示の境界は 2 つのうち新しい方を残す。
  表とクエリは data-model §6.4 に書き、詳細は一覧の実装（#2552）で決める。
- 併合された会話の ID を指す API の要求には、併合先の会話で答える。
- スレッドのミュート（#2567）も会話の ID を鍵にし、併合でどちらかの側のミュートが併合先に効くよう、同じイベントで移す。

### 7. 時期

`v0.1.0` の前に入れる。DB を作り直してよい間なので（ADR-0023 §4）、`conversation_uri` から移す更新の手順は作らない。

### 8. この決定を見直す条件

- 主要実装が `context` を、スレッドより広いまとまり（コミュニティ・フォーラム全体）に使うと分かり、無関係な投稿が 1 つの会話に集まる場合（宣言を読む範囲を実装ごとに絞る）
- 宣言だけで会話に入る投稿（返信のつながりの無いもの）が、ダイレクトメッセージの一覧の混乱や嫌がらせに使われた場合（§2 の 1 を、FEP-7888 のコレクションで確かめた宣言だけに絞る）
- Mastodon が受信で `context` を読むようになった場合（`conversation` を送るのをやめる）
- 会話のコレクション（§9）の取得が負荷の大きな部分になった場合（ページの大きさ・キャッシュを見直す）

### 9. 会話のコレクション

`GET /ap/contexts/{uuid}` は、会話のスレッドの投稿のうち、要求した相手が見られるものを FEP-7888 のコレクションとして返す。

- **形**: ADR-0018 のほかのコレクション（outbox・followers・following）と同じ形で、`OrderedCollection` は最初のページ（`?page=true`）へのリンクだけを持ち、
  ページ（`OrderedCollectionPage`）は `partOf` と次のページ（`?min_id={カーソル}&page=true`）を持つ。スレッドは根から読むものなので、ほかのコレクションと違って古い順（投稿の `id` の昇順）に 40 件ずつ並べる。
  `totalItems` は載せない（見られる件数は相手ごとに違い、数えるのに全件の判定が要るため）。`@context` は ActivityStreams だけ。
- **項目**: 会話（`status_conversations`）の削除されていない投稿の IRI（ローカルは `id`、リモートは `uri`）。文書は埋め込まない。
  - 項目ごとに、単一の公開範囲の判定（`content.CanView`、`ContextObjectFetch`）を、閲覧者を署名者のドメインとして当てる（federation.md §10 の投稿の GET と同じ）。見られない項目は、ページから黙って省く。
  - リモートの投稿は、未ログインの閲覧者として見られるもの（`public` / `unlisted`、作者に `profile_view` が無く、署名者との間にブロックが無い）だけを載せる。このサーバーが受けたリモートの `private` / `direct` の投稿は、宛先の外へ出さない。
  - 項目を省いてもページは詰めない（カーソルは省いた項目も進む）。ページが空でも、次のページがあれば `next` を載せる。
- **対象の会話**: `is_local` が真で、併合されていない会話だけ。併合されたローカルの会話の IRI は、併合先がローカルの会話なら、その IRI へ `308` でリダイレクトし、そうでなければ 404 を返す。
  リモートの IRI を持つ会話と、存在しない会話は 404。どの項目も見られない会話も、空のコレクションを返す（会話の有無は Note の `context` で相手にすでに分かっていて、空かどうかで投稿の有無が漏れないようにするため）。
- **署名と Authorized Fetch**: ほかのコレクションと同じく、署名を §2 の受信の規則で検証し、署名の無い・検証できない要求は未ログインとして扱う。Authorized Fetch が有効なら、署名の無い要求に `401` を返す。
  連合の向きが `publish` を通さないときは 404、クローズしたサーバーでは `410`（federation.md §10・§15）。
- **キャッシュ**: 署名の無い要求への応答（Authorized Fetch が無効なとき）は、だれにも同じなので `public, max-age=60`。署名のある要求への応答と、Authorized Fetch が有効なときの応答は `private, no-store`。
  キャッシュした未ログインの応答を署名した相手が受けても、見える項目が少ないだけで、見せてはいけない項目は出ない。
- **`attributedTo`**: 載せない。このサーバーが作った会話でも、根の投稿がリモートのことがあり、根の作者を会話の持ち主とすると、FEP-7888 の「持ち主へ配送する」が意図しない相手に向くため。
- 配信は `federation.Objects`（`internal/app/federation`）が行い、Note の `context` の IRI と同じ形を組み立てる。

## 経緯

スレッドの表示（FR-106）・リモート投稿の保持期間の参照（FR-803）・取り込み範囲（ADR-0006）は、`statuses.conversation_uri` で同じスレッドを引いていた。
その値は、既知の親への返信なら親の値、返信でなければ自分の `uri`、親が未知の返信なら NULL で、後から埋める処理が無かった。
返信が親より先に届くと、そのスレッドは届いた順で別々に分かれたままになり、リモートが送る `context` / `conversation` も読んでいなかった。
また、data-model §6.1 と visibility.md §3 は、フォローしていない相手からの `direct` の投稿を「会話一覧」で読むとしていたが、その一覧は API も画面も無かった。
ダイレクトメッセージの一覧とスレッドのミュートには、届く順によらない安定した鍵が要る。

決定者は、会話を ID と IRI を持つリソースにすること、リモートの `context` を最初に使い、無ければ親、それも無ければ新しい会話にすること、後から届いた親が同じスレッドと示したら併合してイベントに残すこと、ローカルの投稿が `context` を送り、その IRI の形を ADR-0018 に置くこと、`v0.1.0` の前に入れること、ダイレクトメッセージの一覧を `v0.1.0` に入れること（UI の名前と、別のチャットを作らないことを含む）を決めた。
続けて、併合で親の会話を残すこと、IRI を `/ap/contexts/{uuid}` にすること、このサーバーの IRI を宣言したリモートの投稿は親で決めること、`context` の次に `conversation` を読みローカルの投稿は両方を送ること、会話の IRI を最初の版から FEP-7888 のコレクションとして配信すること（ほかのサーバーがスレッドを補えるようにするため）を決めた。

残った問いは、主要実装の実際の送り方を確かめて答えた（2026-11-09 にソースで確認）。

- **Mastodon**: Note に `context` と `conversation` の両方を載せる。ローカルの会話は `https://{host}/contexts/{親のアカウント ID}-{親の投稿 ID}` で、v4.5 から `Collection` として配信する（v4.4.28 には経路が無い）。
  リモートの会話は受けた IRI をそのまま返し、古いローカルの会話は `conversation` だけに `tag:` の URI を載せる。受信は `conversation` だけを読み、宣言があれば親の会話より優先する（`Status#set_conversation`）。
  出典: [note_serializer.rb（v4.5.21）](https://github.com/mastodon/mastodon/blob/v4.5.21/app/serializers/activitypub/note_serializer.rb)、
  [tag_manager.rb（v4.5.21）](https://github.com/mastodon/mastodon/blob/v4.5.21/app/lib/activitypub/tag_manager.rb)、
  [activity/create.rb（v4.7.5）](https://github.com/mastodon/mastodon/blob/v4.7.5/app/lib/activitypub/activity/create.rb)、
  [contexts_controller.rb（v4.5.21）](https://github.com/mastodon/mastodon/blob/v4.5.21/app/controllers/activitypub/contexts_controller.rb)。
- **Misskey**（2026.11.0-alpha.1）: `context` も `conversation` も送らず、読まない（`ApRendererService.ts`・`ApNoteService.ts`）。スレッドは返信のつながりだけで決まる。
- **GoToSocial**（v0.22.3 の `main`）: `context` も `conversation` も送らず、読まない。スレッドは内部の `ThreadID` で、返信のつながりから決める（`internal/typeutils/internaltoas.go`・`internal/gtsmodel/status.go`）。
- **Akkoma**（`develop`）: 受信は `context`、無ければ `conversation`、無ければ新しい `https://{host}/contexts/{uuid}` を作る。親が既知なら親の `context` を優先する。送信は `context` と同じ値の `conversation` を載せ、`/contexts/` は配信しない（`transmogrifier.ex`・`router.ex`）。
- **FEP-7888**（DRAFT）: `context` は解決できることが望ましい（SHOULD）が、消費者は `id` でまとめればよい。権威のある会話のコレクションに入っているという主張は、確かめるべき（SHOULD）としている（[FEP-7888](https://codeberg.org/fediverse/fep/src/branch/main/fep/7888/fep-7888.md)）。

この確認が、`context` の次に `conversation` を読むこと（Misskey・GoToSocial はどちらも送らないので親で決まり、Mastodon の古い会話と v4.5 より前は `conversation` だけ）と、送るときは Mastodon のために `conversation` も載せることの根拠である。
宣言を親より優先すると、親が先に届いたときと後に届いたときで結果が変わるので、返信のつながりによる併合（§3）を宣言の後に必ず行い、届く順によらない結果にした。

## 採らなかった案

- **`conversation_uri` を残し、親が後から届いたら書き換える**: 表が増えないのが一番の強み。だが、IRI の文字列を鍵にするとダイレクトメッセージの一覧とミュートの鍵が併合のたびに変わり、併合の事実も残らない。ADR-0020 の「状態の変化はイベントで残す」にも合わない。
- **会話を持たず、スレッドを返信のつながりから毎回たどる**（GoToSocial・Misskey の形に近い）: 宣言を読まなくてよい。だが、親が未知の返信をスレッドに入れられず、一覧とミュートの鍵が無い。
- **宣言を読まず、親だけで決める**: 宣言による差し込みが起きない。だが、親を取得できない（削除・取り込み範囲外・取得の上限）返信がスレッドから外れ、決定者の決めた「`context` が先」に反する。
- **親が既知なら親の会話を宣言より優先する**（Akkoma の形）: 併合が減る。だが、宣言した会話が別の会話として残り、その IRI を宣言する後の投稿が親と別の会話に入る。§2 の形は、宣言の会話を作ってから親へ併合するので、IRI が併合先を指し続ける。
- **併合で残るのを、投稿の多い側・古い側にする**: 動かす行が少ない・ID が古い順に安定する。だが、どちらも届いた順で変わり得て、ローカルの根が送った `context` の IRI が併合された側になることがある。親の側ならスレッドの根に近い側の ID と IRI が残る。
- **このサーバーの IRI を宣言したリモートの投稿も受け入れる**: Mastodon が返信でこのサーバーの `context` を引き継ぐので、親の取得を待たずに同じ会話に入る。だが、宣言だけでローカルのダイレクトメッセージの会話に投稿を差し込めてしまう。親の取得（federation.md §6.3）と併合で同じ結果になるので、受け入れない。
- **会話の IRI を最初の版では識別子だけにする（`GET` は 404）**: 公開範囲ごとの絞り込み・ページ分け・キャッシュの実装を後に回せ、読む実装もまだ限られる（Mastodon の受信は `context` を読まない）。だが、ほかのサーバーがこのサーバーのスレッドを補う手段が無く、FEP-7888 の「解決できることが望ましい」にも反する。Mastodon v4.5 も配信しているので、最初の版から配信する。
- **コレクションに文書を埋め込む**: 取得する側の往復が減る。だが、項目ごとに Note を組み立てる費用がかかり、Mastodon も IRI だけを載せる。
- **新しい順に並べる**（outbox と同じ）: ほかのコレクションと揃う。だが、スレッドは根から補うもので、Mastodon の会話のコレクションも古い順（`min_id`）に並べる。
- **IRI を `/ap/conversations/{uuid}` にする**: このサーバーの名前（会話）と揃う。だが、IRI が現れるのは AP の `context` で、Mastodon と Akkoma も `/contexts/` を使う。FEP-7888 の文脈はスレッド以外の種類も含むので、プロパティの名前に揃えた。
- **併合で Note の `Update` を送る**: 連合先が新しい IRI を知る。だが、併合のたびに多くの `Update` が出て、受けた側では編集に見えることがある。残るのは根の側なので、送った IRI がそのまま使える。

## Consequences（影響）

- 良い影響: スレッドが届く順によらず 1 つにまとまる。ダイレクトメッセージの一覧とスレッドのミュートが、併合を越えて同じ鍵で続く。Mastodon・Akkoma のスレッドと同じ会話を共有できる。
- 良い影響: `context` を読まない Misskey・GoToSocial の投稿も、返信のつながりと親の取得で同じ会話に入る。
- 良い影響: 会話のコレクションで、ほかのサーバーがこのサーバーのスレッドを補える。
- 悪い影響: 会話のコレクションのページごとに、項目の数だけ公開範囲の判定が走る。見られない項目の多い会話では、空に近いページが続く。
- 悪い影響: 投稿を保存するたびに会話の行と `status_conversations` の行が増え、取り込みのトランザクションでロックするキーが増える。
- 悪い影響: 大きな会話の併合は、`status_conversations` の多くの行を 1 つのトランザクションで書き換える。返信が先に届いた側（小さいことが多い）が動く側だが、上限は置かない。
- 悪い影響: 他のサーバーの IRI の宣言は確かめないので、返信のつながりの無い投稿が宣言だけで会話に入る。スレッドの表示には出ない（§1）が、ダイレクトメッセージの一覧には出得る（その投稿の送り手が参加者として見える）。Mastodon の会話の一覧も宣言の `conversation` でまとめるので同じ扱いと見ている（要検証）。
- 悪い影響: 投稿の無くなった会話の行が残る。消去するかは後続で決める。

## Open Questions / 要検証

- 要検証: Mastodon 以外の主要でない実装（Pleroma 本家・Friendica・Hubzilla・NodeBB など）が `context` をスレッドより広いまとまりに使っていないか（§8 の 1 つ目）。
- 要検証: Mastodon の会話の一覧が、宣言の `conversation` だけで入った投稿を同じ会話に出すか（Consequences の差し込みの比較）。
- 後続で決める: 投稿の無くなった会話の行の消去（リモート投稿の保持期間の消去と合わせるか）。
