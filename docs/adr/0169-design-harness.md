# ADR-0169: デザインのハーネス（役割・育つ知識・評価）

- Status: Accepted
- Date: 2026-11-12
- Deciders: @rosylilly
- Issue: #2864, #2874

## Decision（決定）

### 1. エージェントがうまくなるべきこと

UI の作業でエージェントが身につけるのは次の 6 つである。役割、知識、関門はすべてここから逆算する。

1. 色・配置・密度の常識を決定者と共有し、2 つの案のどちらが良いかの判断が一致する
2. 文言の方針が明文化されている
3. 操作に対する応答の方針が明確である
4. 1 つの画面の情報設計ができる
5. PC・タブレット・モバイルのどのビューポートでも違和感がない
6. 1 つの画面ではなく、サービスの画面を通した流れが分かっている

### 2. 役割

- 作る役を 4 つに分ける。**見た目**（1・4・5。色を付ける前の灰色の線画で情報設計を決め、その後に色と密度）、**動き**（3・6。状態の移り変わりと画面をまたぐ流れ）、**文言**（2）、**実装**（ADR-0025 の構成に従う）。役は人格ではなく、持つ知識と見るものの違いで分ける。
- 評価する役を 2 つ置き、どちらも作った過程を知らない新しいコンテキストで走らせる。**見た目の評価役**は描画した画面と課題と制約だけを受け取り、ソースと作者の説明は受け取らない。最初の一語で出してよいか・直すか・作り直すかを言い、指摘の数に上限を持ち、壊してはいけないものを 1 行で残す。**歩き手**は目的も期待する道筋も受け取らずに画面を辿り、詰まった所、迷った所、道を誤った所を報告する。6 を確かめる手段はこれである。
- 作る役は評価の基準を読まない。読むと、基準に合わせることが目的になる。

### 3. 知識の形

役ごとに 3 層の知識を持つ。

- **索引**: その役が必ず読む 1 枚。大きさに上限を置き、検査で守る。
- **決定**: 1 行に 1 件。決めたこと、理由、根拠になった決定者の訂正か選択、日付、その決定が効いた回数と外れた回数を持つ。自由な文章の段落は置かない。
- **実例**: 模範とする画面と、決定者が案から選んだときの落選した案とその理由。規則にできない良さは実例で運ぶ。選んだ記録そのものは役が読まない別の記録に置き、一致の確かめ（§7）はそれを再生する（決定者の決定、2026-11-13）。

決定と実例は、索引を小さく保ったまま、上限の大きい領域ごとのファイルに分けてよく、役は作業が触れる領域だけを読む（決定者の決定、2026-11-14）。

記録済みの決定に沿ったものを、評価役は指摘にしない。

### 4. 育ち方と整理

- 知識は決定者の訂正と選択から育つ。信号は、セッションの記録と、画面の上のメモ（ADR-0168）である。
- 訂正の 1 回目は決定の 1 行になる。同じ訂正が 2 回目に来たら、その決定を検査か道具に変える提案をし、変えたら行を消す。知識は文章から仕組みへ一方向に移り、移った分だけ上限に空きができる。強さの順は ADR-0000 §6 に従う。
- 上限に近づいたら整理する。似た行を統合し、外れ続ける行と使われない行を消し、繰り返し使われる行を検査に上げる。整理は行の追加・統合・削除の差分で行い、知識全体を書き直させない。
- 役の知識は、上限を検査で守る代わりに、行の追加に文書の純増の承認（ADR-0000 §6）を要しない。上限そのものを変えるのは決定者である。

### 5. 関門の段

検査は 3 段に分ける。**必ず止めるもの**（コントラスト、横スクロール、トークン以外の値など）、**理由を書けば見送れるもの**（理由には最低の長さがあり、決まり文句は認めない。1 つの変更で見送りが一定数を超えたら、それ自体を指摘する）、**答えるだけのもの**。見送りは記録に残り、同じ見送りが繰り返されたら決定か検査の見直しの信号になる。

### 6. 振り返り

作る役 4 つの観点で、セッションの記録を定期的に読み返す振り返りを持つ。決定者が言い直したこと、案から選んだこと、評価役と決定者の判断が分かれたことを拾い、§4 の行の追加と、仕組みへの格上げの提案にする。提案は pull request で出し、採否は決定者が決める。

### 7. 一致の確かめ方

決定者と評価役の判断が一致するかは、毎回は測らない。決定者が「だいたい一致するようになった」と感じたときに確かめる手順を持つ。過去に決定者が案から選んだ場面を、結果を伏せて評価役に選ばせ、一致した割合と、外れた場面の理由を返す。外れた場面は §4 の信号になる。

### 8. 始める順

文言から始める。機械で判定できる規則（避ける語と言い換え、記号、長さ、en と ja の対応）と判断の要る規則が分けやすく、既存のカタログの検査に置き場所があり、手本になる先行例がある。見た目と動きはその後に続ける。

### 9. UI の変更の進め方と、画面の文書の代わり

- 決定者の判断を、作り込む前に集める。情報設計か見た目が変わる変更（新しい画面、区画の組み替え、新しい部品）では、作る役がまず 2〜3 の案を灰色の線画（§2）のまま、画面の上で切り替えられる variant（ADR-0168 §1）として出し、決定者が選んでから色・密度・実装に進む。落選した案とその理由は §3 の実例になる。
- 直し方が記録済みの決定か画面の上のメモで決まる変更は、案を出さずに直す。
- 画面ごとの設計の文書は置かない。画面に何を置くかを文章で先に決めると、文章の求める説明が画面に足されていく。文書が運んでいたものは ADR-0000 §6 の強い順に移す。区画・見出し・保存の仕方は部品の型（ADR-0110 §5）と検査、入口と出口はアプリの経路の宣言、作業の道筋は E2E のシナリオ（ADR-0015 §5）と歩き手、画面をまたぐ判断は役の知識、その変更の目的と使う人は変更の課題（評価役に渡すもの）が持つ。

## 経緯

長い画面設計書、意味の薄い層のテスト、スクリーンショットの枚数で UI の質を保とうとしたが、決定者の訂正は減らなかった（#2854 の計測で、UI と進め方と文書への訂正は約 100 件）。2026-11-12 に公開されている Claude Code のデザイン向けスキルを 9 つ読んだ。効いている形は、新しいコンテキストで画面だけを見る評価役、段に分けた検査と理由つきの見送り、曖昧な語を観察できる値に置き換えることだった。決定者との判断の一致を測るものも、知識を上限の中で整理するものも、画面をまたぐ流れを確かめるものもなかったので、§3・§4・§7 と歩き手はここで決めた。知識を書き直させないのは、LLM に知識全体を書き直させると内容が大きく失われ、精度が下がるという報告（ACE, arXiv 2510.04618）による。§9 は、案を先に見せた変更は 2 往復で済み、作ってから見せた変更は作り直しになったこと、画面の文書の多くが画面の中身として説明文を求めていたことによる。

## 採らなかった案

- デザインとプログラマの 2 役: 受け渡しが少ないが、見た目と動きでは見るもの（描画した画面と状態の遷移）も知識も違い、1 役のコンテキストに両方を載せることになる。
- 評価を作る役の自己点検にする: 安いが、作った過程を知る役は自分の意図を画面に読み込み、見落とす。
- 知識を規則の文章として書き足す: 書くのは安いが、#2854 の計測で文章の指示はほとんど効かず、量だけが増えた。
- 決定の行の追加ごとに決定者が承認する: 決定者が確かめられるが、知識が育つ速さが決定者の手の空きで決まる。上限の検査で量を抑えるほうが安い。
- 一致率を毎回測る: 継続して見えるが、毎回の比較に評価役の費用がかかり、決定者が実感していない時点の数字は判断に使わない。
- すべての UI の変更で案を出す: 決定者の判断を漏れなく集められるが、決定とメモで直し方の決まった変更にまで選ぶ手間をかける。
- 案を画像で出す: コードより安いが、ビューポート・テーマ・状態を切り替えて比べられず、選んだ案をそのまま作り込めない。
- 画面の文書を短くして残す: 目的が 1 か所で読めるが、文章が画面の中身を求める形は残り、コードとずれる。

## 見直す条件

- 決定者が同じ訂正を言い直す回数（ADR-0000 §7）が、文言で始めてから減らない。
- 一致の確かめで、決定者が一致したと感じているのに一致率が低い、またはその逆が続く: 評価役の入力か基準を見直す。
- 上限に近づくたびに整理しても、すぐに上限に戻る: 上限か、仕組みへ移す基準が合っていない。
- 歩き手の報告が、決定者の流れについての訂正と重ならない。
- 案を先に出した変更でも、決定者が作り直しを求める回数が減らない: §9 の案の出し方か、案を出す変更の範囲を見直す。
