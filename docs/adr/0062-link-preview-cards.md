# ADR-0062: 投稿中のリンクのカード

- Status: Accepted
- Date: 2026-10-20
- Deciders: @rosylilly
- Issue: #652, #669, #1947, #1949, #1951

## Decision（決定）

**投稿時にサーバーがジョブで取得し、カードを URL ごとに共有する。** 取得は投稿と URL の数に比例し、閲覧者の IP は出ず、Mastodon と同じ見え方になる。
相手のサイトの `robots.txt` とページのロボットの指定に従い（§9〜§13）、運用者はカードの取得だけをドメインごとに止められる（§14〜§19）。

この ADR は **他所のページを取得して自サーバーの投稿にカードを出す** ことを扱う。逆向きの **自分のページ（`/@{acct}`、投稿）に OGP / X Card の meta を付けて他所にプレビューを出させる** ことは ADR-0028 が決める。
コードでも両者を混ぜないよう、ADR-0028 の側は「プレビュー」（`content.Previews`、`internal/interface/web`）、この ADR の側は「リンクのカード」（`LinkCard`、API の `card`）と呼び分ける。

### 1. 対象と契機

- **契機**: ローカルの投稿の作成・編集（`content` の投稿の版のイベント）と、ADR-0006 で取り込んだリモートの投稿の `Create` / `Update` の後に、ジョブ `content.fetch_link_card`（引数は投稿の ID）を outbox で積む。
  リモートの投稿のジョブは 0〜60 秒のランダムな遅延を付ける。多数のサーバーが同じ投稿を同時に受けて同じ URL を一斉に取る集中を散らすためで、Mastodon の `DISTRIBUTE_DELAY` と同じ幅にする。
- **選ぶ URL**: 投稿の現在の版の本文にある、次の条件を満たす **最初の 1 件**。
  - スキームが `http` / `https` で、ホストがある
  - メンションとハッシュタグのリンクではない。ローカルの投稿は `content.ParseText` の区分で、リモートの投稿はサニタイズ済み HTML の `a` の `class`（`mention`, `hashtag`, `u-url`）と `rel="tag"`、
    投稿のメンション・タグの URL との一致で除く
  - 自サーバーの URL ではない（自サーバーの投稿やプロフィールへのリンクにカードを出さない）
- **出さない投稿**: 添付（画像・動画・音声）や投票がある投稿、ブースト（ブーストされた投稿のカードを出す）。添付と並べると表示が重くなるためで、Mastodon も添付のある投稿は取らない。
- **公開範囲**:
  - **公開範囲によらず**（`public` / `unlisted` / `local` / `private` / `direct`）、カードがない・古いときに取得する。Mastodon と同じ見え方にする。
  - 取得は相手のサイトに「その URL がいつ投稿されたか」を知らせ、共有リンク・ワンタイムの URL では、GET で動く操作を実行させ得る。
    非公開の投稿でもこれを受け入れ、相手に伝わる情報を §4 の範囲に限ることで抑える。
- 編集で選ぶ URL が変わったら、ジョブを積み直してカードの参照を差し替える。URL がなくなればカードを外す。

### 2. 取得と解釈

- **HTTP**: `kernel.HTTPClient` に `HTTPPurposeHTML` で `GET` を送る。ADR-0019 §1 の宛先の拒否・リダイレクト 5 回・`https` から `http` への格下げの拒否・本文 1 MiB（展開後）・全体 30 秒をそのまま使う。取得の前に §12 と §14 で確かめる。
  - 要求ヘッダは `Accept: text/html, application/xhtml+xml`、`Accept-Language` はインスタンスの既定の言語（利用者の言語にしない。取得を利用者に結び付けないため）。Cookie と `Referer` は送らない。
  - 状態コード 200 と、`Content-Type` が `text/html` / `application/xhtml+xml` の応答だけを解釈する。
  - `http` の URL は、ADR-0019 §1 のスキームの制限（`https` のみ。開発用の設定を除く）に従い取得せず、カードを出さない。
- **解析**: `golang.org/x/net/html` のトークナイザで `<head>` の中だけを読み、`</head>` か `<body>` で止める。文字コードは `golang.org/x/net/html/charset`（`Content-Type` の `charset`、`<meta charset>`、推定の順）で UTF-8 にする。
  スクリプトは実行しない（JavaScript で meta を書き足すページはカードにならない）。
- **項目と優先順**（出典: [The Open Graph protocol](https://ogp.me/)、[X Cards markup](https://developer.x.com/en/docs/x-for-websites/cards/overview/markup)。X Card の項目名は要検証）:

  | 項目 | 優先順 | 上限 |
  | --- | --- | --- |
  | 題名 | `og:title` → `twitter:title` → `<title>` | 200 文字 |
  | 説明 | `og:description` → `twitter:description` → `<meta name="description">` | 500 文字 |
  | サイト名 | `og:site_name` → URL のホスト | 100 文字 |
  | 画像 | `og:image`（`og:image:secure_url` を優先）→ `twitter:image` | URL 2,048 バイト |
  | 画像の代替テキスト | `og:image:alt` → `twitter:image:alt` | 1,500 文字 |
  | 作者 | `article:author`（URL でない値）→ `<meta name="author">` | 100 文字 |
  | 公開日時 | `article:published_time`（RFC 3339 として読めるものだけ） | — |
  | 作者の Fediverse のアカウント | `fediverse:creator`（§5） | — |

  - 値はすべてプレーンテキストにする（HTML の実体参照を戻し、タグを除き、空白を 1 つにまとめる）。上限を超える分は文字（書記素）の境界で切る。
  - 相対 URL は応答の最終 URL を基準に解決し、`http` / `https` 以外は捨てる。
  - `og:url` は、最終 URL と同じオリジンのときだけカードの URL に使う（別のオリジンを名乗るページで、別のサイトのカードに見せかけられないようにする。Mastodon も同じオリジンに限る）。
  - 題名がなければカードを作らない（失敗として扱う）。
- **JSON-LD**: `<head>` の `<script type="application/ld+json">` を、スクリプトとして実行せず JSON として静的に読む（[JSON-LD 1.1](https://www.w3.org/TR/json-ld11/)、[schema.org](https://schema.org/)）。
  - 最上位またはその `@graph` にある `@type` が `NewsArticle` / `Article` / `BlogPosting` / `WebPage` の最初のオブジェクトだけを使う。`@context` の取得・展開はしない（外部 HTTP を増やさない）。
  - 使う項目は `headline`（題名）、`description`（説明）、`author.name`（作者。配列ならカンマと空白でつなぐ）、`datePublished`（公開日時）、`publisher.name`（サイト名）。
    上の表の項目がないときだけ使う（優先順は meta の後、`<title>` / `<meta name="description">` の前）。Mastodon は JSON-LD を meta より先に読むが、ここではページの作者が明示した meta を優先する。
  - JSON として読めないもの、1 つの `<script>` が 64 KiB を超えるもの、JavaScript で後から書き込まれるもの（取得した HTML にないもの）は使わない。上限と値の扱い（プレーンテキスト化）は表と同じ。
- **oEmbed と埋め込み**: oEmbed（[oembed.com](https://oembed.com/)）には対応しない（発見も取得もしない）。`twitter:player` / `og:video` による iframe・動画の埋め込みもしない。
  埋め込みは第三者の iframe とスクリプトを Web クライアントに入れることになり、閲覧者の IP と Cookie を相手に渡し、CSP（ADR-0019 §9）に `frame-src` を足す必要がある。
  動画のページも、題名・説明・サムネイルの静的なカードとして出す。Mastodon は `video` 型の oEmbed の HTML を iframe として出し、`rich` 型（スクリプトを使うもの）は拒否している。
- **失敗**: 取得・解釈の失敗（4xx / 5xx、タイムアウト、上限超過、HTML でない、題名がない）は、URL ごとに KV に 24 時間記録し、その間は同じ URL を取らない（ADR-0006 の取得の失敗の記録と同じ仕組み）。
- **同時取得の抑止**: 取得の前に URL ごとの短期のロック（KV、60 秒）を取り、別のジョブが取得中なら待たずに後で積み直す。ジョブは冪等で、同じ投稿のジョブが重なってもカードの行と参照の UPSERT で同じ結果になる。

### 3. 画像

- 画像の URL は、ほかのリモートのメディアと同じく **宣言値として記録し、クライアントにはメディアプロキシの URL で返す**（ADR-0005、[federation.md §9](../architecture/federation.md)）。
  クライアントが元のサイトの画像を直接読み込むことはない（閲覧者の IP を出さない。ADR-0019 §9 の `img-src` も広げない）。
- カードを作るジョブは、画像を `HTTPPurposeImage` で 1 回だけ取得し、形式を中身で判定し（ADR-0019 §8 の許可リスト、SVG は拒否）、寸法と blurhash を求めて記録する。
  形式・寸法の上限（ADR-0019 §8）に合わないものは画像なしのカードにする。取得した本体は保存しない（保存はメディアプロキシのキャッシュ方針 FR-409 に任せる）。
- 表示は ADR-0005（#644）のメディアプロキシの `small`（静止版の S）を使う。カードの画像の用途は投稿の添付と同じ S の大きさとし、アニメーション画像は最初のフレームの静止画にする。
  API は `small` の URL だけを返し、カードから原寸（`full`）は出さない。`remote_media_policy` が `all` のときは、ADR-0005 と同じく `remote_media_cache` に派生のキーで保存する。
- 画像は `media_files`（`origin = remote`）の部分型として記録する。所有者はアカウントではなくカードの URL なので、`remote_media`（所有者がアカウント）とは別の部分型にする（§6）。

### 4. プライバシー

- 取得はサーバーだけが行い、クライアントは自サーバーの API とメディアプロキシしか呼ばない。
- 相手のサイトに伝わるのは、サーバーの `User-Agent`（§9）、インスタンスの既定の言語、取得の時刻だけで、どの利用者・どの投稿かは伝えない。
- カードは URL ごとに共有するので、同じ URL を複数の投稿が貼っても取得は（再取得の間隔の内は）1 回で済む。
- カードの API の応答に、取得の時刻や失敗の理由など、運用者向けの情報は出さない。

### 5. `fediverse:creator`

- `<meta name="fediverse:creator" content="@user@domain">` を読み（複数あれば最初の 1 件）、カードを作るジョブの中で WebFinger（FR-401）でアカウントに解決する（10 秒まで。解決できなければ記録しない）。
- **検証できたときだけ** カードに作者のアカウントとして出す。検証は、解決した Actor の `attributionDomains`（Mastodon の `toot:attributionDomains`。
  出典: [Mastodon ActivityPub 仕様](https://docs.joinmastodon.org/spec/activitypub/)、2026-10-20 確認）が、ページの最終 URL のホストかその親ドメインを含むこと。
  検証できない宣言は捨てる（任意のページが任意のアカウントを作者と名乗れるため）。Mastodon も同じドメインの照合をし、照合できない作者は「未検証」として区別する。
- ローカルの利用者が自分の `attributionDomains` を設定して Actor に載せることは、この ADR の範囲外とし、後続の Issue にする。
- この検証（WebFinger）は連合の照会でカードの取得ではないので、`no_fetch` のドメイン（§14）にも行う。投稿の作者の解決と同じ扱いにする。

### 6. データモデル（ADR-0020）

`content` モジュールが所有する。

| テーブル | 分類 | 主な列 | 備考 |
| --- | --- | --- | --- |
| `link_cards` | 現在値（キャッシュ） | `url`（PK。正規化した要求の URL）, `card_url`（最終 URL、または同じオリジンの `og:url`）, `title`, `description`, `site_name`, `author_name`, `published_at`（NULL 可）, `image_media_id`（NULL 可）, `creator_account_id`（NULL 可。§5 で検証できたもの）, `language`（NULL 可。`<html lang>`）, `fetched_at` | `remote_media_cache` と同じく、取得の結果を再取得で UPSERT する。インデックス `(fetched_at)` |
| `link_card_media` | リソース（部分型） | `media_id`（PK、`media_files` の部分型）, `remote_url`（一意）, `content_type`, `width`, `height`, `blurhash`, `description`（`og:image:alt`） | §3。リモートの添付の `remote_media` と違い、所有者のアカウントを持たない |
| `status_link_cards` | 投影 | `status_id`（PK）, `url` | 投稿の現在の版から選んだ URL。インデックス `(url)`。`link_cards` の行がない間はカードを出さない。再構築は投稿の版から選び直す |

- URL の正規化: スキームとホストを小文字にし、既定のポートとフラグメントを除く。クエリは並べ替えない（意味が変わり得るため）。
- **再取得**: 新しい投稿が URL を参照したとき、`fetched_at` から 14 日を過ぎていれば取り直す（Mastodon の 2 週間に合わせる）。定期的な一斉の取り直しはしない。
- **保持と消去**: 1 日 1 回のジョブ `content.purge_link_cards` が、`status_link_cards` から参照されなくなって `fetched_at` から 14 日を過ぎた `link_cards` と、どこからも参照されない `link_card_media` を消す（FR-803）。
  投稿の削除・消去（ADR-0006 の保持期間切れ、処分による削除）は、同じトランザクションで `status_link_cards` の行を消す。
- インスタンス設定 `link_cards`（`bool`、既定 `true`）を `instance_setting_revisions` の `key` に持つ。偽ならジョブを積まず、API は `card` を返さない。

### 7. ドメイン単位の処分との関係

- カードの URL のホスト（またはその親ドメイン）に、ドメイン単位の `suspend` の制限（`federation`）があれば、取得しない・既存のカードも出さない。運用者が連絡を断ったドメインに、カードのためだけに接続しないため。
- 同じく `reject_media` の制限（`media_fetch`）があれば、画像なしのカードにする。`media_fetch` はメディアプロキシでも画像の URL のホストに当たる（federation.md §9）。
- 投稿の作者に `media_sensitive`（`force_sensitive`、メディアの強制センシティブ）があるか、投稿がセンシティブなら、カードの画像はセンシティブとして表示する（ぼかす）。
- CW（`spoiler_text`）がある投稿のカードは、本文と同じく CW を開くまで出さない（Web クライアントの表示の規則）。
- カードは連合しない（自サーバーの投稿を配送するときにカードの情報を載せない）ので、ADR-0058 の処分の伝播には関係しない。

### 8. クライアント API

`Status` に省略可能な `card`（`LinkCard`）を持つ。カードがない投稿では省略する。ブーストの行では `boost` の側に付く。名前は自前の API の流儀（[ADR-0016](0016-client-api-style.md)）に従い、Mastodon の `PreviewCard` とは合わせない（[ADR-0016](0016-client-api-style.md)）。

| 項目 | 内容 |
| --- | --- |
| `url` | カードの URL（`card_url`） |
| `title` / `description` / `site_name` | §2 のプレーンテキスト（`description` と `site_name` は空文字があり得る） |
| `author_name` | 省略可 |
| `published_at` | 省略可 |
| `language` | 省略可（表示の `lang` に使う） |
| `image` | 省略可。`url`（メディアプロキシの `small` の URL）、`width`、`height`、`blurhash`、`description` |
| `author` | 省略可。§5 で検証できた作者の `Account` |

Web クライアントは、カード全体を `url` へのリンク（`rel="noopener noreferrer nofollow"`、`target="_blank"`）にし、題名・説明・サイト名は `dir="auto"` と `lang` を付けて出す（ADR-0009）。
カードの部品は独立して失敗し得る区画として `react-error-boundary` で囲む（[web-client](../architecture/web-client/README.md) の E1）。

### 9. `robots.txt` のトークンと User-Agent

- トークンは `my-linkcard` とする。RFC 9309 §2.2.1 の文字種に収まり、大文字と小文字を区別せずに照合する。一致するグループがなければ `*` のグループに従う。
- トークンを User-Agent に含める（RFC 9309 §2.2.1）。ページ・画像・`robots.txt` の取得は `my-linkcard/<version> (+https://<host>/)` にする。ほかの用途の取得は `my/<version> (+https://<host>/)` のまま。
- `my` をトークンにしない。サーバー全体の名前で、語としても一般的なので、カード以外の取得まで断ったように読めるため。

### 10. `robots.txt` の取得と保持

- `kernel.HTTPClient` の用途 `HTTPPurposeRobots` で `GET {scheme}://{authority}/robots.txt` を送る。上限は本文 512 KiB（RFC 9309 §2.5 の下限の 500 KiB を満たす）、全体 10 秒。ADR-0019 §1 の宛先の拒否をそのまま使う。超えた分は読まず、読めた分だけを解釈する。
- 結果はオリジン（スキーム・ホスト・ポート）ごとに KeyValueStore に保持する。保持するのは `my-linkcard` に当たる規則だけで、本文は持たない。期間は下の表のとおりで、24 時間を超えない（RFC 9309 §2.4）。

| 応答 | 扱い | 保持 |
| --- | --- | --- |
| 200 | 解釈して従う | 24 時間 |
| 429 以外の 4xx | ファイルなし。取得してよい（RFC 9309 §2.3.1.3） | 24 時間 |
| 429、5xx、ネットワークの失敗、ADR-0019 が拒否したリダイレクト | 全面禁止とみなす（RFC 9309 §2.3.1.4） | 1 時間 |
| リダイレクトが 5 回を超える | ファイルなし。取得してよい（RFC 9309 §2.3.1.2） | 24 時間 |

429 は RFC では 4xx だが、「今は取らないでほしい」という応答を「ファイルなし」として進まないよう、全面禁止に入れる。

### 11. `robots.txt` の解釈

- `allow`・`disallow`・`user-agent` だけを読み、`*` と `$`、最長一致、同じ長さなら `allow` を優先、複数の一致するグループの統合を RFC 9309 のとおりに行う。`/robots.txt` 自体は常に取得してよい。
- `Crawl-delay` は RFC にないので読まない。取得の間隔は #1948 で決める。
- パーサーは依存を足さず、`internal/domain/content` の純粋な関数として書き、RFC の例をテストにする。依存を足す案は、規則が小さいことと、ライブラリのライセンスと保守の確認が要ることから採らない（既存のライブラリの状況は要検証）。

### 12. `robots.txt` の適用

- ページを取得する前に、ページの URL を確かめる。公開範囲によらず同じ。
- リダイレクトの各段も、要求の前にその段のオリジンの規則で確かめる（`HTTPRequest.CheckRedirect`）。禁止された段には要求を送らない。途中の段が禁止なら、ページはカードを作らず、画像は画像なしのカードにする。
- 画像は `HTTPPurposeImage` の取得の前に、画像の URL のオリジンの規則で確かめる。禁止なら画像なしのカードにする（§7 の `media_fetch` と同じ見え方）。
- 禁止された URL は、取得の失敗と同じく 24 時間覚える（`LinkCardFailureTTL`）。
- 全面禁止とみなしただけのとき（§10 の表の 3 行目）は、一時的な失敗かもしれないので覚えない。ページのジョブは 1 時間後に再試行する。回数はジョブの既定の上限に従う。ADR-0019 が宛先を拒否したときは、待っても変わらないので再試行せず、ページの失敗と同じく 24 時間覚える。
- 画像のオリジンの `robots.txt` を読めないだけのときは、その URL の記録済みの画像を使う。記録がなければ取得せず、次の再取得まで画像なしのカードにする。
- 再取得（§6 の 14 日）で `robots.txt` の禁止が分かったら、そのカードを消す。全面禁止とみなしただけのとき（§10 の表の 3 行目）は、一時的な失敗かもしれないので消さない。
- すでにあるカードを確かめるための一斉の取得はしない。規則を変えたサイトのカードは、次の再取得で消える。
- 運営者が迂回できるインスタンス設定 `link_cards_ignore_robots_txt`（`bool`、既定 `false`）を置く。
  - 真のときは `robots.txt` を取得せず、ページと画像の取得で確かめない。保持している規則も使わない。
  - インスタンス全体の設定で、ドメインごとには持たない。User-Agent は変えず、`my-linkcard` のまま名乗る。
  - §13 のページのロボットの指定と、ドメイン単位の処分（§7）は、この設定によらず効く。
  - 設定を偽に戻すと、次の取得から従う。真の間に作ったカードは、次の再取得で確かめる。

### 13. ページのロボットの指定

- 読むのは、`<head>` の `<meta name="robots">` と `<meta name="my-linkcard">`、応答ヘッダの `X-Robots-Tag` のうちボットの名前がないものと `my-linkcard:` が付いたもの。ほかのボットを名指しした指定は当てはまらない。
- 複数の指定があれば、より厳しいものが勝つ。

| 指定 | カード |
| --- | --- |
| `nosnippet`、`max-snippet:0` | 説明を出さない（`description` の値をどの出どころからも取らない） |
| `noimageindex`、`max-image-preview:none` | 画像を取得せず、画像なしのカードにする |
| `noindex`、`nofollow`、`noarchive`、`none` など | 何も変えない |

- `none` は `noindex, nofollow` と同じ意味（[Robots Meta Tags Specifications](https://developers.google.com/search/docs/crawling-indexing/robots-meta-tag)）なので、何も変えない。
- 題名・サイト名・作者は、どの指定でも残す。これらを出さないでほしいサイトは `robots.txt` で断る。
- 再取得のときは新しい指定に従ってカードを作り直す。

### 14. ドメインごとのルールの 2 つのモード

カードの取得だけに効くルールを、処分とは別に持つ。ルールはドメインごとに 1 つで、モードは次のどちらか。

| モード | 取得 | 取得済みのカード |
| --- | --- | --- |
| `no_fetch`（取得を止める） | そのドメインからページも画像も取得しない | 隠す |
| `no_images`（画像だけ止める） | ページは取得し、画像は取得しない | 画像なしで出す |

- ページの判定は、カードの URL と `card_url`（取得後のページの URL）のホストに当てる。
- 画像の判定は、カードの URL・リダイレクト後の URL・`card_url`・画像の URL のホストのすべてに当てる。`no_fetch` は画像の取得も止めるので、画像の判定では両方のモードが当たる。
- リダイレクトの各段にも当てる（`HTTPRequest.CheckRedirect`）。止めたドメインへのリダイレクトで、ページの取得はそこで終わり、画像はカードに付かない。
- 書き込みと読み出しの両方で判定する。読み出しで判定するので、ルールの追加・変更・削除は取得済みのカードにすぐ効き、カードと画像の行は消さない。`no_images` の間に取り直したカードは画像なしで保存され、ルールを消しても次の取り直し（§6 の期限）まで画像なしのままになる。
- メディアプロキシは、ルールで止めたホストの **カードの画像** を配らず、取得もしない（404）。カード以外のリモートメディアには当てない。

### 15. ルールの適用範囲

- ホストと親ドメインに当てる。処分と同じ `DomainAndParents` を使う。
- ホストに当たるルールはすべて効く。親に `no_fetch`、子に `no_images` があれば `no_fetch` が効く。処分と同じく、子のルールは親のルールを緩めない。
- ドメインの正規化と検証は処分と同じ（`CanonicalHost`、`ValidDomain`）。U-label と A-label は同じドメインになる。

### 16. 処分との分離

- ルールは `suspend` / `reject_media` と独立して効き、どちらかが当たれば止まる。処分の表（`domain_actions`、`domain_restrictions`）には書かない。公開のドメイン一覧（FR-706）、CSV の書き出し、連合、配送、カード以外のメディアは、ルールを読まない。
- カードは連合しないので（§7）、ルールは他のサーバーに伝わらない。

### 17. 失敗の記憶とルールの削除

ルールで飛ばした取得は、失敗の記憶（`content.link_card_failure`）に書かない。ルールを消せば、次に投稿がその URL を必要としたときにすぐカードを作る。ルールを消しても一括で取得し直さない。取得済みの投稿のうち、飛ばされた投稿のカードは、同じ URL を次に投稿が必要としたときに作られたカードを共有して現れる。

### 18. ルールのデータモデル（ADR-0020）

`instance` モジュールの【現在値】`link_card_domain_rules`（`domain` PK, `mode`, `note`, `updated_at`）。

- 所有は `instance`。`link_cards` と同じくサーバーの設定で、`content` は監査の `moderation` に依存できない（`moderation` が `content` に依存している）。`content` は `LinkCardDomains` ポートで読み、プラットフォームがつなぐ。
- イベントと投影にしない。ルールそのものの履歴に意味はなく、誰がいつ何に変えたかは同じトランザクションで書く監査ログ（ADR-0058）に残るので、ADR-0020 の規約 5 の現在値に当たる。投影と違い再構築の対象でない。
- メモ（`note`）は処分の非公開のメモと同じ 5,000 文字まで。ルールの数の上限は 1,000 で、一覧はページングしない。

### 19. ルールの API と権限

- `GET /admin/link_card_domains`、`PUT /admin/link_card_domains/{domain}`（ドメインのルールを設定。あれば置き換える）、`DELETE /admin/link_card_domains/{domain}`。ルールのないドメインの削除は何もしない。
- 権限は `manage_settings`（`link_cards` と同じ、ADR-0058 のサーバー管理）。`manage_domains`（処分）にしない。モデレーションの権限ではなく、サーバーの外への取得の設定なので。
- 監査の種類は対象 `link_card_domain` に `link_card_domain_fetch_stopped`、`link_card_domain_images_stopped`、`link_card_domain_rule_removed`。

### 20. この決定を見直す条件

- 非公開の投稿の URL の取得で、ワンタイムの URL の消費などの実害が報告された場合（`private` / `direct` で取得を起こさない形に寄せる）
- 連合の集中で、相手のサイトへの取得が問題になる規模になった場合（遅延の幅を広げる、または表示時の取得に寄せる）
- 埋め込み（動画の再生など）を求める声が大きい場合（クリックで読み込む・許可したプロバイダだけの埋め込みを、別の ADR で CSP とともに決める）
- カードの出ないサイトが多く、Slack の報告のように利用者の不満が実害になり、多くの運営者が迂回の設定を使うようになった場合（既定を見直す、リモートの投稿の取得だけ従う形に寄せる、または「ファイルなし」の扱いなどを緩める）
- 主要なサーバーの実装と大きく食い違い、相手のサイトの多くが `my-linkcard` を名指しして許可する手間を強いられる場合
- `robots.txt` の取得そのものの量が問題になる場合
- サイト運用者からの要望で、`robots.txt` やホストごとの取得の上限だけでは足りないとき、ルールの自動の追加を考える

## 経緯

URL を貼った投稿にカードを出す仕組みが要るという決定者の指示から始まった（FR-117）。Mastodon・Misskey・Pleroma / Akkoma の利用者はカードを前提に URL を貼る。判断の軸は、SSRF と HTML / 画像となりすましの安全（ADR-0019）、閲覧者の IP を第三者に出さないプライバシー、外部 HTTP の量を閲覧でなく投稿と URL に比例させること（NFR-COST）、追加のミドルウェアを必須にしないこと（NFR-COST-2）だった。2026-10-20 の一次資料では、Mastodon は投稿の保存後に `LinkCrawlWorker` で取り、Misskey は表示時に Summaly で取り、GoToSocial は `card` を常に `null` で返す。

取得の精査（#1947）で、相手のサイトが標準の手段で断れないことが問題になり、決定者は `robots.txt` に従う方針を示し、ページの `<meta name="robots">`（#1949）も同じ判断で扱うとした。RFC 9309 に利用者の要求で動く取得を除外する規定はない。Google・Mastodon・Slack（`Slackbot-LinkExpanding`）は従わず、Slack は従う実装を試したがインターネットの多くがクローラーに閉じていて苦情が多くやめたと説明する。Meta の `FacebookExternalHit` は `robots.txt` の内容を最大 24 時間保持する。X の `Twitterbot` は Google の仕様を実装すると説明する（本文は取得できず検索結果の抜粋で確認。要検証）。いずれも 2026-11-02 の確認である。リモートの投稿を受けた各サーバーが誰にも頼まれず取りに行くのは利用者の要求と言いにくく（[mastodon/mastodon#21738](https://github.com/mastodon/mastodon/issues/21738)）、カードが減ることは受け入れた。Slack の報告が示す問題への逃げ道として、決定者の指定で既定をオフにした迂回の設定を置いた。ページの指定はリンクのプレビューの扱いを定める仕様がなく、このサーバー自身も `unlisted` の投稿に `noindex` を付けてプレビューは出す（ADR-0057）ので、`noindex` はカードの拒否と扱わない。

運用者がカードの取得を止める手段は `link_cards`（全体）と処分しかなく、処分は連合と投稿のメディアも止め、処分の一覧と公開の一覧（FR-706）にも載る。決定者の指示で、連合に影響せずカードの取得だけを止めるルールを足した（#1951）。

## 採らなかった案

取得の方式:

- 表示時にサーバーが取得する（Misskey 型）: 実際に閲覧された投稿の URL だけを取るので連合の集中が小さく保存も要らないが、キャッシュが外れるたびに外部 HTTP が閲覧に比例し、タイムラインの表示がカードの取得を待つ。
- カードを出さない（GoToSocial）: 実装がないが、FR-117 を満たさない。
- 送信側のサーバーが作ったカードを信じる: 外部 HTTP がないが、送信側が任意の題名と画像を任意の URL に付けられ、フィッシングに使える。
- クライアントが直接取得する: CORS で読めないうえ、閲覧者の IP を相手に出す。

`robots.txt`:

- 従わない（Google の利用者起点の取得・Mastodon と同じ）: カードがいちばん多く出るが、相手のサイトが標準の手段で断れず、決定者の方針に反する。
- リモートの投稿の取得だけ従う: 利用者が貼ったローカルの投稿は「利用者の要求」と言えるが、カードは URL ごとに共有する（§6）ので、同じ URL のカードが先に貼った投稿の種類で変わる。

ページのロボットの指定:

- `noindex` もカードの拒否として扱う: 「載せないで」という意思に広く応えるが、`noindex` を付けて共有は歓迎しているページのカードが消える。拒否には `robots.txt` がある。
- 読まない: 実装がなくカードが減らないが、`nosnippet` のように本文を出さないでほしいという明示の指定を無視する。

ドメインごとの設定:

- ドメインへの処分に種類（`no_link_cards` など）を足す: 表と画面が増えず期限やメモの仕組みを使えるが、処分は連合の判定・公開の一覧・CSV・モデレーションの権限に乗り、カードだけの設定をそれぞれから外す分岐が増える。
- インスタンス設定に一覧を持つ: 表が要らないが、問い合わせる値を文字列に詰めることになり（ADR-0020）、親ドメインの引き当てを読み出しのたびに解き、1 ドメインの変更が設定全体の版になる。

## Consequences（影響）

- URL を貼った投稿が、Mastodon などと同じくカード付きで見え、FR-117 を満たす。取得は投稿と URL の数に比例し、閲覧回数に比例しない。閲覧者の IP は第三者に出ない。外部 HTTP は既存の `kernel.HTTPClient` とメディアプロキシの上に乗り、新しいミドルウェアは要らない。
- 相手のサイトは `User-agent: my-linkcard` か `*` で、標準の手段でカードの取得を断れる。説明や画像だけを出さないようにもできる。
- 運用者は、連合を止めずにカードの取得だけを止められ、取得を断ってきたサイトに、すぐ、確実に応えられる。カードが減って困る運営者は、設定で迂回できる。
- **悪い点**:
  - 投稿の直後はカードがなく、ジョブの完了後に現れる（リモートの投稿は最大 60 秒の遅延が加わる）。SSE（FR-207）で投稿の更新を流さない限り、再読み込みまで出ない。
  - `private` / `direct` の投稿に貼った URL も取得するので、相手のサイトはその URL がいつ投稿されたかを知り、GET で動く URL（ワンタイムのリンクなど）は消費され得る。取得は相手のサイトに投稿の時刻を（遅延の幅の精度で）知らせる。公開の投稿についてはこれを受け入れる。
  - JSON-LD を読むので、HTML の解析の対象が `<script type="application/ld+json">` の JSON にも広がる（上限で抑える）。
  - JavaScript で meta を作るページ、`<head>` が 1 MiB を超えるページ、bot を拒否するページはカードにならない。埋め込みがないので、動画のリンクはその場で再生できない。`http` の URL にはカードが出ない（Mastodon は `http` も取る）。
  - `*` を全面禁止にして特定のボットだけを許すサイトでは、Mastodon や Slack では出るカードがここでは出ない。Slack は同じ理由で従うのをやめており、起き得る実害として見込む。
  - `none` や `noindex` だけを付けたページのカードは出続ける。意図とずれるサイトがあり得るが、`robots.txt` で断れる。ページの指定は取得した後で分かるので、ページ自体への要求は止まらない。
  - オリジンごとに 1 日 1 回程度の要求が増える。カードのジョブは遅れるが、投稿の表示は待たない。`robots.txt` が 5xx を返す間、そのサイトの新しいカードは出ない。
  - User-Agent が用途で分かれるので、`my/` で一括して識別していたサイトには別の名前に見える。
  - 迂回の設定を真にしたサーバーには、相手のサイトは `robots.txt` で断れない。サイト運営者向けと運営者向けの文書にそれを書く。
  - カードの表示ごとに、ホストごとの処分の読み出しに加えてルールの読み出しが増える。主キーの引き当てで、表示の流れの N+1 は処分と同じ形のまま残る。
  - 似た目的の場所が 2 つある（処分とルール）。画面の説明で違いを書く。
- 後続: カードの付いた投稿の更新を SSE で流す（FR-207 の実装に合わせる）。ローカルの利用者の `attributionDomains` の設定と Actor への出力。

## Open Questions / 要検証

- 要検証: 主要な実装が、カードを ActivityPub の文書に載せて連合する仕様（FEP など）を持たないこと。
- 要検証: Pleroma / Akkoma の `:rich_media` が取得する契機（投稿の受信時か、表示時か）。
- 要検証: 題名・説明の上限（200 / 500 文字）が、実際のサイトのカードを切りすぎないこと。
- 要検証: `*` を全面禁止にしたサイトのカードが出ない実害がどの程度起きるか。
