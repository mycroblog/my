# ADR-0100: 通話のルーム（公開範囲・発話範囲・ホスト・招待・モデレーション）

- Status: Accepted
- Date: 2026-10-26
- Deciders: @rosylilly
- Issue: #1348

## Context（背景・課題）

M4.3（Voice Chat、epic #1345）は、同じサーバーのローカルの利用者どうしの音声通話を入れる（FR-920〜FR-932）。通話の 1 単位を**ルーム**と呼ぶ。決定者は M4.3 を v0.1.0 の前提にした（#1345 の回答 1）ので、
v0.1.0 の前に DB を作り直せる期間（[ADR-0087](0087-schema-changes-after-launch.md)）のうちにスキーマを決める。

この ADR はルームの振る舞い（誰が開き、誰に見え、誰が話せ、ホストがどう交代し、どこで知らせ、どう通報・記録するか）とデータモデルを決める。
音声をどう運ぶか（P2P のシグナリング・STUN / TURN・ルームのストリーム）は ADR-B（#1349）、SFU（LiveKit・Sora）の adapter は ADR-C（#1350）が決める。この ADR は接続の方式に依存しない。

決定者の指示（#1345、原文の抜粋）:

> 同 Local なユーザー同士で通話(VoiceChat)を開けるようにする機能。通話の1単位をルームとする。
>
> - ルームはインスタンスの設定によりログイン済みの誰でも or 権限を持つユーザーのみが開始できる
>   - 権限を持つ……の場合、これはサポータープランによって提供される
> - 通話の開始者(ホスト)はルームごとに以下範囲を設定できる
>   - 公開範囲 : ローカル(全体)、フォロワーのみ、相互フォロー関係のみ、非公開(招待制)
>   - 発話範囲 : 参加した誰でも(全体)、フォロワーのみ、相互フォロー関係のみ、手動
>   - ルーム名 / ルーム説明文 / ルームハッシュタグ
>   - これらは通話開始後にも変更できる
> - 招待されたユーザーは応答に関わらずその時点からそのルームが見える
> - 参加者が残っていてホストが抜ける時、ホストは次のホストを選ぶかルームの解散をさせるかを選択する
> - 参加者が残っていなければ自動的にルームは解散になる

決定者の回答（#1345 の 1〜39、原文）のうち、この ADR の決定に入るもの: 9〜13、15〜28、30〜39。回答で決まったことは開き直さず、この ADR はそれを実装できる形にする。

## Decision Drivers（判断基準）

1. **決定者の回答をそのまま満たす**（#1345）。回答の振る舞いを変える設計を採らない
2. **公開範囲の判定を 1 か所にする**（NFR-SEC-4、[ADR-0017](0017-visibility-local.md) の `canView` と同じ方針）。一覧・右帯・ハッシュタグ・プロフィール・通知・参加・API が同じ関数を通る
3. **ほぼ $0 の構成で動く**（Cloud Run・Lambda の scale to zero、SQLite の 1 プロセス）。常駐のプロセスやタイマーを前提にしない
4. **データモデルの規約**（[ADR-0020](0020-data-modeling-principles.md)）: 状態を NULL の時刻で表さず、変化はイベント、今の状態は 1 つのモジュールが持つ投影
5. **個人データを必要な間だけ持つ**（[ADR-0038](0038-moderation-personal-data-retention.md)）。誰がどのルームにいたかは個人データで、通報の証拠に要る間だけ残す
6. 接続の方式（P2P・SFU）を後から足せる。ルームのドメインは音声を扱わない

## Considered Options（選択肢）

### モジュール

- **M1**: 新しいモジュール `voice` を置く
- **M2**: `content`（投稿・絵文字）の中に置く

### 状態の置き場所

- **S1**: ルーム・設定・役割・参加と退出・終了は DB のイベントと投影、接続の生存（ハートビート）は `KeyValueStore` の期限つきの値
- **S2**: すべて `KeyValueStore`（またはプロセスのメモリ）に置き、終了したら DB にルームの要約だけを書く
- **S3**: すべて DB に置き、ハートビートも参加者の行の更新にする

### 切断の検知と猶予

- **H1**: 参加者のハートビートの期限切れを、ルームへの要求のたびに遅延評価し、加えて定期ジョブで掃く
- **H2**: ルームのストリーム（SSE）の接続が切れたら、そのプロセスが直ちに退出として扱う

## Decision（決定）

**M1・S1・H1 を採用する。**

決定者の回答（#1352、原文）:

> ADR Accepted

### 1. モジュールと依存の向き（M1）

- `internal/domain/voice` と `internal/app/voice` を置き、スキーマは `schema/<dialect>/14-voice.sql`。ルーム・設定・役割・参加・招待・挙手・終了を `voice` だけが書く。
- `internal/app/voice` が import する他のモジュールの `internal/app`（ADR-0002 の唯一のモジュール間の経路）:
  - `graph`: ホストとのフォロー（承認済み）・相互フォロー・ブロックの判定
  - `identity`: 権限 `start_voice_rooms` の検査と、インスタンス設定 §2 の読み出し
  - `account`: アカウントの状態（凍結・削除）と制限（limited）
  - `content`: 開始の投稿の作成（§9）、カスタム絵文字の引き当て（§10）、ハッシュタグの正規化
  - `notification`: 通知の作成（§8）
  - `moderation`: 監査ログ（`AuditRecorded`）と通報の対象（§11）
- 逆向き（他のモジュールが `voice` を import する）は作らない。凍結・削除・ロールの変化は、各モジュールがいま出している domain event を `voice` のジョブが購読して反映する（[ADR-0072](0072-supporter-plans-and-roles.md) §10 の `moderation.account_suspension_changed` と同じ経路）。
- M2 を採らないのは、ルームが投稿でも絵文字でもなく、独自の状態の遷移とストリームを持つからである。`content` に置くと、`content` が `graph`・`notification` との新しい依存を持ち、すでに大きいモジュールがさらに大きくなる。

### 2. 有効化と開始の権限（回答 25〜27・36）

- 接続の方式の設定 `voice`（ADR-B）が `off` のとき、通話の API は `404` を返し、Web は通話の画面と入口を出さない。`voice` を `off` にしたとき開いているルームは、次の §6 の掃除で理由 `disabled` で終わる。
- インスタンス設定 `voice_room_starters`（`instance_settings`、`manage_settings`）: `everyone`（ログイン済みのローカルの誰でも）か `permitted`（権限 `start_voice_rooms` を持つ人だけ）。既定は `permitted`。
- 新しい権限 `start_voice_rooms` を足す。区分は `member`（[ADR-0070](0070-permission-split-emoji-finance.md) §1）: 自分のルームを開くことだけを許し、他人の行やサーバー全体に効く変更を許さないので、区分の条件を満たす。
  [ADR-0072](0072-supporter-plans-and-roles.md) のプランのロールの許可リスト（FR-912）に足す。組み込みのロールでは `admin` だけが持つ。
- **ホストの資格**: 次をすべて満たす人。ルームを開くとき、ホストを渡すとき、自動でホストを移すとき（§6）に検査する。
  - ローカルの有効なアカウント（凍結・削除されていない）で、制限（limited）されていない
  - `voice_room_starters` が `everyone`、または `start_voice_rooms` を持つ
- 共同ホストに資格は要らない（回答 27）。共同ホストのうち資格のある人だけが、自動でホストを継げる。
- 開催中にホストが資格を失ったら（ロールの付け外し・制限・凍結の domain event と、ホストの操作のたびの検査）、資格のある共同ホストのうち指名の早い人にホストが移り、いなければ理由 `host_ineligible` で解散する（回答 26）。

### 3. ルームの設定（回答 11・12・38）

| 項目 | 値 | 既定 |
| --- | --- | --- |
| 名前 | 必須、1〜100 文字（書記素で数える） | — |
| 説明 | 任意、500 文字まで | 空 |
| ハッシュタグ | 5 個まで。投稿のハッシュタグと同じ正規化（`content` の関数） | なし |
| 公開範囲 `visibility` | `local`（ローカル全体）/ `followers`（ホストのフォロワー）/ `mutuals`（ホストと相互フォロー）/ `invited`（招待制） | `local` |
| 発話範囲 `speakers` | `everyone`（参加した誰でも）/ `followers` / `mutuals` / `manual`（手動） | `manual` |

- ホストは開始のときに決め、開始の後も変える。共同ホストは変えられない（回答 17）。変更は改版（§12 のイベント）として残す。
- 「フォロワー」「相互フォロー」は**その時のホスト**を基準にする（回答 11）。フォローは承認済みのもの（`follow_edges`）だけを数える。
- 範囲を狭めても、ホストが交代しても、参加中の人は残る。範囲は「新しく参加できるか」「一覧に出るか」「聞き手から話者になれるか」にだけ効く。話者は話者のまま残る（回答 12）。

### 4. 公開範囲と発話の判定（判断基準 2）

`internal/domain/voice` に 2 つの純粋な関数を置き、一覧・右帯・ハッシュタグのページ・プロフィールの入口・通知の宛先・参加・API のすべてがこれを通る。
関係の事実（フォロー・ブロック・招待・再入室の禁止・アカウントの状態）は `internal/app/voice` が集めて渡す。

`CanSee(room, viewer, facts)` — 次の順に評価する:

1. ルームが終わっていれば、見えるのは要約（§9 のリンク先）だけで、この関数は偽
2. 閲覧者が未ログイン、リモート、凍結・削除なら偽（未ログインの要約は §9）
3. 閲覧者がホストか共同ホストのいずれかとブロックの関係（どちら向きも）にあれば偽（回答 23）
4. 閲覧者がこのルームから退出させられていれば（再入室の禁止）偽
5. 閲覧者がホスト・共同ホスト・参加者なら真
6. 閲覧者が招待されていれば（取り消されていなければ）真（回答 28。応答にかかわらず）
7. `visibility` が `local` なら真、`followers` なら閲覧者がホストをフォローしていれば真、`mutuals` なら相互フォローなら真、`invited` なら偽

`CanSpeakFreely(room, participant, facts)` — 聞き手が許可なしに話者になれるか:

1. ホスト・共同ホストは真
2. 制限（limited）されたアカウントは、明示の許可がなければ偽（回答 36）
3. 明示の許可（挙手の許可・ホストの許可・話者としての招待）があれば真
4. `speakers` が `everyone` なら真、`followers` ならホストをフォローしていれば真、`mutuals` なら相互フォローなら真、`manual` なら偽

明示の許可はそのルームの中で保たれ、ホストが取り消すまで続く。

### 5. 参加者の役割と操作（回答 15〜17・19・31）

- 役割: **ホスト**（1 人）、**共同ホスト**（最大 3 人。ホストが指名と解除）、**話者**、**聞き手**。共同ホストは話者でも聞き手でもよい。
- 1 人が同時に入れるルームは 1 つ（ホストを含む）。別のルームに入ると前のルームから退出する（理由 `moved`）。同じアカウントの別の端末で入ると、前の端末の接続を切る（参加は 1 つのまま）。
  ホストが別のルームに入るときは、先に §6 のホストの退出の選択を求める。
- 参加者の操作: 参加して聞く、退出、話者になる（`CanSpeakFreely` が真なら）、聞き手に戻る、挙手と取り下げ、リアクション（§10）、自分のマイクのオン・オフ。
- ホストと共同ホストの操作: 発話の許可（挙手への許可と、挙手のない人への許可）・挙手の却下・発話の取り消し（話者を聞き手に戻し、明示の許可も外す）、ミュートさせる（本人は再びオンにできる）、退出させる（同じルームに再入室できない）、招待（§7）。
  ホストと共同ホストは互いを退出させられず、共同ホストはホストを操作できない。
- ホストだけの操作: ルームの設定の変更、共同ホストの指名と解除、ホストを渡す、解散。
- マイクのオン・オフとミュートさせる操作は、その場の状態として ADR-B のストリームで配り、DB に残さない。
- 参加者の一覧（ホスト・共同ホスト・話者・聞き手）は、ルームが見える人全員に見える。参加の前の画面に「参加すると名前が一覧に出る」と示す（回答 31）。
- ルームの人数は、運営者の上限（ADR-B の P2P の上限、SFU の上限）を超えて参加させない（`409`）。

### 6. ホストの退出・切断・解散と、切断の検知（回答 18・26、H1）

- **ホストの退出**: 参加者が残るなら、ホストは「資格のある参加者から次のホストを選ぶ」か「解散する」を選ぶ（選べる人がいなければ解散だけ）。参加者が残らなければ、退出で解散する（理由 `empty`）。
- **参加者がいなくなったら**解散する（理由 `empty`）。
- **ハートビート**: 参加中のクライアントは 15 秒ごとにハートビートを送る（ADR-B のルームのストリームの経路）。`internal/app/voice` は `KeyValueStore` に参加ごとの期限つきの値（45 秒）を書く。
  SFU では、SFU からの参加・退出のイベント（ADR-C）も同じ値を更新・削除してよい。
- **切断**: 値が切れた参加者は、理由 `disconnected` で退出する。ホストの値が切れたときは、ホストのまま 2 分の猶予（`voice_room_host_graces`）に入り、猶予の間も通話は続く。
  猶予の間に戻ればホストのまま続く。猶予が切れたら、資格のある共同ホストのうち指名の早い人にホストが移り、いなければ理由 `host_disconnected` で解散する（回答 18）。
- **遅延評価と掃除**: 期限は 2 か所で評価する。どちらも同じ条件つきの書き込みで、同時に走っても 1 回だけ効く（ADR-0004 の冪等）。
  - ルームへのすべての要求（ハートビート・一覧・参加・操作）の中で、そのルームの期限切れを評価する。参加者が 1 人でも残っていれば、ハートビートが評価を進める
  - 定期ジョブ `voice.sweep`（`Scheduler`、1 分ごと）が、すべての開いたルームを評価し、§2 の `disabled` と、運営者の最長時間（ADR-B）を過ぎたルーム（理由 `time_limit`）も終える。
    誰もいなくなったルームも、このジョブが終える（scale to zero の構成でも、`Scheduler` は既存の定期ジョブと同じに起動する）
- H2 を採らないのは、Lambda の 15 分ごとの再接続と、Cloud Run のインスタンスの入れ替えで、ストリームの切断が退出を意味しないからである。プロセスをまたいで「同じ人がもう別のプロセスに再接続したか」を知るにも、共有の値が要る。

### 7. 招待（回答 28）

- ホストと共同ホストが、任意のローカルの利用者を**聞き手として**か**話者として**招待し、取り消す。話者としての招待は §4 の明示の許可になる。
- 招待された人は、応答にかかわらず招待の時点からルームが見える（§4 の 6）。招待を取り消すと見えなくなる（参加中なら残る、§3）。
- ホストか共同ホストとブロックの関係にある人、再入室を禁止した人は招待できない（`422`）。
- 招待は通知（§8）に届く。1 つのルームの招待は 1 人 1 回で、ルームごとに 1 時間あたり 100 件まで（`KeyValueStore` のレート制限）。

### 8. 知らせる場所と通知（回答 9・10・33）

- **一覧**（`/voice`）: 閲覧者に見える開いたルーム。並びは、閲覧者がフォローしている人がホストか話者のルームを先に、次に参加者の多い順。
- **右帯**: PC の幅の画面で、ホームなどの右帯に一覧の先頭の数件を出す（web-client の右帯の規則に従う）。
- **ハッシュタグのページ**: そのタグを持つ、閲覧者に見える開いたルームを上部に出す（回答 10）。
- **プロフィール**: ホストか話者として開いたルームにいる人のプロフィールに、そのルームが見える閲覧者にだけ入口を出す。聞き手であることは出さない（回答 33）。
- **通知**（`notification` の種類に 2 つ足す。種類ごとの通知の設定で切れる）:
  - `voice_room_started`: ルームを開いたとき、ホストのローカルのフォロワーのうち `CanSee` が真の人へ。ジョブで配り、冪等キーは（ルーム, 宛先）。開始の後に公開範囲を広げても送らない
  - `voice_room_invited`: 招待された人へ
  - 通知の一般の除外（ミュート・通知の除外・ブロック）はいまのとおり効く

### 9. 開始の投稿とリンク先のページ（回答 13・14・30・39）

- 開始のとき、公開範囲が `local` か `followers` なら、ホストは「投稿する」を選べる（既定は投稿する）。`mutuals` と `invited` には対応する投稿の公開範囲がないので出さない。
- 本文はホストが書く（回答 39）。画面はルーム名を入れた本文を下書きとして出し、ホストが編集する。ルームへのリンク（§9 の URL）は本文の末尾に自動で付く。
  投稿の公開範囲は `local`（ルームが `local`）か `private`（ルームが `followers`）。投稿はホストの普通の投稿として `content` の作成の操作で作り、普通の投稿と同じに連合する（回答 14）。ホストはそれを普通に消せる。ルームの設定を変えても投稿は変えない。
- ルームの作成と投稿の作成は 1 つのトランザクションで行う。投稿の検証（文字数など）に失敗したらルームも開かない。
- **ルームの URL**: `/voice/{room_id}`。HTML の外枠と OGP は Go が返す（[ADR-0028](0028-html-shell-link-previews-and-pwa.md)）。
  - ログインしたローカルの閲覧者で `CanSee` が真: ルームの画面（参加の前の画面）
  - リモートの閲覧者・ログインしていない閲覧者: 「このサーバーのローカルの利用者だけが参加できる」と、ログインの入口。ルームの中身は出さない
  - インスタンス設定 `voice_public_summary`（既定は偽、`manage_settings`）が真で、ルームの公開範囲が `local` なら、ログインしていない閲覧者とリモートの閲覧者に要約（名前・説明・ホスト・開いているか）を出し、OGP にも載せる。参加者は出さない（回答 30）
  - 終わったルーム: 終わったことと名前だけ（要約を見せる条件のときだけ名前も出す）

### 10. リアクション（回答 21）

- 参加者が、Unicode の絵文字か、ローカルの有効なカスタム絵文字（[ADR-0051](0051-custom-emoji.md)）を送る。ピッカーは [ADR-0091](0091-composer-emoji-picker.md) のもの。
- サーバーは、そのとき参加している人にストリームで配り、DB に残さない。送った人とブロックの関係にある受け手には配らない（回答 23 の「リアクションを隠す」をサーバーで行う）。
- 参加者ごとに 10 秒に 10 件まで（`KeyValueStore` のレート制限）。超えた分は `429`。
- 参加者の一覧は、閲覧者がブロックしている（またはされている）参加者がいることを、その人を隠さずに印で示す（回答 23）。

### 11. ブロック・凍結・モデレーション（回答 23・24）

- 開催中に閲覧者とホストか共同ホストの間にブロックができたら、その閲覧者は理由 `blocked` で退出する（ホストが閲覧者を、または閲覧者がホストをブロックしたとき）。
  共同ホストを指名するときにブロックの関係にある参加者がいれば、その参加者は退出する。
- 凍結・削除されたアカウントは、その場で理由 `suspended` で退出する。ホストなら §2 の資格の喪失として扱う。
- **通報**: 利用者は見えるルームを通報できる。通報（`reports`）の対象のアカウントはその時のホストで、新しい子の表 `report_voice_rooms`（通報, ルーム, 通報の時点の設定の改版）がルームとその時の名前・説明を指す。
  分類・コメント・規則の引用はいまの通報と同じ。リモートへの転送（`forwarded`）は使わない（ルームはローカルだけ）。
- **モデレーターによる終了**: `manage_reports` を持つ人が開いたルームを終える（理由 `moderator`、任意の理由の文 500 文字まで）。監査ログ（[ADR-0037](0037-audit-log.md)）に、新しい対象の種類 `voice_room` と操作 `voice_room_ended` で残す。
  モデレーターは通報の画面から、そのルームの改版と参加者の記録（§13 の期間内）を見る。
- 録音とテキストのチャットは持たない（回答 22・24）。証拠はルームの設定の改版と参加者の記録だけである。

### 12. データモデル（ADR-0020、S1）

`14-voice.sql` に置く。すべて `voice` が書く。

| 表 | 分類 | 中身 |
| --- | --- | --- |
| `voice_rooms` | リソース | id、開いた人のアカウント、開いた時刻、接続の方式（開いたときの `voice`） |
| `voice_room_revisions` | イベント | 設定の改版: ルーム、名前、説明、`visibility`、`speakers`、改版した人、時刻。開始の設定が最初の改版 |
| `voice_room_revision_hashtags` | リソース（改版の子） | 改版、正規化したタグ、表示の綴り、順序 |
| `voice_room_host_changes` | イベント | ルーム、新しいホスト、理由（`opened` / `handed_over` / `host_disconnected` / `host_ineligible` / `host_left`）、時刻 |
| `voice_room_cohost_changes` | イベント | ルーム、アカウント、`assigned` / `removed`、時刻 |
| `voice_room_participations` | リソース | id、ルーム、アカウント、参加の時刻 |
| `voice_room_participation_ends` | イベント | 参加、理由（`left` / `moved` / `disconnected` / `removed` / `blocked` / `suspended` / `room_ended`）、時刻 |
| `voice_room_role_changes` | イベント | 参加、`speaker` / `listener`、操作した人、時刻 |
| `voice_room_speak_grants` | イベント | ルーム、アカウント、`granted` / `revoked`、操作した人、時刻（話者としての招待も `granted` を書く） |
| `voice_room_hand_raises` | イベント | 参加、`raised` / `lowered` / `granted` / `dismissed`、時刻 |
| `voice_room_invitations` | リソース | id、ルーム、招待された人、`listener` / `speaker`、招待した人、時刻。（ルーム, 招待された人）で一意 |
| `voice_room_invitation_revocations` | イベント | 招待、取り消した人、時刻 |
| `voice_room_bans` | イベント | ルーム、アカウント、操作した人、時刻（退出させる操作が書く） |
| `voice_room_endings` | イベント | ルーム、理由（`host` / `empty` / `host_disconnected` / `host_ineligible` / `moderator` / `time_limit` / `disabled`）、操作した人（NULL 可: 自動の終了）、時刻。ルームごとに 1 つ（一意） |
| `voice_room_heads` | 投影 | ルーム、最新の改版、今のホスト、状態（`open` / `ended`）、参加者の数。一覧はこれを引く |
| `voice_room_participants` | 投影 | 今の参加: ルーム、アカウント、参加、役割（`speaker` / `listener`）、共同ホストか・その指名の順、挙手しているか。**アカウントで一意**（1 人 1 ルーム、§5） |
| `voice_room_host_graces` | 現在値 | ホストの猶予の間だけある行: ルーム、猶予の終わり（決定の内容としての期限） |
| `report_voice_rooms` | リソース | `moderation` の通報の子（`03-moderation.sql`）: 通報、ルーム、改版 |

- 接続の生存（ハートビート）は DB に書かない（S3 を採らない理由。15 秒ごとの書き込みが参加者の数だけ増え、Aurora・Neon で計算を起こし続ける）。`KeyValueStore` の既定の `db` adapter では DB に書かれるが、
  その adapter の期限つきの値の扱いに任せ、運営者は `valkey` に替えられる。
- S2 を採らないのは、プロセスのメモリは複数のプロセスで共有できず、KV だけでは通報の証拠と履歴が残らず、終了時に書く要約はプロセスが落ちると失われるからである。
- 一覧の公開範囲は、開いたルームを `voice_room_heads` から引き、§4 の関数でアプリが絞る。開いたルームの数は運営者の上限（ADR-B）と 1 人 1 ルームで抑えられる。

### 13. 記録の保持と履歴（回答 24・32・37）

- **参加者の記録**（`voice_room_participations`・`voice_room_participation_ends`・`voice_room_role_changes`・`voice_room_hand_raises`・`voice_room_speak_grants`・`voice_room_invitations` と取り消し・`voice_room_bans`）:
  ルームの終了から 90 日で消す。`instance_settings` の `retention_voice_participants`（下限 30 日）で変えられる（ADR-0038 の形）。通報が参照するルームの記録は、その通報の保持の期限まで残す。保全（`retention_holds`）はいまのとおり効く。
- **ルームそのもの**（`voice_rooms`・改版・タグ・ホストの交代・共同ホストの変化・終了）は残す。アカウントの消去（ADR-0020 規約 6）は、そのアカウントが書いた改版の名前・説明を消し、data-model の消去の表に足す。
- **履歴**: ホストだった人（`voice_room_host_changes` に名前がある人）だけが、設定の画面で自分がホストだったルームの一覧（名前・開いた時刻・終わった時刻・終わった理由）を見る（回答 32）。

### 14. API と mykit（回答 2）

[client-api.md](../architecture/client-api.md) の手順で細部を決める。形の目安:

- `GET /voice/rooms`（一覧。`tag` で絞る）、`POST /voice/rooms`（開く。開始の投稿の本文を含む）、`GET /voice/rooms/{id}`、`PATCH /voice/rooms/{id}`（設定）、`DELETE /voice/rooms/{id}`（解散）
- `POST /voice/rooms/{id}/participation`（参加）・`DELETE`（退出。ホストは次のホストか解散を添える）、話者・聞き手・挙手、`/participants/{account_id}` への操作（許可・取り消し・ミュート・退出させる・共同ホスト）、`/invitations`、`/reactions`、`/host`（渡す）
- `GET /accounts/{id}` に開いたルームの入口（§8）を足す。`GET /voice/history`（§13）
- 管理: `POST /admin/voice_rooms/{id}/end`（`admin-moderation` のタグ、[ADR-0058](0058-moderation-admin-separation.md) §3）。インスタンス設定は `/admin/settings` に足す
- スコープ: 読み取りは `read:voice`、操作は `write:voice`（[ADR-0090](0090-third-party-oauth-apps.md) のスコープの規則で足す）
- ルームのストリームとシグナリングは ADR-B が決める。`pkg/mykit` は上の REST だけを持ち、音声の接続は持たない（[ADR-0093](0093-api-client-library-mykit.md)）

### 15. 呼び名（回答 34）

UI の呼び名は、機能を「通話」/ "Voice chat"、単位を「ルーム」/ "room" とする（`locales/en`・`locales/ja`）。コードのモジュール名は `voice`。

この決定を覆す条件: 開いたルームの数がアプリで絞れない規模（数千）になったとき（一覧を投影の側で絞る）。ハートビートの KV の書き込みが `db` adapter で問題になったとき（`valkey` を必須にするか、SFU のイベントだけで生存を決める）。
決定者がテキストのチャットや録音を求めたとき（通報の証拠と保持期間を決め直す）。

## Consequences（影響）

- 良い影響: 公開範囲と発話の判定が 1 か所にあり、一覧・通知・プロフィールの漏れを関数のテストで押さえられる。常駐のプロセスなしで、ホストの猶予と自動の交代が動く。
- 良い影響: 誰がいたかの記録が通報の証拠として残り、期限で消える。録音を持たないので、音声の中身の個人データを持たない。
- 悪い影響: ハートビートの評価が要求ごとと 1 分ごとのジョブに分かれ、猶予の 2 分は最大で 1 分ほど延びる（参加者が残っていればハートビートが評価を進めるので、延びるのは誰もハートビートを送らないときだけ）。
- 悪い影響: 改版の名前・説明はアカウントの消去で消えるので、消去の後の通報では名前を示せない（通報の保持の期間と消去の順序で決まる）。
- 悪い影響: 開始の投稿は連合するが、リモートの人は参加できない。リンク先が「ローカルの利用者だけ」と示すことで補う。
- 後続の作業（ADR の決定の後に Issue にする）:
  - `voice` モジュールのドメインと判定の関数、スキーマ、投影
  - 権限 `start_voice_rooms` と ADR-0072 の許可リスト、インスタンス設定（`voice_room_starters`・`voice_public_summary`・`retention_voice_participants`）
  - ハートビートと `voice.sweep`、ホストの猶予と自動の交代
  - 招待・通知 2 種・開始の投稿・リンク先のページと OGP
  - 通報の対象とモデレーターによる終了、監査ログ
  - API・mykit、Web の一覧・右帯・ハッシュタグ・プロフィール・ルームの画面
  - data-model の各節（表・状態と規則・消去・要件の対応）と overview のモジュールの表の更新

## Pros and Cons of the Options（詳細比較・任意）

| | S1（DB + KV） | S2（KV だけ） | S3（DB だけ） |
| --- | --- | --- | --- |
| 通報の証拠・履歴 | 残る | 終了時の要約だけ。落ちると失う | 残る |
| scale to zero の DB | ハートビートは KV（`valkey` で DB を起こさない） | DB を使わない | 15 秒ごとの書き込みで起こし続ける |
| 複数プロセス | 共有の値で動く | KV なら動く、メモリなら動かない | 動く |
| ADR-0020 | イベントと投影 | 規約の外 | イベントと高頻度の更新が混ざる |

H1 と H2: H2 は単純で即時だが、ストリームの切断と退出を区別できず、Lambda の 15 分ごとの再接続のたびにホストの猶予が始まる。H1 は評価の経路が 2 つになるが、どの構成でも同じに動く。
