# ADR-0117: デモ環境: 筋書きのシードと、試験用のビルドだけに入る fake の決済

- Status: Accepted
- Date: 2026-10-28
- Deciders: @rosylilly
- Issue: #1712

## Context（背景・課題）

本物のサーバーを動かして画面を確かめる場面が増えたが、そのサーバーに入っているデータがほとんどない。

- Web の E2E の 73 の spec のうち 65 は、API を `page.route` で返す。本物のサーバーを動かす経路（`app/web/e2e/server.ts`）が入れるのは、管理者 1 人（alice）・利用規約とプライバシーポリシー・サードパーティの OAuth クライアント 1 つだけである。
- nightly の L4 の課題テスト（ADR-0110 §7、ADR-0114、`app/web/l4/`）は、このフィクスチャで `my serve` を起動する。
  タイムライン・通知・通報は空で、サポーターのプランもないので、多くの画面の L1 の作業が測れない。サポーターの作業は「unavailable」で飛ばしている。
- 決済は Stripe か PAY.JP の鍵がなければ動かない（ADR-0074、ADR-0099）。`internal/adapter/payment/fake` は Go のテストだけで使い、サーバーの binary に入らない（ADR-0074 §8）。
  `internal/platform` も、それをテストだけの差し替え（`Options.PaymentProvider`）として受ける。
- ビルドタグは、今は adapter を**外す**もの（`no_*`、[build-tags.md](../reference/build-tags.md)）だけである。
- 画面のストーリー（ADR-0112）は MSW で API を差し替え、フィクスチャを機能ごとに手で書いている。

画面の作り直し（#1653 以降）では L4 が本番の物差しになり（ADR-0114）、v0 の公開の前には決定者が画面を手で通して確かめる。
どちらも「人が使っている途中のサーバー」を要るので、今それを作る方針を決める。

## Decision Drivers（判断基準）

1. **支払い済みと記録できる fake が、本番の binary に決して入らないこと。** 入れば、誰でもお金を払わずにサポーターのロールを得られる。
2. データが領域の規則を通っていること。画面が見るのは、本物の利用者が作るのと同じ状態でなければならない（ADR-0020 のイベントと投影、可視性、通知の経路）。
3. 外部のサービスと秘密を要さないこと。nightly・手元・fork の誰でも、ネットワークの外へ出ずに同じ環境を作れる（手元のコンテナで動くものは外部に数えない）。
4. 決定的で冪等であること。一つの筋書きを、L4・決定者の手での確認・画面のストーリーで使い回せる。
5. 本物の `my serve` を測ること（ADR-0114 の対象は main の実際の画面）。

## Considered Options（選択肢）

データの入れ方:

- **S1. `my` のコマンドと client / admin の API で入れる**シード（TypeScript、`@mycroblog/mykit`）。
- **S2. SQL か DB のダンプ**をフィクスチャとして置き、起動の前に流し込む。
- **S3. 試験用のビルドだけの `my demo seed`**: Go の中から `internal/app` のサービスを直に呼んで入れる。

決済:

- **P1. 試験用のビルドタグ `e2e_fakes` が fake の決済を binary に足す**（既定では入らない）。
- **P2. fake を常に binary に入れ**、`profile = development` のときだけ選べるようにする。
- **P3. デモ用の別の binary**（`cmd/` の別の main）が、`internal/platform` のテストだけの差し替えで fake を渡す。
- **P4. Stripe のテストモードか stripe-mock** を使う。

メール:

- **M1. `mail = none`**: 送るはずのメールとそのリンクをサーバーのログに書く。
- **M2. `mail = smtp` で Mailpit に送る**: 開発用にすでに使っている Mailpit（`scripts/task.sh docker:mailpit`、`deploy/docker/mailpit/compose.yaml`、`pkg/testkit/mailpittest`）が受け、Web の画面と REST API で見せる。

## Decision（決定）

**S1・P1・M2 を採る。** 決定者が方針を承認した（「その方針で Issue と ADR 起こしましょう」）。メールは、決定者の問い（「Mailpit 建てるんじゃダメなんですか？」）を受けて M2 にした。

### 1. 筋書きのシード

- 筋書き（scenario）をリポジトリに置く。`app/web/demo/` に、データだけの `scenario.ts`、それを適用する `seed.ts`、画像の `assets/` を置く。
- シードは `bin/my` のコマンドと、`@mycroblog/mykit` の client / admin の API だけでデータを作る。**SQL は書かない。** 筋書きの項目を作るコマンドか API がなければ、その項目のためにコマンドか API を足す（足せなければ項目を落とす）。
  通知・タイムライン・投影は、フォロー・返信・リアクション・メンションなどの操作の結果として生まれ、直に入れない。
- 筋書きの中身:
  - 人物: 管理者・モデレーター・一般の利用者を数人。言語は日本語と英語を混ぜ、右から左の文字の投稿を 1 つ含める（`dir="auto"` を確かめるため。ADR-0009）。
  - 投稿: 画像の付いた投稿、返信の連なり（スレッド）、公開範囲の異なる投稿、リアクション、ブースト。
  - 関係: フォロー（承認の要る鍵のアカウントへのフォローの申請を含む）、それによる通知。
  - モデレーション: 未処理の通報 1 つ、ルール。
  - ロールとバッジ: 管理者が作ったロール、それを表に出すバッジ。
  - サポーター: 有効にしたサポーターの制度、プラン（月と年の価格）、§2 の fake で申し込んだサポーター 1 人、費用の項目（管理の API で手で入れる）。
  - 招待（ADR-0108）、お知らせ。
- **決定的**: 同じ筋書きは同じ順で同じ中身を作る。ID と時刻はサーバーが決めるので、画面の確かめは ID と時刻に依存しない。
- **冪等**: 作る要求はそれぞれ、筋書きの項目の名前から作った `Idempotency-Key`（`demo:<項目>`）を付け、人物は利用者名で引く。同じ DB に 2 回流しても増えない。
- 画像は、このリポジトリのために作ったもの（またはシードがコードで描くもの）だけを使い、ライセンスはリポジトリと同じにする。第三者の写真を置かない。
- 投稿の中の URL は `.test` か `.invalid` のホストだけにし、リンクのプレビューも外へ出ない（§3）。
- 人物のパスワードは筋書きに固定で書く。§2 の実行時の確かめにより、この筋書きを入れられるのは `profile = development` のサーバーだけである。

### 2. 試験用のビルドタグ `e2e_fakes` と fake の決済

- **タグの意味**: `no_*` が adapter を外すのに対し、`e2e_fakes` は試験のための fake を**足す**。既定のビルド（タグなし）にも、`no_*` だけのビルドにも fake は入らない。
  今足すのは決済の fake だけで、後で fake を足すときも同じタグと §2 の確かめに入れる。
- **組み立て**: `internal/platform/adapters_payments_fake.go`（`//go:build e2e_fakes`）だけが `internal/adapter/payment/fake` を import し、`payments_provider = fake` の adapter に登録する。
  設定の側（`internal/platform/config`）も、`fake` をこのタグのビルドでだけ選択肢に加える。タグのないビルドで `payments_provider = fake` を設定すると、ほかの外したタグと同じく起動の前の検査で拒む。
- **申し込みの画面**: fake は ADR-0099 §1 の `PageServer` を実装し、PAY.JP と同じく自分のオリジンの `/payments/pages/fake/` に短命のページを出す。
  ページはプランと金額、「試験用のビルドの決済で、お金は動かない」の表示、「支払う」「失敗させる」「取り消す」の操作を持つ。「支払う」は fake の側に加入と確定した支払い（`Final`）を記録して `SuccessURL` へ送る。
  `Mode()` は `test` を返すので、画面は ADR-0074 §5 のテストのモードの表示を出す。事業者の側の状態はプロセスのメモリにだけある（§4 の、起動のたびに作り直す環境の前提）。
- **本番に入れない確かめ**（判断基準 1）。どれか一つが破れても残りが止める:
  1. **実行時**: `payments_provider = fake` は `profile = development` でなければ起動を拒む。起動のときに、試験用のビルドであることを警告のログに出す。
  2. **静的な検査**: `scripts/go-build-tags.sh`（`scripts/task.sh go:build-tags`、`go:check` の一部）は、タグのない `cmd/my` と代表の組み合わせのどれもが `internal/adapter/payment/fake` に依存しないことを確かめる。
  3. **コンテナのイメージ**: `Dockerfile` は `GO_TAGS` に `e2e_fakes` があればビルドを失敗させる。イメージは試験用のビルドを作らない。
  4. **リリース**: 公開する binary とイメージを作るジョブは、成果物の Go のビルド情報（`go version -m` の `build -tags=`。Go 1.27.3 で確かめた）に `e2e_fakes` がないことを確かめるスクリプトを通す。
     `release.yml` にイメージの公開を足すとき（#30）も、そのスクリプトを通す。
- ADR-0074 §8 の「fake は本番の binary に入らない」は保たれる。変わるのは、試験用のビルドに限って fake を組み立てられることだけである。

### 3. 外部のサービスを使わない

デモ環境の設定は次に固定し、秘密を要さない（鍵 `kek` はその場で作る）。

| 項目 | 値 |
| --- | --- |
| `profile` | `development` |
| `db`・`blob` | `sqlite`（起動のたびに新しいファイル）・`fs` |
| `mail` | `smtp` で Mailpit へ（`smtp_host = localhost`、`smtp_port = 1025`、下の「メール」） |
| `federation_mode`（インスタンスの設定） | `off`（ADR-0076。外へ配送も取得もしない） |
| `voice` | `p2p`（STUN・TURN なし。同じマシンのブラウザどうしで繋がる） |
| `payments_provider` | `fake`（§2） |
| Web Push・CAPTCHA・外部 IdP・エラーと計測の送り先 | 設定しない（無効） |

**メール（M2）**:

- Mailpit は、開発の構成と同じ固定のイメージ（`deploy/docker/mailpit/compose.yaml` のタグとダイジェスト）で、同じ設定（`scripts/mailpit-cert.sh` の開発用の CA の証明書で STARTTLS を必須にする）で動かす。
  `mail = smtp` は STARTTLS と証明書の検証を省かないので、`my serve` は `SSL_CERT_FILE` でその CA を信頼する。`SSL_CERT_FILE` はシステムのルート証明書を置き換え、サーバーは外の HTTPS に繋がらなくなるが、デモ環境は外へ出ないので（`federation_mode = off`）かえって都合がよい。
- これで、メールのリンクを開く作業（パスワードの再設定、メールアドレスの確認、メールで送る招待）を、手元でも L4 でも利用者と同じ道筋で通せる。
- **L4 のエージェントは、Mailpit の Web の画面（`http://127.0.0.1:8025`）を別のタブで開いてメールを読む**。利用者がメールのアプリを開いてリンクを押すのと同じ形で、こちらのメールの文面とリンクの分かりやすさも作業に含めて確かめられるからである。
  ハーネスが REST API でリンクを取って渡す形は採らない。メールに気づいて開く段とメールの文面を飛ばし、作業の一部を測らなくなるからである。
  Mailpit の画面の中の手数は Mailpit の作りに左右されるので、ハーネスは Mailpit のオリジンでの手数を別に記録し、作業の手数と lostness から除く（L1 の最短の手順では「メールを開いてリンクを押す」を 1 手と数える）。

### 4. 入口

- **手元**: `scripts/task.sh web:demo` が、`scripts/task.sh docker:mailpit` で Mailpit を起動し（すでに動いていればそのまま使う。Docker が要る）、`GO_TAGS=e2e_fakes` で `bin/my` を作り、`.tmp/demo/` に新しい DB を作ってスキーマを当て、`my serve` を起動してシードを流し、URL と人物のログインを表示する。
  起動のたびに DB を作り直す（fake の状態はメモリにだけあり、残した DB と食い違うため）。決定者の手での確認はこれを使う。
- **L4**: `app/web/e2e/server.ts` に、`voice` と同じく別の DB とポートの `demo` のサーバーを足し、L4（`app/web/l4/run.ts`）はそれを起動する。
  作業は筋書きの人物でログインして始め、シードで測れるようになった作業の `unavailable` を外す。nightly の L4 のジョブも `e2e_fakes` で `bin/my` を作り、Mailpit を同じイメージのダイジェストで動かす。
  Mailpit は証明書を作ってから起動しなければならないので、ジョブの `services:` ではなく、`scripts/mailpit-cert.sh` の後のステップで `deploy/docker/mailpit/compose.yaml` から起動する（`services:` のコンテナはチェックアウトの前に起動し、証明書を読めない）。
- **E2E**: 既存の spec は、今の最小のフィクスチャの `main` のサーバーのままにする（前提を変えない）。本物のデータが要る新しい spec は `demo` のサーバーを使える。E2E と L4 の binary は CI の中だけで使い、公開しない。
- **画面のストーリー**（ADR-0112）: MSW のフィクスチャは、人物・投稿の文・画像を `scenario.ts` から読んでよい（できるところから）。サーバーの応答を録って生成したフィクスチャはコミットしない（ADR-0081）。

## Consequences（影響）

- 良い影響: L4 が、タイムライン・通知・通報・サポーターなど、データのある画面の作業と、メールのリンクを開く作業（パスワードの再設定・メールアドレスの確認・メールの招待）を測れる。決定者は 1 つのコマンドで、使われている途中のサーバーを手元で見られる。
- 良い影響: シードが client / admin の API と `@mycroblog/mykit` を通るので、API とライブラリの実際の使い方の確かめにもなる。シードが通らなければ、API の欠けか退行である。
- 良い影響: 外部のサービスも秘密も要らないので、fork や新しい貢献者の手元でも同じ環境が立つ。
- 悪い影響: 筋書きは API の変更に合わせて保守が要る。シードを nightly の L4 が毎晩動かすので、壊れれば翌日に分かる。
- 悪い影響: ビルドの種類が増え、「試験用のビルド」と「公開するビルド」を取り違える余地が生まれる。§2 の 4 つの確かめで防ぐが、確かめのスクリプトとタグの名前は保守の対象になる。
- 悪い影響: fake の申し込みの画面は Stripe・PAY.JP の画面と違うので、事業者の画面の中の迷いやすさは L4 では測れない（測るのはこちらの画面の流れまで）。
- 悪い影響: `web:demo` と L4 のジョブは Mailpit のために Docker を要る。Mailpit のイメージの更新は、開発の構成・統合テストと同じダイジェストを揃えて行う。
- 後続の作業: ビルドタグと fake の決済の組み立て・申し込みの画面・本番に入れない確かめ（#1716）、筋書きのシードと `web:demo`（#1717。#1716 の後）、L4 をシードに切り替えて測れるようになった L1 の作業を記すこと（#1718。#1716・#1717・#1710 の後）。

## Pros and Cons of the Options（詳細比較・任意）

- **S2（SQL・ダンプ）**: 速く、ID と時刻まで固定できるので、スクリーンショットの比較やストーリーのフィクスチャにそのまま使える。
  ただし ADR-0020 のイベント・投影・現在値の整合をシードの側が手で保つことになり、スキーマが変わるたびに壊れる（v0.1.0 までは DB を作り直してよい、ADR-0087）。判断基準 2 に反する。
- **S3（`my demo seed`）**: Go の中で動くので速く、型で守られる。しかし API の検証と認可を通らず、API の欠けを見つける機会を失う。試験用のビルドのコードも増える。
- **P2（常に入れて profile で止める）**: ビルドの種類が増えず、どの binary でもデモが立つ。しかし本番の binary に fake のコードが入り、設定の誤り一つ（`profile` を変える）で支払いの偽装に届く。判断基準 1 の「決して入らない」を満たさない。
- **P3（別の binary）**: 本番の `cmd/my` には何も足さない、最も強い隔離である。しかし `cmd/my` を単一の binary とする構成（overview §6）から外れ、`my serve` 以外のコマンド（シードの使う `my admin create` など）とフラグを二重に保つことになり、L4 が測るのが本物の `my serve` でなくなる（判断基準 5）。
- **P4（Stripe のテストモード・stripe-mock）**: 本物の事業者の画面を通せる。しかし鍵（秘密）とネットワークが要り（判断基準 3）、fork と手元では動かない。stripe-mock は申し込みの画面を持たない。
- **M1（`mail = none`）**: Docker が要らず、最も軽い。しかしリンクはサーバーのログにしか出ず、利用者の道筋でメールを開く作業を測れない。
