# ADR-0079: CI の検査を Merge Queue に一本化する

- Status: Accepted
- Date: 2026-11-11
- Deciders: @rosylilly
- Issue: #1052, #553, #1064, #1638, #1674, #1734, #2453, #2651

## Decision（決定）

1 つの保証は、結果を決められるいちばん早くて安い層で、1 回だけ確かめる（§18）。main に入る前の保証は Merge Queue の全検査が持ち、手元は速い検査だけを、PR はその PR のファイルだけで決まる検査だけを受け持つ。

### 1. 守るものと防ぐ場所

- Merge Queue の全検査が、main に入る前の唯一の関門である。統合した状態でのコンパイル・型・テストは、ここでしか確かめられない。
- 層は 5 つ: 手元（§10）、PR（§2〜§4）、Merge Queue（§5）、遅い検査（§8）、リリースの関門（§8）。main への push は関門にしない（§7）。

### 2. PR の検査

その PR のファイルか lockfile だけで結果が決まり、ほかの PR と重ねても結果が変わらない検査に限る。目安は 2 分以内。重ねて変わりうる検査を PR で回しても、main に入る前に古くなる。

### 3. PR の lint

Go の lint は PR で、変えたモジュールの全体に対して回し、Merge Queue では回さない。重ねて初めて増える指摘は稀でビルドを壊さず、遅い検査が見つける。

### 4. PR の Docker の検査

イメージでしか分からないもの（各段のビルド、イメージに入るファイル、構成の配線）は、Docker の構成を変えた PR でだけ確かめる。サーバーの組み立てと起動は Go のテストが確かめるので、コードだけの変更では回さない。arm64 は遅い検査に任せる。

### 5. Merge Queue の検査

- 変わった文脈の検査だけを回す。文脈の判定の漏れは「知らないパスはすべての文脈」で防ぐ。
- クライアントが変わったグループは E2E の操作の流れを、アダプタが変わったグループはそのアダプタの実物に対する契約を回す。
- アダプタを外したビルドの組み合わせは遅い検査に回す。壊れるのはアダプタを変えたときだけで、リリースの前には必ず通る。
- 同時に組むグループの数は、runner の同時実行の上限に収まるように絞る。
- PR でも全検査を回したいとき（外の貢献者の PR、Merge Queue で落ちた原因の調査）は、ラベルで切り替える。

### 6. 必須チェックとスキップ

必須チェックは 1 つにし、ワークフローは必ず起動して、絞り込みはジョブの単位で行う。パスで起動しなかったワークフローのチェックは Pending のまま残ってマージを止め、Merge Queue のイベントにはパスのフィルタがないからである（[required status checks](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/collaborating-on-repositories-with-code-quality-features/troubleshooting-required-status-checks)、[merge queue](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue)、2026-10-19 確認）。

### 7. main への push

関門にしない。main のコミットは Merge Queue が検査した木そのものである。push では、PR と Merge Queue が復元するキャッシュだけを作る。キャッシュを共有できるのは既定のブランチで作ったものだけだからである（[Dependency caching](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching)、2026-10-23 確認）。テストの結果もキャッシュに入れ、変更の影響を受けたパッケージのテストだけが走るようにする。

### 8. 遅い検査とリリースの関門

- 遅い検査（E2E のロケールと幅、実物のインフラに対する契約の全部、連合、両アーキテクチャのイメージ、lint の全体、ビルドの組み合わせ、コードスキャン）は nightly と手動で回す。main が動いていなければ回さない。
- **赤は止める合図にする。** nightly が落ちたら自動で Issue にし、直すまではほかの作業より先にする。main が落ちたままの期間を許さない。
- **リリースは検査済みのコミットを昇格させる。** そのコミットで通った遅い検査があればそれを使い、なければ回す。アップグレードとリストアは、そのコミットのイメージで毎回確かめる。
- プレリリースに限り、緊急時に遅い検査を飛ばせる。安定版では飛ばせない。飛ばしたことはリリースの記録に残す。

### 9. E2E の並列化

1 回ビルドした成果物をシャードに配る。主な理由は時間ではなく、すべてのシャードが同じビルドを検査することである。シャードは自分のサーバーと DB を持ち、状態を共有しない。

### 10. 手元の検査と Merge Queue から外れた PR

- 手元では、触った領域の速い検査（書式、変えたパッケージのビルドと静的検査、メッセージの検査）を push の前に走らせる。PR を出す道具がこれを走らせ、落ちたら出さない。
- 全検査を手元で走らせる義務は置かない。並行するエージェントが 1 台のマシンを食い合い、統合して初めて壊れるものは手元では見つからない。
- Merge Queue から外れた PR は、持ち主が rebase して入れ直す。その間も列の残りは進む。

### 11. CI のジョブの組み方

各検査のコマンドの定義は 1 か所（タスク）に置き、手元と CI が同じものを呼ぶ。CI のジョブはワークフローで組み、検査ごとにステップを分けて、落ちたステップの名前が落ちた検査の名前になるようにする。手元と CI の組み合わせのずれは機械で検査する。

### 12. 覆す条件

- Merge Queue で落ちて外れる PR が週に数件を超える: コンパイルと型検査を PR に戻す。
- Merge Queue のグループの所要時間の中央値が 10 分を超える: E2E の流れを見直す。
- 同じ不安定なテストで nightly の Issue が繰り返し開く: 自動で隔離する仕組みを考える。
- runner の同時実行の上限が問題でなくなる: PR でも全検査を回すことを考える。
- Merge Queue で回さない検査の失敗が main に繰り返し入る: その検査を Merge Queue に戻す。
- 手元の速い検査が 1 分を大きく超える: 範囲を削る。

### 13. UI のプレビュー: 置くもの

PR ごとに、部品と画面のカタログを 1 つの URL で公開する。画面のストーリーはアプリ全体をルートで描き、API を差し替えて、画面の要件（ADR-0110）の作業ごとの状態（通常・空・読み込み中・エラー・長い文言・RTL・最小幅）を列挙する。

### 14. UI のプレビュー: 置き場

静的なファイルを返すだけのホスティングに置く。サーバーの実行環境にはしない。PR ごとの URL は検索に載せず、閉じた PR のものは消す。main のものが、決定者が全画面を見る一覧になる。

### 15. UI のプレビュー: CI の構成

ビルドと公開を分ける。ビルドは秘密情報を持たず、フォークの PR でも動く。公開は main の側の定義で動き、成果物を静的なファイルとしてだけ扱って実行しない。プレビューはマージの条件にしない。変わったストーリーの一覧を PR に示し、決定者が見る順にする。

### 16. UI のプレビュー: 見直す条件

画面のストーリーの手入れが画面の追加のたびに大きな手間になるなら、アプリ全体を差し替えた API で動くデモに切り替える。PR ごとの URL を持てなくなったら、main の一覧だけを置く。

### 17. CI から Claude API への認証

- 短命のトークンへの交換（Workload Identity Federation）で認証し、静的な API キーを GitHub に置かない。
- Claude API を使うジョブは、main だけが使える専用の環境で動かす。
- CI 専用のワークスペースに使用額の上限を設け、それを CI 全体の費用の上限にする。
- 信頼できない入力（PR や Issue の本文）を読むジョブには、書き込みの権限もモデルの道具も与えない。出力は機械が検査し、決定者が読んでから公開する。
- 見直す条件: 道具が交換に対応しなくなったら、交換したトークンをそのジョブの中でだけ渡す。静的なキーには戻さない。

### 18. 検査の配置の原則

- 1 つの保証は、結果を決められるいちばん早くて安い層で、1 回だけ確かめる。別の層でもう一度回すのは、その層でしか分からないもの（統合した状態、実物のインフラ、リリースの成果物）に限る。
- テストの範囲は変更の影響範囲で決める。そのために、パッケージの境界をテストの責務の境界にする。
- 組み立ての層のテストは毎回走ってよい。その代わり、Merge Queue の最長のジョブに収まる速さに保つ。

## 経緯

- 当初は PR・Merge Queue・main への push のすべてで同じ検査を回していた。3 日間の実測（2026-10-20〜23、約 5,800 ジョブ）で、main への push が runner 時間の半分を使い、その 60% は次の push で取り消されていた。PR と Merge Queue の失敗はどちらも 1% 前後で、Merge Queue だけが止めたのは、重ねて初めて壊れる型の不一致だった。
- 手元の全検査は、1 台で 5 エージェントを並行させた日に負荷でタイムアウトし、その日 Merge Queue が止めた失敗は手元では見つからないものだった。そこで全検査の義務を外した。
- その後、PR の事前検査で落ちる例が続き、決定者は「速い検査は手元で、保証は CI で」と決めた（§10）。書式の検査を PR を出す手順に入れたとき、実行率は 6% からほぼ 100% になった。
- リリースが nightly と同じ検査を回し直していたこと、nightly の赤を許していたために退行がリリースの直前にまとまっていたことから、昇格の形と「赤は止める合図」を決めた（§8）。
- プレリリースの緊急の口は、リリースと関係のない理由で関門が続けて落ち、候補版を出せなかったために足した。

## 採らなかった案

- PR と Merge Queue の両方で全検査を回す: PR で全部分かるが、同じ検査を 2 回回し、runner を取り合う。
- PR に一本化する: 作者は早く結果を知れるが、重ねて壊れるものが main に入る。
- Merge Queue をやめる: 単純だが、壊れた main は並行するエージェント全員を止める。
- 遅い検査を main への push ごとに回す: 退行に早く気づくが、マージの多い日は runner を使い続ける。
- リリースのたびに遅い検査を回し直す: 同じコミットで同じ結果を得るために、数時間の runner を使う。
- 手元の全検査を必須にする: 自分の PR で閉じた失敗は早く分かるが、並行のマシンを食い合う。
- 手元の検査を一切求めない: 単純だが、書式のような安い失敗が PR で初めて見つかり、往復が増える。
- パスのフィルタでワークフローを分ける: 文脈ごとに読めるが、必須チェックが Pending のまま残る。
- プレビューを部品のカタログだけにする: 安いが、問題の中心である画面の情報設計を見られない。
- 静的な API キーを使う: 設定は簡単だが、漏れると取り消すまで使える。

## Consequences（影響）

- 全検査は、統合した状態に対して 1 回だけ回る。PR の結果は 2 分以内に返る。
- 自分の PR の中で閉じた失敗のうち、速い検査が見ないものは、Merge Queue で初めて見つかる。
- E2E のロケールと幅の退行は、見つかるまで最長 1 日かかる。
- リリースは、遅い検査をすべて通ったコミットからしか作れない。
- 文脈の判定に Merge Queue が頼る。
