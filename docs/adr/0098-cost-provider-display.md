# ADR-0098: 費用の内訳の事業者を入力どおりの表記で出す

- Status: Accepted
- Date: 2026-10-24
- Deciders: @rosylilly
- Issue: #1206

## Context（背景・課題）

費用の集計（FR-902）と公開（FR-903）の内訳は、ADR-0067 §2 の「内訳は `provider_normalized`（NFKC・小文字）でまとめる」に従い、まとめるキーの `provider_normalized` をそのまま事業者として返している。
このため、`GET /instance/cost_totals`・`GET /finance/cost_totals`・`GET /admin/cost_totals` と、それを出す `/about/costs`・`/finance`・`/admin/finance` で、`ConoHa` が `conoha`、`Amazon SES` が `amazon ses` と出る。
取り込んだ費用（ADR-0068）も、事業者の名前 `Google Cloud` を正規化した `google cloud` で出る。

決定者の指示（#1206、原文）:

> 内訳が小文字正規化されるの辛いので完全文字一致とかにしてちゃんと出るようにしたいですね
> （選択）正規化でまとめ、表記は元のまま

まとめ方（正規化でまとめる）は変えず、内訳の 1 行に出す事業者の表記を決める。
1 つの行には表記の違う項目（`ConoHa`・`conoha`・`ＣｏｎｏＨａ`）が入りうるので、どの表記を出すかを決定的に決める規則が要る。

## Decision Drivers（判断基準）

1. 運営者が入力した表記がそのまま出ること（決定者の指示）
2. 同じ入力からは誰が見ても同じ表記が出ること（ADR-0067 の判断基準 1。公開のページは 60 秒キャッシュされ、閲覧者ごとに変わってはならない）
3. 運営者が表記を直したら、その直した表記が出ること
4. データモデル（ADR-0020）と読み取りのときの集計（ADR-0067 §1 の A1）にそのまま乗り、表や投影を増やさないこと

## Considered Options（選択肢）

- **D1**: 期間の中で、正規化した事業者ごとに、その期間に支払いが載る項目のうち、いまのラベルの版が最も新しい項目の `provider` を出す
- **D2**: 正規化した事業者ごとに、期間に関わらず、取り消されていないすべての項目のうち、いまのラベルの版が最も新しい項目の `provider` を出す
- **D3**: 期間の中で、金額の最も大きい項目の `provider` を出す
- **D4**: 完全一致でまとめる（`provider` そのものをキーにする）

## Decision（決定）

**D1 を採用する。** 内訳は ADR-0067 §2 のとおり `provider_normalized`・区分・通貨でまとめ、各行に出す事業者の表記だけをこの ADR が決める。
ADR-0067 §2 の「内訳は `provider_normalized`（NFKC・小文字）でまとめる」は、まとめ方としてそのまま残し、表記には適用しない。

### 1. 表記の規則

- 集計の期間ごとに、`provider_normalized` が同じ内訳の行（区分・通貨が違う行を含む）は、同じ 1 つの表記を出す。
- 表記は、その期間に支払い（按分では日割りの分）が載る費用の項目のうち、いまのラベルの版（`cost_item_heads.label_revision_id`）の `revised_at` が最も新しい項目の `provider` である。
  `revised_at` が同じなら、ラベルの版の `id` が大きいほうを採る。
- 取り込んだ費用（ADR-0068）の表記は、取り込みが使う事業者の名前（`aws` は `AWS`、`gcp` は `Google Cloud`。`rules.sources[].provider` と同じ）である。
  同じ期間・同じ `provider_normalized` に手入力の項目があれば、手入力の項目の表記を優先する。取り込んだ費用だけの行は、取り込みの事業者の名前を出す。
- 行の並びは、今と同じく `provider_normalized`・区分・通貨の順にする。表記で並べ替えない。
- `GET /finance/cost_totals` の項目の行（ADR-0070 §5）の `provider` も、その期間の同じ `provider_normalized` の内訳の行と同じ表記にする。項目の行を内訳の行と見比べられるようにするためである。

### 2. API とデータ

- `CostBreakdownLine.provider` と `FinanceCostItemLine.provider` の意味を「正規化した事業者」から「§1 の表記」に変える。項目を足さない。
  正規化した形は表示に使わず、まとめるキーはサーバーの中だけに持つ。
- 表やカラムは足さない。集計は `cost_item_heads` から読むいまのラベルの版の `provider`・`revised_at`・`id` を使い、読み取りのときに計算する（ADR-0067 §1）。
- 3 つの集計の API（公開・会計の閲覧・管理）は同じ規則で表記を決める。公開の API の内訳でも、出すのは項目の名前ではなく事業者の表記なので、ADR-0067 §8 の公開の範囲は変わらない。
- Web クライアントは、事業者の表記を運営者の入力として `dir="auto"` で出す（ADR-0067 §10）。

### この決定を覆す条件

- 運営者が同じ事業者を期間ごとに違う表記で入れ、期間をまたぐと表記が変わることが分かりにくいと分かったら、D2 に変える。

## Consequences（影響）

- 良い影響
  - `ConoHa`・`Amazon SES`・`Cloudflare R2` が入力どおりに出て、表記の揺れは今と同じく 1 行にまとまる。
  - 表記を直すとラベルの版が新しくなるので、直した表記がすぐ出る。
  - スキーマを変えず、集計の関数が表記を選ぶだけで済む。
- 悪い影響・トレードオフ
  - 同じ事業者でも、期間ごとに載る項目が違えば、期間ごとに違う表記が出うる（例: 先月は `conoha` の項目だけ、今月は `ConoHa` の項目もある）。
  - まとめるキーが API に出なくなるので、クライアントは行を `provider` の文字列で見分ける。1 つの期間の中では `provider_normalized` ごとに表記が 1 つなので、行は見分けられる。
- 後続で必要になる作業
  - #1206: 集計の関数と 3 つの API の内訳・項目の行の表記、`api/spec` の説明、両方の方言のテスト、Web のテスト

## Pros and Cons of the Options（詳細比較・任意）

- D1（採用）の良い点: 期間に載った項目からだけ選ぶので、その期間の内訳に実際にある表記が出る。悪い点: 期間ごとに表記が変わりうる。
- D2 の最も強い論点: どの期間でも同じ事業者は同じ表記になる。悪い点: 期間に載らない（終了した・まだ始まらない）項目の表記が出る。集計の対象の外の項目を読む必要がある。
- D3 の良い点: いちばん大きな支払いの表記が出て、それらしい。悪い点: 金額の改定や按分で表記が入れ替わり、運営者が表記を直しても出るとは限らない（判断基準 3）。
- D4 の良い点: 規則が要らない。悪い点: `ConoHa` と `conoha` が別の行になり、ADR-0067 が正規化でまとめた理由（表記の揺れで内訳が割れる）に戻る。決定者は「正規化でまとめ」を選んだ。
