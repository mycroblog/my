# ADR-0161: イベント（ローカルの利用者の集まりの予定・日程の調整・場所・出欠・リマインダー・通話のルーム）

- Status: Accepted
- Date: 2026-11-09
- Deciders: @rosylilly
- Issue: #2599, #2600

## Decision（決定）

**イベント**は、同じサーバーのローカルの利用者が集まりを計画し、日程を決め、通話のルーム・現地の場所・URL のどれかで会うための単位である。
各節は決定者が決めた内容で、覆る条件を各節の末尾か「覆る条件」に書く。通話のルームの側（予定で開くルームと公開範囲 `following`）は [ADR-0100](0100-voice-chat-rooms.md) §3・§4・§16 が決める。

### 1. 範囲

- **連合しない**。イベントはこのサーバーのローカルの利用者のもので、通話のルーム（ADR-0100）と同じに、リモートの人は見ることも参加することもできない。ActivityPub の `Event` は送らず、受け取っても作らない。
- 最初の版に、次の 4 つの段階をすべて入れる。
  1. 確定した日時と場所（§5・§6）、出欠（§8）、通知（§11）、リマインダー（§12）
  2. 通話のルームと、開始の時刻にルームが開くこと（§10）
  3. 日程の調整（候補への投票、§7）
  4. `.ics` の書き出し（§15）、定員（§8）、共同主催者（§4）
- 持たないもの: 終日のイベント、繰り返し、待機リスト（キャンセル待ち）、支払い、イベントの中のチャット・掲示板。話し合いは普通の投稿と返信で行う。

### 2. モジュールと依存の向き

- 新しいモジュール `gathering` を置く（`internal/domain/gathering`・`internal/app/gathering`、スキーマは `schema/<NN>-gathering/<dialect>.sql`）。ADR-0020 の「イベント」（起きた事実の表）と取り違えないよう、コードの名前は `gathering` にする。UI・API・文書は「イベント」/ "event" と呼ぶ（`locales/en`・`locales/ja`、`tools/i18n/glossary.json` に語を足す）。
- `internal/app/gathering` が import する他のモジュールの `internal/app`（ADR-0002）:
  - `graph`: 主催者とのフォロー（承認済み）・相互フォロー・ブロックの判定
  - `identity`: 権限 `create_events` の検査、インスタンス設定（§3）、利用者のタイムゾーン（`user_time_zones`）
  - `account`: アカウントの状態（凍結・削除）と制限（limited）
  - `notification`: 通知の作成（§11）
  - `moderation`: 監査ログと通報の対象（§14）
  - `voice`: 予定で開くルームの開始と、主催者がホストになれるかの検査（§10、ADR-0100 §16）
- **`voice` は `gathering` を import しない**。ルームの終わりやホストの交代は、`voice` が出している domain event を `gathering` が購読して知る。凍結・削除も、各モジュールの domain event を `gathering` のジョブが購読して反映する（ADR-0100 §1 と同じ経路）。
- 覆る条件: イベントを投稿やタイムラインに深く組み込むことになり、`content` との双方向の依存が要るとき（そのときは `content` から `gathering` を呼ぶ向きだけにする）。

### 3. 作る権限と設定

- **既定では、ログイン済みのローカルの誰でもイベントを作れる**。インスタンス設定 `event_creators`（`instance_settings`、`manage_settings`）が `everyone`（既定）か `permitted`（権限 `create_events` を持つ人だけ）。
- 権限 `create_events` の区分は `member`（[ADR-0070](0070-permission-split-emoji-finance.md) §1）で、プランのロールの許可リスト（FR-912）に入る。組み込みのロールでは `admin` が持つ。
- **通話のルームをイベントの場所にする**には、主催者が通話のルームのホストの資格（ADR-0100 §2。`voice_room_starters` が `everyone` か `start_voice_rooms`）を持つ。資格の検査は `voice` の関数を呼ぶ。通話が `off`（ADR-0101）のとき、通話の場所は選べない。
- 主催者の資格: ローカルの有効なアカウントで、制限（limited）されておらず、`event_creators` が `everyone` か `create_events` を持つ。作るときと、主催者が改版するときに検査する。共同主催者（§4）には資格は要らない。
- インスタンス設定 `event_public_summary`（既定は偽、`manage_settings`）: §9 の未ログインの要約。
- レート制限（`KeyValueStore`）: イベントの作成は 1 人 1 時間に 10 件、招待はイベントごとに 1 時間に 100 件（ADR-0100 §7 と同じ）。

### 4. 主催者と共同主催者

- **主催者**は作った人で、1 人。主催者は変わらない（渡さない）。公開範囲の「フォロワー」「フォローしている人」「相互フォロー」は主催者を基準にする。
- **共同主催者**は主催者が指名と解除をする。最大 3 人（通話のルームの共同ホストの上限 ADR-0100 §5 に合わせ、予定で開くルームの共同ホストの候補にそのまま渡せるようにする）。指名の順を持つ。主催者か共同主催者とブロックの関係にある人は指名できない（`422`）。
- 主催者と共同主催者ができること: 設定の改版（題名・説明・日時・場所）、招待と取り消し、出欠の承認と取り消し（§6）、日程の候補の追加と確定（§7）。
- 主催者だけができること: 共同主催者の指名と解除、公開範囲の変更、中止。

### 5. 設定と日時

| 項目 | 値 | 既定 |
| --- | --- | --- |
| 題名 | 必須、1〜100 文字（書記素で数え、1,000 コードポイントも上限。ADR-0100 §3 と同じ） | — |
| 説明 | 任意、3,000 文字まで。プレーンテキストで、URL だけをリンクにする（§6 の URL と同じ扱い） | 空 |
| 公開範囲 `visibility` | `public`（ローカルの全員）/ `followers`（主催者のフォロワー）/ `following`（主催者がフォローしている人）/ `mutuals`（主催者と相互フォロー）/ `invited`（招待制） | `public` |
| 日時 | 確定した開始と終了（§7 の確定）か、候補への投票（§7） | — |
| タイムゾーン | IANA の名前（`Asia/Tokyo`） | 主催者の `user_time_zones`、なければブラウザの値 |
| 場所 | 0〜3 個。§6 | なし |
| 現地の場所の見せ方 `place_disclosure` | `approved`（承認した参加者だけ）/ `viewers`（イベントが見える全員） | `approved` |
| 定員 | 0（なし）か 1〜10,000 | 0 |

- **時刻は UTC で持ち、イベントのタイムゾーンの名前を一緒に持つ**。画面は閲覧者のタイムゾーンで出し、イベントのタイムゾーンと違えば両方を出す。タイムゾーンの名前は Go の `time.LoadLocation` で検証する（`cmd/my` は `time/tzdata` を埋め込むので、コンテナに tzdata がなくても読める）。
- 開始は終了より前で、長さは 7 日まで。作るときと日時を変えるときに、開始が今より後で、1 年先まで。
- 終日のイベントと繰り返しは持たない（§1）。
- 公開範囲を狭めても、§9 の 5 で出欠に答えた人には見え続ける。

### 6. 場所

- 場所の種類は 3 つ。1 つのイベントに各種類 1 つまで。
  - **通話**（`voice`）: 開始の時刻に開くルーム（§10）。発話範囲（ADR-0100 §3 の `speakers`）を主催者が選ぶ（既定 `manual`）
  - **現地**（`physical`）: 名前（100 文字まで）と住所（500 文字までのテキスト）と、任意の地図の URL
  - **URL**（`url`）: 名前と URL（配信や外部の会議のリンク）
- **URL は `http` と `https` だけ**を受け付け（2,000 文字まで）、サーバーは取りに行かない（リンクのプレビュー（[ADR-0062](0062-link-preview-cards.md)）を作らない）。Web は `rel="nofollow noopener noreferrer"` と `target="_blank"` で出す（[ADR-0019](0019-security-baseline.md)）。住所はテキストのままで、地図を埋め込まず、地図は主催者が付けた URL へのリンクだけにする。
- **現地の場所は、既定では主催者が承認した参加者にだけ見せる**（`place_disclosure` が `approved`）。主催者はイベントが見える全員に見せる（`viewers`）こともできる。URL の場所も同じ設定に従い、既定は承認した参加者だけである（外部の会議のリンクを荒らしから守る）。通話の場所はルームの公開範囲（§10）で守るので、イベントが見える人に常に入口を出す。
- 承認: 「行く」か「たぶん」と答えた人を、主催者か共同主催者が承認し、取り消せる。承認は出欠の答えが「行かない」に変わると外れる。主催者と共同主催者には常に見える。

### 7. 日程の調整

- 主催者は、日時を確定して作るか、候補（最大 20 個）を出して作る。候補にも開始と終了とタイムゾーン（イベントのもの）がある。
- イベントが見える人が、各候補に「行ける」/「たぶん」/「行けない」で答え、確定まで変えられる。答えた人の名前は、イベントが見える人に見える（画面に示す）。
- 主催者か共同主催者が 1 つの候補を確定する。確定はイベント（§13 の `gathering_schedule_confirmations`）として残り、確定の後は投票を受け付けない。答えた人と招待された人に `event_schedule_confirmed` を送る（§11）。
- 確定の後に日時を変えるのは、新しい確定（候補を経ない）として書く。リマインダーと開始のジョブは今の確定に従う（§12）。

### 8. 出欠と定員

- イベントが見える人が「行く」/「たぶん」/「行かない」で答え、変えられる。開始の後と中止の後は答えを変えられない。
- 定員があるとき、「行く」の数が定員に達したら、新しい「行く」を `409` で拒む。「たぶん」と「行かない」は拒まない。待機リストは持たない。定員を「行く」の数より少なくしても、答えた人は残る。
- 出欠の一覧（行く・たぶん）は、イベントが見える人に見える。答える前の画面に「答えると名前が一覧に出る」と示す（ADR-0100 §5 と同じ）。

### 9. 公開範囲の判定

判定を 1 か所にする（NFR-SEC-4、ADR-0017 の `canView` と ADR-0100 §4 と同じ方針）。`internal/domain/gathering` に純粋な関数を置き、一覧・イベントのページ・通知の宛先・出欠・投票・`.ics`・API のすべてがこれを通る。
関係の事実は `internal/app/gathering` が集めて渡す。形は `internal/domain/voice/policy.go` に合わせる。

`CanSee(event, viewer, facts)` — 次の順に評価する:

1. 閲覧者が未ログイン、リモート、凍結・削除なら偽（未ログインの要約は §9 の末尾）
2. 閲覧者が主催者か共同主催者のいずれかとブロックの関係（どちら向きも）にあれば偽
3. 閲覧者が主催者か共同主催者なら真
4. 閲覧者が招待されていれば（取り消されていなければ）真（応答にかかわらず）
5. 閲覧者が出欠か日程の候補に答えていれば真（公開範囲を狭めても、答えた人を締め出さない）
6. `visibility` が `public` なら真、`followers` なら閲覧者が主催者をフォローしていれば真、`following` なら主催者が閲覧者をフォローしていれば真、`mutuals` なら相互フォローなら真、`invited` なら偽

`CanSeePlace(event, place, viewer, facts)` — `CanSee` が真で、次のどれか: 主催者か共同主催者、場所が通話、`place_disclosure` が `viewers`、閲覧者が承認されている。

- 中止したイベントと終わったイベントも、`CanSee` が真の人には見える（中止の理由と、終わったことを示す）。
- **未ログインの閲覧者には既定で何も見せない**。`event_public_summary` が真で、公開範囲が `public` なら、未ログインの閲覧者とリモートの閲覧者に要約（題名・日時・主催者・中止か）を出し、OGP にも載せる。場所・説明・出欠は出さない（FR-928 の通話の要約と同じ形）。
- イベントの URL は `/events/{event_id}`。HTML の外枠と OGP は Go が返す（[ADR-0028](0028-html-shell-link-previews-and-pwa.md)）。リモートの閲覧者と未ログインの閲覧者には、要約を見せる条件でなければ「このサーバーのローカルの利用者だけが参加できる」とログインの入口だけを出す。
- フォローしている人への「新しいイベント」の通知は送らない。イベントは一覧（`/events`。見えるイベントの開始の近い順）・主催者のプロフィールの入口・招待（§11）で知らせる。

### 10. 通話のルーム

- **通話の場所のルームは、開始の時刻に待機つきで開く**。`gathering` のジョブ（§12）が `voice` の予定で開く操作（ADR-0100 §16）を呼び、主催者がホストのルームを開く。ルームは最初の参加者が来るか、待機の終わり（既定は開始から 30 分）まで、空でも終わらない。
- ルームの設定はイベントから作る: 名前は題名、公開範囲はイベントのものを写す（`public` → `local`、`followers` → `followers`、`following` → `following`、`mutuals` → `mutuals`、`invited` → `invited`）、発話範囲は §6 で主催者が選んだもの。共同主催者を指名の順に、ルームの共同ホストの候補として渡す。
- 開始のとき、「行く」「たぶん」と答えた人と、取り消されていない招待を受けてまだ答えていない人を、ルームの招待に写す。「行かない」と答えた人は写さない。ホストが交代して公開範囲の基準が変わっても、その人たちは締め出されない（ADR-0100 §16）。写した招待は `voice_room_invited` を送らない。
- 開始の後に「行く」「たぶん」と答えた人も、ルームが開いている間はルームの招待に足す。
- 開始の投稿（ADR-0100 §9）は作らない。開始の通知は `event_started`（§11）だけで、`voice_room_started` は送らない（同じ人に 2 通届けない）。
- **ルームが開けなくてもイベントは残る**。主催者が資格を失った、主催者が別のルームのホストである、開いたルームの数が上限、通話が `off` のとき、ルームは開かず、主催者に `event_room_unavailable` を送る（§11）。参加者には `event_started` をルームのリンクなしで送る。資格と通話の有効は、確定のときと開始の 1 日前にも検査し、開けない見込みなら主催者に同じ通知を送る（そのときに直せるように）。
- 待機が終わっても誰も来なかったとき、ルームは終わり（ADR-0100 §16）、`gathering` はルームの終わりの domain event を受けて主催者に `event_room_unavailable` を送る。
- イベントを中止したとき、開いているルームは `voice` の操作で終える（主催者の中止は理由 `host`、モデレーターの中止は理由 `moderator`）。イベントの終了の時刻ではルームを閉じない（話が続くなら続ける。ルームは ADR-0100 §6 の規則で終わる）。

### 11. 通知

`notification` の種類を足す。通知の設定（ADR-0086 §9）の「普段の通知」に「イベント」の行を 1 つ足し、アプリ内は既定オン、メールは既定オフにする。通知の一般の除外（ミュート・通知の除外・ブロック）はそのまま効く。

| 種類 | 宛先 | 冪等キー |
| --- | --- | --- |
| `event_invited` | 招待された人 | （招待, 宛先） |
| `event_schedule_confirmed` | 日程の候補に答えた人と、招待された人 | （確定, 宛先） |
| `event_changed` | 「行く」「たぶん」の人と、招待された人。日時・場所・通話のルームが変わったときだけ（題名・説明の改版では送らない） | （改版, 宛先） |
| `event_cancelled` | 「行く」「たぶん」の人と、招待された人 | （中止, 宛先） |
| `event_reminder` | 「行く」「たぶん」の人（§12） | （確定, 前もっての時間, 宛先） |
| `event_started` | 「行く」「たぶん」の人。通話のルームがあればそのリンクを持つ | （確定, 宛先） |
| `event_room_unavailable` | 主催者（§10） | （確定, 理由, 検査の時点） |

- 宛先はジョブが実行のときに決め直し、送る前に `CanSee` を確かめる（ADR-0086 §1 の実行時の再確認と同じ）。
- **メール**: 本文は題名・日時・主催者と共同主催者の表示名・イベントへのリンクだけにし、**場所（住所・URL）を入れない**。メールは転送や保存で外に出やすいため。
  `event_reminder` のメールは、ADR-0086 §11 の 15 分の未読の待ちをせず、リマインダーの時刻にすぐ送る（遅れたリマインダーは意味が薄い）。それ以外の種類のメールは ADR-0086 §11 に従う。

### 12. 定期ジョブとリマインダー

- **リマインダー**: 既定は開始の 1 日前と 1 時間前。利用者ごとに、通知の設定の画面で、前もっての時間を 0〜3 個（5 分〜7 日）に変えられる（現在値。ADR-0020 規約 5）。
- **`gathering.tick`**（`Scheduler`、1 分ごと）: 期限の来たイベント（§13 の `gathering_dues`）だけを読み、リマインダー・開始・ルームの開始・開始の前日の検査のジョブを outbox で積み、次の期限を書く。期限の行は、確定・日時の変更・中止のたびに同じトランザクションで書き直す。
- 積むジョブは冪等で（ADR-0004）、冪等キーは §11 の表のとおり確定（日時の版）を含む。日時が変わると新しい確定のキーで積み、古い確定のジョブは実行のときに今の確定と違えば何もしない。
  そのため、日時を変えたら新しい時刻のリマインダーだけが届き、古い時刻のものは届かない。
- 宛先の多いジョブは 500 人ごとに分けて積む（キーにページを含める）。
- 実際の間隔は構成で違う（Cloud Run は Cloud Scheduler の 1 分ごとの tick（ADR-0004 §12）、ECS Fargate とセルフホストはプロセス内の Scheduler、Neon Free などで `tick_schedule` を延ばした構成ではその間隔）。
  リマインダーと開始はその間隔だけ遅れうる。実際の間隔は #2602 で測り、運営者の文書に書く。

### 13. データモデル

`schema/<NN>-gathering/<dialect>.sql` に置く（ADR-0020）。すべて `gathering` が書く。状態を NULL 許容の日時のカラムで表さず、事実はイベントの行の有無で表す。

| 表 | 分類 | 中身 |
| --- | --- | --- |
| `gatherings` | リソース | id、主催者のアカウント、作った時刻 |
| `gathering_revisions` | イベント | 設定の改版: イベント、題名、説明、`visibility`、タイムゾーン、`place_disclosure`、定員、改版した人、時刻。作ったときの設定が最初の改版 |
| `gathering_revision_places` | リソース（改版の子） | 改版、種類（`voice` / `physical` / `url`）、名前、住所、URL、発話範囲（`voice` のとき）、順序 |
| `gathering_candidates` | リソース | id、イベント、開始、終了、足した人、時刻 |
| `gathering_candidate_withdrawals` | イベント | 候補、取り下げた人、時刻 |
| `gathering_votes` | 現在値 | 候補、アカウント、答え（`yes` / `maybe` / `no`）。確定まで変わり、履歴に意味がない（規約 5） |
| `gathering_schedule_confirmations` | イベント | id、イベント、開始、終了、確定した人、時刻。今の日時は最新の確定 |
| `gathering_confirmation_candidates` | リソース（確定の子） | 確定、候補（候補から確定したときだけ行がある） |
| `gathering_invitations` | リソース | id、イベント、招待された人、招待した人、時刻。（イベント, 招待された人）で一意 |
| `gathering_invitation_revocations` | イベント | 招待、取り消した人、時刻 |
| `gathering_rsvps` | イベント | イベント、アカウント、答え（`going` / `maybe` / `declined`）、時刻 |
| `gathering_rsvp_approvals` | イベント | イベント、アカウント、`approved` / `revoked`、操作した人、時刻 |
| `gathering_coorganizer_changes` | イベント | イベント、アカウント、`assigned` / `removed`、時刻 |
| `gathering_cancellations` | イベント | イベント（一意）、理由（`organizer` / `moderator` / `organizer_suspended` / `organizer_deleted`）、操作した人（NULL 可: 自動の中止）、理由の文 `note`（500 文字まで）、時刻 |
| `gathering_voice_rooms` | リソース | イベント、確定、ルーム（`voice_rooms.id`）、時刻。（イベント, 確定）で一意（ルームを 2 度開かない） |
| `gathering_heads` | 投影 | イベント、主催者、最新の改版、今の確定、状態（`unscheduled` / `scheduled` / `cancelled`）、開始、終了、「行く」の数 |
| `gathering_attendees` | 投影 | イベント、アカウント、今の答え、承認されているか |
| `gathering_coorganizers` | 投影 | イベント、アカウント、指名の順 |
| `gathering_dues` | 投影 | 次に `gathering.tick` が扱う時刻があるイベントだけの行: イベント、`next_due_at`。開始・リマインダー・検査が残らなければ行を消す |
| `gathering_reminder_offsets` | 現在値 | アカウント、前もっての時間（分）。行がなければ既定（§12） |
| `report_gatherings` | リソース | `moderation` の通報の子（`03-moderation.sql`）: 通報、イベント、改版 |

- `next_due_at` は状態ではなく、確定・リマインダーの設定・中止から再構築できる投影の値である。行の有無で「次の期限がある」ことを表し、NULL を使わない。
- 「行く」の数の検査（定員）は、イベントの行を `LockRoom` と同じ形でロックしてから `gathering_heads` を読み、`gathering_rsvps` を書く（ADR-0003 の短いトランザクション）。
- 投影の再構築は CLI から行える（ADR-0020 規約 1）。

### 14. モデレーション

- **通報**: 利用者は見えるイベントを通報できる。通報の対象のアカウントは主催者で、子の表 `report_gatherings`（通報, イベント, 通報の時点の改版）がイベントとその時の題名・説明・場所を指す。リモートへの転送は使わない。
- **モデレーターによる中止**: `manage_reports` を持つ人がイベントを中止する（理由 `moderator`、理由の文 500 文字まで）。監査ログ（[ADR-0058](0058-moderation-admin-separation.md)）に、対象の種類 `event` と操作 `event_cancelled` で残す。
- **主催者の凍結・削除**: 凍結の domain event を受けたジョブが、主催者の開始前のイベントを理由 `organizer_suspended` で中止する。削除は `organizer_deleted`。凍結の解除で中止は戻らない。
- **改版は証拠として残す**。モデレーターは通報の画面から、そのイベントの改版の並びを見る。アカウントの消去（ADR-0020 規約 6）は、そのアカウントが書いた改版の題名・説明・場所を消し、data-model の消去の表に載せる。
- 出欠・投票・招待の記録は、イベントの終わり（終了の時刻か中止）から 90 日で消す（`instance_settings` の `event_records_retention_days`、下限 30 日。ADR-0100 §13 の形）。通報が参照するイベントの記録は、その通報の保持の期限まで残す。

### 15. `.ics` の書き出し

- `GET /events/{id}/calendar.ics`（ログインが要る。`CanSee` が真の人だけ）で、1 つのイベントの iCalendar（RFC 5545）のファイルを返す。購読の URL（秘密のトークンが要る）は持たない。
- `METHOD:PUBLISH` の `VEVENT` 1 つ。`UID` は `<event_id>@<host>`、`DTSTART`・`DTEND` は UTC（`Z`）で書き、どのカレンダーでも同じ瞬間を指すようにする。`SEQUENCE` は改版の数、中止なら `STATUS:CANCELLED`。
- `LOCATION` は閲覧者に `CanSeePlace` が真の場所だけを書く。見えない場所はファイルに現れない。`URL` はイベントのページ。
- 主要なカレンダー（Google カレンダー・Apple のカレンダー・Outlook）が UTC の時刻を閲覧者のタイムゾーンで正しく出すかは **要検証**（#2604）。

### 16. API と mykit

[client-api.md](../architecture/client-api.md) の手順で細部を決める。形の目安:

- `GET /events`（見えるイベントの一覧）、`POST /events`、`GET /events/{id}`、`PATCH /events/{id}`、`POST /events/{id}/cancel`
- `/events/{id}/rsvp`（`PUT` で答える）、`/events/{id}/attendees`（一覧と `/{account_id}/approval`）、`/events/{id}/invitations`、`/events/{id}/coorganizers`、`/events/{id}/candidates`（追加・取り下げ・`/{candidate_id}/vote`・`/{candidate_id}/confirm`）
- 管理: `POST /admin/events/{id}/cancel`（`admin-moderation` のタグ、ADR-0058 §3）。インスタンス設定は `/admin/settings` に置く
- スコープ: 読み取りは `read:events`、操作は `write:events`（[ADR-0090](0090-third-party-oauth-apps.md) のスコープの規則）
- `pkg/mykit` に同じ REST を入れる（[ADR-0093](0093-api-client-library-mykit.md)）

### 覆る条件

- リモートのサーバーと集まりを共有したいという要望が強くなったとき（ActivityPub の `Event`（Mobilizon・Gancio の形）を送る設計を別に決める。公開範囲と場所の見せ方を連合の上で守れるかが論点になる）。
- イベントの数がアプリで絞れない規模になったとき（一覧の公開範囲を投影の側で絞る）。
- 1 分ごとの tick の遅れが、測った構成で数分を超えるとき（リマインダーの時刻に合わせた遅延のジョブに替える）。

## 経緯

集まりは今、投稿と返信の中にあり、日程は外部のサービスで決め、通話のルーム（FR-920〜FR-932）は誰かがボタンを押したときにだけ開く。#2599 で、ローカルの利用者の集まりをサーバーの中で計画し、日程を決め、通話のルーム・現地・URL で会えるようにすることになった。
決定者は、連合しないこと、既定で誰でも作れること（運営者は `create_events` に絞れる。通話のルームを付けるには `start_voice_rooms` が要る）、公開範囲の 5 つの値と招待された人を常に含めることとブロックで隠すこと、現地の場所を既定で承認した参加者にだけ見せること、未ログインの既定（FR-928 と同じ形）、4 つの段階をすべて最初の版に入れること、ルームを開始の時刻に待機つきで開くこと（#2600）を決めた。
続けて、残りの形（モジュール・データモデル・公開範囲の判定・権限・制限・API・tick・URL・モデレーション・持たないもの）、メールに表示名だけを出し場所を入れないこととリマインダーのメールをその時刻に送ること、URL の場所も既定で承認した参加者にだけ見せること、答えていない招待者をルームの招待に写すこと、主催者への通知 `event_room_unavailable` を決めた。
形を決める基準は、通話のルーム（ADR-0100）に合わせること: 公開範囲の判定を 1 か所にする（NFR-SEC-4）、常駐のタイマーを前提にしない（scale to zero、ADR-0004 §12）、データモデルの規約（ADR-0020）、個人データを要る間だけ持つ（ADR-0058）。
公開範囲 `following` は、イベントの公開範囲をルームにそのまま写せるよう、通話のルームにも足した（ADR-0100 §3）。

## 採らなかった案

- イベントを投稿の一種（`content` の投稿に日時と場所を付ける）にする: タイムラインと連合に乗り、新しいモジュールが要らないが、投稿の公開範囲には `following` と招待制がなく、現地の場所を承認した人にだけ見せる判定を投稿の判定に混ぜることになる。連合しない決定とも合わない。
- ActivityPub の `Event` として連合する（Mobilizon・Gancio の形）: 他のサーバーの人とも集まれるが、決定者が連合しないと決めた。リモートのサーバーで場所の見せ方と公開範囲を守れない。
- 定期ジョブを使わず、リマインダーごとに実行の時刻を指定したジョブ（遅延のジョブ）を積む: 時刻の精度は上がるが、日時を変えるたびに積んだジョブを取り消す必要があり、Cloud Tasks の予定の上限（30 日先まで、**要検証**）を超える先のイベントは積めない。1 分ごとの tick で期限の来たものだけを積む形なら、取り消しは実行時の確認で済む。
- 待機リストを持つ: 定員の大きい集まりで便利だが、繰り上げの通知と承認の順序の規則が増える。まず定員で締め切るだけにする。
- 現地の場所を常にイベントが見える全員に見せる: 単純だが、ローカルの全員に見える集まりで住所が広く見える。決定者が承認した参加者だけを既定にした。
- 開始のとき「行く」「たぶん」の人だけをルームの招待に写す: 写す数が少ないが、招待制のイベントで答えていない招待者がルームを見られなくなる。答えていない招待者も写し、「行かない」の人だけを除く。
- 主催者がホストとして参加するまでルームを開かない: ルームの空の時間がないが、主催者が遅れると誰も入れない。決定者が開始の時刻に待機つきで開くと決めた。

## Consequences（影響）

- 公開範囲と場所の判定が 1 か所にあり、一覧・通知・`.ics`・API の漏れを関数のテストで押さえられる。
- 通話のルームとイベントが同じ公開範囲の語彙を持ち、イベントの公開範囲をそのままルームに写せる。
- 状態をイベントの行と投影で持つので、日時の変更・中止・承認の経過が証拠として残る。テーブルの数は多い（約 20）。
- リマインダーと開始は tick の間隔だけ遅れる。tick を延ばした構成（Neon Free など）では数分以上遅れうる。
- メールに場所を入れないので、メールだけを見る人は場所を知るためにサーバーを開く必要がある。
