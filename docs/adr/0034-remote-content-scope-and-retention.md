# ADR-0034: リモートコンテンツの取り込み範囲・リフレッシュ・保持

- Status: Accepted（取り込む範囲に ADR-0044（プロフィールを開いたときの取得）が加わる。取り込みと保持の規則に ADR-0061（連合リレー）が加わる）
- Date: 2026-10-17
- Deciders: @rosylilly
- Issue: #232

## Context（背景・課題）

リモートの投稿・アカウントをどこまで取り込み、いつ取り直し、いつ消すかは、DB の容量・書き込み行数と外部 HTTP の回数を直接決める。
従量課金の DB（Neon / Turso / Aurora DSQL）とサーバーレスの実行環境では、これがそのまま費用になる（G1、NFR-COST-1, NFR-COST-5）。

関連する要件と決定:

- FR-407（リモート Actor / Object の取得とキャッシュ、定期リフレッシュ）、FR-803（古いリモート投稿の定期クリーンアップ）、FR-106（スレッド表示）、FR-202（連合タイムライン）
- [ADR-0020](0020-data-modeling-principles.md)（イベントと版。消去はイベントの不変性より優先）、[ADR-0013](0013-timeline-strategy.md)（fan-out-on-read）
- [data-model §11](../architecture/data-model/11-open-questions.md#11-未決事項) の未決事項「古いリモート投稿の消去条件」
- [ActivityPub 付録 B.5](https://www.w3.org/TR/activitypub/#security-recursive-objects): オブジェクトを再帰的に解決するときは深さに上限を置く

主要実装の参考値（2026-10-17 にソースで確認。出典は [#232 の調査報告](https://github.com/mycroblog/my/issues/232)）: Mastodon は Actor を 1 日で古いとみなして取り直し、GoToSocial は Actor を 6 時間・投稿を 2 時間で古いとみなし、スレッドの祖先と子孫を最大 1,024 回の反復で取得する。

ADR-0005 はリモート **メディア** の方針（既定はキャッシュしない）を決めているが、投稿とアカウントの文書の扱いを決めた ADR はない。

## Decision Drivers（判断基準）

1. ローカルの利用者が見るもの（ホーム・通知・スレッド・プロフィール）が欠けないこと
2. ストレージと書き込み行数が、ローカルの利用者数とフォロー数に比例し、連合先の規模に比例しないこと（NFR-COST）
3. 外部 HTTP の回数を、利用者の操作に比例する範囲に抑えること（取得の増幅を防ぐ）
4. 削除（`Delete`）とプライバシーの要求に従えること（ADR-0020 規約 6）
5. 実装が v0 の規模に見合うこと

## Considered Options（選択肢）

1. **関係のあるものだけ取り込む**: 受信した `Create` は、ローカルのアカウントとの関係があるときだけ保存する。スレッドは利用者が開いたときに深さを限って取得する。古い投稿はローカルからの参照がなければ消す
2. **受信したものはすべて取り込み、期間で消す**: 届いた公開投稿をすべて保存し、一定期間後に一律で消す
3. **取り込まず、表示のたびに取得する**: 投稿は保存せず、表示時にリモートから取得して短期のキャッシュに置く

## Decision（決定）

**選択肢 1 を採用する。**

### 取り込む `Create`

受信した `Create` のオブジェクトを保存するのは、次のどれかに当てはまるときだけ。どれにも当てはまらなければ、受信の記録だけを残して捨てる。

- 作者を、ローカルのアカウントが承認済みでフォローしている
- ローカルのアカウントをメンションしている、または宛先（`to` / `cc`）に含めている
- ローカルの投稿への返信、またはローカルの投稿を含むスレッドへの返信
- ローカルのアカウントがブーストした（`Announce` を受けた）・お気に入りした・ブックマークした・ピン留めした、または URL の検索で解決した（FR-305）

`Announce` の対象は、ブーストした人がローカルのアカウントにフォローされているときだけ取得する。

### 取得とリフレッシュ

- Actor: 取得から 24 時間で古いとみなし、次に使われたとき（署名の検証・表示・配送）に非同期で取り直す。ローカルのアカウントがフォローしている Actor は、定期ジョブで 24 時間ごとに取り直す。取得が 410 なら `remote_deleted` にする。
- 投稿: 受信した `Update` / `Delete` で更新する。定期的な取り直しはしない（投票の集計だけは、締め切り前に表示されたときに取り直す）。
- スレッド: 返信先（`inReplyTo`）は受信時に 1 段だけ非同期で取得する。それより上の祖先と返信の一覧は、利用者がスレッドを開いたときに、深さ 20・件数 100 を上限に非同期で取得する。
- 取得の失敗（404 / 410 / タイムアウト）は KV に短期（1 時間）記録し、同じ URI の取得を繰り返さない。

### 保持と消去

- リモートの投稿は、公開から 90 日（設定 `remote_status_retention_days`）を過ぎ、かつローカルからの参照（返信・ブースト・お気に入り・ブックマーク・ピン留め・通知・ローカルの投稿を含むスレッド）がなければ、消去ジョブが消す（FR-803）。
  消すときは `status_deletions`（`origin = retention`）を記録し、URI を tombstone として残す。後から同じ投稿を取得し直すことは妨げない（tombstone は `remote` / `author` の削除だけが復活を拒む）。
- 運用者は設定 `remote_status_max_retention_days` で、リモートの投稿を保持する期間の上限を決められる。上限を設定すると、公開からその期間を過ぎたリモートの投稿は、ローカルからの参照があっても消去ジョブが消す（`origin = retention`）。既定は上限なし。ローカルの利用者の操作（返信・ブースト・お気に入り・ブックマーク・ピン留め）の行は残し、表示では対象の投稿を「削除済み」として扱う。
- 受信の原本（`received_activity_documents`）は 7 日、受信の記録（`received_activities`）は 30 日で消す。
- ローカルのアカウントとの関係がなくなった（誰もフォローしていない、投稿も参照されていない）リモートのアカウントは、プロフィールの版を最新の 1 つに縮める。アカウントの行（URI）は残す。

### この決定を見直す条件

- 連合タイムライン（FR-202）に、フォロー外の公開投稿も載せるべきだと決めた場合（選択肢 2 に近づく。リレーは v0 の非目標）
- 計測で、関係の判定（受信ごとの問い合わせ）の費用が保存の費用を上回る場合

## Consequences（影響）

- 良い影響
  - ストレージと書き込みが、ローカルの利用者の関係に比例する。シングルユーザーのインスタンスでも、巨大なインスタンスから大量の公開投稿が届いて膨らむことがない。
  - 取得の回数が、利用者の操作（スレッドを開く・検索する）に比例する。
- 悪い影響・トレードオフ
  - 連合タイムラインには、ローカルの誰かがフォローしている作者の投稿だけが載る（Mastodon の連合タイムラインも、そのサーバーが受け取った投稿だけを載せる点では同じ）。
  - 受信ごとに関係の判定が要る（`graph` と `content` の公開 API への問い合わせ）。
  - 消去後に古い投稿へのリンクを開くと、取り直しの分だけ遅い。
- 後続の作業（Issue 化する）
  - 関係の判定と、取り込まなかった `Create` のメトリクス
  - スレッドの取得ジョブ（深さと件数の上限）
  - リモート投稿の保持期間の消去ジョブ

## Pros and Cons of the Options（詳細比較・任意）

### 1. 関係のあるものだけ取り込む（推奨）

- 良い: 判断基準 1〜3 を満たす。Mastodon も、配送で届いた `Create` のうち、ローカルのフォロワー・ローカルの宛先などの関係が無いものを捨てる（`app/lib/activitypub/activity/create.rb` の `related_to_local_activity?`、2026-10-17 確認）。
- 悪い: 関係の判定と、スレッドの取得の分だけ実装が増える。

### 2. すべて取り込み、期間で消す

- 良い: 単純。連合タイムラインが充実する。
- 悪い: 量が連合先の規模に比例し、判断基準 2 に反する。巨大インスタンスのリレー的な配送で、小さなインスタンスの DB が膨らむ。

### 3. 取り込まず、表示のたびに取得する

- 良い: ストレージを最も消費しない。
- 悪い: ホームのタイムラインを作れない（fan-out-on-read でも、投稿の行が要る。ADR-0013）。表示のたびの取得で外部 HTTP が利用者の閲覧回数に比例し、判断基準 3 に反する。
