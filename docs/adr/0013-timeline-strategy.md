# ADR-0013: タイムライン: fan-out-on-read、新着の差し込み、リスト、公開タイムラインのストリーム、フォローしたハッシュタグ

- Status: Accepted
- Date: 2026-10-16
- Deciders: @rosylilly
- Issue: #13, #1016, #1866, #1906, #2570

## Decision（決定）

### 1. fan-out-on-read

- v0 は **fan-out-on-read**: `timeline` モジュールの投影（`feed_entries`・`feed_follow_edges`）を読み、UUIDv7 の `id` でキーセットページング（data-model §6）。
- 可視性フィルタ（ブロック・ミュート・公開範囲）は、方言別の sqlc のクエリと、返す直前のドメインの `CanView` の再適用で適用。
- `TimelineReader` をアプリケーション内部のインターフェイスにし、将来 `home_feed` テーブル（fan-out-on-write）や KV キャッシュに差し替え可能にする。
- 連合タイムラインはインスタンス設定で無効化可能（データ量と課金の抑制）。

### 2. 新着の差し込みの設定

- アカウントの設定（`user_preferences`、`GET` / `PATCH /api/v1/preferences`）に真偽値 `timeline_auto_insert`（「新しい投稿を自動で表示する」）を置く。端末をまたいで同じにする。
- 既定は真（§22）。偽のときは押すまで溜める（web-client.md Y7）。
- Web クライアントの設定画面で `Switch` で切り替える。

### 3. 対象のタイムライン

- ストリーミングで新しい投稿が届くタイムライン。ホーム・リスト（§13）・ローカル・連合（§17）である。
- ハッシュタグ（FR-203）・プロフィール（FR-204）の一覧は新着が届かないので対象外（開いたときに読む）。のちにストリーミングで新着が届くタイムラインが加わったら、同じ設定と §2〜§8 の規則をそのまま当てる。
- ホームを表示していない間に届いた投稿は、設定に関係なくキャッシュの先頭に入る（web-client.md §10）。

### 4. 差し込み方（設定が真で、一時停止していないとき）

- **先頭にいるか** は、フィードの最初の投稿の上端が見えているか（フィードの先頭に置いた目印を `IntersectionObserver` で見る）で決める。
- **先頭にいるとき**: 届いた投稿をすぐ先頭に差し込む。画面は先頭のままで、新しい投稿がそのまま見える。
- **先頭から離れているとき**: 届いた投稿をすぐ先頭に差し込み、差し込んだ高さだけスクロールの位置を足して、読んでいる投稿（画面の上端にかかる投稿）を同じ場所に保つ（スクロールのアンカー）。
  - CSS のスクロールアンカー（`overflow-anchor`）には頼らない。安定版の Safari（macOS・iOS）が対応していない（確認日 2026-10-22、[Can I use](https://caniuse.com/css-overflow-anchor)、[WebKit bug 171099](https://bugs.webkit.org/show_bug.cgi?id=171099)）。
    差し込む前にアンカーの投稿の位置を測り、描画の前（`useLayoutEffect`）に差の分だけスクロールを足す。ブラウザのアンカーと二重に補わないよう、フィードには `overflow-anchor: none` を付ける。
  - 差し込んだ投稿は動きなしで現れる（アニメーションを付けない）。
- **先頭から離れている間のピル**: フィードの上に `NewItemsButton`（`sticky`）を浮かせ、離れてから差し込んだ件数（「N 件の新しい投稿」）を出す。
  - 押すと先頭まで移り（`motion-safe:` のときだけ滑らかに）、タイムラインの見出し（`h1`、`tabindex="-1"`）にフォーカスを移す。押したボタンは消えるので、フォーカスの行き先を見出しにする（設定が偽のときに押したのと同じ）。
  - 利用者が自分で先頭まで戻ったら、件数を 0 に戻してピルを消す。
  - ピルは現れてもフォーカスを取らない。フィードに重なってよいのはピルだけである（LayoutTimeline）。

### 5. 一時停止（WCAG 2.2.2）

- 設定で止められることに加えて、画面の上でその場で止める仕組みを持つ。**フォーカスがフィードの中にある間と、フィードの中の文字を選択している間は差し込まない。**
  - その間に届いた投稿は、設定が偽のときと同じく溜め、`NewItemsButton` が件数を出す。押すと差し込んで見出しにフォーカスを移す（設定が偽のときと同じ）。
  - フォーカスと選択がフィードの外に出たら、溜めた投稿を §4 の規則（先頭にいるか、アンカー）で差し込む。
  - キーボードやスクリーンリーダーで投稿を読んでいる人（フォーカスがフィードの中にある）には、設定が真でも中身が動かない。マウスで読んでいる人は、アンカーで位置が動かない。
- モーダルのダイアログ（投稿のシートなど）が開いている間は、フォーカスがフィードの外のダイアログにあるので一時停止しない。差し込みは今ある投稿の要素を作り直さない（投稿の ID を key にする）ので、閉じたときにフォーカスを戻す先の要素は残る。

### 6. 支援技術への知らせ方

- 差し込んだ投稿を 1 件ずつ読ませない。フィード（`role="feed"`）はライブリージョンにしない。
- 件数は `NewItemsButton` の `role="status"`（polite）だけで知らせる。先頭から離れている間と一時停止の間にピルが件数を出すので、その変化が読み上げられる。
- 先頭にいて一時停止していない間に差し込んだ投稿は知らせない。スクリーンリーダーでフィードを読んでいる人は、フォーカスがフィードの中にあるので一時停止の側にいる（§5）。フィードの外にいる人に届くたびの読み上げを足すと、ほかの操作の読み上げを遮る。
- 差し込みで `aria-posinset` は振り直す（`aria-setsize` は分からないので `-1` のまま、Y6）。

### 7. フォーカス

- 差し込みはフォーカスを動かさず、奪わない。フォーカスのある投稿がフィードの中にあれば一時停止するので（§5）、その投稿の位置も変わらない。
- フォーカスを移すのは、利用者がピルを押したときだけ（見出しへ）。

### 8. つながらないとき（再接続・溜めた投稿が 200 件を超えた）

- 溜めた投稿が読み込み済みの投稿とつながらない（再接続で 1 ページ分の新着が見つかった、または 200 件を超えた）ときは、差し込まない。間に抜けがあるかもしれないからである。
- 先頭にいて一時停止していないときは、そのタイムラインの最初のページだけを取り直す（設定が偽のときに押したのと同じ取り直し）。読んでいる位置は先頭なので、失うものがない。
- 先頭から離れているか一時停止しているときは、取り直さずにピルを出す。押すと最初のページだけを取り直して先頭へ移り、見出しにフォーカスを移す。

### 9. Web の規則との関係

新着の差し込みの決定はこの ADR が持ち、ADR-0110 と ADR-0028 はそれに従う。

### 10. リストの持ち主と表

`timeline` がリストの表を持ち、書くのも読むのも `timeline` だけにする。
メンバーの条件（フォロー中）は `timeline` が自前で持つ `feed_follow_edges`（`active` のフォローだけ）で確かめられ、`graph` の公開 API を呼ばなくてよい。

- `lists`（リソース）: 持ち主のアカウントと作った時刻
- リストの名前（現在値）: 書記素で 1〜50。変えられる。名前の変更の履歴には意味がない（ADR-0020 規約 5）
- `list_members`（現在値）: （リスト、メンバーのアカウント）。足した時刻を持つ

表の細部（カラム・索引・分類）は data-model §4.6 に書く。リストの削除はメンバーの行を同じトランザクションで消す。持ち主のアカウントの消去（data-model §8）でリストも消える。

### 11. リストのメンバー

- メンバーにできるのは、持ち主が承認済み（`active`）でフォローしているアカウントだけ（ローカルとリモートの両方）。承認待ちのフォローの相手は足せない。
- フォローが終わったら（`graph.follow_terminated`。理由を問わない）、その相手を持ち主のすべてのリストから外す。`feed_follow_edges` の行を消す projector と同じ更新で消す。フォローし直しても戻さない。
- 移転（ADR-0089）でフォローが移転先へ移るときも、移転元のフォローの終了として外れる。移転先をリストに入れ直すのは持ち主がする。
- ブロック・ミュートはメンバーのまま残し、読み取りで除く（ホームと同じ）。
- リストはホームに影響しない。リストに入れた人の投稿もホームに出る（隠す機能はない）。

### 12. リストが見える人

- リストとメンバーは持ち主だけが読める。クライアント API は持ち主のトークンでだけ返し、ほかの利用者には存在も含めて返さない（`404`）。
- ActivityPub・プロフィール・検索・webhook のどれにも出さない。ActivityPub の `Collection` としては連合しない。リストに入れられたことは相手に通知しない。
- 管理画面とモデレーターの画面にも出さない。データのエクスポート（FR-008）には持ち主のリストを含める（Mastodon の CSV と同じ形。後続の Issue）。

### 13. リストのタイムライン

- 中身は、ホームタイムラインの規則（`ListHomeEntries` と同じ公開範囲・`direct` の宛先・ブロック・ミュート・ドメインのミュート・処分・タイムラインの言語・フォローごとの `show_boosts`）を、作者をそのリストのメンバーに限って当てたもの。持ち主自身の投稿は入れない。
- fan-out-on-read（§1）のまま、`feed_entries` を `list_members` で絞って読む。新しい投影は作らない。
- 新着の自動の差し込み（§2〜§8）はホームと同じ設定に従う。
- リアルタイム更新（FR-207）: 既存のストリームに `list_update` を足す。`data` は `{"list_id": ..., "status": Status}` で、その投稿が入る持ち主のリストごとに 1 つ送る。新しいストリームの接続は作らない（接続の数の上限を増やさない）。

### 14. リストの上限

- 1 人あたり 50 リスト、1 リストあたり 1,000 メンバー。超える作成・追加は `422`。値は定数で、設定にしない。
- 上限は、fan-out-on-read の `IN` の大きさ（ホームのフォローの数と同じ程度に収まる）と、画面で扱える数から決めた。

### 15. リストの API と画面

- クライアント API: リストの一覧・作成・名前の変更・削除、メンバーの一覧・追加・削除、あるアカウントが入っている自分のリストの一覧、リストのタイムライン（ホームと同じページング）。`pkg/mykit` にも入れる（ADR-0093）。
- Web: リストの一覧と管理の画面、リストのタイムラインの画面、プロフィールのメニューの「リストに追加」。画面の要件（L1）は `docs/architecture/web-client/screens/` に書いてから作る。

### 16. リストの決定を見直す条件

- フォローしていない人（とくにローカルの人）をリストに入れたい要望が強いとき。
- 1,000 メンバーのリストのタイムラインの読み取りが遅いと分かったとき（投影 `feed_list_entries` を足す）。

### 17. 公開タイムラインのストリームのエンドポイント

- `GET /api/v1/streaming/timelines/{timeline}`（`timeline` は `local` か `federated`）を置く。SSE で、`GET /api/v1/streaming` と同じく `fetch` と `Authorization` で読む。
- イベントは `update` の 1 種類で、`data` はそのタイムラインに入る投稿の `Status`。入る投稿は REST のローカル・連合のタイムラインと同じで、連合にはブーストを入れない。
- 何も再送しない。つなぎ直したら、クライアントはそのタイムラインの最初のページを読み直す（`GET /api/v1/streaming` と同じ約束、§8）。
- このストリームは、利用者が同時に開けるストリームの上限（429 `too-many-streams`）に数える。1 つのタブで開くのは、表示しているタイムラインの 1 本だけである。

### 18. 誰が受け取れるか

- ログインした利用者だけ。インスタンス設定 `local_timeline_visibility` / `federated_timeline_visibility` が `off` なら 404 にする（REST のタイムラインと同じ）。
- ログインしていない人には、`everyone` の設定でも届けない（401）。ログインしていない人のつながりは数を抑えられず、長く開いたつながりは Cloud Run などで費用になるからである。ログインしていない人は、開き直して読む。

### 19. 何を届けるか

- REST の `GET /api/v1/timelines/local` / `GET /api/v1/timelines/federated`（連合）が、その時点で同じ利用者に返す投稿と同じものだけを届ける。公開範囲・ブロック・ミュート・ドメインの処分・タイムラインの言語（FR-208）は、REST と同じ方針の関数で、受け取る利用者ごとに判定する。
- ローカルはこのサーバーのアカウントの公開の投稿とログインした人への `local` の投稿、連合は保存したリモートの公開の投稿も含み `local` を含まない（REST と同じ、ADR-0017）。リモートの投稿は、受信箱のジョブが保存したときに届く。

### 20. 配信の経路

- 投稿の作成（ローカルの投稿と、保存したリモートの投稿）は、ホームの新着と同じく `uow.CommitHook` から `stream.Publisher` に「公開のタイムラインの新着」の知らせを 1 つ出す（ADR-0050 の `Relay` と `Bus` をそのまま使う）。
- 各プロセスの `Hub` は、そのタイムラインのストリームを開いている購読にだけ振り分け、購読ごとに §19 の判定をしてから送る。開いている購読がないプロセスは何もしない（遅延 listen、ADR-0050）。

### 21. 公開タイムラインのクライアント

- ローカル・連合のタイムラインの画面は、表示している間だけそのストリームを開き、離れたら閉じる。届いた投稿は、ホーム・リストと同じ `NewPostsFeed` と §4〜§8 の規則（先頭にいるか・アンカー・ピル・一時停止・つながらないとき）で扱う。
- 押すまで溜めるとき（設定が偽、または一時停止の間）も、ホームと同じ「N 件の新しい投稿」のボタンを出す。

### 22. 自動の差し込みの既定

- `timeline_auto_insert` の既定を真にする。設定を一度も変えていない利用者は、ホーム・リスト・ローカル・連合のすべてで自動で差し込まれる。偽を選んだ利用者は溜める。
- WCAG 2.2.2 は、設定で止められることと、フォーカスか選択がフィードの中にある間の一時停止（§5）で満たす。支援技術でフィードを読む人は、フォーカスがフィードの中にあるので、既定が真でも中身が動かない。

### 23. 公開タイムラインのストリームを見直す条件

ログインしていない人にも届けることを決定者が求めるとき（§18 を改める）、または 1 つのタブで複数のつながりを持つことがブラウザ・ホスティングの制約になると分かったとき（今のストリームにクエリで選ばせる形に寄せる）。

### 24. フォローしたハッシュタグの投稿をホームに入れる

- 利用者はハッシュタグをフォローできる。ホームは、自分の投稿と承認済みのフォローの相手の投稿（§1）に加えて、フォローしたハッシュタグを持つ投稿を、作者をフォローしていなくても入れる。
- 入るのは、このサーバーが知っている `public` と `local` の投稿すべてである。ローカルの投稿、フォローの相手から届いた投稿、リレー（FR-411）から取り込んだ投稿、プロフィール・スレッド・検索で取得した投稿を区別しない。
  取り込みの範囲（ADR-0006 §11）は変えない。ハッシュタグをフォローしても、そのタグの投稿を外から取りに行かず、受信した `Create` を新たに保存する条件にもならない。
- 一人のサーバー（FR-811）でもフォローできる。一人のサーバーのタイムラインはホーム・ハッシュタグ・リストなので、リレーで届く公開の投稿を、ハッシュタグの単位でホームに集められる。

### 25. ハッシュタグから入る投稿の条件

- 投稿だけを入れ、ブーストは入れない。タグは投稿の現在版のもの（`feed_tag_entries`）で、編集でタグが外れればホームからも外れる。返信も入れる（ハッシュタグのタイムラインと同じ）。
- 公開範囲は `public` と `local` だけ。`unlisted` は見つけてもらう経路に載せない約束なので入れない。`private` / `direct` はフォロー・宛先の側の規則（§1、data-model §6.1）で入るものだけが入る。
- ブロック・ミュート・ドメインのミュート・タイムラインの言語（FR-208）は、ホームと同じに当てる。
- 作者の処分は、ハッシュタグのタイムライン（data-model §6.3）と同じく `public_discovery`・`visibility_ceiling_private`・`profile_view`（作者のドメインは `public_discovery`・`profile_view`）で除く。
  ホームのフォローの側は `profile_view` だけで除くが、フォローしていない作者の投稿は見つけてもらう経路なので、サイレンスされた作者を出さない。Mastodon もサイレンスされた作者の投稿をハッシュタグのフォロワーに配らない（経緯）。
- 作者をフォローしている、または自分の投稿のときは、フォローの側の行としてだけ数え、同じ投稿を 2 度返さない（エントリの `id` で重複を除く）。

### 26. 読み方

- fan-out-on-read（§1）のまま、新しい投影を作らない。ホームのクエリに、`feed_tag_follows` のタグで `feed_tag_entries (tag_id, entry_id)` を読む枝を足し、フォローの側の枝と `id` で合わせる（data-model §6.1）。
- 読み取り窓（`timeline.HomeWindow` と広げ方）はホームと同じものを両方の枝に当てる。ハッシュタグの枝だけ窓を変えない。
- ストリーム（FR-207）のホームの新着は、今と同じく接続中の利用者ごとに `HomeEntry` で読み直して決めるので、`HomeEntry` が同じ枝を読めば、フォローしたハッシュタグの新着もホームのストリームに届く。新しい知らせもストリームも作らない。
- 窓の中でも賑やかなタグで読み取りが重いと分かったときの手当ては、計測（PostgreSQL と SQLite の `EXPLAIN`）を見て決める（Open Questions）。

### 27. ハッシュタグのフォローの表と上限

- `timeline` が `feed_tag_follows`（現在値。（フォローした人、タグ）とフォローした時刻）を持ち、書くのも読むのも `timeline` だけにする（リストと同じ、§10）。フォローの履歴には意味がない（ADR-0020 規約 5）。
- タグはまだ投稿に使われていないものでもフォローできる。タグの行（`tags`）は `content` の公開 API で名前から得るか作る。
- 1 人あたり 100 タグまで。超えるフォローは `422`。値は定数で、設定にしない。上限は、ハッシュタグの枝の `IN` の大きさ（タグごとの索引の範囲の読み取りの回数）と、画面で扱える数から決めた。
- アカウントの消去（data-model §8）で本人の行を消す。`timeline.RebuildProjections` は利用者の操作の記録なので空にしない。
- クライアント API: フォロー・フォローの解除・フォローしたタグの一覧と、ハッシュタグの取得でのフォローしているかの真偽値。`pkg/mykit` にも入れる（ADR-0093）。データのエクスポート（FR-008）にも入れる（後続の Issue）。

### 28. ハッシュタグから入った投稿の表示

- ホームの応答で、フォローしたハッシュタグの枝からだけ入った投稿（作者をフォローしておらず、自分の投稿でもない）には、合ったフォロー中のタグの名前を付ける。フォローの側から入った投稿には付けない。
- Web はその投稿に「フォロー中のハッシュタグ #tag」の印を出す。なぜ知らない人の投稿があるかが分かり、そのタグのページへ移ってフォローを解ける。
- ストリームの `update` も同じ形の `Status` を送る。

### 29. フォローしたハッシュタグの決定を見直す条件

- 計測で、フォロー 1,000・フォローしたタグ 100 の利用者のホームが、今のホームの読み取りの予算に収まらないと分かったとき（投影 `home_feed` への切り替え（§1）か、ハッシュタグの枝の窓を狭める）。
- リレーの流量が増え、賑やかなタグでホームが埋まるという声が強いとき（タグごとのミュートや、ハッシュタグの枝の件数の割合の上限を考える）。

## 経緯

Mastodon はホームタイムラインを Redis 上に fan-out-on-write で構築するが、常駐ミドルウェアを要求し NFR-COST-2 に反する。小〜中規模では読み取り時の JOIN で十分な性能が出る見込みなので、fan-out-on-read を既定にした。

新着は当初、押すまで溜める形だった（ADR-0110）。新しいデザインシステム（エピック #987）の LayoutTimeline が自動の差し込みを描き、決定者が設定で選べるようにすると決めて（#1016）、はじめは既定を偽（オプトイン）、ホームだけを対象にした。基準は、読む位置とフォーカスを動かさないこと、自動で動く内容を止められること（WCAG 2.2.2、NFR-A11Y-1）、支援技術に届くたびの読み上げを浴びせないこと、端末をまたいで同じになることである。

リストは FR-211 で、決定者が v0 に入れた（#1866）。リストは他人から見えず、リスト単位でタイムラインを表示でき、フォロー解除で自動で外れ、ホームから隠す機能は持たない。キーワードフィルタは FR-209 として別に扱う。

その後、決定者がローカル・連合・リストのすべてで新着が届き、自動更新を既定でオンにすると決めた（#1906）。そこでローカル・連合のストリームを足し（基準は、見えてはいけない投稿を届けないこと、費用を増やしすぎないこと、今のストリームを切らないこと）、既定を真に変えた。一時停止があるので、支援技術の利用者の位置は既定が真でも動かない。

ハッシュタグのフォロー（§24〜§29）は #2570 で決まった。トレンドを作らない小さなサーバーで、フォローしていない人の話題に出会う道がハッシュタグのタイムライン（FR-203）を開くことしかなかった。
決定者は、ホームがフォローしたハッシュタグの投稿を作者をフォローしていなくても取り込むこと、その範囲をこのサーバーが知る `public` と `local` の投稿すべて（リレーで届いたものを含む）とすること、一人のサーバー（FR-811）でも使えることを決め、続けて入る投稿の条件・読み方・上限・印（§25〜§28）も決めた。
Mastodon（2026-11-09 に main のソースで確認）も、`public` でブーストでなくサイレンスされていない投稿だけを、タグをフォローした利用者のホームに配り（`FanOutOnWriteService#broadcastable?`）、自分の投稿・ブロック・ミュート・ドメインのブロックで除く（`FeedManager#filter_from_tags?`）。
Mastodon はタグのフォローの数に上限を持たない（`TagFollow`）が、こちらは fan-out-on-read で読み取りのたびにタグの数だけ索引を読むので、上限を置いた。

## 採らなかった案

- 押すまで溜めるだけにする: WCAG 2.2.2 を最も単純に満たし実装も今のままでよいが、流れを眺めたい利用者に毎回押させ、決定者の決定に合わない。
- 設定を端末（localStorage）に置く: サーバーの変更が要らず端末ごとに変えられるが、端末ごとに選び直すことになり、ほかの表示の設定がアカウントにあるのと揃わない。
- `graph` がリストを持ち、`timeline` は投影を持つ: リストを「関係」として扱えるが、読み取りのために投影を写す必要があり、表が倍になる。
- リストに誰でも入れられる: フォローせずに追えるが、リモートの未フォローの投稿はこのサーバーに届かないことが多く、「入れたのに出ない」が起きる。ローカルだけ許すと規則が 2 つになる。
- リストを ActivityPub の `Collection` として連合する: 公開のリストを共有できるが、「他人から見えない」に反する。
- 今の `GET /api/v1/streaming` にタイムラインを選ぶクエリを足す: タブのつながりは 1 本のままだが、移るたびにつなぎ直し、その間の通知・お知らせを取り逃す（再送はない）。
- ログインした全員にローカル・連合の新着を常に届ける: クライアントは楽だが、見ていない人にも連合の全投稿を送り、通信と判定の負荷が利用者の数に比例する。
- ローカル・連合の最初のページをポーリングする: サーバーの変更が要らずログインしていない人にも使えるが、新着が遅れ、誰もいない時間も読み直しが続く。

- フォローしたハッシュタグを、受信した `Create` を保存する条件に足す: ハッシュタグの投稿が増えるが、保存の量が連合先の規模とタグの人気に比例し、ADR-0006 §11 の「ローカルの関係に比例させる」に反する。決定者はこのサーバーが知る投稿に限った。
- フォローしたハッシュタグの投稿を、投稿の時点で閲覧者ごとの表に書く（Mastodon の fan-out-on-write）: 読み取りは軽いが、書き込みがタグのフォロワーの数に比例し、ホームだけ別の仕組みになる（§1）。
- ハッシュタグから入った投稿をホームではなく別のタブ（フォローしたタグのタイムライン）に出す: ホームの規則が今のままだが、決定者の決定（ホームに入れる）に合わず、開くまで見えない。
- ハッシュタグの枝に `unlisted` も入れる: 投稿は増えるが、作者が見つけてもらう経路から外した投稿を知らない人のホームに出す。
- ハッシュタグの枝の処分をホームと同じ `profile_view` だけにする: 規則が 1 つになるが、サイレンスされた作者の投稿がフォローしていない人のホームに出て、サイレンスの意味が薄れる。
- フォローしたタグの数に上限を置かない（Mastodon）: 使い手の自由が大きいが、読み取りの費用が上限なく増える。

## Consequences（影響）

- 追加インフラ不要。書き込みが軽い。
- フォロー数が多い利用者で読み取りが重くなる。Neon 等の従量課金 DB では読み取り量が費用に効くため、計測して閾値を決める（Open Questions）。
- 流れを眺めたい利用者は、押さずに新着を見られる。読んでいる位置は動かず、フォーカスや選択がフィードの中にある間は動かない。
- スクロールの補正をクライアントで行うので、投稿の高さが後から変わる（画像の読み込み、CW の開閉）と、補正がずれることがある。メディアの派生が持つ `width` / `height`（ADR-0005）で、画像の枠の高さを読み込みの前に決めることで抑える。既定が真なので、当たる人は多い。
- 先頭にいてフィードの外にいる支援技術の利用者には、差し込みが知らされない。
- 状態が 3 つ（溜める・差し込む・一時停止）になり、テストの組が増える。開いたまま長くいると、キャッシュの最初のページが伸び続ける。
- リストは持ち主だけの表で、連合にも他人の API にも出ないので、漏れる経路がない。新しい投影を作らず、ホームの読み取りの規則をそのまま使うので、公開範囲などの規則がずれない。
- フォローを解除するとリストから外れ、フォローし直しても戻らない。うっかり解除すると入れ直しが要る。リストに入れた人の投稿はホームとリストの両方に出る。
- ストリームの `update` と `list_update` の両方で同じ投稿が届くので、クライアントは画面に合う方だけを使う。
- 見ていないタイムラインの新着は送らないので、モバイルの通信と、ほかの利用者のつながりの費用が増えない。ローカル・連合を開いている間はつながりが 1 本増え、上限に数えるので、多くのタブを開く人は先に上限に当たる。
- 投稿 1 件ごとに、開いている購読の数だけ公開範囲・ブロック・ミュートを判定する。大きなサーバーの連合のタイムラインでは、プロセスの負荷が購読の数に比例して増える。
- ログインしていない人のローカル・連合は、自動では流れない。
- 後続（Issue にする）: データのエクスポート（FR-008）にリストを足す。
- フォローしたハッシュタグで、トレンドのない小さなサーバー・一人のサーバーでも、フォローしていない人の投稿に出会える。量はリレーへの参加と取り込みの上限（ADR-0006 §20）で頭打ちになり、保存と外部 HTTP は増えない。
- ホームの読み取りが、フォローしたタグの数だけ索引の範囲を読む分だけ重くなる。賑やかなタグをフォローすると、ホームがそのタグの投稿で埋まる。
- ホームに入る作者の規則が「フォローの相手と自分」から「フォローの相手、自分、フォローしたタグの投稿の作者」になり、ホームに知らない人の投稿が出る。印（§28）で理由を示す。
- 後続（Issue にする）: データのエクスポート（FR-008）にフォローしたハッシュタグを足す。

## Open Questions / 要検証

- フォロー 1,000 / 投稿 100 万件規模でのクエリ計画と rows read の測定（SQLite / PG）
- ブラウザの同じオリジンへの同時接続の上限（HTTP/1.1 で 6 本）と、HTTP/2 で多重化されるときの扱い（要検証。Cloud Run と、自前の VM でのリバースプロキシの既定の設定）。
- 大きなサーバーの連合のタイムラインで、購読ごとの判定がどこまで持つか。必要なら、同じ判定の結果になる購読（ブロック・ミュートのない利用者）をまとめる最適化を後で検討する。
- ハッシュタグの枝を足したホームのクエリ計画と rows read（PostgreSQL と SQLite の `EXPLAIN`。フォロー 1,000・タグ 100・賑やかなタグ）。窓の中でも予算に収まらないときに、ハッシュタグの枝の窓を狭める・件数を限る・投影を作るのどれにするかは、この計測（#2571）で決める。
