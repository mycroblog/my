# ADR-0114: L4 の課題テストを nightly で回す

- Status: Accepted
- Date: 2026-10-28
- Deciders: @rosylilly
- Issue: #1674

## Context（背景・課題）

ADR-0110 §7 は、UI を変える issue のエージェントが PR の前に L4 の課題テストを行うと決めた。
L4 は、画面の要件（L1）の作業を、エージェントが Playwright の ARIA スナップショットだけを手がかりに行い、手数・戻った回数・lostness を測るものである。

一方、並列の作業（[workflow §9](../agents/workflow.md#9-parallel-batches)）では、PR ごとに Web の E2E を回さない。
PR が同じ領域を変え続けるので、PR ごとの実行は main が持たない状態を確かめることになるからである。
L4 もアプリを動かすので同じ理由が当たり、最初の並列の作業（#1643）では L4 を測れず、最短の手順から計算した値を PR に書くことになった。
画面の作り直し（#1653 以降）では L4 が本番になるので、いつどこで測るかを決める必要がある。

## Decision Drivers（判断基準）

1. 並列の作業の速さを落とさないこと（workflow §9 と同じ考え方）。
2. 測る対象が、実際に main にある画面であること。
3. 迷いやすい画面が、人が見る前に issue になること（ADR-0110 の L5 の前に問題を拾う）。
4. 費用に上限があること。

## Considered Options（選択肢）

1. **PR の前にエージェントが手元で測る**（ADR-0110 §7 のまま）。並列の作業でも L4 だけは回す。
2. **nightly で main に対して測る**。PR では、L1 の作業ごとの最短の手順 R を書くだけにする。
3. **決まった手順を E2E に書く**。作業ごとに最短の手順を Playwright の spec にし、手順の数が増えたら失敗にする。

## Decision（決定）

**選択肢 2 を採る。** 決定者が選んだ（「L4 は nightly で回す」）。

- **PR の側**: UI を変える PR は、変えた画面の L1 の作業ごとに最短の手順 R を書き、4 つの観点で変更を見直す。L4 は測らない。
- **nightly の側**: nightly の workflow に、L4 のジョブを足す。
  - 対象は、前回の成功した実行から、L1 の文書か、その画面の `context-map.yaml` の範囲が変わった画面の作業である。1 晩に測る作業の数に上限を設ける（実装で決め、workflow のコメントに書く）。
  - E2E と同じフィクスチャで `my serve` を起動し、エージェント（Claude Code を非対話で動かす）が、Playwright の ARIA スナップショットだけを手がかりに作業を行う。
    スクリーンショットは渡さない。結果は作業ごとの手数・戻った回数・lostness を JSON の成果物として残す。
  - lostness が 0.4 を超えた作業は、画面ごとに 1 つの issue（同じ題名があれば追記）にまとめる。issue には作業・たどった道筋・L1 の最短の手順を書く。
  - API キーは、`main` だけが読める GitHub の environment に置く（ADR-0112 の Cloudflare のトークンと同じ置き方）。
- ADR-0110 §7 のうち、「PR の前に行い、結果を PR に書く」と「nightly への組み込みは別に決める」を置き換える。lostness の式としきい値 0.4 はそのままである。

### 見直す条件

- nightly の L4 の issue が、同じ画面で何晩も続けて出る（PR の時点で拾うべき問題が多い）場合。単独の作業の PR だけ、手元で L4 を回す形を足す。
- 費用が、上限を設けても運用の目標に合わない場合。対象を、L1 が変わった画面だけに絞る。

## Consequences（影響）

- 良い影響: 並列の作業の速さが落ちない。測るのは main の実際の画面で、PR が重なった結果も含む。
- 良い影響: 迷いやすさが、決定者の批評（L5）の前に issue として並ぶ。
- 悪い影響: 問題が見つかるのはマージの翌日で、直すのは別の PR になる。
- 悪い影響: nightly に LLM の API の費用と、API キーという外部の依存が増える。エージェントの振る舞いはぶれるので、1 晩の結果だけで判断せず、続けて出る問題を重く見る。
- 後続の作業: nightly の L4 のジョブと API キーの environment（#1674。キーは決定者が用意する）、workflow §5 と web-client §21 の書き換え（この ADR の PR で行う）。

## Pros and Cons of the Options（詳細比較・任意）

- **選択肢 1**: 問題をマージの前に拾え、PR の作者が直せる。ただし並列の作業ではアプリの起動と作業の実行が PR ごとに要り、workflow §9 が E2E を外した理由（main にない状態を測る、時間と費用）がそのまま当たる。
- **選択肢 3**: 決定的で費用がなく、PR でも回せる。ただし決まった道筋をなぞるだけなので、利用者が迷うかどうか（lostness）を測れない。手順の数の回帰を防ぐ検査としては、L3 に足せる。
