# ADR-0149: 全文検索

- Status: Accepted
- Date: 2026-11-05
- Deciders: @rosylilly
- Issue: #2246, #2257

## Decision（決定）

要件は FR-309 である。覆る条件は §17 に書く。

### 1. 結論

- 投稿の全文検索を、運営者が選ぶ検索エンジンの上に置く。既定は `none` で、全文検索は使えない。
- データベースはどの方言でも検索のバックエンドにしない。全文検索の負荷を、ほかのすべてを支える DB に載せないためである。追加のサービスを置きたくないサーバーは `none` のままにする。
- DB を正とする。索引はいつでも捨てて作り直せる。バックエンドは投稿の ID だけを返し、`my` が DB から読み直して閲覧の方針を通すので、索引が遅れても見せてはいけない投稿は出ない。
- `unlisted`・`private`・`direct` はどの設定でも索引に入れない。`public` と `local` のどちらを入れるかは運営者が選び、`indexable = true` のアカウントだけを候補にする。
- 検索できるのはログイン中の利用者だけで、API 全体より厳しいレート制限を掛ける。
- 最初のバックエンドは今は選ばない。ポート・`none`・索引のジョブ・API・再構築・Web クライアントを `v0.1.0` までに作り、バックエンドの無い間サーバーは `none` で動く。

### 2. `none` は何も動かさない

`search = none`（既定）のサーバーでは次のとおりにする。

- 検索エンジンへの接続を開かない。索引のジョブを積まない（§7 の projector を登録しない）。検索のための行を DB に書かない。
- インスタンス情報が全文検索を使えないと伝え、クライアントは入口を出さない（§9）。
- アカウントとハッシュタグの検索（FR-306、FR-307）は DB の `account_search_terms` と `tag_usage` で動き、`search` の値に関わらず変わらない。

### 3. バックエンドの選択

- 設定キー `search` を `queue` と同じ形で `internal/platform/config/schema.go` に宣言する。`v0.1.0` の時点の選択肢は `none` だけである。
- 任意のバックエンドごとにビルドタグを 1 つ持つ。`internal/platform` の `adapters_search_<name>.go` と `adapters_no_search_<name>.go`（タグ `no_search_<name>`）の対で、外したバックエンドは `config.ExcludedError` で起動を止める。既存の `no_voice_livekit` と同じ形である。
- バックエンドの宛先は運営者が設定したものなので、SSRF を防ぐ `kernel.HTTPClient` ではなくアダプタ自身の `*http.Client` を使う（`internal/adapter/voice/livekit` と同じ）。
- 偽のバックエンドは `none` と別に作る。`internal/adapter/search/fake` に置き、Go のテストはこれを注入する。Web の E2E のサーバーはビルドタグ `e2e_fakes` の `search = fake` で使い、`profile = development` 以外では起動を拒む（`payments = fake` と同じ形、ADR-0015 §6）。製品のビルドには入らない。

### 4. ポート

`internal/app/search` にモジュールとポートを置く。文書と操作は次のものだけにする。

- 文書: 投稿の ID、作者のアカウント ID、公開範囲、言語（`status_revisions.language`）、公開日時、検索する文字列（本文・内容の警告・代替テキスト）。
- 操作: 文書の置き換え（無ければ追加）、ID での削除、作者での一括削除、公開範囲での一括削除、全消去、検索。
- 検索は平文の問い合わせ・カーソル・件数を受け取り、投稿の ID の列と次のカーソルを返す。本文・HTML・ハイライト・スコアを返さない。カーソルはバックエンドごとの不透明な文字列である。
- 問い合わせはエンジンの問い合わせ言語として解釈させない（演算子を渡さない）。語の間は AND とする。
- 並びは新しい投稿から古い投稿へ、ID の順（UUIDv7 は時刻順）とする。関連度の並びはエンジンごとに結果が変わり、ページングの安定を契約にしにくいので最初の版では持たない。
- コントラクトテストは `pkg/testkit` の `testkit.SearchIndexContract` に置く（追加・置き換え・削除・作者での削除・公開範囲での削除・全消去・ID だけを返すこと・ページング）。日本語の扱いは §13 のとおり。

### 5. 何を索引に入れるか

適格の規則を `internal/app/search` の関数 1 つに置き、§7 のジョブ、§8 の読み取り、§10 の再構築が同じものを使う。投稿は次のすべてを満たすときだけ適格である。

1. 削除されていない。
2. 実効の公開範囲（`content.EffectiveVisibility`）が `public` か `local` で、インスタンス設定 `search_visibilities` に含まれる。`unlisted`・`private`・`direct` は設定で変えられない共通の規則で拒む。`unlisted` の作者は一覧に載せないことを選んだからである。
3. 作者のプロフィールが `indexable = true` である。
4. 作者に `profile_view` と `public_discovery` の制限が（アカウントとドメインのどちらにも）無い。ハッシュタグのタイムラインと同じ基準である。

設定は次のとおりにする。

- `search_visibilities` は `public`・`local`・`public,local` のどれかで、既定は `public`。空は受け付けない（止めるのは `search = none` の役目）。`instance_setting_revisions` のキーで、権限は `manage_settings`、変更は監査ログに残す。`search = none` の管理画面には出さない。
- 索引に入れる文字列は本文・内容の警告・代替テキストで、いまの版だけである。投票の選択肢・プロフィール・過去の版は入れない。ブースト（`boosts`）は投稿ではないので入れない。
- リモートの投稿は `public` だけが該当する。`local` はローカルの投稿にしかなく（`statuses` の CHECK）、リモートの `my` からはフォロワー限定として届く。ADR-0057 §6 の `indexable = true` のリモートのアカウントの公開投稿という範囲のままである。
- 設定を狭めると、外れた公開範囲の文書を消す。広げても、過去の投稿は運営者が再構築するまで見つからない（新しい投稿だけが入る）。設定の画面がそのことを言う。
- 閲覧者自身の投稿やブックマークした投稿にも対象を広げない。これで `private` と `direct` は索引に一切入らない。
- 全文検索は `search_indexing` に従わない。`search_indexing` は外部のクローラーへの表明で（ADR-0057 §1）、自分のサーバーの全文検索を動かす設定は `search` と `search_visibilities` である。

### 6. `indexable` の範囲

`indexable` は、その設定が含む公開範囲に及ぶ。`search_visibilities` が `local` を含むサーバーでは、`indexable = true` の作者の `local` 投稿もこのサーバーの全文検索に載る。

- 設定の画面の文言は、そのサーバーの `search_visibilities` に合わせて何が載るかを言う（§16）。
- 外部の検索エンジンへの表明は変えない。`local` の投稿のページの扱いは ADR-0057 §3 の表のままである。
- 連合での `indexable` の意味は変えない。Actor で送る値は Mastodon の定義のまま公開投稿についてのもので、`local` の投稿は `as:Public` を持たない（ADR-0017 §2）。
- 運営者が `local` を足しても、すでに `indexable = true` の作者に選び直しを求めない。設定の画面の文言で伝え、運営者の文書で、足す前に利用者へ知らせることを勧める。
- `indexable` を切ると、その作者の文書をすべて消す。入れると、その作者の過去の適格な投稿を入れ直す（§7）。これは作者本人の選択なので、運営者の設定の拡大（§5 の再構築が要る）とは扱いを分ける。

### 7. 索引を投稿に追随させる

`platform` が `search` の値が `none` でないときだけ `uow.Projectors` に projector を登録し、事実のトランザクションの中で outbox からジョブを積む。投稿のモジュールは `search` を知らない。ジョブは文字列を持たず ID だけを持ち、走るときに現在の状態を読むので、繰り返しと順序の入れ替わりで結果が変わらない。

| ジョブ | 引数 | 積む事実 | すること |
| --- | --- | --- | --- |
| `search.sync_status` | 投稿の ID | `content.status_created`・`status_revised`・`status_deleted`（`ByAccountErasure` を除く） | 適格なら置き換え、そうでなければ削除 |
| `search.sync_author` | アカウントの ID | `account.profile_revised`・`remote_actor_fetched`（`indexable` が変わったとき）、`account.lifecycle_event_recorded`、`moderation.account_restrictions_changed`・`account_restrictions_expired`、§11 の消去 | 作者が適格でなければ作者で一括削除。適格ならその作者の投稿を一定件数ずつカーソルで辿って同期 |
| `search.sync_domain` | ドメイン | `moderation.domain_restrictions_changed`・`domain_restrictions_expired` | そのドメインの作者ごとに `search.sync_author` を積む（`moderation.sever_domain` と同じ分割） |
| `search.narrow` | 公開範囲 | `instance.setting_revised`（`search_visibilities` が狭まったとき） | 公開範囲で一括削除 |
| `search.rebuild` | カーソル | `my search rebuild`（§10） | 全投稿を一定件数ずつ同期 |

- **公開範囲の変化**: `statuses.visibility` は投稿の後に変わらない。後から変わるのは実効の公開範囲だけで、それは処分（`visibility_ceiling_private`）から来るので `search.sync_author` が扱う。添付済みのメディアの代替テキストも直接は変わらない（`ErrMediaAttached`）。変わるのは版のときだけで、`status_revised` が扱う。
- **処分の期限切れ**: 定期ジョブ `moderation.expire_restrictions` は、期限の切れたアカウントとドメインの処分の行を消すトランザクションで、行を消したアカウントごとに `moderation.account_restrictions_expired`、ドメインごとに `moderation.domain_restrictions_expired` を出す。projector はそれぞれ `search.sync_author` と `search.sync_domain` を積むので、処分で索引から消した投稿は期限の後に戻る。期限からそのジョブが走るまでの間も読み取りは期限を見ているので、この遅れは見つからない投稿になるだけで、見せてはいけない投稿は出ない。
- **書いた後に読み直す**: `search.sync_status` は文書を書いた後にもう一度 DB を読み、適格でなくなっているか版が変わっていれば、もう一度同期する。2 つのジョブが同時に走り、古い状態を読んだほうが後から書く競合を、エンジンの版の機能に頼らずに閉じる。削除のジョブはその削除のコミットの後に走るので、読み直しの前に書いた文書は必ず消える。
- **`none` でのジョブの種類**: 種類はどの設定でも登録し、`none` のハンドラーは何もせず成功する。ハンドラーの無い種類は失敗を重ねて dead job になり（`docs/reference/jobs.md`）、`worker_job_types` に書いた `search.*` は一致する種類が無いと起動を止めるからである。`voice.apply` と同じ扱いで、`none` では積まれないので、走るのは切り替える前に積まれたものだけである。
- **遅いバックエンド**: バックエンドの呼び出しはトランザクションの外で行い、短い期限を切り、失敗は既定の待ち時間で再試行する。既定のワーカーは 1 プロセス 1 ジョブで期限の順に走るので、期限を切っても検索のジョブが `federation.inbox` の時間を使う。完全に分けるには `worker_job_types` で分けるか、`queue` のルート（SQS・Cloud Tasks）で別のキューに送る。運営者の文書に、検索を入れるサーバーの構成として書く。

### 8. 結果に通す閲覧の方針

- 閲覧の判定は `content.CanView` だけで行い、文脈 `ContextSearch` を足す。`contextAdmits` は `ViewerLocal` だけを通し（未ログインは方針の段階で閉じる）、`contextShows` はハッシュタグと同じく `public` / `local` で作者に `public_discovery` がないものだけを通す。`ContextStatus` を使うと `unlisted` が通るので使わない。
- 作者本人でも `ContextSearch` の規則の外には広げない。`Viewer.Moderator` は `ContextStatus` と `ContextProfile` にしか効かないので、モデレーターの見え方も広がらない。
- バックエンドが返した ID ごとに DB から投稿を読み、次の順で落とす: 投稿が無いか削除済み → §5 の適格の規則（設定から外れた公開範囲、`indexable = false`）→ `CanView` → ミュート・ドメインのミュート（FR-304）。タイムラインの `timeline.Service` の `Facts` と `canView` の組み立てを再利用し、別の判定を書かない。
- したがって索引の遅れは文書の消去が遅れるだけで、削除・非表示・`private` になった投稿を見せない。バックエンドの HTML とハイライトは受け取らないので描画しようがなく、結果の描画はタイムラインと同じ `Status` である。
- ページングは `timeline.Service.page` と同じ約束にする。上限まで読んで次のカーソルを返し、落とした分だけページは短くなる。空のページに次のカーソルが付くことがあり、クライアントはカーソルの有無で続きを判断する。

### 9. API

- `GET /api/v1/statuses/search`（`searchStatuses`）: `q`（1〜200 文字）、`cursor`、`limit`。`GET /accounts/search` と `GET /tags/search` にそろえる。
- 認可は `security: oauth2: ["read:statuses"]` で、匿名を入れない。未ログインは `guard` が 401 にする。ADR-0090 §2 のグラントに `client_credentials` が無いのでトークンはすべて利用者のもので、スコープは `searchTags` と同じ `read:statuses` である。`direct` は §5 で出ないので `read:direct` は関係しない。`x-first-party-only` にはせず、スコープを持つサードパーティのアプリも使える。
- レート制限は操作ごとの制限にする（`docs/architecture/client-api.md` の操作ごとの制限）。`clientapi` に `SearchLimit = kernel.Limit{Name: "api.search", Max: 30, Window: 5 * time.Minute}` を置き、ハンドラーが `Server.LimitProblem` を呼ぶ。キーはアカウントで、`AccountLimit` に加えて数える。ADR-0019 §5 の表に載らない制限を ADR-0090 §7 が足すのと同じく、この ADR が足す。
- 使えるかどうかはインスタンス情報（`Instance`）の必須の項目 `full_text_search`（使えるか、対象の公開範囲）で読む。`voice_enabled` と同じ置き場所で、失敗する検索を試さなくても分かる。
- `search = none` では 404 と専用の問題の型を返し、何も問い合わせない。バックエンドの失敗は 503 と専用の問題の型で返し、ほかの API に影響しない。
- 問い合わせの方法は `GET` で、問い合わせは URL に載る。
- 問い合わせをログとトレースに書かない。`http request` の行はパスとルートだけを持ち、クエリ文字列を持たない（`internal/platform/http.go`）。トレースの属性とエラーの報告にも入れない。`Cache-Control` は `private, no-store` にする。リバースプロキシ・CDN・実行基盤のログが URL を残す可能性と、そのログの設定は運営者の文書に書く（§16）。

### 10. 再構築

- `my search rebuild` は DB から索引を作り直す。一定件数ずつのカーソル付きのジョブ（`search.rebuild`）で、再開でき、既定の速さで DB と通常のジョブを乱さない。進み具合と失敗は `search` モジュールの表に持ち、`my search status` で読む。`none` ではその旨を言って何もしない。
- 既定は最初に索引を全消去してから入れ直す。これで、削除が届かなかった文書（§12）や、DB をバックアップから戻したときに索引にだけ残る文書が消える。中断からの再開はもう一度消さない。2 回走らせても同じ索引になる。
- `my search rebuild --keep` は消さずに入れ直す。設定を広げたとき（§5）に検索を止めずに過去の投稿を足すためのもので、残った文書は消えない。
- 再構築の間も §7 のジョブは走る。どちらも現在の状態を読むので、途中の投稿と削除は正しく終わる。
- `my search clear` は索引を全消去する。`none` に切り替える前に使う（§12）。

### 11. 削除と消去

ADR-0058 と [data-model §8](../architecture/data-model/08-deletion-and-purge.md#8-削除と消去) に対して、索引は投影と同じ位置に置く。消去の順序はイベントを記録し、表示から即時に外し、非同期に物理削除する形のままで、表示から外すのは §8 の読み取りが担う。索引が持つのは DB の写しで、モデレーションの記録ではない。

- **投稿の削除**: 本人の削除、自動削除（FR-118）、リモート投稿の保持期間（FR-803）、リモートの `Delete` はどれも `status_deletions` と `content.status_deleted` を通るので `search.sync_status` が消す。
- **アカウントの削除**: `account_lifecycle_events` の `deleted`・`deactivated`・`remote_deleted` で `search.sync_author` が作者の文書を消す。7 日の消去ジョブを待たない。`reactivated` では同じジョブが入れ直すので、410 の聞き直しで戻った Actor も元に戻る。
- **消去ジョブ**: `account.erase_deleted` の `DataEraser` に `search` を足す。`EraseAccountData` は自分のトランザクションで `search.sync_author` を積むだけで、エンジンを直接呼ばない。呼ぶと、任意のサービスの障害が全アカウントの消去を止めるからである。再試行の尽きた dead job は運営者に見え、再構築で解消できる。
- **保全**: `retention_holds` は消去ジョブだけを止める。保全の対象の記録は DB に残るので、索引から消す `search.sync_author` は保全で止めない。通報や処分が指す投稿（`StatusRetained`）も、削除が記録された時点で適格でなくなる。
- **バックアップ**: 索引は投稿の本文を持つ。エンジンのスナップショットは DB のバックアップと同じ注意が要り、削除の後もそこに残る。運営者の文書に書く。
- **サービスのクローズ**（ADR-0088）: サーバーはデータを自分では消さないので、DB・Blob と同じく運営者が索引を破棄する。

### 12. `none` が残す索引

バックエンドから `none` に切り替えると、接続が無くなるので `my` はその索引を消せず、その後の削除も届かない。読み取りには出ないが、消したはずの本文がエンジンに残る。また `none` は何も書かないので、切り替えて戻ったことをサーバーは知ることができない。

- `none` に切り替える前に `my search clear` を実行する。切り替えた後なら、運営者がエンジンの側で索引を消す。運営者の文書の手順に書く。別のバックエンドへの切り替えでも、前のエンジンについて同じである。
- `none` の間に積まれるジョブは無く、切り替えの前のジョブは §7 のとおり何もせず終わる。
- `none` からバックエンドに戻すときは `my search rebuild`（全消去する既定）を使う。これで `none` の間の削除が索引に反映される。`--keep` はこの場面では使わない。
- 戻してから再構築が終わるまで、検索は使えるが結果は足りない。正しさは §8 が保つので、ここでは止めない。

### 13. CJK と NFR-I18N-6

- 日本語をどこまで探せるかはバックエンドごとに決める。コントラクトテストは日本語で見つかることを要求しない。バックエンドの文書が、何ができて何が要るか（解析器・プラグインなど）を書く。
- コントラクトテストが要求するのは、日本語の文書を壊さずに置き換え・削除でき、日本語の問い合わせで失敗しないことである。見つかるかどうかは問わない。
- 文書の `language` は渡すので、バックエンドは言語ごとに解析を変えられる。
- NFR-I18N-6 のとおり、全文検索については、バックエンドごとに決めてその文書に書くことが方針である。アカウントとタグは ADR-0009 §7 のままである。

### 14. `v0.1.0` までに作るものと、バックエンドが後で要るもの

`v0.1.0` までに作る: ポートと `none`（#2247）、索引のジョブ（#2248）、API（#2249）、再構築（#2250）、Web クライアント（#2251）。偽のバックエンドで検査する。`search_visibilities`・進み具合の表・ジョブの種類・API・文言は全部ここで入るので、`v0.1.0` の後にバックエンドを足しても、スキーマの変更（ADR-0023）も API の変更も要らない。

バックエンドを足すときに要るものはこれだけである。

- `internal/adapter/search/<name>` のアダプタ。`testkit.SearchIndexContract` を通し、`CGO_ENABLED=0` で作れる。
- `search` の選択肢と `search_<name>_*` の設定。
- `adapters_search_<name>.go` と `adapters_no_search_<name>.go` の対、`docs/reference/build-tags.md`、`tools/agentkit/context-map.yaml` の項目。
- 索引の定義の作成と更新。定義を変えるときに再構築が要るなら、その手順。
- `docs/operations/` のバックエンドの文書: 設定、規模の目安、日本語の扱い（§13）。

ポート・ジョブ・API・再構築・Web クライアント・文言は変えない。

### 15. ライセンス

検索エンジンは運営者が動かすもので `my` が配布しない。エンジンのサーバーのライセンスは運営者の判断の対象である。AGPL との両立の規則は `my` がリンクするものにだけ掛かるので、アダプタは素の HTTP か、両立するライセンスのクライアントライブラリを使う。

## 経緯

全文検索は v0 の非目標で（`docs/requirements/00-vision.md`）、FR-306 と FR-307 は前方一致と名前の検索だけを扱い、ADR-0057 §6 が将来の検索の対象を `indexable = true` のリモートのアカウントの公開投稿とだけ決めていた（#2246）。問いは、望まないサーバーに費用も追加のサービスも負わせずに投稿の全文検索を出せるかである（NFR-COST-2、G3 の差し替え可能性）。

バックエンドを選べること、既定を `none` にすること、DB を使わず検索エンジンに限ることを先に決めた。次に対象を、`public` に固定するのではなく、`local` を中心に運営するサーバーを考えて運営者の設定に委ね、`unlisted` の作者の選択だけは共通の規則で守る形にした。`indexable` の説明はこの拡大に合わせて変える。

CJK は、すべてのバックエンドに日本語の 2 文字以上の部分一致を求める案から、バックエンドごとに決めて文書に書く形に変えた。バックエンドは今は選ばず、中核だけを `v0.1.0` までに作る。作者への再確認はせず文言と運営者への勧めで足りるとし、問い合わせは `GET` のまま前段のログを文書にする形で決めた。

コードと突き合わせた結果、`statuses.visibility` が不変で実効の公開範囲だけが変わること、処分の期限切れにイベントが無かったこと（期限切れのイベントを足した）、ハンドラーの無いジョブが dead job になること、既定のワーカーが 1 ジョブずつであること、`none` が索引に手を出せないことが分かり、それぞれ §7、§12 に反映した。

## 採らなかった案

- DB の全文検索（FTS5、`pg_trgm`）をバックエンドの 1 つにする: 追加のサービスが要らず小さなサーバーに一番安いが、検索の負荷がほかのすべてを支える DB に載り、方言ごとに 2 実装が要る。
- 既定で何かの検索を有効にする: 導入直後に使えるが、費用やサービスを望まないサーバーに負わせる。
- 閲覧者自身の投稿とブックマークに対象を広げる: 自分の投稿を探す用途に一番効くが、`private` と `direct` が索引に入り、§1 の単純さを失い漏えいの範囲が広がる。最初の版では採らない。
- すべてのバックエンドに日本語の部分一致を要求する: 日本語の利用者に保証を与えるが、エンジンの選択を狭め、まだ選んでいないバックエンドの条件を先に固定する。
- Elasticsearch を最初のバックエンドに決める: ポートを本物で早く確かめられるが、`v0.1.0` の条件を増やす。残りは偽のバックエンドで検査できる。
- バックエンドが本文やハイライトを返し、それを描画する: 速くハイライトも出せるが、遅れた索引が削除済みの本文を見せ、エンジン由来の HTML を描画することになる。
- 閲覧者ごとの条件をエンジンの問い合わせに持たせる: ページが欠けないが、方針の再実装で NFR-SEC-4 の単一の関数に反する。
- ジョブに本文を載せる: DB を読まずに済むが、順序の入れ替わりで古い本文が残り、キューに本文が残る。
- エンジンの版の機能で競合を防ぐ: 確実だが、対応の有無がエンジンに依存し（要検証）、§7 の読み直しのほうがエンジンを問わない。
- 消去ジョブから直接エンジンを呼ぶ: `account_erasures` の時点で消え終わっていると言えるが、任意のサービスの障害が全アカウントの消去を止める。
- `none` でジョブの種類を登録しない: 何も動かさないという形に素直だが、切り替え前のジョブが dead job になり、`worker_job_types` の設定で起動が止まる。
- `none` の間の削除を DB に記録し、戻したときに反映する: 再構築なしで戻れるが、`none` が保存先を持つことになる。
- `search_visibilities` を設定ファイルに置く: DB を使わずに済むが、管理画面と監査ログから外れ、利用者に見せる文言が設定に追従できない。
- 運営者が `local` を足したときに `indexable = true` の作者へ確認し直す: 作者の選択が最も確かだが、利用者への通知と確認の状態が増え、答えない作者を決める規則が要る。
- `POST` で問い合わせを本文に入れる: 前段のログに URL として残らないが、ほかの検索の API と形が違い、読み取りに `POST` を使うことになる。

## Consequences（影響）

- 良い: 既定のサーバーの費用も構成も増えない。アカウントとハッシュタグの検索は変わらない。
- 良い: 索引の遅れや破損は見つからない投稿にしかならず、見せてはいけない投稿は構造的に出ない。
- 良い: バックエンドの追加は §14 のものだけで済む。
- 悪い: バックエンドの無い間、API と画面は偽のバックエンドでしか動かず、`v0.1.0` の利用者は使えない。本物のエンジンで確かめるまで §4 のポートの形は未検証である。
- 悪い: 新しい投稿から古い投稿への並びは、関連の高い古い投稿を見つけにくい。著者や日付の絞り込みも無い。
- 悪い: 結果のページが短くなったり空になったりする。クライアントはカーソルで続ける。
- 悪い: `indexable_default` の既定は `false` なので、有効にした直後のサーバーは検索してもほとんど見つからない。既存の利用者は自分で選ぶ必要がある。
- 悪い: すでに `indexable = true` の作者は、運営者が `local` を足して再構築すると、選び直さないまま過去の `local` 投稿が載る。伝えるのは §6 の文言と運営者への勧めだけである。
- 悪い: 日本語の探しやすさはサーバーのバックエンドで変わり、クライアントには分からない。
- 悪い: `none` に切り替えた後の索引の始末は運営者の手順に頼り、サーバーは検査できない。`--keep` の再構築は消し残しを消さない。
- 悪い: ワーカーを分けない小さな構成では、検索のジョブが連合の処理と時間を分け合う。
- 悪い: 問い合わせは URL に載るので、前段のログに残りうる。
- 後続: §16 の変更と #2247〜#2254（#2252〜#2254 は `v0.1.0` の後）。

## Open Questions / 要検証

- Elasticsearch・OpenSearch・Meilisearch が日本語をどう扱うか、エンジンの版の機能と平文の問い合わせの渡し方（要検証。各バックエンドの Issue で確かめる）。
- Cloud Run と AWS の実行基盤のリクエストのログがクエリ文字列を含むか（要検証）。運営者の文書（`docs/operations/search.md` の「The query appears in URLs」）は、問い合わせが URL に載ることを伝え、前段の層ごとにログを確かめるよう勧めている。確かめていないのは、その 2 つの実行基盤の既定のログに何が残るかだけである。
- レート制限の 30 / 5 分は仮の値で、最初の運用で調整する。
