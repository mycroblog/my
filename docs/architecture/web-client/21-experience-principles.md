## 21. 体験の原則

画面を設計・実装・レビューするときの原則です。根拠は [ADR-0110](../../adr/0110-web-experience-principles.md)、見た目の言語は ADR-0111、見え方の一覧は ADR-0112 です。
UI を変える issue は、この節と、その画面の要件（[screens/](screens/README.md)）に従います。

### 21.1 原則と優先順位

原則がぶつかったときは番号の小さい方を取る。

| # | 原則 | やること | やらないこと |
| --- | --- | --- | --- |
| P1 | **迷わない** | 画面ごとに主な操作を 1 つにする。要約を先に、詳しい内容をその後に見せる。主要な情報と補助の情報を分け、関係するものをまとめる。1 つの画面の保存の仕方は 1 つ（すぐ保存か、まとめて保存か） | 楽しさのために導線・境界・文言を弱める |
| P2 | **操作に必ず応える** | 押した直後に見た目が反応する。処理中・成功・失敗を、操作した場所に小さな動き（マイクロインタラクション）で出す。動きの長さと緩急はトークンから選ぶ。`prefers-reduced-motion` のときは、色と形の変化で応える | 反応を読み上げだけで伝える。結果を操作した場所から離れた所にだけ出す。待たせるための演出 |
| P3 | **形で先に伝える** | 状態はバッジとアイコンの形で、数と推移は図で示す。アイコンには文言を添える（G12）。1 つの区画の文字と操作の量に上限を設ける | 説明文を並べて終える。アイコンだけで意味を当てさせる |
| P4 | **同じ意味は同じ見た目と動き** | 新しい見た目は、まず `@my/ui` のパターンの部品として作り、画面はそれを使う | 似た部品を画面ごとに作る。機能の中で部品を複製する |

### 21.2 動きの性格（P2）

- 普段は静かで素早く応える。すべての反応は 100〜200 ms で、既存のトークン（`--transition-duration-fast` 100 ms、`--transition-duration-normal` 200 ms、`--ease-standard` / `--ease-enter` / `--ease-exit`）だけを使い、行き過ぎ（オーバーシュート）をさせない。
- 少しだけ弾むのは、祝う価値のある数か所に限る（例: 最初の投稿、お気に入り、設定の手順の完了）。新しく足すときは、その場面を P2 の例外として PR に書く。
- 動きはすべて `motion-safe:` の下に書く。`prefers-reduced-motion` のときは、色・形・文言の変化で同じ結果を伝える。
- 動きで伝える結果は、必ずほかの手がかり（文言・アイコン・`role="status"`）でも伝える（§5）。

### 21.3 4 観点（レビューのチェックリスト）

UI の PR は、次の 4 観点で点検する。各観点は、画面の要件（L1）・部品（L2）・機械検査（L3）のどこで効かせるかが決まっている。

| 観点 | 問い | 見る場所 |
| --- | --- | --- |
| シグニファイア | 主な操作が 1 つに見え、押せるものが押せるように見えるか。保存の仕方（すぐか、まとめてか）が見て分かるか | 主な操作と保存の仕方（L1 の 4）、主な操作の部品 |
| フィードバック | 操作の直後に、操作した場所で結果（処理中・成功・失敗）が見えるか。動きなしでも分かるか | 操作ごとの結果（L1 の 5）、保存の状態の部品 |
| UX ライティング | 画面が次の行動を示しているか。ボタンは動詞か。エラーは直し方を言うか | `client*` のカタログ、§16 の文言の規約 |
| 情報設計 | 要約が先で詳細が後か。関係するものがまとまり、`h2` の順が優先順位どおりか。導線に迷わないか | 情報の優先順位とまとまり（L1 の 3）、入口と出口（L1 の 6） |

### 21.4 5 つの層

| 層 | 中身 | 効かせ方 |
| --- | --- | --- |
| L1 画面の要件 | [screens/](screens/README.md) の画面ごとの文書 | UI の issue を `agent:ready` にする条件 |
| L2 パターンの部品 | 判断を型で強制する `@my/ui` の部品 | 画面（`app/web`）は L2 の部品で組む。足りなければ `@my/ui` に足す |
| L3 機械検査 | ARIA スナップショット・部品のテスト・lint・文言のカタログ | E2E・部品のテスト・Oxlint・`i18n:check` |
| L4 課題テスト | L1 の作業を ARIA のツリーだけで行い、手数と lostness を測る | nightly が main に対して行い、0.4 を超えた作業を画面ごとの issue にする（ADR-0114）。PR は作業ごとの最短の手順を書く（[workflow §5](../../agents/workflow.md#5-verify)） |
| L5 人の批評 | main の一覧（ADR-0112）を決定者が見て issue にする | merge の後（[workflow §7](../../agents/workflow.md#7-merge-through-the-merge-queue)） |

L3 のうち、今ある検査は次のとおり。

- **送信ボタンのある `form` の中のスイッチ**: `Switch` はすぐ効く操作の部品なので、送信ボタンで保存する `form` の中では `Checkbox` を使う。
  `@my/ui/testing` の `watchSwitchesInSubmitForms` が、`app/web` の各テスト（`src/test/setup.ts`）の描いたもの（途中で開いて閉じたダイアログも含む）を見て、
  送信ボタンを持つ `form`（`form=` で外から結び付いたボタンも含む）の中に `role="switch"` があればそのテストを失敗させる。
- **まとまりのあるメニュー**: 設定のメニューと管理のモードのメニューは `@my/ui` の `NavMenu` で組み、まとまりごとに見える見出しを持ち、すべての項目にアイコンを持ち、
  1 つのまとまりの項目は 7 個までにする（ADR-0110 §5・§6）。`@my/ui/testing` の `watchNavMenus` が、`app/web` の各テストの描いた `NavMenu` を見て、
  アイコンのない項目か 8 個以上の項目を持つまとまりがあればそのテストを失敗させる。機能の部品が `RailItem` で項目を並べることは、`restrict/pattern` が禁じる。
  アプリのナビゲーション（レールとメニューのシート）は、運営の領域（モデレーション・管理）の前に線を引き、利用者の項目と分ける。
- **読み上げだけの結果**: 機能のフックと部品は `useAnnouncer` を呼ばず、結果の見える置き場を言う `@my/ui` の `useNotice`（`inPlace` か `toast`）を使う（Oxlint の `restrict/feature`、§16 の G25）。すぐ保存する操作は `AutosaveControl` の必須の `state` で保存の状態を受け取る（G24）。

### 21.5 祝う場面

§21.2 の弾む動きを使ってよいのは、次の場面だけである。画面は自分で弾む動きを作らず、ここに足すときは PR で決定者に諮る。

| 場面 | 合図 | 部品 | 状態 |
| --- | --- | --- | --- |
| お気に入りを付けた | 投稿の操作の帯のお気に入りを、本人が押してオンにした直後 | `ToggleButton` の `celebrate`（`StatusActions` のお気に入り） | 実装済み |
| 最初の投稿 | アカウントの最初の投稿が送れた直後 | `useCelebration` | 未実装。クライアント API がアカウントの投稿の数を返していないため、返すようになってから付ける |
| 設定の手順の完了 | 最初の設定（オンボーディング）の手順を終えた直後 | `useCelebration` | 未実装。オンボーディングの画面（#1654・#1687）が付ける |

- 動きは 1 つだけ: `@my/ui` の `celebration.ts`（`useCelebration` と `celebrationClasses`）で、要素が `data-celebrating` の間（600 ms）、そのアイコン（子の `svg`）が `animate-celebrate`（`duration-slow`、少し行き過ぎる `--ease-celebrate`）で小さい大きさから入る。
  `--ease-celebrate` はこの動きだけに使い、普段の反応には使わない。サーバーのテーマはほかの緩急と同じく上書きできる（ADR-0059）。
- 動きは `motion-safe:` の下にだけある。`prefers-reduced-motion` のときは何も動かず、同じ間だけ要素が `soft` の塗りになる（色の変化）。場面そのものが形と色を変える（星が塗られる）ので、塗りはその上に足すだけである。
- 祝うのは本人の操作の直後だけで、読み込んだときにすでにオンのもの、オフにする操作、ほかの人の操作の通知では祝わない。結果はいつもどおり文言とアイコン（`aria-pressed`、`useNotice`）でも伝える。
