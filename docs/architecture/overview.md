# アーキテクチャ概要（主要フロー）

部品が 1 つの操作の中でどうつながるかをまとめます。構造の決定は [ADR-0002](../adr/0002-modular-monolith-hexagonal.md)、各モジュールの責務は `internal/app/<module>` のパッケージの説明、ジョブの広がりは [ジョブの全体像](job-system.md) にあります。

## 1. ローカル投稿 → 連合配送

1. クライアント API の投稿作成がユースケースを呼び、ドメインが文字数・公開範囲・メンションを検証して投稿を作る。
2. **1 回のトランザクション** で投稿と付随の行を書き、同じトランザクションの同期の投影が、送るアクティビティ（`Create`）と `federation.fanout` のジョブを書く（Transactional Outbox）。
3. コミットした分だけがワーカーに見える。Cloud Tasks のキューでは、コミットの後にジョブの ID の合図を送る（ADR-0004）。
4. `federation.fanout` は文書を 1 回だけ組み立て、公開範囲に応じて宛先を 500 件ずつ算出し（`local` はリモートのフォロワーだけ）、**shared inbox 単位** の配送ごとに `federation.deliver` を積む。
5. `federation.deliver` が署名付きで POST する。失敗はバックオフで積み直し、続けて失敗するドメインは一時停止する。

## 2. Inbox 受信

1. shared inbox か actor の inbox（ADR-0018）に `POST` が届く。
2. 同期の処理: サイズの制限 → 署名の検証（鍵は KV / DB のキャッシュ、なければ取得）→ ドメインブロックの判定 → `202 Accepted`。
3. `federation.inbox`（活動と検証済みの actor）を積む。
4. ワーカーが活動の種類ごとのハンドラを動かし（活動の ID で重複を捨てる）、通知などを作る。

## 3. リアルタイム更新（SSE）

1. コマンドのトランザクションがコミットされると、コミットのフックがそのトランザクションで発行したイベントを受け取る。
2. `timeline` のフックは新しい投稿・ブーストの ID を、`notification` のフックは通知を受け取りうるアカウントを、ストリームの発行者に知らせる。知らせるのは「何が変わったか」だけで、内容は載せない。
   ローカル・連合のタイムラインに載りうる投稿は、載りうるタイムラインを添えた「公開のタイムラインの新着」としても知らせる（ADR-0013 §20）。
3. ストリーミングの各接続は自分のアカウントを購読し、知らせを受けるたびにユースケースで読み直す。ホームに載るかはホームのタイムラインと同じ条件と `CanView`、通知は前回送ったものより新しい通知の一覧で決める。
4. 結果を SSE のイベント（`update` は投稿、`notification` は通知）として送る。
5. 公開のタイムラインのストリームの各接続はそのタイムラインを購読し、REST の同じタイムラインと同じ条件と `CanView`、閲覧者のタイムラインの言語で載るかを決める。

- 知らせをプロセスの間で運ぶブローカーと、その意味（at-least-once、遅延 listen、取りこぼしたら購読を終える）は ADR-0050 が決める。
- 配信は best effort で、再送しない。クライアントは再接続したらホームと通知を読み直す。
- 読み取りの回数は「新しい投稿数 × 接続数」に比例する。ホームの新着は接続中の利用者ごとに 1 回、公開のタイムラインの新着はそのストリームを開いている接続ごとに 1 回読む。
