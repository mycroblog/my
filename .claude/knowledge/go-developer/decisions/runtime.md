`- <decision> — <why> — <from: the decider's correction or choice> — <YYYY-MM-DD> — held N / missed N`.

- What can be worked out once at build time (an embedded asset's ETag) is worked out at build time and shipped in the binary, never by reading the embedded files at startup; the web build stays embedded — reading the build for its ETags held about 110 MB of idle memory — the decider's choice of keeping the embed with build-time ETags over serving from disk (#3152, #3156, #3158), session 28c4aedc 2026-11-17 — 2026-11-17 — held 0 / missed 0
- A connection pool's size defaults from the processor count (GOMAXPROCS), and its size and the idle connections it keeps can be set by configuration — a fixed size fits only the machine it was measured on, and a pool that drops its idle connections reconnects after every quiet spell — the decider's corrections on the SQLite pool (#3177, #3181), session 28c4aedc 2026-11-17 — 2026-11-17 — held 0 / missed 0
- A periodic job reads only the work that is due: record each item in a table of due work (a due time with an index on (due_at, id)) when it arises, delete the row when done and move it forward when it must wait, never scan a table that only grows (tombstones, events) each run — a run's cost must depend on the work due, not on the rows kept — the decider's rejection of the hourly scan of status_deletions in the purge of deleted statuses (#2937) — 2026-11-21 — held 0 / missed 0
- What an alert needs per process under metrics_exporter = none rides on the line that ends each unit of work (kernel.LogUnit through a LineMeter), never on a timer or the snapshot line, and a process-wide total goes as its increase since the previous line by a compare-and-swap of the last total, so the lines sum exactly — Cloud Run gives no CPU between requests, and the snapshot line is written by whichever process runs the job — the decider's choice for the adapter and pool alerts (#3423) — 2026-11-23 — held 0 / missed 0
