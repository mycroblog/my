# エラーの報告

サーバーが自身のバグや障害をどのように知らせるか、各プラットフォームでその報告をどこで読むか、そして報告をエラートラッカーに送る方法を説明します。
メトリクスは何かがおかしいことを教えてくれます。エラーの報告は、何が失敗したのかをスタックとともに教えてくれます。すべての設定は[設定リファレンス](../reference/configuration.md)にあります。

何を設定していても、すべての報告に次の 3 つのことが起こります。

1. スタックを含む `error report` の行が 1 行、標準エラー出力に出ます（[ログの行](#the-log-line)）。
2. 報告はデータベースのエラーグループに数えられます。管理画面にグループが表示され、`manage_errors` の権限を持つ人には、新しいグループと再発したグループが通知されます（[エラーグループと通知](#error-groups-and-notifications)）。
3. `errors_exporter` を設定すると、報告は外部のサービスにも送られます（[報告をサービスに送る](#sending-reports-to-a-service)）。

`errors_exporter` を設定しない限り、サーバーの外には何も出ていきません。

<!-- source: what-is-reported 8e5ac9d14c36 -->
## 報告されるもの

| 報告されるもの | 報告されないもの（メトリクスとほかのログの行で分かります） |
| --- | --- |
| HTTP ハンドラー、ジョブ、バックグラウンドタスクでのパニック | 4xx の応答（不正な入力、認可、レート制限）とメンテナンスモード |
| クライアント API、管理 API、サインインのページ、ActivityPub、OAuth、メディアが 5xx を返した原因のエラー | クライアントが接続を切ったリクエスト |
| 最終的に失敗したジョブ（`dead`） | ジョブの再試行。再試行を使い切ったときに報告されます |
| 起動の失敗: 不正な設定、またはセットアップできないデータベースやアダプター | 失敗したレディネスチェック |
| Web クライアントが処理しなかったエラー。ブラウザーからサーバーに送られます | ほかのサーバーが原因の失敗: 配送の再試行と断念、拒否された署名、失敗したリモートの取得 |
| | ブラウザー自身のノイズ: 切れたネットワーク、ブラウザー拡張機能からのエラー、新しいデプロイで消えたチャンク |

外部サービス（メール、ストレージ、決済、音声）の障害は、それによってジョブが最終的に失敗したか、リクエストが 5xx を返したときにだけ報告されます。一時的な障害は、代わりに `my.adapter.*` のメトリクスに表れます（[サーバーの運用](running.md#metrics)）。

バックグラウンドタスクでのパニックは、報告されたあとにプロセスを停止させます。そのため、サーバーが壊れた状態のまま動き続けることはありません。プロセスはプラットフォームが再起動します。

## ログの行

この行は `msg` が `error report`、`level` が `ERROR` です（障害がプロセスを停止させるときは `severity` が `CRITICAL` になります）。
そのフィールドと、スクラブがそれらに何をするかは、[サーバーの運用](running.md#error-reports)にあります。要点は次のとおりです。

- `my.error.fingerprint` は、同じエラーならどの発生でも同じ値です。これで検索したり、まとめたりしてください。
- `my.error.where` は発生した場所を示します。たとえば `client_api GET /api/v1/statuses/{id}` です。
- `request_id`、`job_id`、`trace_id`、`span_id` で、同じリクエストやジョブのほかの行を見つけられます。
- `message` は行の最後にあり、エラーの型とメッセージ、改行、Go のスタックが入ります。

スタックを含む行はほかにありません。

<!-- source: google-cloud-cloud-run 925c99683713 -->
### Google Cloud (Cloud Run)

Cloud Error Reporting は、何も設定しなくてもこの行を読み取り、コンソールの Error Reporting にエラーを一覧表示します。無料で、料金がかかるのは Cloud Logging だけです。

- エラーは型とスタックの上位のフレームでまとめられます。サーバーのフィンガープリントは使えないため、Error Reporting のグループが管理画面のグループと異なることがあります。
- グループは 30 日間保持され、新しいエラーと、解決済みのエラーが再発したときに通知されます。通知はプロジェクト全体で 1 時間に最大 20 件です。通知チャネルは Google Cloud コンソールで設定してください。
- 報告の前後に何が起きたかを調べるには、Cloud Logging で `jsonPayload."request_id"="<id>"`、または同じ形で `trace_id` を検索します。

<!-- source: aws 6ca6594afd7e -->
### AWS

CloudWatch Logs は、この行をただの JSON として読み取ります。

- ロググループのログ異常検出をオンにしてください。これまでに見たことのない行のパターンを検出し、SNS にアラームを送れます。読み取るのは行の先頭 1,500 文字だけで、`message` が最後のフィールドになっているのはこのためです。解決済みの状態は保持しません。
- 報告を数えるには、`{ $.msg = "error report" }` のようなメトリクスフィルターを作ります。`my.error.fingerprint` から取ったディメンションは使わないでください。ディメンションの値ごとに、それぞれ別のメトリクスとして課金されます。`my.error.source` と `my.error.kind` は問題ありません。
- 前後の状況は Logs Insights で調べます: ``filter `request_id` = "<id>"``。

<!-- source: self-hosted 90de7a419474 -->
### セルフホスト

行はコンテナのログから読みます: `docker compose logs my | jq -c 'select(.msg == "error report")'`。
`metrics_exporter = prometheus` のときは、報告が急に増えるとアラート `MyErrorReportsIncreasing`（[アラートと対応手順](alerts.md#myerrorreportsincreasing)）が警告します。その元になるカウンターは `my.errors.reported` です。
外部のサービスを必要としない通知には、管理画面と後述の Webhook を使ってください。トラッカーを使うなら [`errors_exporter`](#sending-reports-to-a-service) を使います。

## エラーグループと通知

サーバーは報告をフィンガープリントごとにデータベースで数えます。設定も追加のサービスも不要で、書き込みもわずかです。あるフィンガープリントの最初の報告はすぐに書き込まれ、その後の報告はメモリー上で合計されて 1 分に 1 回書き込まれます。プロセスを強制終了すると直近 1 分間の件数が失われることがありますが、ログの行はそれで失われることはありません。
90 日より古い件数は毎日削除されます。失敗したのがデータベースそのものであれば、報告はログの行にだけ残ります。

<!-- source: the-administration-screen 09092782a7c1 -->
### 管理画面

ロールに `manage_errors` がある人（組み込みの `admin` ロールにはあります）には、管理メニューに「エラー」（`/admin/errors`）が表示されます。

- 一覧にはグループが表示され、既定では未解決のものが表示されます。状態（未解決、解決済み、ミュート中、すべての状態）と発生元（サーバー、Web クライアント）で絞り込めます。各行には、エラーの型、発生した場所、メッセージの最初の数行、直近 24 時間と 7 日間の件数、最初と最後の日時とバージョンが表示されます。
- グループのページには、最新の発生（日時、バージョン、プロセスのロール、リクエスト ID、トレース ID、型、メッセージ、スタック）、直近 90 日間の 1 時間ごとの発生件数、状態の変更履歴が表示されます。リクエスト ID とトレース ID には「コピー」ボタンがあるので、ログの検索に貼り付けてください。
- 「解決にする」は、修正したエラーに使います。別のバージョンのサーバーで再発すると、グループは再び開いて、もう一度通知します。解決したときのバージョンで同じエラーが起きても数えられるだけなので、古いバージョンに残った最後のリクエストでグループが再び開くことはありません。
- 「ミュート」は件数を数え続けますが、通知も Webhook のイベントも送りません。「ミュートを解除」でグループは再び開きます。

同じ操作は `GET /api/v1/admin/error_groups` と `POST /api/v1/admin/error_groups/{id}/resolve`（`/mute`、`/unmute`）でも行えます。

<!-- source: notifications-and-webhooks 99836c7f02ec -->
### 通知と Webhook

- `manage_errors` を持つ人は、新しいエラーグループと再発のときに通知 `admin_error_group` を受け取ります。通知はサーバー全体で 1 時間に最大 10 件で、その時間の残りは、さらにエラーが報告されたことを伝える 1 件の通知にまとめられます。メールでも受け取れます（[モデレーション](moderation.md#notifications-for-moderators-and-the-pending-counts)）。
- Webhook のイベント `error_group.created` と `error_group.regressed` は同じグループを運ぶので、Slack や Discord、自動化ツールに送れます（[サーバーの Webhook](webhooks.md)、[Webhook リファレンス](../reference/webhooks.md)）。Webhook には `manage_webhooks` が、イベントには `manage_errors` が必要です。
- ミュートしたグループが通知することはありません。

<!-- source: errors-from-the-web-client e5b2f45b62be -->
### Web クライアントからのエラー

Web クライアントは、画面が処理しなかったエラーを自分のサーバーの `POST /api/v1/client_errors` に送ります。そのため第三者に見られることはなく、コンテンツセキュリティの設定も変わりません。サーバーはすべてに `204` を返し、受け付けないものは捨てます。受け付けないのは、16 KiB を超える本文、自分の Web クライアントのファイルを含まないスタック、1 つの IP アドレスから 1 分間に 10 件を超える報告です。同じエラーはページの表示ごとに 1 回だけ送られ、ページの表示ごとに最大 20 件です。
サインインしたセッションなしに送られた報告は、数えられてログに記録されますが、それだけでは誰にも通知しません。そのため、匿名のスクリプトが受信箱を埋め尽くすことはできません。サインインしている人のブラウザーも同じエラーを報告すると、グループが通知します。
スタックはミニファイされたビルドのもので、ソースには戻されません。まずルートとメッセージを読んでください。リリースは、そのページを配信したサーバーのバージョンです。オフラインで開いたページや、3 秒待っても応答がなかったページはブラウザーのコピーから表示され、ブラウザーが Web クライアントを保存したときのバージョンを名乗ります。つまり、Web クライアントが同じ、より古いバージョンです。

## 報告をサービスに送る

`errors_exporter` を設定すると、各報告をエラートラッカーにも送ります。ログの行とデータベースのグループはそのまま残ります。報告は 1 回だけ送られ、再試行されることはなく、サービスを待つ処理もありません。

| 値 | 送り先 |
| --- | --- |
| `none`（既定） | どこにも送らない |
| `sentry` | `errors_sentry_dsn` にある Sentry 互換の任意のサービス |
| `otlp` | OpenTelemetry のコレクターまたはバックエンド。ログレコードとして送ります |

`errors_environment`（既定は `production`）は、すべての報告にデプロイメントの名前を付けます。たとえば `staging` です。

どちらのエクスポーターも、ログの行と同じスクラブ済みのフィールドを、フィンガープリントとトレース ID・スパン ID とともに送ります。ホストについての情報は何も送りません。ホスト名、IP アドレス、ユーザー、リクエストの本文、ヘッダー、Cookie は含まれません。

サーバーは、サービスに大量の報告が押し寄せないよう、送る量を制限します。

- 同じフィンガープリントはプロセスごとに 1 分に最大 1 回、すべての報告を合わせて 1 分に最大 60 件まで送ります。残りはログとグループに残ります。
- 送信を待つ報告は最大 1,000 件です。キューがいっぱいのときに来た報告は捨てられます。サーバーが停止するときは、キューが空になるまで最大 2 秒待ちます。
- サービスが `429` を返したり、速度を落とすよう求めたりしたとき（`Retry-After`、`X-Sentry-Rate-Limits`）は、サーバーはその間送信を止めます。
- DSN のキーと報告がほかの場所に渡らないよう、サーバーはサービスからのリダイレクトに従いません。リダイレクトは `failed` として数えられます。サービスが表示する DSN を使ってください。その DSN は受け付け口そのものを指しています。

カウンター `my.errors.exported` を監視してください。`my.outcome` は `success`、`dropped`（制限を超えた、キューがいっぱいだった、またはサービスが速度を落とすよう求めた）、`failed`（サービスに到達できなかった、またはサービスが報告を拒否した）のいずれかです（[サーバーの運用](running.md#metrics)）。

<!-- source: sentry-glitchtip-and-datadog 12c935ec3c05 -->
### Sentry、GlitchTip、Datadog

```sh
MY_ERRORS_EXPORTER=sentry
MY_ERRORS_SENTRY_DSN_FILE=/run/secrets/sentry_dsn   # or MY_ERRORS_SENTRY_DSN; the DSN is a secret
```

サーバーは Sentry のプロトコルを自分で話すので、Sentry SDK は使われず、`SENTRY_*` の環境変数も読みません。サーバーはフィンガープリントを設定するので、サービスはそれでまとめます。また、タグ `service`（`my`）、`my.role`、`my.error.where`、`error.fingerprint` を設定します。リリースはサーバーのバージョンで、環境は `errors_environment` です。

- **Sentry**（ホスト型またはセルフホスト）: プロジェクトのクライアントキーから DSN をコピーします。
- **GlitchTip**: プロジェクトの DSN をコピーします。オープンソースで、小さなサーバーで動きます。新しい issue と再発した issue に対して、お使いのバージョンがどのアラートルールを提供しているか確認してください。
- **Datadog Error Tracking**: お使いの Datadog サイトの Sentry DSN、`https://<DD_API_KEY>@sentry-intake.<DD_SITE>/1` を使います。Datadog には `service` タグが必要ですが、サーバーは常にこれを設定します。Datadog はこれらのイベントをログとして保存し、Error Tracking でまとめます。代わりにエージェントやフォワーダーでログの行を Datadog に送る場合（Error Tracking for Logs）、スタックは `message` に入っています。ログパイプラインでこれを `error.stack` に割り当ててください。そうしないと Datadog はこれをスタックとして認識しません。`sentry` のエクスポーターには、このような割り当ては必要ありません。

<!-- source: otlp-backends 778540dabdc8 -->
### OTLP のバックエンド

```sh
MY_ERRORS_EXPORTER=otlp
OTEL_EXPORTER_OTLP_ENDPOINT=http://collector:4318   # or OTEL_EXPORTER_OTLP_LOGS_ENDPOINT
OTEL_EXPORTER_OTLP_HEADERS=authorization=Bearer%20...
```

各報告は `exception` という名前の OpenTelemetry のログレコードで、重大度 `ERROR`（プロセスを停止させるときは `FATAL`）、`exception.type`、`exception.message`、`exception.stacktrace`、`my.error.fingerprint`、`my.error.where`、`my.error.source`、`my.error.kind`、トレース ID とスパン ID を持ちます。メトリクスやトレースと同じリソースで、OTLP/HTTP（protobuf、gzip）で送られます。

これらのレコードがまとめられたエラーになるかどうかはバックエンドによります。トレースのデータだけからエラーの画面を作るバックエンドもあり、Datadog には `error.stack` が必要です。Sentry、GlitchTip、Datadog には `sentry` を使ってください。ほかのログと並べてレコードを置きたいときに `otlp` を使います。ビルドタグ `no_otel` を付けると `otlp` は含まれません（[ビルドタグ](../reference/build-tags.md)）。

## スクラブが保証すること、しないこと

スクラブは報告が作られるときに 1 回だけ行われます。そのため、ログの行、データベース、すべてのエクスポーターが受け取るのはスクラブ済みのテキストだけです。

- メッセージの中の URL、メールアドレス、`@user@host` 形式のハンドル、IP アドレス、UUID と ULID、10 桁以上の数字は、それぞれ `<url>`、`<email>`、`<acct>`、`<ip>`、`<id>`、`<n>` に置き換えられ、メッセージは 1 KiB に切り詰められます。
- スタックの中の関数の引数の値は `(...)` に置き換えられ、スタックは 16 KiB に切り詰められます。ファイルの位置はソースツリーからの相対パスで残るので、ビルドしたマシンのパスは表れません。
- どの報告にも、リクエストの本文、ヘッダー、クエリー、Cookie、アカウント ID、ユーザー名、IP アドレス、User-Agent は含まれません。

スクラブはパターンに一致するものを置き換えるだけなので、メッセージに個人データが含まれないことは保証しません。エラーメッセージが引用した名前、自由記述のテキスト、10 桁未満の数字は残ることがあります。通常の `http request` と `job` の行の `error` フィールドは、このようにはスクラブされません。ログとエラートラッカーは、ユーザーのコンテンツの断片を含むかもしれない場所として扱い、ほかのログと同じアクセス制御と保持期間を適用してください。`errors_exporter` を設定したら、報告にはそのサービスの保存場所、保持期間、アクセスのルールが適用されます。
